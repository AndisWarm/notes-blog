07 内存管理进阶：fork、malloc 与内存回收¶

本章覆盖：fork 复制了什么、写时复制（Copy On Write）、malloc 1KB vs 1MB、brk 与 mmap、内存不足时发生什么、页面置换算法。

本章是"内存管理"的深水区，面试常考。建议先把第 1-2 节（fork + 写时复制）和第 3-4 节（malloc/brk/mmap）搞清楚，页面置换算法（第 6 节）是经典考点。

1. fork() 会复制哪些东西？¶

一句话回答¶

fork 阶段复制父进程的页表（虚拟内存）；fork 之后，如果发生写时复制，才会复制物理内存。

展开讲¶

fork 时：
  复制父进程的「页表」（虚拟地址 → 物理地址的映射关系）
  不复制物理内存！父子进程的虚拟空间不同，但物理空间是同一个

fork 之后：
  只有父子进程某一方写入时，才触发写时复制，复制物理内存

如果 fork 时直接复制全部物理内存，大进程 fork 会非常慢（内存越大越慢），所以操作系统用"先共享、写时才复制"的策略（详见第 2 节）。

2. 介绍 copy on write（写时复制）¶

一句话回答¶

fork 时父子进程共享同一份物理内存（只复制页表，不复制物理内存），并把这些页标记为只读；一旦某一方发生写操作，CPU 触发写保护中断，操作系统才复制物理内存并重新设置映射——这就是"写时复制"。

完整流程¶

步骤1：fork
  操作系统复制父进程的页表给子进程
  不复制物理内存 → 父子进程共享同一份物理内存
  页表项标记该物理内存权限为「只读」

步骤2：某一方写入
  父进程或子进程向这块内存发起写操作
  → CPU 触发「写保护中断」（违反只读权限导致）

步骤3：写保护中断处理
  操作系统复制这块物理内存
  重新设置映射关系：父子进程各自的物理内存权限改为「可读写」

步骤4：继续写操作
  中断处理完毕，执行真正的写操作

为什么要这么做？¶

  • 防止 fork 创建子进程时，物理内存复制时间过长导致父进程长时间阻塞
  • 很多子进程 fork 后立刻 exec（换程序），根本用不上复制的数据——写时复制避免了白白复制
  • 节约物理内存资源

3. copy on write 节省了什么资源？¶

一句话回答¶

节省了物理内存资源：fork 时子进程不用复制父进程的物理内存，只需复制页表，父子进程页表指向同一份共享的物理内存；只有某一方真正修改时，才复制被修改的那部分物理内存。

关键点¶

时间点 复制了什么 是否复制物理内存
fork 时 页表（虚拟内存） ❌ 不复制
第一次写入时 被修改的那块物理内存 ✅ 才复制

面试金句："写时复制的精髓是'延迟复制、按需复制'——把复制操作从 fork 时刻推迟到真正需要的时刻。"

4. malloc 1KB 和 1MB 有什么区别？¶

一句话回答¶

malloc 源码里有一个默认阈值（约 128 KB）：小于 128 KB 用 brk() 申请内存，大于 128 KB 用 mmap() 申请内存（不同 glibc 版本阈值可能不同）。

区别总结¶

分配大小 使用的系统调用 分配区域
< 128 KB brk() 堆
> 128 KB mmap() 文件映射区

5. 介绍一下 brk 和 mmap¶

一句话回答¶

malloc 不是系统调用，而是 C 库函数；它向操作系统申请内存有两种方式：brk() 把堆顶指针往高地址移动（在堆上分配），mmap() 通过私有匿名映射在文件映射区"偷"一块内存。

方式一：brk()（堆分配）¶

  • 通过 brk() 函数将「堆顶」指针向高地址移动，获得新的内存空间
  • 特点：小块内存分配，释放后不还给操作系统（内存池化管理，下次 malloc 直接复用）
  • 适合小块、频繁分配的场景
堆顶 ──▶（brk 移动堆顶）──▶ 新空间
[ 旧堆 ] [  新分配的堆内存  ]

方式二：mmap()（文件映射区分配）¶

  • 通过 mmap() 系统调用的「私有匿名映射」方式，在文件映射区分配一块内存
  • 特点：大块内存分配，释放时直接归还操作系统（mmap 内存独立，free 后真正释放）
  • 适合大块、不频繁分配的场景
文件映射区： [  偷来的内存（私有匿名映射）  ]

为什么分成两种？¶

对比项 brk() mmap()
分配区域 堆 文件映射区
分配大小 小（<128KB） 大（>128KB）
释放行为 不立即还系统，留在堆里复用 立即归还操作系统
碎片问题 多次分配释放可能产生碎片 无堆碎片问题

6. 操作系统内存不足的时候会发生什么？¶

一句话回答¶

程序 malloc 时只拿到虚拟内存（不分配物理内存）；真正读写时才触发缺页中断去分配物理内存。物理内存不够时，内核先回收内存（后台 kswapd 异步回收 / 直接回收同步阻塞），还不够就触发 OOM Killer 杀掉占用内存多的进程。

完整流程¶

malloc 申请内存 → 只分配虚拟内存（不分配物理内存）
      │
      ▼
程序读写这块虚拟内存 → CPU 发现没有映射到物理内存 → 产生缺页中断
      │
      ▼
缺页中断处理（用户态切到内核态）
      │
      ├── 有空闲物理内存 → 直接分配，建立映射 ✅
      │
      └── 没有空闲物理内存 → 开始回收内存：
              ├── 后台内存回收（kswapd 内核线程）→ 异步，不阻塞进程
              ├── 直接内存回收（direct reclaim）→ 同步，阻塞进程
              │
              └── 回收后还不够 → 触发 OOM 机制
                      └── OOM Killer 选一个占用物理内存高的进程杀掉
                          还不够 → 继续杀，直到释放足够内存

哪些内存可以回收？怎么回收？¶

内存类型 是什么 回收方式
文件页 内核缓存的磁盘数据（Buffer）和文件数据（Cache） 干净页直接释放；脏页先写回磁盘再释放
匿名页 没有文件载体的内存（堆、栈数据） 通过 Swap 机制写到磁盘后释放，再次访问时读回

LRU 回收算法¶

文件页和匿名页的回收都基于 LRU 算法（优先回收不常访问的内存），维护两个双向链表： - active_list：最近被访问过的（活跃）内存页 - inactive_list：很少被访问的（非活跃）内存页

越接近链表尾部越不常访问，回收时优先回收不活跃的内存。

7. 页面置换有哪些算法？¶

一句话回答¶

当缺页且内存已满时，需要选择被置换的物理页面换出。常见算法：OPT（最佳）、FIFO（先进先出）、LRU（最近最久未使用）、Clock（时钟）、LFU（最不常用）。OPT 是理论标杆无法实现，实际系统中 Clock 是优化后的折中方案。

五种算法逐个讲¶

① 最佳页面置换算法（OPT） - 思路：置换在「未来」最长时间不访问的页面 - 需要预知未来访问顺序——实际系统中无法实现 - 作用：作为衡量标准——你的算法效率越接近 OPT，说明越高效

② 先进先出置换算法（FIFO） - 思路：选择在内存驻留时间最长的页面置换（先来先换） - 简单但性能差，比 OPT 差很多（示例中缺页 10 次 vs OPT 7 次）

③ 最近最久未使用置换算法（LRU） - 思路：发生缺页时，选择最长时间没有被访问的页面置换 - 用「历史」使用情况推测「未来」——近似最优（示例中缺页 9 次） - 缺点：为了完全实现 LRU，每次访问都要更新整个链表（找到、删除、移到表头）——开销太大，实际应用少

④ 时钟页面置换算法（Clock） - 思路：既优化置换次数，又方便实现——LRU 的近似 + FIFO 的改进 - 实现：所有页面放在环形链表（像钟面），表针指向最老的页面 - 缺页时检查表针指向的页面： - 访问位是 0 → 淘汰该页，新页插入这个位置，表针前移 - 访问位是 1 → 清除访问位（给它"第二次机会"），表针前移，继续检查

表针 ──▶ 页面A(访问位0) → 淘汰 A，插入新页 ✅
表针 ──▶ 页面B(访问位1) → 清除访问位 → 表针前移
表针 ──▶ 页面C(访问位0) → 淘汰 C，插入新页 ✅

⑤ 最不常用置换算法（LFU） - 思路：发生缺页时，选择「访问次数」最少的页面淘汰 - 实现：每个页面一个访问计数器，被访问 +1，缺页时淘汰计数最小的 - 缺点： - 硬件成本高（每个页要计数器） - 查找最小计数遍历链表，耗时 - 只考虑频率、不考虑时间：过去高频、现在不用的页面不会被淘汰，反而误伤"刚开始频繁访问但次数还不高"的页面 - 改进：定期把访问次数减半（时间中断时除以 2），让"过气"页面加大被置换概率

算法速查表¶

算法 淘汰依据 能否实现 缺点
OPT 未来最久不访问 ❌（理论标杆） 需要预知未来
FIFO 驻留时间最长 ✅ 简单 性能差
LRU 历史最久未访问 ✅ 但开销大 每次访问更新链表
Clock 访问位 + 环形链表 ✅ 折中 近似 LRU
LFU 访问次数最少 ✅ 但成本高 不看时间、误伤新页面
