# 03 存储引擎

本章覆盖：一条 SQL 的执行过程、MySQL 引擎介绍、为什么 InnoDB 是默认引擎、InnoDB 与 MyISAM 的区别、数据文件的分类。

---

## 1. 执行一条 SQL 请求的过程是什么？

### 一句话回答
一条 SQL 从客户端发出到最后返回结果，要经过：**连接器 → 查询缓存（8.0已删除）→ 解析器 → 优化器 → 执行器 → 存储引擎**。

### 完整链路图（背下来）

```
客户端
  │ SQL 语句
  ▼
① 连接器      负责建立连接、校验用户名密码、权限
  ▼
② 查询缓存    命中直接返回（MySQL 8.0 已删除该模块）
  ▼
③ 解析器      词法分析 + 语法分析 → 生成语法树
  ▼
④ 优化器      决定用哪个索引、哪种连接顺序 → 生成执行计划
  ▼
⑤ 执行器      根据执行计划调用存储引擎接口，检查权限，返回结果
  ▼
⑥ 存储引擎    InnoDB 真正读写磁盘/内存数据（含事务、锁、日志）
```

### 各阶段详细讲

**① 连接器**
- 负责和客户端建立 TCP 连接、验证身份（用户名/密码）、校验权限
- `SHOW PROCESSLIST` 能看到当前连接，`Sleep` 状态就是空闲连接
- 连接有超时时间（`wait_timeout` 默认 8 小时）
- 连接建立后，权限就固定了，中途改了权限要重连才生效

**② 查询缓存（8.0 已移除）**
- 老版本会把 SELECT 的结果以 SQL 文本为 key 缓存
- 表一旦有更新，这张表的所有缓存全部失效 → 更新频繁的表缓存命中率极低
- 所以 8.0 直接删掉了这个模块，面试时要说"8.0 已删除"

**③ 解析器**
- **词法分析**：把 SQL 拆成一个个 token（关键字、表名、列名）
- **语法分析**：检查语法对不对，生成**语法树**，语法错误在这里报（"You have an error in your SQL syntax"）

**④ 优化器**
- 决定"怎么查最快"：选哪个索引、多表 JOIN 先连哪张、子查询怎么改写
- 优化器不是万能的，选错索引是慢查询的常见原因（见 09 章）

**⑤ 执行器**
- 先做**权限校验**（有表权限吗？）
- 按执行计划逐行调用存储引擎接口
- 无索引时执行器一行行扫（全表扫描），有索引时走索引接口

**⑥ 存储引擎**
- 真正干活的：读磁盘数据页、修改 B+ 树、写 redo log/undo log、加锁、提交事务
- 存储引擎是插件式的：InnoDB、MyISAM、Memory……

### 面试加分细节
- **权限校验发生在执行器**而不是连接器：连接时只验证账号密码，执行时才验证对具体表的权限
- 8.0 之后优化器改为**基于成本**（cost model），会统计索引区分度等信息
- 一条 UPDATE 与 SELECT 的流程差异在最后：UPDATE 多出"找行 → 加锁 → 改 → 记日志 → 刷盘"的环节，详见 08 章

## 2. 讲一讲 MySQL 的引擎吧，你有什么了解？

### 一句话回答
存储引擎是 MySQL 的"数据存取内核"，负责数据的存储、索引、事务、锁。MySQL 是**插件式架构**，一张表可以选不同引擎，最常用的是 InnoDB 和 MyISAM。

### 引擎的定位
MySQL 分两层：
- **Server 层**：连接管理、SQL 解析、优化、缓存——与引擎无关
- **存储引擎层**：真正管数据的落盘、读盘、索引结构、事务、锁——每个引擎实现不同

所以同一个库可以混合使用不同引擎的表（不推荐混用，但支持）。

### 常见引擎一览

| 引擎 | 特点 | 现状 |
|------|------|------|
| **InnoDB** | 事务、行锁、崩溃恢复、聚簇索引 | 默认引擎，8.0 的唯一主流 |
| **MyISAM** | 无事务、表锁、压缩、全文索引（旧） | 已边缘化，5.7 后逐渐淘汰 |
| **Memory** | 数据全在内存，重启丢数据 | 特殊场景用（临时表） |
| **Archive** | 只支持 INSERT 和 SELECT，高压缩 | 冷数据归档 |
| **CSV** | 数据直接是 CSV 文件 | 很少用 |
| **NDB** | 分布式内存引擎 | MySQL Cluster 专用 |

### 怎么查看和修改引擎

```sql
-- 查看某表的引擎
SHOW TABLE STATUS LIKE 'user'\G

-- 查看支持的引擎
SHOW ENGINES;

-- 建表时指定引擎
CREATE TABLE t (id INT) ENGINE = InnoDB;

-- 修改已有表的引擎
ALTER TABLE t ENGINE = InnoDB;
```

### 面试延伸：为什么说"存储引擎是插件式的"？
MySQL 的架构像电脑的"主板 + 显卡"：Server 层是主板（接口固定），引擎是显卡（实现可换）。`SHOW ENGINES` 能看到所有可用的"显卡型号"。这保证了 MySQL 生态的灵活性——但同时也意味着引擎之间的事务、锁行为可能完全不同。

## 3. MySQL 为什么 InnoDB 是默认引擎？

### 一句话回答
因为 InnoDB 是**唯一同时支持事务、行级锁、崩溃恢复**的引擎，这三个能力是企业级数据库的硬需求，所以从 MySQL 5.5.5 起成为默认引擎（之前的默认是 MyISAM）。

### 展开：MySQL 需要什么？

**① 事务（ACID）**
- 电商扣款、转账，必须"要么全成要么全不做"
- MyISAM 完全不支持事务，一个 UPDATE 半路失败，数据就停在中间状态

**② 并发能力（行级锁）**
- MyISAM 用**表锁**：任何写操作锁整张表，写入一多就互相排队
- InnoDB 用**行锁**：只锁正在改的那几行，不同行的写入互不干扰
- 互联网高并发下，表锁 = 死路

**③ 崩溃恢复（crash recovery）**
- 数据库突然断电/宕机，内存里没来得及落盘的数据怎么办？
- InnoDB 有 redo log（重做日志），重启时自动重放，数据不丢
- MyISAM 没有这个机制，宕机后数据可能损坏甚至丢失

**④ 其他细节**
- 外键约束只有 InnoDB 支持
- InnoDB 支持 MVCC（多版本并发控制），让"读"不阻塞"写"
- 8.0 起 MyISAM 的很多特性（全文索引等）InnoDB 也有了，MyISAM 彻底边缘化

### 面试回答模板
"InnoDB 支持事务、行级锁、崩溃恢复，这三点是业务数据库的底线。MyISAM 只能做表锁、无事务、无崩溃恢复，只适合读多写少的轻量场景。所以 MySQL 5.5.5 之后默认引擎换成 InnoDB，8.0 时代基本只剩 InnoDB 可选。"

## 4. 说一下 MySQL 的 InnoDB 与 MyISAM 的区别？

### 对比表（面试必背）

| 对比项 | InnoDB | MyISAM |
|--------|--------|--------|
| 事务 | ✅ 支持（ACID） | ❌ 不支持 |
| 锁粒度 | 行锁（+间隙锁） | 表锁 |
| 崩溃恢复 | ✅ redo log 重放恢复 | ❌ 容易损坏 |
| 索引结构 | 聚簇索引（数据和索引在一起） | 非聚簇索引（索引和数据分离） |
| 外键 | ✅ 支持 | ❌ 不支持 |
| MVCC | ✅ 支持 | ❌ 不支持 |
| 全文索引 | 8.0 起支持 | 早期就支持 |
| 存储文件 | .ibd（数据+索引）、.frm（8.0并入数据字典） | .MYD（数据）、.MYI（索引） |
| COUNT(*) 速度 | 慢（要扫描） | 快（有单独计数器） |
| 缓存 | 缓存索引+数据 | 只缓存索引 |
| 适用场景 | 绝大多数业务库 | 只读、数据仓库等极端场景 |

### 关键区别 1：聚簇 vs 非聚簇

这是最深层的区别：

```
MyISAM（索引和数据分开存）:
  .MYI 索引文件：主键索引叶子节点 → 存数据行的磁盘地址
  .MYD 数据文件：真正的行数据
  查询流程：先查索引找到地址 → 再按地址去 .MYD 读数据（一次回表）

InnoDB（聚簇索引）:
  .ibd 文件：主键索引的叶子节点 → 直接存整行数据
  查询流程：主键查询直接拿到整行，无需二次跳转
```

### 关键区别 2：锁的粒度
- MyISAM 写操作锁**整张表**：一个 UPDATE 在跑，其他所有读写都排队
- InnoDB 只锁**涉及的行**：不同行的 UPDATE 可以并发执行

### 关键区别 3：COUNT(*) 为什么 MyISAM 快？
MyISAM 把"总行数"作为元数据**单独存了一份**，COUNT(*) 直接读数字。
InnoDB 因为 MVCC 的原因，不同事务看到的行数可能不同，没法缓存行数，只能扫一遍（8.0 有优化，但本质还是扫描）。
> 但注意：MyISAM 的 COUNT(*) 只有在不带 WHERE 时才能用缓存，带条件照样扫描。

### 面试回答模板
"主要区别在四个方面：事务（InnoDB 有，MyISAM 没有）、锁（行锁 vs 表锁）、崩溃恢复（InnoDB 有 redo log，MyISAM 没有）、索引（InnoDB 聚簇索引数据索引一体，MyISAM 分离且查询要回表）。结论：无脑选 InnoDB，MyISAM 只会在面试题和遗留系统里出现。"

## 5. 数据管理里，数据文件大体分成哪几种数据文件？

### 一句话回答
按作用分：**表结构文件、表数据文件、日志文件、系统文件**；如果按 InnoDB 的实际磁盘产物分，核心是 `.ibd` 数据文件、`.ibdata` 共享表空间、redo/undo 日志文件。

### 按作用分类（通用回答）

**① 数据文件**：真正存表数据的文件
- InnoDB：`.ibd`（每表一个，独立表空间）或 `.ibdata1`（共享表空间）
- MyISAM：`.MYD`（数据）+ `.MYI`（索引）

**② 日志文件**：记录操作历史，用于恢复和复制
- **binlog**（二进制日志）：Server 层记录所有写操作，用于主从复制和恢复
- **redo log**：InnoDB 层的物理日志，崩溃恢复用
- **undo log**：记录数据修改前的状态，回滚和 MVCC 用
- **error log**（错误日志）：启动、运行时的错误信息
- **slow query log**（慢查询日志）：记录执行超过阈值的 SQL
- **general log**（通用日志）：记录所有 SQL 操作（一般不开，太占空间）

**③ 配置文件**：`my.cnf` / `my.ini`，数据库启动参数（端口、内存大小、日志开关）

**④ 系统文件**：`ibdata`、`ib_buffer_pool`、`auto.cnf`（server-uuid）等 MySQL 运行必需文件

### 从 MySQL 安装目录看（Windows）

```
mysql/
├── data/               # 数据目录
│   ├── ibdata1         # 共享表空间（系统表、undo log 默认位置）
│   ├── ib_logfile0     # redo log 文件（8.0 改名为 #ib_redo*）
│   ├── undo_001        # undo log（8.0 独立文件）
│   ├── mysql/          # 系统库（user 表等）
│   ├── 你的库名/        # 业务库目录
│   │   └── 表名.ibd    # 每张 InnoDB 表的数据+索引
│   └── *.err           # 错误日志
├── bin/                # 可执行程序
├── lib/                # 依赖库
└── my.ini              # 配置文件
```

### InnoDB 表空间详解（面试深水区）

- **独立表空间**（默认）：每张表一个 `.ibd` 文件，DROP 表直接删文件，空间立释放；迁移单表容易
- **共享表空间**（`innodb_file_per_table=0` 时）：所有表共用一个 `ibdata1`，表多了文件巨大，DROP 表后空间不归还（碎片）
- 8.0 默认：每表一个 `.ibd` + 数据字典并入系统表空间

### 面试注意
问"数据文件分几种"时，回答要分**两层**：
1. 宏观层：结构文件 / 数据文件 / 日志文件 / 配置文件
2. InnoDB 微观层：.ibd（表数据）、ibdata（系统+undo）、redo log、binlog

把 binlog 说成 InnoDB 的是常见错误——**binlog 是 Server 层日志，redo/undo 才是 InnoDB 层**。
