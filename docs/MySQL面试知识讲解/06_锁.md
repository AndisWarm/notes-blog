## 1. 讲一下 MySQL 里有哪些锁？

### 一句话回答
MySQL 的锁分三个维度看：**按粒度**（全局锁、表锁、行锁）、**按性质**（共享锁 S、排他锁 X）、**按实现**（乐观锁、悲观锁、意向锁、间隙锁、Next-Key 锁、自增锁、元数据锁）。面试先答"粒度+性质"两个主维度，再展开细节。

### 维度一：按粒度（从大到小）

| 锁类型 | 锁的范围 | 特点 |
|--------|----------|------|
| **全局锁** | 整个数据库实例 | `FLUSH TABLES WITH READ LOCK`，全库只读，备份用，业务几乎不用 |
| **表级锁** | 整张表 | 开销小、粒度大、并发差；MyISAM 只有这种 |
| **行级锁** | 单行/索引区间 | InnoDB 特性，开销大、粒度细、并发高 |

**表级锁细分：**
- **表读锁（共享）**：所有事务可读，写被挡
- **表写锁（排他）**：只有持锁事务能读写，其他全等
- **元数据锁（MDL）**：DDL（ALTER）时自动加，防止结构变更和查询冲突
- **意向锁（IS/IX）**：加行锁前先给表加个"意向"，告诉别人"这表有行被锁了"，避免锁表时逐行检查
- **自增锁（AUTO-INC）**：AUTO_INCREMENT 生成时用的特殊表锁（8.0 默认是轻量的 interleaved 模式）

**行级锁细分（InnoDB）：**
- **记录锁（Record Lock）**：锁单条索引记录
- **间隙锁（Gap Lock）**：锁两个记录之间的区间，只防插入（见 05 章第 9 节）
- **临键锁（Next-Key Lock）**：记录锁+间隙锁，默认锁单位

### 维度二：按性质（S/X）

| 锁 | 含义 | 兼容性 |
|----|------|--------|
| 共享锁（S 锁，读锁） | 可以读，不可写 | S 和 S 兼容（可同时读） |
| 排他锁（X 锁，写锁） | 可读可写，独占 | X 和任何锁都互斥 |

兼容矩阵：S 兼容 S；S 与 X 互斥；X 与 X 互斥。

```sql
-- 手动加锁（一般不用，了解语法即可）
SELECT * FROM t WHERE id = 1 LOCK IN SHARE MODE;  -- 加 S 锁
SELECT * FROM t WHERE id = 1 FOR UPDATE;           -- 加 X 锁
```

### 维度三：按使用方式

| 类型 | 说明 |
|------|------|
| 悲观锁 | 先锁后操作（SELECT FOR UPDATE），认为"总会有人抢" |
| 乐观锁 | 不加锁，更新时带版本号校验（`WHERE version = 旧值`），失败重试 |

### 面试回答模板
"按粒度分全局锁、表锁、行锁；按性质分 S 共享锁和 X 排他锁；InnoDB 的行锁又细分为记录锁、间隙锁、临键锁，并配合意向锁与表锁协作。MyISAM 只有表锁，InnoDB 才有行锁。"

## 2. 数据库的表锁和行锁有什么作用？

### 一句话回答
**表锁**保护整张表的操作一致性（DDL、MyISAM 写），**行锁**让 InnoDB 只锁住涉及的行，实现细粒度并发——两者的本质都是"互斥写"，区别在锁的粒度不同、并发能力不同。

### 表锁的作用

1. **保证整表操作的原子性**：ALTER TABLE（DDL）期间锁全表，防止查询读到"改了一半"的表结构
2. **MyISAM 的写锁**：MyISAM 没有行锁，写操作只能锁整表
3. **批量操作的简单方案**：某些特殊操作（如表重建）需要全表锁

表锁的代价：一次写操作阻塞整张表的读写 → 并发差。

### 行锁的作用

1. **并发写**：只锁涉及的行，不同行的 UPDATE 互不干扰
2. **配合事务和 MVCC**：实现 RC/RR 隔离级别的写写互斥
3. **锁的精度高**：锁冲突概率低，适合高并发 OLTP

行锁的代价：锁管理开销大（每条锁记录都要维护）、可能出现死锁（多个事务互相等锁）。

### 什么时候用哪个？

| 场景 | 选哪种 |
|------|--------|
| 高并发 DML（互联网业务） | 行锁（InnoDB） |
| 全表批量更新 | 表锁更合适（行锁逐个加反而慢，还要防死锁） |
| 备份、DDL | 全局锁/表锁（MDL） |
| 报表只读场景 | 表锁共享读（多个读可并发） |

### 面试回答模板
"表锁保护整表操作的一致性，粒度大并发差；行锁把锁的范围缩小到行，不同行的读写互不阻塞，是 InnoDB 高并发的基础。行锁不是没有代价：锁管理开销大、可能死锁。大事务批量更新时表锁反而更划算。"

## 3. MySQL 两个线程的 UPDATE 语句同时处理一条数据，会不会有阻塞？

### 答案
**会阻塞**：InnoDB 行锁（X 锁）互斥，后到的 UPDATE 必须等先到的 UPDATE 提交/回滚释放锁后才能继续。

### 时间线演示

```
表 t 有数据 id=1, balance=1000

线程A: UPDATE t SET balance = 900 WHERE id = 1;   -- 拿到 id=1 的 X 锁
线程B: UPDATE t SET balance = 800 WHERE id = 1;   -- 请求同一行的 X 锁 → 阻塞等待！

线程A: COMMIT;                                    -- 释放锁
线程B: 获得锁，继续执行 → 成功
```

### 细节要点（面试深问）

**① 阻塞时长取决于持有时间**
锁在事务提交/回滚时才释放（不是语句执行完就释放）：
```sql
-- 线程A如果包在长事务里，B 会一直等
BEGIN;
UPDATE t SET balance = 900 WHERE id = 1;
-- ... 长业务逻辑 ...
COMMIT;  -- B 等到这会儿才能执行
```

**② 等待超时会报错**
```sql
-- 默认锁等待超时 50 秒
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';  -- 50
```
超过 50 秒还在等 → 报 `Lock wait timeout exceeded` 错误。

**③ 行锁是"基于索引"的**
InnoDB 的行锁本质是**锁索引记录**：
- WHERE 条件走索引 → 锁索引行
- WHERE 条件没索引 → 会锁全表记录（等于表锁效果，详见第 5 题）

**④ 读不受影响（MVCC）**
B 如果只是 SELECT（快照读）→ 不阻塞，直接读旧版本；只有**写写**才互斥。

### 面试回答模板
"会阻塞。InnoDB 的 X 锁互斥，后到的写等先到的写提交。阻塞时间取决于事务持有锁的时长，超过 innodb_lock_wait_timeout（默认50秒）会超时。快照读不受影响，只有写写互斥。"

## 4. 两条 UPDATE 语句处理一张表的不同的主键范围的记录，会不会遇到阻塞？底层是为什么？

### 题目
两条 UPDATE 分别处理**不同主键范围**的记录（比如一条 id=1~10，一条 id=15~20），会不会阻塞？

### 答案
**不会阻塞**（前提：两条语句的锁区间没有交集）。底层原因：**InnoDB 行锁只锁涉及的主键记录（和必要的间隙），不同区间的锁互不冲突，天然并行**。

### 底层原理

```
表 t：id 1,2,3,...,20（主键索引，聚簇）

线程A: UPDATE ... WHERE id BETWEEN 1 AND 10;
  → 锁住 id=1~10 的记录锁（+ 边界间隙）
线程B: UPDATE ... WHERE id BETWEEN 15 AND 20;
  → 锁住 id=15~20 的记录锁（+ 边界间隙）

两个锁集合没有交集 → 各自执行，互不等待 ✅
```

为什么能并行？
- InnoDB 锁的最小单位是**索引记录**（聚簇索引的叶子节点）
- 每个主键区间对应不同的索引记录集合
- 锁之间只有**冲突时才排队**（S/X 互斥矩阵），区间无交集 = 无冲突
- 这就是"行锁让不同行的写可以并发"的直接体现

### 边界情况：间隙锁可能造成"意外"阻塞！

注意 RR 隔离级别下的**范围 UPDATE 会加间隙锁/临键锁**：

```
线程A: UPDATE ... WHERE id BETWEEN 1 AND 10;
  → 加临键锁覆盖 (1,2] (2,3] ... (9,10] (10,15]  ← 注意 (10,15) 这段"间隙"
线程B: UPDATE ... WHERE id = 12;   -- 12 在 A 的间隙锁区间内
  → 阻塞！虽然 12 不属于 A 的 1-10，但间隙锁把这个空档也锁了
```

如果表中 id 是**连续无空隙**的（1~10、15~20 之间 11~14 不存在），B 的 id=12 不存在也就无所谓；但如果 12 存在且被 A 的范围包含，就会阻塞。**范围更新锁的区间比"命中的记录"更大**——这是 RR 防幻读的代价。

### 面试回答模板
"不同主键区间的 UPDATE 互不阻塞，因为行锁只锁命中的索引记录，锁集合无交集就并行。但要注意 RR 下的范围更新会带间隙锁，锁区间会**延伸**到记录之间的空档，如果另一条语句恰好在空档区间插入/更新，还是会阻塞。"

## 5. 如果 2 个范围不是主键或索引？还会阻塞吗？

### 答案
**会阻塞**（比主键场景严重得多）：WHERE 条件列**没有索引**时，InnoDB 只能全表扫描定位记录，会把**扫描经过的所有记录全部加锁**——两个范围即使不同，也会因为锁重叠而互相阻塞，甚至锁住整张表。

### 底层原因

InnoDB 行锁是"**锁索引记录**"，锁必须挂在索引上：
- 有索引：精确锁定命中的索引记录 → 锁区间小
- **无索引：无法按索引定位，只能扫描整张表找到匹配行 → 扫描过程中碰到每条记录都要加锁**（因为不知道哪条会被 WHERE 命中，先锁住再说）

```
表 t：字段 age 无索引，数据 age=20,30,40,50

线程A: UPDATE t SET ... WHERE age BETWEEN 20 AND 30;
  → 全表扫描，把扫描到的每条记录都加 X 锁（包括 age=40,50！）
线程B: UPDATE t SET ... WHERE age BETWEEN 40 AND 50;
  → 扫描时发现 age=40,50 已被 A 锁住 → 阻塞！
```

### 后果

1. **无索引更新 = 变相锁全表**：第一个更新把所有行都锁住，并发直接退化成串行
2. 大量锁记录 → 锁内存开销暴涨
3. 极易死锁

### 正确姿势（面试必答）

```sql
-- 给 WHERE 条件列建索引
ALTER TABLE t ADD INDEX idx_age (age);
```
索引建好后，两条 UPDATE 只锁各自命中的记录，互不阻塞。

### 面试回答模板
"会阻塞，而且更严重：无索引时 InnoDB 无法按索引定位，只能全表扫描，扫描过程中把每条记录都加锁，等于把整张表锁住了，两个不同范围的更新也会互相阻塞。解法很简单：给 WHERE 列建索引，让行锁精确落在目标记录上。"

## 6. 补充：死锁是怎么回事？怎么避免？

### 一句话回答
死锁 = **两个事务互相持有对方需要的锁，谁也不让谁**，形成循环等待。InnoDB 检测到死锁会主动回滚其中一个事务（报 Deadlock found 错误），让另一个继续。

### 经典死锁例子

```
事务A: UPDATE t SET ... WHERE id=1;   -- 持有 id=1 的锁
事务B: UPDATE t SET ... WHERE id=2;   -- 持有 id=2 的锁
事务A: UPDATE t SET ... WHERE id=2;   -- 等 B 释放 id=2 → 阻塞
事务B: UPDATE t SET ... WHERE id=1;   -- 等 A 释放 id=1 → 阻塞
→ A 等 B，B 等 A，死锁！
```

### InnoDB 怎么处理死锁？

- **死锁检测**：等待图检测到循环 → 选择回滚"undo 量较小"的事务（成本低者），报 `ERROR 1213 (40001): Deadlock found when trying to get lock`
- 被回滚的事务由应用层捕获异常后**重试**

### 避免死锁的方法（面试背）

1. **固定访问顺序**：所有事务都按"先 id 小后 id 大"的顺序更新，破坏循环
2. **减少事务持锁时间**：短事务、事务内不做外部调用
3. **尽量用索引**：缩小锁范围（无索引更新锁全表，死锁概率指数级上升）
4. **避免范围更新与插入混用**：间隙锁参与时死锁概率高
5. **合理设计隔离级别**：RR 的间隙锁是死锁高发区，写密集场景可评估切 RC
6. **业务兜底重试**：捕获 1213 异常后重试事务

### 面试金句
"死锁不可避免，只能降低概率 + 优雅重试。数据库会主动回滚一个事务打破死锁，应用层要做重试机制。"
