# 03 短链系统设计

本章覆盖：短链系统的核心需求与典型场景（微博、营销短信）、HTTP 重定向原理、301/302 的选择（必考）、短链生成的两大方案对比（哈希截断 vs 分布式 ID 发号器 + Base62）、存储与 Redis 缓存设计（读多写少）、缓存穿透与布隆过滤器、网关 IP 限流，最后串一条完整的流转链路。

## 1. 短链系统是干什么的？核心需求是什么？

### 一句话回答
短链系统的核心需求就两条：**把超长的网址压缩成一个很短的字符串**；**用户点击这个短字符串后，能精准跳回原来的长链接**，不能跳错、不能跳丢。

### 展开讲：拆解"核心需求"

先感受一下"长网址"到底有多长。一个真实的营销链接经常长成这样：

```
https://www.example.com/promotion/2026/summer/activity/detail?utm_source=weibo&utm_medium=post&utm_campaign=618&ref_id=10086&channel=ab12
```

这种网址动辄上百个字符，直接发给用户会遇到一堆麻烦：

- **微博限制字数**：一条微博有字数上限，一长串链接就把宝贵字数全占了，文案都写不下；
- **短信按条计费**：营销短信按条数算钱，一条链接占掉大半条短信，一条 70 字的短信可能装不下，被迫发两条，成本翻倍；
- **显示难看、容易被截断**：长链接在聊天窗口里会折行、被截断，用户看不清、不敢点；
- **二维码装不下**：线下物料上的二维码，内容越长越密，扫描成功率越低。

把上面那个一百多字符的网址压缩成这样：

```
https://dwz.cn/Ab3xY9
```

一个短链接就 8~10 个字符，短信发得下、微博放得下、二维码扫得清——这就是"长变短"的价值。

而"短变长"（点击跳回）同样重要：用户在微博看到 `Ab3xY9` 这个短码，点一下，浏览器必须打开**原来那条**长链接指向的页面，跳错页面就是事故。所以短链系统本质上是两个方向的映射：

| 方向 | 做什么 | 用户感知 |
|---|---|---|
| 长 → 短 | 把长链接压缩成短字符串 | 生成链接的人（博主、运营） |
| 短 → 长 | 点击短字符串跳回长链接 | 点击链接的人（粉丝、收短信的人） |

### 典型应用场景

- **微博**：博主发长文带链接，微博自动把链接变成短链，既省字数又能统计这条微博带了多少流量；
- **营销短信**：商家群发短信里的链接几乎全是短链，省字数省钱，还能统计"多少人点了这条短信"；
- **二维码/线下物料**：海报、名片、快递单上的二维码，背后常常就是一个短链；
- **防封禁/换源**：外链被屏蔽时，通过短链中转，随时可以更换指向的目标地址，不用重新印刷物料。

### 比喻
短链系统就像**快递柜的取件码**。快递员（生成链接的人）把包裹（长链接）存进快递柜，柜子给他一个 6 位数的取件码（短链）；取件人（点链接的人）输入取件码，柜门打开，精准拿到属于他那份的包裹。取件码不能和别人混淆——短链也不能跳错页面，这就是"精准映射"。

也可以理解成**电话簿**：长链接是人的全名，短链是小名。你喊小名，电话簿一查，找到对应的人——短链系统的核心就是维护好这本"电话簿"。

### 面试怎么答
先答需求：**"短链系统就两件事：长链接变短、短链接能精准跳回长链接"**；再补场景：微博省字数、短信省钱省条数、二维码好扫、方便统计点击。把"精准"二字强调出来——这是后面所有设计的出发点。

## 2. 核心原理：HTTP 重定向是怎么让短链"跳"起来的？

### 一句话回答
短链跳转靠的是 HTTP 协议自带的**重定向（Redirect）机制**：浏览器访问短链 → 服务器查数据库找到长链接 → 返回一个带**状态码**和 **Location 响应头**的响应 → 浏览器看到后**自动**发起第二次请求去访问长链接。

### 展开讲：一次点击的完整过程

假设用户点击了短链 `https://dwz.cn/Ab3xY9`，浏览器背后经历了这样的过程：

1. **浏览器请求短链**：浏览器向短链服务器发一个 `GET /Ab3xY9` 的请求；
2. **服务器查长链**：短链服务器拿着 `Ab3xY9` 去 Redis / MySQL 里查，找到它对应的长链接；
3. **服务器返回"重定向指令"**：服务器不直接返回网页内容，而是返回一个特殊的响应，告诉浏览器"你要的东西在别处"，响应长这样：

```
HTTP/1.1 302 Found
Location: https://www.example.com/promotion/2026/summer/activity/detail?utm_source=weibo
```

4. **浏览器自动跳转**：浏览器读到 `302` 和 `Location` 头，会自动再发一次请求，去访问 `Location` 里写的长链接；
5. **长网站返回内容**：长链接所在网站正常返回 `200` 和网页内容，用户看到最终页面。

整个过程中，**用户只点了一下**，剩下的都是浏览器在后台自动完成的，用户感觉不到中间拐了个弯。

### 比喻
重定向就像**商场前台指路**。你问前台"3 楼在哪"（请求短链），前台不亲自带你上楼，而是告诉你"出门右转坐电梯到 3 楼"（返回 `Location`）。你按照指引自己走过去（浏览器自动发第二次请求），最终到达目的地（长链接页面）。前台只是"指路"，不负责"带路"。

### 面试怎么答
画出四个关键动作：**请求短链 → 查库找长链 → 返回 `302` + `Location` → 浏览器自动二次请求**。只要把这个"两次请求"的模型讲清楚，面试官就知道你懂 HTTP 重定向的本质。可以顺手补一句："所以短链服务器本身不存网页内容，它只负责**指路**。"

## 3. 关键考点：为什么用 302 不用 301？

### 一句话回答
因为 `301` 是"**永久**重定向"，浏览器会把它**缓存**在本地，用户第二次点击**根本不经过服务器**，你就**统计不到点击量**；`302` 是"**临时**重定向"，**每次都经过服务器**，方便做数据埋点和流量监控——短链系统需要统计，所以必须用 `302`。

### 展开讲：301 和 302 的本质区别

`301` 和 `302` 都是重定向，区别在于"**这个跳转是不是永久的**"：

- **`301 Moved Permanently`（永久重定向）**：服务器告诉浏览器"这个地址**永远**搬到新地方了，以后别再找我了"。浏览器是个听话的"记性很好的学生"，它会把"短链 → 长链"这个对应关系**记在小本本（本地缓存）里**。用户第二次点击同一个短链时，浏览器**直接从小本本里翻出长链**，压根不再请求短链服务器；
- **`302 Found`（临时重定向）**：服务器告诉浏览器"这次先临时去这个地方"。浏览器**不记小本本**，每次都老老实实先问短链服务器"这个短链去哪？"，服务器每次都回答一次。

对短链系统来说，这个差别是**致命的**：

| 对比项 | 301 永久重定向 | 302 临时重定向 |
|---|---|---|
| 浏览器是否缓存跳转结果 | 缓存，第二次不走服务器 | 不缓存，每次都走服务器 |
| 能否统计每次点击 | ❌ 第二次点击统计不到 | ✅ 每次点击都经过服务器 |
| 能否实时监控/改指向 | ❌ 用户端缓存旧的指向，改不了 | ✅ 改数据库立刻生效 |
| 适合场景 | 网站换域名等"真搬家" | 短链跳转、活动页等"临时指路" |

三个直接影响：

1. **点击量统计失真**：营销短信最关心的就是"这条短信带来了多少点击"。如果用 `301`，同一用户第二次点，浏览器本地就跳了，服务器**根本不知道**，统计数据直接少一截，KPI 都算不准；
2. **无法改指向**：运营想把短链从活动页 A 改到活动页 B，用 `301` 的话，已经点过的用户浏览器里缓存着 A，改不动他们；用 `302` 改一下数据库就全部生效；
3. **无法做监控**：`302` 让每次点击都经过服务器，就可以顺便记录 IP、时间、设备、来源，做流量分析和风险控制。

### 比喻
`301` 像快递**永久改址**：快递公司把你的地址永久改成新地址并登记在册，下次寄件直接送新地址，**不再通知旧地址的人**——旧地址（服务器）就收不到任何消息了。`302` 像**临时转寄**：每次包裹都先到老地址，再由老地址的人告诉快递员"今天送到隔壁去"——每次都要经过老地址，所以老地址能记录每一次包裹来过。

### 面试怎么答
一句话点破：**"301 会被浏览器缓存，第二次点击不经过服务器，统计不到点击量；302 每次都经过服务器，方便埋点统计"**。再补一句加分项："而且用 302 改指向即时生效，用 301 用户端缓存是旧的，改不动。"这个考点几乎必问，先答结论再补原因，稳。

## 4. 短链接怎么生成？两种方案对比

### 方案一：MD5 等哈希算法截断（不推荐）

#### 一句话回答
把长链接丢进 MD5 等哈希算法，算出一个固定长度的哈希值，再截取其中一段转换字符拼成 6 位短码——思路直观，但有**致命缺点：哈希冲突**，处理冲突的代码非常复杂。

#### 展开讲
步骤看起来很简单：

1. 对长链接做 MD5 计算，得到一串 32 位的十六进制哈希值（不管链接多长，结果都是定长）；
2. 从哈希值里截取一段（比如取前 6 个十六进制字符，或转成 Base62 后截 6 位）；
3. 把这段作为短码，存进数据库。

**问题出在"截断"上**：哈希算法虽然能把任意输入变成定长输出，但不同的长链接**有可能算出相同或相似的哈希值**，截断之后撞车的概率进一步放大。当两个不同的长链接映射出同一个短码时，就发生了**哈希冲突**——第二个链接的短码和第一个一样，点击时不知道该跳哪个。

**处理冲突的代价**：发现冲突后，要么给长链接"加点盐"（拼个随机字符串）重新算，要么换个截取位置重新截，算完还要**再查一次数据库确认没撞**。这个"检测冲突 → 重算 → 再检测"的循环写起来又绕又容易出 bug，而且冲突多了性能还会下降。另外，同一个长链接每次算出的哈希值一样，短码固定，但**同一个长链接应该允许生成不同的短码**（不同渠道、不同活动各一个），哈希方案天然做不到，还得额外加随机因子。

### 方案二：分布式 ID 发号器 + Base62 转换（业界标配）

#### 一句话回答
先由一个"**发号器**"给每个新链接分配一个**全局唯一、单调递增的数字 ID**（比如 10086、10087……），再用**十进制转 62 进制**的方法把这个数字变成短字符串——一个数字对应一个短码，**天然不冲突**。

#### 展开讲：分三步

**第一步：发号器发一个唯一数字 ID。**

发号器就是一台"取号机"，保证每次发出去的号码都不重复。业界常用两种实现：

- **MySQL 号段模式**：数据库里维护一张"号段表"，每次取走一批号（比如一次取 1000 个号 1~1000），用完了再来取下一批，多个服务各领各的号段，互不冲突；
- **Redis 自增**：直接用 Redis 的 `INCR` 命令，每调一次就 +1，原子操作不会重复：

```
127.0.0.1:6379> INCR link_id
(integer) 10086
127.0.0.1:6379> INCR link_id
(integer) 10087
```

假设这次拿到 `10086` 这个数字 ID。

**第二步：把十进制数字转成 62 进制字符串。**

`Base62` 就是用 62 个字符来表示数字：`0-9`（10 个）+ `a-z`（26 个）+ `A-Z`（26 个）= **62 个字符**。转换方法和小学学的"十进制转二进制"一模一样，只是把"除以 2 取余数"换成"除以 62 取余数"：

- 十进制转二进制：`13 ÷ 2 = 6 余 1`，`6 ÷ 2 = 3 余 0`，`3 ÷ 2 = 1 余 1`，`1 ÷ 2 = 0 余 1`，倒着读余数：`1101`；
- 十进制转 62 进制：完全同理，除以 62 取余，直到商为 0，余数**倒着读**。

把 `10086` 转成 62 进制（字符表 `0-9a-zA-Z`，第 0 位是 `0`，第 61 位是 `Z`）：

```
10086 ÷ 62 = 162 余 42    → 字符表第 42 位 = 'q'
162   ÷ 62 = 2   余 38    → 字符表第 38 位 = 'c'
2     ÷ 62 = 0   余 2     → 字符表第 2 位  = '2'
余数倒着读：2 c q → 短码 "2cq"
```

伪代码也就几行：

```python
def to_base62(num):
    chars = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
    result = ""
    while num > 0:
        result = chars[num % 62] + result
        num = num // 62
    return result

print(to_base62(10086))   # 输出 2cq
```

**第三步：容量核算——6 位短码能装多少链接？**

每一位有 62 种选择，6 位就是：

```
62^6 = 62 × 62 × 62 × 62 × 62 × 62 = 56,800,235,584 ≈ 568 亿
```

**568 亿**个不同短码，全世界人口一人 7 个都还有富余。短链系统做到这个量级之前，根本不用担心号码不够用。而且因为是"**一个数字对应一个短码**"的一一映射，**不会冲突**——这是它碾压哈希方案的根本原因。

### 两种方案对比

| 对比项 | 方案一：MD5 截断 | 方案二：发号器 + Base62 |
|---|---|---|
| 冲突 | 有，且截断后更严重 | 无，一一对应 |
| 冲突处理代码 | 复杂：检测 → 重算 → 再检测 | 不需要 |
| 同一长链多次生成 | 结果固定，难区分渠道 | 每次发新号，天然区分 |
| 短码可预测性 | 不可预测 | 递增可预测（可加随机偏移缓解） |
| 业界使用 | 少见 | **标配** |

### 比喻
方案二就像**银行取号机 + 进制转换**：取号机保证每个人拿到的号都不同（唯一 ID），柜台再把这个号写在"短号牌"上给你。号是唯一的，号牌自然不重复；哈希方案则像几个人抢同一个 QQ 昵称，抢到重名就得有人改名，还得反复协调，麻烦透顶。

### 面试怎么答
先一句话表态：**"业界标配是分布式 ID 发号器 + Base62，不用 MD5 截断，因为哈希有冲突，处理冲突的代码又复杂又容易错"**。然后讲三步：发号器拿唯一 ID（MySQL 号段 / Redis `INCR`）→ 十进制转 62 进制（除法取余，类比转二进制）→ 6 位容量 `62^6 ≈ 568 亿`。能顺手写出 `to_base62` 伪代码，这题直接封神。

## 5. 存储与抗并发：读多写少怎么设计？

### 一句话回答
**写**：MySQL 一张两列的表（数字 ID/短串 + 长链接），短串加**唯一索引**；**读**：**绝对不能直接打 MySQL**，引入 Redis 缓存——先查 Redis，命中直接拼 `302` 返回，未命中才查 MySQL，查到后**回填 Redis**。

### 展开讲：存储设计

表结构非常简单，两张信息就够：

```sql
CREATE TABLE short_link (
  id         BIGINT PRIMARY KEY,      -- 发号器给的数字 ID（或直接存短串）
  short_code VARCHAR(8)  NOT NULL UNIQUE,  -- 短码，加唯一索引，双保险防重复
  long_url   VARCHAR(2048) NOT NULL,       -- 原始长链接
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

- `short_code` 加**唯一索引**：就算发号器万一出错，数据库层面也插不进重复的短码，这是最后一道防线；
- 主键用数字 ID，查询快、占空间小。

### 展开讲：为什么读绝对不能直接打 MySQL

短链系统是典型的**读多写少**：一条链接只生成一次（写一次），但可能被点击几百万次（读几百万次）。如果每次点击都查 MySQL：

- MySQL 磁盘 IO 慢，每秒能扛的查询量有限（几千到几万 QPS）；
- 双 11 级别的活动链接一被转发，瞬间几十万点击全砸 MySQL，数据库直接被打挂，全站瘫痪。

所以**读必须走缓存**：Redis 是内存数据库，读写都是微秒级，单机就能扛十几万 QPS。读流程：

1. 点击短链 → 先查 Redis，key 就用短码，比如 `link:Ab3xY9`；
2. **命中** → 直接拿到长链接，返回 `302` + `Location`，全程不碰 MySQL；
3. **未命中** → 查 MySQL，拿到长链接后**回填 Redis**（并设置过期时间），再返回 `302`；
4. 下次点击同一个短链，Redis 直接命中。

伪代码：

```python
def redirect(short_code):
    long_url = redis.get(f"link:{short_code}")        # 1. 先查缓存
    if long_url is None:                              # 2. 未命中
        long_url = mysql.query("SELECT long_url FROM short_link WHERE short_code=?", short_code)
        if long_url is None:
            return 404                                # 短链不存在
        redis.set(f"link:{short_code}", long_url, ttl=86400)  # 3. 回填缓存
    return 302(Location=long_url)                     # 4. 返回重定向
```

缓存命中率 90% 以上时，MySQL 的压力只剩下十分之一不到，这就是 Redis 的价值。

### 比喻
读走缓存就像**脑子里记熟的电话号码**：常打的电话（热点短链）记在脑子里，直接拨号，不用翻手机通讯录（MySQL）；偶尔不记得了才翻通讯录，查完再记到脑子里。要是每次都翻通讯录（直接打 MySQL），通讯录这本"书"翻几次就翻烂了。

### 面试怎么答
先讲结构：**"两列表 + 短码唯一索引"**；再讲策略：**"读多写少，读必须走 Redis，未命中查 MySQL 后回填"**；最后补一句关键理由：**"MySQL 扛不住百万次点击，Redis 内存读写能扛十几万 QPS"**。写/读两条路径分开讲，面试官会认为你脑子里有清晰的架构图。

## 6. 健壮性兜底：黑客传不存在的短链怎么办？

### 6.1 缓存穿透：布隆过滤器 + 空值缓存

#### 一句话回答
黑客拿一串**根本不存在的短链**疯狂请求时，Redis 没有、MySQL 也没有，每次都穿透到数据库，会把 MySQL 打穿——对策有两个：**布隆过滤器**在入口直接挡掉不存在的短链；**Redis 空值缓存**对查不到的短链也缓存一个极短时间的空值。

#### 展开讲
正常流程是"Redis 未命中 → 查 MySQL → 回填"，但**恶意请求的短链在 MySQL 里也不存在**，于是"查了没有 → 没有东西可回填 → 下次请求又来查一遍"，**每个请求都真实打到 MySQL**。黑客只要伪造几百万个随机短码，就能让 MySQL 每秒钟被无效查询轰炸，活活打挂——这叫**缓存穿透**：请求像针一样"穿透"缓存层，直接扎到数据库。

**对策一：布隆过滤器（第一道闸门）**

在系统启动时，把**所有已生成的短链**都登记进布隆过滤器。每次点击短链，**先问布隆过滤器"这个短码存在吗"**：

- 回答"**不存在**" → **一定不存在**（布隆过滤器不会漏报），直接返回 `404`，连 Redis 和 MySQL 都不碰；
- 回答"可能存在" → 放行，走 Redis → MySQL 的正常流程。

这样打进来的假短链在**最外层就被拦下**，数据库一根汗毛都伤不到。布隆过滤器的原理见下一节。

**对策二：Redis 空值缓存（第二道保险）**

万一布隆过滤器误判放进来一个不存在的短链，MySQL 查完发现没有——此时**不要什么都不做**，而是往 Redis 里存一个空值，并设置**极短的过期时间**（比如 30 秒）：

```python
redis.set(f"link:{short_code}", "", ttl=30)   # 缓存空值，30 秒后自动消失
```

那么这 30 秒内再来请求这个短码，Redis 命中"空值"，直接返回 404，**不会穿透到 MySQL**。过期时间必须极短，否则黑客换新短码时，Redis 里堆满没用的空 key，浪费内存。

### 6.2 网关层 IP 限流：防薅羊毛

#### 一句话回答
在网关（Nginx 等）层面对**同一 IP 的请求频率**做限制：比如 1 秒最多 10 次，超过直接拒绝，防止黑客用脚本批量刷短链、刷接口薅羊毛。

#### 展开讲
布隆过滤器挡的是"不存在的短链"，但黑客还可以**拿真实存在的短链**刷量——疯狂点击同一个短链，把点击统计刷爆，或者用脚本批量调用"生成短链"接口，把发号器的号码池薅干。对策是在网关层做**IP 限流**：

- **按 IP 限速**：同一 IP 每秒最多 N 个请求，超过返回"请求过于频繁"；
- **按接口限流**："生成短链"接口限得比"跳转"接口更严，因为生成是写操作，代价高；
- 黑白名单：发现恶意 IP 直接拉黑。

这样即使有脚本，也只能以人类速度访问，系统稳如泰山。

### 面试怎么答
**"短链系统要防缓存穿透：入口用布隆过滤器挡不存在的短码，Redis 对查不到的短链缓存短时空值；网关层再做 IP 限流防脚本刷量"**。能说出"布隆过滤器挡不存在 + 空值缓存兜底"这一组合拳，就说明你考虑到了真实线上的攻击场景，比只背概念的人高一个段位。

## 7. 可补充：布隆过滤器的通俗原理

### 一句话回答
布隆过滤器 = 一个**全是 0 的位数组** + **多个哈希函数**：写入数据时把几个哈希位置都置成 1；查询时看这几个位置——**只要有一个是 0，数据一定不存在；全为 1，才"可能"存在**。

### 展开讲：两个操作

**写入（登记一个短码）**：

1. 拿 3 个（也可以是 N 个）不同的哈希函数，分别对短码做计算，得到 3 个哈希值；
2. 每个哈希值对位数组长度取模，得到 3 个位置；
3. 把这 3 个位置全部置为 1。

**查询（判断一个短码在不在）**：

1. 同样用这 3 个哈希函数算出 3 个位置；
2. 检查这 3 个位置：**只要有 1 个位置是 0** → 这个短码**一定没被登记过**（因为登记时会把对应位置置 1，位置是 0 就说明从没人登记到这儿）；
3. 3 个位置**全是 1** → 只能说**"可能存在"**——因为有可能别的短码的哈希位置和它重合了，把位置"借"给了它（误判）。

### 展开讲：误判率与特性

| 布隆过滤器的回答 | 真实含义 | 能否直接采信 |
|---|---|---|
| "不存在" | 一定不存在 | ✅ 放心信，直接挡掉 |
| "可能存在" | 可能真存在，也可能误判 | ⚠️ 放行去查真正的存储 |

**误判不会漏掉真数据**：真存在的短码一定被置过 1，查询一定放行；可能误判的只是"不存在的东西被放进去查一次"，最多浪费一次查询，不会出大错。用**位数组更长、哈希函数更多**，误判率可以压得很低（比如 1% 以下）。

### 比喻
像**机场安检门的"已登记名单"**：每个登记过的乘客（已生成的短链），会在名单上盖几个章（置 1）。安检员查人时：**名单上对应格子有一个是空的，这人肯定没登记过**，直接拦下；格子全有章，也可能是有人的章盖重合了（误判），放进去再核验一次就行。布隆过滤器最妙的地方是：**"没登记"的判断绝对可信，放行的判断可以再核实**——正好用在"先挡掉不存在的短链"这个场景。

### 面试怎么答
三句话讲完：**"布隆过滤器是位数组 + 多个哈希函数，写入置 1、查询看位；只要有一位是 0 就一定不存在，全为 1 才可能存在；用它做缓存穿透的第一道闸门，配合空值缓存兜底"**。再补一句特性总结：**"它保证不漏报，只可能有误报"**，这个特性是它能用来挡穿透的根本原因。

## 8. 总结：完整流转链路

### 一句话回答
短链系统一条完整链路是：**用户请求转换长链 → 分布式 ID 发号器拿唯一数字 → Base62 转成 6 位字符 → 存 MySQL 和 Redis → 用户点击短链 → 命中 Redis 缓存 → 返回 HTTP 302 完成跳转**，中间穿插布隆过滤器、空值缓存、IP 限流三道防线。

### 展开讲：两条链路分别走

**链路一：生成短链（长 → 短，低频写）**

```
用户提交长链接
   ↓
① 分布式 ID 发号器（Redis INCR / MySQL 号段）→ 拿到唯一数字，如 10086
   ↓
② Base62 转换（十进制转 62 进制，除法取余）→ 得到短码 "2cq"
   ↓
③ 存入 MySQL（short_code 唯一索引兜底防重）
   ↓
④ 回填 Redis 缓存（link:2cq → 长链接）
   ↓
返回短链 https://dwz.cn/2cq 给用户
```

**链路二：点击跳转（短 → 长，高频读）**

```
用户点击短链 https://dwz.cn/2cq
   ↓
① 布隆过滤器问"2cq 存在吗？" → 不存在直接 404，挡住恶意请求
   ↓
② 查 Redis 缓存 link:2cq → 命中直接拿长链接
   ↓
③ 未命中 → 查 MySQL → 回填 Redis（查不到则缓存短时空值）
   ↓
④ 返回 HTTP 302 + Location: 长链接
   ↓
⑤ 浏览器自动发起第二次请求 → 用户看到目标页面
```

### 设计要点回顾

| 环节 | 关键设计 | 一句话理由 |
|---|---|---|
| 生成 | 发号器 + Base62 | 不冲突，容量 568 亿 |
| 跳转 | `302` + `Location` | 每次经过服务器，能统计点击 |
| 存储 | MySQL 两列表 + 唯一索引 | 数据持久化，防重复 |
| 读 | Redis 缓存优先 | 读多写少，扛高并发 |
| 防攻击 | 布隆过滤器 + 空值缓存 + IP 限流 | 挡住穿透与刷量 |

### 本节小结
短链系统不复杂，但每个环节都踩在经典考点上：`302` 而非 `301`（统计）、发号器 + Base62（生成）、Redis 缓存（抗读并发）、布隆过滤器 + 空值缓存（防穿透）。把这条"生成 → 存储 → 跳转"的链路在脑子里走一遍，面试时从需求讲到兜底，层层递进，就是一份完整的高分答案。
