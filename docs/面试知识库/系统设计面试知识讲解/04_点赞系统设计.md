# 04 点赞系统设计

本章覆盖：点赞场景的高频读写分析（为什么直接写 MySQL 会被打挂）、"Redis 扛读写 + 异步同步 MySQL"的核心思路、Redis Set 存储设计（`sadd`/`srem`/`sismember`/`scard`）、String + `incr/decr` 的进阶优化、MQ 异步削峰落库 MySQL、大 V 热点 Key 与本地缓存合并方案、点赞接口设计要点与操作时序。

## 1. 场景分析：点赞系统到底难在哪里？

### 一句话回答
点赞系统的难点是**高频读写**：短时间可能有几十万用户同时点赞/取消点赞，同时每个用户点开内容都要立刻知道"**总赞数**"和"**我点过没有**"——如果所有读写都直接打 MySQL，数据库瞬间就被打挂。

### 展开讲：拆解"高频读写"

先看一次点赞发生了什么。用户点一下"👍"：

- **写**：这条内容的赞数 +1，还要记录"用户 A 给内容 X 点过赞"这个状态（防止重复点赞、用于点亮红心）；
- **读**：用户点开内容页的瞬间，页面要显示"总赞数 10086"和"👍 已点亮/未点亮"——也就是要查"总赞数"和"我有没有点过"。

麻烦在于这两件事都是**高频**的：

- 明星发一条微博，几十万人在几十分钟内涌入点赞，**写入 QPS（每秒请求数）瞬间飙升**；
- 每个用户进入内容页都要**读**赞数和点赞状态，一条爆款内容的**读取量是点赞量的几倍甚至几十倍**；
- 用户还会反复操作：点赞 → 取消 → 再点赞，一条内容在短时间内被反复写。

**为什么传统方案会被打挂？** 如果直接让 MySQL 扛：

- MySQL 数据在磁盘上，每秒能处理的读写量有限（单机几千到一两万 QPS），几十万的并发一来，**连接池先被占满**，后面的请求全部排队超时；
- 每次点赞都要 `UPDATE` 总赞数（行锁），同一行被几十万人抢着改，**锁竞争**让性能雪上加霜；
- "我点过没有"这种查询，如果表数据量大，**索引都救不回来**，一个查询扫半天。

结论：**点赞系统天生是"内存型"场景，必须用 Redis 这种内存数据库扛住瞬时高频，再想办法把数据沉淀到 MySQL。**

### 比喻
点赞像**演唱会门口的签名墙**：粉丝（用户）涌上来签名（点赞），几十万人挤在一起，如果每个人都要找工作人员（MySQL）翻厚厚的登记本（数据库表）确认"我签过没"、再改一遍总数，工作人员瞬间被淹没，队伍彻底瘫痪。聪明的做法是：**墙边放一块大白板（Redis），大家直接在白板上签到、数人头**，又快又不会挤爆；晚上演出结束，工作人员再慢悠悠把白板上的签名誊抄到正式登记本（MySQL）上存档。

### 面试怎么答
先定性：**"点赞是典型的高频读写场景：写是瞬时高并发点赞，读是每个用户都要查总赞数和我的状态"**；再点破传统方案的死穴：**"直接写 MySQL 扛不住连接池和行锁，所以核心读写必须交给 Redis"**。一上来就把"为什么用 Redis"讲清楚，比直接背方案强得多。

## 2. 核心思路：一句话说清点赞系统的整体设计

### 一句话回答
点赞系统的核心思路是：**所有核心读写完全交给 Redis 内存完成**（快、抗并发），**再异步悄悄同步到 MySQL 永久保存**（稳、不丢数据）——用户操作秒级响应，数据库压力被削平。

### 展开讲：这句话拆成三层

1. **读走 Redis**：总赞数、点赞状态都存在 Redis 里，查询微秒级返回，不碰 MySQL；
2. **写走 Redis**：点赞/取消点赞直接改 Redis，毫秒级完成，用户立刻看到红心点亮/熄灭；
3. **MySQL 异步落库**：Redis 是内存数据库，**怕丢数据**（宕机、重启数据就没了），所以点赞成功后**发一条消息给消息队列（MQ）**，由后台消费者把点赞记录和总数**分批、慢慢**写进 MySQL——用户感觉不到这个"悄悄存档"的过程。

### 展开讲：为什么这个顺序是"先 Redis、后 MQ、最后 MySQL"

这个顺序不是随便排的，每一步都有明确理由：

| 环节 | 干什么 | 为什么放在这一步 |
|---|---|---|
| Redis | 承接所有实时读写 | 内存快，能扛十万级 QPS，用户无感 |
| MQ | 削峰填谷，缓冲写压力 | 点赞洪峰来时先"排队"，消费者按自己的节奏慢慢消费 |
| MySQL | 永久存储，最终存档 | 磁盘慢但可靠，只承受"消费速度"的压力，永远打不垮 |

用户请求经过 Redis 立刻返回，**响应快**；MySQL 虽然晚一点拿到数据，但**最终一定会一致**（最终一致性）——中间有一两秒的延迟，用户根本感知不到，这就是"先 Redis 后 MQ 最后 MySQL"的合理性。

### 比喻
像**外卖店的处理流程**：顾客下单（点赞）→ 前台立刻接单、收钱、告诉顾客"好了"（Redis 秒回）→ 小票塞进订单箱（MQ 排队）→ 后厨按自己的节奏一单一单慢慢做（消费者慢慢写 MySQL）。顾客要的是"下单成功"的即时反馈，后厨慢慢做不会让顾客饿死，只要最终送到就行。

### 面试怎么答
一句话亮出架构：**"Redis 扛实时读写，MQ 削峰，MySQL 异步落库，最终一致"**。然后解释顺序：**"Redis 快所以扛前台，MQ 缓冲所以扛洪峰，MySQL 只承受消费速度的写入所以永远安全"**。这个"三层递进"的表述就是点赞系统的骨架，后面所有细节都是往骨架上填肉。

## 3. 第一步：Redis 存储设计——用 Set 集合存点赞

### 一句话回答
每个内容用 Redis 的一个 **Set（集合）** 来管点赞：集合里存的是所有点过赞的用户 ID——点赞就是 `sadd` 把用户塞进去，取消就是 `srem` 移出来，"我点过没"用 `sismember` 查，总赞数用 `scard` 数集合大小，四个命令全搞定。

### 展开讲：先认识 Set 集合

Redis 的 `Set` 是**无序、不重复**的字符串集合，完美契合点赞语义：

- **不重复**：同一个用户不可能在集合里出现两次 → 天然防止"一个用户点两次算两赞"；
- **无序**：赞谁先谁后不重要；
- **集合操作快**：增、删、查、数个数全是 O(1)，几十万用户在一个集合里也毫无压力。

以内容 ID 为 `10086` 为例，key 的命名约定为 `article:likes:10086`——**"业务:类型:ID"** 三段式命名，一眼就能看懂这个 key 是什么。

### 展开讲：四个核心命令

**① 用户 A 点赞 → `sadd`（把用户塞进集合）**

```
127.0.0.1:6379> SADD article:likes:10086 userA
(integer) 1
```

返回值 `1` 表示成功加入。如果用户 A 再点一次，集合里已有他，`sadd` 返回 `0`，**不会重复添加**——重复点赞自动被忽略。

**② 用户 A 取消点赞 → `srem`（把用户移出集合）**

```
127.0.0.1:6379> SREM article:likes:10086 userA
(integer) 1
```

返回值 `1` 表示成功移除；如果用户本来就没点过赞，返回 `0`，什么也不发生。

**③ 判断"我点过没有" → `sismember`（查集合里有没有我）**

```
127.0.0.1:6379> SISMEMBER article:likes:10086 userA
(integer) 1      # 1 = 点过，红心点亮
127.0.0.1:6379> SISMEMBER article:likes:10086 userB
(integer) 0      # 0 = 没点过，红心是灰的
```

用户每次打开内容页，前端就用这个命令拿到自己的点赞状态，**微秒级返回**。

**④ 总赞数 → `scard`（数集合里有多少人）**

```
127.0.0.1:6379> SCARD article:likes:10086
(integer) 10086
```

页面右上角显示的"赞 10086"就是它，不用专门维护一个计数器，集合大小就是赞数，**永远和集合内容一致，不会算错**。

### 展开讲：伪代码串一遍完整操作

```python
def like(content_id, user_id):
    key = f"article:likes:{content_id}"
    redis.sadd(key, user_id)        # 点赞：塞入集合（幂等，重复点无效）
    return "ok"

def unlike(content_id, user_id):
    key = f"article:likes:{content_id}"
    redis.srem(key, user_id)        # 取消：移出集合
    return "ok"

def get_status(content_id, user_id):
    key = f"article:likes:{content_id}"
    liked = redis.sismember(key, user_id)   # 我点过吗
    count = redis.scard(key)                # 总赞数
    return {"liked": liked, "count": count}
```

### 补充进阶：超大平台用 String + `incr/decr` 分开存总数

抖音这种量级，一个视频的点赞请求可能是百万级的，虽然 Set 的单个命令也很快，但**集合里的成员会越攒越多**，而且"数集合大小"（`scard`）每次都要遍历整个集合。所以超大平台会把"**点赞状态**"和"**总赞数**"**拆开存**：

- **点赞状态**：依然用 Set（`video:likes:10086`）存用户 ID，负责"我点过没"；
- **总赞数**：单独用一个 String（`video:likecount:10086`），用**原子加减**维护：

```
127.0.0.1:6379> INCR video:likecount:10086      # 点赞，总数 +1
(integer) 10087
127.0.0.1:6379> DECR video:likecount:10086      # 取消，总数 -1
(integer) 10086
```

`incr`/`decr` 是**原子操作**（不会出现两个请求同时 +1 结果只加了一次的情况），维护一个计数器比遍历集合快得多，展示总数时只读这一个 key 就行。

**注意细节**：拆开后要先判断"这次点赞是否有效"再决定要不要动计数器——比如用户 A 已经点过赞又发来点赞请求（`sadd` 返回 0），就不能再 `incr`，否则总数虚高。所以顺序必须是：**先 `sadd`/`srem` 改状态，根据返回值决定是否 `incr`/`decr` 总数**。

### 比喻
Set 集合像**班级的纸质签到表**：谁来了就在名字后打个勾（`sadd`），走了就擦掉（`srem`），点名时看有没有你的勾（`sismember`），数一数有多少个勾就是出勤人数（`scard`）。签到表不会出现同一个人两个勾，也不会数错人。进阶版的 String 计数器，则像旁边再挂一块**电子计数牌**：签到表负责"谁来了"，计数牌负责"来了多少人"，各司其职、互不拖累。

### 面试怎么答
先报四个命令：**"点赞 `sadd`、取消 `srem`、判断 `sismember`、总数 `scard`，全在 Set 上完成，O(1) 复杂度"**；再主动补进阶：**"超大平台会把状态（Set）和总数（String + `incr`/`decr`）拆开，展示总数只读计数器，性能更好，但要注意根据 `sadd` 返回值决定是否 `incr`，避免总数虚高"**。能说出这个"拆开 + 防虚高"的细节，说明你不仅会用 Redis，还懂真实场景的坑。

## 4. 第二步：持久化到 MySQL——MQ 异步削峰落库

### 一句话回答
Redis 是内存数据库，**宕机/重启数据就丢了**，所以必须把点赞数据落库 MySQL（"点赞明细表"+"内容汇总表"）；但**不能同步写**（会拖慢用户响应、扛不住洪峰），而是把点赞消息丢进 **MQ**，消费者**攒一批写一批**，平滑慢速写入 MySQL——这就是**异步削峰**。

### 展开讲：为什么要落库 MySQL

Redis 再快，本质还是**内存**：断电、宕机、重启，内存里的东西说没就没。点赞数据要是只有 Redis 一份，一次宕机，所有赞数全部清零，运营哭都没地方哭。所以必须有"永久存档"——MySQL 落库，数据才能长期保存、才能做报表、才能恢复 Redis。

### 展开讲：落哪些表

**① 点赞明细表**（记录"谁赞了哪条内容"）

```sql
CREATE TABLE like_record (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  content_id BIGINT NOT NULL,          -- 被赞的内容
  user_id    BIGINT NOT NULL,          -- 点赞的用户
  status     TINYINT DEFAULT 1,        -- 1 点赞 / 0 取消
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_content_user (content_id, user_id)   -- 同一个人对同一内容只有一条记录
);
```

**② 内容汇总表**（记录"每条内容的总赞数"）

```sql
CREATE TABLE like_count (
  content_id BIGINT PRIMARY KEY,
  like_count BIGINT NOT NULL DEFAULT 0,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

明细表回答"**谁**赞了"，汇总表回答"**多少**赞"，两张表配合，既查得到个人状态，又出得了总数。

### 展开讲：为什么不能同步写，要用 MQ 异步写

如果用户点一下赞，Redis 更新完**当场**再去写 MySQL：

- **用户响应变慢**：一次请求要等磁盘写入完成才返回，本来 1 毫秒能响应的事变成 50 毫秒，体验变差；
- **数据库扛不住洪峰**：几十万点赞瞬间涌入，MySQL 同时收到几十万条 INSERT/UPDATE，和第一节说的一样，直接打挂；
- **高并发写同一行**：汇总表同一行被疯狂 UPDATE，行锁把性能拖到地板。

正确姿势是**先给用户响应，再慢慢存档**：

```
用户点赞 → Redis 秒回 → 同时发一条消息到 MQ
                            ↓（消费者慢慢消费）
                    攒批 → 批量写 MySQL（明细表 + 汇总表）
```

**MQ 在这里的角色是"削峰填谷"**：点赞洪峰再猛，MQ 都先"吞"下来排队；消费者按自己的节奏（比如每秒只消费 1000 条）慢慢处理，数据库永远只承受"消费速度"的压力，而不是"洪峰速度"的压力。洪峰过去之后，MQ 里的积压消息继续被消费，直到全部落库——**高峰削平、低谷填满**，数据库的负载曲线被拉成一条平线。

**批量写（攒批）**：消费者不一条一条写，而是**攒够一批（比如 100 条）或每隔 1 秒**，用一条批量 SQL 写进去，把几十次磁盘 IO 合并成一两次，吞吐量翻几倍：

```sql
-- 攒批后一次性批量插入明细
INSERT INTO like_record (content_id, user_id, status) VALUES
(10086, 1001, 1), (10086, 1002, 1), (10087, 1003, 1), ...;
```

### 比喻
像**餐厅传菜**：客人点完菜（点赞），服务员先口头应一声"好嘞"（Redis 秒回），再把菜单**夹到厨房的订单夹上**（发消息到 MQ）；厨房不催不动，**攒够几张单子一起做**（攒批批量写），高峰期也不会把厨房挤爆。要是每道菜都等厨房现炒完再回话（同步写 MySQL），客人早饿跑了。

### 面试怎么答
先讲必要性：**"Redis 是内存的，怕丢，必须落 MySQL；明细表记谁赞的，汇总表记总数"**；再讲方式：**"不能同步写，点赞成功后发消息到 MQ，消费者攒批批量写库，把洪峰削成平流，这叫异步削峰"**。最后补一句点睛：**"用户感知是秒回，数据最终一致，丢了中间一两秒没关系，最终一定落库"**。

## 5. 第三步：大 V 热点问题——热点 Key 与本地缓存合并

### 一句话回答
顶流明星发一条微博，几百万人同时点赞，请求全部打在**同一个 Redis key**（`article:likes:10086`）上，单台 Redis 会被打爆——这就是**热点 Key 问题**；解法是在**应用进程里加本地缓存（Local Cache）**，先汇总再合并更新 Redis，把 Redis 的压力成百上千倍降下来。

### 展开讲：热点 Key 是什么、为什么危险

普通的点赞请求是"雨露均沾"的，一万条内容各有一万人点，Redis 每台机器各扛一部分，没事。但顶流明星发一条微博，**几百万人全去点同一个 key**：

- 单 key 的所有操作都落在**同一台 Redis 实例**上（即使 Redis 做了集群，同一个 key 也只存在一个分片里），没法分散；
- 这台 Redis 的 CPU、网络带宽瞬间被打满，请求排队超时；
- 更糟的是，超时的请求会**重试**，重试又加重负载，形成"**雪崩式恶性循环**"，最终整个 Redis 集群被拖垮。

就像演唱会散场时**几万人全挤同一个出口**，其他出口（其他 key）空着，这一个出口（热点 key）堵死，谁都出不去。

### 展开讲：解决方案——本地缓存（Local Cache）+ 合并更新

**第一步：本地缓存"接住"大部分请求**

在每个**应用进程（JVM）内存里**放一个本地缓存（比如 Java 的 `Guava Cache`、`Caffeine`）。用户点赞时：

1. **先查本地缓存**：热点内容的总赞数存在进程内存里，读取不经过网络，比查 Redis 还快；
2. 本地缓存**有** → 直接在本地 +1，返回成功（如果本地缓存了点赞状态，`sismember` 也在本地完成）；
3. 本地缓存**没有/过期** → 才去查一次 Redis，查完回填本地。

注意：每个应用进程的本地缓存是**各自一份**的（进程内内存没法共享），所以它存的是"**可能不太准、但足够新**"的数据——对点赞这种最终一致就够的业务，完全够用。

**第二步：汇总合并，攒着更新 Redis**

本地缓存的赞数不能改一次就同步一次 Redis（那和直接打 Redis 没区别），而是**每隔一两秒**（或攒够一定量），把这段时间**新增的赞数汇总成一次请求**，批量更新 Redis：

```
用户 A 点赞 → 本地 +1（进程内存，秒回）
用户 B 点赞 → 本地 +1
用户 C 点赞 → 本地 +1
   ... 1 秒内 1 万个请求全部在本地消化 ...
每秒定时任务 → 汇总新增 1 万赞 → 一次 INCRBY 更新 Redis
```

```python
# 每 1.5 秒执行一次的合并任务
def flush_local_cache():
    delta = local_counter.get_and_reset()           # 拿这 1.5 秒新增的赞数，并清零
    if delta > 0:
        redis.incrby("article:likecount:10086", delta)   # 合并成一次更新
    # 点赞状态明细同样攒批发到 MQ
```

效果：假如 1 秒内有 1 万个点赞请求，原来 Redis 要处理 1 万次；现在本地缓存消化 1 万次，Redis 只收到 **1 次**合并更新——**压力成百上千倍下降**，热点 Key 直接降温。

**第三步：仍要兜底**

- 本地缓存要设**过期时间**，防止陈旧数据一直占着；
- 缓存一致性要求高的场景，可以本地缓存只缓存"总数"，"点赞状态"仍查 Redis（或者用更短的本地区过期时间）；
- 极端情况下可以给热点 key 做**多副本缓存**（把同一个 key 复制几份分散到不同分片），进一步分摊压力。

### 比喻
热点 Key 像**顶流明星签名会**：几万人只找这一个人签名（同一个 key），明星累死也签不完（Redis 被打爆）。解决办法是请几个**助理（本地缓存）**先帮忙收下签名请求、记在助理自己的小本本上，每过一两分钟把一批签名统一拿给明星签（合并更新）——明星的工作量从几万次变成几十次，轻松搞定。

### 面试怎么答
**"热点 Key 的问题在于几百万请求打同一个 Redis key，单机扛不住；解法是进程内本地缓存（Guava Cache）接住大部分请求，每隔一两秒把新增赞数汇总成一次 `incrby` 合并更新 Redis，压力降低成百上千倍"**。再补一句权衡：**"本地缓存是进程内的，各实例不共享，所以接受短暂不精确，靠定时合并保证最终一致"**——知道"为什么可以接受不精确"，是这道题答出深度的关键。

## 6. 总结：点赞系统全貌与完整链路

### 一句话回答
点赞系统的完整链路是：**前端请求 → 拦截器校验 → Redis 处理点赞状态（Set）和总数 → 立即返回前端 → MQ 异步削峰批量落库 MySQL**，遇到大 V 爆款内容，再加**本地缓存汇总合并**保护 Redis——层层分工，各司其职。

### 展开讲：完整流转图

```
用户点击"👍"
   ↓
① 前端请求 → 拦截器校验（登录态？参数合法？频率限制？）
   ↓
② Redis 处理：SADD 用户进 Set（状态） + INCR 总数（计数）
   ↓
③ 立即返回前端："点赞成功"，红心点亮，赞数 +1（毫秒级）
   ↓
④ 同时发一条消息到 MQ（记录这次点赞）
   ↓
⑤ MQ 消费者攒批 → 批量写 MySQL 明细表 + 汇总表（平滑落库）
   ↓
⑥ 用户下次打开内容页：Redis 查"我点过没"（SISMEMBER）+ 总赞数（SCARD）
```

**热点内容走另一条快车道**：

```
顶流明星的内容被疯狂点赞
   ↓
应用进程本地缓存（Guava Cache）先接住，本地 +1，秒回用户
   ↓
每隔 1~2 秒汇总新增赞数 → 合并成一次 INCRBY 更新 Redis
   ↓
Redis 再按正常流程发 MQ → 落库 MySQL
```

### 展开讲：每层各自的职责

| 层 | 组件 | 职责 | 为什么需要它 |
|---|---|---|---|
| 入口 | 拦截器 | 校验登录态、参数、限流 | 挡住非法请求，防止刷赞 |
| 实时层 | Redis Set + String | 点赞状态、总赞数 | 内存快，扛十万级 QPS |
| 缓冲层 | MQ | 承接写流量，削峰 | 把洪峰变成平流，保护 MySQL |
| 持久层 | MySQL 明细表 + 汇总表 | 永久存档 | 数据不怕丢，可恢复、可统计 |
| 加速层 | 本地缓存 | 热点内容合并更新 | 让 Redis 从几百万次压力降到几百次 |

### 本节小结
点赞系统的本质是**"快与稳的分离"**：Redis 负责快（实时读写、秒回用户），MQ 负责稳（削峰缓冲），MySQL 负责久（永久存档），本地缓存负责省（热点合并）。面试时从场景分析讲起，沿着"Redis → MQ → MySQL"三层递进，最后用大 V 热点补上点睛之笔，就是一套完整且有条理的高分答案。

## 7. 可补充：点赞接口设计要点

### 7.1 幂等性：同一个请求不能生效两次

#### 一句话回答
点赞接口必须**幂等**：同一个用户对同一条内容重复调用点赞接口（网络重试、用户连点、脚本重复请求），结果必须和调用一次一样——不能因为重复请求导致赞数 +2。

#### 展开讲
Redis 的 Set 天然帮我们实现了幂等：`sadd` 重复添加同一个用户返回 `0`，不会重复入集合；所以点赞逻辑要**以 `sadd` 的返回值为准**：

```
SADD article:likes:10086 userA → 返回 1（新增，第一次点赞）→ 才 INCR 总数
SADD article:likes:10086 userA → 返回 0（已存在，重复请求）→ 不动总数
```

同理取消点赞：`srem` 返回 `1` 才 `decr`，返回 `0` 说明本来就没点过，不动总数。这样无论请求重复多少次，总数和状态都只会变一次——**幂等靠"先改状态、按返回值决定是否动计数"的顺序保证**。

### 7.2 Redis 操作时序：先改状态，再动计数

#### 一句话回答
点赞/取消点赞时，**必须先操作 Set 改状态，根据返回值再决定是否增减计数**——顺序反了，就会出现"状态没改成功但计数变了"或"计数虚高"的错误。

#### 展开讲
正确的时序：

```python
def like(content_id, user_id):
    added = redis.sadd(f"article:likes:{content_id}", user_id)  # ① 先改状态
    if added == 1:                                              # ② 新增才动计数
        redis.incr(f"article:likecount:{content_id}")           # ③ 总数 +1
    return "ok"

def unlike(content_id, user_id):
    removed = redis.srem(f"article:likes:{content_id}", user_id)  # ① 先改状态
    if removed == 1:                                              # ② 确实移除了才动计数
        redis.decr(f"article:likecount:{content_id}")             # ③ 总数 -1
    return "ok"
```

两个命令虽然不能保证"绝对原子"（极端情况下中间断电），但 Redis 单命令本身是原子的，这套顺序在绝大多数场景下已经把"计数和状态不一致"的概率降到最低；要求更高的系统可以用 Lua 脚本把两步包成一个原子操作：

```lua
-- 点赞（Lua 脚本，两步原子执行）
if redis.call('sadd', KEYS[1], ARGV[1]) == 1 then
    return redis.call('incr', KEYS[2])
else
    return -1   -- 重复点赞，不计数
end
```

### 7.3 为什么"先 Redis 后 MQ 最后 MySQL"的顺序是合理的

#### 一句话回答
因为**响应快**（用户只等 Redis，毫秒级返回）和**数据最终一致**（MQ 慢慢落库，MySQL 永远不被冲垮）可以同时满足——用户要的是"即时反馈"，系统要的是"数据不丢"，这个顺序正好各取所需。

#### 展开讲
- **响应快**：点赞请求到 Redis 就返回了，全程不碰磁盘、不碰 MQ（发消息也是异步的），用户感觉"秒赞"；
- **数据最终一致**：MQ 里的消息最终一定会被消费，MySQL 最终一定会有这笔记录；即使某一刻 MySQL 和 Redis 数据有差距（比如差 1 秒），用户完全感知不到，业务也完全接受；
- **系统稳**：三个组件各扛各的——Redis 扛前台并发、MQ 扛流量洪峰、MySQL 扛持久化，任何一个环节都不会成为被击穿的短板。

这也正是所有"高并发 + 数据持久化"系统的通用范式：**热数据用内存、流量用队列削峰、冷数据落磁盘**。点赞系统只是这个范式的一个经典实例。

### 比喻
像**便利店收银 + 记账**：顾客扫码付款（点赞），收银机（Redis）立刻显示"支付成功"（秒回），小票（MQ）排队进入后台系统，会计（消费者）下班前把今天所有账目批量录入总账（MySQL）——顾客要的是"付成功了"的即时反馈，账本最终一定对得上，这就是"先收银、后排队、最后记账"的顺序之美。

### 本节小结
点赞接口的三个要点：**幂等**（`sadd` 返回值判断重复）、**时序**（先改状态再动计数，必要时 Lua 脚本原子化）、**分层顺序**（Redis 快、MQ 稳、MySQL 久）。把它们讲透，点赞系统从存储到接口到架构就全部闭环了——这也是一道系统设计题最完整的答法。
