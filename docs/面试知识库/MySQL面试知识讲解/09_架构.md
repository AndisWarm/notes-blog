# 09 架构

本章覆盖：MySQL 主从复制原理、主从延迟的处理方法、分表与分库的区别。

---

## 1. MySQL 主从复制了解吗？

### 一句话回答
主从复制 = **主库（Master）把 binlog 同步给从库（Slave），从库重放 binlog 保持数据一致**，实现读写分离、容灾备份。核心是三个线程：主库 **dump 线程**、从库 **IO 线程**和 **SQL 线程**。

### 复制原理（三大线程，必背）

```
┌─────────────────────┐         ┌─────────────────────┐
│ 主库 Master          │         │ 从库 Slave           │
│                     │ binlog  │                     │
│ ① 写操作 → binlog   │ ───────▶│ ② IO线程 拉取 binlog │
│                     │         │     ↓               │
│ ④ dump线程 推 binlog │         │ ③ 写入 relay log     │
│                     │ ◀───────│ ⑤ SQL线程 读 relay   │
│                     │         │    log 重放          │
└─────────────────────┘         └─────────────────────┘
```

**① 主库记录 binlog**：所有写操作（事务提交后）写入 binlog
**② 从库 IO 线程**：主动连主库，请求"从指定 binlog 位置开始的数据"
**③ 主库 dump 线程**：读取 binlog 发给从库（5.7 后支持半同步/多线程）
**④ 从库写入 relay log（中继日志）**：IO 线程把收到的 binlog 原样落盘
**⑤ 从库 SQL 线程**：读取 relay log 并重放，完成数据同步

从库记录两个关键位置：
- `relay log` 读到的位置（SQL 线程进度）
- binlog 拉到哪了（IO 线程进度）

### 三种复制模式（按 binlog 格式）

| 模式 | 原理 | 特点 |
|------|------|------|
| 异步复制 | 主库提交后不管从库 | 最快，主库挂了可能丢数据 |
| 半同步复制（5.5+） | 主库等**至少一个从库**确认收到 binlog 才提交 | 不丢数据（增强），延迟略高 |
| 全同步复制 | 等所有从库确认 | 最安全但极慢，基本不用（MySQL 没有原生全同步） |

### 为什么要主从复制？

1. **读写分离**：主库写、从库读，读压力分流（互联网标配）
2. **高可用**：主库挂了，从库提升为主库（MHA/Orchestrator 等工具）
3. **容灾备份**：从库是实时的备份
4. **数据分析**：报表查询走从库，不干扰主库业务

### 面试回答模板
"主从复制三线程：主库 dump 线程发 binlog，从库 IO 线程拉 binlog 写 relay log，SQL 线程重放。异步默认（快但可能丢）、半同步（等一个从库确认，不丢）、全同步（不用）。用途：读写分离、高可用、容灾、报表隔离。"

## 2. 主从延迟都有什么处理方法？

### 一句话回答
主从延迟 = **从库重放速度跟不上主库写入速度**。应对分两个层面：**架构层面**（读写分离改规则、强制走主库）和**技术层面**（并行复制、优化从库配置、分库分散压力）。

### 先明确：为什么会有延迟？

1. 主库是**并发写**，从库是**单线程重放**（老版本 SQL 线程只有一个）——吞吐量天然差一个数量级
2. 从库还要做其他查询（报表），挤占资源
3. 大事务（binlog 巨大）重放时间长
4. 网络传输延迟

### 处理方法（面试分类背）

**① 读请求分类，必要时走主库**
```text
实时性要求高（刚下单查订单状态）→ 主库读
实时性要求低（历史数据、统计）→ 从库读
```
核心思想：**"读己之写"必须走主库**——用户刚写的数据要立刻读到自己写的。

**② 强制从库/主库策略**
- 写后读：写入后带"版本/时间戳"，读时如果从库落后则改查主库
- 或用中间件（ShardingSphere、MyCat）的 `hint` 强制走主库

**③ 并行复制（从库技术优化）**
- 5.6：按库并行（不同库并行重放）
- 5.7/8.0：**按事务并行**（基于 WRITESET，同一行冲突的事务串行、不同行的事务并行）——这是最有效的优化，`slave_parallel_workers` 调大
```sql
-- 8.0 配置示例
SET GLOBAL slave_parallel_workers = 8;   -- 并行线程数
SET GLOBAL slave_parallel_type = LOGICAL_CLOCK;
```

**④ 缩短大事务**
- 大事务 binlog 大，重放慢 → 拆成小批次
- 避免一次性 DELETE 百万行

**⑤ 从库配置优化**
- 从库磁盘用 SSD（重放是随机写）
- 调大 redo log、buffer pool
- 从库不开慢查询日志等额外开销

**⑥ 一主多从 / 分库**
- 多个从库分摊读压力
- 业务分库，把热点库的写入分散

**⑦ 监控延迟**
```sql
-- 从库执行：看延迟秒数（0 表示无延迟）
SHOW SLAVE STATUS\G   -- Seconds_Behind_Master 字段
```

### 面试回答模板
"延迟根因是从库重放是串行的、还有资源竞争。解法分层：读分类（实时读走主库）；并行复制（WRITESET 多线程重放，最有效）；拆大事务；从库 SSD+调参；一主多从分库分压；配合 Seconds_Behind_Master 监控。设计原则：'永远别指望从库数据跟主库零延迟'，实时性要求高的读必须走主库。"

## 3. 分表和分库是什么？有什么区别？

### 一句话回答
**分表**：一张大表拆成多张小表（数据不变多，变"薄"）；**分库**：数据分散到多个数据库实例（数据变多，变"宽"）。分表解决"单表太大查询慢"，分库解决"单库连接/容量/写入瓶颈"。垂直分和水平分是两种拆分维度，分表分库都能各自套用。

### 先分清两个维度

**维度一：垂直拆分（按"字段/功能"切）**

| | 垂直分表 | 垂直分库 |
|---|----------|----------|
| 做法 | 一张宽表拆成多张窄表（常用字段一张、大字段/低频字段一张） | 按业务域拆库：用户库、订单库、商品库 |
| 解决 | 单行太大、IO 浪费 | 单库压力大、业务解耦 |

```
垂直分表示例：
user(id, name, phone, avatar, bio, address, last_login)
  → 拆成 user_base(id, name, phone) + user_profile(id, avatar, bio, address, last_login)
```

**维度二：水平拆分（按"行"切）**

| | 水平分表 | 水平分库 |
|---|----------|----------|
| 做法 | 同一张表按规则拆成 N 张结构相同的表（user_0, user_1, user_2...） | 同样的表结构分布在 N 个数据库实例（db1.user, db2.user...） |
| 拆分规则 | 取模、范围、哈希、时间 | 同左，但落在不同库 |
| 解决 | 单表数据量大（千万级+） | 单库连接数、容量、IO 瓶颈 |

```
水平分表（同库）：
user_0: id%4=0
user_1: id%4=1
user_2: id%4=2
user_3: id%4=3

水平分库（不同实例）：
db1.user, db2.user, db3.user, db4.user（规则同上）
```

### 区别对比表（面试核心）

| 对比项 | 分表 | 分库 |
|--------|------|------|
| 数据总量 | 不变（拆细） | 增加（分散） |
| 所在实例 | 同一数据库 | 不同数据库/实例 |
| 解决瓶颈 | 单表扫描慢、行锁竞争 | 单库连接数、磁盘、IO、CPU |
| 复杂度 | 低（改 SQL 即可） | 高（跨库事务、跨库 JOIN、全局 ID） |
| 典型规模 | 千万~亿行单表 | 亿级以上、高并发 |

### 拆分带来的问题（必问：分完的代价）

1. **全局唯一 ID**：自增主键失效（多库多表会撞）→ 雪花 ID、号段方案
2. **跨表/跨库 JOIN**：单表 JOIN 没了 → 冗余字段、应用层组装、大宽表
3. **跨库事务**：本地事务失效 → 分布式事务（TCC、本地消息表、Seata）
4. **查询路由**：应用层/中间件要按分片键路由（ShardingSphere、MyCat）
5. **扩容难**：取模分片加库要迁移数据（一致性哈希可缓解）

### 什么时候该用？（面试答分层）

```
第一层：先优化——索引、SQL、缓存、读写分离
第二层：垂直分表（宽表拆窄表）
第三层：水平分表（同库拆 N 张小表）
第四层：水平分库（拆到多实例）
最后才考虑：分库分表中间件 + 分布式事务
```

### 面试回答模板
"分表是'数据变薄'（拆行/拆列），分库是'数据变宽'（拆到多实例）。垂直解决单行大、业务耦合；水平解决单表/单库瓶颈。分库分表是最后的杀手锏：先索引优化、再缓存、再读写分离，真到千万级以上才上分库分表——因为它带来全局 ID、跨库 JOIN、分布式事务三大难题。"

## 4. 补充：读写分离与主从的常见组合方案

### 典型架构图

```
         ┌─────────────┐
 写入 ──▶│  主库 Master │──binlog──▶┌──────────────┐
         └─────────────┘           │ 从库1（读）    │
                                   ├──────────────┤
                                   │ 从库2（读）    │
                                   └──────────────┘
```

- 应用层直连：代码里写死主从两套数据源（简单，早期项目）
- 中间件方案：ShardingSphere / MyCat 透明路由读写
- 高可用：MHA、Orchestrator、MySQL InnoDB Cluster（组复制）

### 面试金句
"读写分离解决'读压力'，分库分表解决'写压力和数据量'，主从复制是前两者的地基。架构演进路线：单机 → 主从+读写分离 → 缓存 → 分库分表 → 分布式中间件。"
