## 1. 事务的特性是什么？如何实现的？

### 一句话回答
事务四大特性 **ACID**：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。实现上：**原子性靠 undo log、持久性靠 redo log、隔离性靠锁 + MVCC、一致性是前三者共同保证的结果**。

### 四大特性逐个讲

**① 原子性（Atomicity）：要么全做，要么全不做**

```sql
-- 转账：扣钱 + 加钱 两步必须同时成功或同时失败
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
```

如果第二步失败，第一步必须**回滚**。
实现：**undo log**。执行每条写操作前，先把"修改前的旧值"记进 undo log；事务回滚时，用 undo log 里的旧值把数据恢复回去。

**② 一致性（Consistency）：事务前后，数据都符合业务规则**

比如"转账后总金额不变"、"账户余额不能为负"。一致性是**结果**，由原子性、隔离性、持久性共同保证，外加业务约束（唯一索引、CHECK 约束、外键）。

面试金句："一致性不是 MySQL 一个组件实现的，而是事务管理 + 约束共同保证的结果。"

**③ 隔离性（Isolation）：并发事务互不干扰**

两个事务同时改同一行，不能乱套。
实现：**锁（行锁/表锁/间隙锁）+ MVCC（多版本并发控制）**。MVCC 让"读不阻塞写、写不阻塞读"，锁保证"写不互相覆盖"（详见本章第 6-8 节）。

**④ 持久性（Durability）：事务提交后，数据永久保存**

即使宕机、断电，已提交的数据不丢。
实现：**redo log**。提交时先写 redo log（顺序写磁盘），再异步刷数据页；宕机重启时用 redo log 重放恢复（详见 08 章第 4 节）。

### 记忆表

| 特性 | 一句话 | 靠什么实现 |
|------|--------|-----------|
| 原子性 | 全做或全不做 | undo log（回滚日志） |
| 一致性 | 数据始终符合业务规则 | 前三者 + 数据库约束 |
| 隔离性 | 并发事务互不干扰 | 锁 + MVCC |
| 持久性 | 提交后不丢失 | redo log（重做日志） |

## 2. MySQL 可能出现什么和并发相关的问题？

### 一句话回答
并发问题本质是**多个事务同时读写同一份数据**导致的三个经典问题：**脏读、不可重复读、幻读**，外加丢失更新（两个问题变体）。

### 三个经典问题

**① 脏读（Dirty Read）：读到别人未提交的数据**

```
事务A: UPDATE 余额 SET 1000（未提交）
事务B: SELECT 余额 → 读到 1000（这是 A 的未提交数据！）
事务A: ROLLBACK → 余额回到 0
事务B: 刚才读到的 1000 是假的（脏数据）
```

危害：B 基于一个"根本不存在"的值做决策。

**② 不可重复读（Non-Repeatable Read）：同一事务内，两次读同一行，值不一样**

```
事务B: SELECT 余额 → 1000
事务A: UPDATE 余额 → 800（已提交）
事务B: SELECT 余额 → 800（同一事务里两次读到不同值！）
```

危害：同一事务内数据不一致，比如统计报表算到一半数据变了。

**③ 幻读（Phantom Read）：同一事务内，两次查询"结果集的行数/内容"不一样，多出了行**

```
事务B: SELECT * FROM 订单 WHERE 金额 > 100 → 3 行
事务A: INSERT 一笔金额 500 的订单（已提交）
事务B: SELECT * FROM 订单 WHERE 金额 > 100 → 4 行（多了一行"幻影"！）
```

危害：新增的行像"幻影"一样出现。注意幻读针对的是**记录集合**（插入/删除），不可重复读针对**单条记录**（修改值）。

### 第四类：丢失更新（Lost Update）

两个事务同时改同一行：
```
事务A: 读余额 1000 → 改成 900
事务B: 读余额 1000 → 改成 800
事务B 先提交（800），事务A 后提交（900）
→ 最终 900，B 的修改"丢了"
```
丢失更新在数据库层（InnoDB 行锁）一般不会发生（写写互斥），但**读改写**组合（应用层先读后写）会通过"更新丢失"的形式出现，通常用 `SELECT ... FOR UPDATE` 或乐观锁解决。

### 三个问题的关系（面试常问）
- 脏读最严重（读到假数据）
- 不可重复读是"值"不一致，幻读是"行集合"不一致
- 隔离级别从低到高逐个解决：读未提交（啥都能读到）→ 读已提交（解决脏读）→ 可重复读（解决不可重复读）→ 串行化（解决幻读）

## 3. 哪些场景不适合脏读，举个例子？

### 一句话回答
一切**基于"别人未提交数据"做决策**的场景都怕脏读：转账对账、库存扣减、余额查询、报表统计、投票计数……凡是对数据正确性敏感的操作，读到脏数据就是事故。

### 具体例子

**场景一：转账**
```
A 给 B 转账，事务中：A 余额 -500（未提交）
此时查询 A 的余额 → 显示少了 500
如果 A 的事务最终回滚 → 刚才显示的余额是假的
用户以为钱扣了，实际没扣 → 客服投诉现场
```

**场景二：库存扣减**
```
用户1 下单：库存 -1（未提交）
用户2 查询库存 → 显示 99（实际库存 100，用户1 还没付完款）
用户2 以为快卖完了，催促下单；用户1 最后取消订单，库存回 100
```

**场景三：并发投票/统计**
- 投票进行中，实时显示票数——票数来自未提交事务的话，会忽高忽低
- 大屏报表、实时大盘数据，全屏脏数据

### 哪些场景"不怕"脏读？
- 对精确性不敏感的**近似统计**：热门榜、在线人数（差几个人无所谓）
- 只读参考数据：商品浏览页的"销量"（显示 100 还是 101 不影响购买决策）
- 这时候故意用低隔离级别（读未提交）换性能，是工程取舍

### 面试回答模板
"对数据正确性敏感的场景都怕脏读：资金、库存、订单、统计报表。因为脏读读到的是**未提交、可能回滚**的数据，一旦事务回滚，之前读到的东西就是假的。低隔离级别只适合对精确度不敏感的读（热榜、在线人数这类近似值场景）。"

## 4. MySQL 是怎么解决并发问题的？

### 一句话回答
两套机制配合：**锁**管"写写冲突"（同一行不能同时被两个事务改），**MVCC** 管"读写冲突"（读不加锁、不被写阻塞，读的是快照版本）。

### 解决矩阵

| 冲突类型 | 解决机制 |
|----------|----------|
| 写 vs 写（同时改同一行） | **锁**：行锁互斥，后到者等待 |
| 读 vs 写（读的人遇到正在改的人） | **MVCC**：读的人读"修改前的旧版本"，不阻塞 |
| 写 vs 读（改的人遇到正在读的人） | **MVCC**：写的人正常改，读的人看旧版本，互不等待 |

### 锁机制（详见 07 章）
- InnoDB 行锁：基于索引记录加锁，写同一行互斥
- 锁有共享锁（S，读锁）和排他锁（X，写锁）
- 锁粒度从"表锁 → 行锁 → 间隙锁"逐级细化

### MVCC（Multi-Version Concurrency Control，多版本并发控制）
核心思想：**不锁数据，而是给数据"留多个历史版本"**。

- 一行数据被修改时，旧版本不直接删除，而是保留在 undo log 里
- 每个事务开始时有一个**事务 ID（trx_id）**和**读视图（ReadView）**
- 读数据时，根据 ReadView 判断"该看哪个版本"：看自己启动时刻之前已提交的版本，看不到"后来者"和"未提交者"
- 所以读操作**永远不需要等写操作**，写操作也**不需要等读操作**

### 一句话总结
"写写用锁排队，读写用 MVCC 快照隔离——这就是 InnoDB 高并发的核心秘密。"

## 5. 事务的隔离级别有哪些？

### 一句话回答
SQL 标准定义了四个隔离级别：**读未提交、读已提交、可重复读、串行化**，从低到高，分别解决脏读、不可重复读、幻读，代价是并发性能逐级下降。

### 四个级别对照表（必背）

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现机制 |
|----------|------|-----------|------|----------|
| 读未提交（READ UNCOMMITTED） | 可能 | 可能 | 可能 | 无 MVCC 快照，直接读最新 |
| 读已提交（READ COMMITTED） | 解决 | 可能 | 可能 | 每次 SELECT 生成新 ReadView |
| 可重复读（REPEATABLE READ） | 解决 | 解决 | 基本解决（InnoDB 特殊） | 事务开始生成 ReadView 并复用 + 间隙锁 |
| 串行化（SERIALIZABLE） | 解决 | 解决 | 解决 | 所有读写加锁，完全串行 |

### 关键说明

**① 读未提交**
- 啥都不防，直接读最新数据（可能读到别人未提交的脏数据）
- 性能最好，正确性最差，生产环境基本不用

**② 读已提交（RC）**
- 每个 SELECT 都生成一个新的**读视图（ReadView）**
- 只能看到"当前时刻已提交"的数据 → 解决脏读
- 但两次 SELECT 的 ReadView 不同 → 同一事务内两次读结果可能不同（不可重复读）
- **Oracle 的默认隔离级别**就是 RC；MySQL 的 RC 也常用于互联网业务（更低的锁开销）

**③ 可重复读（RR）**
- 事务**第一次 SELECT 时**生成 ReadView，之后**一直复用**
- 同一事务内所有读看到的是同一个快照 → 解决不可重复读
- **MySQL 默认隔离级别**
- SQL 标准里 RR 应该允许幻读，但 **InnoDB 用间隙锁把幻读也基本解决了**（详见第 9 节）

**④ 串行化**
- 读加共享锁、写加排他锁，事务一个接一个执行
- 完全隔离但并发度几乎为 0，生产环境极少用

### 面试回答模板
"四级隔离：读未提交（不防）、读已提交（防脏读，Oracle 默认）、可重复读（防不可重复读，MySQL 默认）、串行化（全防但并发最低）。MySQL 的可重复读还通过间隙锁顺带解决了幻读，这是 InnoDB 比标准更严的地方。"

## 6. MySQL 默认级别是什么？

### 答案
**可重复读（REPEATABLE READ）**。

### 怎么查看和修改

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;   -- 8.0 写法
SELECT @@tx_isolation;            -- 5.7 写法

-- 全局修改（重启失效，正式改要写配置文件）
SET GLOBAL transaction_isolation = 'READ-COMMITTED';

-- 当前会话修改
SET SESSION transaction_isolation = 'READ-COMMITTED';
```

### 为什么 MySQL 默认选 RR？（面试深问）

**原因一：历史包袱（主从复制）**
- 早期 binlog 用 **statement 格式**（记录 SQL 语句本身）
- 如果隔离级别是 RC，主库上"先读后写"的语句在从库重放时结果可能不一致（从库的执行顺序和主库不同）
- RR 的快照读保证语句在主从两端看到相同的数据 → 复制安全
- 后来 binlog 有了 row 格式（记录变更前后的行），RC 在复制上也安全了，但 RR 的默认地位已经固定

**原因二：业务语义**
- RR 让事务内多次读结果一致，对报表、对账类业务更友好

### 面试补充
- 互联网大厂（尤其分库分表、高并发场景）常把隔离级别**改成 RC**：RR 的间隙锁在并发插入时容易死锁，RC 只锁命中的行，锁冲突少、死锁少
- 面试答："默认 RR 是历史原因（statement 复制）加业务习惯，如今 row 格式下 RC 在多数场景更香，很多公司线上用 RC"——很加分

## 7. 可重复读隔离级别下，A 事务提交的数据，在 B 事务能看见吗？

### 一句话回答
**B 事务在快照里看不见**：如果 B 事务在 A 提交**之前**就已经开始（且已经产生过读快照），那 A 提交后，B 继续用旧快照读，**看不到 A 的数据**；只有 B 还没开始、或者 B 用的是**当前读（加锁读）**，才能看到。

### 详细拆解

RR 隔离级别下，ReadView 在**第一次 SELECT** 时生成，之后固定不变：

```
时间线：
T1: B 事务 BEGIN
T2: B 事务 SELECT（此时生成 ReadView，快照=此刻的已提交数据）
T3: A 事务 BEGIN → UPDATE → COMMIT（A 提交了）
T4: B 事务 SELECT → 还是用 T2 的快照 → 看不到 A 的修改
T5: B 事务 COMMIT
```

**但如果 B 在 T3 之后才第一次 SELECT**：
```
T1: A 事务 BEGIN → UPDATE → COMMIT
T3: B 事务 BEGIN
T4: B 事务 SELECT（此时才生成 ReadView，A 已提交 → 能看到！）
```
关键点：**ReadView 生成时机 = 第一次读的时刻**，不是 BEGIN 的时刻。

### 补充：当前读（加锁读）永远看到最新

以下操作是"当前读"，读的是**最新已提交数据**，不受快照限制：
```sql
SELECT ... FOR UPDATE;    -- 加锁读
SELECT ... LOCK IN SHARE MODE;  -- 共享锁读
UPDATE / DELETE / INSERT;  -- 写操作本质都是当前读
```
所以 B 事务用 `SELECT ... FOR UPDATE` 就能看到 A 刚提交的数据。

### 面试回答模板
"RR 下 B 是否能看到 A 的提交，取决于 B 的快照（ReadView）什么时候生成：A 提交前 B 已生成快照 → 看不到（快照隔离）；B 在 A 提交后才第一次读 → 能看到。另外快照读（普通 SELECT）和当前读（FOR UPDATE 等）行为不同，当前读永远读最新。"

## 8. 举个例子说可重复读下的幻读问题

### 先复习：什么是幻读
同一事务内，**两次范围查询的行集合不一样**：第二次多了行（或少了行），多出来的行像"幻影"一样。

### 完整例子（面试能复述）

数据：订单表 `orders(id, user_id, amount)`，现有 3 条：amount 分别为 100、200、300。

```
事务 B（假设隔离级别为"标准可重复读"，无间隙锁）:
┌─────────────────────────────────────────────┐
│ BEGIN;                                       │
│ SELECT * FROM orders WHERE amount > 100;     │
│ → 返回 2 行（200, 300）                       │
│                                              │
│ 【此时事务 A 插入一笔 amount=400 并提交】       │
│                                              │
│ SELECT * FROM orders WHERE amount > 100;     │
│ → 返回 3 行（200, 300, 400）← 多了 400！      │
│ 这就是幻读：第二次读出了"幻影行"                │
└─────────────────────────────────────────────┘
```

注意细节：
- 事务 B 两次 SELECT 之间**没有修改任何数据**，但结果变了
- 幻读和不可重复读的区别：不可重复读是**同一行值变了**；幻读是**行的集合变了**（INSERT/DELETE 导致）

### 幻读为什么锁解决不了？

- 行锁只能锁"**已存在的行**"
- 插入的新行（400）在事务 B 第一次查询时**根本不存在**，行锁锁不到它
- 所以光靠行锁，事务 B 挡不住 A 插入新行 → 需要**间隙锁**锁住"范围"，让新行插不进来（详见下一题）

### 面试常见追问
"MySQL RR 下你会遇到这个幻读吗？"
→ 默认**不会**：InnoDB 的 RR 用**间隙锁 + 当前读**把幻读基本堵死了。上面例子在 MySQL 默认 RR 下，事务 B 第一次 SELECT 是快照读（不锁），A 依然能插入；但 B 若用 `SELECT ... FOR UPDATE`（当前读），间隙锁会锁住 amount>100 的整个区间，A 的插入会被阻塞。详见第 9 节。

## 9. MySQL 设置了可重读隔离级别后，怎么保证不发生幻读？

### 一句话回答
两条防线：**MVCC 快照读**（普通 SELECT 读旧快照，永远稳定）+ **当前读加锁（Record Lock + Gap Lock + Next-Key Lock）**（锁定范围，让别的事务插不进新行）。

### 防线一：快照读（普通 SELECT）

- RR 下普通 SELECT 走 MVCC，读的是事务开始时的快照
- 别的事务插入再多的新行，快照里都没有 → 快照读**永远不可能幻读**
- 这是"读读/读写"场景的幻读免疫

### 防线二：当前读 + 间隙锁（写场景）

`SELECT ... FOR UPDATE`、UPDATE、DELETE 这类当前读，必须锁住真实数据，此时靠**间隙锁**防幻读：

```
数据：amount = 100, 200, 300（索引列 amount）
事务 B: SELECT * FROM orders WHERE amount > 100 FOR UPDATE;
锁定的范围：
  - 记录锁：锁住 200、300 这两行
  - 间隙锁：锁住 (100,200)、(200,300)、(300,+∞) 这些"空隙区间"
  → 任何事务想往这些区间 INSERT 都会阻塞等待

事务 A: INSERT (amount=400) → 被 (300,+∞) 的间隙锁挡住，阻塞！
```

### 锁的类型细节（08/07 章衔接）

- **Record Lock（记录锁）**：锁单条记录
- **Gap Lock（间隙锁）**：锁两个记录之间的"空隙"，只防插入
- **Next-Key Lock（临键锁）**：记录锁 + 间隙锁合体，InnoDB 默认的锁单位

InnoDB 默认用 **Next-Key Lock**（左开右闭区间）锁范围，例如 `amount > 100` 会锁 `(100,200]、(200,300]、(300,+∞]` 的临键区间——既锁了行，又堵了间隙。

### 注意：快照读的幻读"残留"场景
如果事务里**先快照读、再当前读**混用，理论上还是可能出现不一致（先 SELECT 看到 2 行，再 FOR UPDATE 看到 3 行），所以严格说 InnoDB 的 RR 在"快照读+当前读混合"的极端场景下不完全免疫幻读。面试主动提这点 = 深度加分。

### 面试回答模板
"RR 防幻读靠双保险：普通 SELECT 走 MVCC 快照，看不到新行；UPDATE/FOR UPDATE 走当前读，用 Next-Key Lock（记录锁+间隙锁）锁住整个区间，别的事务插不进新行。代价是间隙锁会让并发插入互相阻塞、易死锁，这也是为什么有的团队切 RC。"

## 10. 串行化隔离级别是通过什么实现的？

### 一句话回答
**全部读写加锁**：读加共享锁（S 锁）、写加排他锁（X 锁），事务之间完全互斥串行执行。读未提交→串行化逐级增强锁，到串行化就是"锁死一切"。

### 实现细节

- 普通 SELECT 也要加**共享锁**（S 锁）：多个事务可以同时读，但任何写都被挡住
- UPDATE/INSERT/DELETE 加**排他锁**（X 锁）：和其他所有锁互斥
- S 锁和 X 锁互斥、X 锁和 X 锁互斥 → 同一份数据同一时刻只能被一个事务"持有"
- 事务没提交，锁不释放，其他事务只能等 → 事务变成严格排队

### 效果
- 脏读、不可重复读、幻读全部不可能发生（同一时刻只有一个人在动数据）
- 代价：并发度趋近于 0，性能最差

### 使用场景
- 极少数对一致性要求极致、并发极低的场景（如钱包对账、批量结算）
- 或者短事务场景（单条 UPDATE 的锁持有时间极短，串行化也没那么可怕）
- 生产环境几乎不用，面试要能说清"它用锁实现，MySQL 默认是不用的 RR"

### 和 RR 的区别（追问点）
- RR：读写不互斥（MVCC 快照），只锁写写（行锁）+ 范围防插入（间隙锁）
- 串行化：**读也锁**，读写也互斥 → 相当于把 MVCC 的并发红利全放弃

## 11. 介绍 MVCC 实现原理

### 一句话回答
MVCC（多版本并发控制）= **数据保留多个历史版本 + 每个事务通过"读视图（ReadView）"判断自己能看到哪个版本**，从而让"读"不阻塞"写"、不加锁也能隔离。核心组件：隐藏字段、undo log 版本链、ReadView。

### 三大组件

**① 隐藏字段（每行数据都带）**

| 隐藏字段 | 作用 |
|----------|------|
| DB_TRX_ID | 最近一次修改该行的事务 ID |
| DB_ROLL_PTR | 回滚指针，指向 undo log 中该行的旧版本 |
| DB_ROW_ID | 行 ID（没主键时用） |

**② undo log 版本链**

每次 UPDATE 不直接覆盖旧值，而是把旧值写进 undo log，新行通过 ROLL_PTR 指向上一个版本：

```
行数据（最新版本，trx_id=100, name='李四'）
   ↑ DB_ROLL_PTR
undo log 版本1（trx_id=50, name='张三'）
   ↑
undo log 版本2（trx_id=10, name='王五'）
```

一条记录的"前世今生"串成一条**版本链**。

**③ ReadView（读视图）**

事务首次快照读时生成，包含四个关键信息：
- m_ids：当前**活跃**（未提交）的事务 ID 列表
- min_trx_id：活跃事务中最小的 ID
- max_trx_id：下一个将分配的事务 ID（当前活跃事务的最大 ID + 1）
- creator_trx_id：创建该 ReadView 的事务自己的 ID

### 可见性判断规则（核心算法）

读某版本时，看该版本的 trx_id 与 ReadView 的关系：

```
如果 trx_id < min_trx_id（该版本的事务已提交且早于所有活跃事务）
  → 可见 ✅

如果 trx_id >= max_trx_id（该版本是 ReadView 创建之后才开启的事务改的）
  → 不可见 ❌

如果 min_trx_id <= trx_id < max_trx_id：
  → 看 trx_id 在不在 m_ids 里：
     在 → 未提交 → 不可见 ❌
     不在 → 已提交 → 可见 ✅

如果 trx_id == creator_trx_id（自己改的）
  → 可见 ✅（自己的修改自己当然看得到）
```

不可见就往**版本链往下**找下一个旧版本，再套一遍规则，直到可见。

### RC 与 RR 的区别（ReadView 生成时机）

| 隔离级别 | ReadView 生成时机 | 效果 |
|----------|-------------------|------|
| 读已提交（RC） | **每次 SELECT 都生成** | 能读到别的事务刚提交的 → 不可重复读 |
| 可重复读（RR） | **第一次 SELECT 生成，之后复用** | 事务内永远读同一快照 → 可重复读 |

### 完整例子

```
数据行：name='张三'，当前 trx_id=10（已提交）
事务A（id=100）启动，事务B（id=101）启动
事务A: UPDATE name='李四'（未提交）
事务B: SELECT name
  ReadView：m_ids=[100,101]，min=100，max=102
  读最新版本 trx_id=100 → 在活跃列表 → 不可见
  沿版本链找 trx_id=10 → < min(100) → 可见
  → B 读到 '张三' ✅（没读到 A 未提交的 '李四'）
```

### 面试回答模板
"MVCC 靠三个东西：每行隐藏的 trx_id 和回滚指针、undo log 版本链、ReadView。读数据时用 ReadView 的可见性规则沿版本链找'自己能看的版本'。RC 每次 SELECT 新建 ReadView，RR 复用第一个 ReadView。于是读不加锁也能隔离，读写互不阻塞。"

## 12. 一条 UPDATE 是不是原子性的？为什么？

### 一句话回答
**是原子性的**（前提：在事务里，或单条语句自带隐式事务）。靠两样：**undo log 记录旧值可回滚** + **行锁保证并发下不会出现中间状态被读到**。

### 拆解"原子性"的三个层次

**① 单条 UPDATE 语句本身**
- 未开启显式事务时，单条语句自动提交（autocommit=1），语句要么全部生效要么报错回滚
- 语句执行一半报错（如唯一索引冲突）→ 已改的行全部回滚

**② 多条语句组成的事务**
```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;  -- 这里失败
ROLLBACK;  -- 第一条也回滚
```
- undo log 里记录了每条语句的旧值，ROLLBACK 沿 undo 链恢复

**③ 并发视角**
- 更新过程中，行锁（X 锁）锁住这行，其他事务读不到"改了一半"的中间状态（快照读读旧版本，当前读被阻塞）
- 所以"原子性"不只是失败回滚，还包括"别人看不到半成品"

### 常见面试追问
- "如果 UPDATE 匹配 100 行，第 50 行报错，前 49 行会怎样？" → 回滚（undo log）
- "单条 UPDATE 和 BEGIN...COMMIT 包裹的 UPDATE 有区别吗？" → 单条等价于一个隐式事务，行为一致

### 面试回答模板
"UPDATE 是原子的：底层 undo log 保存旧版本，执行失败或 ROLLBACK 时整条语句（或整个事务）的修改全部还原；行锁保证并发下没有中间状态暴露。生产上要保证原子性，就把它放进事务里，别用 autocommit 一条条裸跑。"

## 13. 滥用事务，或者一个事务里有特别多 SQL 的弊端？

### 一句话回答
长事务/大事务的四大弊端：**锁持有时间长（阻塞并发、容易死锁）→ undo log 膨胀（拖慢回滚和 MVCC）→ 主从延迟放大 → 回滚成本爆炸**。

### 弊端逐条讲

**① 锁持有时间过长 → 阻塞 + 死锁**
- 事务提交/回滚才释放锁
- 一个事务锁 10 分钟，期间所有要改这些行的请求全排队 → 数据库连接被打满
- 多个长事务互相等锁 → 死锁概率大增

**② undo log 膨胀（最隐蔽的坑）**
- 长事务期间，被改动的所有行的旧版本都留在 undo log
- undo log 不能清理（可能还有老事务的 ReadView 需要它）
- 后果：undo 文件越来越大，磁盘占用暴涨；而且**所有读操作要沿长版本链找版本**，查询变慢
- 面试金句："一个跑 1 小时的只读事务，也会让 undo log 无法清理，把整个库拖慢。"

**③ 主从复制延迟**
- binlog 是**事务级别**写入的：一个事务的 binlog 要在提交时一次性传给从库
- 大事务（改 100 万行）的 binlog 巨大，传输 + 从库重放耗时长
- 期间从库持续落后主库 → 读写分离场景下读不到最新数据

**④ 回滚成本**
- 事务越长，中途失败回滚要恢复的版本越多
- 回滚本身也是写操作，极端情况回滚时间比执行时间还长

**⑤ 连接资源占用**
- 长事务占住连接（连接池数量有限），高并发下连接池耗尽，其他请求全部排队

### 正确姿势（面试答这套）
1. **事务尽量短小**：只把"必须一致的多步操作"放进事务
2. **不在事务里做外部调用**（HTTP、RPC、发消息）：网络等待期间锁一直挂着
3. **分批处理**：大更新拆成小批次（`UPDATE ... WHERE id BETWEEN ... LIMIT 1000` 循环）
4. **读操作尽量走快照读**，别在长事务里 SELECT FOR UPDATE
5. 监控长事务：`information_schema.innodb_trx` 表可以查活跃事务和持锁时长

```sql
-- 查看当前活跃事务（发现长事务的利器）
SELECT * FROM information_schema.innodb_trx\G
```

### 面试回答模板
"大事务的弊端：锁持有久导致并发阻塞和死锁、undo log 膨胀拖慢全局、binlog 太大加剧主从延迟、回滚成本高。所以事务要'短、小、快'：不放外部调用、大更新分批、尽早提交。"
