# 03 消息可靠性

本章覆盖：消息丢失的三个环节（生产、存储、消费）、消息可靠性保证手段、消息顺序性保证、重复消费的产生与解决。

> 这是面试**必考题**，考官最喜欢追问每个环节的细节。学习顺序：先理解"消息从哪来、到哪去"的三个环节（第 1 节），再逐个击破每环节怎么防丢（第 2 节），最后是顺序性和重复消费（第 3、4 节）。

---

## 1. 消息丢失怎么解决？（三环节防丢）

### 一句话回答
使用消息队列，全程就分三大块：**生产者、中间件（Broker）、消费者**。要保证消息不丢，就是保证这三个环节各自都不能丢。

```text
 生产者（生产阶段） ──► 中间件Broker（存储阶段） ──► 消费者（消费阶段）
   发送消息             持久化+多副本              处理完才回ack
```

### 展开讲：三个环节逐个击破

#### 环节一：消息生产阶段（生产者会不会丢？）
**取决于生产者对异常情况的处理是否合理。**

- 消息从生产出来、提交给 MQ 的过程中，只要能正常收到 MQ 的 **ack 确认响应**，就表示发送成功；
- 所以只要**处理好返回值和异常**——返回异常就进行**消息重发**——这个阶段不会丢消息。

> 比喻：寄快递，快递员（MQ）收了件会给你一张回执（ack）。只要拿到回执，包裹就安全了；没拿到回执，你就再寄一次（重发）。

#### 环节二：消息存储阶段（中间件会不会丢？）
**靠多副本（集群）。**

Kafka 使用时部署一个集群，生产者发布消息时，队列中间件通常**写多个节点（多个副本）**。这样即便其中一个节点挂了，也能保证集群数据不丢失。

> 比喻：重要的文件不只在公司电脑存一份，还要在云端、家里各备份一份。一台电脑坏了，其他副本还在。

#### 环节三：消息消费阶段（消费者会不会丢？）
**核心原则：处理完才回 ack，不能收到就回 ack。**

- 消费者**接收消息 + 消息处理之后**，才回复 ack → 消息不会丢；
- 如果**收到消息就回 ack**，消息处理中途挂掉了 → 消息就丢了（MQ 以为你处理完了，把消息删了）。

> 比喻：快递签收要"验货后签收"，而不是"拿到手就签收"。你还没验货就签了字，货物坏了快递公司就不认账了。

### 面试怎么答
分三段答，考官追问细节就有素材："**生产阶段靠 ack + 失败重发；存储阶段靠多副本集群（如 Kafka 写多节点）；消费阶段靠处理完才回 ack**。"然后主动补充："三个环节只要有一个环节处理不当就会丢消息，所以每个环节都要单独把关。"

## 2. 消息队列的可靠性怎么保证？

### 一句话回答
可靠性三板斧：**消息持久化**（消息写到磁盘）、**消息确认机制**（处理完才确认）、**消息重试策略**（失败自动重试 + 死信兜底）。

### 展开讲：三种手段

#### 手段一：消息持久化
确保消息队列能够持久化消息。在系统崩溃、重启、网络故障等情况下，**未处理的消息不应丢失**。

- 例如 RabbitMQ 可通过配置将消息持久化到磁盘：队列和消息都设置为持久化（`durable = true`）；
- 服务器重启后，消息依然可以被重新读取和处理。

> 反面教材：如果消息只存在内存里，服务器一断电，消息全没了。

#### 手段二：消息确认机制（ack）
消费者**成功处理消息后**才向消息队列发送确认（acknowledgment）。MQ 只有收到确认后，才会把消息从队列中移除。**没收到确认 → 过一段时间重新发送**（给其他消费者或再次发给同一个消费者）。

以 Kafka 为例：消费者通过 `commitSync`（同步提交）或 `commitAsync`（异步提交）方法**提交偏移量（offset）**，从而确认消息的消费。

> 关键点：确认动作发生在"业务处理成功之后"，这是防丢的核心防线。

#### 手段三：消息重试策略
消费者处理消息失败时，要有合理的重试策略：设置**重试次数**和**重试间隔**。

典型配置：第一次失败后等 5 秒重试第二次；重试 3 次仍失败 → 把消息发送到**死信队列**，后续人工排查或特殊处理。

> 死信队列：给"处理不了的问题消息"准备的收容所，不让它们无限重试占资源（详见 09 章 RabbitMQ）。

### 面试怎么答
"可靠性靠三件套：持久化保证机器重启不丢；确认机制保证处理成功才删除，没确认就重发；重试策略配合死信队列保证失败消息有兜底。"再补一句加分项："**这三件套是所有 MQ 通用的设计思想，具体实现各家不同**"（引出 Kafka 的 offset、RocketMQ 的重试队列等细节，见 07/08/09 章）。

## 3. 消息顺序性怎么保证？

### 一句话回答
先想清楚**哪些消息必须有序**（比如同一订单的创建→付款→完成），然后靠"MQ 的分区/队列有序 + 消费者串行消费"两步保证。

### 展开讲：三个层面

#### 层面一：识别有序场景
先明确业务中哪些消息需要保证顺序。例如金融交易系统中，**同一用户的转账操作顺序不能打乱**；电商里同一订单的"创建 → 付款 → 完成"不能乱序。

不需要保证顺序的例子：不同订单之间的消息可以并发消费（先处理第三个订单的付款、再处理第二个订单的创建，完全没问题）。

#### 层面二：MQ 对顺序性的支持
部分 MQ 自带顺序保证功能：

- **Kafka**：把消息划分到**同一个分区（Partition）**，分区内消息天然有序，消费者按分区顺序读取即可；
- **RocketMQ**：把一组消息发送到**同一个队列（MessageQueue）**，队列内严格有序。

代价：这限制了并行处理能力——同一分区/队列只能串行消费，需要在**顺序性和吞吐量之间权衡**。

#### 层面三：消费者顺序处理策略
消费者处理顺序消息时，**避免并发处理导致顺序打乱**：

- 用**单线程**消费同一分区/队列的消息；
- 或者用线程池 + 对顺序消息**串行化处理**（比如按订单号哈希到固定线程）。

> 经典误区：生产者发消息是有序的，但消费者用多线程并发处理，顺序照样乱。顺序性是**生产、存储、消费三段协同**的结果，缺一不可。

### 面试怎么答
"保证顺序分三步：第一识别业务上哪些消息必须有序；第二利用 MQ 的分区/队列机制把同组消息放进同一分区；第三消费者对同一分区的消息串行消费（单线程），避免并发打乱顺序。同时要说明这牺牲了并行度，是顺序性和吞吐量的权衡。"

## 4. 消息重复消费怎么解决？

### 一句话回答
重复消费**无法从根上消灭**（生产端可能重复发送、消费端可能拉重），只能靠**业务端做幂等**：为每条消息留"业务标识"，处理前先查重，处理过就跳过。

### 展开讲：为什么会重复？

重复消息有两个来源：

1. **生产端**：为了保证发送成功，可能会重复推送（直到收到成功 ACK），产生重复消息。成熟的 MQ Server 会想办法避免存储重复消息（比如用空间换时间，存储已处理过的 message_id），给生产端提供幂等性的发送接口；
2. **消费端**：这个无法根本解决——在高并发标准下，"拉取消息 + 业务处理 + 提交消费位移"很难做成一个原子事务；另外消费端服务可能宕机，重启后很可能会拉取到重复消息。

### 所以结论是：业务端自己做控制
**对于已经消费成功的消息，在本地数据库表或 Redis 缓存里存业务标识，每次处理前先校验，保证幂等。**

### 面试怎么答
"重复消费的根源有两个：生产端为确认成功可能重发，消费端提交位移与业务处理不是原子的、宕机后可能重拉。MQ 自己解决不了消费端的问题，所以业务端必须做幂等：用消息唯一 ID 在 DB 或 Redis 做去重校验，处理过的直接跳过。"**"消费端幂等必须业务自己做"是这句话的灵魂**。
