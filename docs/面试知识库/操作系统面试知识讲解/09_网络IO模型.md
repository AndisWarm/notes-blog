# 09 网络 I/O 模型

本章覆盖：五种 I/O 模型、服务器处理并发请求的四种方式、I/O 多路复用、select/poll/epoll 区别、边缘触发 vs 水平触发、Redis/Nginx/Netty 的高性能网络模型、零拷贝。

> 本章是理解高性能服务器（Redis、Nginx、Netty）的基础，面试追问概率高。建议重点掌握第 4 节（select/poll/epoll）和第 6 节（Reactor 模式）。

## 1. 你了解过哪些 I/O 模型？

### 一句话回答
五种 I/O 模型：**阻塞 I/O、非阻塞 I/O、I/O 复用（select/poll/epoll）、信号驱动 I/O、异步 I/O**。核心区别是"**谁在等、怎么等**"——阻塞是自己干等；非阻塞是边干边问；多路复用是"一个人帮一帮人等"；异步是"全交给内核，好了叫我"。

### 五种模型逐个讲

**① 阻塞 I/O**
- 应用程序发起 I/O 操作后**被阻塞**，直到操作完成才返回
- 适用：对实时性要求不高的场景
- 类比：打电话订餐，挂电话前一直干等着（期间啥也干不了）

**② 非阻塞 I/O**
- 发起 I/O 操作后**立即返回**，不阻塞
- 但需要**不断轮询**或使用 select/poll/epoll 检查操作是否完成
- 适用：需要多路复用的场景（如同时处理多个 socket 连接的服务器）
- 类比：点完外卖不干等，但每隔一分钟刷一次手机看送到没

**③ I/O 复用模型（多路复用）**
- 通过 select、poll、epoll 等系统调用，**一个线程同时等待多个 I/O 操作**
- 任何一个准备就绪，应用程序就会被通知
- 适用：高并发的服务端程序（Nginx、Redis 的核心）
- 类比：前台小姐姐一个人盯着整个大厅的客人，谁举手就处理谁

**④ 信号驱动 I/O**
- 发起 I/O 操作后可以**继续做其他事情**
- 操作完成时，操作系统发送**信号**通知
- 适用：需要异步 I/O 通知的场景，可提高并发能力

**⑤ 异步 I/O**
- 发起 I/O 操作后**立即做其他事情**，完成时得到通知
- **由操作系统内核完成整个 I/O 操作**，应用程序只需等通知
- 适用：大量并发连接和高性能场景，减少系统调用次数
- 类比：雇了个管家（内核）全程代办，办好打电话通知你

### 记忆表

| 模型 | 发起后 | 谁来等 | 通知方式 |
|------|--------|--------|----------|
| 阻塞 I/O | 干等 | 自己 | 无（直接返回结果） |
| 非阻塞 I/O | 立即返回 | 自己轮询 | 轮询检查 |
| I/O 复用 | 立即返回 | 内核帮忙看着多个 | select/poll/epoll 通知 |
| 信号驱动 I/O | 干别的 | 内核（第一阶段） | 信号通知 |
| 异步 I/O | 干别的 | 内核（全过程） | 完成回调通知 |

## 2. 服务器处理并发请求有哪几种方式？

### 一句话回答
四种方式：**单线程（一次一个请求）、多进程/多线程（一请求一进程/线程）、I/O 多路复用（一个线程监听处理多个客户端）、多路复用+多线程（多进程 × 每进程多线程）**。

### 四种方式

**① 单线程 Web 服务器**
- 一次处理一个请求，结束后再处理下一个
- 性能最低

**② 多进程/多线程 Web 服务器**
- 为每个用户请求生成一个独立进程或线程来响应
- 问题：并发请求到**成千上万**时，进程/线程会消耗大量系统资源

**③ I/O 多路复用 Web 服务器**
- **一个线程**就能监听和处理多个客户端的 I/O 事件
- Nginx、Redis 的架构基础

**④ 多路复用 + 多线程 Web 服务器**
- 多进程 × 每进程多线程，每个线程处理一个请求
- 避免单进程服务过多请求，充分利用多 CPU 计算能力

## 3. 讲一下 I/O 多路复用

### 一句话回答
I/O 多路复用是**复用一条线程处理多个 socket 中的事件**，能复用资源，防止创建过多线程导致上下文切换开销过大。

### 原理

```
一个线程
  │
  ├── 监听 socket1 的事件
  ├── 监听 socket2 的事件
  ├── 监听 socket3 的事件
  │        ...
  └── 谁有事件就处理谁
```

- 传统方式：每个连接一个线程 → 连接多了线程爆炸 → 上下文切换开销巨大
- 多路复用：**一个线程管所有连接** → 资源复用、开销小
- 这就是 C10K（一万个并发连接）问题的核心解法

## 4. select、poll、epoll 的区别是什么？★ 必考

### 一句话回答
**select/poll 每次调用都要把整个文件描述符集合拷贝进内核、遍历查找事件（O(n)），且 select 还有 1024 上限；epoll 用红黑树在内核里维护待检测的 socket、用回调机制记录就绪事件，只返回有事件的描述符，效率 O(1)，是解决 C10K 的利器。**

### select/poll 的问题

**select 的工作方式：**
1. 把已连接的 Socket 放进**文件描述符集合**
2. 调用 select，把整个集合**拷贝**到内核
3. 内核**遍历**整个集合检查网络事件
4. 检查完把集合**拷贝**回用户态
5. 用户态**再遍历一遍**找到可读/可写的 Socket

**select 的 2 次遍历 + 2 次拷贝**，而且：
- 使用固定长度的 **BitsMap**，支持的文件描述符数量**有限制**（Linux 下 FD_SETSIZE 默认最大 1024，只能监听 0~1023）

**poll 的改进：**
- 用**动态数组**（链表形式）替代 BitsMap，**突破了 1024 的限制**
- 但本质没变：仍是**线性结构**存储 socket 集合，仍需**遍历 + 拷贝**
- 时间复杂度 **O(n)**，并发数上来性能呈指数级下降

### epoll 的两大绝招

**绝招一：内核红黑树管理所有待检测的描述符**
- `epoll_ctl()` 把要监控的 socket 加入内核里的**红黑树**
- 增删改查时间复杂度 **O(logn)**
- select/poll 每次都要传整个 socket 集合进内核，epoll 只需传变化的那个 → **减少大量数据拷贝和内存分配**

**绝招二：事件驱动 + 就绪链表**
- 内核维护一个**链表记录就绪事件**
- socket 有事件发生时，通过**回调函数**把它加入就绪链表
- `epoll_wait()` 只返回**有事件发生的描述符个数**，不用像 select/poll 那样轮询扫描整个集合

**epoll 的代码结构：**

```
int epfd = epoll_create(...);
epoll_ctl(epfd, ...);   // 把所有要监听的 socket 加入 epfd

while(1) {
    int n = epoll_wait(...);   // 只返回有事件的描述符
    for(接收到数据的socket){
        // 处理
    }
}
```

### 三者对比表

| 对比项 | select | poll | epoll |
|--------|--------|------|-------|
| 数据结构 | 固定 BitsMap | 动态数组（链表） | 内核红黑树 + 就绪链表 |
| 上限 | **1024** | 系统文件描述符上限 | 系统文件描述符上限 |
| 事件查找 | 遍历 O(n) | 遍历 O(n) | 回调就绪，O(1) |
| 数据拷贝 | 2 次（进 + 出） | 2 次 | 几乎无（内核维护） |
| 高并发 | 差 | 差 | **好（C10K 利器）** |

## 5. epoll 的边缘触发（ET）和水平触发（LT）有什么区别？

### 一句话回答
**水平触发（LT）**：只要有数据没读完，就不断通知你；**边缘触发（ET）**：只在"没有 → 有"的状态变化那一刻通知一次，不管你有没有读完。ET 效率更高但必须配合非阻塞 I/O 一次性读完。

### 快递箱例子（最直观）

| 模式 | 行为 | 类比 |
|------|------|------|
| 边缘触发（ET） | 只通知**一次**，你不取也不再提醒 | 快递箱只发一条短信，一直不取也不会再发 |
| 水平触发（LT） | **不断通知**，直到你取完快递 | 快递箱发现没取走，就一直发短信催你 |

### 两种模式详解

**水平触发（LT）——默认模式**
- socket 有可读事件时，服务器**不断地从 epoll_wait 中苏醒**，直到内核缓冲区数据被 read 读完
- 收到通知后没必要一次执行尽可能多的读写操作（反正会再通知）

**边缘触发（ET）**
- 有可读事件时，服务器**只苏醒一次**，即使没 read 完也不再通知
- 所以程序必须**一次性将内核缓冲区的数据读取完**，否则会错失数据

### ET 为什么要配合非阻塞 I/O？

- ET 只通知一次，不知道到底能读写多少数据 → 需要**循环读写**直到数据读完
- 如果文件描述符是**阻塞**的，没有数据可读写时会阻塞在读写函数，程序无法继续
- 所以**循环 I/O 操作直到 read/write 返回 EAGAIN 或 EWOULDBLOCK 错误**——这要求是非阻塞 I/O

### 为什么 ET 效率更高？

**ET 减少 epoll_wait 的系统调用次数**（LT 每次数据没读完都叫醒你一次）。系统调用有开销，涉及上下文切换，调用次数越少效率越高。

## 6. Redis、Nginx、Netty 是依赖什么做到高性能的？

### 一句话回答
它们都基于 **Reactor 模式**（反应堆模式）——在 I/O 多路复用接口基础上实现的网络模型。核心是"**来了事件就反应**"：Reactor 负责监听分发事件，处理资源池负责处理事件。

### Reactor 模式的核心组成

```
Reactor（反应堆）：负责监听和分发事件（连接事件、读写事件）
      │
      ▼ 分发
处理资源池：负责处理事件（read → 业务逻辑 → send）
```

**灵活组合**：Reactor 数量可以是一个或多个；处理资源池可以是单进程/单线程，也可以多进程/多线程。

### 三巨头各自的方案

**① Redis（6.0 之前）：单 Reactor 单进程**

```
单进程：监听 + 处理 全部在一个进程内完成
```

- 优点：实现简单，不用考虑进程间通信和多进程竞争
- 缺点：
  - **无法充分利用多核 CPU**
  - 业务处理时整个进程无法处理其他连接事件——**业务耗时长了响应延迟**
- 为什么 Redis 能用？Redis 业务处理主要**在内存中完成**，操作极快，**性能瓶颈不在 CPU**，所以单进程没问题

**② Netty：多 Reactor 多线程**

```
主线程（mainReactor）：只负责接收新连接
    │ 传给
子线程（subReactor）：负责业务处理，直接回发给客户端
```

- 优势：**主线程和子线程分工明确**——主线程只 accept 新连接，子线程处理业务；交互简单，子线程无须返回数据

**③ Nginx：多 Reactor 多进程（变体）**

```
主进程：只初始化 socket，不 accept 连接
    │
子进程们：各自 accept 新连接（通过锁保证一次只有一个 accept，防止惊群），
          accept 后在自己的 Reactor 里处理，不转给其他子进程
```

- 与标准多 Reactor 多进程的差异：主进程**不创建 mainReactor accept 连接**，而是由**子进程的 Reactor 来 accept**，用锁防止"惊群现象"（多个进程同时被唤醒抢同一连接）

### 记忆表

| 组件 | Reactor 方案 | 特点 |
|------|-------------|------|
| Redis | 单 Reactor 单进程 | 内存操作快，瓶颈不在 CPU |
| Netty | 多 Reactor 多线程 | 主线程接收，子线程处理 |
| Nginx | 多 Reactor 多进程 | 子进程 accept + 锁防惊群 |

## 7. 零拷贝是什么？

### 一句话回答
**零拷贝**是用 `sendfile` 等一次系统调用，把"磁盘 → 网卡"的数据传输从传统方式的 4 次上下文切换 + 4 次数据拷贝，减少到 **2 次上下文切换 + 2 次数据拷贝**，而且数据全程在内核态完成搬运（由 DMA 搬运，不经过 CPU），文件传输性能**提高至少一倍**。

### 传统 I/O 的问题（4 次上下文切换 + 4 次数据拷贝）

从硬盘读数据再通过网络发送：

```
① 用户态 → 内核态：read() 系统调用
② 硬盘 → 内核缓冲区（DMA 搬运）
③ 内核缓冲区 → 用户缓冲区（CPU 搬运）← 白白搬一次！
④ 内核态 → 用户态：read() 返回
⑤ 用户态 → 内核态：write() 系统调用
⑥ 用户缓冲区 → 内核缓冲区（CPU 搬运）← 又搬一次！
⑦ 内核缓冲区 → 网卡（DMA 搬运）
⑧ 内核态 → 用户态：write() 返回
```

- 4 次上下文切换（①④⑤⑧）
- 4 次数据拷贝：2 次发生在内存缓冲区和硬件设备之间（DMA 完成，②⑦），**2 次发生在内核态和用户态之间（CPU 完成，③⑥）——这两次是多余的**

### 零拷贝怎么做的？

```
① 用户态 → 内核态：sendfile() 系统调用（一次搞定）
② 硬盘 → 内核缓冲区（DMA 搬运）
③ 内核缓冲区 → 网卡（DMA 搬运）
④ 内核态 → 用户态：sendfile() 返回
```

- **一次系统调用合并了磁盘读取和网络发送** → 上下文切换从 4 次降到 **2 次**
- **拷贝都在内核中完成** → 数据拷贝从 4 次降到 **2 次**，且这 2 次都是 **DMA 搬运**，不经过 CPU

### 收益

| 对比项 | 传统 I/O | 零拷贝（sendfile） |
|--------|----------|-------------------|
| 上下文切换 | 4 次 | **2 次** |
| 数据拷贝 | 4 次（2 次过 CPU） | **2 次（全部 DMA）** |
| 性能 | 基准 | **提高至少一倍** |

> 面试金句："零拷贝的'零'不是零拷贝，而是**零 CPU 拷贝**——数据搬运全交给 DMA 硬件，CPU 只负责发起和收尾。"
