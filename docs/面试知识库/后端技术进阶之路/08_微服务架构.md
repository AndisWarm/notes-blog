# 08 微服务架构

本章覆盖：微服务高可用保障、微服务分布式事务落地、微服务负载均衡。

---

## 1. 微服务如何保证系统高可用？

### 一句话回答
靠"外围防护 + 内部自愈"的组合拳：注册中心管发现、网关管入口、熔断限流管依赖、重试超时管调用、幂等管重复，环环相扣。

### 展开讲

**1. 注册中心与服务发现：** 服务启动时把自己注册到注册中心（Nacos、Consul、Eureka），消费者从注册中心拉取可用实例列表。坏实例被健康检查自动摘除，新实例上线自动加入——"机器坏了系统自动换人，不用人工改配置"。

**2. 网关（API Gateway）：** 统一入口做路由、鉴权、限流、灰度发布。入口限流挡住第一波洪水，后面的服务才不会被打爆。

**3. 熔断：** 下游故障率超阈值就快速切断（详见 06 章第 11 节），防止一个服务变慢拖垮整条调用链（雪崩）。

**4. 限流：** 控制单位时间进入系统的请求量（令牌桶、滑动窗口等），超出的请求排队或直接拒绝，保证系统在能力范围内运行。

**5. 重试：** 对"瞬时失败"（网络抖动、超时）做有限次重试（如 3 次），但要带退避（指数退避 + 随机抖动）避免重试风暴；幂等接口才能放心重试。重试和熔断要配合：熔断打开期间不能重试。

**6. 超时：** 所有下游调用必须设置超时（连接超时 + 读超时），否则一个慢接口能占死线程池。超时后快速失败，宁可返回兜底也不无限等待。

**7. 幂等：** 同一请求执行多次结果一致。用唯一请求号 + 去重表（或 Redis setnx），保证重试、MQ 重复投递不会造成重复下单、重复扣款。

**8. 其他：** 多副本部署 + 健康检查 + 滚动发布（金丝雀发布），配置中心统一管理开关（降级开关、灰度开关），全链路监控（SkyWalking）和告警。

### 比喻
高可用像一支军队：注册中心是花名册（谁在编一查便知），网关是城门（先安检限流），熔断是盾牌（挡不住就撤退），超时是号角（吹了就撤），幂等是记账本（重复报账对不上账就拒收）。

## 2. 微服务场景下如何实现分布式事务保证一致性？

### 一句话回答
看业务一致性要求：强一致场景（订单 + 库存、支付）用 TCC 或 Seata AT 模式；可容忍最终一致（下单 + 通知、加积分）用 MQ 事务消息或本地消息表 + 定时对账。

### 展开讲

**微服务下的典型场景：** 用户下单 = 订单服务扣库存（库存服务）+ 扣余额（账户服务）+ 发通知（通知服务），跨了多个服务、多个数据库，本地事务管不了。

**方案落地：**

- **TCC（强一致首选）：** 下单流程拆成：Try 预占库存（库存服务）+ 预扣余额（账户服务）→ Confirm 确认扣减 → Cancel 释放。每步要幂等（用事务 ID 去重），空回滚要处理（Try 没执行也被 Cancel 时直接成功返回）。实现可以用 Seata TCC 模式，避免手写太多样板代码
- **Seata AT 模式：** 自动模式，框架通过解析 SQL 生成 undo log，业务代码几乎无侵入，提交时全局锁保证写冲突；代价是性能比 TCC 差，适合一致性要求高但不追求极致性能的场景
- **MQ 事务消息（最终一致）：** 订单服务先发半消息，本地下单事务成功后提交消息，库存服务消费消息扣库存；失败走重试和人工补偿。适合"下单后异步扣库存/发积分"这类可容忍短暂不一致的场景
- **本地消息表 + 定时任务：** 下单事务里同时写业务表和消息表，定时任务扫描消息表投递 MQ，消费方处理成功后回执，没回执的重发——简单可靠，适合小团队
- **Saga：** 下单 → 扣库存 → 支付 → 发货，任何一步失败执行逆向补偿（退款、释放库存），适合长流程，但中间状态对外可见，需要业务能接受

**选型逻辑：**
- 涉及资金、强一致、短事务 → TCC 或 AT
- 跨服务但可异步、可容忍秒级延迟 → MQ 事务消息
- 链路很长、中间状态可接受 → Saga
- 任何方案都离不开**幂等 + 对账兜底**：定时对账任务扫描两边数据，不一致告警并自动补偿

### 对比表格

| 方案 | 一致性 | 业务侵入 | 适合场景 | 落地框架 |
|------|--------|----------|----------|----------|
| TCC | 强 | 高 | 下单扣库存、扣款 | Seata TCC |
| AT 模式 | 强 | 低 | 一般业务强一致 | Seata AT |
| MQ 事务消息 | 最终 | 低 | 异步解耦 | RocketMQ |
| 本地消息表 | 最终 | 中 | 简单可靠 | 自研 |
| Saga | 最终 | 高 | 长流程 | Seata Saga |

### 比喻
像网购退款流程：强一致像"先把钱扣住，双方确认才放行"（TCC）；最终一致像"先发货，账后面慢慢对，对不上就人工介入"（MQ + 对账）。不管哪种，对账（复盘）永远是最后一道保险。

## 3. 微服务负载均衡怎么做？

### 一句话回答
微服务内部用的是**客户端负载均衡**：服务 A 从注册中心拿到服务 B 的实例列表，自己选一个来调，典型实现是 Spring Cloud LoadBalancer（前身 Ribbon）。

### 展开讲

**客户端 vs 服务端负载均衡：**

| 维度 | 客户端负载均衡 | 服务端负载均衡 |
|------|----------------|----------------|
| 决策位置 | 调用方自己选 | 独立负载均衡器（Nginx/LVS）选 |
| 实例感知 | 直连注册中心，实时感知 | 通过配置/健康检查感知 |
| 灵活性 | 可按服务个性化策略 | 全局统一 |
| 典型实现 | Ribbon、Spring Cloud LoadBalancer | Nginx、LVS、网关 |

**核心机制：**
1. **注册中心感知：** 服务 A 的调用组件订阅服务 B 的实例变更，服务 B 有节点上线/下线，A 的本地缓存实时更新——不用重启、不用改配置
2. **选取策略：** 轮询、随机、权重、最少活跃调用数（LoadBalancer 默认轮询，可自定义）
3. **失败重试：** 选中的实例调用失败，自动换下一个实例重试（需开启重试策略），配合超时控制防止拖死调用线程

**Spring Cloud 的演变：**
- 旧版：**Ribbon**（Netflix 出品，功能全但已进入维护模式）
- 新版：**Spring Cloud LoadBalancer**（官方替代，默认集成在 OpenFeign 中，基于 WebClient/RestTemplate 均可使用）

**调用链路示意：** 服务 A（Feign 客户端）→ 注册中心拿到 B 的实例列表 → LoadBalancer 按策略选一台 → 发起 HTTP 调用 → 失败则换一台重试。

**与其他层的关系：** 外部流量走网关（服务端负载均衡，Spring Cloud Gateway 内置 LoadBalancer 过滤器转发到具体实例），服务间调用走客户端负载均衡，两层各管各的。

### 比喻
客户端负载均衡像你手机里的打车 App：App 直接看到附近所有司机（注册中心列表），自己挑一个叫车；叫的司机没接单，App 自动换下一个（重试）。服务端负载均衡则像打车平台的总调度台，统一给你派单。
