# 06 第三次握手：密钥交换与加密切换

> 本章目标：看懂客户端如何交出第三味配料（pre-master）、双方如何算出主密钥，以及 ChangeCipherSpec 和 Finished 这两个"分水岭"消息的作用。

---

## 回顾：现在双方手里有什么？

握手进行到第三次握手之前，双方已经完成：

| 消息 | 结果 |
| --- | --- |
| ClientHello | 客户端给了 **Client Random** |
| ServerHello + Certificate | 服务器给了 **Server Random** + 证书 |
| （客户端内部）验证证书 | 通过了，信任服务器的公钥 |

目前只有**两味配料**，而生成主密钥需要**三个随机数**。第三味配料叫 **pre-master**，由客户端生成、由服务器安全接收——这就是第三次握手的第一件事。

## ClientKeyExchange：交出 pre-master

### 客户端做了什么

1. 客户端验证完证书、认定可信之后，**生成一个新的随机数 pre-master**；
2. 用**服务器的公钥**加密这个随机数（还记得公共快递柜吗？投进去只有持私钥的服务器能取）；
3. 把加密后的结果放进 **Client Key Exchange** 消息发给服务器。

### 服务器收到后做了什么

- 用**自己的私钥**解密，得到客户端发来的 pre-master。

至此，**双方手里都有了三个随机数**：Client Random、Server Random、pre-master。而且 pre-master 全程只有双方知道——它被服务器公钥加密着在网络上传送，中间人即使截获，没有服务器私钥也解不开。

### 为什么叫 pre-master？它是"钥匙的原料"

pre-master 直译是"预主密钥"——**它还不是最终密钥，只是制造最终密钥的原料**。接下来的核心步骤是：

## 主密钥（Master Secret）的诞生

双方用同一个"配方"（RFC 5246 里叫 PRF，伪随机函数），把三个随机数合在一起计算：

```
Master Secret = PRF( pre-master,
                     "master secret" + Client Random + Server Random )
```

> 不要求理解 PRF 的数学细节，抓住三个要点即可：
> 1. **输入**：pre-master + Client Random + Server Random（三味配料缺一不可）；
> 2. **输出**：主密钥（Master Secret），**双方各自算、结果一样**；
> 3. **主密钥就是数据传输时使用的对称加密密钥的基础**，正式通信的会话密钥（Session Key）由主密钥再派生而来。

**为什么三个随机数缺一不可？** 这是安全设计上的"三人成众"：

- **pre-master**：只有双方知道，是"私密核心"，保证了攻击者算不出结果；
- **Client Random + Server Random**：每次握手都不同，保证了**每次会话的密钥都不同**（就算 pre-master 因为某种原因被偷，攻击者没有这两个随机数也算不出最终密钥）。

> 原文原话：**"这里的主秘钥就是数据传输时所使用的对称加密秘钥。"**（严格说会话密钥由主密钥派生，但对理解握手流程，记住"三个随机数 → 主密钥 → 加密数据"这条链就够了。）

## ChangeCipherSpec：按下"加密模式"开关

主密钥算好了，但**从哪一刻开始用**？答案在 ChangeCipherSpec（密钥规格变更协议）里：

- 客户端发送一条 **Change Cipher Spec** 消息：**"我已经生成主密钥，并且把模式切换到加密模式，请你（服务器）开始使用加密方式发送消息。"**
- 这条消息**本身不加密**（它只是通知），但它是一个**分水岭**：

```
┌──────────────────────────────┐  ┌──────────────────────────────┐
│   ChangeCipherSpec 之前        │  │   ChangeCipherSpec 之后        │
│   （明文世界）                  │  │   （加密世界）                  │
│                              │  │                              │
│   ClientHello                 │  │   之后所有消息（从 Finished    │
│   ServerHello                 │  │   开始）都用对称密钥加密         │
│   Certificate ...             │  │                              │
│   ClientKeyExchange           │  │                              │
│   （这些都是明文）             │  │                              │
└──────────────────────────────┘  └──────────────────────────────┘
```

> 记忆：**ChangeCipherSpec 之前是明文时代，之后是密文时代。** 原文："ChangeCipherSpec 之前传输的 TLS 握手数据都是明文的，之后都是对称秘钥加密的秘文。"

## Finished：加密世界的第一次通话

切换加密后，客户端马上发出第一条**加密消息**——Finished（原文叫 Encrypted Handshake Message，加密握手消息）：

- 客户端把**之前所有发送过的握手数据**（从 ClientHello 到 ChangeCipherSpec 的全部内容）做一个**摘要（哈希指纹）**；
- 用**主密钥**（对称加密）把摘要加密，发给服务器。

服务器收到后解密、重新算一遍指纹来验证：

1. **验证加密通信是否可用**——如果双方算出的密钥不一致，服务器解密会失败，说明密钥协商出了问题；
2. **验证之前的握手信息是否被中途篡改过**——如果指纹对不上，说明中间有人改过消息，立刻终止连接。

> 打个比方：双方第一次用新钥匙互开对方的锁。钥匙不对（指纹不符），立刻喊停，谁也别想用这把"坏的钥匙"继续传数据。

**为什么 Finished 必须加密发送？** 如果明文发指纹，中间人可以照着改自己的指纹伪装。加密发送 + 指纹校验双管齐下，等于既验钥匙、又验消息。

## 第三次握手小结（消息清单）

| 消息 | 谁发的 | 明文/密文 | 干什么 |
| --- | --- | --- | --- |
| ClientKeyExchange | 客户端 | 明文（内容用服务器公钥加密） | 送出 pre-master |
| （可选）CertificateVerify | 客户端 | 明文 | 双向认证时证明自己的私钥 |
| ChangeCipherSpec | 客户端 | 明文 | 宣布"我开始加密了" |
| Finished | 客户端 | **密文** | 加密的握手指纹，供服务器验证 |

到这一步，**客户端这边的活儿干完了**，球被踢回给服务器——第四次握手。
