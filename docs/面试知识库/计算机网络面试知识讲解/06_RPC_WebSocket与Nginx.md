# 06 RPC、WebSocket 与 Nginx

> 面试问法：为什么有 HTTP 还要用 RPC / HTTP 长连接与 WebSocket 区别 / Nginx 负载均衡算法 / Nginx 在哪一层。
> 共 4 题，属于"应用层周边"知识。

## Q1 为什么有 HTTP 协议了，还要用 RPC？

### 一句话答案

**RPC 是"调用方式"不是协议**（gRPC、Thrift 才是协议实现），目标是让程序员**像调用本地方法一样调用远程方法**；HTTP 主要用于对外（B/S），RPC 主要用于内部微服务（C/S），且 RPC 比 HTTP/1.1 更早、内部性能更好。

### 大白话讲解

- **RPC 是什么**：Remote Procedure Call，远程过程调用。本质是**一种调用方式**——让代码 `getUser(123)` 像本地函数一样，实际却在另一台服务器上执行。具体协议实现是 gRPC、Thrift 等（它们不一定基于 TCP）。
- **HTTP 和 RPC 的分工**：
  - 对外（B/S 架构，用户 ⇄ 网站）→ 用 **HTTP**：通用、规范、浏览器天然支持；
  - 对内（服务器集群内部，微服务之间）→ 用 **RPC**：更轻、更快、效率更高。
- **历史原因**：RPC 出现比 HTTP 早，性能比主流 HTTP/1.1 好，所以大公司内部一直沿用。
- **现状补充**：HTTP/2 优化后性能可能超过很多 RPC 协议，但因为出现晚，不太可能取代 RPC；同时 B/S 和 C/S 正在融合（很多软件多端共存，对外 HTTP、内部 RPC）。

> 一句话：**对外见客户穿正装（HTTP），内部干活穿工装（RPC）。**

## Q2 HTTP 长连接与 WebSocket 有什么区别？

### 一句话答案

**HTTP/1.1 是半双工**（一问一答，客户端不问服务器不能主动答）；**WebSocket 是全双工**（双方随时互发）。需要服务器主动推送数据的场景（聊天、游戏、实时通知）用 WebSocket。

### 大白话讲解

- **半双工**：像对讲机——按住才能说，说完对方才能说。HTTP/1.1 就是"客户端不问，服务端不答"。
- **全双工**：像打电话——双方随时能说。WebSocket 就是打电话。

**服务器推送的两种实现方式：**

| 方式 | 原理 | 适用场景 |
| --- | --- | --- |
| **轮询/长轮询**（HTTP 模拟推送） | 客户端定时反复问"有新消息吗？" | 简单场景（如登录页检测） |
| **WebSocket** | 连接建立后双方随时互发 | 频繁交互的复杂场景（网页游戏、聊天、行情） |

> 记忆：**HTTP/1.1 = 对讲机（半双工），WebSocket = 电话（全双工）**。注意 TCP 本身是全双工的，是 HTTP/1.1 的"请求-应答"模式把它用成了半双工。

## Q3 Nginx 有哪些负载均衡算法？

### 一句话答案

**轮询、IP 哈希、URL 哈希、最短响应时间、加权轮询** 五种。

### 大白话讲解

负载均衡 = 把请求"均匀"分给多台后端服务器。Nginx 支持：

| 算法 | 原理 | 适用场景 |
| --- | --- | --- |
| **轮询** | 按顺序依次分配，最简单 | 服务器配置相同的场景；缺点：无法处理某节点变慢、无法保持会话连续性 |
| **IP 哈希** | 按客户端 IP 的哈希值分配，**同一 IP 永远进同一台服务器** | 需要**会话保持**（同用户请求固定打一台） |
| **URL 哈希** | 按请求 URL 的哈希值分配，同一 URL 固定一台 | 提高后端**缓存命中率** |
| **最短响应时间** | 谁响应快先给谁 | 后端性能不均的场景 |
| **加权轮询** | 按权重分配，权重高接的请求多 | 服务器性能不同时，让高性能的多干活 |

**五种算法分别应用在哪些方面：**

| 算法 | 应用场景 | 典型例子 |
| --- | --- | --- |
| **轮询** | 服务器**配置相同、业务无状态**的通用场景 | 默认配置；后端清一色同规格机器、无会话依赖的普通 API |
| **IP 哈希** | **会话保持**（Session 不共享时） | 登录态、购物车等需要粘性的应用；未引入 Redis 共享会话的旧架构 |
| **URL 哈希** | **缓存命中率优化** | 静态资源、CDN 回源；同一资源固定打同一台缓存服务器，避免缓存反复失效 |
| **最短响应时间** | **后端性能不均、动态择优** | 服务器配置参差、响应波动大的场景；慢节点自动少接请求 |
| **加权轮询** | **异构集群、按能力分配** | 新老机器混跑、高性能机器多干活；扩容/缩容过渡期临时调流量比例 |

**选型思路（面试加分点）：** 选哪种算法，本质是回答两个问题：

1. **要不要会话保持？** 要 → IP 哈希；Session 已共享（Redis）、无状态 → 轮询/加权轮询随便用。
2. **后端是否同质？** 同质 → 轮询；异构 → 加权轮询（静态权重）或最短响应时间（动态感知）。

**两组容易混淆的对比：**

- **轮询 vs 加权轮询**：轮询是"均分"，加权轮询是"按比例分"——加权是轮询的升级版，解决后端性能差异；
- **IP 哈希 vs URL 哈希**：IP 哈希"认人"（会话保持），URL 哈希"认路径"（缓存命中）——一个管用户粘性，一个管资源粘性。

**两个常见的坑：**

1. **IP 哈希在代理场景失效**：用户走公司代理/NAT 后，多个真实用户共享一个出口 IP，被分到同一台服务器 → 负载倾斜；
2. **最短响应时间别只看连接数**：连接少不代表处理快，生产上按**平均响应时间**动态分配，避免慢节点因"连接少"被过度分发。

> 记忆：轮询=挨个来；IP 哈希=认人；URL 哈希=认路径；最短响应=谁快找谁；加权=能者多劳。

## Q4 Nginx 位于七层网络结构中的哪一层？

### 一句话答案

**应用层**——Nginx 是七层负载均衡（基于 HTTP 层做转发）。

### 大白话讲解

Nginx 能读懂 HTTP 协议内容（URL、Cookie、请求头），所以它能做"按 URL 分流""按 Cookie 会话保持"这类**应用层**的精细操作，属于**七层负载均衡**。

> 对比：LVS、F5 等是基于 IP/端口转发的四层负载均衡（传输层），不解析 HTTP 内容，但性能更高。面试里能说出这个对比是加分项。

## 本单元小结

| 概念 | 一句话记住 |
| --- | --- |
| RPC | 像调本地方法一样调远程方法；对外 HTTP、对内 RPC |
| WebSocket | 全双工电话；HTTP/1.1 是半双工对讲机 |
| 负载均衡算法 | 轮询 / IP 哈希 / URL 哈希 / 最短响应 / 加权轮询 |
| Nginx 层级 | 七层（应用层）负载均衡 |
