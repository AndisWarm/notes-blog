## 一、网络基础补课

### 1. 子网、子网掩码、网段 ——「同子网/跨子网」到底是什么

**关联章节**：《01 网络模型》Q3、《10 网络排查》Q1 里反复出现「同子网」「跨子网」，但没解释子网是什么。

**一句话答案**：子网 = 用**子网掩码**把一段 IP 地址切成「网络号 + 主机号」两部分；**网络号相同**的机器算「同一个网段（同子网）」，可以直接通信；网络号不同就要**交给网关转发**（跨子网）。

**大白话讲解**：

IP 地址其实由两段拼成：前一段是「小区名（网络号）」，后一段是「门牌号（主机号）」。但光看 IP 你分不出哪几位是小区、哪几位是门牌——**子网掩码就是那把切分的尺子**。

- 例：`192.168.1.10`，掩码 `255.255.255.0`（也写作 `/24`）。
- 掩码里是 `255` 的位 = 网络号；是 `0` 的位 = 主机号。
- 于是 `192.168.1` 是网络号，`.10` 是主机号。

**怎么判断两台机器在不在同一子网？** 把「源 IP」和「目的 IP」分别跟掩码做**按位与**，结果相同就同网段，不同就跨网段：

```
本机：192.168.1.10  AND 255.255.255.0  = 192.168.1.0
对方：192.168.1.20  AND 255.255.255.0  = 192.168.1.0   ← 相同 → 同子网
对方：192.168.2.30  AND 255.255.255.0  = 192.168.2.0   ← 不同 → 跨子网
```

**为什么这很关键？** 因为同子网内数据可以直接发（ARP 查对方 MAC 即可），而跨子网必须先把包交给**网关**转发（详见下一条）——这就是《01》里「同子网查目标 MAC、跨子网查网关 MAC」的底层原因。

> 记忆：**子网掩码 = 切蛋糕的刀**，网络号是蛋糕的「大块」，主机号是「小块」。同一大块里的机器，一嗓子就能喊到；不同大块的，得先出门（找网关）。

### 2. 网关是什么

**关联章节**：《01 网络模型》Q3、《10 网络排查》Q1。

**一句话答案**：网关（Gateway）= 一个网段通往「外面世界」的**唯一出口**，通常就是你家路由器。跨网段的数据都要先发给网关，再由网关转发出去。

**大白话讲解**：

把局域网想象成一栋楼，楼里的人互相喊话（同子网）没问题，但要寄东西去别的楼（跨子网），必须先送到**传达室**，传达室再帮你转出去。**传达室就是网关**。

- 你电脑网络设置里的「默认网关」（default gateway，如 `192.168.1.1`），就是路由器的内网地址。
- 数据帧的**目的 MAC 填网关的 MAC**（因为局域网里只能直接送到网关），但**目的 IP 仍是最终目标**（网关看 IP 帮你转发）。
- 一句话：**MAC 是「下一跳给谁」（网关），IP 是「最终到哪」（目标）**。

### 3. ICMP 协议 —— ping 到底在干什么

**关联章节**：《10 网络排查》Q5（「ping 走 ICMP 协议」）。

**一句话答案**：ICMP（互联网控制消息协议）= 网络里的「**对讲机/报修单**」，专门传**诊断和控制信息**（如「通不通」「超时了」「目标不可达」），不传业务数据。ping 就是发一个 ICMP「你在吗？」的探测包。

**大白话讲解**：

业务数据走 TCP/UDP，但「主机通不通」「路由对不对」这种**管理信息**得有个专门的协议，就是 ICMP。常见用途：

| 场景 | 用 ICMP 的什么 | 类比 |
| --- | --- | --- |
| ping | Echo Request / Echo Reply（请求/应答） | 「喂，在吗？」「在呢」 |
| tracert/traceroute（查路径） | 每跳返回「超时」，逐步探测经过哪些路由器 | 一路问「你经过谁」，逐站报站名 |
| 报错 | 目标不可达（Destination Unreachable） | 「这地址送不到」 |

**为什么 ping 不通 ≠ 服务不通？** 因为 ICMP 和 TCP 是两套东西。防火墙可以**单独禁掉 ICMP**（防探测扫描）但放行 80/443 的 TCP——于是「ping 不通、网页却打得开」，这就是《10》Q5 那道题的原理。

## 二、HTTP 周边

### 4. CDN 是什么，怎么加速

**关联章节**：《02 HTTP 基础》Q1、《06 RPC·WebSocket·Nginx》Q3（「CDN 回源」）。

**一句话答案**：CDN（内容分发网络）= 把网站静态资源（图片、CSS、JS、视频）**缓存到离用户近的节点服务器**，用户访问时就近取，不用每次都跑回源站（原服务器），于是更快、源站压力更小。

**大白话讲解**：

想象全国只有一家总仓库（源站）在北京，广东的用户每次下单都要从北京发货，又慢又挤。CDN 就是在全国各地开**分仓**，把热门货提前铺到分仓，用户下单就近发货。

- **缓存内容**：静态资源（图片、CSS、JS、视频、下载文件），动态接口一般不缓存。
- **怎么把用户引到最近的分仓？** 靠**智能 DNS**：CDN 商在你访问 `www.xxx.com` 时，根据你的地理位置，把域名解析到离你最近的 CDN 节点 IP（而不是源站 IP）。
- **回源**：分仓没货（缓存没命中）时，才回总仓库（源站）取一次，取完顺便在分仓留一份。

> 一句话：**CDN = 离你更近的仓库 + 智能指路（DNS）**。这也是为什么它属于「应用层协议」——本质是 HTTP 内容的就近分发。

### 5. 正向代理 vs 反向代理

**关联章节**：《06 RPC·WebSocket·Nginx》Q4（Nginx 是反向代理，但没解释这两个词）。

**一句话答案**：**正向代理**站在**客户端**这边，帮客户端访问服务器（服务器不知道真实客户端是谁）；**反向代理**站在**服务器**这边，帮服务器接收请求（客户端不知道后面是哪台真服务器）。

**大白话讲解**：

| 对比 | 正向代理 | 反向代理 |
| --- | --- | --- |
| 站在谁这边 | 客户端 | 服务器 |
| 谁被「藏起来」 | 真实客户端（服务器看到的是代理） | 真实服务器（客户端看到的是代理） |
| 典型用途 | 翻墙、公司统一出口、上网审计 | 负载均衡、缓存、安全隔离、HTTPS 卸载 |
| 代表 | 公司代理、VPN、梯子 | **Nginx**、F5、云厂商的负载均衡 |

- **正向代理**：你上不了某网站，让「中间人」替你访问再转给你。服务器只认识这个中间人。
- **反向代理**：你访问 `www.xxx.com`，其实打到了 Nginx，Nginx 再把请求分给后面多台 Tomcat。你从头到尾只看到 Nginx。

> 一句话：**正向代理替「客户」出头，反向代理替「老板」挡活**。Nginx 是反向代理，所以它才能做负载均衡、按 URL 分流。

### 6. RFC 是什么

**关联章节**：《02 HTTP 基础》Q7（「根据 RFC 规范」）。

**一句话答案**：RFC（Request for Comments）= 互联网标准的**官方文档系列**，所有协议（HTTP、TCP、IP、DNS……）的规则都写在编号 RFC 文档里，比如 HTTP/1.1 定义在 RFC 7230~7235。

**大白话讲解**：

协议不能靠大家「口头约定」，得有一份白纸黑字的规范。RFC 就是这份规范，编号唯一、永久可查。面试里说「RFC 规定 GET 是安全幂等的」，意思是「官方文档里白纸黑字这么写的」。记住「RFC = 协议说明书」即可，不需要背编号。

## 三、HTTPS 与加密进阶

### 7. 前向安全与 (EC)DHE —— 为什么 TLS 1.3 弃用 RSA

**关联章节**：《02 HTTP 基础》Q14、《03 HTTPS 与加密》Q3（「TLS 1.3 移除 RSA（不支持前向安全），改用 (EC)DHE」）。

**一句话答案**：前向安全（Forward Secrecy）= **即使服务器私钥将来泄露，过去的历史加密通信也解不开**。RSA 密钥交换做不到这点（私钥泄露=历史全泄），所以 TLS 1.3 换成了临时密钥的 (EC)DHE。

**大白话讲解**：

先看 RSA 的致命弱点。TLS 1.2 的 RSA 握手是：客户端生成 pre-master key → 用**服务器公钥**加密发过去 → 服务器用**私钥**解开。问题来了：

- 服务器私钥是**长期固定的**（一直用来解密钥交换）。
- 攻击者如果哪天偷到/将来拿到私钥，就能**回放**之前录下的所有流量，解密出每个会话的 pre-master key → 历史通信全部裸奔。

**前向安全**要的就是「就算私钥泄露，历史也保得住」。怎么做到？用**临时密钥（Ephemeral）**：

- (EC)DHE = 每次握手都**现场生成一对一次性密钥**，用完即弃。
- 服务器的长期私钥只用来**签名**（证明身份），不参与加密密钥交换。
- 所以哪怕长期私钥泄露，攻击者也只能伪造身份，却**解不开任何历史会话**——因为每次会话的临时密钥早没了。

> 一句话：**RSA 用「长期锁」锁门，钥匙丢了历史全开；(EC)DHE 用「一次性锁」，开完就扔，历史永远安全。** DHE = Diffie-Hellman 临时密钥交换，ECDHE 是它的椭圆曲线升级版（更快更省）。

### 8. 数字签名与证书链

**关联章节**：《03 HTTPS 与加密》Q2（「验证服务器证书的签名」「根证书」）。

**一句话答案**：数字签名 = 用私钥对内容**盖章**，别人用公钥验章，能证明「内容没被改 + 确实是私钥主人发的」；证书链 = 从你信任的**根证书**逐级向下验证到服务器证书的信任链条。

**大白话讲解**：

**数字签名怎么工作？（先讲原理）**

1. 发送方对内容算出「摘要」（指纹）；2. 用**私钥**把摘要加密，得到「签名」；3. 接收方用**公钥**解开签名得到摘要，再自己算一遍内容摘要，两个对得上 = 内容没被改、且是私钥主人签的。

**证书链是什么？（为什么会有「链」）**

浏览器不能凭空信任每一张服务器证书，它只信任内置的**根证书（root CA）**。但根 CA 不会直接给千千万万网站发证书，而是：

```
根 CA（浏览器内置信任，私钥离线保管）
   └─ 签名 → 中间 CA（intermediate，替根 CA 干活）
               └─ 签名 → 服务器证书（www.taobao.com）
```

验证时，浏览器拿着服务器证书，向上找「谁签了它」，再向上找「谁签了中间证书」，一直追到根——**每一级都用上一级的公钥验签名**，链条没断才算可信。

> 一句话：**签名 = 盖章，证书链 = 从根到叶的「担保人」链条**。中间 CA 存在的意义：根私钥离线锁保险柜，泄露风险极低；中间 CA 出事可以只吊销它，不用动根。

## 四、DNS 进阶

### 9. DNS 记录类型：A / AAAA / CNAME / MX / NS

**关联章节**：《04 DNS 域名解析》（原题没问，但理解 DNS 绕不开）。

**一句话答案**：DNS 不止存「域名→IP」一种映射，不同类型存不同信息：**A 存 IPv4、AAAA 存 IPv6、CNAME 存别名、MX 存邮件服务器、NS 存权威服务器、TXT 存任意文本**。

**大白话讲解**：

| 类型 | 存什么 | 例子 | 类比 |
| --- | --- | --- | --- |
| A | 域名 → IPv4 地址 | `www.a.com → 1.2.3.4` | 名字 → 门牌号 |
| AAAA | 域名 → IPv6 地址 | `www.a.com → 2400:...` | 名字 → 新式门牌 |
| CNAME | 域名 → 另一个域名（别名） | `www.a.com → a.com` | 「小名」→ 大名 |
| MX | 该域的邮件服务器 | `a.com → mail.a.com` | 收信地址 → 邮局 |
| NS | 该域由哪些 DNS 服务器负责 | `a.com → ns1.a.com` | 这块地归谁管 |
| TXT | 任意文本 | SPF 反垃圾、域名验证 | 备注栏 |

**为什么 CNAME 常见？** 网站常把 `www` 指向主域名（`www.a.com → a.com`），主域名再用 A 记录指向 IP。好处：换服务器时只改主域名的 A 记录即可，所有别名自动跟随。

> 记法：**A/AAAA 是「地址」，CNAME 是「别名」，MX 是「邮件」，NS 是「管辖」**。

### 10. 递归查询 vs 迭代查询

**关联章节**：《04 DNS 域名解析》Q2（「本地 DNS 全程跑腿」，但没点出这两个词）。

**一句话答案**：**递归查询** = 你问本地 DNS，它**替你跑完全程**、直接把最终答案给你；**迭代查询** = DNS 服务器之间「**只指路不代跑**」，每次告诉你下一步找谁，你自己（其实是本地 DNS）接着问。

**大白话讲解**：

把解析 `www.server.com` 比作「找人办事」：

- **递归**（客户端 → 本地 DNS）：你说「帮我查出来」，本地 DNS 说「包在我身上」，它去问完根、顶级、权威，最后直接把 IP 给你。**一问一答，结果包办。**
- **迭代**（本地 DNS → 根/顶级/权威）：本地 DNS 问根「IP 是啥？」，根说「我不知道，但 .com 归它管，你去问它」；本地 DNS 再问 .com，它说「去问权威」……**每问一次只拿下一步的地址，不包办结果。**

```
递归：客户端 ──一次性委托──> 本地DNS（内部自己跑全程）──返回最终IP
迭代：本地DNS ──> 根DNS（给.com地址）──> 顶级DNS（给权威地址）──> 权威DNS（给IP）
```

> 一句话：**递归 = 外卖小哥送到门口；迭代 = 只给你下一个路口的指路牌**。真实世界里：客户端对本地 DNS 用递归，本地 DNS 对外用迭代。

### 11. DNSSEC / DoH / DoT —— 安全 DNS

**关联章节**：《04 DNS 域名解析》Q5（提到了但不展开）、《11 网络攻击》Q5（防御用 DoH/DoT）。

**一句话答案**：三者都是给 DNS「上锁」，但锁法不同：**DNSSEC 防篡改（但不加密）**，**DoH/DoT 加密整个查询（防窃听也防篡改）**。

**大白话讲解**：

普通 DNS 是**明文**的，两个问题：别人能**偷看**你在查什么（窃听），也能**改掉**返回结果（篡改 → DNS 劫持）。

| 方案 | 防窃听 | 防篡改 | 原理 | 端口 |
| --- | --- | --- | --- | --- |
| DNSSEC | ✗（内容仍明文） | ✓ | 给 DNS 响应加**数字签名**，客户端验签 | 53 |
| DoT（DNS over TLS） | ✓ | ✓ | 整个 DNS 查询走 TLS 加密通道 | 853 |
| DoH（DNS over HTTPS） | ✓ | ✓ | 把 DNS 查询伪装成 HTTPS 请求 | 443 |

- **DNSSEC**：不加密，只加签名。像「明文信封 + 盖章」——信可以看，但改一个字章就验不过。
- **DoH/DoT**：整个查询加密。像「密码保险柜」——连你在查什么别人都看不见。DoH 走 443，还能伪装成普通网页流量，更难被封锁。

> 一句话：**DNSSEC = 防改不防看；DoH/DoT = 又防看又防改**。这也是《11》里说「用 DoH/DoT 防 DNS 劫持」的原因。

## 五、Cookie 与 Token 周边

### 12. Cookie 三个安全属性：HttpOnly / Secure / SameSite

**关联章节**：《05 Cookie·Session·JWT》Q13/Q14、《11 网络攻击》Q3/Q4（反复出现，但没集中讲）。

**一句话答案**：**HttpOnly = JS 读不到（防 XSS 偷 Cookie）**；**Secure = 只走 HTTPS（防明文泄露）**；**SameSite = 控制跨站请求是否带 Cookie（防 CSRF）**。

**大白话讲解**：

Cookie 由服务器下发，可以带属性。三个安全属性各管一摊：

| 属性 | 作用 | 防什么 | 一句话 |
| --- | --- | --- | --- |
| HttpOnly | 禁止 JavaScript 读取该 Cookie | XSS 偷 Cookie | 只许浏览器带，不许 JS 摸 |
| Secure | 只在 HTTPS 连接里发送 | 明文被窃听 | 明信片不发，只发挂号 |
| SameSite | 跨站请求时不自动携带 | CSRF 借你之手 | 别人的网站带不动我的 Cookie |

**SameSite 三个值**：

- `Strict`：任何跨站请求都不带 Cookie（最严，体验也受影响）；
- `Lax`：默认值（现代浏览器），只有「点击链接跳转」这类顶级导航的 GET 才带，跨站 POST/iframe 都不带；
- `None`：跨站也带，但必须同时配 `Secure`（否则浏览器拒绝）。

> 记忆：**HttpOnly 挡「偷」，Secure 挡「听」，SameSite 挡「借」**。三个一起上，XSS 和 CSRF 都被大幅削弱。

### 13. Base64 是什么 —— JWT 为什么是「明文」

**关联章节**：《05 Cookie·Session·JWT》Q9（「前两部分是 Base64 编码」「载荷是明文，别放敏感信息」）。

**一句话答案**：Base64 是一种**把二进制数据转成可打印字符的编码**，**不是加密**，任何人都能轻松还原。所以 JWT 的 Header/Payload 只是「换了种写法」，内容本质是明文。

**大白话讲解**：

- 计算机数据是二进制（0/1），有些场合只认「可打印的英文字符」（如 URL、JSON、HTTP 头），Base64 就把二进制转成 A-Z、a-z、0-9、`+`、`/` 这些字符，方便传输。
- 规则简单：每 **3 字节 → 4 个字符**，末尾不够用 `=` 补位。**全程可逆，没有密钥**。
- 所以 JWT 中间那段 `eyJ1c2VySWQiOiIxMjMifQ` 其实解码出来就是 `{"userId":"123"}`——**任何人拿到都能解**。

> 结论：**Base64 是「包装」不是「加密」**。JWT 靠的是第三段**签名**来防篡改，而不是靠 Base64 保密。这也是为什么反复强调「别把密码放 JWT 载荷里」。

---

### 14. Cookie 的 Domain / Path 作用域

**关联章节**：《05 Cookie·Session·JWT》Q6/Q7（讲 Cookie vs localStorage，但没讲 Cookie 的生效范围）。

**一句话答案**：Cookie 不是全站通吃，它的生效范围由 **Domain（哪个域）+ Path（哪些路径）** 共同决定；只有落在作用域内的请求，浏览器才会携带它。

**大白话讲解**：

- **Domain**：默认是「设置该 Cookie 的那个域」。可以显式设成父域（如 `example.com`）让所有子域（`a.example.com`、`b.example.com`）共享；但**不能**设成别人的域（如 `taobao.com`）。
- **Path**：默认是「设置时的路径」。设成 `/` 表示全站所有路径都带；设成 `/admin` 则只有访问 `/admin/...` 时才带。

> 一句话：**Domain 管「哪些域能用」，Path 管「哪些页面能用」**。这也是为什么同一个浏览器里，不同站点、不同页面的 Cookie 互不干扰。

## 六、RPC 周边

### 15. 序列化与反序列化

**关联章节**：《06 RPC·WebSocket·Nginx》Q1（RPC 要「像调本地方法一样调远程方法」，但没讲参数怎么传过去）。

**一句话答案**：序列化 = 把内存里的对象/结构**转成可传输、可存储的字节流**；反序列化 = 把字节流**还原回对象**。RPC 必须靠它把「参数打包发出去、结果打包发回来」。

**大白话讲解**：

调用远程方法 `getUser(123)`，参数 `123` 在内存里是一个「对象」，网络只能传字节流，怎么办？先**序列化**成字节（比如 `{"id":123}` 或一段二进制），发过去；对面**反序列化**还原成对象，执行完再把结果序列化发回来。

| 序列化格式 | 特点 | 类比 |
| --- | --- | --- |
| JSON | 文本，人可读，通用，体积大、慢 | 手写信，看得懂但厚 |
| Protobuf | 二进制，紧凑、快，需要提前定义结构 | 电报编码，看不懂但快 |
| Java 原生序列化 | 只限 Java，兼容性差 | 自己家的暗号 |

> 一句话：**序列化 = 打包发货，反序列化 = 拆包还原**。JSON 好读但慢，Protobuf 难读但快——所以性能敏感的内部 RPC 常用 Protobuf。

---

### 16. gRPC 为什么高效

**关联章节**：《06 RPC·WebSocket·Nginx》Q1（「gRPC、Thrift 才是协议实现」）。

**一句话答案**：gRPC 高效的三板斧：**① 基于 HTTP/2（多路复用 + 头部压缩 + 二进制帧）；② 默认 Protobuf 序列化（体积小、编解码快）；③ 强类型接口定义，自动生成客户端/服务端代码**。

**大白话讲解**：

- **HTTP/2**：一条连接能并发跑多个请求（Stream），省掉 HTTP/1.1 的建连和队头阻塞开销。
- **Protobuf**：比 JSON 体积小得多（整数用变长编码），解析也快，适合高频内部调用。
- **IDL 自动生成代码**：写好一份 `.proto` 接口定义，自动生成各语言的客户端/服务端代码，调用方像调本地函数一样调用。

> 一句话：**gRPC = HTTP/2 的高速公路 + Protobuf 的紧凑快递 + 自动生成的司机**。这就是它比「HTTP/1.1 + JSON」适合内部微服务的原因。

## 七、TCP 内核机制

### 17. 滑动窗口 —— 流量控制的核心

**关联章节**：《09 TCP 可靠传输与 UDP》Q2（「通过滑动窗口告诉发送方我还能收多少」，只有一句话，这里展开）。

**一句话答案**：滑动窗口 = 发送方**允许连续发送、但还没收到确认的数据范围**。窗口大小由接收方的接收窗口（rwnd）决定；每收到一个 ACK，窗口就「向右滑」，腾出空间继续发。它让发送方**流水线式发送**，又不把接收方淹没。

**大白话讲解**：

**没有滑动窗口时**：发一个包 → 等 ACK → 再发下一个。一来一回，大部分时间在干等，带宽浪费。

**有了滑动窗口**：发送方可以一口气发多个包（比如连续发 1~5 号），不用每个都等。接收方只回「我已经收到 N 号之前的所有数据」，发送方据此把窗口往前滑。

```
窗口 = [1,2,3,4,5] 可发
发 1~5 号后，收到「ack=4」（前 3 个都收到）
窗口右滑 = [4,5,6,7,8]，又能继续发 6,7,8
```

**窗口大小谁说了算？** 接收方。TCP 头里有个「窗口字段」，接收方每次 ACK 都带上「我的接收缓冲区还能装多少字节（rwnd）」，发送方**绝不超过这个数**发数据——这就是**流量控制**（防止慢的接收方被快的发送方冲垮）。

> 关键：**发送窗口 = min(拥塞窗口 cwnd, 接收窗口 rwnd)**——拥塞窗口防「网络堵」，接收窗口防「对方撑」，取小的那个。这就是《09》Q2 那个公式的完整含义。

### 18. MSS 与 MTU —— 为什么要分片

**关联章节**：《09 TCP 可靠传输与 UDP》Q5（「初始 cwnd = 1 个 MSS」，但没讲 MSS 是什么）。

**一句话答案**：MTU = 数据链路层一帧能装的最大字节数（以太网默认 **1500**）；MSS = TCP 一次能发的数据部分上限 = MTU − IP 头(20) − TCP 头(20) = **1460**。有了 MSS，TCP 就不用让 IP 层去分片。

**大白话讲解**：

**MTU（最大传输单元）**：网络底层「一帧最多装多少」，以太网默认 1500 字节。装不下就得**分片**——把一个包切成几片发，到目的地再拼。

**分片为什么不好？** 效率低、开销大，而且**丢一片就得重传整个包**（IP 层没有重传，重传是 TCP 的事，TCP 又不知道分片细节）。

**MSS（最大报文段大小）**：TCP 很聪明，它问底层「你能装多少」，然后主动把自己的数据段控制在一个合适的大小（1500 − 20 − 20 = 1460），这样**TCP 段 + IP 头 + TCP 头正好塞进一帧，不需要 IP 分片**。

> 一句话：**MTU 是「马路限宽」，MSS 是「货车自觉不超宽」**。TCP 用 MSS 主动规避 IP 分片，是可靠传输的效率优化。

### 19. 累计确认

**关联章节**：《09 TCP 可靠传输与 UDP》Q3（QUIC 对比里提到「累计确认」，没展开）。

**一句话答案**：累计确认 = TCP 的 ACK 表示「**这个序号之前的所有字节我都收到了**」，一个 ACK 能一次性确认多个连续数据段，而不必每个包各回一个 ACK。

**大白话讲解**：

- 发送方发了 1、2、3、4 号数据段，接收方收到后回一个「ack=5」（意思是 5 号之前全收到）。**一个 ACK 顶四个用**，省流量。
- **代价**：如果中间丢了 2 号（收到 1、3、4），接收方只能回「ack=2」，表示「2 号之前的收到了、2 号还没到」——后面的 3、4 即使收到了，发送方也得**从 2 号开始重传**。
- 进阶优化：**SACK（选择性确认）** 可以在 ACK 里额外说「3、4 号其实也收到了」，发送方就只需重传 2 号，不用把 3、4 也重发。

> 一句话：**累计确认 = 「这批货到几号了」的总进度条，省事但粗；SACK = 额外备注「哪些个别货也到了」，精准重传**。这也是 QUIC 换用「独立包号确认」想改进的点（见《09》Q3）。

## 八、安全防御进阶

### 20. CSP 内容安全策略

**关联章节**：《11 网络攻击》Q3/Q4（防御手段里都提到 CSP，没展开）。

**一句话答案**：CSP（Content Security Policy）= 服务器通过响应头告诉浏览器「**只允许从这些来源加载脚本/资源**」，即使恶意脚本被注入页面，浏览器也会拒绝执行——给 XSS 上一道兜底保险。

**大白话讲解**：

XSS 防不胜防，万一某个输入点没过滤好、恶意 `<script>` 混进了页面怎么办？CSP 就是最后一道闸门：

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.trusted.com
```

意思是：默认资源只允许来自本站（`'self'`），脚本只允许来自本站和 `cdn.trusted.com`。攻击者注入的 `<script>alert(1)</script>` 属于「内联脚本」，不在白名单里 → **浏览器直接拒绝执行**。

- 还能禁止内联脚本、禁止 `eval`、限制图片来源等。
- 是「纵深防御」的一环：**输入验证/输出编码是主动防，CSP 是被动兜底**。

> 一句话：**CSP = 给浏览器一张「白名单」，不在名单上的脚本一律不执行**。就算 XSS 混进来了，也执行不动。

---

### 21. HSTS 强制 HTTPS

**关联章节**：《11 网络攻击》Q5（防御 DNS 劫持时提到「HTTPS + HSTS」）。

**一句话答案**：HSTS（HTTP 严格传输安全）= 服务器通过响应头告诉浏览器「**以后访问本站，一律强制用 HTTPS**」，即使你手输 `http://` 或点了 http 链接，浏览器也会自动升级成 `https://`。

**大白话讲解**：

攻击者搞「SSL 剥离」（把 `https://` 偷偷降级成 `http://` 再钓鱼），靠的是用户第一次访问走了明文 HTTP。HSTS 就是堵这个洞：

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

- 浏览器第一次用 HTTPS 访问后，记下这条规则，在 `max-age`（如一年）内，**所有 `http://` 请求都自动改走 `https://`**，根本不发明文请求。
- **局限**：第一次访问如果就走 HTTP，HSTS 还没生效，仍有被剥离的风险。解法：浏览器内置预加载列表（Preload List），把知名站点提前写死成强制 HTTPS。

> 一句话：**HSTS = 浏览器里的「永久转 HTTPS」红头文件**，从源头掐断明文降级钓鱼。

### 22. UDP 反射放大攻击 —— DDoS 的「借刀杀人」

**关联章节**：《11 网络攻击》Q1（表格里「网络层 UDP 反射攻击（NTP Flood）」，没展开）。

**一句话答案**：攻击者伪造受害者的 IP，向有「放大效应」的服务器（如开放的 DNS/NTP 服务）发**小请求**，服务器把**大响应**打给受害者，达到「用小流量制造大流量」的放大效果。

**大白话讲解**：

正常 UDP 服务有个特性：请求很小、响应可能很大（比如查 DNS 记录，问一句能回一大段）。攻击者利用这一点：

1. 伪造源 IP = 受害者 IP，向一堆开放的 DNS/NTP 服务器发小查询；
2. 这些服务器「傻乎乎」地把大响应发回「源地址」——也就是受害者；
3. 受害者被海量响应淹没，网络瘫痪。

**为什么叫「反射 + 放大」？**

- **反射**：攻击流量不是直接打受害者，而是「打到第三方、反弹到受害者」；
- **放大**：响应比请求大很多倍（NTP 可达数百倍），攻击者花 1 份流量，受害者收到 100 份。

**防御**：关掉公网上不必要的 UDP 服务、限速、用带防反射的 DNS 配置（如限制递归查询来源）。

> 一句话：**反射放大 = 伪造你的地址去「撩」第三方，让第三方把「回礼」全砸给你**。攻击者自己不扛流量，受害者却被打爆。
