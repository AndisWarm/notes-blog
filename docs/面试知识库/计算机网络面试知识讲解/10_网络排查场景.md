# 10 网络排查场景

> 面试问法：打开百度首页发生了什么 / 网页转圈怎么排查 / 两台服务器如何判断连通 / 服务端正常却请求不到 / ping 不通但 HTTP 能通。
> 共 5 题，这类场景题越来越常见，考的是对协议体系的整体理解。

## Q1 描述一下打开百度首页后发生的网络过程

### 一句话答案

**解析 URL → 查缓存 → DNS 解析 → 获取 MAC 地址（ARP）→ TCP 三次握手 → （HTTPS 则 TLS 握手）→ 发 HTTP 请求 → 服务器处理并返回响应**。

### 大白话讲解

输入 `www.baidu.com` 回车后，背后发生的事（按顺序）：

1. **解析 URL**：分析用的是什么协议（HTTP/HTTPS）、请求什么资源路径。若协议或主机名不合法，则把内容交给搜索引擎。
2. **缓存判断**：浏览器缓存 → 系统缓存（hosts 文件）→ 路由器缓存 → ISP 的 DNS 缓存，**哪一层命中就返回 IP**，不走完整解析。
3. **DNS 解析**：缓存没命中 → 本地 DNS 服务器 → 根 → 顶级（.com）→ 权威，逐级查到 IP（详见《04_DNS域名解析》）。
4. **获取 MAC 地址**：数据要在局域网里传，必须知道目的 MAC 地址（ARP 协议查）。判断是否同子网：同子网就查目标主机的 MAC；不同子网就**把包发给网关**（查网关的 MAC）。
5. **建立 TCP 连接**：三次握手（详见《07_TCP三次握手》）。
6. **TLS 四次握手**：HTTPS 才有（详见《03_HTTPS与加密》）。
7. **发送 HTTP 请求**：带上 URL、请求方法（GET/POST 等）。
8. **服务器处理并返回响应**：读取网页文件，生成 HTTP 响应，浏览器渲染展示。

> 面试亮点：能把"第 4 步 ARP + 网关"讲出来的人不多，这是拉开差距的地方。

## Q2 网页非常慢转圈圈的时候，如何定位问题？

### 一句话答案

**一层一层排查：客户端网络 → DNS → TCP 三次握手 → HTTP 响应码 → 前端渲染**，最直接的手段是抓包。

### 大白话讲解

排查思路（从外到内）：

**第一步：先分清是客户端还是服务端的问题**
- 浏览器能访问**其他网站**吗？
  - 不能 → 客户端网络问题：检查 WiFi 是否正常、网线插没插、网络配置。
  - 能 → 客户端网络正常，进入下一步。

**第二步：抓包确认 DNS 是否解析出 IP**
- 没解析出来 → 域名写错了；
- 解析出来了 → 继续看 TCP。

**第三步：确认有没有完成三次握手、有没有发出 HTTP 请求**
- 没握手成功 → 网络层/传输层问题；
- 握手成功且发了请求，但页面就是不出来 → 看服务端返回的响应码：
  - **404** → URL 写错了；
  - **500** → 服务器内部出问题；
  - **200** → 数据到了，F12 看前端代码是不是渲染出错。

**第四步（补充）**：如果客户端网络正常但**访问很慢**，看客户端网口流量是否过大，导致 TCP 丢包重传。

> 记忆口诀：**插网线 → 网络配置 → DNS 解析 → 三次握手 → 响应码**，一层层往下查，抓包全程辅助。

## Q3 Server A 和 Server B，如何判断两个服务器正常连接？出错怎么办？

### 一句话答案

TCP 连接建立后，双方长时间无数据交互时**无法主动感知对端死活**——需要**TCP 保活机制**（内核级）或**应用层心跳**（如 HTTP keepalive_timeout 定时器）来探测。

### 大白话讲解

**问题背景**：客户端宕机/网络断开，服务端一直不主动发数据 → 服务端永远感知不到，连接一直占着 ESTABLISHED，浪费资源。

**TCP 保活机制**（内核提供）：定义一段时间，期间无任何连接活动就启动保活——每隔一个时间间隔发一个**探测报文**（数据极少），连续几个探测无响应就判定连接死亡，通知上层应用。

Linux 三个默认参数：

```
net.ipv4.tcp_keepalive_time = 7200   # 2小时无活动启动保活
net.ipv4.tcp_keepalive_intvl = 75    # 每隔75秒发一次探测
net.ipv4.tcp_keepalive_probes = 9    # 连续9次无响应判定死亡
```

即：**Linux 默认至少 2 小时 11 分 15 秒才能发现一个"死连接"**（7200 + 75×9）。

⚠️ 注意：应用要使用保活机制，必须通过 socket 接口设置 **SO_KEEPALIVE** 选项，否则不生效。

**保活探测的三种结果：**

| 情况 | 表现 |
| --- | --- |
| 对端程序正常工作 | 正常响应 → 保活计时器重置，等下个周期 |
| 对端主机宕机后重启 | 能响应，但没有该连接信息 → 回 **RST**，很快发现连接被重置 |
| 对端主机宕机/不可达 | 石沉大海，连续探测无响应 → 达到次数后报告连接死亡 |

**应用层心跳（更快的方案）**：内核保活太慢（2 小时+），生产环境常在应用层自己做。比如 Web 服务的 `keepalive_timeout` 参数：设置 60 秒 → 服务软件启动定时器 → 60 秒内客户端没发新请求 → 回调函数主动释放连接。

> 面试补充：进程崩溃和主机宕机不同——进程崩溃时操作系统回收资源会发 FIN（能感知），主机宕机不会发任何东西（只能靠探测）。

## Q4 服务端正常启动了，但客户端请求不到，有哪些原因？如何排查？

### 一句话答案

**先排查"根本没响应"：IP、端口、防火墙、代理；再排查"有响应但报错"：按状态码（400/401/403/404/500/502/503/504）逐个定位**。

### 大白话讲解

**① 请求完全没响应时的排查顺序：**

1. **IP 地址**是否正确 → ping 一下；
2. **端口号**是否正确 → 本机 telnet IP+端口 测连通性；
3. **防火墙**是否拦截 → 关防火墙或让运维开放对应 IP/端口；
4. **客户端代理设置** → 浏览器/测试工具挂了代理也会导致请求失败。

**② 有响应但返回错误码时的排查：**

| 状态码 | 含义 | 排查方向 |
| --- | --- | --- |
| 400 | 客户端请求错误 | 请求参数格式错误 |
| 401 | 未授权 | 请求头缺 token、auth 等信息 |
| 403 | 禁止访问 | 账号没权限；中间件不允许远程连接（如 Tomcat） |
| 404 | 资源未找到 | URL 地址不正确 |
| 500 | 服务器内部错误 | 登录服务器查错误日志，按提示定位 |
| 502/503/504 | 网关错误/服务不可用/网关超时 | 单次调用就报：后端配置问题或服务挂了；压测时出现：后端压力过大、响应超时 |

## Q5 服务器 ping 不通但是 HTTP 能请求成功，会出现这种情况吗？

### 一句话答案

**会**。ping 走 **ICMP** 协议，HTTP 走 **TCP** 协议——如果服务器防火墙**禁止了 ICMP 但放行 TCP**，就会出现"ping 不通但 HTTP 能通"。

### 大白话讲解

- **ping**：用 ICMP 协议探测主机是否存活（网络层）；
- **HTTP**：基于 TCP 协议传输（传输层 + 应用层）。

防火墙可以按协议分别放行：很多服务器为了防探测，会禁 ICMP（防 ping 扫描），但 80/443 端口的 TCP 照常开放 → 于是 ping 不通，网页却正常打开。

> 补充：反过来"ping 通但 HTTP 不通"也常见——主机活着，但 Web 服务没启动/端口被防火墙挡了。

## 本单元小结

| 场景 | 排查主线 |
| --- | --- |
| 打开网页全过程 | URL → 缓存 → DNS → ARP/MAC → TCP 握手 → TLS → HTTP |
| 页面转圈 | 客户端网络 → DNS → 三次握手 → 响应码 → 前端渲染 |
| 判断服务器连通 | TCP 保活（7200s/75s/9 次）+ 应用层心跳 |
| 服务端正常却请求不到 | IP → 端口 → 防火墙 → 代理；再按 4xx/5xx 逐项定位 |
| ping 不通但 HTTP 通 | ICMP 被防火墙禁，TCP 放行 |
