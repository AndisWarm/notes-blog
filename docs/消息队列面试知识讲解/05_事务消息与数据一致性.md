# 05 事务消息与数据一致性

本章覆盖：普通消息的完整生命周期、为什么会出现数据不一致、事务消息（半消息机制）如何保证数据一致性、RocketMQ 分布式事务完整流程。

---

## 1. 如何保证数据一致性？（为什么要事务消息）

### 一句话回答
"本地业务执行成功"和"消息成功发送"是两个独立动作，可能一个成功一个失败。**事务消息**用"半消息 + 二次确认 + 回查"机制，把两个动作绑成最终一致。

### 展开讲：先看普通消息的生命周期

一条普通 MQ 消息，从产生到被消费的完整流程：

```text
 ①生产者产生消息 ──► ②MQ持久化存储
                          │
                     ③MQ返回ACK给生产者
                          │
                     ④MQ把消息push给消费者
                          │
                     ⑤消费者消费完，响应ACK
                          │
                     ⑥MQ收到ACK，删除消息
```

### 问题场景：下订单的例子

订单系统创建完订单后，再发消息给下游系统。**如果订单创建成功，但消息没有成功发送出去**，下游系统就无法感知这件事，导致数据不一致：

- 订单系统：订单已创建 ✓
- 下游系统：不知道这单存在 ✗

> 为什么不一致？"创建订单"和"发消息"是两个独立操作，中间任何一步失败（网络抖动、服务宕机）都会让两边结果不同。传统"先发消息再执行本地事务"或"先执行本地事务再发消息"都有盲区。

### 两个错误顺序示范

| 顺序 | 问题 |
|------|------|
| 先发消息，再执行本地事务 | 本地事务失败，但消息已发出，下游白干了（甚至误操作） |
| 先执行本地事务，再发消息 | 本地成功，但发消息失败，下游永远不知道 |

### 面试怎么答
"普通消息流程里，本地事务和发消息是两个独立动作，可能产生'订单建了但下游不知道'的不一致。要解决这个问题，需要事务消息：它让消息先以'半消息'状态存起来，等本地事务确认成功后才允许被消费，从机制上保证了两者一致。"

## 2. 事务消息如何实现？（半消息机制）

### 一句话回答
生产者先发一条**半消息**（暂不可消费）给 MQ，MQ 确认收到后，生产者再执行本地事务，然后向 MQ 报告 commit（放行）或 rollback（删除）。如果 MQ 迟迟收不到结果，就**主动回查生产者**要答案。

### 展开讲：完整 8 步流程（面试必背）

```text
 ①生产者 ──半事务消息──► MQ服务器（消息状态：待发送）
 ②MQ持久化消息（待发送状态，不会触发推送）
 ③MQ ──ACK──► 生产者（此时消息不可被消费）
 ④生产者执行本地事务
 ⑤  ├─ 成功 ──► 向MQ发送 commit
    └─ 失败 ──► 向MQ发送 rollback
 ⑥  ├─ commit ──► MQ把消息状态改为"可发送"（放行）
    └─ rollback ──► MQ直接删除消息
 ⑦ 消息可发送后，MQ push给消费者，消费者消费完回ACK
 ⑧ 若MQ长时间没收到commit/rollback ──► 回查生产者 ──► 按查询结果执行最终状态
```

逐步解释：

1. **生产者发送半事务消息（Half Message）**：这条消息 MQ 会存下来，但标记为"待发送"，**暂时不会被消费者看到**；
2. MQ 把消息持久化到存储系统，状态为**待发送**；
3. MQ 返回 ACK 给生产者（注意：此时 MQ **不会触发消息推送**）；
4. **生产者执行本地事务**（比如创建订单、扣库存）；
5. 本地事务执行完，向 MQ 报告结果：
   - 成功 → 发 **commit**；
   - 失败 → 发 **rollback**；
6. MQ 根据结果处理：
   - commit → 消息状态更新为**可发送**；
   - rollback → **删除消息**；
7. 状态为可发送后，MQ 才 push 给消费者，消费者消费完回 ACK；
8. **兜底回查**：如果 MQ 长时间没收到 commit 或 rollback（比如生产者宕机了），它会**主动回查生产者**——问"你那条本地事务到底成功没？"，然后按查询到的结果执行最终状态。

### 核心要点（为什么这样设计）

| 要点 | 解释 |
|------|------|
| 半消息 | 消息已入 MQ 但不可消费，是"预订位" |
| 二次确认 | 本地事务成功与否由生产者事后报告（commit/rollback） |
| 回查机制 | 生产者失联时 MQ 主动问结果，防"永远悬着" |
| 最终一致性 | 保证的是"本地成功 ⇒ 消息必达"，不是 2PC 那种强一致 |

> 重要概念辨析：事务消息保证的是**最终一致性**，不是强一致。它的承诺是"本地事务成功 ⟺ 消息最终被消费"，中间允许短暂的不一致窗口（比如本地成功但 commit 还没到 MQ 的几毫秒）。

### 面试怎么答
"事务消息用半消息机制：先发一条不可消费的半消息，MQ 确认收到后我才执行本地事务，然后 commit 或 rollback。关键是第 8 步回查——如果 MQ 迟迟等不到我的结果，它会反向问我本地事务的状态，防止消息永远悬而未决。这套机制保证'本地成功 ⇒ 消息必达'的最终一致性。"

## 3. RocketMQ 怎么处理分布式事务？（A 转账给 B 的完整例子）

### 一句话回答
RocketMQ 的事务消息是**最终一致性**的分布式事务方案——不是 2PC/3PC/TCC 那种强一致，而是保证"A 本地成功 ⟺ B 最终收到消息"。

### 展开讲：转账场景

假设 A 给 B 转 100 块钱，且 A、B 不在同一个服务上。目标是：A 减 100，B 加 100。

实际情况可能有四种：

| 情况 | A 账户减 100 | B 账户加 100 | 一致性 |
|------|-------------|-------------|--------|
| 1 | 成功 | 成功 | ✓ 一致 |
| 2 | 失败 | 失败 | ✓ 一致 |
| 3 | 成功 | 失败 | ✗ 不一致 |
| 4 | 失败 | 成功 | ✗ 不一致 |

第 1、2 种没问题；**第 3、4 种就是分布式事务要解决的**。看 RocketMQ 如何保证：

#### 完整流程（对应上面的 8 步机制）

1. **A 服务先发送半消息（Half Message）** 给 Broker，消息携带"B 服务即将 +100 元"的信息。半消息 = 暂不能被消费的消息（Producer 已发到 Broker，但被标记为暂不能投递，需要 Producer 二次确认后才能被消费）；
2. A 服务确认半消息发送成功后，**执行本地事务**（A 账户扣 100）；
3. 本地事务有三种结果：
   - 成功 → 第 4.1 步；
   - 失败 → 第 4.2 步；
   - 网络原因没响应 → 第 4.3 步；
4. 分支处理：
   - **4.1 本地事务成功** → Producer 向 Broker 发送 **Commit**，B 服务就可以消费该消息了；
   - **4.2 本地事务失败** → Producer 向 Broker 发送 **Rollback**，Broker 直接删除半消息；
   - **4.3 迟迟没有返回** → 执行 RocketMQ 的**回查回调接口**，查询本地事务的真实状态。

**核心结论：只有 A 服务本地事务执行成功，B 服务才能消费该消息。**

### 追问：A 成功但 B 消费失败怎么办？

如果 B 最终执行失败，几乎可以断定是**代码问题**引起的异常。因为消费端 RocketMQ 有**重试机制**，不是代码问题一般重试几次就能成功。

如果是代码问题导致多次重试仍失败，也没关系：
- 把该异常**记录下来**，由**人工处理兜底**；
- 人工修正后，事务就达到了最终一致性。

### 面试怎么答
"RocketMQ 的分布式事务是最终一致性方案，不是 2PC 那种强一致。转账场景中：A 先发半消息 → 执行本地扣款 → commit 或 rollback → 只有本地成功 B 才能消费。如果 B 消费失败，靠 RocketMQ 的重试机制自动重试，多次失败后记录日志人工兜底。**关键点是回查机制**——A 本地事务的结果丢失时，Broker 会反查 A 要答案。"
