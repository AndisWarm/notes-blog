# 07 RocketMQ 详解

本章覆盖：为什么选 RocketMQ、RocketMQ vs Kafka 对比与选型、延时消息底层原理、分布式事务（半消息机制）、消息顺序保证、重复消费防护、消息积压处理。

> 前 6 章是 MQ 通用知识，本章开始进入"三大中间件逐个击破"。RocketMQ 是阿里的电商级消息中间件，面试重点：延时消息原理、顺序消息、队列数与消费者数的关系（积压扩容的盲区）。

## 1. 为什么选择 RocketMQ？

### 一句话回答
项目选 RocketMQ 的三个理由：**Java 开发（易读源码）、阿里背书（经得起双十一考验）、特性丰富（12 种高级特性）**。

### 展开讲：三个原因

1. **开发语言优势**：RocketMQ 用 Java 开发。比起用 Erlang 开发的 RabbitMQ，Java 有更易上手的阅读体验和更大的受众群。遇到底层问题，熟悉 Java 的同学可以直接深入读源码分析排查；
2. **社区氛围活跃**：RocketMQ 是阿里巴巴开源且内部大量使用的消息队列——经受住了残酷的生产环境考验（双十一），能针对线上复杂需求提供解决方案；
3. **特性丰富**：官方文档列举的高级特性达 **12 种**：顺序消息、事务消息、消息过滤、定时消息等。丰富的特性能在复杂业务场景下提供更多思路和解决方案。

### 面试怎么答
"三个理由：技术栈亲和（Java 源码可读可排查）、生产验证（阿里双十一扛过真实流量）、特性全（12 种高级特性，比如顺序消息、事务消息、定时消息）。"

## 2. RocketMQ 和 Kafka 的区别是什么？如何做技术选型？

### 一句话回答
**Kafka 赢在吞吐（日志流场景），RocketMQ 赢在业务功能（延迟消息、事务消息）。** 选型口诀：只要收发包、容忍小概率丢数据、要极致吞吐 → Kafka；要业务功能（延迟/事务消息）、Java 技术栈 → RocketMQ。

### 展开讲：先看各自的优缺点

#### Kafka 的优缺点
- **优点**：高吞吐——普通机器（4CPU 8G）一台能抗住**十几万 QPS**；支持集群部署，部分机器宕机不影响使用；
- **缺点**：配置不当存在丢消息风险。Kafka 收到消息后默认先写入 **OS Page Cache**，由操作系统决定何时刷盘（和 MySQL/Redis AOF 做法一致，并非 Kafka 独有）。如果配置 `acks=0/1` 或开启 `unclean.leader.election.enable` 等不安全参数，主节点宕机时可能丢消息。要强可靠需配合 `acks=all` + 多副本 ISR + 禁止 unclean 选举。另外功能相对单一，延迟消息、事务消息等高级特性较弱，适用场景偏大数据和日志流。

> 补充解释几个参数：`acks=0` 发出去就不管；`acks=1` 只要 Leader 存了就返回成功；`acks=all` 要等所有同步副本都存了才算成功（最安全最慢）。

#### RocketMQ 的优缺点
- **优点**：支持功能多（延迟队列、消息事务等），单机吞吐 **10 万级**，支持大规模集群部署、线性扩展方便，Java 开发契合国内大部分公司技术栈；
- **缺点**：性能比 Kafka 略弱。关键差异在**零拷贝**：
  - Kafka 发送消息给消费者用的是 `sendfile` **真·零拷贝**——数据完全不经过用户态，由 DMA 从 page cache 直接送往网卡；
  - RocketMQ 用 `mmap + write`——严格说只是**减少了一次 CPU 拷贝**（省去了 read 系统调用中用户态与内核态的拷贝），但 page cache 到 socket buffer 仍有一次 CPU 拷贝，不是真正的零拷贝，业界称"广义零拷贝"。

### 怎么选？

| 需求 | 选择 |
|------|------|
| 只收发消息、可容忍小部分数据丢失、要求极高吞吐 | **Kafka**（如用户行为日志收集与传输） |
| 需要延迟队列、消息事务等业务功能 + Java 技术栈 | **RocketMQ** |

### 面试怎么答
"两者的核心差异：Kafka 是吞吐机器（十几万 QPS），但功能单一、配置不当会丢消息；RocketMQ 功能全（延迟/事务消息），吞吐 10 万级略逊，且零拷贝上是 mmap+write 的广义零拷贝，不如 Kafka 的 sendfile 彻底。选型看场景：日志流选 Kafka，业务消息选 RocketMQ。"

## 3. RocketMQ 延时消息的底层原理

### 一句话回答
延时消息发出去后先进**延时 Topic 的队列**，由 `ScheduleMessageService` 的定时任务轮询，**到点后转发到原始 Topic**，消费者此时才能消费到。

### 展开讲：原理流程

```text
 生产者发送延时消息（如延迟30分钟）
        │
        ▼
 Broker 收到后存入"延时Topic"的队列（按延迟级别分队列）
        │
        ▼
 ScheduleMessageService 中每个 queue 对应的定时任务不停地执行
        │ 检查哪些消息已到设定时间
        ▼
 到点的消息被转发到"消息的原始Topic"
        │
        ▼
 消费者从原始Topic消费（此时才真正"看到"消息）
```

关键组件：
- **延时 Topic**：专门存放延时消息的队列区域；
- **ScheduleMessageService**：调度服务，每个 queue 对应一个定时任务，不停检查"哪些消息到点了"；
- **转发**：到点的消息从延时 Topic 转发到消息原本的 Topic。

> 为什么这样设计？好处是 Broker 不用为每条消息单独"定闹钟"，而是**按延迟级别分桶轮询**，性能可控。RocketMQ 的延时消息只支持**固定延迟级别**（如 1s/5s/10s/30s/1m/2m...），不支持任意秒数，就是这个原因。

### 面试怎么答
"延时消息的底层是'两级 Topic'：消息先进延时 Topic 的队列，ScheduleMessageService 的定时任务持续检查，到点的消息再转发到原始 Topic，消费者才能消费。由于是按延迟级别分队列轮询，所以 RocketMQ 延时消息只支持固定级别，不支持任意时间。"

## 4. RocketMQ 怎么处理分布式事务？

### 一句话回答
RocketMQ 的分布式事务是**最终一致性**方案（不是 2PC/3PC/TCC 那种强一致）：**半消息 + 二次确认 + 回查**，保证"本地事务成功 ⟺ 消息最终被消费"。

### 展开讲：A 转 B 100 块钱的完整流程

可能出现的四种情况（只有 1、2 一致，3、4 不一致）：

| 情况 | A 减 100 | B 加 100 |
|------|---------|---------|
| 1 | 成功 | 成功 ✓ |
| 2 | 失败 | 失败 ✓ |
| 3 | 成功 | 失败 ✗ |
| 4 | 失败 | 成功 ✗ |

RocketMQ 的保证流程：

1. **A 服务发送半消息（Half Message）** 给 Broker：消息已成功发到 Broker 端，但被标记为**暂不能投递**状态——需要 Producer 二次确认后，Consumer 才能消费；
2. A 服务确认半消息发送成功后，**执行本地事务**（A 扣 100）；
3. 本地事务三种结果：成功 / 失败 / 网络等原因没响应；
4. 分支处理：
   - **本地事务成功** → Producer 向 Broker 发送 **Commit** → B 服务可以消费该消息；
   - **本地事务失败** → Producer 向 Broker 发送 **Rollback** → Broker 直接删除半消息；
   - **迟迟没有返回** → 执行 RocketMQ 的**回查回调接口**，查询本地事务真实状态。

**核心：只有 A 服务本地事务执行成功，B 服务才能消费该消息。**

### 追问：B 消费失败怎么办？
- B 最终执行失败，几乎可以断定是**代码问题**——因为消费端有重试机制，不是代码问题一般重试几次就能成功；
- 代码问题多次重试失败 → 把异常记录下来，**人工兜底处理**，最终达到一致性。

### 面试怎么答
"RocketMQ 事务消息是最终一致性方案。转账例子：A 先发半消息占位 → 执行本地事务 → commit 放行或 rollback 删除 → 只有本地成功 B 才能消费；B 失败靠重试，多次失败人工兜底。**点睛之笔是回查**：本地事务结果丢失时，Broker 反查 A 要答案，防止消息永远悬着。"（完整流程详见 05 章第 3 节）

## 5. RocketMQ 消息顺序怎么保证？

### 一句话回答
**局部顺序一致**：把一组必须有序的消息发到**同一个队列（MessageQueue）**，Broker 对队列加锁保证同一队列同一时刻只被一个消费者消费，消费者串行处理。

### 展开讲：原理

#### 为什么需要顺序？
一个订单产生 3 条消息：订单创建 → 订单付款 → 订单完成。消费时必须按这个顺序，否则业务混乱（先完成再创建？）。但**不同订单之间的消息可以并发**（可以先处理第三个订单的付款，再处理第二个订单的创建）。

#### 推荐的解决方案
**按业务划分队列**：把需要顺序消费的消息发往同一队列，不同业务之间的消息仍并发消费。既满足顺序消费，又提高处理速度，避免消息堆积。

#### 底层原理（两层保障）
- **Producer 端**：把一批需要保证顺序的消息发送到**同一个 MessageQueue**；
- **Consumer 端**：通过**加锁机制**保证消费顺序——**Broker 端对 MessageQueue 加锁，保证同一个 MessageQueue 只能被同一个 Consumer 消费**，消费者单线程串行处理队列内消息。

```text
 订单A：创建 → 付款 → 完成（必须有序）
 订单B：创建 → 付款 → 完成（必须有序）
        │                │
        ▼                ▼
   MessageQueue 1    MessageQueue 2（按业务分队列）
   （Broker 加锁，同一时刻只被一个消费者消费，串行处理）
```

### 面试怎么答
"RocketMQ 保证的是局部顺序：按业务把有序消息发到同一队列；Broker 对 MessageQueue 加锁，保证同一队列只能被同一个消费者消费，消费者串行处理。不同业务的队列之间仍可并发，兼顾了顺序和吞吐。"

## 6. RocketMQ 怎么保证消息不被重复消费？

### 一句话回答
RocketMQ 保证**至少一次**（不丢但可能重），所以防重复靠**业务层幂等**：用唯一订单号或事务 ID 做幂等标识，确保同样操作只执行一次。

### 展开讲
在业务逻辑中实现幂等性，确保即使消息被重复消费，也不会影响业务状态。例如支付/转账类操作，用**唯一订单号或事务 ID** 作为幂等标识，同样的操作只会被执行一次。

具体做法（结合 04 章的五种幂等方案）：处理前先查"这个订单号处理过没"——查数据库唯一索引或 Redis，处理过就跳过。

### 面试怎么答
"RocketMQ 默认是至少一次语义，重复消费不可避免，所以业务侧必须做幂等：用唯一业务 ID（订单号/事务 ID）做幂等键，消费前先查重，处理过就丢弃。"

## 7. RocketMQ 消息积压了，怎么办？

### 一句话回答
像大禹治水，分**"紧急疏通止损"和"事后排查根因"**两步：少量积压→扩容消费者（先确认队列数够）；海量积压→临时 Topic 嫁接术（10 倍队列 + 10 倍机器）；业务允许→重置消费点位跳过；最后死磕消费者代码瓶颈。

### 展开讲：完整处理层次

#### 第一招：扩容消费者（但要小心队列数的坑）
处理慢了，直接加几台消费者服务器？**有一个非常核心、经常踩坑的知识点**：

> **在 RocketMQ 里，一个队列（MessageQueue）同一时刻只能被一个消费者机器全权占有。**

比如 Topic 默认只有 **4 个队列**，部署 4 台消费机器就到上限了。此时紧急再加 10 台机器，这 10 台只能干瞪眼分不到队列，**起不到任何加速作用**。

#### 第二招：临时 Topic 嫁接术（海量积压的真正大招）
积压太多时，快速恢复正常业务的杀手锏：

1. 写一套非常简单的**"搬砖程序"**上线：没有任何复杂业务逻辑，唯一任务就是**全速把积压的老 Topic 消息拉出来，原封不动发到临时的新 Topic**；
2. 建新 Topic 时，**一口气分配数十或上百个队列**；
3. 部署几十台真正干活的业务消费者机器，对接多队列的新 Topic；
4. 突破原队列数量限制，**以十倍甚至几十倍速度清掉积压**；
5. 积压处理完，切回原老 Topic 架构。

#### 第三招：业务兜底方案
如果系统濒临崩溃，且这些积压消息（如非关键点击日志、普通埋点数据）**丢了不影响核心营收**——直接在控制台**一键把消费组的消费点位（Offset）重置到最新时间点**，人为跳过积压消息，先保住系统可用性。

#### 事后：排查根因
积压十有八九不是发得快，而是**消费得慢**。查消费者代码：
- 是不是在调第三方接口，恰好网络抖动一直超时？
- 是不是写 MySQL 出现慢查询甚至死锁？

找到卡脖子的地方优化掉（引入缓存、优化 SQL），才能保证以后不再发洪水。

### 面试怎么答
"处理积压是一套组合拳：先评估积压量——少量积压且队列数够，就扩容消费者；海量积压用转存临时 Topic 的杀手锏（10 倍队列 + 10 倍机器极速消化）；业务允许就重置消费点位跳过；最后一定回过头查消费者代码的性能瓶颈，治标更要治本。**一定要点出队列数和消费者数的关系**——这是 RocketMQ 扩容的盲区：队列只有 4 个，加再多机器也白搭。"

## 附：用一句话记住今天的内容

> **RocketMQ = 阿里的业务型 MQ（Java、12 种特性、10 万级吞吐）：延时消息靠"延时 Topic + 定时任务到点转发"；事务靠"半消息 + commit/rollback + 回查"的最终一致；顺序靠"同一队列 + Broker 加锁 + 串行消费"；防重靠业务幂等；积压大招是"临时 Topic 嫁接术"——但先记住：一个队列只能被一台消费机器占有，队列数是扩容的天花板。**
