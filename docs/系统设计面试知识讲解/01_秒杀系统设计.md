# 01 秒杀系统设计

本章覆盖：秒杀场景的核心特点与四大问题（高并发、防超卖、用户体验、防刷）、五层架构设计（前端、网关、缓存、消息队列、数据库）、Redis 原子操作 + MQ 异步扣库存的完整下单流程、以及业界经典的「层层漏斗」三关设计（前端网关拦截 → Redis 预扣库存 → MQ 异步下单）。

---

## 1. 秒杀是什么？它的核心特点是什么？

### 一句话回答
秒杀就是**在极短时间内，大量用户同时抢购少量商品**的场景，核心特点是**高并发、低库存、短时间爆发式访问**。

### 展开讲：秒杀的三个核心特点

**特点一：高并发**

平时一个电商网站每秒可能只有几百个请求，秒杀开始的瞬间，请求量可能暴涨到每秒几万、几十万。就像平时商场门口冷冷清清，一搞「全场一折」促销，门口瞬间堵了几万人。

**特点二：低库存**

秒杀商品通常只有几件、几十件。库存是**极其稀缺的资源**，谁抢到谁赢。这意味着系统绝大部分请求最终是「失败」的，但我们依然要让每一个请求都能被「快速、正确地处理」，而不是把服务器压垮。

**特点三：短时间爆发式访问**

秒杀的时间窗口极短，通常只有几秒到几分钟。流量不是均匀分布的，而是**在开场那一瞬间形成尖峰**。这个「尖峰」就是系统设计的最大挑战——我们不是要扛住「平均流量」，而是要扛住「峰值流量」。

### 比喻：商场限时抢购

想象一家商场宣布：上午 10 点整，10 部最新款手机，每部只要 1 块钱，先到先得。10 点钟声一响，商场门口 10 万人同时往里冲——这就是高并发；货架上只有 10 部手机——这就是低库存；10 点整到 10 点零 5 分这 5 分钟——这就是短时间爆发。

### 面试怎么答
先给结论：「秒杀的核心特点是高并发、低库存、短时间爆发式访问」，再用一句话点出本质：「绝大部分流量是无效流量，设计的核心是把无效流量挡在外面，把有效流量快速、正确地转化为订单。」这句话一出口，面试官就知道你抓住了秒杀的本质。

## 2. 秒杀要解决的四大问题是什么？

### 一句话回答
四大问题是：**高并发处理**（扛住海量请求）、**库存一致性**（防超卖）、**用户体验**（抢到了要有反馈）、**防刷机制**（防止机器人和黄牛）。

### 展开讲：四大问题逐个拆

**问题一：高并发处理**

10 万人同时点按钮，服务器如果每来一个请求就开一个线程处理，瞬间就把线程池打爆、把数据库连接池打爆。解决思路是**层层分流、层层拦截**，把 10 万请求在到达数据库之前就削减到几百个。这就像游乐场门口，保安先拦住一部分、检票员再拦一部分、最后只有买了票的人才能进场。

**问题二：库存一致性（防超卖）**

库存只有 10 件，但 10 万人同时扣库存，如果处理不好，就会出现「卖出去了 100 件」——**超卖**。这是秒杀系统最不能犯的错：卖了 10 件商品，却让 100 个人付了钱，剩下 90 个人要么退款要么投诉。库存数据必须**准确**，扣减必须**不重不漏**。

**问题三：用户体验**

用户抢不到没关系，但系统不能「卡死」「白屏」「转圈半天没结果」。秒杀对体验的要求是：**快速给出结果**——抢到了就明确告诉用户「抢到了，正在下单」，没抢到就明确告诉「已售罄」。最怕的是用户刷了半天，最后超时失败，也不知道自己到底抢没抢到。

**问题四：防刷机制**

秒杀利益巨大，必然有人用脚本、机器人抢购：毫秒级点击、批量注册小号、用代理 IP 刷接口。如果不防刷，10 台手机可能全被同一批脚本抢走，普通用户根本抢不到，活动也就失去了意义。

### 比喻：演唱会抢票

想象一场演唱会只有 500 个座位（低库存），开票瞬间 50 万人同时抢（高并发），开票后 3 分钟售罄（短时间爆发）。你作为主办方要解决：服务器别被挤爆（高并发）、座位别卖给 5000 个人（防超卖）、买票的人要立刻知道买没买到（体验）、黄牛脚本别把票全扫走（防刷）。

### 四大问题对比表

| 问题 | 本质 | 典型表现 | 核心解法 |
|---|---|---|---|
| 高并发 | 请求量超过系统处理能力 | 服务器崩溃、接口超时 | 分层拦截、限流、削峰 |
| 防超卖 | 并发扣库存导致数据错乱 | 卖出数量超过库存 | Redis 原子操作 + 异步落库 |
| 用户体验 | 结果反馈不及时、不明确 | 白屏、转圈、重复支付 | 异步下单 + 前端轮询查结果 |
| 防刷 | 恶意流量抢占资源 | 脚本抢购、黄牛囤货 | 验证码、频率限制、黑名单 |

### 面试怎么答
四个问题一口气报出来：「高并发、防超卖、用户体验、防刷」，然后说「这四个问题里，**防超卖是底线**（卖多了要赔钱），**高并发是核心挑战**（其他三个问题都在高并发背景下才变得棘手），所以我的设计围绕『把流量挡在外面、把库存扣得准确』展开」。这样回答既全面又有主次。

## 3. 秒杀系统的分层设计长什么样？（架构总览）

### 一句话回答
秒杀系统分五层：**前端层**（挡第一波）、**网关层**（拦流量、验身份）、**缓存层**（Redis 扛住高并发读和扣库存）、**消息队列**（削峰填谷、异步下单）、**数据库层**（最终落库、保证数据正确）。

### 展开讲：五层架构逐层看

**第一层：前端层**

- **动静分离**：把商品详情页的静态资源（图片、CSS、JS）放到 CDN 上。用户打开页面时，图片从离自己最近的 CDN 节点加载，根本不经过我们的服务器。服务器只需要处理「动态请求」（比如查询库存、提交订单），压力小一大半。
- **请求拦截**：秒杀按钮点击后立即**置灰**（防止反复点击）、点击前要求输入**验证码**（人机校验 + 错峰）、限制同一用户**点击频率**（比如 1 秒最多 1 次）。

**第二层：网关层**

- **流量拦截**：按 IP 限流（同一个 IP 每秒最多 N 个请求）、维护黑名单（检测到脚本行为直接拉黑）。
- **身份验证**：校验用户是否登录、Token 是否有效、请求签名是否合法。没有合法身份的直接拒绝，根本到不了后面。

**第三层：缓存层**

- 商品库存提前**预热**到 Redis（活动开始前把库存从数据库加载到 Redis）。
- 秒杀期间**库存的检查和扣减全部在 Redis 完成**——Redis 是单线程执行命令、速度极快，每秒可以扛几十万次操作，而数据库每秒可能只能扛几千次。

**第四层：消息队列（MQ）**

- **削峰填谷**：Redis 扣减成功只是「占了名额」，真正创建订单是异步的。把「创建订单」的消息扔进 MQ，订单服务按自己的速度慢慢消费。就像水库大坝：洪峰来了先蓄在水库里，再慢慢放水，下游河道永远不会被冲垮。
- **异步解耦**：秒杀服务和订单服务解耦，订单服务挂了也不影响秒杀主流程。

**第五层：数据库层**

- **乐观锁扣库存**：更新库存时带上版本号条件，`UPDATE stock SET count = count - 1 WHERE id = ? AND count > 0`，防止并发覆盖。
- **主从读写分离**：写库只负责写，读库分担查询压力。

### 比喻：机场安检

想象机场登机流程：大门口保安先看行程码（前端拦截）→ 安检通道分流（网关限流）→ 值机柜台快速办理（Redis 高并发处理）→ 行李分拣传送带慢慢运（MQ 削峰）→ 飞机最终载客起飞（数据库落库）。每一层都只放行一部分人，最终只有少量「有效旅客」走到登机口。

### 面试怎么答
按「用户请求从浏览器到数据库的路径」串讲五层：「浏览器端先把静态资源打到 CDN，动态请求进网关，网关做限流和鉴权，然后到 Redis 层做库存预扣，扣成功发消息到 MQ，MQ 背后订单服务慢慢消费并写 MySQL」。一句话概括设计思想：「**能用前置拦截解决的，绝不拖到后面；能异步做的，绝不同步做；能放在 Redis 的，绝不放在 MySQL。**」

## 4. 核心方案：库存防超卖怎么实现？

### 一句话回答
**Redis 原子操作预扣库存 + MQ 异步落库**：秒杀请求先在 Redis 里用原子命令（`DECR` 或 Lua 脚本）扣减库存，扣减成功才发消息给 MQ，后台订单服务消费消息，用乐观锁在 MySQL 真正扣库存生成订单，最后做一致性校验兜底。

### 展开讲：为什么「先查再减」会超卖

先看一个错误示范——很多新手会这么写：

```java
// 错误写法：先查库存，再减库存
int stock = redis.get("stock");      // 第 1 步：查
if (stock > 0) {                     // 第 2 步：判断
    redis.set("stock", stock - 1);   // 第 3 步：减
    // 下单...
}
```

这 3 步之间不是原子的。假设库存只剩 1 件，用户 A 查到了 `stock = 1`，还没来得及减，用户 B 也查到了 `stock = 1`。两个人同时判断「有货」，同时执行减库存，库存变成了 `-1`——**超卖**了。

**比喻**：商店只剩最后一件衣服，两个顾客同时伸手去拿。谁先拿到取决于谁手快，但两个人都「看到」了衣服，都以为自己买到了。问题就出在「看到」和「拿到」之间有时间差——**一查一减之间，别人插队了**。

### 展开讲：方案一——Redis 单命令原子扣减

Redis 是**单线程**执行命令的，一个命令从开始到结束不会被其他命令打断。所以用 `DECR` 这个原子命令扣减库存，天生不会超卖：

```bash
# 扣减前先检查库存
GET stock        # 假设返回 10，有货
DECR stock       # 原子扣减，返回 9，扣减成功
```

`DECR` 返回扣减后的值，如果返回**负数**，说明扣超了，需要把库存加回来并返回「已售罄」：

```bash
DECR stock       # 返回 -1，说明超扣了
INCR stock       # 加回来，恢复库存
```

### 展开讲：方案二——Lua 脚本把「检查 + 扣减」捆绑原子执行

用 `DECR` 虽然单命令原子，但「先检查再扣减」是两条命令，中间还是有空隙。更严谨的做法是**用 Lua 脚本把检查和扣减捆绑在一起**，让 Redis 把整个脚本当一条命令执行，中间不可能插入任何其他操作：

```lua
-- Lua 脚本：检查库存是否充足，充足则扣减，返回 1；不足返回 0
local stock = redis.call('GET', KEYS[1])
if tonumber(stock) <= 0 then
    return 0   -- 库存不足，直接失败
end
redis.call('DECR', KEYS[1])
return 1       -- 扣减成功
```

调用方（Java 伪代码）：

```java
// 把 Lua 脚本和库存 key 一起发给 Redis，原子执行
Long result = redis.eval(SCRIPT, Arrays.asList("seckill:stock:1001"), Collections.emptyList());
if (result == 1L) {
    // 扣减成功，发消息给 MQ，异步创建订单
    mq.send("order:create", orderMessage);
} else {
    // 库存已空，直接返回「已售罄」
    return "已售罄";
}
```

**为什么 Lua 脚本靠谱？** Redis 执行 Lua 脚本时，整个脚本是原子性的——就像把「检查钱包 → 掏钱 → 成交」写成一份合同，一次性签完，中间不可能有人插队。库存为 0 之后，脚本直接返回 0，所有后来的请求立刻得到「已售罄」，不会白跑一趟数据库。

### 展开讲：完整下单流程（背这个流程图）

1. **秒杀请求到达**：用户点击按钮，请求进入网关；
2. **基础校验**：网关校验 Token、签名、频率，前端已经用验证码拦过一波；
3. **Redis 检查库存**：执行 Lua 脚本（`GET` 检查 + `DECR` 扣减，原子执行）；
4. **扣减成功 → 发消息到 MQ**：把「用户 ID + 商品 ID + 秒杀单号」封装成消息发出去，同时给前端返回「抢购成功，正在排队出票」；
5. **后台服务消费消息**：订单服务从 MQ 拉取消息，创建订单；
   - **乐观锁减库存**：`UPDATE goods SET stock = stock - 1 WHERE id = ? AND stock > 0`，防止数据库层面并发错误；
   - **唯一标识防重复消费**：每个秒杀请求生成唯一订单号（用户 ID + 商品 ID），MQ 消息带这个唯一 ID，消费端先去查「这个 ID 的订单是否已存在」，存在就丢弃——保证**同一请求只下一单**；
6. **最终一致性校验**：定时任务定期对比「Redis 剩余库存 + 数据库已扣库存」与「活动总库存」是否一致，发现不一致就触发**补偿逻辑**（比如 Redis 有库存但订单没建，说明消息丢了，补发消息重建订单；订单建了但 Redis 没扣，说明异常，回滚订单）。

### 比喻：奶茶店限时半价

奶茶店搞限时半价，只有 100 杯的料。门口服务员用**电子计数器**（Redis）发号——每放进来一个人就按一下减一，这个「按一下」是瞬间完成、不可能两个人同时按成功的（原子操作）。拿到号的人去柜台（MQ 消费者）排队做奶茶（创建订单），做奶茶的速度是有限的，但排队的人再多也不会把柜台挤塌。打烊后店员核对：发的号 + 柜台做的奶茶 = 100 杯，对不上就查原因（最终一致性校验）。

### 面试怎么答
主线一句话：「**Redis 原子预扣 + MQ 异步落库**」。展开说流程：「请求先过网关校验，然后 Redis Lua 脚本原子扣库存，扣成功发 MQ，订单服务消费消息用乐观锁落库、用唯一 ID 防重复下单，最后定时任务做一致性对账」。面试官问「为什么用 Lua 不用 GET+DECR」→ 答「GET 和 DECR 两条命令之间有间隙会超卖，Lua 脚本把检查和扣减捆成一个原子操作」。问「消息丢了怎么办」→ 答「最终一致性校验 + 补偿逻辑兜底」。

## 5. 「层层漏斗」原则：10 万人抢 10 台手机

### 一句话回答
秒杀设计的核心思想是**层层漏斗**：每一层都过滤掉一部分流量，让请求从 10 万量级逐层衰减，最后只有极少数「有效请求」到达数据库。10 万个人抢 10 台手机，系统要扛的不是 10 万次下单，而是如何优雅地拒绝 99990 个请求、并正确处理 10 个订单。

### 展开讲：为什么必须层层过滤

数据库每秒只能处理几千次操作，而秒杀峰值有每秒几十万请求。如果不分层，10 万个请求同时打到数据库，数据库瞬间宕机——结果不是「10 个人买到」，而是「0 个人买到，系统瘫痪」。所以设计目标很明确：**让每一层的处理能力都能接住上一层的流量，越到后面流量越少**。

### 比喻：游乐场限量体验项目

游乐场新开了一个项目，一天只接待 10 个游客（低库存），开园瞬间 10 万人冲过来。你设计了三个关卡：

- **第一关·门口**：保安检查预约码，没有预约的直接劝返（前端/网关拦截）；
- **第二关·闸机**：凭预约码刷一次卡，卡里的名额立即核销一次（Redis 预扣），名额用完闸机自动关闭，后面的人看到「名额已满」直接离开；
- **第三关·项目入口**：核销成功的人排成小队，项目工作人员按固定速度放人进去体验（MQ 异步消费），体验完成发纪念品（生成订单）。

三关下来：10 万人 → 被第一关筛掉大半 → 第二关只剩 10 个名额 → 第三关慢慢体验。项目组不慌、游客不挤、名额不出错。

### 第一关：前端与网关拦截（拦第一波流量）

**做什么**：

- **动静分离**：静态资源上 CDN，图片、CSS、JS 不经过服务器；
- **按钮置灰 + 频率限制**：用户点击后按钮立即变灰，同一用户 1 秒最多点 1 次；
- **验证码错峰**：这是最妙的一招。正常情况下用户点击是「毫秒级」的——10 万人可能在同 1 毫秒内同时点下按钮。但让用户先输验证码，输入过程至少要 2~5 秒——**验证码把「一毫秒的尖峰」物理打散成「几秒钟的平缓流量」**。10 万个请求不再同时到达，而是分散在这几秒里陆陆续续到达，服务器的压力瞬间降了一个数量级。
- **网关限流**：IP 限流、黑名单、Token 校验，非法请求在网关就返回。

**比喻**：演唱会入场不搞「开门一拥而入」，而是让观众先到检票口排队检票，每人验票花 3 秒，10 万人就被「拉长」成了一条持续几小时的长队，入口永远不会被挤爆。

### 第二关：Redis 预扣库存（拦第二波流量）

**做什么**：

- 活动开始前把库存**预热**到 Redis；
- 请求到达后用 **Lua 脚本**执行「检查库存 + 扣减库存」的原子操作；
- **库存为 0 之后，所有请求直接返回「库存已空」**，不再往后走——第二关把 10 万请求直接砍到只剩 10 个「幸运儿」。

**为什么「查一下再减 1」会超卖**：前面讲过，`GET` 查库存和 `DECR` 减库存之间有时间差，两个请求可能同时看到「还剩 1 件」，都以为抢到了。Lua 脚本把「查」和「减」捆绑成一步原子操作，就像把「看商品 → 扫码 → 付款」合并成一次扫码，不存在中间插队的窗口。

**比喻**：餐厅只有 10 个座位，门口放一个电子叫号器，每个进店的人按一下「-1」，按完立即显示剩余座位。两个人同时伸手按，只有一个人的手指先碰到按钮（原子性），另一个人看到「剩余 0」只能离开。绝不可能出现「剩余 0 了还放进来 2 个人」。

### 第三关：MQ 异步下单（拦第三波流量）

**做什么**：

- Redis 扣减成功只代表「抢到名额」，**并不直接创建订单**；
- 系统把「创建订单」的消息发到 MQ，**立即**给前端返回「抢购成功，正在出票」；
- 前端**轮询**查订单状态（比如每 2 秒查一次）；
- 订单服务**按数据库能承受的速度**从 MQ 消费消息，真正在 MySQL 里扣库存、生成订单、落库。

**为什么必须异步**：MySQL 每秒只能扛几千次写操作，而抢到名额的瞬间可能有几千人同时下单。如果同步创建订单，MySQL 又被压垮。放进 MQ 之后，订单服务每秒固定消费 1000 条，数据库稳稳当当，哪怕瞬间积压 1 万条，也只是「排队等一会儿」，不会崩。

**比喻**：抢到名额的人不是立刻冲进仓库搬货，而是先领一张「提货单」（MQ 消息），仓库工作人员按提货单慢慢备货（消费消息），备好货通知你来取（前端轮询查结果）。仓库不会因为 10 万人同时冲进来而瘫痪。

### 三关对比表（背这个）

| 关卡 | 位置 | 拦什么 | 手段 | 效果 |
|---|---|---|---|---|
| 第一关 | 前端 + 网关 | 无效/恶意流量 | 动静分离、验证码错峰、限流、鉴权 | 10 万 → 1 万 |
| 第二关 | Redis | 抢不到名额的请求 | Lua 原子预扣库存 | 1 万 → 10 |
| 第三关 | MQ + 订单服务 | 瞬时写库压力 | 异步消费、削峰填谷 | 10 个订单稳稳落库 |

### 面试怎么答
先亮出总纲：「秒杀设计的核心思想是**层层漏斗**，10 万人抢 10 台手机，重点是让流量逐层衰减」。然后按三关讲：「第一关前端和网关做动静分离、验证码错峰、限流鉴权，把一毫秒的尖峰打散成几秒的平缓流量；第二关 Redis 用 Lua 脚本原子预扣库存，库存为 0 直接返回已售罄，把并发砍到只剩库存数量；第三关扣减成功只发 MQ 消息，订单服务异步消费、MySQL 落库，前端轮询查结果」。最后补一句：「三层任何一层单扛都扛不住，组合起来才能既快又准」。

## 6. 面试怎么答的总结：完整作答主线

### 一句话回答
「**动静分离和验证码拦第一波 → Redis Lua 脚本原子预扣减拦第二波 → MQ 排队削峰 → MySQL 落地**」——这就是秒杀系统设计的完整答题主线。

### 展开讲：四步作答模板

**第一步：动静分离和验证码拦第一波**

「静态资源放 CDN，动态请求进网关；秒杀按钮置灰、限制点击频率；要求输入验证码，把一毫秒的点击尖峰物理打散成几秒钟的平缓流量；网关做 IP 限流和黑名单，Token 校验非法请求。」

**第二步：Redis Lua 脚本原子预扣减拦第二波**

「活动开始前把库存预热到 Redis；请求到来用 Lua 脚本原子执行『查库存 + 扣库存』，避免『查一下再减 1』的超卖问题；库存为 0 后所有请求直接返回已售罄，不再穿透到数据库。」

**第三步：MQ 排队削峰**

「Redis 扣减成功只发一条消息到 MQ，立即给前端返回抢购成功；前端轮询查订单状态；订单服务按数据库能承受的速度异步消费消息，把瞬时洪峰变成平缓的队列。」

**第四步：MySQL 落地**

「订单服务消费消息时用乐观锁 `UPDATE ... WHERE stock > 0` 扣减数据库库存，用唯一订单号保证幂等、防止重复下单；最后定时任务对账，Redis 库存、数据库扣减、订单三者一致，不一致走补偿逻辑。」

### 比喻：快递分拣中心

「层层漏斗」就像快递分拣中心：10 万件包裹同时涌进来（高并发），传送带先把外包装破损的直接剔出去（第一关），扫码机按单号快速分流、重复单号直接拦截（第二关），然后包裹上分拣线慢慢流转，分拣员按自己的节奏处理（第三关），最后每件包裹准确送到对应的货架（MySQL 落库）。分拣中心不会因为双十一包裹暴增而瘫痪，靠的就是一层层分流、一步步消化。

### 面试怎么答（速记版）

- 总纲：「层层漏斗，让流量逐层衰减」；
- 第一波：动静分离 + 验证码错峰 + 限流鉴权；
- 第二波：Redis 预热 + Lua 原子预扣库存，为 0 即返回；
- 第三波：MQ 异步下单 + 前端轮询 + 乐观锁落库 + 幂等防重；
- 兜底：定时对账 + 补偿逻辑，保证最终一致性。

## 本节小结

秒杀系统设计的本质是「用漏斗把流量逐层削掉、用原子操作保证库存准确、用异步把压力摊平」：前端和网关拦第一波（动静分离、验证码错峰、限流鉴权），Redis Lua 脚本原子预扣库存拦第二波（防超卖的关键），MQ 异步消费拦第三波（削峰填谷），最终 MySQL 乐观锁落库并靠对账兜底。面试时按「动静分离和验证码拦第一波 → Redis Lua 原子预扣减拦第二波 → MQ 排队削峰 → MySQL 落地」这条主线作答即可。
