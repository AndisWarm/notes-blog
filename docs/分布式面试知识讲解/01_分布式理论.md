# 01 分布式理论

> 本笔记覆盖：什么是分布式系统、分布式和微服务有什么区别、介绍一下 CAP 理论、怎么理解 BASE 理论

---

## 1. 什么是分布式系统？

### 一句话回答

**分布式系统就是把多台独立的计算机通过网络连接起来，让它们协同工作，一起去完成同一个任务。** 对于用户来说，他感觉不到背后有成百上千台机器，只会觉得自己在用一台超级强大的计算机。

### 展开讲

在单机时代，一台服务器搞定所有事情：接收请求、查数据库、返回结果，全都在这台机器上。但随着用户量变大，单台服务器的 CPU、内存再强也是有天花板的——遇到双十一这种海量流量，单机肯定扛不住。

这时候有两种扩容思路：

- **垂直扩容（Scale Up）**：疯狂升级单台服务器的硬件。比如内存从 16G 升到 64G、128G，CPU 从 8 核换到 32 核。听着简单，但硬件是有物理极限的，而且价格呈指数级上涨，花大钱也只能换来一点点提升。
- **水平扩容（Scale Out）**：多买几台普通机器，把它们通过网络连起来一起干活，这就是分布式系统。每台机器的成本不高，想要更强的能力，就再加几台机器。

我们之所以用分布式系统，主要有两个根本原因：

1. **高并发和高性能**：把压力分散到多台机器上，扛住单机扛不住的海量流量。
2. **高可用（容灾能力）**：单台机器宕机，整个业务就瘫痪了（这叫单点故障）。而在分布式系统里，哪怕有几台机器坏了，只要其他机器还在运转，系统依然能对外提供服务——这叫**部分失效**，不影响全局。

不过，引入分布式并不是百利而无一害的，**它引入了极大的复杂性**，其中最典型的就是**数据一致性问题**。

机器变多了，它们之间只能通过网络沟通，但网络是不稳定的。举个例子：用户下了一笔订单，订单节点记录了「已下单」，然后通过网络告诉库存节点「扣减库存」，结果这时网络卡了，库存节点没收到消息。订单生成了，库存却没扣，数据就不一致了。

为了解决这个问题，就会涉及到分布式事务、分布式锁、以及著名的 CAP 定理等复杂技术，这也是后面几章要讲的内容。

### 比喻

就像开一家饭店。最开始客人少，店里只有一个大厨（单机系统），洗菜、切菜、炒菜他一个人全包了。但后来生意越来越好，一个大厨根本忙不过来（单机遇到性能瓶颈）。这时老板没有去高薪聘请一个三头六臂的神厨（垂直扩容），而是雇了十个普通厨师，有人专门洗菜、有人专门切菜、有人专门炒菜（水平扩容，即分布式）。大家通过大喊或传纸条来配合（网络通信），共同为大堂里的客人上菜。客人根本不在乎后厨是一个人还是十个人，他只在乎菜上得快不快、好不好吃。

### 面试怎么答

1. 先说定义：多台独立计算机通过网络协同完成同一个任务，对用户透明。
2. 说两个动机：高并发高性能（水平扩容）、高可用（容灾，避免单点故障）。
3. 主动补一句「代价」：引入了网络不可靠带来的数据一致性难题，所以才有分布式事务、分布式锁、CAP 这些技术——能说出来说明你真的理解，而不是背定义。

## 2. 分布式和微服务有什么区别？

### 一句话回答

**分布式是一种「物理部署方式」，主要解决单台机器性能扛不住的问题；微服务是一种「软件架构设计思想」，主要解决系统代码堆积太多、难以维护的问题。**

### 展开讲

**分布式系统**是从**物理层面**出发的。当业务流量越来越大，单台服务器的硬件再怎么升级也不起作用时，我们就多买几台机器，把它们连起来一起干活。只要是多台机器通过网络协同工作来完成一个任务，这就是分布式。它追求的是堆更多的机器，来扛住更高的并发、保证一台机器宕机了别的机器还能顶上（高可用）。

**微服务**是从**软件工程和业务逻辑层面**出发的。早期开发习惯把所有功能（订单、用户、支付、积分）全部写在一个庞大的项目里，打包成一个巨大的系统部署。业务简单时没问题，但业务越来越复杂后，几百个程序员改同一份代码，牵一发而动全身，系统变得极其臃肿且难以维护。

微服务就是把巨大的单体应用，按照业务边界拆分成一个个独立的小服务。每个服务只管自己的事，互不干扰，相互之间通过明确的接口（HTTP/RPC）沟通。

这里有一个初学者最容易陷入的误区：**有多个机器在跑，不代表它就是微服务。**

举个反例：把一个什么功能都塞在一起的巨无霸单体项目，原封不动复制 10 份，部署在 10 台服务器上，前面架一个 Nginx 做负载均衡。这叫「分布式系统」（集群部署），因为确实是多台机器在协同工作，但它**绝对不是微服务**——内部依然是一个揉在一起的庞大单体。

反过来，一旦采用微服务架构，拆分成几十上百个独立小服务，一台机器绝对跑不起来这么多服务，通常要部署在成百上千台服务器上。所以**微服务架构天然就是需要用分布式的方式部署的**。

### 比喻

- **分布式**：有 1 万块砖要搬，一个人搬不动，就雇 10 个人一起搬。重点是「人多力量大」。
- **微服务**：一家什么都卖的超级大杂货铺，拆分成专门卖菜的、专门卖肉的、专门卖衣服的独立店铺（订单服务、支付服务等）。重点是「各管各的，边界清晰」。

### 面试怎么答

1. 一句话给出核心区别：分布式是「机器的拆分和协同」（物理层面），微服务是「业务逻辑和业务边界的拆分」（软件工程层面）。
2. 补一个反例证明你真懂：10 份一样的单体部署在 10 台机器上是分布式但不是微服务。
3. 再补一个联系：微服务架构天然需要分布式部署。两者不是竞争关系，而是不同维度。

## 3. 介绍一下 CAP 理论

### 一句话回答

**CAP 定理说的是：在一个分布式系统中，一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者不可得兼，最多只能同时满足两个。**

### 展开讲

CAP 是三个单词的缩写：

- **C（Consistency）一致性**：分布式系统中所有数据备份，在同一时刻是否是同样的值。也就是说，所有节点访问的都是同一份最新的数据副本。用户无论从哪个节点读数据，读到的都应该是最新的、一样的。
- **A（Availability）可用性**：在集群中一部分节点故障后，集群整体是否还能响应客户端的读写请求。也就是说，不管系统内部出了什么岔子，只要请求来了，就必须给出响应（哪怕数据可能不是最新的）。
- **P（Partition tolerance）分区容错性**：系统在遇到网络分区（网络故障导致节点之间互相联系不上）时，依然能继续工作。分布式系统里网络是必然可能出故障的，所以 P 是必须保证的前提。

为什么三者不可得兼？关键在「网络分区」上。

假设集群有两个节点 A 和 B，突然 A 和 B 之间的网络断了（发生分区）。这时来了一个写请求，把数据写到了 A 节点。那么：

- 如果追求**一致性 C**：B 节点没有这份新数据，所以必须拒绝用户的读请求，告诉用户「现在读不了」——但这样就违背了**可用性 A**（请求没有得到响应）。
- 如果追求**可用性 A**：B 节点继续响应读请求，但读到的可能是旧数据——这样就违背了**一致性 C**。

所以在分区发生的那一刻，你必须在 C 和 A 之间二选一，这就是「三者不可得兼」的真正含义。

实际系统中，**P 通常必须选**（网络故障无法避免），所以真正的选择是 **CP**（牺牲可用性保一致性，如 Zookeeper、etcd）还是 **AP**（牺牲强一致性保可用性，如大多数互联网系统、Eureka、Cassandra）。

### 比喻

想象你和一个朋友各拿一本一模一样的账本，约好每天对账。突然有一天你们的电话线断了（网络分区）。这时有个客户来问你「我欠多少钱」，而你的账本恰好是三天前的（朋友的账本上刚记了一笔新账）。

- 选**一致性**：你只能说「稍等，我联系不上我朋友，现在没法确认，不能回答你」——客户得到的是「不可用」。
- 选**可用性**：你按手里的旧账本回答客户——回答倒是快了，但数据可能已经过时，不一致。

### 面试怎么答

1. 先直接说结论：C、A、P 三者不可得兼，最多满足两个。
2. 分别解释三个概念，注意 P 的定义要说清「网络分区」这个前提。
3. 用「分区发生的那一刻必须二选一」的逻辑推演，证明不是背概念。
4. 最后落到实际：P 必选，所以业界只有 CP（如 Zookeeper）和 AP（如大多数高并发系统）两种路线。

## 4. 怎么理解 BASE 理论？

### 一句话回答

**BASE 理论是对 CAP 中「一致性」的一种务实妥协：既然强一致性太难做到，那就允许数据短时间内不一致，只要保证最终结果是对的，以此换取系统极高的可用性。**

### 展开讲

先回顾一下背景：CAP 定理说一致性、可用性不可兼得。如果我们死磕强一致性，要求所有机器上的数据每时每刻都必须一模一样，那系统在同步数据时稍微遇到点网络波动，可能就得暂停服务（拒绝请求），可用性就大大降低了。

于是前人提出了 BASE 理论，它是三个英文短语的缩写：

**第一个是 Basically Available（基本可用）**：系统遇到故障或流量洪峰时，允许损失一部分可用性，保住核心业务正常运转。

典型的做法是**服务降级**和**响应变慢**。比如双十一零点，大家集中冲进去买东西，服务器压力巨大，电商平台可能把「查看商品历史评价」「申请退款」这类非核心功能暂时停掉，或者页面加载比平时慢一两秒。虽然体验打了折扣，但用户依然能完成最核心的「下单付款」，系统没有直接崩溃。

**第二个是 Soft State（软状态）**：传统数据库里，数据要么是成功、要么是失败，这叫「硬状态」。而分布式系统里，机器之间同步数据通过网络、有延迟，所以我们允许数据存在一种「中间状态」，而且这种中间状态不影响系统基本可用。

比如银行 APP 跨行转账：钱扣了，但对方还没收到，这时候就处于「转账处理中」的软状态。

**第三个是 Eventually Consistent（最终一致性），这是整个理论的灵魂**：既然允许了中间状态的存在，系统总不能一直错下去吧？最终一致性保证：不管中间因为网络延迟或重试折腾了多久，经过一段时间后，所有节点的数据最终一定会达到完全一致的正确状态。

还是转账的例子：不用要求点完确定的一瞬间对方立刻收到钱（那是强一致性），只要银行系统内部不断重试和对账，承诺「2 小时内一定到账」，最后钱实实在在打进对方账户，就满足了最终一致性。

### 比喻

想象你和朋友一起维护一份共享文档，你们各自有副本。如果要求「强一致性」，你们每敲一个字都必须实时同步，网络一卡就都得停摆等对方。

BASE 的做法是：先各自干活（基本可用），允许你改你的、我改我的、内容暂时不一样（软状态），但每天晚上系统自动合并同步一次，第二天早上大家的文档完全一致（最终一致性）。

### 面试怎么答

1. 一句话定性：BASE 是对强一致性的降级妥协，用「短暂不一致」换「高可用高性能」。
2. 拆开讲三个字母：基本可用（服务降级）、软状态（中间状态）、最终一致性（灵魂）。
3. 强调适用范围：除了支付结账这种极少数对钱要求强的场景，绝大部分互联网高并发架构（比如消息队列异步处理）践行的都是 BASE。
4. 如果能补一句「BASE 是 AP 路线的具体实现思想」，跟 CAP 串联起来，会非常加分。

## 本章小结（背诵卡片）

| 问题 | 一句话答案 |
|------|-----------|
| 什么是分布式系统 | 多台独立计算机通过网络协同完成任务，对用户透明；为了高并发高性能和高可用，代价是数据一致性难题 |
| 分布式 vs 微服务 | 分布式是物理部署方式（机器的拆分），微服务是软件架构思想（业务的拆分）；多个机器跑不一定微服务 |
| CAP 理论 | C（一致性）、A（可用性）、P（分区容错性）三者不可得兼；P 必选，实际是 CP vs AP 之争 |
| BASE 理论 | 对强一致性的妥协：基本可用 + 软状态 + 最终一致性，用短暂不一致换高可用 |
