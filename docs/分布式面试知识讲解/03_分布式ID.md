# 03 分布式 ID

> 本笔记覆盖：什么情况需要用分布式 ID、分布式 ID 有什么方案（UUID / 数据库号段 / Redis / 雪花算法）

---

## 0. 先搞懂：为什么单体时代不需要分布式 ID？

单体架构时代，比如存个订单，直接依托 MySQL 单表主键的**自增属性**（从 1、2、3 这样往上加）就完美搞定了：既不重复，插入性能又好（主键递增，B+ 树往末尾追加，不用在中间挪数据）。

但分布式 ID 要解决的核心痛点，就是在「**多节点、多数据库环境下，如何生成一个全局唯一且最好是有序的标识**」。

---

## 1. 什么情况需要用分布式 ID？

### 一句话回答

**当遇到数据库分库分表、微服务高并发多节点写入、多系统数据合并这三种情况时，单机的自增主键或 UUID 都玩不转了，就必须引入分布式 ID。**

### 展开讲

#### 第一种情况（最绝对的刚需）：数据库分库分表

假设单聊订单业务，每天产生几百万订单，单张 MySQL 表装不下、也扛不住并发，必须把这单表拆成 10 张甚至 100 张表（分散在多个库里）。

一旦拆表，原来最省事的「数据库自增主键」就立刻失效了。为什么呢？因为**各个子表之间互相不知道对方的状态**：

- 表 A 自己从 1 开始递增，刚刚生成了 ID 为「1」的订单；
- 表 B 也在运行，也从 1 开始，也生成了 ID 为「1」的订单。

两个库都生成了 ID=1 的订单，这时候你想查这条订单，系统就彻底懵了——查哪张表？查出来是哪条？

所以在分库分表场景下，必须把「生成 ID 的权力」剥离出来，找一个**凌驾于所有子表之上**的独立系统或算法来充当**发号器**，保证它发出来的 ID 绝对不会重复。这就必须用分布式 ID 了。

#### 第二种情况：高并发微服务多节点，对写入性能要求极高

你可能有个疑问：既然多台机器容易生成同样的 ID，那我在本地自己生成一个永远不重复的 UUID 不就行了吗？

UUID 确实全球唯一，但在实际工程里（特别是 Java + MySQL 架构），**极不推荐用 UUID 做核心表的主键**。原因有二：

1. **存储空间大**：UUID 是一串 32 位的乱码字符串（实际存储约 36 个字符含连字符），做主键占空间很大（尤其作为聚簇索引时，会被复制到每个二级索引里）。
2. **无序导致页分裂**：MySQL 底层用 B+ 树索引，它最喜欢「趋势递增」的数据，这样能按顺序往后排。而 UUID 杂乱无章，每次插入新数据，数据库可能都要在 B+ 树索引的**中间**硬塞进去，引发非常影响性能的「**页分裂**」现象——一个数据页满了还要拆成两页，导致写入极慢、空间碎片化。

所以我们需要一种**既能在成百上千台机器并发时绝不碰撞（唯一），又能在进数据库时不乱插队、大致保持递增趋势**的 ID 方案——这就必须用到雪花算法一类的技术。

#### 第三种情况：多系统打通合并数据

比如公司收购了一个竞品，或者要把原来独立的 A 系统和 B 系统的数据汇总到数据仓库里做报表。如果当初它们各自用的是自己库里的自增 ID，这两套数据一相遇，ID 必定大量重叠冲突，合并起来简直是灾难。

这也是为什么大厂在设计之初，只要涉及核心业务对象，一律采用全局唯一的分布式 ID。

### 比喻

想象一家电影院，很多个放映厅（多个数据库）。每个厅自己按「1、2、3」给座位编号（自增主键），厅之间互不商量。当你想把几个厅的票务数据合并统计时，发现每个厅都有「3 号座」，根本分不清是哪一场的。

于是电影院干脆成立一个总票务中心（发号器/分布式 ID 系统），所有放映厅的座位号都从总票务中心领取——每张票在全影院范围内唯一，不会再撞号。

### 面试怎么答

1. 先给结论：分库分表、微服务高并发写入、多系统数据合并，三种场景必须用。
2. 核心讲第一种：分库分表后各子表自增 ID 互相不知道对方状态，必然撞号，需要一个凌驾于所有表之上的发号器。
3. 第二种顺带把 UUID 的问题讲清楚：全局唯一但不递增 → B+ 树页分裂 → 写入慢、占空间大。这一条是很多面试官真正想考察的点。
4. 收尾提一句趋势递增的价值：满足 MySQL 索引的有序插入，性能和唯一性兼得。

## 2. 分布式 ID 有什么方案？

### 一句话回答

**主流的四种方案是：UUID（简单但无序、占空间）、数据库号段模式（性能好、稳定，中小公司首选）、Redis 自增（快但重度依赖 Redis）、雪花算法（高并发首选，本地纯计算，但要防时钟回拨）。**

### 展开讲

#### 方案一：UUID

代码本地一行就能生成，也确实保证全球唯一。但在基于 MySQL 存储的业务中（尤其是核心表），**几乎极少用 UUID 当主键**：

- **占空间大**：32 位乱码字符串（实际约 36 字符含连字符），存储成本高；
- **完全无序**：B+ 树索引最喜欢趋势递增的数据，UUID 乱序插入会引发「页分裂」，写入性能极差。

所以 UUID 只适合日志跟踪、非核心表之类的场景，不适合做主键。

#### 方案二：数据库号段模式

既然 UUID 不递增，那用数据库专门做个「发号器」拿自增 ID 好了。但有个问题：每次生成一个 ID 都要查一次数据库，并发一高数据库就被压垮了。

于是大家把它优化成了**号段模式**——就像去批发市场进货：

- 业务节点不再每次向数据库要「1 个」ID，而是一次性申请「1000 个」ID（一个号段，比如 1001~2000）；
- 拿到本地内存里缓存起来，慢慢分配给业务，发完了再找数据库要下一个号段。

好处：

- **性能大幅提升**：1000 次 ID 分配才打 1 次数据库；
- **稳定**：就算数据库短暂宕机，系统靠本地库存还能顶住一段时间的业务。

美团的 Leaf 组件里就有这种模式的身影。

**发号表长什么样？（核心格式）**

美团 Leaf 的号段表 `leaf_alloc` 是这个模式的经典模板：

```sql
CREATE TABLE `leaf_alloc` (
  `biz_tag`     varchar(128) NOT NULL DEFAULT '',   -- 业务标识：order / user / coupon…
  `max_id`      bigint(20)  NOT NULL DEFAULT '1',   -- 当前已分配到的最大 ID
  `step`        int(11)     NOT NULL,               -- 步长：每次领多少个号（如 1000）
  `description` varchar(256) DEFAULT NULL,          -- 业务描述
  `update_time` timestamp   NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`biz_tag`)
) ENGINE=InnoDB;
```

三个关键设计点：

- **主键是 `biz_tag` 而不是自增 id**：一张表服务多个业务，每个业务一行，互不干扰；
- **表里只有「账本」**：只记「发到哪了」（max_id），号本身不存在库里；
- `max_id` 是共享的，靠**行锁 + 原子 UPDATE** 保证并发安全——这是整个模式并发不出错的根基。

**取号就一条 SQL：**

```sql
UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = 'order';
```

意思是「把 order 业务的额度往后推 step 步（如 1000），这 1000 个号归我」。InnoDB 按主键 `biz_tag` 加**行锁**，多个线程同时来也只会串行执行，不会撞号。

**号段怎么算：** UPDATE 之后读回新的 `max_id`，本次号段就是 `[新max_id - step + 1, 新max_id]`：

| 步骤 | 值 |
| --- | --- |
| 执行前 max_id | 1000 |
| UPDATE 后 max_id | 2000 |
| 本次领取的号段 | [1001, 2000] |

> 注意：读回新值必须和 UPDATE 合并成**一次原子操作**，否则两个线程可能算出同一段号。MySQL 的实现技巧是 `UPDATE ... SET max_id = LAST_INSERT_ID(max_id + step)`——把新值记在当前连接里，随后的 `SELECT LAST_INSERT_ID()` 取回的一定是「我自己」推进后的值（PostgreSQL/SQL Server 用 `UPDATE ... RETURNING` 一步到位）。

**为什么性能好（对比「每次查一次库」）：**

| 方案 | 发 1000 个 ID | 数据库操作次数 |
| --- | --- | --- |
| 朴素方案 | 要 1 个 ID 查 1 次库 | 1000 次 |
| 号段模式 | 1 次领号段（UPDATE + SELECT） | 1 次 |

差**三个数量级（约 1000 倍）**：内存取号是纳秒级，数据库往返是毫秒级。号段模式把 999 次昂贵的数据库操作换成了几乎免费的本地内存操作。

#### 方案二进阶：单 buffer 与双 buffer（Leaf 的实现细节）

buffer = 号段缓存在内存里的容器，里面装「上界 maxId、当前发到 current、步长 step」。取号就是 `current + 1`，纯内存——**只要 buffer 还有号，就不碰数据库**。两种实现的差别，只在回答一个问题：**「下一次去领号段，什么时候出发？」**

**单 buffer：用完再取**

```
领段 [1001, 2000] → 内存发号 1001...2000 → buffer 空了 → 同步去数据库领下一段 → 继续发
```

- 缺点：**取号毛刺**。发到 2000 的瞬间，业务正好要号，但 buffer 空了，只能干等这次数据库往返（约 1ms）。低并发无所谓；高并发下每秒有多次空窗，每次空窗积压的请求全卡在数据库上——延迟尖刺 + 数据库瞬间打满。
- 适用：QPS 低、对延迟不敏感的小系统。

**双 buffer：快用完就预取**

准备**两个** buffer，一个在发、一个在备：

1. 当前 buffer 用到 **10%**（Leaf 默认阈值）→ 立刻**异步**派线程去数据库领下一段，填进备用 buffer；
2. 当前段发完 → **无缝切换**到已备好的那段（切换只是改一个下标标识，原子操作，取号线程不会拿到空段）；
3. 原 buffer 变成新的备用位，循环往复。

```
buffer[0] = [1001, 2000] 发号中 → 用到 10%（发到 1090）→ 异步预取 [2001, 3000] 填 buffer[1]
buffer[0] 发完 → 切换 buffer[1] 开始发 → buffer[0] 变备用位 → 循环
```

- 效果：**取号路径上永远只有内存操作**，数据库延迟被「藏」在后台，毛刺基本消失；
- 阈值为什么是 10%：预取要留足提前量（取下一段约 1ms，10% = 100 个号，只要 1ms 内消耗不到 100 个号就能从容完成）；太高会来不及、太低会频繁打库；
- 预取失败怎么办：当前段用完且备用段没准备好时，**退化成同步取号**（即单 buffer 行为）——双 buffer 是尽力优化，靠重试把这种情况压到极低；
- 注意：双 buffer **没有减少数据库总次数**（仍是每 1000 号打 1 次库），它优化的是**时机**——把延迟从取号路径上摘出去。

**单 vs 双对比：**

| 对比项 | 单 buffer | 双 buffer |
| --- | --- | --- |
| 取号时机 | 段用完才取 | 用到 10% 异步预取 |
| 取号毛刺 | 有（空窗期同步等数据库） | 基本无（永远有备用段） |
| 数据库请求 | 同步，阻塞取号 | 异步，后台完成 |
| 实现复杂度 | 低 | 中（双段 + 切换 + 异步线程池） |
| 内存 | 1 个段 | 2 个段（翻倍） |
| 数据库压力 | 一样（每 1000 号一次） | 一样（预取只改时机不改次数） |
| 适用 | 低 QPS、延迟不敏感 | 高并发、核心链路 |

> 类比：单 buffer = 米缸只有一格，吃完了才去买米，买米那会儿家里没米做饭（毛刺）；双 buffer = 两个米缸，一个在吃、吃到还剩 10% 就派人把另一个装满，吃完无缝切换——家里从来不断米。

#### 方案三：基于 Redis 生成

利用 Redis 的 `INCR` 指令（单线程原子操作，加 1 返回结果）来计数发号。

好处：

- **快**：全内存操作，比查数据库快非常多；
- **纯数字、绝对递增**：满足索引有序性。

硬伤：

- **重度依赖 Redis**：为了生成 ID 专门维护一套能抗住极高并发、且数据严格持久化不丢失的 Redis 集群，运维成本和网络开销都不低；
- Redis 挂了或丢数据，ID 就断了或可能重复。

#### 方案四：雪花算法（Snowflake）—— 高并发场景最主流

前面几种方案（查数据库、查 Redis）都要走一趟**网络请求**。雪花算法的巧妙之处在于：**完全不需要依赖外部服务，在机器本地纯计算生成 ID**。

它的核心思想是拼凑出一个 64 位的长整型数字，按二进制位切分成几段：

| 段 | 位数 | 存什么 |
|----|------|--------|
| 符号位 | 1 位 | 固定为 0 |
| 时间戳 | 41 位 | 当前系统时间（毫秒级） |
| 机器号 | 10 位 | 这台机器的唯一标识（可再分机房/机器） |
| 序列号 | 12 位 | 同一毫秒内的自增流水号（2^12 = 4096 个） |

这样设计极其精妙：

1. **递增**：开头存的是时间戳，随着时间推移，生成的 ID 肯定一直变大，完美迎合 MySQL 对递增的需求；
2. **不重复**：中间存机器号，全网所有机器各管各的序列号，绝对不会重复；
3. **性能极高**：本地纯计算，不走网络，单机每毫秒可生成 4096 个 ID。

但它有一个公认的软肋——**时钟回拨**：因为严重依赖机器当前时间，万一某台机器的时间被系统往回调了几毫秒（比如 NTP 校时），生成的 ID 就可能跟刚才的重复。实际应用中需要用特殊的时间校验代码来防范（比如记录上次生成 ID 的时间，发现时钟回拨就等待或拒绝生成）。

#### 四种方案对比

| 方案 | 唯一性 | 趋势递增 | 性能 | 复杂度 | 适用场景 |
|------|--------|---------|------|--------|---------|
| UUID | 强 | 无（无序） | 高（本地生成） | 极低 | 日志、非核心表 |
| 数据库号段 | 强 | 递增 | 中高（批量取号） | 低 | 中小公司通用方案 |
| Redis 自增 | 强 | 绝对递增 | 高 | 中 | 能接受依赖 Redis 的场景 |
| 雪花算法 | 强 | 趋势递增 | 极高（本地计算） | 中（要防时钟回拨） | 大厂/核心系统高并发 |

### 比喻

四种方案就像是四种发号方式：

- **UUID**：每个人自己随便编一个全世界唯一的乱码编号——简单，但编号又长又没规律，图书馆（数据库）整理起来（B+ 树排序）特别费劲；
- **号段模式**：小卖部不再每次去批发市场进 1 瓶水，而是一次进 1000 瓶存在仓库（本地内存）里慢慢卖——进货次数少了，效率高了；
- **Redis 自增**：雇一个算数极快的会计（Redis），谁要号他就当场加一报出来——快是快，但这个会计工资（运维成本）很高，而且他不能请假（宕机）；
- **雪花算法**：每个柜台自己配一个智能时钟（时间戳）+ 专属柜台号（机器号）+ 计数器（序列号），组合起来就是全球唯一递增的号码——不用找任何人，自己就能发号，但要小心时钟不准（时钟回拨）。

### 面试怎么答

1. 按顺序讲四种方案，每种「一句话说原理 + 一个缺点」：UUID 无序占空间 → 号段模式批量取号省数据库压力 → Redis 快但依赖重 → 雪花本地纯计算性能最高。
2. 雪花算法要展开讲 64 位结构（时间戳 41 位 + 机器号 10 位 + 序列号 12 位），这是高频考点，最好能画出分段表。
3. 主动提「时钟回拨」问题及应对思路——这是面试官最常追问的深水区。
4. 给出选型结论：普通公司用数据库号段（美团 Leaf 的 segment 模式），大厂核心系统用雪花（或直接上百度 UidGenerator、美团 Leaf-snowflake 等开源封装）。

## 本章小结（背诵卡片）

| 问题 | 一句话答案 |
|------|-----------|
| 什么时候用分布式 ID | 分库分表（各子表自增撞号）、微服务高并发写入（UUID 页分裂）、多系统数据合并 |
| UUID | 本地生成、全球唯一，但无序+占空间 → B+ 树页分裂，只适合日志场景 |
| 数据库号段 | 一次申请一批 ID（如 1000 个）缓存本地慢慢发，性能高、稳定，中小公司首选；表 = biz_tag + max_id + step，取号 = 一条原子 UPDATE 推进 step |
| 单/双 buffer | 单 buffer 用完再取、有毛刺；双 buffer 用到 10% 异步预取备用段、无缝切换，取号无毛刺（数据库次数不变） |
| Redis 自增 | INCR 原子加 1，快且绝对递增，但重度依赖 Redis 集群（运维成本、丢数据风险） |
| 雪花算法 | 64 位 = 时间戳(41) + 机器号(10) + 序列号(12)，本地纯计算、趋势递增、性能极高；软肋是时钟回拨 |
| 选型结论 | 普通公司：号段模式；大厂核心系统：雪花算法（或用开源框架 Leaf / UidGenerator） |
