# 02 分布式锁

> 本笔记覆盖：用 Redis 怎么实现分布式锁、还有没有其他方法实现分布式锁（Zookeeper）、怎么选型

---

## 0. 先搞懂：什么是分布式锁？

### 一句话回答

**分布式锁是用于分布式环境下并发控制的一种机制，用来控制某个资源在同一时刻只能被一个应用（或一个客户端）使用。**

### 展开讲

单机时代，多个线程抢同一个资源，我们用 `synchronized`、`ReentrantLock` 这类**本地锁**就够了——因为所有线程都在同一台机器的同一个 JVM 里，锁的状态放在内存里大家都能看到。

但分布式环境下，多个应用实例部署在不同的机器上，各自有各自的 JVM 和内存。A 机器上的线程加了个锁，B 机器上的线程根本看不见，本地锁就失效了。这时候我们需要一个**所有机器都能访问到的共享存储**来放锁。

Redis 就是最常用的选择：它本身可以被多个客户端共享访问，正好是一个共享存储系统；而且读写性能极高，能应对高并发的锁操作。

### 比喻

本地锁就像教室里的黑板锁——只有一个教室，一把锁就够了。分布式锁就像整栋教学楼的共享储物柜——每个教室的学生都要用，就必须有一个大家都能看到、共用的锁，放在楼道里（共享存储），而不是各自教室里。

## 1. 用 Redis 怎么实现分布式锁？

### 一句话回答

**利用 Redis 的 `SET` 命令加上 `NX` 参数（key 不存在才设置成功）实现加锁，配合过期时间防止死锁；用 Lua 脚本实现「先校验再删除」的原子解锁，防止误删别人的锁。**

### 展开讲

#### 第一步：加锁，必须满足三个条件

`SET` 命令的 `NX` 参数可以实现「key 不存在才插入」，所以可以用它来实现分布式锁：

- 如果 key 不存在，则插入成功 → **加锁成功**；
- 如果 key 存在，则插入失败 → **加锁失败**。

但只用 `NX` 还不够，一个正确的加锁操作必须同时满足三个条件：

1. **原子性**：加锁包含「读取锁变量、检查锁变量值、设置锁变量值」三个操作，必须作为一个原子操作完成。如果分开执行，两个客户端可能同时读到「锁不存在」，然后都设置成功——锁就失效了。所以要用一条 `SET` 命令带上 `NX` 选项一次完成。
2. **过期时间**：锁变量必须设置过期时间。否则客户端拿到锁后突然宕机/发生异常，锁永远释放不了，其他客户端就永远拿不到锁（死锁）。所以 `SET` 时要加上 `EX`/`PX` 选项。
3. **唯一标识**：锁变量的值必须能区分来自不同客户端的加锁操作。否则释放锁时可能出现「A 的锁被 B 删了」的误释放。

满足这三个条件的命令如下：

```bash
SET lock_key unique_value NX PX 10000
```

- `lock_key`：锁的名字（key 键）；
- `unique_value`：客户端生成的唯一标识（比如 UUID），区分不同客户端的锁操作；
- `NX`：只在 `lock_key` 不存在时才设置——保证只有一个人能加上锁；
- `PX 10000`：设置过期时间为 10 秒——防止客户端异常后锁永远不释放。

#### 第二步：解锁，必须用 Lua 脚本保证原子性

解锁的过程就是删除 `lock_key`。但**不能乱删**：要保证执行删除的客户端就是当初加锁的客户端。所以解锁前要先判断锁的值 `unique_value` 是不是自己的，是才删。

这样一来，解锁就包含了「判断 + 删除」两个操作。两个操作分开执行有个致命问题：万一刚判断完「是我的锁」，还没来得及删，锁就过期了，然后另一个客户端 B 加锁成功……这时候如果 A 继续执行删除，就把 B 的锁删掉了（误释放）。

所以解锁必须用 Lua 脚本，把「判断 + 删除」写成一段脚本，Redis 执行 Lua 脚本时是**原子**的（中间不会插入其他命令）：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

这段脚本的意思是：如果锁的值等于自己的 `unique_value`，就删除；否则什么都不做。整个判断和删除一气呵成，不可能被中途打断。

至此，我们就通过 `SET` 命令 + Lua 脚本，在 Redis 单节点上完成了分布式锁的加锁和解锁。

#### 为什么是 Lua？其他脚本语言不行吗？

**不是「必须用 Lua」，而是「Redis 只内嵌了 Lua 这一种脚本引擎」，并且脚本必须在 Redis 服务端原子执行才能解决竞态。**

1. **Redis 服务端只内嵌 Lua。** Redis 内部只有 Lua 解释器，没有 Python / JavaScript / Ruby 等运行时。把其他语言的代码发给 Redis，它根本没有执行环境。所以不是「别的语言写不了逻辑」，而是「Redis 不认别的语言」。

2. **原子性来自「在服务端内执行」，不是来自「脚本」本身。** 如果在应用层用 Python/Go/Java 写一个「函数」，内部发多条 Redis 命令，那它仍然只是多条独立命令，不具备原子性——这正是要规避的竞态来源。真正的原子性来源是：脚本被 `EVAL`/`EVALSHA` 送进 Redis，由 Redis 单线程一口气执行完，中间不被其他命令打断。

所以 Lua 是 Redis 提供的唯一「服务端原子脚本」入口，不是因为 Lua 这门语言多特殊。

两个补充：

- **加锁其实可以不用 Lua。** `SET key token NX PX` 本身就是一条原子命令（Redis 2.6.12+ 原生支持），Lua 主要用于**解锁**和**续期**。
- **Redis 7 之后有 Redis Functions**，本质仍是 Lua，但把脚本管理、版本化做得更规范，推荐替代裸 `EVAL`。也可以直接换 etcd / ZooKeeper 这类自带 CAS（比较并删除）原生命令的方案。

#### 完整流程细化：续期、单实例局限、Redlock

**续期（看门狗）。** 如果临界区执行时间可能超过锁的过期时间，需要用后台线程在锁过期前不断刷新过期时间，否则会出现「业务还没跑完锁就过期，别人抢到锁，自己业务结束后误删别人的锁」。续期也要带上「确认锁还是我的」的判断（通常还是用 Lua），否则会把别人的锁给续了。Java 的 Redisson 客户端就自带这种「看门狗」续期机制。

**单实例的局限。** 上面的流程都是单机 Redis。致命弱点：主节点刚写入锁就宕机、还没同步到从节点，从节点提升为主后锁就丢了，可能出现两个客户端同时持锁。

**Redlock 算法（多实例）。** 高可用场景下 Redis 官方提出 Redlock：用 N 个（通常 5 个）互相独立的 Redis 实例（不是主从集群），客户端依次向所有节点 `SET NX PX` 加锁，只有当大多数节点（≥ N/2+1）加锁成功、且总耗时小于锁的过期时间，才算加锁成功；解锁时向所有节点发送 Lua 解锁脚本。

> 注意：Redlock 有争议（时钟跳跃、GC 停顿等场景下仍可能失效）。业务需要强一致性保证时，优先考虑 etcd / ZooKeeper 这类基于共识协议、自带 CAS 的方案，而不是 Redis。

### 比喻

加锁就像在储物柜上贴一张写着你名字的便签（`unique_value`）：

- **`SET ... NX`**：便签只有在柜子上没有其他便签时才能贴上（原子操作，不会两个人同时贴上）；
- **`PX 10000`**：便签有保质期，10 秒后自动风化消失。万一你贴完便签人就跑了（宕机），柜子也不会永远被占着；
- **解锁用 Lua 脚本**：撕便签前先看一眼是不是你的名字——如果是别人的名字（说明你的便签已经过期，别人已经占了柜子），绝不乱撕。

### 面试怎么答

1. 先亮结论：`SET key value NX PX 过期时间` 加锁 + Lua 脚本解锁。
2. 讲加锁三个要点：原子性（NX 一条命令完成检查+设置）、防死锁（过期时间）、防误删（唯一 value）。
3. 讲解锁要点：为什么用 Lua 脚本——判断和删除必须原子，防止「判断完还没删，锁过期被别人拿到，然后误删别人的锁」。
4. 主动提一句局限性：单节点 Redis 会有主从切换导致锁丢失的风险（Redis 同步是异步的，master 挂了还没同步到 slave，锁就丢了），引出 RedLock 或 Zookeeper——能说到这层，面试官会认为你是真用过。

## 2. 还有没有其他方法实现分布式锁？（Zookeeper）

### 一句话回答

**可以基于 Zookeeper 的「临时顺序节点 + Watcher 监听机制」实现：所有客户端在 `/locks` 下创建临时顺序节点，只有序号最小的节点能拿到锁，其余节点监听前一个节点，前一个释放后自己上位。**

### 展开讲

#### 先了解 Zookeeper 的两个关键特性

Zookeeper 是一个为分布式应用提供一致性服务的软件，内部是一个分层的文件系统目录树结构，规定同一个目录下只能有一个唯一文件名。它的数据模型有四种节点：

| 节点类型 | 特点 |
|---------|------|
| 持久节点 | 创建后不会因为会话失效而消失 |
| 临时节点 | 客户端连接失效（会话结束），节点立即被删除 |
| 顺序节点 | 创建时 ZK 自动在节点名后加一个数字后缀，并且是有序的（如 `seq-0000000000`、`seq-0000000001`） |
| 临时顺序节点 | 上面两者的结合：会话结束自动删除，名字带递增序号 |

还有一个**监视器（Watcher）**机制：创建节点时可以注册对该节点的监视器，当节点状态发生改变时，ZK 会向客户端发送**且仅发送一条**通知（watch 只能被触发一次）。

#### 利用这两个特性实现分布式锁

1. 首先创建一个持久节点 `/locks`，作为锁的根目录。不同的使用场景可以建不同的路径，互不干扰。
2. 请求进来时，所有客户端都在 `/locks` 下创建**临时顺序节点**。假设三个客户端同时抢锁，会看到 `/locks` 下面有 `seq-0000000000`、`seq-0000000001`、`seq-0000000002` 三个节点。
3. 每个客户端判断自己创建的节点是不是 `/locks` 路径下**序号最小的**：
   - 是 → **获取锁成功**，开始处理业务；
   - 否 → 阻塞线程，同时注册一个 Watcher，**监听前一个节点**（序号比自己小 1 的那个）。
4. 获取到锁的客户端处理完业务，`delete` 自己的节点，表示释放锁。
5. 前一个节点被删除，触发后一个节点的 Watcher，唤醒线程，后一个客户端重复第 3 步的判断——此时它已经是序号最小的了，成功上位获取锁。

整个过程就像一个**排队机制**：按序号从小到大依次获取锁，前一个人走了，下一个人自动补上。这种实现方式叫「公平锁」——先来的人（序号小的）一定先拿到锁。

#### Redis 和 Zookeeper 怎么选？

Zookeeper 实现的分布式锁是**强一致性**的，因为底层用的 ZAB 协议（原子广播协议）天然满足 CP（对照第一章的 CAP 理论）。但强一致性意味着性能的下降——每步操作都要经过节点间的同步确认。

所以选型建议是：

- **如果项目没有强依赖 ZK**，用 Redis 就好。因为 Redis 用途很广，大部分项目都引用了，没必要为了一把锁再引入一个新组件（多一个组件就多一份运维成本）；
- 如果业务场景**无法忍受 Redis 异步同步数据导致的锁丢失**，再考虑 ZK；或者在业务层做兜底处理。

一句话总结：**Redis 和 Zookeeper 的选择，本质上是性能和一致性的取舍**——Redis 快但可能丢锁（AP 路线），ZK 强一致但慢（CP 路线）。

### 比喻

想象银行柜台取号：所有人都取一个号（临时顺序节点），柜员只叫当前最小的号。没叫到你时，你就坐在椅子上等着（阻塞），并且竖着耳朵听前一个号办完（Watcher 监听前一个节点）。前一个号办完了（节点删除），广播叫下一个号，你听到后一看——到自己了，去办业务。

排队是公平的：先取号的人先办。而且如果你中途离开了（客户端宕机），你的号自动作废（临时节点随会话消失），不会卡住后面的人——这是临时节点比 Redis 过期时间更优雅的地方，因为**节点消失是 ZK 主动推送的**，不用等过期时间到了才释放。

### 面试怎么答

1. 先介绍 ZK 的两个特性：临时顺序节点（会话结束自动删除 + 递增序号）、Watcher（一次性通知）。
2. 讲清四步流程：创建临时顺序节点 → 判断自己是否最小 → 不是则监听前一个节点并阻塞 → 前一个删除后自己被唤醒拿锁。
3. 提一句「公平锁」的性质，以及临时节点天然解决「客户端宕机锁不释放」的问题。
4. 对比选型：ZK 强一致（ZAB 协议、CP）但性能低；Redis 性能高但可能丢锁（AP）。没强依赖 ZK 就用 Redis。
5. 如果面试官追问，可以补：Redisson 封装了 Redis 锁的看门狗续期机制；ZK 方案用 Curator 的 InterProcessMutex——说明你了解工业级实践。
