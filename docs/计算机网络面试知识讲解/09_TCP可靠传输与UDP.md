# 09 TCP 可靠传输与 UDP

> 面试问法：TCP vs UDP / TCP 为什么可靠 / 怎么用 UDP 实现 HTTP / 粘包 / 拥塞控制。
> 共 5 题，拥塞控制四算法是本章重头戏。

## Q1 TCP 和 UDP 区别是什么？

### 一句话答案

**TCP 面向连接、可靠、有流量/拥塞控制、首部大（20+ 字节）、一对一、流式；UDP 无连接、不可靠、无控制、首部小（8 字节）、支持多对多、报文式**。

### 大白话讲解

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接，传数据前先建连接 | 无连接，即刻传输 |
| 服务对象 | 一对一（一条连接只有两个端点） | 一对一、一对多、多对多 |
| 可靠性 | 可靠交付：无差错、不丢失、不重复、按序到达 | 不可靠，丢了就丢了；可基于它做可靠协议（如 QUIC） |
| 拥塞/流量控制 | 都有，网络堵了自动降速 | 没有，网络再堵照发不误 |
| 首部开销 | 无选项时 20 字节，用了选项更长的 | 固定 8 字节 |
| 传输方式 | **流式**：无边界，保证顺序和可靠 | **报文式**：一包一包有边界，可能丢包乱序 |

> 一句话：**TCP 是挂号信（贵、稳、有回执），UDP 是明信片（便宜、快、丢了不管）**。用 UDP 的典型：视频直播、语音通话（能容忍丢一点）、DNS 查询。

## Q2 TCP 为什么可靠传输？

### 一句话答案

靠"六件套"：**连接管理、序列号、确认应答、超时重传、流量控制、拥塞控制**。

### 大白话讲解

| 机制 | 解决什么问题 | 怎么工作 |
| --- | --- | --- |
| **连接管理** | 传输前提 | 三次握手建连、四次挥手断连，保证连接的可靠性 |
| **序列号** | 乱序、重复 | 给每个字节编号：按序还原、去重、还能"多次发送一次确认"提效率 |
| **确认应答** | 对方收没收到 | 接收方回 ACK（带序列号）告诉发送方"收到哪些了" |
| **超时重传** | 丢包 | 超时没收到 ACK 就重传；两种情况：数据包丢（重传数据）、确认包丢（收到重复数据就丢弃，再回 ACK） |
| **流量控制** | 接收方处理不过来 | 接收方通过首部的**滑动窗口**告诉发送方"我还能收多少"，发送方据此限速，防止缓冲区溢出 |
| **拥塞控制** | 网络堵了 | 发送方维护**拥塞窗口**，网络拥堵时减少发送量 |

> 关键公式：**发送方的发送速度 = min(滑动窗口, 拥塞窗口)**——一个受接收方能力限制，一个受网络状况限制。

## Q3 怎么用 UDP 实现 HTTP？（QUIC 与 HTTP/3）

### 一句话答案

**基于 UDP 的 QUIC 协议**实现了类似 TCP 的可靠性，HTTP/3 就是用它传输的。

### 大白话讲解

UDP 不可靠，但 QUIC 在 UDP 之上补齐了可靠性。先搞清楚四者关系，再看 QUIC 的四大能力：

**先看四者的分层定位（TLS、QUIC、TCP、UDP 关系）：**

```
应用层:    HTTP/1.1          HTTP/2            HTTP/3
安全层:    TLS 1.2/1.3      TLS 1.2/1.3      (TLS 1.3 内嵌进 QUIC)
传输层:    TCP              TCP              QUIC ──跑在 UDP 之上
```

| 协议 | 层 | 管什么 | 类比 |
| --- | --- | --- | --- |
| **TCP** | 传输层 | 可靠传输：不丢、不乱、按序 | 挂号信服务 |
| **UDP** | 传输层 | 无连接快速传：丢了不管 | 明信片服务 |
| **TLS** | 安全层（传统在 TCP 之上） | 加密 + 身份认证 | 防拆信封 + 公章 |
| **QUIC** | UDP 之上的"新型传输层" | 可靠传输 + 加密 + 更优设计 | 自己造的轻轨列车 |

**四组关键关系：**

1. **TCP 和 UDP = 平级兄弟**：传输层的两个选项，二选一。TCP 可靠但笨重，UDP 轻快但不可靠，上层协议都要落到其中之一；
2. **TLS 和 TCP = 叠加关系**（传统栈）：TLS 原本是独立的安全层，跑在 TCP 之上。为什么不能直接跑 UDP？因为**握手消息本身不能丢**——证书交换、密钥协商需要可靠交付，UDP 做不到。TCP 时代是"两层分离、串行握手"：先 TCP 三次握手，再 TLS 握手；
3. **QUIC 和 UDP = 寄生关系**（改造底层）：QUIC 只借 UDP 的端口和无连接特性，可靠性和拥塞控制全部自己实现——本质是"在明信片上实现了挂号信的服务"，绕开了"改 TCP 必须改内核"的困境；
4. **QUIC 和 TLS = 融合关系**（最大变革）：TLS 1.3 **内嵌**进 QUIC，不是"跑在它之上"，而是一体——一次握手同时完成"传输建连 + 加密协商"，这就是 1-RTT/0-RTT 的来源。

> 演变主线：从"可靠（TCP）+ 安全（TLS）各自独立、串行叠加"到"可靠 + 安全 + 低延迟一体化（QUIC 内嵌 TLS 1.3 跑在 UDP 上）"——QUIC 就是这场融合的产物。

**四大能力：**

| 能力 | 说明 |
| --- | --- |
| **连接迁移** | 网络变化（WiFi → 移动数据）时连接不断，快速迁移保持可靠 |
| **重传机制** | 丢失的数据包重新发送，保证可靠性 |
| **前向纠错** | 接收端能修复部分丢失的数据，减少重传需求 |
| **拥塞控制** | 内置拥塞控制，根据网络状况动态调速，避免拥塞丢包 |

**QUIC vs TCP 核心对比：**

| 维度 | TCP（HTTP/1.1/2） | QUIC（HTTP/3） |
| --- | --- | --- |
| 底层 | 操作系统内核协议栈 | UDP 之上（用户态实现） |
| 握手 | TCP 3 次握手 + TLS 握手 = 最多 3-RTT | 首次 1-RTT，重复连接 **0-RTT**（缓存上次的密钥） |
| 队头阻塞 | **有（两层）**：TCP 层丢一个包后续全卡；HTTP/2 层一个流丢包阻塞其他流 | **基本消除**：丢包只影响所在流，其他流照跑 |
| 连接迁移 | 换网络（WiFi → 4G）连接断，重新握手 | 用**连接 ID** 标识连接，不绑 IP/端口，换网络不断连 |
| 实现位置 | 内核，改协议要升级内核 | 用户态，升级浏览器/服务器即可 |
| 重传 | 重传同样的字节（序列号不变，累计确认） | 重传用**新包号**，收到重复包号即知是重传，RTT 估算更准 |

**三个痛点逐个说：**

1. **握手慢**：TCP 三次握手 1-RTT + TLS 1.2 握手 2-RTT = 3-RTT 才能发第一个字节。QUIC 把传输握手和 TLS 合并（内置 TLS 1.3），首次 1-RTT，重复访问 0-RTT——第一字节零往返。
2. **队头阻塞**：HTTP/2 多路复用解决了应用层串行，但 TCP 层保证"按序交付"——一个包丢了，后面的包排队等重传，所有流一起卡住。QUIC 在单条连接里跑**多个独立流**，每个流独立确认、独立重传，一个流丢包不连累别人。
3. **连接迁移**：TCP 靠（源 IP、源端口、目的 IP、目的端口）四元组标识连接，手机切网 IP 变了连接就死。QUIC 用**连接 ID** 标识，换网络无缝迁移，视频通话不掉线。

> 面试金句：**"QUIC 把 TCP 从内核搬到了用户态"**（迭代速度）；**"TCP 的队头阻塞在传输层，QUIC 把它拆成了流的粒度"**（丢包影响从整条连接缩小到单个流）；**"0-RTT 是 QUIC 的王牌"**（重复访问零等待，弱网体验提升明显）。

### 追问：0-RTT / 1-RTT / 2-RTT 是什么？

**RTT = Round Trip Time（往返时间）**：从"发出一个包"到"收到对方的回包"的时间，即**一问一答的一个来回**。N-RTT 表示**从发起连接到发出第一个业务数据需要几个来回**——每少一个来回，弱网下用户就少等几百毫秒。

| 指标 | 含义 | 场景 |
| --- | --- | --- |
| **0-RTT** | 第一个包就带业务数据，零等待 | 会话恢复：用缓存好的密钥，第一包直接发数据 |
| **1-RTT** | 一个来回后能发数据 | 首次连接的最快情况 |
| **2-RTT** | 两个来回后才能发数据 | 握手流程需要两轮问答 |

**数字怎么来的（关键：HTTPS 是两层握手叠加，RTT 要相加）：**

| 组合 | RTT 计算 | 总计 |
| --- | --- | --- |
| TCP 三次握手 | SYN → SYN+ACK → ACK | 1-RTT |
| TCP + TLS 1.2 | 1 + 2（TLS 完整握手四步） | **3-RTT** |
| TCP + TLS 1.3 | 1 + 1（TLS 1.3 精简握手） | 2-RTT |
| QUIC 首次连接 | 传输握手 + TLS 合成一次 | **1-RTT** |
| QUIC 重复访问 | 缓存密钥直接发数据 | **0-RTT** |

- **TLS 1.2 为什么 2-RTT？** 完整握手四步（ClientHello → ServerHello+证书 → ClientKeyExchange → Finished），客户端要等服务器发证书、再回密钥交换，两轮问答后才能算出会话密钥发数据。
- **QUIC 首次为什么 1-RTT？** 把"建传输连接"和"TLS 握手"**合成一次握手**（TCP 时代是串行两套流程），省掉一个来回。
- **0-RTT 为什么能零等待？** 前提是**重复访问**：上次连接结束时服务器发了一张票据（session ticket），下次客户端在第一个包里就带上用票据加密的数据，服务器一收到立即能解密。

**两个细节（面试追问）：**

1. **0-RTT 有重放风险**：首包数据是提前加密的，攻击者可原样重发 → 只用于幂等请求（GET），写操作默认不启用；
2. **减的是"往返次数"不是"延迟"**：0-RTT 省的是一个完整来回的时间，后续吞吐仍受带宽和拥塞控制限制。

> 面试亮点：HTTP/3 = QUIC = UDP + 可靠性补丁 + 更快的握手（0-RTT）。这也解释了上一章说"TCP 是流式"时为什么 QUIC 值得一提——UDP 之上可以造出可靠传输。

## Q4 TCP 粘包怎么解决？

### 一句话答案

粘包的本质是**不知道消息的边界在哪**。三种解法：**① 固定长度消息；② 特殊字符做边界；③ 自定义消息结构（包头带长度）**。

### 大白话讲解

TCP 是**流式**的——数据像水管里的水，连续无边界。发送方发了两条消息，接收方可能一次全收到（粘包），也可能收到半条（拆包）。解决思路就一个：**让接收方知道"一条消息到哪结束"**。

**方案一：固定长度**

每条消息固定 64 字节，凑够 64 字节就算一条。最简单，但灵活性差，实际很少用。

**方案二：特殊字符做边界**

消息之间插入特殊字符串（如换行符），读到特殊字符就算一条结束。**HTTP 就是活例子**：用回车换行符（CRLF）当报文边界。注意：消息内容里如果恰好有这个字符，要**转义**，否则会被误判为边界。

**方案三：自定义消息结构（最常用）**

```
struct {
    u_int32_t message_length;   // 4 字节：数据长度
    char message_data[];        // 数据本体
} message;
```

接收方先读固定的包头（4 字节）→ 解析出数据长度 → 按长度读满数据 → 组装成完整消息。

> 一句话：**方案三 = 先读"信封上的重量"，再按重量收"包裹"**。

## Q5 TCP 的拥塞控制介绍一下？（必考）

### 一句话答案

四个算法：**慢启动（指数增长）→ 拥塞避免（线性增长）→ 拥塞发生（超时重传重置为 1 / 快重传减半）→ 快速恢复**。核心是"网络堵了就少发，不堵就多发"。

### 大白话讲解

**为什么需要拥塞控制？**

网络是共享的。发送方如果无视拥堵狂发数据 → 丢包 → 重传 → 更堵 → 更丢包 → 恶性循环。所以 TCP 要"自我牺牲"：**网络拥堵时主动降低发送量**，避免数据填满整个网络。

**核心概念：拥塞窗口（cwnd）**

发送方维护的变量，随网络拥堵程度动态变化：
- 网络不堵 → cwnd 增大；
- 网络堵了（发生**超时重传**就认为堵了）→ cwnd 减小。

发送窗口 = min(cwnd, 接收窗口 rwnd)——**取"网络允许"和"接收方允许"中较小的**。

**算法一：慢启动（Slow Start）**

规则：**每收到一个 ACK，cwnd + 1**。

假设初始 cwnd = 1（能发 1 个 MSS 的数据）：
- 收到 1 个 ACK → cwnd = 2；
- 收到 2 个 ACK → cwnd = 4；
- 收到 4 个 ACK → cwnd = 8……

**指数增长**（1→2→4→8）。名字叫"慢启动"其实增长很快——它只是"从 1 开始慢慢加"，不是"慢慢涨"。

**什么时候停止指数涨？** 慢启动门限 **ssthresh**：
- cwnd < ssthresh → 慢启动；
- cwnd ≥ ssthresh → 进入拥塞避免。

**算法二：拥塞避免（Congestion Avoidance）**

规则：**每收到一个 ACK，cwnd 只加 1/cwnd**（即"每轮 RTT 只 +1"）。

- 8 个 ACK 各加 1/8，总共才 +1 → 从 8 变 9，**线性增长**。
- 指数变线性，增长变温和。但依然在涨——涨到网络终于撑不住，开始丢包 → 触发重传 → 进入拥塞发生。

**算法三：拥塞发生（Congestion）**

分两种情况，力度差别很大：

**① 发生超时重传（网络严重拥堵）**——"回到解放前"：
- `ssthresh = cwnd / 2`；
- `cwnd 重置为 1`；
- 重新开始慢启动。

> 类比：秋名山漂移突然急刹车，反应强烈，造成网络卡顿。

**② 发生快速重传（网络轻度拥堵）**——只丢了一小部分，没那么严重：
- `cwnd = cwnd / 2`（减半）；
- `ssthresh = cwnd`；
- 进入快速恢复。

**算法四：快速恢复（Fast Recovery）**

快速重传 + 快速恢复通常一起用。前提：能收到 3 个重复 ACK，说明"网络没那么糟糕"。

流程（cwnd 和 ssthresh 已在上面更新为"减半后的值"）：
1. `cwnd = ssthresh + 3`（+3 表示有 3 个包被确认收到了）；
2. 重传丢失的数据包；
3. 再收到重复 ACK → cwnd + 1；
4. 收到新数据的 ACK → 说明恢复结束，`cwnd = ssthresh`，回到拥塞避免（线性增长）。

> 对比：超时重传"一夜回到解放前"（cwnd=1 重新爬），快速恢复"原地小幅减半再爬"（cwnd 减半后线性涨），温和得多。

**四算法完整流程：**

```
慢启动(指数↑) → 到ssthresh → 拥塞避免(线性↑) → 丢包
   ├─ 超时重传 → cwnd=1, ssthresh减半 → 重新慢启动
   └─ 快重传(3个重复ACK) → cwnd减半 → 快速恢复 → 拥塞避免
```

## 本单元小结

| 概念 | 一句话记住 |
| --- | --- |
| TCP vs UDP | 连接/可靠/控制 vs 无连接/不可靠/轻量 |
| 可靠六件套 | 连接管理、序列号、确认应答、超时重传、流量控制、拥塞控制 |
| 流量 vs 拥塞控制 | 流量控制限接收方能力；拥塞控制限网络状况；发送取两者最小值 |
| 粘包 | 没边界；固定长度 / 特殊字符 / 包头带长度 |
| 慢启动 | 每收一个 ACK 加 1，指数增长，到 ssthresh 为止 |
| 拥塞避免 | 每轮只加 1，线性增长 |
| 超时重传 | cwnd 重置 1，回到解放前 |
| 快重传+快恢复 | 3 个重复 ACK，cwnd 减半，温和处理 |
