# 11 网络攻击

> 面试问法：DDoS / SQL 注入 / CSRF / XSS / DNS 劫持。
> 共 5 题，覆盖面试最常见的五类攻击，重点记住"是什么 + 怎么防"。

## Q1 什么是 DDoS 攻击？怎么防范？

### 一句话答案

**DDoS（分布式拒绝服务）**：攻击者用僵尸网络（被恶意软件控制的肉鸡）向目标发送海量流量，把目标服务器或网络淹没，导致正常用户无法访问。防范：增强带宽/硬件、防火墙与入侵检测、流量清洗与负载均衡、访问控制策略。

### 大白话讲解

**攻击原理**：攻击者通过恶意软件控制大量设备（电脑、IoT 设备等）组成**僵尸网络**，统一发指令 → 所有肉鸡同时向目标 IP 发请求 → 流量远超服务器承载 → 拒绝服务。因为每个肉鸡都是"合法"设备，很难区分攻击流量和正常流量。

**常见攻击类型（按层分类）：**

| 类型 | 典型攻击 | 攻击目标 |
| --- | --- | --- |
| 网络层 | UDP 反射攻击（NTP Flood） | 用大流量拥塞带宽 |
| 传输层 | SYN Flood、连接数攻击 | 占满服务器连接池资源 |
| 会话层 | SSL 连接攻击 | 耗尽 SSL 会话资源 |
| 应用层 | DNS flood、HTTP flood、游戏假人 | 耗尽应用处理性能 |

**防范措施：**

1. **增强网络基础设施**：提升带宽、增加服务器处理能力——"抗揍"。
2. **防火墙 + 入侵检测系统**：限制不必要流量、拦截可疑 IP；IDS 及时发现响应。
3. **流量清洗 + 负载均衡**：专业 DDoS 防护服务商做流量清洗（滤掉恶意流量）；负载均衡把流量分到多台服务器。
4. **访问控制策略**：限制特定 IP/IP 段、设置访问频率限制。

> 面试金句：**"DDoS 的本质是资源不对等——攻击者用分布式资源耗尽你的集中式资源"**。

## Q2 SQL 注入问题是什么？

### 一句话答案

**SQL 注入**：应用把用户输入直接拼进 SQL 语句执行，攻击者利用这点注入恶意 SQL。防范：**参数化查询**（根本解法）、输入验证与转义、限制数据库权限。

### 大白话讲解

**攻击原理**：用户输入被直接当作 SQL 的一部分。比如查用户信息：

```sql
-- 用户输入了：' OR '1'='1
SELECT * FROM users WHERE name = '' OR '1'='1'
```

`'1'='1'` 恒为真 → 一次查出全表数据。如果拼进 DELETE/UPDATE，后果更严重。

**为什么能成功？** 因为**输入没被验证/转义**就直接进了 SQL。

**防范四招：**

1. **参数化查询（最重要）**：用预定义变量接收输入，交给数据库引擎处理，**输入永远只是"数据"，不会被当成 SQL 代码**——从根上杜绝注入。
2. **输入验证和转义**：校验输入格式，过滤/转义特殊字符。
3. **限制数据库权限**：只授予业务所需最低权限——即使被注入，损失也有限。
4. **输入过滤**：检查过滤特殊字符和危险词汇。

> 面试金句：**"参数化查询让输入只当数据、不当代码——这是 SQL 注入的根治方案"**。

## Q3 CSRF 攻击是什么？

### 一句话答案

**CSRF（跨站请求伪造）**：诱导已登录用户在不知情的情况下发出"合法请求"，执行攻击者控制的操作（转账、改密码等）。防范：校验请求来源（Referer）、CSRF Token、双重验证等。

### 大白话讲解

**攻击原理**：你在银行 A 登录了（Cookie 还在）；攻击者让你访问恶意网站 B；B 页面里藏着一个发往银行 A 的请求（比如转账表单自动提交）→ 浏览器**自动带上你的 Cookie** → 服务器以为是"你本人"操作 → 转账成功。

关键点：**CSRF 利用的是"浏览器自动携带 Cookie"这个机制**，攻击者不需要拿到你的 Cookie，只需要"借你的手"发请求。

**攻击过程拆解（以"转账"为例）：**

**前置条件（三个缺一不可）：**

1. 目标站点用 **Cookie 维持会话**（Session 方案天然中招；JWT 放请求头则不中）；
2. 用户**已登录**目标站点，浏览器里存着有效的会话 Cookie；
3. 用户**访问了攻击者控制的页面**，且此时 Cookie 未过期。

**五个步骤：**

1. **用户正常登录**目标站点（银行 A）：浏览器收到会话 Cookie，此后任何发往 bank.com 的请求都自动携带；
2. **用户被诱导访问恶意网站 B**（钓鱼链接/论坛帖子/邮件）：注意此时用户**没有退出银行 A**，Cookie 依然有效；
3. **B 页面自动发出伪造请求**，常见三种载体（页面一加载就发出，无需点击）：
   - **表单自动提交**（POST）：`<form action="https://bank.com/transfer" method="POST">` 藏转账参数 + `submit()`；
   - **图片标签**（GET）：`<img src="https://bank.com/transfer?to=attacker&amount=10000">`；
   - **JavaScript 发请求**：`fetch('https://bank.com/transfer', {method:'POST', body:'to=attacker&amount=10000'})`；
4. **浏览器自动带上 Cookie**：关键点——浏览器按**请求的域名**决定带不带 Cookie，不按**页面从哪来**。请求发往 bank.com 就自动附上 bank.com 的 Cookie，攻击者从头到尾拿不到你的 Cookie；
5. **服务器误以为是你本人**：Cookie 校验通过 → 转账执行。攻击者没破密码、没碰加密——伪造请求和你的真实请求长得一模一样，服务器无法区分。

**完整攻击链路：**

```
用户 → 登录 bank.com（浏览器存好 Cookie）
     → 访问 evil.com（恶意页面自动发出 POST /transfer）
     → 浏览器自动带上 bank.com 的 Cookie
     → bank.com 校验 Cookie 通过 → 转账成功 ✗
```

**为什么 JWT 放请求头能免疫？** 浏览器自动携带的只有 Cookie。伪造请求发生在 evil.com 的页面里，它无法读取 bank.com 域下的 JWT，浏览器也不会替跨站请求自动加 `Authorization` 自定义头 → 伪造请求没有凭证，服务器直接拒绝。

**防范五招：**

1. **验证用户会话**：校验请求的会话标识与当前会话匹配。
2. **CSRF Token（核心方案）**：服务器生成随机 Token 嵌入表单，提交时校验——攻击者伪造的请求拿不到这个 Token。
3. **检查 Referer 头**：确认请求来自可信来源（可被绕过，作辅助手段）。
4. **内容安全策略（CSP）**：限制可执行脚本来源。
5. **避免自动提交表单**：关键操作加验证码/二次确认。

> 关联记忆：上一章《05》讲过——**JWT 放请求头（Authorization）而不是 Cookie，就是利用"跨站请求不会自动带自定义头"来天然防 CSRF**。

## Q4 XSS 攻击是什么？

### 一句话答案

**XSS（跨站脚本攻击）**：把恶意脚本注入网页，在用户浏览器中执行，盗取 Cookie、会话等敏感信息。分**存储型、反射型、DOM 型**三类。防范：输入验证、输出编码、CSP、HttpOnly Cookie。

### 大白话讲解

**攻击原理**：网站没对用户输入做处理，直接把内容渲染到页面 → 攻击者提交的内容里夹带 `<script>` 代码 → 别人访问页面时代码执行 → 脚本可以读 Cookie、模拟操作、劫持会话。

**三类 XSS：**

| 类型 | 特点 | 例子 |
| --- | --- | --- |
| **存储型**（持久型） | 恶意脚本**永久存服务器**，所有访问者都中招 | 论坛评论区存了恶意代码，每个浏览帖子的人被攻击 |
| **反射型**（非持久型） | 脚本经 URL 参数带进来，服务器原样返回 | 点恶意链接，搜索结果页把参数里的脚本"反射"回浏览器 |
| **DOM 型** | 页面本身没变，但**浏览器端 DOM 环境被恶意修改**，客户端代码意外执行 | 修改 URL hash 触发前端代码执行 |

**防范四招：**

1. **输入验证**：校验/过滤/转义所有用户输入，禁止 HTML 标签和 JS 代码进入；
2. **输出编码**：页面输出用户内容时做 HTML 转义、URL 编码——让 `<script>` 显示成纯文本而不是被执行；
3. **CSP**：限制页面可执行的脚本来源；
4. **HttpOnly Cookie**：Cookie 加 HttpOnly 后 **JS 读不到**——XSS 即使得手也偷不走会话 Cookie。

> 一句话：**XSS 偷的是"浏览器里的东西"（Cookie/会话），CSRF 偷的是"你的身份去操作"（借你的手）**——一个攻浏览器，一个攻请求。

## Q5 了解过 DNS 劫持吗？

### 一句话答案

**DNS 劫持**：攻击者篡改 DNS 查询的响应，把域名解析到攻击者控制的**虚假 IP**，用户以为上了真网站，实际进了钓鱼站。

### 大白话讲解

**攻击原理**：正常 DNS 解析会拿到目标网站的真实 IP；DNS 劫持就是在解析环节动手脚——通过植入恶意 DNS 记录，或劫持用户 DNS 流量（如篡改路由器/运营商 DNS 配置），把域名指向攻击者的 IP。

**危害**：用户访问"假网站" → 输入账号密码 → 直接被攻击者收走（钓鱼）。

**用户侧感知**：地址栏域名没变、看着像真网站，但内容被替换。

> 面试补充：防范方向——使用可信 DNS（如 DoH/DoT 加密 DNS 防窃听篡改）、检查 hosts 文件、路由器 DNS 设置别被篡改、网站侧部署 HTTPS + HSTS（防劫持后降级到明文 HTTP 钓鱼）。

## 本单元小结

| 攻击 | 一句话记住 | 核心防范 |
| --- | --- | --- |
| DDoS | 僵尸网络海量流量淹没目标 | 带宽扩容、流量清洗、负载均衡 |
| SQL 注入 | 输入拼进 SQL，被当作代码执行 | 参数化查询（根治） |
| CSRF | 借已登录用户之手发伪造请求 | CSRF Token、Referer 校验 |
| XSS | 恶意脚本注入页面，浏览器里执行 | 输入验证、输出编码、HttpOnly |
| DNS 劫持 | 篡改解析结果，指向钓鱼站 | 可信 DNS、HTTPS/HSTS |
