# 08 TCP 四次挥手

> 面试问法：四次挥手过程 / 为什么中间两次不能合并 / 什么时候能合并 / 各次丢包 / 2MSL / 大量 TIME_WAIT。
> 共 8 题，与三次握手并列为面试最高频。

## Q1 TCP 四次挥手过程说一下？

### 一句话答案

**① 主动方发 FIN（不再发数据）→ FIN_WAIT_1；② 被动方回 ACK → 主动方 FIN_WAIT_2、被动方 CLOSE_WAIT；③ 被动方发完剩余数据后发 FIN → LAST_ACK；④ 主动方回 ACK → 被动方 CLOSE、主动方 TIME_WAIT，等 2MSL 后 CLOSE**。

### 大白话讲解

```
主动关闭方(客户端)                        被动关闭方(服务端)
ESTABLISHED                              ESTABLISHED
  │  ① FIN（我不再发数据了）               │
  │────────────────────────────────────→│  → CLOSE_WAIT
  │  ② ACK（收到，但我还有数据要发）       │
  │←────────────────────────────────────┤
  │  FIN_WAIT_1 → FIN_WAIT_2              │
  │  （这期间还能接收数据）                │
  │  ③ FIN（我的数据发完了，拜拜）         │
  │←────────────────────────────────────┤  → LAST_ACK
  │  ④ ACK（拜拜）                       │
  │────────────────────────────────────→│  → CLOSE
  │  TIME_WAIT（等2MSL后CLOSE）           │
```

**每个状态的细节：**

1. **第一次挥手**：客户端调用 close → 发 FIN → 进入 **FIN_WAIT_1**。FIN 表示"我不会再发送数据了"。
2. **第二次挥手**：服务端内核立刻回 **ACK** → 服务端进入 **CLOSE_WAIT**。注意：内核收到 FIN 时会把"文件结束符 EOF"插入接收缓冲区（排在已收数据的**后面**），应用程序要**先读完缓冲区的存量数据**，然后 read() 返回 0，才知道对端关了。
3. **第三次挥手**：服务端应用**处理完剩余数据后**才调用 close → 发 FIN → 进入 **LAST_ACK**。所以第二步和第三步之间可能隔很久。
4. **第四次挥手**：客户端回 **ACK** → 进入 **TIME_WAIT**；服务端收到后进入 **CLOSE**。
5. 客户端等 **2MSL** 后，也进入 **CLOSE**。

## Q2 为什么四次挥手中间两次不能变成一次？

### 一句话答案

**第二次挥手（ACK）由内核立即回复，而第三次挥手（FIN）的控制权在应用程序**——应用可能还有数据要发，所以 ACK 和 FIN 一般分开发送。

### 大白话讲解

- 服务端收到 FIN 时，**内核**马上回 ACK——这是内核的自动行为，不能等；
- 但**发不发 FIN、什么时候发 FIN，由应用程序决定**：它可能还有数据没发完，要等发完再调用 close 才发 FIN。
- 所以"回 ACK"和"发 FIN"是两件不同主体（内核 vs 应用）控制的事，通常不能合并。

> 面试金句：**"第二次挥手是内核回执，第三次挥手是应用告别"**——一个在收到时立刻发生，一个要等应用处理完业务数据。

---

## Q3 第二次和第三次挥手能合并吗？（进阶追问）

### 一句话答案

**能**：当被动关闭方**没有数据要发**，并且**开启了 TCP 延迟确认机制**时，第二、三次挥手会合并成一个报文发送 → 出现"三次挥手"。

### 大白话讲解

- **TCP 延迟确认**：接收方收到数据/FIN 后，不立刻回 ACK，而是等一小段时间，如果这段时间内刚好要发别的报文（比如 FIN），就**搭顺风车**一起发。
- 所以当被动方"无数据可发 + 延迟确认生效"时，ACK 和 FIN 装进同一个包 → 四次挥手变三次。

> 这是原题里的冷门追问，能答出来是明显加分项。

---

## Q4 第三次挥手一直没发，会发生什么？

### 一句话答案

**主动方一直卡在 FIN_WAIT_2**：用 `shutdown` 关闭的连接可以一直等；用 `close` 关闭的**孤儿连接**最多等 `tcp_fin_timeout`（默认 60 秒），超时直接关闭。

### 大白话讲解

- 主动方收到第二次挥手的 ACK 后进入 **FIN_WAIT_2**：我的发送通道关了，等你发 FIN 关你的通道。
- 如果服务端一直不发 FIN（比如应用卡住）：
  - **shutdown 关闭**：连接还能收发数据，可以一直处于 FIN_WAIT_2；
  - **close 关闭的孤儿连接**（没有进程引用的连接）：无法再收发数据，不能无限等 → `tcp_fin_timeout` 默认 **60 秒**，超时直接关闭连接。

---

## Q5 第二次和第三次挥手之间，主动断开的那端能干什么？

### 一句话答案

**如果主动方用 `shutdown` 只关闭了发送能力、保留接收能力，那么这段时间它还能接收数据**。

### 大白话讲解

`shutdown` 可以只关"发送方向"（SHUT_WR），保留接收方向。此时：

- 主动方发出 FIN 后（发送通道关闭）；
- 但在服务端发 FIN（第三次挥手）之前，**主动方依然可以正常接收服务端发来的数据**。

> 对比：`close` 是"双杀"（发送 + 接收全关）；`shutdown` 可以"单杀"（只关发送）。面试时主动提到 shutdown/close 的区别很加分。

---

## Q6 断开连接时客户端 FIN 包丢失，服务端的状态是什么？

### 一句话答案

**客户端会超时重传 FIN（次数由 `tcp_orphan_retries` 控制），重传耗尽后客户端直接 CLOSE，而服务端一直停留在 ESTABLISHED**。

### 大白话讲解

- 客户端发 FIN 后进入 **FIN_WAIT_1**；正常收到 ACK 会很快变 FIN_WAIT_2。
- 第一次挥手丢了 → 客户端收不到 ACK → **超时重传 FIN**，次数由 `tcp_orphan_retries` 控制。
- 重传次数耗尽后：客户端再等"上次超时 × 2"，还是没收到 → **客户端直接进入 CLOSE 状态**。
- 而服务端完全不知道这事，**一直保持 ESTABLISHED**（连接被"半吊着"，直到它自己发现或保活机制介入）。

> 关键：**主动方的 FIN 丢了，主动方会重传；但被动方毫不知情，状态不变**。

## Q7 为什么四次挥手之后要等 2MSL？（高频）

### 一句话答案

**2MSL = 两次"报文最大生存时间"，保证最后那个 ACK 丢了也能被兜住（被动方重发 FIN 时还能响应），同时让旧报文在网络中自然消亡**。

### 大白话讲解

先弄清两个概念：

- **MSL（Maximum Segment Lifetime）**：报文在网络上存在的最大时间，超过即被丢弃。它与 TTL 相关但不同：**TTL 是"路由跳数"（每过一个路由器减 1），MSL 是"时间"**。Linux 把 MSL 设为 30 秒，即认为报文经过 64 跳不会超过 30 秒。
- **为什么是 2 倍**：报文"一来一回"需要 2 倍时间——如果最后那个 ACK（第四次挥手）丢了，被动方会重发 FIN（第三次挥手），这个重发的 FIN 需要 1 个 MSL 到达；TIME_WAIT 状态的客户端收到后要重发 ACK，又是 1 个 MSL。所以等 2MSL = **至少允许报文丢一次**。

**2MSL 还有第二个作用**：保证本次连接的所有报文（可能还滞留在网络中）在 2MSL 后**全部消亡**，不会串到下一次使用相同四元组的新连接里。

## Q8 服务端出现大量 TIME_WAIT 有哪些原因？

### 一句话答案

三个典型场景：**① HTTP 没用长连接（每次请求后服务端主动关连接）；② HTTP 长连接超时被服务端关闭；③ HTTP 长连接的请求数达到上限被服务端关闭**。

### 大白话讲解

先明确：**TIME_WAIT 出现在"主动关闭连接"的一端**。服务端大量 TIME_WAIT = 服务端在大量主动断连。什么场景服务端会主动断？

**场景一：HTTP 没有使用长连接**

- HTTP/1.0 默认短连接（要开 Keep-Alive 需在头里加 `Connection: Keep-Alive`）；**HTTP/1.1 默认长连接**（要关则在头里写 `Connection: close`）。
- 只要任意一方写了 `Connection: close`，一次请求后就关连接。**大多数 Web 服务实现里是服务端主动关** → 服务端产生 TIME_WAIT。

**场景二：HTTP 长连接超时**

- 长连接不是永久的：Web 服务有超时参数（如 nginx 的 `keepalive_timeout`，假设 60 秒）。
- 客户端完成请求后 60 秒内没发新请求 → 定时器到点 → **nginx 主动关闭连接** → 产生 TIME_WAIT。
- 如果看到"大量客户端建连后长时间不发数据"的现象，大概率是这个原因，可以往网络方向排查（数据是不是没送到服务端）。

**场景三：HTTP 长连接的请求数量达到上限**

- nginx 的 `keepalive_requests` 参数（默认 **100**）限制一条长连接最多处理多少请求，达到上限 nginx **主动关闭**。
- QPS 高的场景（上万甚至几万 QPS）：默认值 100 很快就触顶，nginx 频繁关连接 → **大量 TIME_WAIT**。
- 解法很简单：**调大 `keepalive_requests`**。

> 面试总结句式："TIME_WAIT 在主动关闭方出现。服务端大量 TIME_WAIT 说明服务端在频繁主动断连，常见是短连接、长连接超时、请求数到上限三种情况。"

## 本单元小结

| 概念 | 一句话记住 |
| --- | --- |
| 挥手四包 | FIN → ACK → FIN → ACK，各自状态：FIN_WAIT_1/2、CLOSE_WAIT、LAST_ACK、TIME_WAIT |
| 为什么四次 | ACK 是内核回执，FIN 由应用决定（可能还有数据要发） |
| 何时能合并 | 被动方无数据可发 + 延迟确认 → 三次挥手 |
| FIN_WAIT_2 卡住 | shutdown 可一直等；close 孤儿连接最多 60 秒 |
| 第一次挥手丢 | 客户端重传 FIN（`tcp_orphan_retries`），服务端一直 ESTABLISHED |
| 为什么 2MSL | 兜住丢失的 ACK（一来一回）+ 让旧报文消亡 |
| 大量 TIME_WAIT | 短连接 / 长连接超时 / 长连接请求数到上限 |
