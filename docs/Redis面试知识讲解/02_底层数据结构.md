# 02 底层数据结构

本章覆盖：String 为什么用 SDS、跳表怎么实现（层高怎么定）、为什么不用 B+ 树、压缩列表与连锁更新、listpack、哈希表怎么扩容（渐进式 rehash）。这是 Redis 面试里最容易被深挖的部分。

---

## 1. String 是使用什么存储的？为什么不用 C 语言中的字符串？

### 一句话回答
Redis 的 String 用 **SDS（Simple Dynamic String，简单动态字符串）** 存储，不用 C 语言的字符串，因为它能 **O(1) 获取长度、二进制安全、不会缓冲区溢出**。

### 展开讲：SDS 长什么样

SDS 结构（Redis 5.0）如下：

```
struct sdshdr {
    int len;      // 已用长度
    int alloc;    // 分配的空间长度
    char flags;   // 类型标记
    char buf[];   // 字符数组，真正存数据的地方
};
```

四个成员各管一件事：

- **len**：记录字符串长度 → 获取长度 O(1)；
- **alloc**：分配给字符数组的空间长度 → 用 `alloc - len` 算出剩余空间，判断够不够用；
- **flags**：标记 SDS 类型（sdshdr5、sdshdr8、sdshdr16、sdshdr32、sdshdr64 五种，按字符串长度选不同大小的结构省内存）；
- **buf[]**：字符数组，保存实际数据，**能存二进制**（不依赖 `\0` 结尾）。

### 为什么不用 C 语言字符串？三个致命缺陷

**缺陷 1：获取长度要遍历，O(N)**

C 的 `strlen` 函数要一个个字符数过去才知道多长。数据量大时很慢。

SDS 有 `len` 字段，**直接返回这个值就行，O(1)**。

**缺陷 2：不二进制安全**

C 字符串用 `\0` 标识结尾，所以**不能存包含 `\0` 的数据**（比如图片、序列化对象），存到一半就被截断了。

SDS 用 `len` 记录长度，**可以存储任意二进制数据**（包括 `\0`）。写入时是什么样，读出来就是什么样。当然为了兼容部分 C 库函数，SDS 末尾还是会补一个 `\0`，但只是"附赠"，不靠它判断结尾。

**缺陷 3：会缓冲区溢出**

C 的 `strcat` 等函数**不检查缓冲区够不够**，全靠开发者自己保证。一旦拼超了，就溢出写到别的内存里，程序可能直接崩。

SDS 有 `alloc` 和 `len`，API 内部先算 `alloc - len` 判断剩余空间，**不够就自动扩容**再执行修改，不会溢出。

### 比喻
C 字符串像**一条没标长度的绳**：想知道多长只能从头数到尾；中间有结（`\0`）就当绳到头了；往上挂东西挂多了绳子就断（溢出）。

SDS 像**一条标了长度和承重上限的绳**：看一眼标签就知道多长、还能挂多少，挂多了自动换更粗的绳。

## 2. 跳表是怎么实现的？

### 一句话回答
跳表是在**链表**基础上做的"多层"改进：底层是完整的有序链表，上面每层是稀疏的"快速通道"，查找时从高层往低层跳，时间复杂度从 O(N) 降到 **O(logN)**。

### 展开讲：为什么需要跳表

链表查找元素只能从头一个节点一个节点往后走，查 N 个节点最坏要 O(N) 次。**跳表给链表加了几条"快车道"**，让查找可以跳着走。

举例：一个层级为 3 的跳表，节点 1~5：

- L0 层级（底层）：5 个节点全有（1、2、3、4、5）；
- L1 层级：只有 3 个节点（2、3、5）；
- L2 层级：只有 1 个节点（3）。

**查找节点 4**：

- 普通链表：从头遍历，需要找 4 次；
- 跳表：从头节点直接从 L2 跳到节点 3，再往前遍历找到节点 4，**只找 2 次**。

数据量越大，这种"跳跃"的收益越大，复杂度是 **O(logN)**。

### 展开讲：跳表节点结构

Zset 要同时保存「元素」和「权重（分数）」，对应跳表节点：

```c
typedef struct zskiplistNode {
    // Zset 对象的元素值
    sds ele;
    // 元素权重值（分数）
    double score;
    // 后向指针，指向前一个节点，方便从尾部倒序访问
    struct zskiplistNode *backward;
    // level 数组：每个元素代表一层，保存该层的前向指针和跨度
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // 该层指向下一个节点的指针
        unsigned long span;             // 跨度：到下一个节点的距离
    } level[];
} zskiplistNode;
```

几个要点：

- `ele` + `score`：元素和分数；
- `backward`：后向指针，只会在第一层用，方便倒序；
- `level[]` 数组：每个跳表节点可以同时存在于多层，`level[0]` 是第一层，`level[1]` 是第二层……每层都有独立的 `forward` 指针和 `span` 跨度；
- **span（跨度）不是用来遍历的**，遍历用 `forward` 就行；跨度是用来**快速算排名**的（把沿途的 span 加起来就知道这个元素排第几）。

### 比喻
跳表像**商场里的扶梯 + 楼梯**：一楼是普通楼梯（底层链表，每层都停），上面是扶梯（高层节点，只在几个大站停）。要去 5 楼，先坐扶梯一口气到 4 楼，再走一步楼梯到 5 楼，比一层层爬楼梯快得多。

## 3. 跳表是怎么设置层高的？

### 一句话回答
**随机**。创建节点时不断生成 [0,1) 的随机数，小于 0.25（25% 概率）就加一层，直到随机数大于 0.25 停止；层高最大 64。

### 展开讲

具体做法：

1. 生成一个 [0-1] 的随机数；
2. 如果随机数 < 0.25（概率 25%），层数 +1，**继续生成下一个随机数**；
3. 直到某个随机数 > 0.25，停止，确定最终层数。

这意味着：**每增加一层的概率不超过 25%，层数越高概率越低**（比如 4 层高的概率约 0.25³ ≈ 1.6%），最大限制是 **64 层**。

两个补充点：

- Redis **没有**严格维持相邻两层节点数量 2:1 的比例（不像平衡树那么严格），靠概率天然形成"高层稀疏、底层稠密"的形态；
- **头节点**比较特殊：如果最大层高是 64，创建跳表时头节点**直接创建 64 层**（省得以后每加一个节点都要给头节点加层）。

### 为什么用随机而不是严格平衡？
严格平衡（像红黑树那样旋转调整）实现复杂、写操作要全局调整；随机层高实现简单，统计上效果已经足够好（查找期望 O(logN)）。这是"用概率换实现简单"的经典设计。

## 4. Redis 为什么使用跳表而不是用 B+ 树？

### 一句话回答
因为**场景不同**：B+ 树是为磁盘 I/O 设计的，要降低树高减少磁盘访问；Redis 是纯内存操作，没有磁盘 I/O 瓶颈，跳表更简单、写操作更稳定，性能同样 O(logN)。

### 展开讲：对比表

| 特性 | 跳表 (Skip List) | B+ 树 (B+ Tree) |
|---|---|---|
| 主要应用场景 | 内存数据库 (Redis) | 磁盘数据库 (MySQL) |
| 查找复杂度 | 平均 O(log N) | O(log N)（底数大、高度低） |
| 实现难度 | 低（几十到几百行代码） | 高（要处理分裂、合并） |
| 写操作代价 | 局部指针修改，无全局重平衡 | 可能引发连锁分裂/合并 |

### 原因一：内存 vs 磁盘的设计初衷（最重要）

- **B+ 树为磁盘而生**：磁盘访问很慢（毫秒级），所以要尽量**降低树的高度**，一次查询少读几个磁盘块。B+ 树一个节点能存很多 key，树很矮。
- **Redis 纯内存**：内存访问是纳秒级，**没有"磁盘 I/O"瓶颈**。跳表虽然比 B+ 树高（层数多），但内存里多跳几次指针的开销非常小。B+ 树为了压低树高搞出的复杂页管理机制，在内存场景下**显得多余且笨重**。

### 原因二：实现复杂度与代码维护

- 跳表本质是"多层链表"，插入/删除就是**改指针**，代码很简洁（几百行 C 代码）；
- B+ 树插入删除可能引发节点**分裂（Split）和合并（Merge）**，甚至整树重平衡，实现健壮的 B+ 树代码量大、难调试；
- Redis 作者 Antirez 非常看重**代码可读性和简洁性**。

### 原因三：写入性能与重平衡代价

- **B+ 树有写入抖动**：插入触发页分裂时，可能要移动大量数据或改树结构，产生性能抖动；
- **跳表是局部操作**：插入一个节点只改前后节点的指针，再随机生成层高，**不需要全局旋转或复杂的结构调整**。

### 结论：不是"谁更先进"，而是"谁更匹配场景"

1. 内存场景下，B+ 树的 I/O 优化优势无用武之地；
2. 高频更新场景中，跳表实现简单、性能稳定；
3. Zset 的核心操作（增删改查、范围查询），跳表能以更低复杂度实现同等甚至更优性能。

一句话：**B+ 树是"磁盘场景的最优解"，跳表是"Redis 内存有序数据场景的最优解"**，技术选型的核心是"适配场景"。

## 5. 压缩列表是怎么实现的？

### 一句话回答
压缩列表是 Redis 为了**节约内存**设计的**连续内存块组成的顺序型数据结构**（有点像数组），用来存少量数据；缺点是会有"连锁更新"问题。

### 展开讲：整体结构

压缩列表表头有四个字段：

- **zlbytes**：整个压缩列表占用的内存字节数；
- **zltail**：尾部节点距离起始地址的字节偏移量（有了它，取尾元素 O(1)）；
- **zllen**：节点数量；
- **zlend**：结束标记，固定值 0xFF（十进制 255）。

因为 `zltail` 和 `zllen` 的存在，**找第一个和最后一个元素都是 O(1)**；但找中间元素只能**逐个遍历，O(N)**。所以压缩列表**不适合存太多元素**。

### 展开讲：节点（entry）结构

每个节点包含三部分：

- **prevlen**：前一个节点的长度 → 目的是**从后向前遍历**；
- **encoding**：当前节点数据的类型和长度（字符串 or 整数）；
- **data**：实际数据。

关键设计：**根据数据类型（字符串/整数）和大小，用不同大小的空间存 prevlen 和 encoding**。小的数据用小空间，大的用大空间。这种"按需分配"就是 Redis 省内存的秘诀。

### 展开讲：连锁更新问题（压缩列表的"阿喀琉斯之踵"）

**问题来源**：每个节点都记录**前一个节点**的长度（prevlen）。

**触发场景**：往压缩列表中间插入一个特别长的节点，或某个节点被改大 → 它的"下一个"节点的 prevlen 装不下了，需要扩容 → 扩容后这个节点自己变大了 → 又导致它"再下一个"节点的 prevlen 装不下……**像多米诺骨牌一样一路往后传**。

**后果**：连锁更新导致内存空间要**多次重新分配**，直接影响访问性能。

**所以**：压缩列表只用于**节点数量不多**的场景（比如 Zset 少于 128 个元素时），节点少，即使连锁更新，代价也能接受。

### 后记：两个替代品

- **quicklist（Redis 3.2 引入）**：把一个大列表切成多个小压缩列表，控制每个压缩列表的大小，**减少**连锁更新的影响范围（但没有根除）；
- **listpack（Redis 5.0 引入）**：彻底去掉"记录前一个节点长度"的字段，**根除**了连锁更新。下一节细讲。

## 6. 介绍一下 Redis 中的 listpack？

### 一句话回答
listpack 是 Redis 5.0 设计的**替代压缩列表**的新数据结构，核心改进是**节点不再记录前一个节点的长度**，从而彻底解决连锁更新问题。

### 展开讲：为什么需要 listpack

quicklist 只是把压缩列表切小了，但每个小压缩列表内部**还是**压缩列表，连锁更新的问题**并没有根除**。

连锁更新的根源是结构设计：**每个节点要保存前一个节点的长度**。想彻底解决，就得改结构 → listpack 应运而生。

### 展开讲：listpack 的结构

- **头部**：两个属性，记录 listpack 总字节数和元素数量；
- **末尾**：结尾标识；
- **中间**：一个个 entry（节点）。

每个节点包含三部分：

- **encoding**：元素的编码类型（对不同长度的整数和字符串做不同编码）；
- **data**：实际数据；
- **len**：encoding + data 的总长度。

### 核心区别：为什么不连锁更新了

**listpack 只记录"当前节点"的长度（len），不记录"前一个节点"的长度**。

所以向 listpack 加入一个新元素时，**不会影响其他节点的任何长度字段**，连锁更新问题从根源上消失。

同时 listpack 保留了压缩列表的优点：

- 还是用**一块连续内存**紧凑地存数据；
- 还是**按数据大小用不同编码**，节省内存。

### 版本演进一句话总结

压缩列表（老）→ quicklist（3.2，治标：切小）→ listpack（5.0，治本：去掉 prevlen）→ **Redis 7.0 压缩列表正式废弃，全面改用 listpack**。

## 7. 哈希表是怎么扩容的？（渐进式 rehash）

### 一句话回答
Redis 哈希表扩容用**双表机制**：正常用「哈希表 1」，触发扩容时给「哈希表 2」分配 2 倍空间，然后**把数据分多次慢慢搬**（渐进式 rehash），避免一次性大量拷贝阻塞主线程。

### 展开讲：双哈希表

rehash 需要用 2 个哈希表：

- 正常服务阶段：数据都写入**哈希表 1**，「哈希表 2」**没分配空间**；
- 数据增多触发 rehash 后，分三步：
  1. 给「哈希表 2」分配空间（一般比表 1 大 **2 倍**）；
  2. 把「哈希表 1」的数据**迁移**到「哈希表 2」；
  3. 迁移完成后，释放「哈希表 1」空间，把「哈希表 2」变成新的「哈希表 1」，再新建一个空表当「哈希表 2」，为下次 rehash 做准备。

### 问题：一次性迁移会阻塞

如果「哈希表 1」数据量很大，一次性把几百万个 key 搬过去，**大量数据拷贝会阻塞 Redis，期间无法服务其他请求**。

### 解法：渐进式 rehash（分摊开销）

把一次性迁移拆成**多次小迁移**：

1. 先给「哈希表 2」分配好空间；
2. **在 rehash 期间，每次哈希表操作（增删查改）时，除了执行本身操作，还顺带迁移「哈希表 1」中一个索引位置上的所有 key-value 到「哈希表 2」**；
3. 请求越多，迁移越多，最终在某个时间点全部搬完，完成 rehash。

巧妙之处：把一次性大量数据迁移的开销，**分摊到每次请求处理中**，每次只做一点点，主线程永远不卡。

### 展开讲：rehash 期间的读写规则

渐进式 rehash 期间有两个哈希表同时存在，规则如下：

- **查找/删除/更新**：先在「哈希表 1」找，找不到再去「哈希表 2」找；
- **新增**：**只写入「哈希表 2」**，不再往「哈希表 1」写 → 保证「哈希表 1」的 key 只减不增，最终自然搬空。

### 比喻
像**搬家**：一次性把所有家具搬过去，人累垮（阻塞）；渐进式 rehash 是每天上下班顺带搬几件，过一阵子就搬完了，生活不受影响。

## 8. 哈希表扩容的时候，有读请求怎么查？

### 一句话回答
**先查「哈希表 1」，查不到再查「哈希表 2」**。

### 展开讲
渐进式 rehash 期间两个哈希表同时存在，一个 key 可能还没搬走（在表 1），也可能已经搬走（在表 2）。所以查找逻辑是：

1. 先在「哈希表 1」里找；
2. 没找到，继续到「哈希表 2」里找。

删除、更新同理。只有**新增**是特殊规则：一律写「哈希表 2」，保证表 1 只减不增，最终搬空。

### 面试怎么答
一句话："先查旧的，查不到再查新的，新增只写新的。"
