# 03 线程模型

本章覆盖：Redis 为什么快、单线程到底指什么、哪些地方用了多线程（后台 BIO 线程 + 6.0 I/O 线程）、I/O 多路复用怎么实现、Reactor 网络模型。

---

## 1. Redis 为什么快？

### 一句话回答
三大原因：**数据在内存 + 高效数据结构**（瓶颈不是 CPU）、**单线程免竞争**（省去锁和线程切换）、**I/O 多路复用**（一个线程处理大量客户端连接）。

### 展开讲

官方基准测试：**单线程的 Redis 吞吐量可以达到 10W/每秒**。

**原因 1：内存操作 + 高效数据结构**

Redis 大部分操作都在内存中完成，而且用了高效的数据结构（跳表、哈希表等）。所以 Redis 的**瓶颈可能是机器的内存或者网络带宽，而不是 CPU**。既然 CPU 不是瓶颈，就不需要多线程去"榨干 CPU"。

**原因 2：单线程免竞争**

- 避免了多线程之间的**竞争**（不用加锁）；
- 省去了**线程切换**带来的时间和性能开销；
- 也不会导致**死锁**问题。

**原因 3：I/O 多路复用**

用一个线程处理多个客户端 Socket 请求（select/epoll 机制）：

- 内核中同时存在多个监听 Socket 和已连接 Socket；
- 内核一直监听这些 Socket 上的连接请求或数据请求；
- 一旦有请求到达，就交给 Redis 线程处理。

这样就实现了**一个 Redis 线程处理多个 I/O 流**的效果。

### 比喻
像**一个效率极高的前台**：不派一堆人（多线程）去分别等各个客户（Socket），而是所有客户在一个大厅里等着，前台一次只看"谁叫号了"（事件就绪），叫到谁就快速处理谁，一个人搞定所有人，还不用协调一堆人之间别撞车（锁）。

### 面试怎么答
三句话：内存快（瓶颈不在 CPU）→ 单线程免竞争 → I/O 多路复用。说完可以补一句："所以单线程也能到 10W QPS。"

## 2. Redis 哪些地方使用了多线程？

### 一句话回答
**"Redis 单线程"指的是主线程串行执行命令**（接收请求 → 解析 → 读写 → 返回）；但 Redis 程序本身不是单线程的：一直有**后台线程（BIO）**，6.0 之后还引入了**多个 I/O 线程**处理网络请求。

### 展开讲：后台线程（BIO）

Redis 启动时会启动后台线程，把耗时任务丢给它们，避免阻塞主线程：

| 版本 | 后台线程 | 职责 |
|------|---------|------|
| 2.6 | bio_close_file、bio_aof_fsync | 关闭文件、AOF 刷盘 |
| 4.0+ | bio_lazy_free | 异步释放内存（lazyfree） |

**lazyfree 很重要**：执行 `unlink key` / `flushdb async` / `flushall async` 时，删除操作交给后台线程执行，主线程不卡。

> 面试考点：**删除大 key 不要用 `del`**（主线程执行会卡顿），要用 `unlink`（异步删除）。

工作模式：**生产者-消费者**。生产者把耗时任务丢进任务队列，后台线程（BIO）不停轮询队列，拿到任务就执行。

### 展开讲：为什么这些任务要单独线程

"关闭文件、AOF 刷盘、释放内存"都很耗时，如果都在主线程做，主线程很容易阻塞，就无法处理后续请求了。

### 展开讲：6.0 的多线程 I/O（重点）

网络硬件变强后，**瓶颈有时出现在网络 I/O 处理上**，于是 Redis 6.0 引入 I/O 多线程：

- **网络 I/O（读写 socket）**：多线程处理；
- **命令执行**：**仍然是单线程**！不要误解 Redis 有多线程同时执行命令。

官方说法：6.0 的多线程 I/O 特性**性能提升至少一倍以上**。

**几个重要细节：**

1. **默认关闭**：`io-threads` 配置默认值是 1（即只有主线程做网络 I/O），要手动改大才生效；

```
# 启用 I/O 多线程（4 表示共 4 个 I/O 线程，主线程算 1 个，额外启动 3 个）
io-threads 4
# 读请求也使用 I/O 多线程（默认多线程只处理写响应）
io-threads-do-reads yes
```

2. **默认只处理写**：I/O 多线程默认只针对**发送响应数据**（write socket），读请求要多线程需要额外开 `io-threads-do-reads yes`；
3. **线程数建议**：4 核 CPU 设 2 或 3，8 核 CPU 设 6，**一定要小于机器核数**，不是越大越好。

### 展开讲：Redis 6.0 默认启动的线程

不手动开启 I/O 多线程时，Redis 6.0 一共 4 个线程：

- **redis-server 主线程**：执行命令和网络 I/O；
- **bio_close_file**：异步关闭文件；
- **bio_aof_fsync**：异步 AOF 刷盘；
- **bio_lazy_free**：异步释放内存。

如果显式开启 `io-threads 4`，再额外启动 io_thd_1、io_thd_2、io_thd_3 三个 I/O 线程分担网络 I/O 压力。

### 面试怎么答
先澄清概念："单线程指命令执行单线程"，然后分三点：后台 BIO 线程（2.6 关文件/AOF 刷盘、4.0 加 lazyfree 异步删大 key）→ 6.0 引入 I/O 多线程（只做网络 I/O，命令执行还是单线程，且默认关闭）。

## 3. Redis 怎么实现的 I/O 多路复用？

### 一句话回答
Redis 用**一个线程同时监听多个 Socket**：把客户端连接的 fd 注册进内核（epoll），内核发现哪个 fd 有数据就通知事件处理器处理，"多路"指多个网络连接，"复用"指复用同一个线程。

### 展开讲：为什么要 I/O 多路复用

Redis 跑在单线程里，所有操作**顺序线性执行**。而读写操作等用户输入/输出是**阻塞**的——如果等某个客户端的数据等到天荒地老，整个进程就没法服务其他客户了。

I/O 多路复用就是来解决这个问题的：**用一个线程检查多个 Socket 的就绪状态**，哪个就绪处理哪个，谁也不耽误。

> "多路" = 多个网络连接（客户端）；"复用" = 复用同一个线程（进程）。

### 展开讲：工作原理

1. **每个 socket 连接对应一个 fd（文件描述符）**：客户端连接 Redis 时，会生成一个套接字描述符（文件描述符的一种）；
2. **把 fd 注册到监听列表**：多个客户端连接时，Redis 用 I/O 多路复用程序把每个客户端的 fd 注册到监听队列中；
3. **监听与回调**：文件事件处理器用 I/O 多路复用模块同时监控多个 fd 的读写情况。当 accept、read、write、close 等文件事件产生时，就回调 fd 上绑定的事件处理器处理。

以 **epoll** 为例：

- 多个客户端连接时，把 fd 注册进 epoll；
- epoll 同时监听这些 fd 是否有数据到来；
- 有数据来了，就通知事件处理器赶紧处理 → **不会出现服务端一直干等某个客户端给数据**的情况。

### 展开讲：设计模式

Redis 的 I/O 多路复用采用的是 **Reactor（反应堆）模式**实现。

### 比喻
像**餐厅只有一个服务员（单线程）**：服务员把每桌客人（socket）都登记了（注册 fd），谁一招手（数据到达）服务员就过去服务，服务完继续等着。不会因为一直伺候某一桌而饿死其他客人。

## 4. Redis 的网络模型是怎样的？

### 一句话回答
Redis 6.0 之前是**单 Reactor 单进程**模型；6.0 之后网络 I/O 改成了**多线程**（多个 I/O 线程），但命令执行仍是单线程。

### 展开讲：6.0 之前——单 Reactor 单线程

单 Reactor 单进程：**所有工作（监听、读、业务处理、写回）都在同一个进程内完成**。

**优点**：实现简单，不需要进程间通信，不用担心多进程竞争。

**两个缺点**：

1. **无法充分利用多核 CPU**（只有一个进程）；
2. **Handler 业务处理时，整个进程无法处理其他连接的事件**——如果业务处理耗时长，响应延迟就高。

所以单 Reactor 单进程**不适用计算密集型场景，只适用于业务处理非常快速的场景**。

Redis 恰好符合：业务处理主要在内存中完成，操作非常快，瓶颈不在 CPU → 所以 6.0 之前用单 Reactor 单线程很合适。

### 展开讲：6.0 之后——网络 I/O 多线程

网络硬件提升后，**性能瓶颈有时出现在网络 I/O 上**，所以：

- 网络 I/O（读 socket、写 socket）→ **多线程**处理，提高并行度；
- 命令执行 → **仍然是单线程**。

> 再次强调：**没有多线程同时执行命令**。

### 面试怎么答
版本分界线要记牢：**6.0 前单线程，6.0 后 I/O 多线程 + 命令单线程**。再补一句"6.0 的 I/O 多线程默认关闭，要手动开"就更完整。
