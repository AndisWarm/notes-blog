# 06 事件同步机制：链下索引怎么和链上保持一致

> 这是全项目最有**通用后端价值**的 60 行代码——换个皮就是 Kafka 消费者、binlog 同步、支付回调对账。

## 6.1 问题定义

链上发生的事（登记、授权、撤销、状态变更），后端怎么知道？

**约束条件**：
- 后端可能随时重启
- 事件**绝不能丢**（授权记录是给用户看的凭证）
- 重复处理不能产生脏数据
- 后端自己不发交易（V2 铁律），**监听是它感知链上世界的唯一途径**

## 6.2 方案：把链当成仅追加的消息队列

```go
// backend/internal/chain/listener.go
```

```
每 2 秒一轮 scanOnce:
    │
    ▼
┌─────────────────┐
│ latest = 链上最新块高 │
│ last   = chain_cursor 表里的游标 │
└────────┬────────┘
         │
         ▼ latest <= last?
    ┌─────────┐
    │  是 → 睡  │  无新块，等待下一轮
    └────┬────┘
         │ 否
         ▼
┌────────────────────────────────────────┐
│ logs = eth_getLogs(from=last+1, to=latest, │
│                     address=[Registry, License]) │
└────────┬───────────────────────────────┘
         │
         ▼ 逐条处理
┌────────────────────────────────────────┐
│ handleLog(按 topics[0] 分发)            │
│   - WorkRegistered → MarkAnchored      │
│   - LicenseGranted → UpsertLicense     │
│   - LicenseRevoked → RevokeLicense     │
│   - WorkStatusChanged → SetChainStatus │
└────────┬───────────────────────────────┘
         │
         ▼
┌─────────────────┐
│ SaveProcessedBlock(latest) │ ← 游标推进，持久化
└─────────────────┘
```

## 6.3 三个关键性质及其来源（背下来）

| 性质 | 靠什么保证 | 面试话术 |
|------|-----------|---------|
| **不丢** | 游标先处理后推进；重启从 last+1 继续，宕机期间的块照样扫到 | "位点持久化 + 断点续扫" |
| **不重（重放安全）** | 落库全部幂等：UpsertLicense 是 `ON CONFLICT DO UPDATE`；MarkAnchored/SetChainStatus 是按键 UPDATE | "幂等写入，同一事件处理两遍结果不变" |
| **可重建** | 链是唯一真相源：把 SQLite 删了、游标归零，从创世块重扫即可完整重建索引 | "事件溯源，索引可全量重建" |

**关键洞察**（面试亮点）：
> **位点 + 幂等是一对，缺一不可**——只有位点没有幂等会重复计数，只有幂等没有位点会全量重扫。

## 6.4 四个事件的处理细节

| 事件 | topics 里有什么 | data 里有什么 | 落库动作 |
|------|----------------|---------------|---------|
| **WorkRegistered** | id、author (indexed) | 三个哈希 | MarkAnchored：按 originalHash 匹配本地行，回填 chainWorkId/author/txHash/block，状态→ANCHORED |
| **LicenseGranted** | id、workId、licensee (indexed) | licensor、usage、validUntil | UpsertLicense (insert or update) |
| **LicenseRevoked** | id、workId | — | UPDATE revoked=1 |
| **WorkStatusChanged** | id (indexed) | status (uint8) | SetChainStatus 按 chain_work_id 更新 |

**技术细节**：
- indexed 参数从 topics 恢复：`lg.Topics[1].Bytes()`
- 非 indexed 用 ABI 从 data 解包：`UnpackIntoInterface`

## 6.5 动手实验：断点续扫复现（面试演示用）

```powershell
# 1. prepare 一个新作品，记下 txRequest —— 不要点上链
# 2. 关掉后端窗口 (Ctrl+C)
# 3. 用 MetaMask 发送这笔交易（链不依赖后端！）
# 4. 交易上链成功，此时链下谁都不知道
# 5. 重启后端，盯日志：数秒内出现
#    "anchored: chainWorkId=N author=0x... block=M"
# 6. 刷新前端，作品状态 ANCHORED，txHash/block 齐全
```

**对照实验**：后端运行期间把 chain_cursor 的 last_block 改成 0，观察日志把历史事件全部重扫一遍而数据没有变乱（幂等的直接证据）。

## 6.6 与业界对照（面试就这么讲）

| 本项目 | 业界对应 | 说明 |
|--------|---------|------|
| chain_cursor 游标 | Kafka 消费位点 | 记录消费到哪里 |
| 事件日志 | binlog / CDC | 仅追加的数据变更流 |
| listener 监听器 | The Graph 索引器 | 链上数据的链下索引 |
| 2秒轮询 | WebSocket `eth_subscribe` | 生产可换订阅，游标机制不变 |

**面试话术**：
> "这本质是一个**消息消费系统**——事件日志是仅追加的消息流，游标是消费位点，重启从位点续读所以'不丢'；写入用 upsert 幂等所以'不重'。这套模式与 Kafka 消费者完全同构，我可以画图讲。"

## 6.7 边界与展望（诚实清单）

| 边界 | 现状 | 生产方案 |
|------|------|---------|
| **轮询 vs 订阅** | 2s FilterLogs，延迟秒级 | WebSocket 订阅，毫秒级，需处理断线重连 |
| **链重组 (reorg)** | 本地链不会发生 | 公网需"确认数延迟"（游标落后链头 N 块）或支持游标回退 |
| **"no local row" 分支** | 只打日志，不自动建行 | 别人绕过后端直接调合约的作品，索引不认识但链上反查仍可验 |

## 6.8 代码精读：handleLog 的 switch

```go
func (l *Listener) handleLog(lg types.Log) error {
    switch lg.Topics[0] {
    case regABI.Events["WorkRegistered"].ID:
        // indexed: id, author; data: originalHash, signedHash, manifestHash
        var data struct {
            OriginalHash [32]byte
            SignedHash   [32]byte
            ManifestHash [32]byte
        }
        regABI.UnpackIntoInterface(&data, "WorkRegistered", lg.Data)
        chainWorkID := new(big.Int).SetBytes(lg.Topics[1].Bytes()).Uint64()
        author := common.BytesToAddress(lg.Topics[2].Bytes()).Hex()
        matched, _ := l.repo.MarkAnchored(
            hexutil.Encode(data.OriginalHash[:]), chainWorkID, author,
            lg.TxHash.Hex(), lg.BlockNumber)
        // ...

    case licABI.Events["LicenseGranted"].ID:
        // indexed: id, workId, licensee; data: licensor, usage, validUntil
        // ...
        return l.repo.UpsertLicense(domain.License{...})

    // ... 其他事件
    }
}
```

**面试追问**：如果处理到一半崩了怎么办？
> 游标是"处理完一批才推进"——处理到一半崩了，下轮会重扫这一批。**幂等兜住了正确性**。

## 6.9 为什么这个设计"值钱"

这 60 行代码体现的工程能力：

1. **分布式系统思维**：链是真相源，索引是缓存
2. **容错设计**：宕机自动补齐，重放安全
3. **可演进性**：轮询可换订阅，游标机制不变
4. **可观测性**：日志清晰，问题可追踪
