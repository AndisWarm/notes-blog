# 08 C2PA 与自建信任链：从 untrusted 到 Trusted

> 本章讲清：C2PA 是什么、为什么需要信任链、怎么自建 CA、trusted vs untrusted 的区别。

## 8.1 C2PA 是什么

### 生活类比
> C2PA 就像**照片的"出生证明 + 防伪标签"**，直接嵌入照片文件里。就像钞票上的防伪线，撕下来就坏，而且普通人用验钞机（c2patool）就能验真假。

### 技术定义
**C2PA**（Content Provenance and Authenticity，内容来源与真实性联盟）是 Adobe、微软、BBC、尼康等发起的开放标准。把创作声明（manifest）嵌入媒体文件内部，包含：

- **断言（Assertions）**：谁创作的、什么时候、做了什么操作
- **硬绑定（Hard Binding）**：对图像数据分块哈希，内容改了立刻检测出
- **签名**：用证书对以上全部签名

### 文件结构

```
JPEG/PNG 文件
├── 图像数据本身
└── JUMBF 容器（C2PA 嵌入）
    ├── manifest（声明）
    │   ├── assertions（断言）
    │   │   ├── c2pa.actions（创作动作）
    │   │   └── stds.schema-org.CreativeWork（标题、作者、originalHash）
    │   ├── hard binding（分块哈希）
    │   └── 签名信息（证书链、签名值）
    └── 其他元数据
```

## 8.2 为什么需要信任链

### 问题：签名有效 ≠ 签名可信

| 概念 | 含义 | 本项目状态 |
|------|------|-----------|
| **签名有效** | 签名数学上正确，内容没被改 | c2patool 默认就能验 |
| **签名可信** | 签名者是"自己人"，身份可确认 | 需要 trust anchor |

**生活类比**：
> 一张签名借条：签名是真的（有效），但签名的人是谁？如果是陌生人签的，你敢借钱吗？需要银行（CA）证明"这个人是真实存在的"。

### 信任链结构

```
Root CA（根证书，自签，验证方预先信任 = trust anchor）
   └── 签发 → 叶子证书（绑定签名者身份 + 公钥）
                  └── 用叶子私钥 → 给 C2PA manifest 签名
```

验证方沿链向上验到自己信任的根：
- 根在信任列表内 → **Trusted**
- 根不在 → **untrusted**（签名有效但来源不认识）

## 8.3 自建 CA 五步（make-ca.sh）

```bash
# tools/ca/make-ca.sh

# 1. 生成根私钥（EC P-256）
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out rootCA.key

# 2. 自签根证书（10年）
openssl req -x509 -new -nodes -key rootCA.key -sha256 -days 3650 \
    -subj "/C=CN/O=ImageProvenance Demo CA/CN=Demo Root" \
    -out rootCA.pem

# 3. 生成叶子私钥
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out sign.key

# 4. 根签发叶子证书（3年，带 C2PA 要求的扩展）
openssl req -new -key sign.key -subj "/C=CN/O=ImageProvenance Demo/CN=Demo Signer" -out sign.csr
openssl x509 -req -in sign.csr -CA rootCA.pem -CAkey rootCA.key \
    -days 1095 -sha256 -out sign.crt \
    -extfile <(echo "keyUsage=critical,digitalSignature
                     extendedKeyUsage=critical,emailProtection")

# 5. 合并链（叶子 + 根）
cat sign.crt rootCA.pem > sign-chain.pem
```

### 两个非显然细节

| 细节 | 原因 |
|------|------|
| `keyUsage=critical,digitalSignature` | C2PA 证书 profile 硬性要求 |
| `extendedKeyUsage=critical,emailProtection` | C2PA 规范沿用 S/MIME 类目的历史选择，不是笔误 |

**面试追问**：EKU=emailProtection 出现在这里很奇怪？
> 这是 C2PA 规范的要求——C2PA 证书 profile 复用了 S/MIME 的类目，因为数字签名场景类似。少一个 c2patool 拒收。

## 8.4 签名：manifest 定义文件

后端生成的 manifest 定义（BuildToolManifest 的输出）：

```json
{
  "claim_generator": "ImageProvenanceV2/0.1",
  "title": "作品标题",
  "alg": "es256",
  "private_key": "/绝对路径/sign.key",
  "sign_cert": "/绝对路径/sign-chain.pem",
  "assertions": [
    {
      "label": "c2pa.actions",
      "data": {
        "actions": [{
          "action": "c2pa.created",
          "when": "2026-07-26T12:00:00Z",
          "digitalSourceType": "http://cv.iptc.org/newscodes/digitalsourcetype/digitalArt"
        }]
      }
    },
    {
      "label": "stds.schema-org.CreativeWork",
      "data": {
        "@context": "https://schema.org",
        "@type": "CreativeWork",
        "name": "作品标题",
        "author": [{
          "@type": "Person",
          "name": "0x创作者钱包地址",
          "identifier": "0x创作者钱包地址"
        }],
        "identifier": "0x原图哈希"  // ← 关键：链上链下互指
      }
    }
  ]
}
```

### 三个考点

| 字段 | 考点 | 本项目处理 |
|------|------|-----------|
| `digitalSourceType` | C2PA 2.1（c2patool 0.27+）强制字段，缺它判 Invalid | 补上，前向兼容 |
| `identifier` | 嵌 originalHash，链上链下互指 | 四态验证第三态的关键 |
| 证书路径 | 必须绝对路径，c2patool 相对 manifest 文件解析 | 后端启动时 filepath.Abs 处理 |

## 8.5 trusted vs untrusted 对照实验（招牌实验）

```bash
# ① 默认验证（你的根不在任何信任列表里）
c2patool signed.png | grep -E "validation_state|untrusted"
# → signingCredential.untrusted / validation_state 非 Trusted

# ② 加载自己的根做 trust anchor
cp rootCA.pem trust-anchors.pem  # 与资产同目录（Windows 路径坑的规避）
c2patool signed.png trust --trust_anchors trust-anchors.pem | grep validation_state
# → "validation_state": "Trusted"
```

**同一张图、同一个签名，结论由"验证方信任谁"决定**——这就是 PKI 的核心思想被 C2PA 复用。

**面试话术**：
> "信任不是签名本身给的，是**信任锚**给的。验证方沿证书链逐级验签直到自己信任的根。同一张签名图，信任列表外=untrusted、列表内=Trusted，我做了这组对照实验。"

## 8.6 篡改检测（hard binding 亲手触发）

```bash
# 篡改签名版图片（尾部翻一个字节）
python -c "
d = bytearray(open('signed.png','rb').read())
d[-20] ^= 0xff
open('tampered.png','wb').write(bytes(d))
"

# 验证
c2patool tampered.png trust --trust_anchors trust-anchors.pem | grep -E "validation_state|hash"
# → Invalid + assertion.dataHash.mismatch
```

**后端识别**：
- 提取幸存 manifest 里的 identifier（=originalHash）反查
- 命中 → **manifest-only（签名后被篡改）**
- C2PA state = Invalid

## 8.7 验证报告解读

```json
{
  "validation_state": "Trusted",
  "validation_results": {
    "success": [
      { "code": "signingCredential.trusted" },
      { "code": "claimSignature.validated" },
      { "code": "assertion.hashedURI.match" },
      { "code": "assertion.dataHash.match" }
    ]
  }
}
```

**后端解析**（c2pa/tool.go）：
```go
func ValidationState(report []byte) string {
    var doc struct {
        ValidationState string `json:"validation_state"`
    }
    json.Unmarshal(report, &doc)
    return doc.ValidationState  // "Trusted" | "Valid" | "Invalid"
}
```

## 8.9 生产环境 vs Demo

| | Demo（本项目） | 生产 |
|---|---|---|
| CA | 自建（tools/ca） | C2PA 信任列表成员 CA |
| 信任锚 | 本地 rootCA.pem | 系统/浏览器内置根证书库 |
| 验证结果 | Trusted（demo 环境） | Trusted（全球通用） |

**诚实声明**：
> "自建 CA 生产不可用——生产要接入 C2PA 信任列表成员 CA。demo CA 的价值是完整演示信任模型的机制。"
