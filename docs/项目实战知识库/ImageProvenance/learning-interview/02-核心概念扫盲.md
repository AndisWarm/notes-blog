# 02 核心概念扫盲：小白也能懂的技术词典

> 本章目标：每个概念都用"生活类比 + 技术定义 + 项目里怎么用"三段式讲清楚。

---

## 2.1 区块链（Blockchain）

### 生活类比
> 想象一个**全世界共享的公开账本**，任何人都可以查看，但没人能偷偷改掉过去的记录。每页纸（区块）都写着"这一页的内容 + 上一页的页码指纹"，想改某一页就得把后面所有页都重抄，而且全世界一半的账本管理员同时同意才行——实际上不可能。

### 技术定义
区块链是一个**分布式、不可篡改、按时间顺序记录交易的数据库**。由多个节点共同维护，通过共识机制保证数据一致性。

### 项目里怎么用
- 把作品的"指纹"（哈希）写到区块链上，证明"某个时间点，这个作品存在"
- 记录授权关系（谁授权谁使用某作品）
- 记录作品状态（正常/有争议/已撤销）

### 面试高频追问

**Q: 区块链为什么不可篡改？**
> 每个区块包含前一个区块的哈希值，形成链条。改历史区块需要重新计算后面所有区块，并且控制超过一半的网络节点（51%攻击），成本极高。

**Q: 区块链和数据库有什么区别？**
| | 数据库 | 区块链 |
|---|---|---|
| 谁能改 | 管理员 | 没人能改历史 |
| 信任基础 | 信任管理员 | 信任数学和共识 |
| 适合场景 | 企业内部数据 | 多方互不信任的协作 |
| 性能 | 高 | 低（本项目 41 万 gas ≈ 0.1 美元） |

## 2.2 哈希（Hash）

### 生活类比
> 哈希就像**内容的指纹**。每个人的指纹独一无二，而且不能从指纹反推出人长什么样。同样，任何文件都可以算出一个固定长度的"指纹"（哈希值），文件内容变一点点，指纹就完全不同。

### 技术定义
哈希函数把任意长度的输入转换成**固定长度的输出**（SHA-256 是 256 位 = 64 个十六进制字符）。特性：
- **单向性**：从哈希值推不出原始内容
- **雪崩效应**：输入改 1 比特，输出面目全非
- **抗碰撞**：很难找到两个不同输入产生相同输出

### 项目里怎么用
- **哈希三元组**：原图哈希 + 签名版图哈希 + 声明哈希
- **防篡改**：改一个字节，哈希就不同，系统立刻发现
- **链上存储**：链上只存 32 字节哈希，不存图片本身（省 gas）

### 代码示例（项目实际代码）
```go
// backend/internal/hash/sha256.go
func BytesSHA256(data []byte) string {
    sum := sha256.Sum256(data)
    return "0x" + hex.EncodeToString(sum[:])
}
```

### 面试高频追问

**Q: 为什么不用 MD5？**
> MD5 已被破解，能人为制造碰撞（两个不同文件相同哈希）。SHA-256 目前安全，且是比特币、以太坊等主流区块链的标准。

**Q: 哈希能反推出原图吗？**
> 不能。哈希是单向的，就像指纹不能还原出人一样。这也是链上公开哈希不泄露作品内容的原因。

## 2.3 数字签名（Digital Signature）

### 生活类比
> 数字签名就像**手写签名的电子版**，但更安全。传统签名可以模仿，数字签名需要你的"私钥"才能签，别人用"公钥"能验证是你签的，但伪造不了。

### 技术定义
用私钥对数据加密生成签名，用公钥验证签名。特性：
- **不可伪造**：没有私钥签不出来
- **不可抵赖**：签了就承认是你签的
- **绑定内容**：签名和具体内容绑定，改内容签名就失效

### 项目里怎么用（两处独立使用）

| 场景 | 算法 | 签什么 | 谁验证 |
|------|------|--------|--------|
| **以太坊交易** | ECDSA / secp256k1 | 整笔交易 | 每个链节点（恢复出发送者地址） |
| **C2PA 声明** | ES256 / P-256 | manifest 文件 | 任何拿到文件的人（c2patool） |

### 关键概念：地址 = 身份

在以太坊里，你的"地址"就是公钥的哈希。所以：
> **"能签出这笔交易" = "你持有这个地址的私钥" = "你就是这个人"**

这就是为什么本项目 `author = msg.sender` 是安全的——msg.sender 是从交易签名恢复出来的，伪造不了。

### 面试高频追问

**Q: 私钥丢了怎么办？**
> 自托管钱包的固有代价。缓解方向：助记词备份、社交恢复（找几个朋友帮你恢复）、MPC 钱包（多方计算分片存储）。

**Q: 签名和加密有什么区别？**
| | 签名 | 加密 |
|---|---|---|
| 目的 | 证明身份 | 保护内容 |
| 用谁钥匙 | 私钥签，公钥验 | 公钥加，私钥解 |
| 本项目 | 证明"我是作者" | 不用（内容公开可验证） |

## 2.4 智能合约（Smart Contract）

### 生活类比
> 智能合约就像**自动售货机**：投币（发送交易）→ 出货（执行代码），规则写死在机器里，没人能改。不需要售货员，不需要信任对方，代码即法律。

### 技术定义
部署在区块链上的**自动执行程序**。一旦部署，代码不可变，执行结果由所有节点共同确认。

### 项目里怎么用
四个合约分工：

| 合约 | 功能 | 类比 |
|------|------|------|
| **RegistryV2** | 作品登记、哈希存储、状态管理 | 户籍科——管"谁是谁" |
| **LicenseV2** | 授权签发、撤销、有效性检查 | 版权局——管"谁能用" |
| **RoyaltyV2** | 分账规则设置 | 财务——管"怎么分钱" |
| **IRegistry** | 接口定义 | 通讯录——其他合约查"谁是作者" |

### 面试高频追问

**Q: 智能合约安全吗？**
> 代码公开透明，但 bug 也公开。本项目防御：Solidity 0.8 内置溢出检查、所有输入校验、无转账逻辑（无重入攻击面）、无管理员后门。

**Q: 合约能改吗？**
> 本项目合约**不可升级**——存证系统要不可变，这是特性不是缺陷。业务合约可谈代理模式（Proxy Pattern）。

## 2.5 C2PA（Content Provenance and Authenticity）

### 生活类比
> C2PA 就像**照片的"出生证明 + 防伪标签"**，直接嵌入照片文件里。就像钞票上的防伪线，撕下来就坏，而且普通人用验钞机（c2patool）就能验真假。

### 技术定义
C2PA 是**内容来源与真实性联盟**制定的开放标准（Adobe、微软、BBC、尼康等发起）。把创作声明（manifest）嵌入媒体文件内部，包含：
- **断言（Assertions）**：谁创作的、什么时候、做了什么操作
- **硬绑定（Hard Binding）**：对图像数据分块哈希，内容改了立刻检测出
- **签名**：用证书对以上全部签名

### 项目里怎么用
```json
// manifest 核心内容（简化）
{
  "claim_generator": "ImageProvenanceV2/0.1",
  "assertions": [
    {
      "label": "c2pa.actions",
      "data": { "actions": [{ "action": "c2pa.created", "when": "2026-07-26T12:00:00Z" }] }
    },
    {
      "label": "stds.schema-org.CreativeWork",
      "data": {
        "name": "作品标题",
        "author": [{ "name": "0x创作者钱包地址" }],
        "identifier": "0x原图哈希"  // ← 关键：链上链下互指
      }
    }
  ]
}
```

### 面试高频追问

**Q: C2PA 和区块链是什么关系？**
> 互补关系：C2PA 解决"文件流转中身份跟着走"，区块链解决"时间点不可抵赖"。本项目设计：**manifest 里嵌 originalHash（指回链上记录），链上锚 manifestHash（指回文件内声明）**——互相引用，双重保险。

**Q: 截图/压缩后 C2PA 还在吗？**
> 诚实回答：不在。这是 C2PA 生态的公开难题——破坏性处理会剥离元数据。方向是平台侧保留凭证 + 水印/指纹互补，本项目按边界不做。

## 2.6 IPFS（InterPlanetary File System）

### 生活类比
> IPFS 就像**按内容找书**而不是按书架位置找书。传统互联网是"去某个网站拿文件"（位置寻址），IPFS 是"我要哈希值为 XXX 的文件"（内容寻址）——谁有就给谁，而且拿到后自动校验是不是要的。

### 技术定义
分布式文件系统，文件用**内容哈希**（CID）作为地址。相同内容永远有相同 CID，不同内容几乎不可能有相同 CID。

### 项目里怎么用
- 签名后的图片和 manifest 文件存到 IPFS
- 链上只存 CID，不存文件本身
- 未启动 IPFS 时自动回退本地内容寻址存储（同一接口两个实现）

### 面试高频追问

**Q: IPFS 节点关了文件还在吗？**
> 诚实回答：pin 只保证本节点保留。生产环境要用 pinning 服务（如 Pinata）多副本。本项目是单节点演示。

## 2.7 其他重要概念速查

| 概念 | 一句话解释 | 项目应用 |
|------|-----------|----------|
| **Gas** | 区块链上的"计算油费"，执行操作要付费 | registerWork ≈ 41.3 万 gas |
| **钱包（Wallet）** | 管理私钥的工具，相当于"电子印章盒" | MetaMask，创作者自己控制 |
| **ABI** | 合约的"说明书"，告诉程序怎么调用合约 | 前端用 ABI 打包交易数据 |
| **事件（Event）** | 合约的"广播"，链下程序监听用 | WorkRegistered、LicenseGranted |
| **TSA** | 可信时间戳机构，第三方证明"某时存在" | RFC3161 双时间戳锚定 |
| **pHash** | 感知哈希，内容像则哈希像 | 相似预警，汉明距离 ≤10 触发 |
| **SQLite** | 轻量数据库，单文件零运维 | 链下索引，存储作品元数据 |
| **CID** | 内容标识符，IPFS 的文件地址 | 链上存 CID 指向实际文件 |
