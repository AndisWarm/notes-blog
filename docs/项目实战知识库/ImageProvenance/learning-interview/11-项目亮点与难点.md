## 11.2 技术决策（面试讲"为什么"）

### 决策 1：后端零私钥

| 维度 | 内容 |
|------|------|
| **问题** | V1 后端热钱包代签，链上 author 恒为服务器，确权系统"作者"是假的 |
| **方案** | 后端只准备 calldata，用户钱包签名发送 |
| **代价** | 用户需懂 MetaMask，体验门槛高 |
| **收益** | 身份真实可信，平台无法伪造 |
| **验证** | 代码无私钥配置、health 接口声明、链上数据 |

**STAR 话术**：
> "S：一期跑通了闭环，但架构审查发现后端代签导致链上作者失真。T：二期必须修复，否则确权叙事不成立。A：把上链动作从后端移到用户钱包，后端降为零私钥。R：链上 author 全是真实用户地址，系统可信度质变。"

### 决策 2：哈希三元组

| 维度 | 内容 |
|------|------|
| **问题** | V1 单哈希，用户拿到签名版验证时对不上 |
| **方案** | 原图 + 签名版 + 声明，三哈希上链 |
| **代价** | 多 10 万 gas（~$0.9） |
| **收益** | 四态验证完整、链上反查、防抢注 |
| **量化** | 成本收益比：$0.9 换核心功能完整 |

### 决策 3：事件驱动链下同步

| 维度 | 内容 |
|------|------|
| **问题** | 后端怎么知道链上发生了什么？ |
| **方案** | 2s 轮询事件日志 + 游标持久化 + 幂等写入 |
| **替代** | WebSocket 订阅（实时但复杂）、后端轮询合约状态（慢且贵） |
| **选择理由** | 简单可靠、断点续扫、可全量重建 |
| **通用性** | 与 Kafka 消费者同构，模式可迁移 |

## 11.3 四个踩坑故事（现象→定位→根因→修复→沉淀）

### 故事 1：GBK 编码污染

| 阶段 | 内容 |
|------|------|
| **现象** | 作品标题入库后乱码 |
| **定位** | Windows curl 按 GBK 编码发表单，后端当 UTF-8 解析 |
| **根因** | 跨编码边界没有有效性校验，坏字节一旦入库永久乱码 |
| **修复** | 入口加 `utf8.ValidString(title)`，无效直接 400 |
| **沉淀** | **跨编码边界必须在入口做有效性校验**，而不是在出口修补 |

### 故事 2：钱包余额"刷不出来"

| 阶段 | 内容 |
|------|------|
| **现象** | 水龙头充值后，MetaMask 界面余额纹丝不动 |
| **定位** | 后端日志显示钱已到账，前端缓存不更新 |
| **根因** | `hardhat_setBalance` 直改状态**不出块**，MetaMask 以**区块高度为缓存键** |
| **修复** | 充值后补挖空块 `evm_mine` 击穿缓存 + 前端直读链上余额 |
| **沉淀** | **理解客户端缓存失效机制比改 UI 重要** |

### 故事 3：c2patool 路径地狱

| 阶段 | 内容 |
|------|------|
| **现象** | Windows 盘符路径被当 URL scheme，`file://` 又被禁 |
| **定位** | c2patool 的 URL 解析器拒绝 `F:\...` 和 `file://` |
| **根因** | c2patool 设计为 Unix 优先，Windows 路径兼容差 |
| **修复** | 信任锚复制到资产临时目录用相对路径；manifest 里证书路径启动时 `filepath.Abs` 统一转绝对 |
| **沉淀** | **外部工具调用要隔离路径假设**，临时目录是安全边界 |

### 故事 4：C2PA 规范演进

| 阶段 | 内容 |
|------|------|
| **现象** | 新版 c2patool 0.27 下所有签名突然判 Invalid |
| **定位** | C2PA 2.1 把 `digitalSourceType` 转为强制字段 |
| **根因** | 依赖开放规范，规范演进导致前向不兼容 |
| **修复** | 补字段后新旧双版本通过 |
| **沉淀** | **依赖开放规范要跟踪演进，并建立跨版本回归**——这个缺陷是 L4 独立环境回归发现的 |

## 11.4 技术难点与解法

### 难点 1：四态验证的完整判定

**问题**：用户可能传原图、签名版、篡改后的图、从未登记的图，怎么区分？

**解法**：
```
计算 SHA-256
    │
    ├─ 命中 original_hash → 态1：原始文件
    ├─ 命中 signed_hash   → 态2：官方签名版
    ├─ DB miss → 链上 getWorkByHash 兜底
    ├─ 仍 miss → 提取 C2PA manifest identifier 反查
    │            命中 → 态3：签名后被篡改
    └─ 全部落空 → 态4：无记录
```

**关键设计**：manifest 里嵌 originalHash，链上锚 manifestHash——**互相引用**。

### 难点 2：事件同步的一致性

**问题**：后端可能随时重启，事件不能丢、不能重。

**解法**：游标 + 幂等
- 游标：chain_cursor 表持久化扫描位置
- 幂等：UpsertLicense `ON CONFLICT DO UPDATE`，MarkAnchored 按键 UPDATE

**验证实验**：停后端 → 上链 → 重启 → 自动补齐。

### 难点 3：C2PA 信任链

**问题**：c2patool 默认验证显示 untrusted，没有说服力。

**解法**：自建 CA
- openssl 造 Root CA + 叶子证书
- 根证书作为 trust anchor
- 验证结果：Trusted

**关键细节**：KU/EKU 按 C2PA 证书 profile 配置，EKU=emailProtection 是规范要求。

## 11.5 项目边界（诚实声明，面试加分）

| 不做 | 为什么 | 面试话术 |
|------|--------|----------|
| AI 生成检测 | 技术边界：现有技术无法可靠检测 | "我聚焦'确权'而非'辨伪'" |
| 相似图像检索 | pHash 只做链下预警 | "相似检索是另一个大课题" |
| 真实司法链对接 | MockJudicialAnchor 仅演示形态 | "预留接口，诚实声明边界" |
| 代币/真实支付 | RoyaltyV2 只记录比例 | "避免金融合规风险" |
| 公链主网部署 | 本地链+测试网 | "架构链无关，部署是下一步" |

**关键术语：GIGO**
> Garbage In, Garbage Out——区块链只能保证"上链后不被篡改"，不能保证"上链前是真的"。诚实承认是专业表现。
