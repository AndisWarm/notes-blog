# 07 大白话：威胁模型与安全性分析

> 对应原文档：`docs/10-威胁模型与安全性分析.md`
> 本文作用：这篇是 docs 里**方法论门槛**最高的一篇——它用了一套叫"威胁建模"的专业方法
> （STRIDE）。本文先讲清这套方法本身，再翻译原文档的结论。
> 适用场景：准备答辩"安全性"相关追问，或写论文"安全性分析"章节之前。

## 一、先理解：什么是"威胁建模"

**威胁建模** = 系统性地问自己四个问题，而不是拍脑袋想"哪里有风险"：

```text
1. 我保护的是什么？（资产）
2. 谁可能来破坏？（攻击者）
3. 他们能怎么破坏？（威胁）
4. 我怎么防？（防御）
```

**为什么需要这套方法**：如果你不系统地问，你只会防住"你碰巧想到的"攻击。
威胁建模的价值是**穷举**——把该想的都想一遍，再决定哪些防、哪些不防（残余风险）。

docs/10 的结构就是这四问的顺序：资产 → 信任边界 → 攻击者模型 → 威胁枚举(STRIDE) → 防御映射 → 残余风险。

## 二、STRIDE 是什么：六类威胁的检查清单

STRIDE 是微软提出的一套威胁分类法，每个字母是一类威胁：

| 字母 | 威胁 | 人话 | 本项目的例子 |
|---|---|---|---|
| S | Spoofing 假冒 | 冒充别人 | 冒充作者登记、替别人发授权 |
| T | Tampering 篡改 | 改数据 | 改图片、改链下数据库、抢注 |
| R | Repudiation 抵赖 | 做了不认账 | 作者否认"登记是我做的" |
| I | Information Disclosure 泄露 | 不该看的看到 | 从链上记录反推作品内容 |
| D | Denial of Service 拒绝服务 | 让系统没法用 | 刷接口、打崩后端 |
| E | Elevation of Privilege 提权 | 拿到不该有的权限 | 伪造事件骗过监听器、伪造 calldata |

**STRIDE 的用法**：对每个资产，逐类问"这会不会被 S/T/R/I/D/E？"，
把想到的场景列出来——docs/10 的表格就是这么来的（14 项威胁）。

## 三、docs/10 的四个核心结论（先看结论再看表格）

### 结论 1：平台后端被设计成"即使被攻破也伪造不了作者身份"

这是全文最核心的立场，逻辑链是：

```text
后端没有链上私钥（代码层面就没有）
  → 后端无法替任何人签名发交易
  → 链上 author 只能来自用户钱包的签名
  → 信任根在"用户钱包 + 链共识"，不在平台
```

**人话**：别的系统靠"承诺不干坏事"（信任），本系统靠"想干也干不了"（能力边界）。

### 结论 2：合约层"无转账逻辑" = 无重入攻击面

重入攻击（reentrancy）是智能合约最著名的攻击方式：合约在"收到钱"的过程中，
被恶意合约反复回调，把钱抽干。**本系统合约没有转账逻辑**（没有 ether 进出），
所以这个攻击面天然不存在——这是一个"因为不做，所以安全"的漂亮论证。

### 结论 3：14 项威胁中 12 项有验证过的防御，2 项如实记为残余

**诚实的成分很关键**：不是"全都防住了"的表演性安全，而是
"受限环境下的完整威胁建模闭环"——防得住的给出验证证据，防不住的写清理由和对策。

### 结论 4：四类"信任根"被分散

```text
身份根 → 用户钱包（私钥在用户手里）
记录根 → 链共识（链上记录改不了）
凭证根 → 信任锚（C2PA 验证依赖的根证书）
时间根 → 链上区块时间 + RFC3161 第三方（双时间戳）
```

平台唯一持有的密钥（C2PA 签名私钥）**只能签"内容声明"，不能动任何链上资产**——
这是"密钥职责分离"的设计。

## 四、读威胁表的方法：一行一行拆

原文档的"四、威胁枚举与防御映射"是全文最大的一张表（14 行），
每行是：编号 + STRIDE 分类 + 威胁场景 + 防御机制 + 验证证据。

拆一行示例（S1）：

```text
威胁场景：平台代签导致 author 失真（一期真实缺陷）
防御机制：创作者钱包直发交易，author=msg.sender；后端零私钥
验证证据：E2E"on-chain author == creator wallet"；health.signerMode
```

注意它的结构：**威胁必须对应"真实发生过的场景"（一期缺陷是现成素材），
防御必须对应"具体的机制"，验证必须对应"测试证据"**。
这三段齐全，才叫完整的威胁论证——这也是论文"安全性分析"章节的写作模板。

## 五、五类资产和信任边界（原文档第一、二节）

### 资产（保护什么）

| 资产 | 诉求 |
|---|---|
| 作品登记记录 | 完整性、不可篡改、可公开验证 |
| 作者身份 | 真实性——必须是创作者本人 |
| 授权关系与分账规则 | 只能由作者创建/变更 |
| 证据材料（PDF） | 可独立核验，不依赖平台存活 |
| 作品内容本体 | 完整性可验；**保密性不在目标内**（登记即公开语义） |

注意最后一行：**"保密性不在目标内"**——这个系统公开宣称"登记 = 公开"，所以
"别人看到了我的图"不算安全事件。边界划得清楚，论证才站得住。

### 信任边界（谁是可信的）

```text
[用户钱包]──签名──▶[前端 Vue]──HTTP──▶[后端 Go]──RPC──▶[链节点/合约]
  可信根:用户私钥      不可信输入源      半可信(零私钥)     信任根:共识
```

四类角色信任程度不同：用户私钥是信任根；前端是不信输入源；后端半可信（零私钥）；
链共识是最终信任根。

## 六、残余风险清单（原文档第六节，答辩直接引用）

6 条残余风险，条条都有"现状与理由"和"对策方向"：

| 残余 | 人话 | 为什么接受 |
|---|---|---|
| R1 无鉴权无限流 | API 可以被刷 | 本地单机演示定位；生产化方向已列 |
| R2 "先上链者赢" | 真正的首创者若后登记，系统无法自动裁定 | 链只能证明时序，不能证明创作事实（GIGO） |
| R3 破坏性处理后无法关联 | 截图/压缩后凭证丢失 | C2PA 生态公开难题；相似检索被明确收窄 |
| R4 本地链无 reorg 处理、无 TLS | 演示环境不发生/不设防 | 公网部署：确认数延迟入账、HTTPS |
| R5 登记内容公开可取 | 图可以被任何人下载 | "公开可验证"目标的一体两面；需保密可用 local 模式 |
| R6 恶意后端可给错误 calldata | 后端可以给你"无害但错误"的交易数据 | 已分析损失上界；前端本地重算比对列为展望 |

**答辩用法**：被问"你的系统有什么弱点"，照着这个表背两条 +
"每一条都有明确的收窄理由和解决方案"——这比支支吾吾强得多。
