# 05 大白话：面试讲述指南

> 对应原文档：`docs/08-面试讲述指南.md`
> 本文作用：讲清"面试"和"答辩"有什么不同、面试官在挖什么、STAR 怎么用、以及原文档里
> 技术清单部分的阅读地图。
> 适用场景：你拿着这个毕设项目去找工作（Go 后端 / 区块链 / 全栈 / 测试 / 安全方向）。

## 一、答辩 vs 面试：同一项目，两套讲法

| 维度 | 答辩（docs/07） | 面试（docs/08） |
|---|---|---|
| 问的人 | 评委，守**研究边界** | 面试官，挖**工程决策** |
| 关注点 | 选题意义、边界诚实、系统是否成立 | 你**为什么**这么做、原理懂不懂、踩过什么坑 |
| 答的节奏 | 30 秒口径 + 追问展开 | 决策 + 原理 + 数字 + 踩坑，四样齐全 |
| 风险点 | 吹牛被戳穿 | 只会报功能清单（"我做了 A、B、C"）——最弱的讲法 |

**一句话：答辩讲"这个系统没问题"，面试讲"我会做这个系统"。**

## 二、面试的基本功：STAR 叙事法

原文档给了可背诵的 2 分钟 STAR 版本，先理解它的结构：

| 字母 | 含义 | 这个项目里对应什么 |
|---|---|---|
| S (Situation) | 背景 | 数字图像被盗用后创作者举证困难；现有存证服务是黑盒，声明和文件分离 |
| T (Task) | 任务 | 一期跑通后审查出四个结构性缺陷，最致命是"后端代签 → 链上作者是假的"；二期要把四个闭环做实 |
| A (Action) | 行动 | ①身份：钱包直发交易 ②验证：哈希三元组+链上反查 ③授权：authorOf 强制校验 ④信任：自建 CA |
| R (Result) | 结果 | 20/20 单测、98.5% 覆盖率、76/76 回归、799ms/3ms 性能数据 |

**STAR 的作用**：把"我做了个项目"升级成"我在什么背景下，为了解决什么问题，
做了哪些决策，产生了什么可量化的结果"。

> 原文档 30 秒版建议背熟；STAR 版讲完**停住**，让面试官挑方向追问，不要一口气讲十分钟。

## 三、四个踩坑故事（面试官最爱问："遇到过什么问题？"）

原文档给了四个完整故事，每个都是 **现象 → 定位 → 根因 → 修复 → 沉淀** 结构。
这里是精简版，方便记忆：

| 坑 | 一句话版本 | 沉淀的教训 |
|---|---|---|
| **GBK 编码污染** | 标题乱码 → 查出来是 Windows curl 按 GBK 发中文、后端当 UTF-8 入库 → 修数据 + 入口校验 | 跨编码边界必须在入口做有效性校验 |
| **钱包余额"刷不出来"** | 水龙头充值后界面不动 → 后端日志显示钱到了 → 根因：充值 RPC 不出块，MetaMask 以区块高度做缓存键 → 修复：补挖空块 + 直读链上余额 | 理解客户端缓存失效机制，比改 UI 重要 |
| **c2patool 路径地狱** | Windows 盘符路径被当 URL、file:// 被禁 → 复制到临时目录用相对路径；manifest 里路径相对解析 → 启动时转绝对路径 | 工具链的路径解析规则要先摸清 |
| **规范演进兼容** | 新 c2patool 把所有签名判 Invalid → 定位到 C2PA 2.1 把 digitalSourceType 改为强制字段 → 补字段后双版本通过 | 依赖开放规范必须跟踪规范演进 |

**为什么面试官爱听踩坑**：踩坑故事最能证明"你真的亲手做过"，
比背概念可信得多。每个故事结尾的"沉淀"一句是点睛之笔。

## 五、必须先弄懂的几个原理（面试高频，原文档有的放矢）

### 为什么事件不用轮询合约状态？（4.6 高频追问）

- 事件（log）是链上**廉价的广播机制**，带索引、天然增量，适合链下订阅；
- 轮询合约状态要逐个作品查询，成本高、还得自己记增量；
- 所以监听器用 FilterLogs 拉事件——这本质是一个"消息消费系统"（类比 Kafka 消费者）。

### 为什么合约不可升级反而是特性？（4.1 高频追问）

- 存证系统要的是**不可变**——记录一旦上链谁都改不了，包括作者自己；
- 升级能力反而会引入"平台能不能改我的存证"的信任问题；
- 业务合约才考虑代理模式。

### 为什么"能签出交易"等于"持有私钥"？（4.3）

- 以太坊地址 = 公钥哈希的后 20 字节；
- 交易签名只有私钥持有者能做；
- 所以链上身份 = 密钥，不需要账号密码体系。
- 这也是"后端零私钥"设计的根基：后端没有私钥 → 后端永远当不了作者。

### IPFS 的 CID 为什么"地址即校验"？（4.9）

- CID 由内容哈希直接导出：同一内容永远得到同一 CID；
- 取回文件时重算哈希，对不上就说明文件被改；
- 所以存储层换任何实现（IPFS → 本地）都不破坏可验证性——因为验证靠哈希不靠存储。

## 六、工程向高频追问（原文档第 5 节，挑三个必会的）

### Q1：并发上来了瓶颈在哪、怎么扩？

```text
瓶颈排序：c2patool 进程调用（CPU 密集）→ TSA 网络往返 → SQLite 单写
方案：异步任务队列 + c2patool 工作池；TSA 并行化；SQLite → PostgreSQL；
     轮询 → WebSocket 订阅；无状态 API 水平扩容
```

### Q2：怎么保证链下索引和链上最终一致？

**三件套**：事件溯源（链是仅追加日志）+ 消费位点（游标持久化）+ 幂等写入（upsert）。
任何时刻索引可从创世块重放重建；verify 接口还有实时链上兜底。
"这套模式与 Kafka 消费者完全同构"——能说出这句，说明你真的理解。

### Q3：安全上最自豪的设计？

**后端零私钥**。确权系统最大的信任问题是"平台能不能替我签名"，
我的答案是架构上让平台**没有能力**代签，而不是承诺不代签。
可验证：health 接口、代码里没有任何私钥配置、链上 author 全是用户地址。

## 七、诚实红线（面试的保命条款）

原文档结尾的提醒，务必记住：

```text
分账"记录了比例"  ≠  "实现了分账支付"
本地链演示        ≠  "已上线"
Mock 司法锚定     ≠  "对接了司法链"
```

**被戳穿一次，前面的加分全部清零。** 面试官都是专业的，宁可少说三分，不可多说一分。
