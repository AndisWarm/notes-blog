# 04 大白话：演示脚本 与 答辩问题集

> 对应原文档：`docs/06-演示脚本.md`、`docs/07-答辩问题集.md`
> 本文作用：讲清"答辩"这个场景本身——评委是谁、在防什么、演示怎么设计、27 个问题背后的逻辑。
> 这篇是 docs 里**最实用**的一篇：读完你就能看懂答辩的全部设计。

## 一、先理解"答辩"是什么

毕设答辩 = 你当着几个评委的面，**演示系统 + 回答追问**。评委通常：

- 看过你的论文，但不一定跑过你的系统；
- 会从"你这东西真的有用吗""这里是不是有问题"的角度追问；
- 有经验，知道哪些点是"吹牛的高发区"。

所以 docs/06 和 07 的设计逻辑是：

```text
06 演示脚本：在 5 分钟内，把系统最亮的点演出来（先发制人）
07 问题集：  预判评委所有可能的追问，准备好答案（防守反击）
```

**演示是进攻，问题集是防守。** 两篇一起用。

## 二、docs/06 演示脚本：四幕怎么设计的

演示脚本结构：开场 30 秒 + 四幕 + 备选加演。

### 开场 30 秒：一句话定位

先给评委一个"钩子"：

> "本系统面向多方互信场景，把 C2PA 国际标准的文件内来源声明与区块链的跨主体锚定结合起来，
> 解决图像作品在确权时点之后的声明、授权与取证问题。"

拆开看这句话在说什么（这是论文的选题逻辑）：

```text
C2PA（文件内声明）   → 解决"文件离开平台后声明跟着走"
区块链（跨主体锚定） → 解决"时间 + 权属关系全网可查"
两句话 = 系统的全部价值
```

### 四幕的设计意图

| 幕 | 演什么 | 对应哪个闭环 | 为什么放这个顺序 |
|---|---|---|---|
| 第 1 幕 创作者确权 | 上传 → 三哈希 + C2PA trusted → 钱包上链 → author=创作者 | 身份闭环 | 最核心、最震撼的改进，先演 |
| 第 2 幕 越权攻击 | 乙替甲的作品发授权 → 被拒；甲自己发 → 成功 | 授权闭环 | 用"反面案例"证明权限是合约强制的 |
| 第 3 幕 验证与篡改 | 原图/签名版/篡改版 → 三种验证结果 | 验证闭环 | 证明系统真的能检测 |
| 第 4 幕 取证材料 | 证据 PDF：三哈希 + 双时间戳 + 二维码 | 信任闭环 | 收尾，落点到"取证" |

**设计要点**：每幕都"埋点"——故意展示一个能引发追问的点
（比如"作者地址=甲的地址"就是为了让评委问"那以前的项目呢"），
把评委引到你准备好的答案上。

### 备选加演

时间富余时演的三个"彩蛋"：相似预警、信任列表对照（untrusted vs trusted）、断点续扫。
每个都是一个独立小故事，随时能插入。

## 三、docs/07 问题集：27 个问题怎么组织的

问题集按主题分 8 组，每组对应系统的一个侧面：

| 组 | 问题 | 在防什么 |
|---|---|---|
| 一、选题与边界 | 为什么做这个？能证明版权吗？为什么不做 AI 检测？ | 选题的意义和边界 |
| 二、架构与技术选型 | 为什么用区块链？为什么用 C2PA？为什么本地链？ | 技术选型的合理性 |
| 三、身份闭环 | 代签有什么问题？用户没钱包怎么办？为什么三个哈希？ | 最核心的改进点 |
| 四、合约设计 | 越权防护怎么实现？为什么不做 NFT？合约安全？ | 合约的正确性 |
| 五、C2PA 与密码学 | 自建 CA 有意义吗？改 1 字节为什么能发现？截图后呢？ | 密码学原理 |
| 六、数据一致性与工程 | 链下链上不一致怎么办？性能？测试怎么做？ | 工程质量 |
| 七、现场突发情况 | 交易 pending 怎么办？余额为 0？后端挂了？ | 临场应变 |
| 八、灵魂拷问 | 和商业服务比意义在哪？工作量？重做会改什么？ | 认知深度 |

## 四、必须知道的三个关键口径（贯穿全部 27 题）

### 口径 1：GIGO 边界（最重要的一句）

> "链上记录不能证明上链前内容的真实性。"

GIGO = Garbage In, Garbage Out（垃圾进，垃圾出）。系统证明的是
"**某人在某时刻持有该文件并作出声明**"，不证明"这图就是他画的"。

**为什么必须主动说**：这是系统的第一弱点，评委必问。主动承认 + 讲清边界依据，
比被逼问出来得分高得多（原文档标注 ⚠ 的题都是这个策略）。

### 口径 2：诚实承认局限（⚠ 题的通用策略）

原文档的指导原则："承认局限时，诚实承认 + 讲清边界依据，比强行辩解得分高"。
典型的如：

- "截图/压缩后还能验证吗？" → 不能，这是破坏性处理，C2PA 生态的公开难题；
- "自建 CA 生产能用吗？" → 不能，生产要接 C2PA 信任列表成员 CA，demo 的价值是演示机制。

### 口径 3：数字说话

27 题里几乎每题都能引用实测数字（20/20、98.5%、76/76、799ms、413k gas……）。
**有数字的口径比形容词有说服力一个量级**——这是整份问题集的底色。

## 五、几个高频问题的"人话版"答案

### "为什么用区块链？数据库 + 时间戳不行吗？"

数据库做不到三件事：

1. **防篡改的时间锚**——链上记录运营方自己也改不了，数据库管理员能改；
2. **验证不依赖平台**——删了数据库，拿哈希直接问合约照样能验；
3. **权限由合约强制**——越权在共识层被拒，不是应用层 if 判断。

### "那 SQLite 还有什么用？"

**缓存加速器**：列表、详情、授权记录毫秒级查询（实测 3ms）。
真相源永远是链，索引可通过事件监听完整重建。

### "为什么锚定三个哈希？贵了多少？"

三个字节流（原图/签名版/声明）各需要自己的锚点。
代价：registerWork 约 41.3 万 gas，比单哈希贵约 10 万（+32%），
换来链上反查、防抢注、四态验证三个能力。

### "后端会不会伪造 calldata 骗用户签？"

诚实回答（这个追问很内行）：钱包里能看到目标合约地址和数据，MetaMask 会解码方法名；
更根本的是 registerWork **不转移任何资产**——最坏情况是登记了错误哈希，
用户可当场验证。彻底解法（前端本地重算比对）写在展望。

## 六、现场突发预案（第 7 组）的"话术思维"

| 突发 | 处置 | 话术技巧 |
|---|---|---|
| 交易一直 pending | 清除 MetaMask nonce 缓存 | 顺势解释"生产环境不存在此问题" |
| 余额为 0 | 点"领取测试币" | 顺势讲水龙头设计（仅 31337 放行） |
| 后端意外退出 | 重启 | **变演示点**："正好展示断点续扫——宕机期间的事件已自动对账" |
| 上传返回 409 | 换一张图 | 顺势讲防抢注双拦截 |
| C2PA 显示 untrusted | 查 trust anchor | 顺势讲信任列表内外对照 |

**核心技巧：把事故变成演示素材。** 每个预案都自带"顺势话术"——这是答辩的临场智慧。
