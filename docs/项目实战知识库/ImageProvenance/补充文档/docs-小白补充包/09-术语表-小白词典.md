| 四个闭环 | 二期改进的四个核心目标：身份、验证、授权、信任 | 01、02 |

| 状态机 | 作品在链下索引中的状态流转：UPLOADED → SIGNED → PINNED → PENDING_ANCHOR → ANCHORED | 01、02 |

## B. 区块链与合约

| 术语 | 人话 | 出处 |
|---|---|---|
| 上链 | 把信息写入区块链，写入后不可篡改、全网可查 | 01 |
| 智能合约 | 跑在区块链上的小程序，代码公开、任何人可调用 | 01 |
| msg.sender | 合约里的特殊变量：**谁调用的合约，它就是谁的地址**。由交易签名决定，伪造不了 | 01、02 |
| author = msg.sender | 合约把调用者记为作者——所以必须让创作者自己的钱包来调用 | 01、02 |
| authorOf | Registry 合约暴露的查询接口："这个作品的作者是谁？"供其他合约校验权限 | 01、02、04 |
| require / revert | Solidity 的校验语法：条件不满足就拒绝执行（revert = 回滚，相当于"拒绝并撤销"） | 01、02、04 |
| 越权 | 没有权限却执行了操作（比如替别人发授权） | 01、02、04 |
| 防抢注 | 同一哈希只能注册一次，重复注册直接 revert | 01、02 |
| hashIndex | 合约里的"哈希 → 作品编号"反查表，支持链上直接验证（不依赖链下数据库） | 01、02 |
| 链上反查 / getWorkByHash | 拿文件哈希直接问合约查作品——链下数据库丢了也能验证 | 01、02、04 |
| gas | 在以太坊发交易/执行合约要付的网络费，按计算量计费 | 03、02、04 |
| gas 代币 | 用来付 gas 的网络币（如 ETH）——元交易要解决的问题就是用户得有它 | 03 |
| 部署顺序 | RegistryV2 → LicenseV2 → RoyaltyV2：后两个依赖第一个的地址（构造函数注入） | 01、02 |
| immutable | Solidity 关键字：构造时赋值、之后不可改的变量 | 01 |
| ABI | 合约的"接口说明书"（函数签名、参数格式），前端/后端调用合约时用 | 02、05 |
| calldata / txRequest | 后端打包好的"待签交易数据"（发给谁、什么操作），钱包签名后发送 | 01、02、05 |
| signerMode | health 接口返回的标志：creator-wallet = 创作者钱包模式（后端零私钥的证明） | 02、04 |
| 水龙头 / faucet | 给任意地址充值测试币的接口（仅本地链 31337 放行） | 02、04 |
| chainId 31337 | Hardhat 本地链的网络编号——水龙头只在这个链上工作 | 02、04 |
| Hardhat | 以太坊本地开发环境：本地起一条链、部署合约、跑测试 | 02、06 |
| Solidity 0.8.20 | 合约语言版本：0.8 起内置溢出检查（防整数溢出攻击） | 01、04、07 |
| EVM | 以太坊虚拟机：合约代码的运行环境 | 05 |
| 重入攻击 | 合约收到钱的过程中被恶意合约反复回调抽钱——本系统**无转账逻辑**，攻击面天然不存在 | 07 |
| reorg | 区块链重组（公网上的小概率事件）：本地链不发生，公网需按确认数延迟入账 | 05、07 |
| 无特权角色 | 合约没有 owner 后门——平台自己也改不了记录（存证要的就是这个） | 07 |
| ecrecover | Solidity 内置函数：从签名反推出签名者地址——元交易的核心 | 03 |
| nonce | 序号：防同一签名被重复提交（重放攻击） | 03 |
| deadline | 截止时间：过期签名作废（防囤签） | 03 |
| 域分隔符 | 签名里包含 chainId + 合约地址：防跨链/跨合约重放 | 03 |
| 重放攻击 | 把别人签过的东西再提交一遍 | 03 |

## C. 哈希与密码学

| 术语 | 人话 | 出处 |
|---|---|---|
| 哈希 | 内容算出的固定长度"指纹"：同内容同指纹，改 1 字节指纹全变 | 01 |
| SHA-256 | 项目用的哈希算法（输出 32 字节） | 01、02 |
| 雪崩效应 | 输入改 1 比特，输出面目全非——所以"改 1 字节即检出" | 01、05 |
| 哈希三元组 | originalHash（原图）+ signedHash（签名版）+ manifestHash（声明）三个哈希，全部上链 | 01、02 |
| 四态验证 | 原始文件 / 官方签名版 / 签名后被篡改 / 无记录 四种验证结果 | 01、02、04 |
| manifest-only | 四态之一："文件被改了，但里面的声明还指向登记作品" | 02 |
| ECDSA | 以太坊用的数字签名算法：私钥签名、公钥验签 | 03、05 |
| ES256 | C2PA 用的签名算法（P-256 曲线的 ECDSA） | 01、02、05 |
| 签名权与支付权分离 | 元交易的核心思想：签名的人（创作者）不必是付 gas 的人（平台） | 03 |
| 非对称加密 / 公私钥 | 一对密钥：私钥签名、公钥验签；私钥泄漏 = 身份丢失 | 05 |

## D. C2PA 与信任链

| 术语 | 人话 | 出处 |
|---|---|---|
| C2PA | 内容真实性标准组织：定义"内容凭证"（谁声明、何时、如何创作） | 01、02、04 |
| manifest（内容凭证声明） | 一组断言 + 对内容的绑定 + 签名，嵌入文件内部 | 01、02 |
| JUMBF | manifest 在文件里的存放格式（JPEG 的元数据容器） | 01、02 |
| assertion | manifest 里的一条条"断言"（如：创作者地址、创作动作、originalHash） | 02 |
| hard binding | C2PA 对图像内容分块算哈希写入 manifest，验证时重算比对——改 1 字节即 Invalid | 02、04、07 |
| digitalSourceType | C2PA 2.1 起强制的字段（声明创作方式），缺失判 Invalid——项目踩过的兼容性坑 | 02、04、05 |
| c2patool | C2PA 官方命令行工具：签名（加 manifest）和验证 | 01、02 |
| untrusted / trusted | C2PA 验证签名的两种结论：不在信任列表内 = untrusted，在 = trusted | 01、02、04 |
| 自建 CA / demo CA | 用 openssl 自己建的证书体系（根证书 + 叶子证书）——等价于联盟场景的平台方 CA | 01、02 |
| trust anchor（信任锚） | 验证方信任的根证书——信任不是签名给的，是信任锚给的 | 01、02、05 |
| 证书 profile | C2PA 对签名证书的要求（如 EKU=emailProtection），不满足则不被认可 | 02 |
| PKI | 公钥基础设施：CA、证书链、信任锚这一整套体系 | 05、07 |

## E. 链下工程

|---|---|---|

| 幂等 / upsert | 同一操作重复执行结果一样（有则更新、无则插入）——重放安全 | 02、05 |
| SQLite / modernc.org/sqlite | 链下索引数据库；modernc 是纯 Go 实现（免 CGO，部署简单） | 02、05 |
| 链为准 | 设计原则：链是唯一真相源，索引可随时重建，验证失败时回退链上 | 02、04、07 |
| 里程碑 M1–M6 | 二期实施的 6 个阶段：合约 → 信任链 → 后端 → 前端 → 加分项 → 测试材料 | 02 |
| 验收标准 | 每个里程碑"怎么算做完"的明确标准（如：npm test 全绿） | 02 |
| E2E | 端到端测试：从用户入口到最终结果的完整流程自动化 | 02、04 |
| 回归 | 改动后把原有测试全部重跑，确认没改坏旧功能 | 02、04 |
| 覆盖率 / coverage | 测试执行到多少代码的度量（本项目行覆盖率 98.5%） | 02、04、07 |
| 攻击用例 | 故意测试"坏人操作"的用例（越权、抢注、篡改……必须被拒绝） | 02、04 |
| 单测 | 单元测试：单个函数/模块级别的测试 | 02 |
| gas 报告 | 每个合约操作的 gas 消耗统计（性能与成本的量化证据） | 02、04 |

## G. 时间戳、PDF 与加分项

| 术语 | 人话 | 出处 |
|---|---|---|

| TSA | 时间戳机构（项目用 freeTSA） | 02、04 |

| 汉明距离 | 两个二进制指纹不同的位数（≤10 触发相似预警） | 02、04 |
| 病态输入 | pHash 不适用的输入（纯噪声图、线性渐变图）——实验发现的适用边界 | 02、04 |
| 证据 PDF | 一键导出的存证报告：三哈希 + 双时间戳 + 二维码 + C2PA 信任状态 | 01、04 |
| UTF-8 / GBK | 字符编码：Windows 命令行工具按 GBK 发中文会污染数据（项目踩过的坑） | 02、04、05 |
