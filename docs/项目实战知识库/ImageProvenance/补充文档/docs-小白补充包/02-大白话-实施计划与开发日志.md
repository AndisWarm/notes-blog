## 一、先搞清楚这两篇文档是什么

| 文档 | 是什么 | 类比 |
|---|---|---|
| `03-实施计划` | 开工前的**计划书**：分几个阶段、每个阶段做什么、怎么算做完（验收标准） | 装修图纸 + 工期表 |
| `04-开发日志` | 干活时的**流水账**：每阶段实际做了什么、验证结果、踩了什么坑 | 施工日志 |

## 二、里程碑总览：M1–M6 在干什么

整个二期被切成 6 个里程碑（Milestone），**按依赖顺序排列**——后面的依赖前面的：

```text
M1 合约层（最优先，接口先冻结）
  → M2 C2PA 信任链（可与 M1 并行）
  → M3 后端改造
  → M4 前端重构
  → M5 加分项（时间不足可裁剪，从后往前裁）
  → M6 测试数据与论文材料
```

| 里程碑 | 一句话 | 做了什么 | 验收标准（怎么算做完） |
|---|---|---|---|
| M1 | 合约 V2 + 攻击性测试 | 4 个合约 + 20 个测试用例（含 5 组攻击用例） | `npm test` 全绿；第二个账户给他人作品发授权必须被拒 |
| M2 | C2PA 信任链 | openssl 自建 CA + 证书，签名从 untrusted 变 trusted | `c2patool verify` 显示签名可信 |
| M3 | 后端改造 | 删代签、加 prepare 接口、事件监听、SQLite 索引、四态验证 | 杀掉后端再重启，索引自动补齐漏掉的事件 |
| M4 | 前端重构 | 三个视图 + 钱包直发交易 + 四态结果页 | `npm run build` 通过；E2E 15/15 |
| M5 | 加分项 | PDF 升级、RFC3161 时间戳、pHash 相似预警、EIP-712 文档 | 各项实测成功 |
| M6 | 测试数据与论文材料 | 性能采集、攻击用例报告、演示脚本、README | 全量回归通过 |

> 注意 M1 的"接口先冻结"：合约一旦写完测试通过就**不改了**，因为后端、前端都依赖它。
> 这是工程上很常见的"先定接口，再分层实现"的做法。

## 三、开发日志里反复出现的几个概念（先看懂再读日志）

### 1. 事件监听 + 断点续扫（M3 的核心）

二期流程是：后端准备数据 → 用户钱包发交易 → **后端需要知道交易上链了**。
怎么知道？监听链上事件：

```text
用户钱包发交易 → 合约执行 → 发出事件（WorkRegistered 等）
                                          ↓
                            后端监听器每 2 秒拉一次新事件
                                          ↓
                              写进 SQLite 索引（镜像）
```

**断点续扫**：监听器记录"我已经处理到第几个区块"（游标，存在 `chain_cursor` 表）。
如果后端宕机 10 分钟，重启后从游标继续扫——宕机期间链上发生的事件自动补齐。

> 类比：快递员送快递，会记下"我送到第几号门牌了"，第二天接着送，不会从头再来。
> 这就是"链上链下数据一致性"的答案，也是答辩问题 20 的素材。

### 2. 状态机（M3）

后端给每个作品一条状态链（上篇讲过）：

```text
UPLOADED → SIGNED → PINNED → PENDING_ANCHOR → ANCHORED
```

- 每一步失败可以重试、可以查；
- PENDING_ANCHOR 表示"后端已准备好、等钱包上链"；
- 监听器看到链上事件后，把它翻成 ANCHORED。

### 3. 幂等（idempotent）

指"同一个操作做多次结果一样"。日志里说"镜像 upsert 幂等"：
如果同一个事件被处理了两遍，第二次不会产生重复数据（有则更新，无则插入）。
这保证断点续扫重放事件时数据不乱。

### 4. prepare 管道（M3）

`POST /api/works/prepare` 是后端的核心接口，一条串行管道：

```text
上传 → 算 originalHash → 查重 → 生成 manifest → pHash 相似预警
     → c2patool 签名 → 算 signedHash → trust 验证 → 算 manifestHash
     → IPFS 存储 → SQLite 入库 → 返回 txRequest{to, data, chainId}
```

最后返回的 `txRequest` 是给钱包用的"待签交易"——后端到此为止，不碰私钥。

## 四、开发日志里最重要的几条记录（每一条都是答辩/面试素材）

### 1. M1：防抢注、越权防护的诞生

- 合约加了 `hashIndex`（哈希→作品编号反查表），同一哈希只能注册一次；
- LicenseV2/RoyaltyV2 强制 `authorOf(workId) == msg.sender`；
- 20 个测试全过，覆盖率 98.55%。

**为什么值得记**：防抢注 + 防越权是这个系统"确权"叙事的核心证据。

### 2. M3：身份闭环实证——"链上 author = 创作者钱包"

日志原文："账户 #1（创作者，非部署者非后端）发交易 → 监听器 4s 内 ANCHORED，
**链上 author=0x7099...79C8=创作者钱包**（V1 致命缺陷修复实证）"。

**为什么值得记**：一句话证明了整个二期最大的改进是真的。

### 3. M5：pHash 的实验发现（论文素材）

pHash（感知哈希）用来做相似预警。但实验发现两类"病态输入"：
纯随机噪声图、逐像素渐变图——它们的 pHash 对微小修改极敏感（距离 20+），
而正常自然图像表现正常。已固化成单测。

**为什么值得记**：诚实记录了技术的适用边界，论文第 5 章可以写
"pHash 预警模块的适用性实验"，还反过来论证了"不做相似检索"边界收窄的合理性。

### 4. 两个用户报告的 bug（注意：这个系统真的有用户在用！）

| Bug | 现象 | 根因 | 修复 |
|---|---|---|---|
| 标题乱码 | 作品标题显示乱码 | Windows curl 按 GBK 编码发中文，后端当 UTF-8 入库 | 修数据 + 入口加 UTF-8 校验（非法直接 400） |
| 点"领取测试币"没反应 | 界面不刷新 | 充值 RPC 不改区块状态，MetaMask/ethers 以区块高度做缓存键，感知不到变化 | 充值后补挖一个空块 + 前端直读链上余额 |

**为什么值得记**：这是两个真实工程故事，面试讲"踩坑"时最有用——
现象 → 定位 → 根因 → 修复 → 沉淀，结构完整（docs/08 里的踩坑故事就来自这些）。

### 5. C2PA 前向兼容（重要教训）

新版 c2patool（0.27+，对应 C2PA 2.1 规范）把 `digitalSourceType` 字段从建议改为**强制**，
缺了直接判 Invalid。本机旧版本宽容通过，一旦升级全线爆红。修复：manifest 里补字段。

**为什么值得记**："依赖开放规范的系统必须跟踪规范演进"——这是论文"踩坑"章节的好素材。
