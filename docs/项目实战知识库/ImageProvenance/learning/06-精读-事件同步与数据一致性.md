# 06 精读:事件同步与数据一致性

**学习目标**:吃透 listener 的"游标断点续扫 + 幂等镜像"模式——这是全项目最有
**通用后端价值**的 60 行代码:换个皮就是 Kafka 消费者、binlog 同步、支付回调对账。
学完必须亲手复现"停机→上链→重启→自动补齐"。

**主文件**:`backend/internal/chain/listener.go` + `repository` 的游标/镜像方法。

## 6.1 问题定义

链上发生的事(登记、授权、撤销、状态变更)后端怎么知道?约束:
后端可能随时重启;事件绝不能丢(授权记录是给用户看的凭证);重复处理不能产生脏数据;
后端自己不发交易(V2 铁律),所以**监听是它感知链上世界的唯一途径**。

## 6.2 方案:把链当成仅追加的消息队列

```text
每 2 秒一轮 scanOnce:
  latest = 链上最新块高
  last   = chain_cursor 表里的游标
  if latest <= last: 无新块,睡
  logs = eth_getLogs(from=last+1, to=latest, address=[Registry, License])
  逐条 handleLog(按 topics[0] 分发)
  SaveProcessedBlock(latest)          ← 游标推进,持久化
```

四个事件的处理(handleLog 的 switch):

| 事件 | topics 里有什么 | data 里有什么 | 落库动作 |
|---|---|---|---|
| WorkRegistered | id、author(indexed) | 三个哈希 | MarkAnchored:按 originalHash 匹配本地行,回填 chainWorkId/author/txHash/block,状态→ANCHORED |
| LicenseGranted | id、workId、licensee | licensor、usage、validUntil | UpsertLicense(insert or update) |
| LicenseRevoked | id、workId | — | UPDATE revoked=1 |
| WorkStatusChanged | id | status(uint8) | SetChainStatus 按 chain_work_id 更新 |

对照第 02 章自测题 4:indexed 参数从 topics 恢复(`lg.Topics[1].Bytes()`),
非 indexed 用 ABI 从 data 解包(`UnpackIntoInterface`)。

## 6.3 三个关键性质及其来源(背下来,这是模式的精髓)

| 性质 | 靠什么保证 |
|---|---|
| **不丢** | 游标先处理后推进;重启从 last+1 继续,宕机期间的块照样扫到 |
| **不重(重放安全)** | 落库全部幂等:UpsertLicense 是 `ON CONFLICT DO UPDATE`;MarkAnchored/SetChainStatus 是按键 UPDATE——同一事件处理两遍结果不变 |
| **可重建** | 链是唯一真相源:把 SQLite 删了、游标归零,从创世块重扫即可完整重建索引 |

**思考题**:游标是"处理完一批才推进"——如果处理到一半崩了,下轮会重扫这一批,
哪个性质兜住了正确性?(答:幂等。**位点 + 幂等是一对,缺一不可**——只有位点没有幂等
会重复计数,只有幂等没有位点会全量重扫。)

**与业界对照**(面试就这么讲):Kafka 消费位点 ≈ chain_cursor;binlog/CDC ≈ 事件日志;
The Graph 索引器 ≈ 这个 listener 的工业级版本。你能讲出同构关系,这段代码就"值钱"了。

## 6.4 动手实验(必做):断点续扫复现

```powershell
# 1. prepare 一个新作品(网页或 curl),记下返回的 work.id 和 txRequest —— 不要点上链
# 2. 关掉后端窗口(Ctrl+C)
# 3. 后端死了,用钱包把这笔 txRequest 发出去(网页点"② 钱包上链确权"会失败——
#    因为页面靠后端;所以第 1 步后直接在 MetaMask 里确认,或用 e2e 脚本的发送逻辑)
#    最简单做法:第 1 步后立即点"②",MetaMask 弹窗先别确认 → 关后端 → 再确认
# 4. 交易上链成功(链不依赖后端!),此时链下谁都不知道
# 5. 重启后端,盯日志:数秒内出现 anchored: chainWorkId=N ...
# 6. 刷新前端,作品状态 ANCHORED,txHash/block 齐全
```

再做一个对照:后端运行期间用 sqlite 工具把 chain_cursor 的 last_block 改成 0,
观察日志把历史事件全部重扫一遍而数据没有变乱(幂等的直接证据)。

## 6.5 边界与展望(诚实清单,答辩/面试都用得上)

- **轮询 vs 订阅**:2s FilterLogs 简单可靠,延迟秒级;生产换 WebSocket `eth_subscribe`
  降到毫秒级,但要处理断线重连——游标机制不用改,这是该设计的可演进性;
- **链重组(reorg)**:本地链不会发生;公网上已入库的事件可能被重组掉——
  工业方案是"确认数延迟"(游标落后链头 N 块)或支持游标回退重扫,当前实现未做,
  说得出方案即可;
- **"no local row" 分支**:WorkRegistered 匹配不到本地行时只打日志(别人绕过后端
  直接调合约的作品,索引不认识但链上反查仍可验)——读 handleLog 确认这个分支,
  想想要不要为这类作品自动建行(设计讨论题,无标准答案)。
