# 08 实操:C2PA 与自建信任链

**学习目标**:脱离后端,徒手用 c2patool + openssl 复现本项目的信任链全流程:
造 CA → 签图 → 信任列表外/内两次验证 → 篡改检测。做完这章,`docs/07` 第 15–18 题
就是你的主场。

**前置**:第 03 章。工具:`tools/bin/c2patool.exe`(下文简写 c2patool)、Git Bash(openssl)。

## 8.1 读懂 make-ca.sh(先读脚本再运行)

`tools/ca/make-ca.sh` 五步,对应 PKI 教科书的最小闭环:

```text
1 genpkey EC P-256            → rootCA.key(根私钥)
2 req -x509 自签 10 年        → rootCA.pem(根证书:Issuer=Subject)
3 genpkey EC P-256            → sign.key(叶子私钥)
4 req + x509 -req 根签发 3 年 → sign.crt(叶子证书,带扩展)
5 cat 叶子+根                 → sign-chain.pem(签名时提交的完整链)
```

两个非显然细节(都有踩坑史):
- 扩展 `keyUsage=critical,digitalSignature` + `extendedKeyUsage=critical,emailProtection`
  ——**C2PA 证书 profile 的硬性要求**,少了 c2patool 拒收(EKU 用 emailProtection 是
  C2PA 规范沿用 S/MIME 类目的历史选择,不是笔误);
- 脚本里的 `MSYS_NO_PATHCONV=1`:Git Bash 会把 `-subj /C=CN/...` 当路径改写(docs/04 M2 踩坑)。

**动手**:在 /tmp 下把这五步**手敲一遍**(别用脚本),造一套自己的 CA。
敲完对比:`openssl verify -CAfile 你的根.pem 你的叶子.crt` → OK。

## 8.2 签名:manifest 定义文件怎么写

后端生成的 manifest 定义(BuildToolManifest 的输出)骨架:

```json
{
  "claim_generator": "ImageProvenanceV2/0.1",
  "title": "作品标题",
  "alg": "es256",
  "private_key": "<绝对路径>/sign.key",
  "sign_cert": "<绝对路径>/sign-chain.pem",
  "assertions": [
    { "label": "c2pa.actions",
      "data": { "actions": [{ "action": "c2pa.created",
                              "when": "2026-07-26T12:00:00Z",
                              "digitalSourceType": "http://cv.iptc.org/newscodes/digitalsourcetype/digitalArt" }] } },
    { "label": "stds.schema-org.CreativeWork",
      "data": { "@context": "https://schema.org", "@type": "CreativeWork",
                "name": "作品标题",
                "author": [{ "@type": "Person", "name": "0x钱包地址", "identifier": "0x钱包地址" }],
                "identifier": "0x<originalHash>" } }
  ]
}
```

三个考点:`digitalSourceType` 是 C2PA 2.1 强制字段(缺它 0.27+ 判 Invalid——
本项目真实修过的前向兼容缺陷);`identifier` 嵌 originalHash 是链上链下互指的关键;
证书路径必须绝对路径(c2patool 相对 manifest 文件解析,后端启动时 filepath.Abs 处理)。

**动手**:
```bash
c2patool 任意.png -m 你的manifest.json -o signed.png -f
```

## 8.3 验证:信任列表外 vs 内(本项目的招牌对照实验)

```bash
# ① 默认验证(你的根不在任何信任列表里)
c2patool signed.png | grep -E "validation_state|untrusted"
#   → signingCredential.untrusted / validation_state 非 Trusted

# ② 加载自己的根做 trust anchor
cp 你的rootCA.pem trust-anchors.pem     # 与资产同目录(Windows 路径坑的规避,见 c2pa/tool.go 注释)
c2patool signed.png trust --trust_anchors trust-anchors.pem | grep validation_state
#   → "validation_state": "Trusted"
```

同一张图、同一个签名,结论由**验证方信任谁**决定——这就是 PKI 的核心思想被 C2PA 复用。
项目的对照证据存于 `reports/test-results/c2pa-trust-comparison.md`,和你现在做的一致。

## 8.4 篡改检测(hard binding 亲手触发)

```bash
python -c "
d = bytearray(open('signed.png','rb').read())
d[-20] ^= 0xff                      # 尾部翻一个字节(避开文件头与 manifest 块)
open('tampered.png','wb').write(bytes(d))
"
c2patool tampered.png trust --trust_anchors trust-anchors.pem | grep -E "validation_state|hash"
# → Invalid + assertion.dataHash.mismatch 一类的失败码
```

再把 tampered.png 传给系统 `/api/works/verify-file`(若该图走过登记流程):
后端提取幸存 manifest 里的 identifier 反查 → **manifest-only(签名后被篡改)**。
至此四态验证的最后一块拼图(第 05 章 5.3)你已亲手造过。

## 8.5 读一份完整验证报告

```bash
c2patool signed.png trust --trust_anchors trust-anchors.pem > report.json
```
在 report.json 里找到并理解:`claim_generator`、两条 assertions、
`signature_info`(算法/证书主体)、`validation_results` 里的 success 数组
(signingCredential.trusted、claimSignature.validated、assertion.hashedURI.match×N、
assertion.dataHash.match)——后端的 `ValidationState()` 解析的就是这份 JSON 的
`validation_state` 字段(c2pa/tool.go,含"非 JSON 前缀行"的正则兜底)。
