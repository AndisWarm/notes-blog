# 04 精读:智能合约层

**学习目标**:逐函数吃透四个合约(共约 300 行),能讲出每个 `require` 存在的理由;
跑通并读懂 20 个单测。合约是全系统的"宪法",这章是 L2 深度的分水岭。

**读法**:开两个窗口——左边合约源码,右边对应测试文件;每读一个函数就找到测它的用例。

## 4.1 IRegistry.sol(10 行,先读它)

只有两个方法:`authorOf(workId)` 和 `workExists(workId)`。
**设计问题**:License/Royalty 为什么依赖这个接口而不是直接 import RegistryV2?
——面向接口的最小依赖:License 只需要"谁是作者"这一个事实,不需要知道 Registry 的
全部实现;部署时注入地址(构造函数 `require(registryAddr != 0)`),测试时也容易替换。

## 4.2 RegistryV2.sol(核心,逐段读)

### 数据结构
```solidity
Work { id, author, originalHash, signedHash, manifestHash, imageCid, manifestCid, createdAt, status }
mapping(uint256 => Work) works          // id → 作品
mapping(bytes32 => uint256) hashIndex   // 任意一个哈希 → id(0 = 不存在)
enum WorkStatus { Active, Disputed, Revoked }
```

### registerWork:五个 require 各自防什么

| require | 防什么 |
|---|---|
| 三个哈希非零、两个 CID 非空 | 垃圾数据占用索引位(bytes32(0) 会撞索引默认值) |
| `hashIndex[originalHash] == 0` | **防抢注**:同一原图不可二次登记 |
| `hashIndex[signedHash] == 0` | 防拿别人的签名版哈希登记 |
| `hashIndex[manifestHash] == 0` | 防拿别人的声明哈希登记 |

关键行:`author: msg.sender` ——不是参数传入,是从交易签名恢复的,**伪造不了**。
这一行就是整个 V2 身份闭环(对照第 02 章 2.2)。

**思考题**:为什么 id 从 1 开始(`++workCount`)而不是 0?
(答:`hashIndex` 用 0 表示"不存在",id=0 会与之冲突——mapping 默认值语义,Solidity 常见坑。)

### getWorkByHash:验证不依赖链下库的关键

任何一个哈希 → hashIndex → 完整 Work。第 05 章你会看到后端 verify 在数据库 miss 时
就调它兜底;把 `backend/data/index.db` 删了验证照样工作,底气全在这个函数。

### setStatus:标记而非删除

仅作者可调(`works[id].author == msg.sender`),枚举三态,发 `WorkStatusChanged` 事件。
**为什么没有 deleteWork?**——链上数据本就不可删,与其提供假删除,不如提供带历史的状态标记;
Revoked 表达"作者收回声明"但记录仍在,这符合存证系统的语义。

## 4.3 LicenseV2.sol

### grantLicense 的 require 清单(对照单测逐个触发过才算学会)

```solidity
workExists(workId)                → "work not found"(幽灵作品)
authorOf(workId) == msg.sender    → "not author"(越权,核心防线)
licensee != address(0)            → "licensee required"
bytes(usage).length > 0           → "usage required"
validUntil > block.timestamp      → "invalid expiry"
```

### isLicensed:为什么是遍历而不是 mapping?

`licensesByWork[workId]` 数组线性扫描,检查 `licensee 匹配 && !revoked && 未过期`。
**权衡讨论**(好面试素材):mapping(workId→licensee→bool) 查询 O(1) 但表达不了
"多笔授权、各自期限、可单独撤销";数组方案表达力完整,代价是 gas 随授权数线性增长——
在"单作品授权数有限"的业务假设下成立。追问"如果一个作品十万笔授权怎么办"的答案:
链下索引(licenses 表)承担规模化查询,链上 isLicensed 服务合约间调用。

### revokeLicense:谁能撤?

`rec.licensor == msg.sender`——是**授权人**(签发者)而非作品作者。思考:这两者什么时候
不同?(作品转让后……本项目没有转让功能,所以当前恒相同,但字段语义是按"签发者"设计的。)
`!rec.revoked` 防重复撤销事件污染。

## 4.4 RoyaltyV2.sol

- 基点制:`creatorShareBps + platformShareBps == 10000` 强制等式——用整数基点而非
  百分比浮点(EVM 无浮点,金融字段用最小单位整数是行业惯例)。
- 覆盖式更新:同 workId 再次 setRoyaltyRule 直接覆盖 + 事件。**已知取舍**:链上只有
  最新规则,历史要靠 RoyaltyRuleSet 事件回放(这是 learning/10 的练习一)。
- `hasRule` + `getRoyaltyRule`(无规则 revert)配对:前端先 hasRule 再 get,
  避免用 try/catch 控制流程。

## 4.5 MockJudicialAnchor.sol

只 emit 事件不存储——**接口占位**:证明系统预留了司法锚定的调用形态,同时诚实保持
"不接真实司法链"边界。读一遍即可。

## 4.6 动手实验

```powershell
cd contracts
npm test                 # 20 个用例,读 test/*.test.js,把每个用例名和合约 require 连线
npx hardhat coverage     # 看哪些分支没覆盖到(答案:几乎没有,98.4% 分支覆盖)
```

**实验 A(触发每一个 revert)**:在 Hardhat console(`npx hardhat console --network localhost`)
里手动调用 grantLicense,把 4.3 清单里五个 revert 逐个触发一遍,截图留档。

**实验 B(改坏它)**:把 RegistryV2 里 `author: msg.sender` 改成
`author: tx.origin`,跑 `npm test` 看什么用例挂(然后查一下 tx.origin 钓鱼攻击,
理解为什么永远用 msg.sender)。**改完记得 git checkout 还原。**

**实验 C(加字段走全流程)**:给 Work 加一个 `string note` 字段,体验改一处
牵动多少地方(struct、registerWork 参数、事件、测试、后端 ABI 打包……)。
不要求做完,做到"知道会牵动哪里"即可还原——这个体感是 L3 的门票。
