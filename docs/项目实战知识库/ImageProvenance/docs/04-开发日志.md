## 2026-07-26 缺陷修复：作品标题乱码（用户报告）

**现象**：前端作品列表中 work #4 标题显示为乱码（用户截图 乱码.png），其余中文均正常。

**根因**：该记录是 M5 测试时用 **Windows curl 命令行**上传的——curl 把命令行参数按本地编码（GBK）发送，
后端将 GBK 字节（`\xd6\xd0\xce\xc4...`）当作 UTF-8 原样入库，属于**测试数据污染**，非前端/字体问题。
浏览器 FormData 强制 UTF-8，正常使用不会触发。

**修复（三层）**
1. 数据修复：SQLite 中 work #4 标题按 GBK→UTF-8 转码，显示恢复"中文标题测试·相似图"；
2. 后端防御：`Prepare` 增加 `utf8.ValidString(title)` 校验，无效 UTF-8 直接 400 拒绝（错误信息提示 Windows curl 的 GBK 编码问题），杜绝坏数据入库和嵌入 C2PA manifest；
3. 回归验证：UTF-8 multipart 上传中文标题"风景写生·测试作品"往返一致；GBK 字节标题被 400 拒绝。

**教训（论文/使用文档素材）**：跨编码边界（命令行 → HTTP → SQLite → 前端）必须在入口做 UTF-8 有效性校验；
Windows 命令行工具（curl、openssl -subj、ipfs config）是本项目三次编码/路径踩坑的共同来源。

  交易完成后自动刷新余额（useWallet.refreshBalance）。

## 2026-07-26 缺陷修复：点击"领取测试币"没反应（用户报告）

**排查过程**：后端日志显示 5 次 `POST /api/chain/faucet` 全部 200，Hardhat 日志确认 `hardhat_setBalance`
每次都执行——**钱实际到账了，但界面刷不出来**。

**根因**：`hardhat_setBalance` 直接改状态、**不产生新区块**；MetaMask 与 ethers 都以区块高度作为
余额查询的缓存键，链上没有新块就认为状态没变，`eth_getBalance` 一直返回缓存的 0。
体感即"点了没反应"。

**修复（三处）**
1. 后端 faucet 充值后补发 `evm_mine` 挖一个空块（区块号推进 → 击穿钱包缓存），实测 20→21；
2. 前端充值成功后显示绿色到账提示，余额数字直接取自后端链上读回的 `balanceWei`，不再依赖
   MetaMask 的缓存刷新；faucet 日志打印地址与到账余额，便于后续排查；
3. 顺带修复排查中发现的问题：work #20（猪八戒）`author_address` 为空——prepare 原先不强制连接钱包。
   现 CreatorView 在"① 生成声明与签名"前强制要求连接 MetaMask，作品声明必须绑定创作者地址。

**教训**：本地开发链的"作弊型" RPC（setBalance/evm_mine）不走出块流程，任何依赖区块高度做缓存的
客户端（MetaMask、ethers Provider）都感知不到状态变化；改状态后必须手动推进区块。

## 2026-07-26 功能补齐:链上 Disputed/Revoked 状态镜像到链下索引与前端

  `pragma_table_info` 防重入 ALTER,旧库无损迁移(既有数据库实测,历史行默认 0)。
