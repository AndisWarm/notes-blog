# 一期（ImageProvenance_bak）设计与实现审查报告

> 审查对象：`ImageProvenance_bak/`（已跑通的一期实现：Go/Gin 后端 + Vue 3 前端 + Hardhat 合约 + Kubo/IPFS + c2patool + PDF 报告）
> 参照文档：`ImageProvenance/docs/` 下开题报告、毕设方案、学习路线、开题审查结果
> 审查日期：2026-07-26
> 目的：找出一期在设计与实现层面的短板，作为二期（本项目）改进的依据

## 一、一期已达成的部分（应当保留）

- **主闭环完整**：上传 → SHA-256 → Manifest 生成 → c2patool 签名 → IPFS 存储 → Registry 上链 → 查询 → 精确哈希验证 → PDF 取证报告，全链路可运行。
- **工程配套齐全**：一键启动脚本、健康检查、性能/Gas 采集脚本（`collect-performance.ps1`）、测试结果沉淀到 `reports/`。
- **边界纪律好**：不做 AI 检测、不做相似检索、不接真实司法链、不做代币，与开题口径一致。
- **工具链落地**：Windows 下用 c2patool 预编译二进制 + Kubo 本地节点，避开了 node-gyp/abigen 的坑，与审查结果建议一致。

以上是二期的地基，**不推翻，只升级**。

## 二、发现的问题（按答辩风险排序）

### 问题 1（P0，致命）：链上作者身份失真——"确权"叙事被打穿

**证据**：
- `backend/internal/chain/registry.go`：`RegistryClient` 持有后端配置的 ECDSA 私钥（Hardhat demo key），所有 `registerWork` 交易由后端代签。
- `contracts/Registry.sol:39`：`author: msg.sender` —— msg.sender 恒为后端热钱包地址。
- `web/src/App.vue`：MetaMask 集成只做了 `eth_requestAccounts` 展示账户，**不参与任何签名或交易**。

**后果**：链上所有作品的 author 都是同一个后端地址。答辩追问"链上作者地址是谁的？"——回答只能是"是后端服务器的"，整个"创作者确权"立论瞬间垮塌，且与开题报告承诺的"作者地址写入存证合约"直接矛盾。

**这是一期最大的结构性缺陷，二期必须优先解决。**

### 问题 2（P0）：C2PA 哈希语义未落地——开题审查待办 #1 仍然悬空

开题审查结果（第五节待办 1）明确要求：区分"原图哈希"与"签名后图哈希"（c2patool 会把 manifest 嵌入 JPEG 的 JUMBF box，产生一个新文件、新 SHA-256）。一期合约只有 `imageHash` 一个字段，语义不明：
- 用户拿到的是**签名后的图**（系统分发的），拿它验证时算出的哈希与链上锚定的原图哈希不一致 → "上传原图查不到、上传签名图才查到"（或反过来）的自打脸场景在演示中随时可能出现。
- C2PA 内部本身有 hard-binding 哈希，与链上锚定哈希的关系没有任何文档或字段说明。

### 问题 3（P0）：三份合约互相孤立，权限形同虚设

- `License.sol`：`grantLicense` 只检查 `workId > 0`，**不校验作品是否存在、msg.sender 是否为作品作者**。任何地址可以给任何（甚至不存在的）作品签发授权。
- `Royalty.sol`：`setRoyaltyRule` 同样任何人可对任何 workId 设置分账规则，还能随意覆盖别人已设的规则。
- 答辩演示"越权授权"一试就破：评委用另一个账户给你的作品发授权，系统照单全收。

### 问题 4（P1）：Registry 缺少哈希反查与防重复注册

- 合约无 `mapping(bytes32 => uint256)` 反查索引：链上无法由哈希直接查作品，验证完全依赖链下数据库——链下库一丢，"链上可验证"就名存实亡。
- 无重复检测：同一张图任何人可以再注册一次（抢注）。这恰恰是"确权"系统最应该防的第一件事。

### 问题 5（P1）：C2PA 签名停留在 untrusted 开发证书

README 自己承认 `signingCredential.untrusted` 是"预期边界"。但一期没有做任何信任链建设（自建 demo CA、配置 c2patool trust anchor），验证结果永远是"签名不可信"，演示效果打折，也浪费了 C2PA 这个最大创新点的说服力。

### 问题 6（P1）：后端没有链上事件监听，链下索引一致性靠祈祷

- `chain/registry.go` 只有发交易逻辑，无 `FilterLogs`/`SubscribeFilterLogs`。开题报告承诺的"监听链上事件并同步到链下索引库"没有实现。
- 上传→IPFS→上链→入库 的多步流程没有状态机：任何一步失败就产生"文件已传但链上没有 / 链上有但库里查不到"的悬挂状态，这正是开题报告"拟解决的关键问题二"，一期未解决。

### 问题 7（P2）：前端 995 行单文件 App.vue

无路由、无组件拆分、无角色分区（创作者/使用方/验证方视图混在一页）。作为论文里"前端模块设计"一节的支撑材料太弱，也不利于演示分角色故事线。

### 问题 8（P2）：承诺过但缺失的加分项

- RFC3161 链下时间戳双锚定（毕设方案 4.4 承诺"双锚定"）——未实现。
- pHash 相似预警小模块（开题审查判断三建议的 P1 加分项，对标李林逸 2024）——未实现。
- 攻击性测试用例（重复注册、越权授权、篡改图验证失败）——测试只覆盖正常路径。

---

## 三、结论

一期证明了技术闭环可行，但当前形态**过不了一场认真追问的答辩**：身份失真（问题 1）+ 越权授权（问题 3）+ 哈希语义含糊（问题 2）三个问题两三个追问就能连环引爆。二期不需要扩大功能面，而是把"确权"两个字做实：

1. 让创作者钱包成为链上作者（身份闭环）；
2. 把哈希语义定义成可验证的三元组并支持链上反查（验证闭环）;
3. 让合约之间互认并校验权限（授权闭环）;
4. 建立 demo 信任链让 C2PA 验证从 untrusted 变 trusted（信任闭环）。
