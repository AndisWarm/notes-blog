## 一、选题与边界

### 1. 为什么做这个课题?它解决什么真实问题?

【30 秒口径】数字图像复制零成本、传播无痕迹,创作者面临"作品是我的,但我证明不了"的困境。
本系统把三件事组合成一个可验证闭环:**内容指纹上链**(不可篡改的时间锚定)、
**C2PA 签名嵌入文件**(作者声明随文件流转)、**授权关系上链**(谁授权给谁、何时到期可查可撤)。
产出的是"声明 + 记录 + 技术取证材料",服务于事前存证和事后举证。

【追问防御】"取证材料"是关键措辞——系统不判定版权归属,归属判定是司法的事。

### 2. ⚠ 链上记录能证明版权吗?有人偷图抢先注册怎么办?

【30 秒口径】不能,而且我在页脚和论文里都明确写了 **GIGO 边界:链上记录不能证明上链前
内容的真实性**。系统证明的是"某人在某时刻持有该文件并作出声明"。对抢注,系统做了三层缓解:
① 三哈希链上查重,同一文件不可能二次登记(实测后端 409 + 合约 revert 双拦截);
② pHash 相似预警,近似图上传时提示可能重复;③ 真实纠纷中,先创作者往往能出示原始工程文件、
更早的 RFC3161 时间戳等,本系统的证据 PDF 是呈堂材料之一而非唯一依据。

【追问"那系统价值何在"】把举证成本从"什么都拿不出"降低到"有链上时间锚 + 可信第三方时间戳 +
内容完整性证明"的水平;这与版权局登记、公证处存证是同一逻辑,只是技术化、自动化了。

### 3. 为什么不做 AI 生成检测 / 相似图像检索?

【30 秒口径】这是开题时明确收窄的研究边界。AI 检测与以图搜图各自是独立的大课题,
且与"确权存证"的技术闭环正交。我保留了 pHash 相似**预警**(链下、只提示不拦截),
并在实验中发现了它的适用边界——纯噪声图和线性渐变图是 DCT pHash 的病态输入,微小修改就产生
20+ 距离,而自然图像特征的图表现正常。这个实验反过来佐证了"不做相似检索"收窄的合理性,
写进了论文第 5 章。

## 二、架构与技术选型

### 4. 为什么要用区块链?数据库 + 时间戳不行吗?

【30 秒口径】三点数据库给不了:① **防篡改的公开时间锚**——记录一旦上链,运营方自己也改不了,
数据库管理员可以;② **验证不依赖平台存活**——我做了链上 `hashIndex` 反查,把本地数据库删了,
拿文件哈希直接问合约照样能验(演示过"链上反查"路径);③ **权限由合约强制**——授权、分账、
状态标记都经 `authorOf` 校验,越权在共识层被拒,不是应用层的 if 判断。

【追问"那你还要 SQLite 干嘛"】定位是**缓存加速器**:列表、详情、授权记录的毫秒级查询(实测 3ms)。
真相源永远是链,索引通过事件监听可完整重建。

### 5. 为什么引入 C2PA?哈希上链不就够了吗?

【30 秒口径】哈希解决"这份文件是否登记过",C2PA 解决"文件离开平台之后"的问题——
作者声明、创作时间、创作者地址被**签名后嵌入文件内部**(JUMBF 容器),文件传到哪,声明跟到哪;
第三方用标准工具就能验,不需要访问我的系统。两者互补:链管时间与权属关系,C2PA 管内容与
声明的绑定。还有一个关键联动:C2PA manifest 里嵌了 originalHash,篡改文件后哈希全变,
但幸存的 manifest 还指向登记作品——这就是四态验证里"签名后被篡改"态的实现原理。

### 6. 为什么本地链演示、不上主网/测试网?

【30 秒口径】研究边界 + 演示可控性。架构本身是链无关的:RPC 地址、部署文件都是配置项,
水龙头接口做了 chainId 31337 检查,连公共测试网时自动失效、改用公共水龙头。
换句话说,换一个 RPC URL 加一次部署就能上 Sepolia,不需要改任何业务代码。

### 7. 技术栈为什么是 Go + Vue + Hardhat?

【30 秒口径】Go:静态编译单二进制、并发模型适合事件监听长任务,modernc.org/sqlite 纯 Go
免 CGO 部署简单;Vue 3 组合式 API + ethers v6 是轻量的 dApp 前端组合,合约地址与 ABI 从
`/api/chain/info` 动态拉取,前端零硬编码;Hardhat 是以太坊事实标准开发环境,测试、覆盖率、
gas 报告工具链完整。

## 三、身份闭环(V1→V2 核心改进,大概率被问)

### 8. 一期后端代签有什么问题?二期怎么解决的?

【30 秒口径】一期后端持热钱包私钥代用户发交易,导致链上 `author` 恒为服务器地址——
确权系统里"作者"字段是假的,这是致命缺陷,而且私钥集中在后端是单点安全风险。
二期把流程拆成两段:后端只做链下重活(三哈希、C2PA 签名、IPFS)并打包 calldata 返回,
**交易由创作者自己的钱包签名发送**,合约里 `author = msg.sender`。后端从头到尾没有任何
链上私钥——`/api/health` 里 `signerMode: creator-wallet` 就是这个标志。

【追问"后端会不会伪造 calldata 骗用户签"】问到这个说明评委很内行。诚实回答:用户钱包里
能看到目标合约地址和数据,MetaMask 会解码方法名;更根本的防线是**登记这个动作对用户只有收益
没有转账**——registerWork 不转移任何资产,最坏情况是登记了错误哈希,用户可当场验证。
这类"交易透明度"问题的彻底解法是前端本地重算哈希与 calldata 比对,可作为展望。

### 9. 用户没有钱包/不会用 MetaMask 怎么办?

【30 秒口径】这是去中心化身份的固有门槛,我做了两级缓解:演示环境有本地水龙头,任何自有账户
一键充值测试币;更根本的方案我写了 **EIP-712 元交易设计文档**(docs/05)——用户只用钱包
离线签名结构化消息,gas 由平台中继代付,`registerWorkWithSig` 用 ecrecover 恢复真实作者。
这保住了"签名权在用户"的本质,同时把 gas 门槛移走,和一期代签有本质区别:代签是身份伪造,
元交易是**签名权与支付权分离**。设计做了三层防重放(nonce、deadline、chainId),留作展望未实现。

### 10. 为什么锚定三个哈希而不是一个?贵了多少?

【30 秒口径】原图、C2PA 签名版、声明文件各是独立字节流,单哈希只能验其中一个形态。
三哈希让"原始文件、官方分发版、声明"都能独立命中,配合 `hashIndex` 反查支撑四态验证。
成本是实测的:registerWork 约 41.3 万 gas,比单哈希方案贵约 10 万(+32%),换来链上反查、
防抢注和四态验证三个能力——论文里我把这笔账算成了一张表。

## 四、合约设计

### 11. 越权防护是怎么实现的?测过吗?

【30 秒口径】LicenseV2 / RoyaltyV2 构造时注入 IRegistry 接口,grantLicense、setRoyaltyRule、
setStatus 第一行就是 `require(registry.authorOf(workId) == msg.sender, "not author")`。
测试三级覆盖:合约单测有 6 组攻击用例(非作者授权/改分账/改状态、幽灵 workId、重复哈希、
撤销过期后 isLicensed);E2E 用两个真实账户实测越权 revert;前端把 revert 原因翻译成中文
提示。攻击用例报告在 `reports/test-results/attack-cases.md`。

### 12. 授权为什么不做成 NFT?分账为什么不做真实支付?

【30 秒口径】刻意的边界。确权 ≠ 资产化:本课题的授权是"许可关系记录"(被授权方、用途、
期限、可撤销),LicenseRecord + isLicensed 已完整表达,NFT 的可转让性反而引入
"授权被二次转卖"这类本课题不处理的法律语义。分账同理——RoyaltyV2 记录比例(基点制,
总和强制 10000),真实支付涉及代币合规问题,超出毕设范围;展望里给了 splitter 合约方案。

### 13. 合约安全考虑了哪些?重入呢?

【30 秒口径】本系统合约**无转账逻辑**,没有以太进出,重入攻击面天然不存在;
Solidity 0.8.20 内置溢出检查;所有外部输入有 require 校验(零地址、空串、过期时间、
份额总和);状态标记是追加式的,不删除任何历史。覆盖率 98.5%,分支覆盖 98.4%。

【追问"为什么不上形式化验证/审计"】规模判断:四合约共 300 行内,穷举式单测 + 攻击用例
性价比更高;真实生产部署前应做第三方审计,写在展望。

### 14. setStatus 的 Disputed/Revoked 是干什么的?链下怎么知道?

【30 秒口径】给作者一个链上表态通道:作品陷入争议可标 Disputed,确权声明想收回可标 Revoked,
记录不删除(链上也删不掉)。链下通过监听 `WorkStatusChanged` 事件镜像进索引,
授权管理页有作者操作入口和状态徽标,来源验证页对非正常状态作品显示红色警示——
验证方在引用作品前能看到权属风险。整条链路(标记→事件→镜像→警示)有 5 个专项用例覆盖,
同步延迟实测 ≤3 秒。

## 五、C2PA 与密码学

### 15. 自建 CA 有什么意义?为什么不用 c2patool 自带的开发证书?

【30 秒口径】开发证书永远验出 `signingCredential.untrusted`,等于"签了但没人信"。
我用 openssl 自建了符合 C2PA 证书 profile 的 CA(EC P-256 根证书 + ES256 叶子证书,
KU=digitalSignature、EKU=emailProtection 均为 critical),再把根证书配置为 c2patool 的
trust anchor——同一张图,信任列表外验出 untrusted,列表内验出 **Trusted**,这组对照
(`reports/test-results/c2pa-trust-comparison.md`)恰好演示了 C2PA 信任模型的工作原理。
生产环境的对应物是向 C2PA 信任列表成员 CA 申请证书,机制完全一致。

### 16. 篡改 1 个字节为什么能被发现?

【30 秒口径】C2PA 的 hard binding:签名时对图像数据分块计算哈希写入 manifest,验证时重算比对。
改 1 字节 → 数据哈希不匹配 → `validation_state: Invalid`;同时文件的 SHA-256 全变,
链上三哈希都不命中;但 manifest 里嵌的 originalHash 还在,反查得到登记作品——
于是系统给出精确结论:"这是登记作品 #N 被篡改后的版本",而不是笼统的"验证失败"。

### 17. ⚠ 截图/微信压缩后还能验证吗?

【30 秒口径】不能,而且这是诚实声明过的边界。截图和有损压缩是破坏性处理:像素重编码导致
哈希全变,C2PA 元数据也被剥离,系统会给出"无记录"态,并在文案里解释了原因。
pHash 预警可以在**登记侧**提示近似图,但**验证侧**的相似检索是刻意不做的
(见第 3 题)。这也是 C2PA 生态自身的公开难题(内容凭证的存活性问题)。

### 18. digitalSourceType 是什么?(或:你们 C2PA 版本兼容性怎么处理的?)

【30 秒口径】这有个真实的工程故事:C2PA 2.1 规范(c2patool 0.27+)把 `c2pa.created`
动作的 `digitalSourceType`(IPTC 数字来源类型词表)从建议改成强制,缺失直接判 Invalid。
我在 0.27.3 环境做独立回归时全线爆红,定位后在 manifest 里补了
`digitalsourcetype/digitalArt`(人类用数字工具创作),新旧版本双验通过。
这个案例说明依赖开放规范的系统必须跟踪规范演进——写进了论文踩坑一章。

### 19. 为什么要 RFC3161 时间戳?区块时间不够吗?

【30 秒口径】双时间锚互补:区块时间戳在本地/联盟链场景公信力有限,公链上也存在矿工可
小幅操纵的理论空间;RFC3161 是独立第三方(freeTSA)对 manifest 哈希的签名时间证明,
司法实践中接受度高。两个时间源相互印证,任一方被质疑另一方仍然成立。TSA 不可达时优雅跳过,
不阻塞登记。

## 六、数据一致性与工程实现

### 20. 链下数据库和链上不一致怎么办?后端宕机会丢事件吗?

【30 秒口径】不会丢。监听器用**游标断点续扫**:每轮 FilterLogs 处理完把区块高度持久化,
重启从游标继续,宕机期间的事件自动补齐——这个场景我做过实测:停掉后端、钱包上链、重启后端,
作品数秒内自动补到 ANCHORED。设计原则是"链为准":索引任何时候都可以从创世块重扫重建,
verify 接口在索引 miss 时还会实时回退链上 `getWorkByHash`。

### 21. 性能如何?瓶颈在哪?

【30 秒口径】prepare 全程 799ms:C2PA 签名 250ms、IPFS pin 5ms、RFC3161 约 450ms(可关);
上链 138ms(本地链,公网看出块时间);事件同步 ≤3s(2s 轮询间隔的期望内);验证查询 3ms
(SQLite 索引命中)。瓶颈是外部 TSA 网络往返,其次是 c2patool 进程调用,都在链下、可并行化。
10 轮采集数据在 `reports/test-results/performance-table.md`。

### 22. 测试是怎么做的?

【30 秒口径】四层:① 合约单测 20 用例(含 6 组攻击用例),语句覆盖 98.2%、分支 98.4%;
② 后端 Go 单测(仓储三级查找、C2PA 解析、pHash 边界);③ 全链路 E2E 15 用例 +
状态/授权/分账专项 22 用例 + 边界扩展 31 用例,双账户覆盖正反路径;④ 独立环境云端回归:
在隔离沙箱从源码复刻全套环境重跑全部用例,76/76 通过,gas 与本机误差 <0.01%——
排除了"只在我机器上能跑"的可能。

### 23. (若被问到)云端回归里链是怎么来的?

【30 秒口径】沙箱无法安装 Hardhat,我用 go-ethereum v1.16.7 的 EVM 内核构建了等价开发链:
chainId 同为 31337、同一组测试账户、支持 evm_increaseTime 等测试 RPC。等价性有两个锚点:
四个合约的部署地址与本机 Hardhat 逐一相同(CREATE 地址由部署者地址+nonce 决定),
registerWork gas 412,516 对本机 412,528。这本身也验证了系统的链无关性。

## 八、灵魂拷问

### 24. ⚠ 和阿里云/腾讯的版权存证服务比,你的意义是什么?

【30 秒口径】技术路线同源(哈希上链 + 可信时间戳),差异在三点:① 商业服务是黑盒,
本系统全链路开放可审计,包括密钥在谁手里(答案:后端零私钥,签名权在创作者)——这恰是
确权系统最该被审计的部分;② 引入 C2PA 开放标准,声明嵌入文件跟随流转,不锁定在单一平台;
③ 作为研究,我完成了从威胁建模(抢注、越权、篡改、身份伪造)到防御实现到攻击性测试的完整
论证,这是使用商业 API 得不到的。

### 25. 项目工作量和难点在哪?哪些是你独立完成的?

【30 秒口径】(按实际情况作答,以下是事实清单)四个合约与 20 个单测;后端 9 个模块
(prepare 管道、事件监听、三级验证、C2PA 集成、PDF、pHash、TSA);前端三视图与两个
composable;openssl CA 工具链;四套自动化测试脚本;两期架构的重构论证。
最难的三处:① 身份闭环重构——把"后端代签"改成"钱包直发"牵动合约、后端、前端全链路;
② c2patool 集成的工程细节(证书路径解析、Windows 路径被当 URL、trust anchor 加载);
③ 链下链上一致性(事件驱动 + 游标 + 幂等 upsert)。

### 26. 如果重做一次,你会改什么?

【30 秒口径】三点:① 元交易(EIP-712)应该进主线而不是展望——钱包门槛是真实拦路虎;
② 事件监听会用 WebSocket 订阅替代轮询,同步延迟从秒级到毫秒级;③ 测试脚本从第一天就
以"链上时间"为基准而不是墙钟(踩过 evm_increaseTime 的坑)。这题答"有具体反思"远好于
答"没什么要改"。

### 27. 系统的局限性总结(主动亮出,常有此环节)

【口径】五条,对应五个边界:链上记录不证明上链前真实性(GIGO);破坏性处理后无法验证
(不做相似检索);授权与分账是记录不是执行(不做支付);司法锚定是接口演示(Mock);
本地链演示(未上公网,但架构支持)。每一条都有明确的"为什么收窄"和"如果要做,方案是什么"
——收窄是论证过的选择,不是没做完。
