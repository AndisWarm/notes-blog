# 08 扩展知识：常见疑问与 TLS 1.3

> 本章目标：把读完全文后最常冒出的疑问一次讲清——为什么要三个随机数、ECDHE 的前向保密是怎么回事、证书链怎么验、TLS 1.3 比 1.2 快在哪，最后附一份全系列术语对照表。

---

## Q1 为什么需要三个随机数？两个不行吗？

生成主密钥需要 Client Random + Server Random + pre-master，三个缺一不可。各司其职：

| 随机数 | 谁生成 | 保密程度 | 作用 |
| --- | --- | --- | --- |
| Client Random | 客户端 | 公开（明文发送） | 保证每次会话密钥不同（防重放、防撞钥匙） |
| Server Random | 服务器 | 公开（明文发送） | 同上，且双方各出一份，谁都无法单方面预知 |
| pre-master | 客户端 | **秘密**（公钥加密传输） | 真正保密的"核心原料"，攻击者不知道它就算不出密钥 |

**最关键的原因**：如果只用两个公开的随机数，那任何在网络上偷听的人（他们也能看到 Client Random 和 Server Random）都能算出这把"密钥"，加密等于没加。**pre-master 是唯一的秘密成分**，它让密钥真正成为"只有双方知道"的秘密。

而另外两个公开随机数负责**新鲜度**——让每次会话的密钥都不一样。三者合在一起：**一个提供秘密性，两个提供新鲜度。**

## Q2 ECDHE 的前向保密（Forward Secrecy）是什么？

第 4 章提过：ECDHE 是当前主流的密钥交换算法，重要原因是**前向保密**。用一个故事讲清楚：

**老式 RSA 密钥交换的悲剧**：

1. 服务器有一对长期私钥/公钥（用很多年）。
2. 每次握手，客户端把 pre-master 用服务器公钥加密发过去。
3. 黑客**今天**把网络上所有加密流量都录下来（存硬盘，不着急破解）。
4. 若干年后，黑客通过某种方式**拿到了服务器的私钥**（泄露、破解）。
5. 黑客用私钥**把几年前录下的所有 pre-master 全部解密** → 算出所有历史会话密钥 → **历史上所有加密通信全部被还原**。

这就是"没有前向保密"：**一把私钥泄露，过去现在一起完蛋。**

**ECDHE 的解法**：

1. 每次握手，服务器**临时**生成一把一次性密钥对（用完即弃，所以叫 ephemeral，临时）。
2. 即使今天服务器长期私钥泄露，也只能解开**当前或未来**的会话，**过去的会话用的是当年的临时密钥**，早已丢弃，无法回溯。
3. 结论：**破解今天，不影响昨天。** 这就是"前向保密"——保护已经过去的通信。

> 一句话：**前向保密 = 今天的泄露，换不回昨天的秘密。** 这也是现代 HTTPS 全面改用 ECDHE、废弃 RSA 密钥交换的根本原因。

## Q3 证书链（Certificate Chain）是什么？

第 5 章提过服务器发的是"一串证书"，这里展开。信任体系是分层的：

```
根 CA 证书（浏览器/操作系统内置，信任的起点）
    ▲ 签发
中间 CA 证书（可有多层）
    ▲ 签发
服务器证书（网站的，域名 www.example.com）
```

- 浏览器内置的是**根 CA 证书**（含根 CA 的公钥）；
- 如果直接用根 CA 给每张网站证书签名，根 CA 私钥的使用风险太大（根私钥一泄露，全行业崩溃），所以中间插了**中间 CA**：根 CA 只给中间 CA 签发证书，中间 CA 再给网站签发；
- 验证时从**服务器证书 → 中间 CA → 根 CA** 逐级验证签名，最后一级必须落在浏览器内置信任的根上，整条链才算可信；
- 如果链条中间断了（比如中间 CA 证书没发全），浏览器会报"证书链不完整"错误。

> 记忆：**根在系统里，逐级往上验，链到头可信。**

## Q4 会话恢复（Session Resumption）：为什么第二次访问更快？

TLS 1.2 完整握手要 2 个往返（RTT）。如果每次访问网站都重新完整握手，延迟翻倍。所以 TLS 提供了**会话恢复**机制：

- 第一次完整握手后，服务器可以发一个 **Session Ticket**（会话票据，里面藏着会话密钥的信息，用服务器自己的密钥加密），交给客户端保存；
- 下次访问同一服务器时，客户端直接把票据放进 ClientHello 里带过去；
- 服务器验票据有效 → 双方直接复用之前的会话密钥 → **跳过证书、pre-master 等大部分步骤，1 个往返（甚至 0.5 个往返）就完成握手**。

> 代价与取舍：会话恢复省时间，但会话密钥复用意味着"新鲜度"变弱（密钥用的时间更长）。所以票据都有有效期（通常几小时），过期就得重新完整握手。

## Q5 TLS 1.3 把握手砍到了 1 个往返，怎么做到的？

TLS 1.3（RFC 8446）对握手做了大刀阔斧的简化，核心变化：

| 对比项 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 完整握手往返数 | 2 个往返（4 轮消息） | **1 个往返**（2 轮消息） |
| 消息数 | 13 步左右 | 精简到约 5 条核心消息 |
| 密码套件 | 四段式，几百种组合 | 固定少数几种（如 `TLS_AES_128_GCM_SHA256`），删掉了密钥交换/签名/哈希的自由组合 |
| RSA 密钥交换 | 可用 | **彻底删除**（强迫使用 ECDHE，保证前向保密） |
| 握手加密 | ChangeCipherSpec 之后才加密 | **几乎整个握手都加密**（连证书都加密发送，防隐私泄露） |
| 会话恢复 | Session Ticket | 0-RTT（首包就能带数据）等机制 |

**TLS 1.3 为什么能 1 个往返？** 关键思路：客户端在 ClientHello 里**直接猜**服务器会选什么（带上自己的密钥交换参数，比如 ECDHE 的公钥），服务器回 ServerHello 时把参数和证书一起带回，双方立刻就能算出密钥、直接发 Finished——省掉了"协商完再交换密钥材料"的第二个往返。

> 记忆：**1.2 先商量再动手，1.3 边打招呼边把事办完。** 截至今天，主流浏览器和服务器早已默认启用 TLS 1.3。

## Q6 常见面试追问速答

- **问：TLS 握手为什么要加密 Finished？** 答：防止中间人伪造"握手成功"的假象；加密 + 指纹能同时验证密钥一致性和消息完整性。
- **问：证书过期了会怎样？** 答：浏览器验证失败，拒绝连接或给出"不安全"警告（HTTPS 变灰锁/红锁）。
- **问：CA 公钥哪里来的？** 答：操作系统/浏览器内置的根证书库，随系统更新，用户也可以手动安装信任根证书。
- **问：客户端身份验证（双向 TLS）在什么场景用？** 答：银行、企业内部系统、API 网关等需要确认"客户端是谁"的场景，会用到 CertificateRequest/CertificateVerify。
- **问：为什么不用非对称加密加密所有数据？** 答：非对称加密慢几个数量级，大数据量下性能不可接受；混合加密用非对称只做密钥协商，数据用对称加密。

| --- | --- | --- |
| TLS | Transport Layer Security | 传输层安全协议，HTTPS 的安全基础 |
| 握手 | Handshake | 双方建立安全会话前的协商过程 |
| ClientHello / ServerHello | — | 握手前两轮的"打招呼"消息 |

| 非对称加密 | Asymmetric Encryption | 公钥加密私钥解密，慢但不用传钥匙 |
| 混合加密 | Hybrid Encryption | 非对称协商密钥 + 对称加密数据 |

| pre-master | Pre-Master Secret | 客户端生成的第三味密钥配料（秘密） |
| 主密钥 | Master Secret | 三个随机数算出的会话密钥核心 |
