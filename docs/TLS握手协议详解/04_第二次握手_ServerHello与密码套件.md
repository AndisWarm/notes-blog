# 04 第二次握手：ServerHello 与密码套件

> 本章目标：看懂服务器如何"点菜"（选版本、选套件、给随机数），并彻底拆解密码套件那一长串名字到底是什么意思——这是面试里最喜欢追问的细节之一。

---

## ServerHello：服务器的"点菜"回执

**ServerHello 消息的意义是将 Server 选择的连接参数传送给 Client。** 它要做三件事：

1. **确认 TLS 版本号**：检查客户端报的版本是否支持，回一个最终使用的版本（比如 TLS 1.2）；
2. **从密码套件清单里选一个**：客户端列了十几样，服务器选中最合适的那一个；
3. **生成自己的随机数**（Server Random），并一起发回去。

原文报文示例：

```
Version: TLS 1.2                            ← ① 最终确定用这个版本
Random: 9f0ae9qe9rer9q0etub61t4y...         ← ② 我生成的随机数（Server Random）
Cipher Suite: TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256  ← ③ 我从你的清单里选了它
```

把这三行翻译成人话：

> "收到你的消息。我们统一用 TLS 1.2。我也随机报一个数字（Server Random）。你清单里的套餐我看过了，就选 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` 这一种吧。"

注意：**服务器不会发明新套餐**——它只能从客户端提供的清单里挑。如果客户端清单里没有服务器想要的那种，服务器也可以直接拒绝握手（毕竟一方不会的套餐没法用）。

## 密码套件：一长串名字里的四个零件

密码套件（Cipher Suite）有固定的格式和规范。**基本形式是「密钥交换算法 + 签名算法 + 对称加密算法 + 摘要算法」**，四个零件用下划线连成一长串。以最常见的

```
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
```

为例，它其实是四段信息拼起来的：

```
TLS + ECDHE + RSA + WITH + AES_128_GCM + SHA256
     └─┬──┘  └┬┘        └────┬────┘    └──┬──┘
    密钥交换  签名算法       对称加密算法    摘要算法
    （handshake）（认证）    （加密）      （哈希）
```

| 零件 | 本套件中的值 | 负责什么 | 属于协议哪部分 |
| --- | --- | --- | --- |
| 密钥交换算法 | **ECDHE** | 基于非对称密钥，用于安全地**交换（商量出）对称密钥** | 握手（Handshake） |
| 签名算法 | **RSA** | 用于**验证证书签名**、认证服务器身份 | 认证（Authentication） |
| 对称加密算法 | **AES_128_GCM** | 用对称密钥**加密正式数据**；AES 是算法，128 是密钥强度，GCM 是分组模式 | 加密（Encryption） |
| 摘要算法 | **SHA256** | 计算消息的**哈希值（指纹）**，防止中途被篡改 | 哈希（Hashing） |

> 连起来读一遍：**"用 ECDHE 商量密钥，用 RSA 验明身份，用 128 位 AES 的 GCM 模式加密数据，用 SHA256 做指纹防篡改。"** 从此这一长串名字不再是天书。

### 零件一：密钥交换算法（Key Exchange）

解决"对称密钥怎么安全送达"的问题，常用选手：

| 算法 | 全称 / 思路 | 特点 |
| --- | --- | --- |
| **ECDHE** | 椭圆曲线迪菲-赫尔曼**临时**密钥交换 | 每次握手都现场生成新密钥对（临时 = ephemeral），**前向保密**（第 8 章细讲）；现代 HTTPS 的绝对主力 |
| DHE | 迪菲-赫尔曼密钥交换（传统版） | 思路同 ECDHE，但不基于椭圆曲线，速度较慢 |
| RSA（作为密钥交换时） | 用服务器公钥加密 pre-master 直接传 | 简单但**没有前向保密**——服务器私钥一旦泄露，历史上所有会话都能被解密；已被淘汰 |

> 记不住没关系，先记住一句话：**ECDHE 是当前默认主力，因为它每次握手用临时密钥，被破一个不连累一片（前向保密）。**

### 零件二：签名算法（Signature / Authentication）

解决"证书是不是真的"的问题——谁给证书盖的章：

| 算法 | 说明 |
| --- | --- |
| **RSA** | 最经典的数字签名算法，用 CA 的私钥给证书内容"盖章" |
| **ECDSA** | 基于椭圆曲线的签名算法，密钥更短、速度更快，现代证书常见 |

### 零件三：对称加密算法（Bulk Cipher / Encryption）

解决"数据怎么加密"的问题，看三个信息：

| 字段 | 例子 | 含义 |
| --- | --- | --- |
| 算法名 | **AES** | 高级加密标准，当前最主流的对称加密算法 |
| 密钥长度 | **128 / 256** | 密钥位数，越长越难破解（256 位更安全但稍慢） |
| 分组模式 | **GCM** | 加密的工作模式；GCM 模式顺便提供完整性校验（自带"防篡改"），是现代首选；老的 CBC 模式不提供 |

> 小知识：套件里写着 GCM 时，数据加密自带认证（AEAD），所以摘要算法主要负责握手消息的验证，数据本身的防篡改由 GCM 一并完成。

### 零件四：摘要算法（Hashing / PRF）

解决"怎么验证消息没被改"的问题：

| 算法 | 输出长度 | 说明 |
| --- | --- | --- |
| **SHA256** | 256 位 | 当前主流指纹算法 |
| SHA384 / SHA512 | 384 / 512 位 | 更长的指纹，更保守的选择 |

## 为什么密码套件要"四件套"缺一不可？

因为 TLS 的三大安全目标需要不同工具分别实现：

- **防偷看** → 对称加密（AES）负责；
- **防冒充** → 签名（RSA/ECDSA）+ 证书负责；
- **防篡改** → 摘要（SHA256）负责；
- **把前两者串起来** → 密钥交换（ECDHE）负责安全地送出加密用的钥匙。

少了任何一件，整个安全链条就断了一环。这也是为什么密码套件总是一长串名字——它其实是**四个零件的打包合同**。

## 第二轮收尾：ServerHelloDone

ServerHello 说完之后，服务器还会继续发证书等消息（第 5 章细讲），最后发一条 **ServerHelloDone**："我说完了，该你了。"（原文：Server 通知 Client 自己完成了协商过程。）

到这一刻为止，双方手里各自拥有的"配料"是：

| 配料 | 谁生成的 | 状态 |
| --- | --- | --- |
| Client Random | 客户端 | 双方都有 |
| Server Random | 服务器 | 双方都有 |

还差第三味配料（pre-master），它在第三次握手里由客户端送出——钥匙的"临门一脚"。

## 本章知识点小结

- **ServerHello 做三件事**：确认 TLS 版本、从清单里选密码套件、给出 Server Random。
- **密码套件 = 四件套合同**：密钥交换（如 ECDHE）+ 签名（如 RSA）+ 对称加密（如 AES_128_GCM）+ 摘要（如 SHA256）。
- **密钥交换**解决"钥匙怎么安全送"；**签名**解决"你是谁"；**对称加密**解决"内容加密"；**摘要**解决"有没有被改"。
- 服务器只能**从客户端清单里选**，不能自创套餐。
- 第二轮以 **ServerHelloDone** 收尾，把话筒交给客户端。
