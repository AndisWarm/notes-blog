# 01 什么是 TLS，为什么需要它

> 本章目标：不碰任何公式，先把「TLS 解决什么问题」「它在网络的哪一层」「它由哪几个小协议组成」讲清楚。这些都是后面看懂握手流程的地基。

---

## 从一个生活场景说起

想象你在邮局寄一张**明信片**：

- 邮递员在途中可以**翻开看**你的内容（偷看）；
- 路上的人可以**把字涂掉重写**（篡改）；
- 有人可以**冒充收件人**收下这张明信片（冒充）。

这三个问题——**偷看、篡改、冒充**——就是"不安全通信"的全部含义。早期的 HTTP 协议就像寄明信片：**所有内容都是明文**，谁在中间都能看、能改、能冒充。

你可能会想："我平时上网也没出什么事啊？"那是因为绝大多数网站已经不给你寄明信片了——它们都换成了**挂号信**，这封"挂号信"的名字就叫 **HTTPS**，而给信封贴上防拆封条、写上暗号的那套规矩，就是 **TLS 协议**。

## HTTP 的裸奔问题（为什么必须加密）

HTTP（超文本传输协议）是浏览器和网站之间对话的"语言"，但它有个致命缺点：**所有对话内容都是明文**，就像在大街上喊。

如果你在咖啡厅用公共 Wi-Fi 访问一个纯 HTTP 网站，你在页面上填的密码、银行卡号，会以原文形式在空气里（网络上）飞来飞去。中途任何一个能收到这些数据包的人，都能直接读出来。这叫**窃听**。

- **偷看** → 需要**加密**（把内容变成别人看不懂的乱码）
- **篡改** → 需要**完整性校验**（让对方能发现内容被动过）
- **冒充** → 需要**身份认证**（让对方能确认"你确实是你"）

TLS 一揽子解决这三个问题。**HTTPS = HTTP + TLS**：HTTP 负责说人话，TLS 负责给这些话加密、防改、验明正身。

## TLS 是什么：夹在中间的"保密翻译官"

TLS 的全称是 **Transport Layer Security（传输层安全协议）**，它的前身叫 SSL（Secure Sockets Layer，安全套接层），所以有时你也听人叫它"SSL/TLS"——其实是同一个东西的两代名字。

TLS 是**一种密码学协议，用来保证两个实体（通常是客户端和服务器）之间的会话安全**。它位于**应用层和传输层之间**：

```
┌────────────────────────────┐
│  应用层（HTTP 说人话）        │  ← 你的网页内容在这里产生
├────────────────────────────┤
│  TLS 层（保密翻译官）         │  ← 把内容加密、加防改标记
├────────────────────────────┤
│  传输层（TCP 快递员）         │  ← 负责把包裹安全送达
├────────────────────────────┤
│  网络层 / 链路层              │  ← 物理传输
└────────────────────────────┘
```

打个比方：HTTP 是你要寄的**信的内容**，TCP 是**快递员**，而 TLS 是站在中间帮你把信装进上了锁的保险箱、又负责查验身份的**保密翻译官**。快递员（TCP）照样干活，但他看到的只是一堆乱码，不知道信里写了什么。

## 密码学基础三件套（握手故事的主角）

要读懂握手，必须先认识三种"工具"。这里用生活类比讲，不涉及任何数学。

### 1. 对称加密：同一把钥匙锁门和开门

- **是什么**：加密和解密**用同一把钥匙**。
- **类比**：家门钥匙。出门锁门用这把钥匙，回家开门还是这把钥匙。
- **优点**：快！加密超大文件也几乎感觉不到延迟。
- **缺点**：钥匙怎么安全地送到对方手里？如果寄钥匙的路上被人抄走，锁就白上了。

### 2. 非对称加密：公钥锁、私钥开

- **是什么**：有两把钥匙，**公钥**（可以随便发给任何人）和**私钥**（自己死死藏好）。用公钥加密的内容，只有对应的私钥能解开；反过来，用私钥加密的内容，只有公钥能解开。
- **类比**：小区门口的**公共快递柜**。任何人（公钥持有者）都能往里投件，但只有拿专属钥匙（私钥）的你能取出。
- **优点**：**不需要传钥匙**——把公钥满世界发都没关系，因为只有你的私钥能解。
- **缺点**：慢，比对称加密慢几个数量级（就像开保险柜比开门慢得多）。

### 3. 混合加密：HTTPS 的聪明做法

- **是什么**：**先用非对称加密安全地商量出一把对称密钥，然后用这把对称密钥加密正式通信内容。**
- **类比**：先寄一把"临时家门钥匙"（用快递柜安全地送），之后所有信都用这把钥匙加解密。快和安全的优点全占了。
- **为什么必须这样**：对称加密快但钥匙送不出去，非对称加密能安全送钥匙但慢。**取长补短**——非对称只用来干"送钥匙"这一件小事（哪怕慢也没关系），正式数据量大，交给对称加密。

> TLS 握手干的头等大事，就是**安全地商量出这把"临时家门钥匙"**，它有个正式名字叫**会话密钥（Session Key）**。

### 附：哈希（Hash）——"指纹"制造机

除了加密，握手过程还经常用到 **哈希算法（摘要算法）**，它的作用也需要提前认识：

- **是什么**：任意长度的内容，经过哈希算法算出一串**固定长度的短字符串**（叫"摘要"或"散列值"），这串字符就像内容的**指纹**。
- **特点**：内容哪怕只改一个标点符号，指纹就完全变样；而且**几乎不可能**从指纹反推出原文。
- **类比**：把一段话丢进"指纹机"，出来一串 64 位十六进制字符。你没法从指纹还原出原话，但任何人拿到原话都能验证指纹对不对得上。
- **用途**：**防篡改**。把"原文 + 原文的指纹"一起发出去，对方算一下指纹就知道有没有被人改过。

## TLS 的四个核心子协议

TLS 不是一个大而化之的协议，而是由四个"分工明确的小协议"组成的家族。原文把四个核心子协议列了出来，这里逐个认识：

| 子协议 | 英文名 | 负责什么 | 什么时候出场 |
| --- | --- | --- | --- |
| **握手协议** | Handshake Protocol | 协商连接参数、身份认证、交换生成密钥所需的信息 | 连接建立时（重头戏） |
| **密钥规格变更协议** | Change Cipher Spec Protocol | 通知对方"我要切换到加密模式了" | 握手进行到一半时 |
| **应用数据协议** | Application Data Protocol | 用商量好的密钥加密传输真正的业务数据（如 HTTP 请求/响应） | 握手完成后 |
| **警报协议** | Alert Protocol | 报告错误和警告（如证书过期、解密失败） | 任何时刻出现问题 |

**握手协议**是四兄弟里最精密、最复杂的部分：通信双方要在这里**协商连接参数，并且完成身份验证**。后面 7 章全部在讲它。

> 记忆口诀：**握手定规矩，规格变更打招呼，应用传数据，警报报故障。**

## 一张图总结

```
HTTP 明文问题（偷看/篡改/冒充）
        │
        ▼
TLS 协议出场（位于应用层与传输层之间）
        │
        ├── 加密     ← 对称加密（快）+ 非对称加密（安全）→ 混合加密
        ├── 防篡改   ← 哈希（指纹）
        ├── 身份认证 ← 数字证书 + CA（第 5 章细讲）
        │
        ▼
四个子协议分工：握手 / 密钥规格变更 / 应用数据 / 警报
```
