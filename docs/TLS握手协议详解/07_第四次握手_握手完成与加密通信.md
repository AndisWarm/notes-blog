# 07 第四次握手：握手完成与加密通信

> 本章目标：看完服务器端的收尾动作，走完整场握手，并搞清楚握手成功之后数据是怎么加密传输的。

---

## 服务器如法炮制：ChangeCipherSpec + Finished

客户端那边（第三次握手）已经切换加密并发出自己的 Finished，服务器收到后：

1. 验证客户端的 Finished 指纹 → 确认密钥协商正确、消息没被篡改；
2. 确认无误后，服务器也发送自己的 **Change Cipher Spec** 消息——"我这边也切换加密模式了"；
3. 然后服务器发送自己的 **Finished**（Encrypted Handshake Message）——同样把之前所有发送过的握手数据做摘要、用主密钥加密，发给客户端验证。

**如果双方都验证加密和解密没问题，那么握手正式完成。**

```
Client                                        Server
  │  ⑩ ChangeCipherSpec（我切加密了）             │
  │  ⑪ Finished（加密指纹 1）                    │
  ├────────────────────────────────────────────→│  验证指纹 1 ✓
  │                                             │
  │  ⑫ ChangeCipherSpec（我也切加密了）           │
  │  ⑬ Finished（加密指纹 2）                    │
  │←────────────────────────────────────────────┤  验证指纹 2 ✓
  │                                             │
  ▼       握手完成，双方确认：                    ▼
    · 身份已验证（证书通过）                         
    · 密钥已协商（三个随机数 → 主密钥）               
    · 消息未被篡改（指纹通过）                       
```

为什么服务器不能省略自己的 Finished？因为**握手是双向的信任建立**——服务器也要确认客户端那边的密钥和消息没问题。只有两边的 Finished 都验证通过，双方才都确信"我们用的是同一把钥匙、说的话都没被改过"。

## 握手完成之后：加密时代正式开始

握手一结束，之前攒下的所有努力立刻派上用场：**后续双方就能够基于「会话密钥」加解密 HTTP 的请求和响应了。**

日常流程是这样：

```
浏览器（客户端）                        服务器
  │                                      │
  │  HTTP 请求（明文内容）                 │
  │  ──► 用会话密钥加密 ──► 密文           │
  ├─────────────────────────────────────→│  ←─ 用会话密钥解密出 HTTP 请求
  │                                      │
  │  ←──────────────────────────────────┤  HTTP 响应 → 用会话密钥加密
  │  ←─ 用会话密钥解密出明文 ── 密文 ◄──── │
  │                                      │
  └────── 以上过程循环，直到连接结束 ──────┘
```

几个要点：

- **快**：正式数据用的是对称加密（AES），速度飞快——握手时那段慢悠悠的非对称加密只用在"送钥匙"阶段；
- **每次连接一把新钥匙**：下一次访问同一网站，会重新握手、重新生成随机数、得到一把全新的会话密钥（TLS 1.2 的完整握手如此；第 8 章会讲"会话恢复"机制可以跳过部分流程）；
- **TCP 负责运货，TLS 负责保密**：密文仍由 TCP 正常传输，TCP 并不知道也不关心内容是什么。

## 整个握手的一张终局图

把四轮 13 步再整体回放一遍（这次带上每步的"用途"）：

```
Client                                    Server
  │ ① ClientHello（版本+随机数+套件清单）      │
  │────────────────────────────────────────→│
  │ ② ServerHello（选版本+选套件+随机数）      │
  │ ③ Certificate（身份证）                  │
  │ ④ ServerKeyExchange（选配）              │
  │ ⑤ CertificateRequest（选配）             │
  │ ⑥ ServerHelloDone（我说完了）            │
  │←────────────────────────────────────────┤
  │ ⑦ Certificate（选配）                    │
  │ ⑧ ClientKeyExchange（pre-master）        │
  │ ⑨ CertificateVerify（选配）              │
  │ ⑩ ChangeCipherSpec（切加密）             │
  │ ⑪ Finished（指纹1，加密）                 │
  │────────────────────────────────────────→│
  │ ⑫ ChangeCipherSpec（切加密）              │
  │ ⑬ Finished（指纹2，加密）                 │
  │←────────────────────────────────────────┤
  │                                          │
  │  ◄══════ 握手完成，加密通信开始 ══════►    │
```

**整场握手回答的三个问题**：

| 问题 | 由哪几步回答 |
| --- | --- |
| 你是真的吗？（身份） | ②③ 服务器亮证书 → 客户端验证（第 5 章） |
| 我们用什么钥匙？（密钥） | ①② 两个随机数 + ⑧ pre-master → 主密钥（第 6 章） |
| 之前没被搞鬼吧？（完整） | ⑪⑬ 双方 Finished 指纹互验 |

## 与 TCP 握手的区分（高频混淆点）

很多初学者会把 TLS 握手和 TCP 三次握手搞混，这里明确一下：

| | TCP 三次握手 | TLS 四次握手 |
| --- | --- | --- |
| 目的 | 建立**可靠的传输通道** | 建立**安全的加密通道** |
| 消息 | SYN / SYN+ACK / ACK | ClientHello / ServerHello / 证书 / Finished 等 |
| 内容 | 只协商序列号等传输参数 | 协商版本、密码套件、身份、密钥 |
| 顺序 | **先 TCP 后 TLS**：TCP 通道建立后，TLS 在它之上握手 | — |

> 记忆：**TCP 先铺路，TLS 再上锁。** 浏览器地址栏的小锁，是 TLS 的功劳，不是 TCP 的。

## 本章知识点小结

- 第四次握手 = 服务器的 **ChangeCipherSpec + Finished**，与客户端对称地完成加密切换和指纹验证。
- **双方 Finished 都通过 → 握手完成**：身份、密钥、完整性三个问题全部确认。
- 握手完成后，**HTTP 请求/响应用会话密钥（对称加密）加密传输**，又快又安全。
- 一次连接一把钥匙；TCP 管运输，TLS 管保密。
- TCP 握手在前，TLS 握手在后，两者目的不同，别混淆。
