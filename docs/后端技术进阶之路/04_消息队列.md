# 04 消息队列

本章覆盖：为什么要用消息队列（解耦/异步/削峰）、MQ 在架构设计中的作用与代价、消息队列的演进、防止消息重复、三种消息语义、100% 不丢消息、如何从零设计一个 MQ、RabbitMQ 架构、Kafka 架构、Kafka 为什么快、Kafka 会丢消息吗、Kafka 百万积压处理、RocketMQ 与 Kafka 的区别、RocketMQ 为什么性能不如 Kafka。

## 1. 你的项目为什么要用消息队列？

### 一句话回答
核心就六个字：**解耦、异步、削峰**。消息队列（MQ）是一个消息中转站：生产者发消息、队列存消息、消费者取消息，三者通过队列隔开，换来了系统架构的弹性。

### 展开讲：用一个电商例子串起来

假设做个电商系统：用户付完款后，系统要干好几件事——扣库存、发优惠券、加积分、发短信通知。

#### 第一板斧：解耦（把绑在一起的系统拆开）

**没有 MQ 时**：订单系统直接用 RPC 调用挨个通知这些子系统。代码高度耦合：哪天不需要发短信了，订单系统要改代码重新发版；新加一个自动发货服务，订单系统又要改代码；发积分服务挂了报错，连累整个支付流程失败。

**有了 MQ 后**：订单系统付完款，只对着 MQ 丢一句话"用户A支付成功了"，主线任务结束。后续不管有几个系统关心这件事，它们自己去订阅 MQ 就行。哪怕以后新加再多依赖服务，订单系统代码一行都不用改。

> 比喻：没有 MQ 就像"公司老板亲自盯着每个员工干活"，谁出问题都来找老板；有 MQ 就像"老板把任务贴到公告栏"，谁认领谁做，老板发完公告就去喝茶了。

#### 第二板斧：异步（主流程秒回）

如果串行调用发短信、加积分这些非核心流程，每个接口哪怕只要 50 毫秒，加起来用户等待的时间就是大半秒甚至好几秒，体验极差。

有了 MQ，主流程只做两件事：把订单状态改掉；往 MQ 抛一条消息（几毫秒）。然后立刻给前端响应"支付成功"。发短信、加积分这种不非得在零点几秒内完成的操作，交给后台顺着 MQ 慢慢执行。

> 关键认知："响应快"不是真的变快了，而是把非核心操作挪到了后台。总耗时没变，但用户感知的等待时间大幅缩短。

#### 第三板斧：削峰填谷（高并发保命神器）

平时 MySQL 一秒钟扛一两千并发没事。一旦秒杀，瞬间两万个请求涌进来，直接打数据库 → 宕机。

MQ 此时扮演"蓄水池"：瞬时请求先进队列存起来，数据库按自己每秒 2000 的节奏慢慢消化。就像游乐场门口的蛇形排队通道，把瞬间爆发的流量洪峰（削峰）分散到后续慢慢处理（填谷）。用户体感是排队多了几秒，但总比系统崩溃好无数倍。

| 痛点 | 解决什么 | 例子 |
|------|---------|------|
| 解耦 | 系统之间互相依赖、牵一发动全身 | 支付成功 → 通知 N 个下游 |
| 异步 | 主流程响应慢、用户等待久 | 发短信、加积分挪到后台 |
| 削峰 | 瞬时流量把数据库打崩 | 秒杀、抢购、双十一 |

### 比喻
MQ 像一个**传话的公告栏**：发帖的人不用等所有读者看完才走，读者也不用认识发帖的人，各自按自己的节奏来。

## 2. 消息队列在架构设计中有什么用？

### 一句话回答
除了第 1 节的解耦、异步、削峰三大价值，MQ 在架构里还承担**日志收集、广播通知、系统间最终一致性**等角色；但它不是银弹——引入它同时要吞下可用性降低、开发复杂度上升、数据一致性变难三大苦果。

### 展开讲：五大用途

1. **应用解耦**：上游只管发消息，下游自己订阅。一个系统挂了只是消息积压，不影响其他系统，恢复后继续消费；
2. **流量削峰**：秒杀等瞬时洪峰先落队列，后端按自身能力消费，保护数据库；
3. **异步提速**：非核心步骤（发短信、加积分、更新轨迹）挪到后台异步执行，主流程毫秒级返回；
4. **日志收集**：各服务把日志打进 MQ（如 Kafka），由统一的日志系统消费、存储、分析。这是 Kafka 最经典的场景——高吞吐、允许延迟；
5. **广播通知**：一条消息推给多个订阅方（比如商品改价通知所有缓存系统、搜索系统、推荐系统），用 Fanout 交换机或广播模型一次投递全员收到。

### 引入 MQ 的三大代价（面试必答）

| 代价 | 说明 |
|------|------|
| 可用性变低 | 多了一个"中间人"，它会宕机、会网络故障，链路反而多了一个故障点，所以要搭集群 |
| 开发复杂度上升 | 要处理消息重复（幂等）、消息丢失（确认/补偿）、顺序性、积压等一堆新问题 |
| 数据一致性难保证 | 本地事务成功和消息投递是两个动作，可能"A 以为成功、B 实际失败"，需要事务消息或对账兜底 |

### 比喻
MQ 像**快递中转站**：让寄件人和收件人彻底解耦，还能在爆仓时排队（削峰）。但包裹多了，就有丢件、重复投递、积压的问题——你得为每个问题准备应对方案。

## 3. 消息队列是怎么演进的？

### 一句话回答
消息队列从**"能传消息"**一步步进化到**"高吞吐、强可靠、功能全"**：ActiveMQ → RabbitMQ → Kafka → RocketMQ → Pulsar，每一次换代都针对上一代的痛点。

### 展开讲：演进脉络

#### 第一代：ActiveMQ（2004，Apache）
JMS（Java 消息服务）规范的参考实现，功能标准但性能平庸（万级吞吐）。**痛点**：吞吐上不去、消息堆积时表现差，逐渐被淘汰出主流。

#### 第二代：RabbitMQ（2007，Erlang）
完全实现 AMQP 协议，路由灵活（交换机机制）、功能标准、轻量易用。**痛点**：吞吐仍是万级，**不支持消息回溯**（消费完就没了），主要适合中小规模业务。

#### 第三代：Kafka（2011，LinkedIn 开源）
为海量日志而生，**颠覆性设计**：顺序写磁盘 + 零拷贝 + 批量处理，单机吞吐 10 万级+，消息持久化可**按 offset 回溯重放**。**痛点**：功能单一（延迟消息、事务消息弱），配置不当会丢消息，主题一多性能下降。

#### 第四代：RocketMQ（2016，阿里巴巴开源）
针对 Kafka 在**海量 Topic 场景随机写**的硬伤，用 CommitLog 混合存储让写入永远顺序化；补齐了事务消息、延迟消息、消息过滤等电商业务必需的高级特性。**痛点**：零拷贝是 mmap+write 的"广义零拷贝"，吞吐略逊 Kafka。

#### 第五代：Pulsar（2018，Apache）
引入**存算分离**：Broker 无状态、存储交给 BookKeeper，支持百万级 Topic，云原生友好。**痛点**：架构复杂、生态相对年轻，国内落地少于前四者。

### 演进主线（面试一句话总结）
- **可靠性从弱到强**：内存 → 磁盘持久化 → 多副本 + 选主；
- **吞吐从万级到十万级**：随机写 → 顺序写 + 批量 + 零拷贝；
- **功能从单一到丰富**：纯转发 → 事务消息、延迟消息、回溯、过滤；
- **架构从单体到存算分离**：Broker 自带存储 → Broker 与存储分离（Pulsar）。

### 比喻
像**邮局的发展史**：先是小巷里的代收点（ActiveMQ），后来是正规邮局（RabbitMQ），再后来是流水线自动化分拣中心（Kafka，极快但只会分拣），然后是能处理挂号信、代付代收的"全能邮局"（RocketMQ），最后是网点与仓库分离的现代物流（Pulsar）。

## 4. 消息队列怎样防止消息重复？

### 一句话回答
重复消费**无法从根上消灭**（生产端可能重复发送、消费端可能拉重），只能靠**业务端做幂等**：给每条消息留"业务标识"，处理前先查重，处理过就跳过。

### 展开讲：为什么会重复？

重复消息有两个来源：

1. **生产端**：为了保证发送成功，生产端可能会重复推送（直到收到成功 ACK），产生重复消息；
2. **消费端**：这个无法根本解决——"拉取消息 + 业务处理 + 提交消费位移"很难做成一个原子事务，消费服务宕机重启后很可能拉取到重复消息。

### 五种幂等方案（面试核心）

| 方案 | 做法 | 适用 |
|------|------|------|
| 幂等键（唯一标识） | 客户端为每个请求生成全局唯一 ID（UUID/业务主键），服务端校验是否已处理 | 接口调用、消息消费（最通用） |
| 数据库唯一约束 | 给"业务单号"建唯一索引，第二次插入同单号直接报错被拦下 | 数据插入场景 |
| 乐观锁 | `UPDATE ... SET balance = balance - 100, version = version + 1 WHERE id = 1 AND version = 5`，版本对不上更新 0 行 | 余额扣减、订单状态变更 |
| 分布式锁 | Redis `SETNX` 保证同一时刻只有一个请求执行关键操作 | 秒杀等高并发资源抢夺 |
| 消息去重表 | 消费者处理前查 Redis/DB 中该消息 ID 是否处理过，处理过则丢弃 | 消息队列场景 |

### 面试怎么答
"重复消费的根源有两个：生产端为确认成功可能重发，消费端提交位移与业务处理不是原子的、宕机后可能重拉。MQ 自己解决不了消费端的问题，所以业务端必须做幂等：用消息唯一 ID 在 DB 或 Redis 做去重校验，处理过的直接跳过。实际项目中最常用的是'唯一业务键 + 数据库唯一索引/Redis 去重'的组合，比如支付场景用订单号做幂等键。"

### 比喻
像**快递包裹上的运单号**：同一个包裹不管送几次，运单号一样，你签收一次就够了。系统要做的就是"看运单号，签过就拒收"。

## 5. 最多一次、至少一次和正好一次有什么区别？

### 一句话回答
这是消息队列对"消息丢失/重复"的三种承诺：**最多一次**（不重复但可能丢）、**至少一次**（不丢但可能重复）、**正好一次**（不丢也不重，但代价是性能和复杂度）。

### 展开讲：逐个解释

| 语义 | 含义 | 代价 | 适用 |
|------|------|------|------|
| 最多一次（At most once） | 消息不会重复，但可能**丢** | 丢了就没了 | 日志、埋点（丢了不可惜） |
| 至少一次（At least once） | 消息不会丢，但可能**重复** | 消费者要做幂等 | 绝大多数业务（默认选项） |
| 正好一次（Exactly once） | 不丢也不重复 | 性能开销大、配置复杂 | 金融、转账（最严格） |

**为什么"正好一次"这么贵？**
要做到不丢，生产者要确认（ack）；要做到不重，消费者要幂等或事务；两者叠加意味着每个环节都要强校验、状态要全局记录，性能必然下降。Kafka 的精确一次（0.11+）需要开启幂等生产者 + 事务 API 才能实现，吞吐明显打折。

### 工程上的实际选择
- **绝大多数业务选"至少一次" + 业务幂等**：这是成本最低、效果最好的组合——MQ 层面只管不丢，重复由业务去重；
- **日志、监控埋点选"最多一次"**：丢几条无所谓，换来最低延迟和最高吞吐；
- **极少数字段级敏感业务才用"正好一次"**：如资金、积分变动，且通常配合数据库事务落地。

### 比喻
- 最多一次：**快递可能半路丢了**，但绝不会送两份；
- 至少一次：**保证送到**，但可能因为补发而收到两份（你得自己扔掉多的一份）；
- 正好一次：**保证恰好送到一份**——快递公司全程监控、逐件签收，成本最高。

## 6. 在使用 MQ 的时候，怎么确保消息 100% 不丢失？

### 一句话回答
全程分三大环节：**生产者、中间件（Broker）、消费者**。每个环节单独把关——生产端靠 ack + 失败重发，存储端靠持久化 + 多副本，消费端靠"处理完才回 ack"，三关全守才能说"不丢"。

```text
 生产者（生产阶段） ──► 中间件Broker（存储阶段） ──► 消费者（消费阶段）
   发送消息             持久化+多副本              处理完才回ack
```

### 展开讲：三个环节逐个击破

#### 环节一：生产阶段
**靠 ack 确认 + 失败重发**。消息提交给 MQ 后，只要收到 MQ 的 ack 确认响应，就表示发送成功；返回异常就进行消息重发。只要处理好返回值和异常，这个阶段不会丢。

> 比喻：寄快递，快递员（MQ）收件会给你一张回执（ack）。拿到回执包裹就安全了；没拿到就再寄一次（重发）。

#### 环节二：存储阶段
**靠持久化 + 多副本**。消息要写磁盘（断电不丢），且 Kafka/RocketMQ 都要部署集群、消息写多个副本，一个节点挂了，其他副本还在。

> 比喻：重要文件不只在公司电脑存一份，还要云端、家里各备份一份。一台电脑坏了，其他副本还在。

#### 环节三：消费阶段
**核心原则：处理完才回 ack，不能收到就回 ack**。消费者"接收消息 + 处理成功"之后才回复 ack，MQ 才删除消息。如果收到消息就回 ack，消息处理中途挂掉，MQ 以为你处理完了就把消息删了——消息就丢了。

> 比喻：快递签收要"验货后签收"，而不是"拿到手就签收"。你还没验货就签字，货物坏了快递公司不认账。

### 各中间件的具体手段
- **RabbitMQ**：生产者开 Publisher Confirm；队列和消息都设持久化；消费者手动 ack；
- **Kafka**：生产者 `acks=all`（等所有 ISR 副本写成功）；禁止 unclean 选举；消费者处理完再 commit offset；
- **RocketMQ**：同步刷盘 + 同步复制（主从都写完才返回成功）。

### 面试怎么答
分三段答："生产阶段靠 ack + 失败重发；存储阶段靠持久化 + 多副本集群；消费阶段靠处理完才回 ack。三个环节只要有一个处理不当就会丢消息，所以每个环节都要单独把关。"

## 7. 如何设计实现一个消息队列？

### 一句话回答
不要求你写过 MQ 源码，只要懂**基本架构和工作原理**：回答框架是"先讲整体流程（生产者 → Broker → 消费者），再逐个攻克 RPC 设计、持久化、消费关系、可靠性、高可用、事务、扩展性这 8 个设计点"。

### 展开讲：8 个设计点（面试背这个）

#### ① 整体流程
producer 发消息给 broker，broker 存储好，再发给 consumer 消费，consumer 回复消费确认。这是最基本的骨架。

#### ② RPC 设计
producer 发消息给 broker、broker 发消息给 consumer，需要两次 RPC。可参考 Dubbo：**服务发现**（消费者怎么找到 broker 地址）、**序列化协议**（消息用什么格式传输）。

#### ③ Broker 持久化设计
消息放**文件系统**还是**数据库**？
- 文件系统：性能高（顺序写磁盘），Kafka 的做法；
- 数据库：管理方便，但性能差；
- 还要考虑消息**堆积**如何处理。

#### ④ 消费关系如何保存
**点对点**（一个消息只被一个消费者消费）还是**广播**（所有订阅者都能收到）？路由/订阅关系用什么保存（ZooKeeper / config server / NameServer）？

#### ⑤ 消息可靠性
消息重复如何**幂等**？生产者 ack 机制？消费者确认机制？（对应本章第 4、6 节）

#### ⑥ 高可用设计
参考 Kafka：**多副本 → leader & follower → broker 挂了自动重新选举 leader**，对外服务不中断。

#### ⑦ 事务特性
用经典的**本地消息表**方案：本地业务和消息写同一个数据库事务 → 消息投递成功后本地才删除 → 定时任务扫描本地消息表**补偿发送**失败的。注意这是自研 MQ 的事务思路，与 RocketMQ 的半消息机制是两条不同路线。

#### ⑧ 伸缩性和可扩展性
参照 Kafka 的 `broker → topic → partition` 分层：每个 partition 分布在不同机器上。资源不够 → 给 topic 增加 partition → 数据迁移 → 增加机器，横向扩容提高吞吐。

### 面试怎么答
先表态："这类题考察的是对 MQ 架构原理的理解和设计思维。"然后按 8 点顺序展开，每点一两句话，最后总结："核心设计理念参考 Kafka：broker-topic-partition 分层存储 + 多副本高可用 + 本地消息表做事务，保证可靠性、可扩展性和幂等。"

### 比喻
设计 MQ 就像**设计一家快递公司**：要有收件网点（生产者接入）、中转仓库（Broker 存储）、送货线路（消费者对接）、防丢件制度（可靠性）、备用仓库（高可用）、爆仓时的分仓扩容（可扩展性）。

## 8. RabbitMQ 是什么？架构是怎么样的？

### 一句话回答
RabbitMQ 是 **AMQP 协议的最佳实现**（Erlang 编写），核心架构是"生产者 → 交换机 → 队列 → 消费者"，靠**交换机路由**做消息分发，而不是 Kafka 那种分区模型。

### 展开讲：AMQP 与核心组件

**AMQP 是图纸（协议标准），RabbitMQ 是房子（具体实现）**，就像接口和实现类的关系。AMQP 规定了消息必须经过交换机路由到队列，RabbitMQ 把这套规范做成了产品。

七大核心组件：

| 组件 | 角色 | 类比 |
|------|------|------|
| 生产者 Producer | 发送消息的一方 | 寄件人 |
| 消费者 Consumer | 监听并处理消息的一方 | 收件人 |
| 队列 Queue | 真正存储消息的地方，FIFO | 信箱/货架 |
| 交换机 Exchange | 消息分发器，按规则路由到队列 | 邮局分拣员 |
| 路由键 RoutingKey | 生产者发消息时带的标识，决定去哪 | 收件地址 |
| 绑定 Binding | 把交换机和队列关联起来的纽带 | 投递路线 |
| 连接 Connection | 客户端和 RabbitMQ 之间的 TCP 长连接 | 快递干线 |
| 信道 Channel | 建立在连接之上的轻量级信道 | 干线上的车道 |

**信道为什么存在？** TCP 连接创建销毁开销大，所以一条 TCP 连接（Connection）+ 多个信道（Channel）复用，大大节省资源。

**四种交换机类型**（面试高频）：

| 类型 | 匹配依据 | 特点 | 比喻 |
|------|---------|------|------|
| Direct 直连 | 路由键完全相等 | 精准一对一 | 点名投递 |
| Fanout 扇形 | 不看路由键 | 无脑广播给所有绑定队列 | 大喇叭 |
| Topic 主题 | 通配符 `*`（一个词）/ `#`（多个词） | 最灵活，按业务主题路由 | 通配符分拣 |
| Headers 头 | 消息头键值对 | 性能差，基本不用 | — |

**高可用**：集群 + **镜像队列**——队列内容复制到多个节点，一个节点故障其他节点继续服务。

### 面试怎么答
"RabbitMQ 是 AMQP 协议的最佳实现。核心流程：生产者发消息给交换机，交换机按路由键和绑定规则投到队列，消费者从队列取消息。四种交换机：Direct 精准匹配、Fanout 广播、Topic 通配符、Headers 冷门。可靠性靠持久化 + confirm/ack 双重确认 + 镜像队列。"

### 比喻
RabbitMQ 像**一个分工明确的邮局**：寄件人（生产者）把信投进邮局（交换机），分拣员按地址（路由键）把信分到对应的分拣格（队列），收件人（消费者）来取。地址写得多精确（Direct）、写得多宽泛（Topic）、还是广播（Fanout），决定了信件怎么分。

## 9. Kafka 架构长什么样？

### 一句话回答
Kafka 是 LinkedIn 开源的**分布式流式消息队列**，架构核心是 `Broker → Topic → Partition` 三层模型：一个 Topic 分成多个 Partition，Partition 带多副本分布在多台 Broker 上，消费者以**消费组（Consumer Group）**为单位并行消费。

### 展开讲：核心概念逐个拆

#### Broker（服务器节点）
Kafka 集群由多台机器组成，每台机器就是一个 Broker，负责存储和读写消息。

#### Topic（主题）与 Partition（分区）
- **Topic**：消息的分类，比如"订单日志"一个 Topic；
- **Partition**：每个 Topic 分成多个分区（P0、P1、P2...），消息按分区存储；
- **为什么分区**：分区是**并行处理的基本单位**——不同分区可以在不同机器、被不同消费者并行读写，吞吐量翻倍增长；
- **分区内有序**：写入同一分区的消息按追加顺序存储，消费者按顺序读取。

#### 副本与 ISR
- 每个分区有多个**副本（Replica）**：一个 Leader（负责读写）+ 多个 Follower（负责备份）；
- Leader 挂了，从 **ISR（In-Sync Replica，同步中的副本集）** 里选出新 Leader；
- 副本数 n 允许 n-1 个节点故障。

#### 消费者组（Consumer Group）与 Offset
- 消费者以**组**为单位消费 Topic：**一个分区同一时刻只能被组内的一个消费者消费**（保证组内不重复、不乱序），但多个组可以同时消费同一个分区；
- **分区数 = 同组消费者的并行上限**：10 个分区最多 10 个消费者线程并行，多开的线程分不到分区，纯属浪费；
- 消费者用 **Offset（偏移量）** 记录自己读到哪了，可以重置 offset 回溯重新消费。

#### 协调者：ZooKeeper / KRaft
- 早期依赖 ZooKeeper 做元数据管理和集群选主，节点一多开销大；
- Kafka 3.3 引入内置的 **KRaft** 模式，**Kafka 4.0（2025）彻底移除 ZooKeeper**，只支持 KRaft。

### 面试怎么答
"Kafka 是分布式流式 MQ，核心是三层模型：Topic 分多个 Partition 并行存储，Partition 多副本 + Leader 选举保证高可用；消费端是消费组模型，一个分区同一时刻只能被组内一个消费者消费，分区数决定并行上限；消费者用 offset 记录进度，可回溯重放。协调者早期用 ZooKeeper，4.0 后纯 KRaft。"

### 比喻
Kafka 像**一个超大图书馆**：每本书（Topic）分成多册（Partition）放在不同书架上（Broker），每册都有几份复印本（副本）；读者（消费者）办卡成组，一组人分工各读各的册子，谁读到哪页用书签（offset）记录，可以翻回去重读。

## 10. Kafka 为什么这么快？

### 一句话回答
四大法宝：**顺序写磁盘、批量处理、零拷贝、消息压缩**。

### 展开讲：逐个解释

#### 法宝一：顺序写磁盘
Kafka 把所有消息**追加写到日志尾部**（顺序写），而不是到处乱写（随机写）。机械硬盘顺序写和随机写的速度差**几十倍**——顺序写时磁盘读写头只需移动一次。

#### 法宝二：批量处理
生产者可以**攒一批消息再发送**，减少网络开销和磁盘 I/O 次数。比如攒 1000 条发一次，I/O 次数直接降为 1/1000。

#### 法宝三：零拷贝（面试追问点）
Kafka 用 `sendfile` 系统调用，数据**直接从 page cache 送往网卡，完全不经过用户态**。

传统方式：磁盘 → 内核缓冲 → 用户缓冲 → 内核缓冲 → 网卡（4 次拷贝 + 2 次上下文切换）。
Kafka 零拷贝：磁盘 page cache → 网卡（DMA 直达，**1 次拷贝**）。

对比：RocketMQ 的 `mmap + write` 只是"广义零拷贝"——省去 read 的用户态拷贝，但 page cache 到 socket buffer 仍有一次 CPU 拷贝。

#### 法宝四：消息压缩
Kafka 支持消息压缩（gzip、snappy、lz4 等），**减少网络传输数据量**，提升整体吞吐。

### 面试怎么答
"Kafka 快靠四件事：顺序写磁盘（避开随机写硬伤）；批量发送（攒一批再发，减少 IO 次数）；零拷贝（sendfile 直接从 page cache 到网卡，不经过用户态）；消息压缩（减少网络传输量）。"

### 比喻
像**流水线工厂**：工人不再东跑西跑取料（顺序写），原料攒满一车再运（批量），传送带直达装车口不用人手搬（零拷贝），货品压缩打包再运输（压缩）——每一环都省掉多余动作。

## 11. Kafka 会丢消息吗？

### 一句话回答
**会，但都是配置/使用不当造成的**。Kafka 本身的设计允许高可靠，丢消息只发生在三个环节：生产端、Broker 端、消费端——每个环节都有对应的"防丢配置"。

### 展开讲：三个环节逐个分析

#### 环节一：生产端丢消息
**原因**：`acks` 参数配置不当。
- `acks=0`：发出去就不管，可能直接丢；
- `acks=1`：只要 Leader 存下就返回成功——Leader 还没同步给副本就挂了，消息丢失；
- `acks=all/-1`：必须等所有 ISR 副本都存下才算成功，最安全。

**对策**：关键业务配置 `acks=all`。

#### 环节二：Broker 端丢消息
**原因**：
1. **消息只在内存/页缓存**：Kafka 收到消息默认先写 OS Page Cache，由操作系统决定何时刷盘。如果配置了异步刷盘且机器突然断电，未落盘的消息就丢了；
2. **分区副本不足**：副本数=1 时，唯一副本所在机器宕机，数据全丢；
3. **unclean 选举**：开启 `unclean.leader.election.enable` 后，Leader 挂了会把"数据不全的副本"选为新 Leader，新 Leader 上没有的部分消息就丢了。

**对策**：多副本（如 3 副本）+ `acks=all` + 禁止 unclean 选举 + 关键场景同步刷盘。

#### 环节三：消费端丢消息
**原因**：**先提交 offset，再处理业务**——消息拉取后立即提交位移，然后处理业务时宕机，重启后 offset 已跳过，这批消息就丢了。

**对策**：**处理完业务再提交 offset**（手动提交，而不是自动提交），失败则不提交、下次重新消费。

### 总结表

| 环节 | 丢消息原因 | 防丢对策 |
|------|-----------|----------|
| 生产端 | `acks=0/1` 配置过松 | `acks=all` |
| Broker 端 | 副本不足、unclean 选举、未刷盘 | 多副本 + ISR + 禁 unclean + 同步刷盘 |
| 消费端 | 先提交 offset 后处理业务 | 处理成功后再提交 offset |

### 面试怎么答
"Kafka 丢消息都是配置问题：生产端 acks 调成 all；Broker 端保证副本数 ≥ 2 且不开 unclean 选举；消费端业务处理成功后再提交 offset。三个环节都按高可靠配置，Kafka 基本不会丢消息——但吞吐会有所下降，这是可靠性和性能的权衡。"

### 比喻
像**寄贵重物品**：你要求"签收回执"（acks=all）、多复印几份留存（多副本）、明确"本人签收后才行"（处理完再提交 offset）——每道手续都做齐，东西才不会丢。

## 12. Kafka 百万消息积压如何处理？

### 一句话回答
两个方向：**增加消费者实例**（但不超过分区数）或**增加分区数**（加完重新均衡消费组）；积压严重时用"**转存临时 Topic + 10 倍队列 + 10 倍机器**"的紧急扩容方案。

### 展开讲：分情况处理

#### 第一步：先排查是不是有 bug
积压的第一反应不是扩容，而是**先查消费者代码**——是不是调第三方接口超时、是不是慢查询、是不是死锁？bug 不修，扩再多机器也没用。

#### 第二步：不是 bug，怎么优化？
1. **优化消费逻辑**：之前一条一条消费，改成**批量处理**（一次拉一批、批量入库），消费速度立刻上几个台阶；
2. **水平扩容**：
   - **加消费者实例**：注意**消费者数量不能超过分区数**——一个分区同一时间只能被一个消费者消费，加再多消费者，超出分区的部分也没活干；
   - **加分区数**：分区多了并行度才高，创建新分区后需要**重新平衡消费组**。

#### 第三步：bug 导致几百万条积压几小时，紧急扩容方案（面试重点）
思路：**修 bug + 临时把消费能力放大 10 倍**。完整五步：

1. **先修复消费者问题**，恢复消费速度，然后把现有 consumer 全部停掉；
2. **新建一个临时 topic**，分区数是原来的 **10 倍**；
3. **写一个临时分发程序**：消费积压的数据，**不做耗时处理**，直接均匀轮询写入临时 topic 的 10 倍分区；
4. **临时征用 10 倍机器**部署 consumer，每台消费一个临时分区的数据——相当于把队列资源和消费资源都扩大 10 倍，以 10 倍速度消化积压；
5. **积压消化完**，恢复原先部署架构，用原来的 consumer 继续消费。

```text
 积压的老Topic（4个分区）
      │
      ▼
 [临时分发程序]（不做业务，只搬运）
      │
      ▼
 临时新Topic（40个分区 = 10倍）
      │
      ▼
 40台消费机器（10倍人手）──► 极速消化积压
```

> 为什么能加速：原来 4 个分区最多 4 台机器并行，现在 40 个分区 = 40 台机器并行，吞吐直接 ×10。

### 面试怎么答
"积压的本质是生产快于消费。我的处理顺序是：先排查消费者有没有 bug → 没有就批量消费、水平扩容（注意 Kafka 加消费者不能超过分区数，超了要加分区）→ 若已积压几百万条，用紧急扩容：新建 10 倍分区的临时 topic，写个纯搬运的临时 consumer 把积压消息转过去，再上 10 倍机器消费，消化完切回原架构。"

### 比喻
像**快递爆仓**：先查是不是分拣机坏了（bug）；没坏就开更多分拣口（加消费者，但口子数量有限）；口子真不够就临时租一个 10 倍大的中转仓，把包裹先搬过去，10 倍的人手同时分拣，清完再搬回来。

## 13. RocketMQ 和 Kafka 有什么区别？

### 一句话回答
**Kafka 赢在吞吐（日志流场景），RocketMQ 赢在业务功能（延迟消息、事务消息）**。选型口诀：只要收发包、要极致吞吐 → Kafka；要业务功能（延迟/事务消息）+ Java 技术栈 → RocketMQ。

### 展开讲：四大维度对比

#### 维度一：核心定位
- **Kafka**：为海量日志和数据流而生，分布式文件系统思维，少 Topic、大吞吐；
- **RocketMQ**：阿里为电商业务而生，数据库引擎思维，海量 Topic、功能全面。

#### 维度二：功能特性（RocketMQ 胜）

| 功能 | Kafka | RocketMQ |
|------|-------|----------|
| 延迟/定时消息 | 弱 | 支持（固定延迟级别） |
| 事务消息 | 弱（0.11+ 有事务 API，配置复杂） | 支持（半消息 + 回查） |
| 消息过滤 | 弱（消费端过滤） | 支持（Tag + SQL 过滤） |
| 消息回溯 | 按 offset 回溯 | 按时间回溯 |
| 管理控制台 | 一般 | 完善 |

#### 维度三：性能与架构（Kafka 胜）

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| 单机吞吐 | 10 万级+（十几万 QPS） | 10 万级（略逊） |
| 存储模型 | 独立分区文件（Topic 多时随机写） | CommitLog 混合存储（永远顺序写） |
| 零拷贝 | `sendfile` 真·零拷贝 | `mmap+write` 广义零拷贝 |
| 协调机制 | ZooKeeper / KRaft | 轻量 NameServer（节点间互不通信） |
| 高可用粒度 | 分区级选主 | 节点级主从切换 |

#### 维度四：消费确认机制

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| 消费端确认 | 提交 offset（"进度条"模式） | 逐条 CONSUME_SUCCESS / RECONSUME_LATER（"签收"模式） |
| 单条失败重试 | 弱（业务自己处理） | 强（内置重试队列 + 阶梯延迟 + 死信队列） |

### 怎么选？

| 需求 | 选择 |
|------|------|
| 只收发消息、可容忍小概率丢数据、要求极高吞吐 | **Kafka**（用户行为日志收集与传输） |
| 需要延迟队列、事务消息等业务功能 + Java 技术栈 | **RocketMQ** |

### 面试怎么答
"两者的核心差异：Kafka 是吞吐机器（十几万 QPS），但功能单一、配置不当会丢消息；RocketMQ 功能全（延迟/事务消息），吞吐 10 万级略逊。存储上 Kafka 独立分区文件、Topic 多时顺序写变随机写，RocketMQ 用 CommitLog 混合存储永远顺序写；零拷贝上 RocketMQ 是 mmap+write 的广义零拷贝，不如 Kafka 的 sendfile 彻底；协调上 Kafka 用 ZK/KRaft，RocketMQ 用轻量 NameServer。选型看场景：日志流选 Kafka，业务消息选 RocketMQ。"

### 比喻
Kafka 像**只装货不挑拣的传送带**（快、量大、功能少）；RocketMQ 像**全能的快递中心**（功能全、能处理挂号件、延迟件、保价件，但吞吐略逊）——运输队选传送带，快递公司选全能中心。

## 14. RocketMQ 为什么性能不如 Kafka？

### 一句话回答
三大差距：**零拷贝不彻底**（mmap+write vs sendfile）、**存储格式非零拷贝友好**、**批量与压缩机制不如 Kafka 极致**——但差距换来的是海量 Topic 下依然稳定的顺序写。

### 展开讲：逐个分析

#### 差距一：零拷贝（最关键）
- **Kafka**：`sendfile` **真·零拷贝**——数据从 page cache 直接 DMA 到网卡，**完全不经过用户态**，只有 1 次拷贝；
- **RocketMQ**：`mmap + write` 是**广义零拷贝**——省去了 read 系统调用中用户态与内核态的拷贝，但 page cache 到 socket buffer 仍有一次 **CPU 拷贝**。

一次数据拷贝的差距，在高吞吐场景（每秒几十万条消息 × 每条消息几 KB）下被放大成明显的性能差。

#### 差距二：存储格式
- **Kafka**：分区文件里消息是**紧挨着顺序存储**的（消息 → 消息 → 消息...），消费时整段读走，天然适配零拷贝；
- **RocketMQ**：CommitLog 混合存储 + ConsumeQueue 索引结构，消费者要先读 ConsumeQueue 拿位置，再定位到 CommitLog 里"掏"数据——多一层索引跳转，**无法像 Kafka 那样整段连续传输**，零拷贝的优势打折扣。

#### 差距三：批量与压缩
- **Kafka**：生产者批量发送是**核心设计**——攒一批、压缩（gzip/snappy/lz4）、一批传输，压缩率优化到极致；
- **RocketMQ**：批量发送和压缩能力相对弱，默认单条处理路径更重，IO 次数和传输字节数都更高。

### 为什么 RocketMQ 依然选 mmap？
这是**有意的取舍**：mmap 方式让 Broker 可以在用户态**灵活管理消息**（支持海量 Topic、按 Tag 过滤、消费进度精确管理），而这些是 sendfile 做不到的。Kafka 放弃灵活性换极致吞吐，RocketMQ 牺牲一点吞吐换业务功能——**没有谁更优，只有场景不同**。

### 面试怎么答
"RocketMQ 性能不如 Kafka 的核心是零拷贝：Kafka 用 sendfile，数据从 page cache 直接到网卡不经过用户态；RocketMQ 用 mmap+write，虽然省了一次用户态拷贝，但 page cache 到 socket buffer 还有一次 CPU 拷贝。加上 Kafka 批量发送和压缩更极致、消息紧挨存储适配零拷贝，吞吐就被拉开了。但这是 RocketMQ 有意的取舍——mmap 换来的是海量 Topic 下依然顺序写、事务消息、消息过滤等业务能力。"

### 比喻
Kafka 像**直达高速的集装箱专列**（车厢直接上船，不停站）；RocketMQ 像**市内配送车**（要查门牌号、按地址送货，灵活但慢一点）——一个为"量大从速"，一个为"服务到家"。
