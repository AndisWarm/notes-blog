## 1. OSI 七层网络模型是什么？

### 一句话回答
OSI 七层模型是国际标准组织提出的**理论参考模型**，从上到下是应用层、表示层、会话层、传输层、网络层、数据链路层、物理层；实际在用的是 **TCP/IP 四层模型**（应用层、传输层、网络层、网络接口层），Linux 就是按它实现的。

### 展开讲

**七层逐个看（从上到下）：**

| 层 | 职责 | 数据单元 | 典型协议/设备 | 生活类比 |
|----|------|----------|---------------|----------|
| 应用层 | 给应用程序提供统一接口，直接面向用户 | 报文（Message） | HTTP、DNS、FTP、SMTP | 你写的快递单 |
| 表示层 | 数据格式转换、加密压缩，让对方能识别 | 报文 | JPEG、ASCII、SSL/TLS（部分） | 翻译官，把中文译成英文 |
| 会话层 | 建立、管理、终止通信会话 | 报文 | NetBIOS、RPC | 约好通话时间并开始通话 |
| 传输层 | 端到端传输，保证数据完整到达，端口寻址 | 报文段（TCP 段 / UDP 数据报） | TCP、UDP | 快递分拣中心，保证包裹不丢不坏 |
| 网络层 | 寻址与路由，把数据从一台主机送到另一台 | 分组（数据报） | IP、ICMP；路由器 | 卡车按地图规划路线 |
| 数据链路层 | 相邻节点间传输，封帧、差错检测、MAC 寻址 | 帧（Frame） | 以太网、ARP；交换机 | 快递员按门牌号投递 |
| 物理层 | 在介质上传输比特流（0 和 1） | 比特（Bit） | 网线、光纤、集线器 | 马路、电线本身 |

**七层和四层的对应关系：**

| OSI 七层 | TCP/IP 四层 | 核心协议 |
|----------|-------------|----------|
| 应用层 + 表示层 + 会话层 | 应用层 | HTTP、DNS、FTP、SMTP |
| 传输层 | 传输层 | TCP、UDP |
| 网络层 | 网络层 | IP、ICMP |
| 数据链路层 + 物理层 | 网络接口层 | 以太网、Wi-Fi |

**三个要点：**
- 每层只干自己那摊事：应用层不管数据怎么走，物理层不懂 HTTP，各层通过"封装"（上层数据包上加上本层的头）逐层向下传递，接收方再逐层"解封装"
- OSI 七层是**概念理论，没有具体实现**，太复杂，实际没人完整用；TCP/IP 四层是事实标准
- 记忆口诀：七层从上到下「应表会传网链物」，四层从上到下「应传网链」

### 比喻
把网络比作寄快递：你写快递单（应用层）、快递公司分拣装车（传输层）、卡车按路线运输（网络层）、快递员按门牌号投递（数据链路层）、马路本身（物理层）。换快递员不影响你写字，换运输方式不影响分拣——每一层都是独立的，这正是分层存在的意义（详见第 2 节）。

## 2. 我们为什么需要 7 层 OSI 网络模型？

### 一句话回答
分层是为了让**复杂问题变简单**：每一层只负责一种职责，层与层之间用标准接口通信，任何一层可以独立替换升级，出了问题也能快速定位是哪一层的锅。

### 展开讲

**分层的四大好处：**

| 好处 | 具体表现 |
|------|----------|
| 职责单一 | 每层只做一件事：应用层管内容、传输层管可靠、网络层管找路、链路层管相邻传输，互不掺和 |
| 标准化 | 层与层之间的接口是公开标准，任何厂商按标准做都能互通，不用关心别人内部怎么实现 |
| 模块化 | 某层可以独立升级替换：今天用光纤（物理层），明天换 5G，上层代码一行不用改 |
| 便于排查 | 网络出问题按层排查：先看网线通不通（物理层），再 ping 通不通（网络层），再测端口（传输层），再抓包看应用数据（应用层），层层缩小范围 |

**为什么不直接搞一个"万能协议"？**
- 网络通信太复杂：要跨设备、跨运营商、跨国家，要处理信号、路由、拥堵、丢包、加密、应用格式……一件事里塞太多职责，谁也做不好，改一个点全盘重来
- 分层把"一个大问题"拆成"几个小问题"，每个小问题单独解决、单独演进，这是计算机领域通用的"分而治之"思想

**分层的代价：**
- 每过一层要加一个头部（封装），多了一点额外开销
- 某些功能放哪层有争议（比如加密，OSI 放在表示层，现实中 HTTPS 却在应用层和传输层之间加了个 SSL/TLS 层）
- 这就是为什么现实中没有完美按七层实现——七层是"理论课本"，四层是"实用主义"

### 比喻
分层就像**邮政系统**：写信的人只负责写内容（应用层），邮局负责分拣、贴邮票、按地址分类（传输层），运输车队负责把信从城市 A 送到城市 B（网络层），投递员负责按门牌号送到你家（链路层），公路铁路本身是物理层。你写信不用关心火车还是飞机运，换邮局也不用改写信格式——每层各管一段，整条链路才跑得起来。出了问题也好查：信没送到，先问运输的（网络层），再问投递的（链路层），而不是把整条链路拆了重来。

## 3. CDN 是怎么工作的？

### 一句话回答
CDN（内容分发网络）把网站的静态资源**提前复制到全国各地乃至全球的边缘节点**上，用户请求时通过 **DNS 调度**把用户导向"离他最近"的节点，由边缘节点直接返回缓存内容，源站只负责在缓存没有时被"回源"一次。

### 展开讲

**一次完整的 CDN 请求流程（以访问一张图片为例）：**

```
用户输入域名 → ① 本地 DNS 查询
            → ② DNS 返回 CDN 专用的 CNAME 记录
            → ③ 请求转到 CDN 的智能调度系统（GSLB）
            → ④ GSLB 根据用户 IP 所在地、网络运营商、节点负载，
                 返回"离用户最近、最快"的边缘节点 IP
            → ⑤ 用户请求到达边缘节点
            → ⑥ 边缘节点查缓存：
                  命中 → 直接返回（快，一次搞定）
                  未命中 → 回源站拉取 → 缓存到本地 → 返回用户
```

**四个关键环节：**

| 环节 | 干什么 | 类比 |
|------|--------|------|
| DNS 调度 | 把不同用户解析到不同节点 IP，实现"就近接入" | 快递分拣中心按收货地址把包裹分到不同片区 |
| 边缘节点 | 部署在用户身边的机房，缓存静态资源 | 小区门口的快递驿站，货放家门口 |
| 缓存 | 资源第一次被请求后留在节点上，后续直接命中 | 驿站收到包裹后放货架，再来取直接给 |
| 回源 | 缓存没有 / 过期时，节点去源站拉最新内容 | 驿站没货了，才去总仓库调货 |

**缓存命中与失效：**
- 命中（Cache Hit）：节点上有资源且没过期，直接返回，用户无感知，源站零压力
- 未命中（Cache Miss）：第一次访问或缓存过期，节点回源拉取并更新缓存
- 过期时间由 HTTP 缓存头（Cache-Control、Expires）控制；源站内容更新后可以"主动刷新"CDN 缓存

**典型场景：**
- 大促秒杀：图片、JS、CSS 全走 CDN，源站只扛接口请求
- 视频点播：视频文件巨大，放 CDN 上避免源站带宽被打爆
- 跨国访问：海外用户访问国内网站，CDN 在海外有节点，不用跨洋传输

### 比喻
CDN 就像**连锁便利店**：源站是总仓库，边缘节点是开在你家楼下的分店。总仓库把热销商品提前配送到各分店，你买东西直接去楼下分店拿，不用每次都打车去总仓库。分店没货了才打电话让总仓库调货（回源），调来的货还会留在分店（缓存），下次再来直接拿。

## 4. 你懂 CDN 吗？

### 一句话回答
CDN 的本质是"**用空间换时间、用距离换速度**"：通过遍布各地的缓存节点缩短用户和内容之间的物理距离，同时把流量压力从源站分散到边缘，源站只做"内容生产"，CDN 做"内容分发"。

### 展开讲

**CDN 与源站的关系：**
- 源站是内容的"生产者"（你的服务器），CDN 是内容的"搬运工和仓库"
- 用户看到的数据来自边缘节点，但数据的"最终权威版本"在源站
- 接入方式：域名解析从"直接指向源站 IP"改为"CNAME 到 CDN 调度域名"，源站 IP 可以隐藏，反而更安全

**加速原理（为什么快）：**
| 加速点 | 原理 |
|--------|------|
| 距离近 | 边缘节点在用户本地/就近城市，网络往返时间（RTT）大幅缩短 |
| 带宽大 | CDN 节点带宽充裕，扛得住高并发，用户不用挤源站的小水管 |
| 命中即得 | 缓存命中时数据不出本地网络，速度接近本地读取 |
| 多节点容灾 | 某个节点挂了，调度系统自动把用户导向其他节点，不中断服务 |

**静态加速 vs 动态加速：**
- 静态加速：图片、CSS、JS、视频等"内容固定"的资源，边缘缓存，命中率高，是 CDN 的主场
- 动态加速：接口、登录、购物车等"因人而异"的内容不能缓存，CDN 做的是"优化链路"——通过智能路由选择最快路径到源站，配合 TCP 优化、连接复用来提速

**回源策略（进阶点）：**
- 缓存时间（TTL）：按资源类型设置，图片设长、接口设短
- 回源鉴权：节点回源时带上密钥，防止别人绕过 CDN 直接打源站
- 刷新与预热：内容更新后手动刷新缓存；大促前把热点资源提前"预热"到各节点
- 回源超时和并发限制：防止回源请求把源站压垮

**防刷（CDN 的护城河）：**
- Referer 防盗链：只允许自己网站引用图片
- 鉴权 URL：带签名和时间戳的链接，过期作废
- 访问频率限制 + IP 封禁：识别恶意请求
- 搭配 WAF（Web 应用防火墙）拦截攻击流量，源站 IP 不暴露，攻击者找不到"老巢"

### 比喻
CDN 像**大型连锁超市的供应链**：超市（CDN）在你家附近开店并囤货（缓存），你随时能买到；货架空了才通知总部（源站）补货（回源）。总部不需要在你家门口开工厂，也不用接待每个顾客，只负责生产（出内容）和给分店供货（回源），压力小很多。而防盗链和鉴权，就像超市只认会员卡、限购和查小票，防止别人白嫖货架。

## 5. 你知道哪些网络攻击？

### 一句话回答
面试常考六种：**XSS**（往网页里注入脚本偷数据）、**CSRF**（借已登录用户的手发请求）、**SQL 注入**（把恶意 SQL 拼进查询）、**DDoS**（用海量流量淹没服务器）、**中间人攻击**（通信双方之间插一脚偷听篡改）、**DNS 劫持**（把域名解析到钓鱼站）。

### 展开讲

**① XSS 跨站脚本攻击**
- 原理：网站把用户输入直接渲染到页面，攻击者提交的内容里夹带 `<script>` 代码，别人访问页面时代码在浏览器里执行
- 三类：存储型（脚本存服务器，所有访问者中招）、反射型（脚本经 URL 参数带进来）、DOM 型（前端代码被恶意修改执行）
- 危害：盗取 Cookie、劫持会话、模拟用户操作
- 防御：输入验证过滤、输出编码转义、CSP 限制脚本来源、Cookie 加 HttpOnly（JS 读不到）

**② CSRF 跨站请求伪造**
- 原理：你在银行 A 登录着（Cookie 还在），攻击者让你访问恶意网站 B，B 里藏着一个发往银行 A 的转账请求，浏览器自动带上你的 Cookie，服务器以为是"你本人"操作
- 关键：攻击者不需要拿到你的 Cookie，只需要"借你的手"
- 防御：CSRF Token（核心）、校验 Referer、关键操作二次确认、JWT 放请求头而不是 Cookie

**③ SQL 注入**
- 原理：用户输入被直接拼进 SQL 语句执行，比如输入 `' OR '1'='1` 让条件恒为真，一次查出全表数据
- 危害：拖库、删库、篡改数据
- 防御：参数化查询（根治，输入永远只是"数据"不是"代码"）、输入校验转义、限制数据库权限

**④ DDoS 分布式拒绝服务**
- 原理：攻击者用僵尸网络（被恶意软件控制的肉鸡）同时向目标发海量流量，把带宽和连接资源耗尽，正常用户访问不了
- 危害：服务瘫痪，业务损失
- 防御：带宽扩容、流量清洗（滤掉恶意流量）、负载均衡、防火墙与访问控制

**⑤ 中间人攻击（MITM）**
- 原理：攻击者站在通信双方中间，同时冒充对方，窃听甚至篡改数据，双方还毫无察觉
- 典型场景：连了恶意 Wi-Fi、DNS 被篡改后流量被引到攻击者那里
- 防御：HTTPS 加密传输（TLS 证书验证身份），让中间人"看不见也改不了"

**⑥ DNS 劫持**
- 原理：篡改 DNS 解析结果，把域名解析到攻击者控制的虚假 IP，用户以为上了真网站，实际进了钓鱼站
- 危害：输入账号密码被直接收走；域名没变、页面却不对
- 防御：用可信 DNS（DoH/DoT 加密 DNS）、检查 hosts 文件和路由器 DNS 配置、网站部署 HTTPS + HSTS

**速记表：**

| 攻击 | 一句话记住 | 核心防御 |
|------|-----------|----------|
| XSS | 往页面注入脚本，在浏览器里偷东西 | 输入验证、输出编码、HttpOnly |
| CSRF | 借已登录用户的手发伪造请求 | CSRF Token、Referer 校验 |
| SQL 注入 | 输入拼进 SQL 被当成代码执行 | 参数化查询（根治） |
| DDoS | 僵尸网络海量流量淹没目标 | 流量清洗、扩容、负载均衡 |
| 中间人 | 在通信中间偷听篡改 | HTTPS/TLS 证书验证 |
| DNS 劫持 | 篡改解析结果指向钓鱼站 | 可信 DNS、HTTPS + HSTS |

### 比喻
- XSS 像**在超市货架上偷偷贴假标签**，顾客照着标签买单，钱进了骗子口袋（脚本在别人浏览器里执行）
- CSRF 像**骗子借用你的手签合同**，合同是你的笔迹，责任却由你承担（浏览器自动带 Cookie）
- DDoS 像**雇了一群人在店门口堵着**，真顾客进不去，店再大也没用
- 中间人攻击像**快递被偷偷拆开看过又封上**，你以为原封未动，其实内容早被改了

## 6. 程序是怎么一步步运行起来的？

### 一句话回答
一条完整的链路：**源代码 → 编译（预处理、编译、汇编）→ 链接 → 装载（加载进虚拟内存）→ CPU 取指执行**。编译器把"人写的代码"变成"机器认识的指令"，操作系统把指令装进内存，CPU 一条条取出来执行。

### 展开讲

**第一步：编译——把人话翻译成机器话**
- 预处理：展开头文件、替换宏定义
- 编译：把 C 代码翻译成**汇编代码**（更接近机器的语言）
- 汇编：把汇编代码翻译成**机器指令**（0 和 1 组成的二进制），得到目标文件（.o）
- 这个阶段解决的是"语言问题"：从人能读的语法变成 CPU 能读的指令

**第二步：链接——把散件拼成整机**
- 一个程序往往由多个目标文件 + 库文件组成，链接器把它们拼在一起，**解析符号引用**（你在 a.c 里调用 b.c 的函数，链接器负责把"调用"指到"定义"那里）
- 静态链接：把库代码直接复制进可执行文件（体积大，但发布简单）
- 动态链接：可执行文件只记录"运行时去哪个 .so/.dll 找"，程序跑起来才加载（省磁盘省内存，但依赖环境）
- 产物：**可执行文件**（ELF 格式，Linux；PE 格式，Windows），里面是机器指令 + 数据 + 各种段

**第三步：装载——从硬盘搬进内存**
- 用户双击/敲命令运行程序，操作系统创建**进程**，加载器（Loader）把可执行文件按段装入**虚拟内存**
- 关键点：装的是"虚拟地址"，不直接对应物理内存，靠**页表 + MMU** 做地址映射，物理内存不够时靠换页（详见第 10 节）
- 装载完成后，CPU 从程序的入口点（main 函数）开始执行

**第四步：CPU 取指执行——真正跑起来**
- CPU 按**冯·诺依曼"存储程序"思想**工作：程序和数据都在内存里，CPU 不断重复"取指令 → 译码 → 执行 → 写回"
- 取指：按程序计数器（PC）指向的地址，把指令从内存取出来
- 译码：搞清楚这条指令要干什么（加法？跳转？读内存？）
- 执行：让运算器真正干活
- 写回：把结果存回寄存器或内存

**指令流水线：**
- 现代 CPU 不傻等一条指令跑完再取下一条，而是把"取指、译码、执行、写回"拆成几个阶段，像工厂流水线一样**同时处理多条指令的不同阶段**——第一条在执行时，第二条已经在译码，第三条正在取指
- 好处：一个时钟周期能"流出"一条完成结果的指令，吞吐量大幅提升
- 代价：遇到跳转（if/循环）流水线可能"断流"，所以有分支预测技术提前猜

### 比喻
编译链接像**做菜**：源代码是菜谱文字（人能读），编译是把它翻译成厨师的动作指令（机器指令），链接是把"切菜、炒菜、装盘"几个模块拼成一套完整流程（可执行文件），装载是备好食材上灶台（进内存），CPU 取指执行就是厨师按指令一步一步把菜做出来。指令流水线则是**多个厨师协作的流水线厨房**：一个切菜、一个炒菜、一个装盘，同一时间各干各的活，出菜速度自然快。

## 7. 操作系统是怎么一步步启动起来的？

### 一句话回答
加电后大致走五步：**固件（BIOS/UEFI）自检 → 引导程序（Bootloader）→ 加载内核 → 内核初始化 → 启动第一个用户进程（init/systemd）拉起所有服务**。核心思想是"层层接力"：小代码引导大代码，最终把整个操作系统拉起来。

### 展开讲

**Linux 启动五步：**

```
① 加电 → BIOS/UEFI 固件
     POST 自检：检查 CPU、内存、显卡等硬件是否正常
     从启动盘（硬盘/SSD）读取引导程序
② 引导程序（GRUB）
     展示/读取启动菜单，找到内核文件（vmlinuz），
     把内核镜像加载到内存
③ 内核加载与初始化
     解压内核，初始化内存管理、进程管理、设备驱动等子系统，
     挂载根文件系统
④ 启动 init 进程（PID 1）
     传统 SysV：init 按 /etc/inittab 跑启动脚本
     现代发行版：systemd 按单元（unit）并行启动服务
⑤ 服务启动
     网络、SSH、数据库、定时任务等依次（或并行）拉起来
     出现登录界面 → 启动完成
```

**BIOS 和 UEFI 的区别：**
| 对比项 | BIOS（老） | UEFI（新） |
|--------|-----------|-----------|
| 引导方式 | 读硬盘第一个扇区（MBR）里的引导程序 | 直接从 GPT 分区的 EFI 系统分区读引导文件 |
| 磁盘支持 | MBR 只支持 2TB 以内 | GPT 支持大磁盘和更多分区 |
| 速度 | 慢 | 快（可并行初始化） |
| 安全性 | 无 | 支持安全启动（Secure Boot，防恶意引导代码） |

**Windows 启动（对照着记）：**
```
加电 → UEFI/BIOS → 读引导程序（bootmgr）
     → 加载 winload.exe
     → 加载内核 ntoskrnl.exe + 硬件抽象层（HAL）
     → 内核初始化 → 会话管理器（smss）启动子系统
     → 登录进程（winlogon）→ 桌面服务 → 进入登录界面
```
Windows 和 Linux 本质相同：固件 → 引导程序 → 内核 → 第一个用户进程 → 服务。区别只是名字和实现。

**为什么非要"层层接力"？**
- 加电瞬间，内存里什么都没有，CPU 只能执行**固定地址**的固件代码（BIOS 芯片里的程序），所以第一步必须从固件开始
- 固件本身很小，装不下整个操作系统，所以它只负责"把引导程序找出来"，引导程序再负责"把内核搬进内存"，内核再负责"把用户空间拉起来"——每一层只做一点点，层层放大

### 比喻
启动过程像**接力赛**：固件是第一棒（只跑一小段：自检 + 找队友），引导程序是第二棒（把内核这位"主将"送进场），内核是第三棒（安顿好场地：内存、进程、驱动），init 是最后一棒（把各个服务选手都叫上场）。任何一棒掉了，整场比赛都完不成。也可以比作**装修房子**：先通电验房（自检），再叫物业开门（引导程序），装修队进场布置水电（内核初始化），最后家具家电进场（启动服务）。

## 8. 进程切换的本质是什么？

### 一句话回答
进程切换的本质是**上下文切换**：把当前进程的运行现场（寄存器、程序计数器、栈指针等）保存到它的 PCB（进程控制块）里，再把下一个进程之前保存的现场恢复出来，让 CPU 接着"上次断掉的地方"继续跑。

### 展开讲

**先理解"上下文"是什么：**
- 一个进程在 CPU 上跑，靠的是寄存器里那一堆状态：程序计数器（PC，下一步执行哪条指令）、通用寄存器（中间计算结果）、栈指针（函数调用到哪了）、状态寄存器（各种标志位）
- 这些"正在跑"的状态合起来叫**CPU 上下文**，一旦切换进程，这些状态不保存就会丢

**PCB（进程控制块）是什么：**
- 操作系统给每个进程建的一张"身份证+档案"，记录：进程 ID、状态（就绪/运行/阻塞）、寄存器现场、内存信息（页表指针）、打开的文件、调度信息（优先级、时间片）等
- 进程的一切信息都在 PCB 里，切换进程 = 切换"当前 PCB"和"下一份 PCB"

**上下文切换的完整过程：**

```
进程 A 正在运行
  → ① 触发切换（时间片用完 / 系统调用 / 中断 / 进程主动让出）
  → ② CPU 从用户态切换到内核态（调度器是内核代码，用户态没权限）
  → ③ 把进程 A 的寄存器现场保存进 A 的 PCB
  → ④ 从进程 B 的 PCB 恢复寄存器现场（含页表指针、PC）
  → ⑤ CPU 回到用户态，从 B 上次停下的指令继续执行
```

**为什么必须经过内核态？**
- 进程调度、PCB 操作都是操作系统的特权活，普通程序没有权限动别人的 PCB
- 所以每次进程切换至少包含"用户态 → 内核态 → 用户态"的往返，这本身就是开销

**切换的代价（为什么频繁切换性能差）：**
| 代价 | 说明 |
|------|------|
| 直接开销 | 保存/恢复寄存器和 PCB 的时间，两次态切换的系统调用开销 |
| 间接开销 | 切走一个进程，它的**缓存（Cache）和 TLB（快表）全失效**，换回来的进程重新加载，命中率下降；指令流水线也要重新预热 |
| 数量级 | 一次进程切换大概几百到几千个时钟周期，看起来小，但高并发下每秒成千上万次切换就是巨大浪费 |

**线程切换和进程切换的区别：**
- 同一进程内的线程切换：共享地址空间（页表不用换），只保存线程自己的寄存器和栈，开销小
- 进程切换：地址空间都换了（页表、TLB 全换），开销大
- 这也是"多线程比多进程更轻"的根本原因

### 比喻
进程切换像**舞台上的演员换场**：每个演员（进程）有自己的剧本、道具和站位（寄存器状态），换场时必须把上一个演员的所有道具和位置记录下来（存进 PCB），下一个演员按自己的记录重新摆好（恢复现场）。记录和重新摆位都要时间，如果每秒换几十次场，时间全浪费在"摆道具"上——所以系统要尽量减少切换，就像节目单要合理安排演员连续演出。

## 9. 并发和并行是一回事吗？

### 一句话回答
不是。**并发**是"看起来同时发生"——一个 CPU 在极短时间内轮流处理多个任务（交替执行）；**并行**是"真的同时发生"——多个 CPU 核同时处理多个任务（同时执行）。

### 展开讲

**核心区别：**

| 对比项 | 并发 | 并行 |
|--------|------|------|
| 本质 | 交替执行（时间上轮流） | 同时执行（同一时刻都在跑） |
| 硬件要求 | 单核 CPU 就能做到 | 必须多核 / 多 CPU |
| 关注点 | 任务之间的调度、切换、协作 | 任务是否真的分摊到不同核心 |
| 例子 | 一个厨师轮流做三桌菜 | 三个厨师同时各做一桌 |

**详细解释：**
- 单核 CPU 一次只能执行一条指令，但操作系统用**时间片轮转**把 CPU 切成一小段一小段的（比如每段几十毫秒），任务 A 跑一会儿、任务 B 跑一会儿、任务 C 跑一会儿……因为切换得极快（毫秒级），人感觉"同时在进行"，这就是并发
- 多核 CPU 上，任务 A 在核 1 跑的同时，任务 B 在核 2 跑，同一时刻真的有两件事在发生，这就是并行
- 一句话：**并发是"逻辑上的同时"，并行是"物理上的同时"**；并行是并发的一种"升级形态"（多核让并发变成了真正的并行）

**场景举例：**
- 单核机器上跑 10 个程序：只能并发（轮流用 CPU），不可能并行
- 双核机器上跑 2 个程序：可以并行（各占一核）
- 线程池、协程、异步编程解决的都是"并发"问题——把等待时间让出去，让 CPU 去干别的，不一定需要多核

**和线程/进程的关系：**
- 进程和线程是操作系统提供"并发"的载体：一个进程内多个线程并发执行，多核时这些线程可以并行
- 线程数 > CPU 核数时，必然有线程在"排队等 CPU"，这部分是并发；核数够多时，可以真并行
- 面试常问的"多线程一定快吗"：如果任务是 CPU 密集且核数有限，开太多线程反而因为切换开销变慢；如果是 I/O 密集（等网络、等磁盘），多线程并发能大幅提速——因为等待时间被别的线程利用了

### 比喻
并发像一个**一个人同时照看三壶开水**：这壶看一眼、那壶看一眼，水开前干别的，轮着来——看似三壶都在"被照看"，其实只有一个你（单核）。并行是**三个人各守一壶水**：同一时刻真的有三个人在等三壶水开（三核）。家里只有一个灶（单核），就只能轮流炒菜；有三个灶（多核），才能三个锅同时炒。

## 10. 内存分页和分段有什么区别？

### 一句话回答
**分页**是把内存切成**固定大小**（Linux 默认 4KB）的页，按"块"管理，用户无感知；**分段**是按程序的**逻辑结构**（代码段、数据段、栈段）切分成大小不一的段，用户看得见。分页没有外部碎片但有内部碎片，分段相反；分页用页表，分段用段表。

### 展开讲

**分页（Paging）：**
- 把虚拟内存和物理内存都切成固定大小的块：虚拟的叫"页"（Page），物理的叫"页框"（Page Frame），Linux 默认 4KB
- 地址转换：虚拟地址 = **页号 + 页内偏移**，MMU 拿页号查**页表**得到物理页框号，加上偏移就是物理地址
- 特点：
  - 页的大小固定，管理简单，物理内存分配就像"按格子发宿舍"，页与页紧密排列，**没有外部碎片**
  - 但程序不可能正好用完一页，最后那页剩的空间就浪费了——**内部碎片**（平均每进程浪费半页）
  - 对用户完全透明，程序员感知不到分页的存在
  - 页表可能很大，用多级页表 + TLB 快表优化

**分段（Segmentation）：**
- 按程序逻辑划分：代码段、数据段、栈段、堆段，每段大小不固定，符合程序员的思维
- 地址转换：虚拟地址 = **段号 + 段内偏移**，查**段表**得到段基地址，加上偏移得到物理地址
- 特点：
  - 段是逻辑单位，**便于共享和保护**（代码段可以设为只读共享，多进程共用一份）
  - 段的大小不固定，频繁分配释放会在段与段之间留下小空隙——**外部碎片**，久了碎片多了内存利用率下降，需要"紧凑"（把段挪到一起）
  - 对用户可见（程序员能感知"我的代码段、数据段"）

**对比表：**

| 对比项 | 分页 | 分段 |
|--------|------|------|
| 划分方式 | 固定大小（4KB），物理划分 | 按逻辑结构，大小可变 |
| 用户是否可见 | 透明，用户无感知 | 可见，符合程序员思维 |
| 地址空间 | 一维（页号+偏移） | 二维（段号+段内偏移） |
| 映射表 | 页表 | 段表 |
| 外部碎片 | 没有 | 有 |
| 内部碎片 | 有（不足一页也占一页） | 基本没有 |
| 共享与保护 | 较麻烦 | 方便（按段设置权限） |
| 典型使用者 | Linux 等现代操作系统 | 早期系统、部分架构 |

**段页式（结合两者）：**
- 先按逻辑分段（用户视角），再把每段分成固定大小的页（管理视角）
- 地址 = 段号 + 段内页号 + 页内偏移，先查段表再查页表
- 好处：既有分段"符合逻辑、便于共享保护"的优点，又有分页"无外部碎片、管理方便"的优点
- 代价：两次查表，地址转换更复杂（靠 TLB 缓解）

**虚拟内存和这俩什么关系？**
- 虚拟内存是"操作系统给程序画的大饼"：程序以为自己有连续的大内存，实际靠页表/段表映射到零散的物理内存，不够还能换到磁盘（swap）
- 现代系统普遍用**分页实现虚拟内存**；分段更多作为一种"逻辑组织"概念保留（如程序的内存布局：代码段、数据段、堆、栈）

### 比喻
分页像**酒店按标准间分配房间**：房间大小统一（4KB），客人来多少都按整间给，房间之间没有缝隙浪费（无外部碎片），但一个人住双人间就浪费了半个房（内部碎片）。分段像**按家庭大小分配住房**：一家三口住小三居、五口住大四居，户型贴合需求（无内部碎片），但不同户型拼接处容易留下用不上的边角料（外部碎片）。段页式则是**先按家庭选户型，再统一按标准间装修**：户型贴合需求，房间又能整齐拼接。

## 11. malloc 内存分配器是怎样实现的？

### 一句话回答
malloc 不是系统调用，而是 **C 库里的内存分配器**：小内存（小于约 128KB）用 **brk** 把堆顶往上推，大内存用 **mmap** 在文件映射区申请；内部用**空闲链表**管理小块，按 first-fit/best-fit 等策略找空闲块；为了性能，主流实现（ptmalloc、tcmalloc）都采用**内存池**思想。

### 展开讲

**malloc 和操作系统的关系：**
- 直接找操作系统要内存要用系统调用，但每次系统调用都有开销，所以 malloc 先向系统"批发"一大块，再自己"零售"给程序——这是**内存池**思想
- 底层两种系统调用：

| 方式 | 干什么 | 特点 |
|------|--------|------|
| brk / sbrk | 把堆顶指针往高地址移动，在堆上分配 | 适合小内存（<128KB）；释放后不还给系统，留在堆里复用；多次分配释放容易产生碎片 |
| mmap | 私有匿名映射，在文件映射区拿一块 | 适合大内存（>128KB）；释放时直接归还操作系统 |

- 阈值：glibc 默认约 **128KB**（不同版本略有差异），小于走 brk，大于走 mmap

**分配器内部怎么管内存：**
- 把内存切成块（chunk），每个块头部记录"大小 + 是否空闲"
- 空闲块用**双向链表**串起来（空闲链表），分配时遍历找块：
  - first-fit：找到第一个够大的就用（快，但可能把大块切碎）
  - best-fit：找最接近需求大小的（省内存，但遍历慢）
- free 时把块标记为空闲，并尝试和相邻空闲块**合并**，减少碎片
- 碎片问题：brk 方式堆是从低到高的，如果高地址的块没释放，低地址的块释放了也没法还给系统，只能留在堆里；小块频繁申请释放还会把大块切成碎片，久了"内存明明够却申请不到连续大块"

**主流实现：**
- **ptmalloc（glibc 默认）**：把空闲块按大小分类放进不同的"箱子"（bin），按大小快速找到合适箱子；支持多线程（每个线程有自己的 arena 减少锁竞争）。缺点：多线程下锁竞争仍存在，内存碎片控制一般
- **tcmalloc（Google）**：核心是**线程本地缓存（Thread-Cache）**——每个线程先在自己私有的小池子里分配，不用加锁，线程缓存不够才去中心堆取；还按大小分级（小对象从固定大小池取，大对象走页级分配）。高并发场景性能明显优于 ptmalloc
- **jemalloc（Facebook）**：类似思路，大厂中间件（Redis 等）常用

**面试常问细节：**
- malloc 后马上就有物理内存吗？没有。malloc 只拿到**虚拟内存**，真正读写时才触发**缺页异常**去分配物理内存
- free 的内存一定还给系统吗？不一定。brk 的小块内存留在堆里复用；mmap 的大块才真正归还
- 为什么 malloc 1KB 和 1MB 行为不同？1KB 走 brk（堆）、1MB 走 mmap（文件映射区），分配区域和释放行为都不同

### 比喻
malloc 像**批发商零售**：程序是顾客，操作系统是生产厂家。厂家只接大宗订单（系统调用），一次一小包太浪费，所以批发商（malloc）先整卡车进货（brk/mmap），再分装零售给顾客。空闲链表像**仓库的货架登记本**：每块空货架记着位置和大小，顾客来取货就翻本子找合适的（first-fit 是找到第一个能装下的，best-fit 是找装得最贴合的）。tcmalloc 则像**每个售货员自己带个小挎包**：小件直接从小挎包拿，不用每次跑大仓库排队（线程本地缓存，免锁），人多时优势特别明显。

## 12. 你知道几个网络 I/O 模型？

### 一句话回答
五种：**阻塞 I/O、非阻塞 I/O、I/O 多路复用（select/poll/epoll）、信号驱动 I/O、异步 I/O（AIO）**。核心区别是"**谁在等、怎么等**"——阻塞是自己干等；非阻塞是边干边问；多路复用是"一个人帮一帮人等"；信号驱动和异步都是"交给内核，好了叫我"，区别在叫你的时机。

### 展开讲

**① 阻塞 I/O**
- 发起读写后**一直等着**，内核把数据准备好、拷贝完才返回
- 简单直接，但等待期间 CPU 闲着，一个线程只能服务一个连接
- 类比：打电话订餐，挂电话前一直干等

**② 非阻塞 I/O**
- 发起后立即返回（没数据就返回"还没好"），但要**不断轮询**检查
- 不浪费等待时间，但轮询本身消耗 CPU，还要配合多路复用才实用
- 类比：点完外卖不干等，但每隔一分钟刷一次手机

**③ I/O 多路复用（select/poll/epoll）**
- **一个线程同时盯着成千上万个连接**，谁就绪处理谁
- select：把整个文件描述符集合拷进内核遍历（O(n)），有 1024 上限
- poll：用动态数组突破 1024，但仍要遍历 + 拷贝，O(n)
- epoll：内核用红黑树维护监听的 socket，事件发生通过回调加入就绪链表，只返回有事件的（O(1)），几乎不拷贝——解决 C10K 的利器，Nginx、Redis 的基石

| 对比项 | select | poll | epoll |
|--------|--------|------|-------|
| 数据结构 | 固定 BitsMap | 动态数组 | 内核红黑树 + 就绪链表 |
| 上限 | 1024 | 系统上限 | 系统上限 |
| 查找效率 | 遍历 O(n) | 遍历 O(n) | 回调就绪 O(1) |
| 数据拷贝 | 进出各一次 | 进出各一次 | 几乎无 |

**④ 信号驱动 I/O**
- 发起后继续干别的，内核**第一阶段（数据准备好）**完成后发信号通知，用户再去把数据从内核拷到用户空间
- 第二阶段（拷贝）仍然阻塞，属于"半异步"

**⑤ 异步 I/O（AIO）**
- 发起后完全撒手，内核**把整个读写做完**（包括拷贝到用户缓冲区）再通知
- 全程不阻塞，是真正意义上的异步，但实现复杂、Linux 原生 AIO 支持有限

**五种模型对比表：**

| 模型 | 发起后 | 谁在等 | 通知方式 | 是否真异步 |
|------|--------|--------|----------|-----------|
| 阻塞 I/O | 干等 | 自己 | 无（直接返回结果） | 否 |
| 非阻塞 I/O | 立即返回 | 自己轮询 | 轮询检查 | 否 |
| I/O 多路复用 | 立即返回 | 内核帮忙盯着一堆 | select/poll/epoll 通知 | 否 |
| 信号驱动 I/O | 干别的 | 内核（数据准备好阶段） | 信号通知，再自己拷贝 | 半异步 |
| 异步 I/O | 干别的 | 内核（全过程） | 完成回调通知 | 是 |

**实际工程怎么选：**
- 高并发服务器（Nginx、Redis、Netty）几乎都用 **I/O 多路复用 + Reactor 模式**：一个线程监听所有连接的事件，谁有事处理谁
- 多路复用不是"异步"，它只是"一个线程同时等很多 I/O"；数据拷贝还得用户态自己干
- 追求极致性能还可以上零拷贝（sendfile）：把"磁盘 → 网卡"的数据搬运全交给 DMA，减少拷贝和上下文切换

### 比喻
- 阻塞 I/O：**在餐厅门口站着等位**，啥也干不了
- 非阻塞 I/O：**拿了个叫号器，但不时去问"到我了没"**（轮询）
- 多路复用：**一个前台小姐姐同时盯着大厅所有顾客**，谁举手就服务谁（epoll 还升级成"顾客举手时前台自动被提醒"，不用挨个扫视）
- 信号驱动：**让服务员"菜好了叫我"，但你自己还得去端菜**（数据拷贝还是自己的活）
- 异步 I/O：**全包服务**——点完单去干别的，服务员做好菜直接端到你桌上再叫你
