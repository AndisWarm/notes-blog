05 Cookie、Session 与 JWT¶

面试问法：HTTP 为什么无状态 / Cookie vs Session / Session vs Token / 禁用 Cookie 怎么办 / localStorage / JWT 全家桶 / CSRF 与三件套的关系。 共 14 题，是"会话保持"主题的高频考点群。

Q1 HTTP 到底是不是无状态的？¶

一句话答案¶

HTTP 协议本身是无状态的——每个请求相互独立，服务器不保留客户端的状态信息；但可以靠 Cookie + Session 等机制"补上"状态保持的能力。

大白话讲解¶

无状态 = 服务器"不记人"。每次请求都是新的，它不知道"你是谁、之前干过什么"。

为什么要无状态？ 因为这样服务器简单、可规模化——不用给每个用户维护记忆，随便哪台服务器都能处理任意请求。

怎么解决"记不住人"？ 客户端自己带"身份凭证"（Cookie），服务器看凭证认人。这就是"协议无状态，应用补状态"。

Q2 携带 Cookie 的请求是有状态还是无状态？为什么还说 HTTP 无状态？¶

一句话答案¶

靠 Cookie 可以实现"一定程度的状态保持"，但这属于在无状态协议上的补充机制——HTTP 协议本身依然是每个请求独立的。

大白话讲解¶

  • 浏览器发请求时自动带上 Cookie，服务器读 Cookie 就能识别用户、管理会话 → 看起来"有状态"了。
  • 但 HTTP 协议的设计初衷依然是每个请求独立，服务器并不保存状态，所有状态信息都靠请求自己带过来。
  • 结论："HTTP 无状态"说的是协议本来的设计；Cookie 只是附加在协议上的补丁。

Q3 Cookie 和 Session 有什么区别？¶

一句话答案¶

Cookie 存客户端（浏览器），Session 存服务器端。二者在存储位置、容量、安全性、生命周期、性能五方面不同。

大白话讲解¶

Session 的工作方式：服务器为每个用户分配唯一 Session ID，通过 Cookie 发给客户端；客户端后续请求带上它，服务器凭 ID 找到对应的 Session 数据。

对比项 Cookie Session
存储位置 客户端（浏览器） 服务器端
数据容量 单个约 4KB，且浏览器限制每个域名 Cookie 总数 理论不限，受服务器内存限制
安全性 存客户端易被 XSS 窃取；可设 HttpOnly 防 JS 读取；仍可能被 CSRF 利用 敏感数据在服务器更安全；但要防 Session 劫持（偷 Session ID）
生命周期 可设过期时间；会话 Cookie 关浏览器即删 默认关浏览器结束；也可设超时时间
性能 每次请求都携带，数据大时影响网络传输 每次请求都要查服务器 Session，高并发下增加服务器负载

Q4 Token、Session、Cookie 的区别？¶

一句话答案¶

  • Session 存服务器，靠 sessionId 在服务器端"查名单"；
  • Cookie 存客户端，用来装 sessionId，浏览器自动携带；
  • Token（如 JWT） 也是令牌，但无状态——用户信息加密在令牌里，服务器解密即知是谁，需开发者手动添加。

大白话讲解¶

概念 存储位置 怎么认人 谁负责携带
Session 服务器 拿 sessionId 查服务器名单 依赖 Cookie
Cookie 客户端 装 sessionId 的容器 浏览器自动加
Token 客户端（请求头） 解密令牌里的用户信息 开发者手动加

一句话：Session 是"服务器记名单"，Cookie 是"递名单的纸条"，Token 是"把名单直接印在自己身上"（所以 Token 不需要服务器记）。

Q5 如果客户端禁用了 Cookie，Session 还能用吗？¶

一句话答案¶

默认不能——Session 靠 Cookie 传 sessionId；但可以用 URL 重写 或 隐藏表单字段 绕过。

大白话讲解¶

禁用 Cookie 后，服务器没法把 sessionId 发给客户端，客户端也没法把 sessionId 带回来 → 服务器认不出你是谁。

两种绕法：

  1. URL 重写：把 sessionId 拼在 URL 里，如 http://example.com/page;jsessionid=XXXXXX。缺点：URL 不整洁，且链接被分享出去会导致 sessionId 泄露。
  2. 隐藏表单字段：HTML 表单里藏一个存 sessionId 的隐藏字段，提交时一起送回服务器。缺点：只适用于表单提交，不适合链接点击和 Ajax。

面试常答："默认不行，但有两种方案……" 能说出来就是加分。

Q6 localStorage 和 Cookie 有什么区别？¶

一句话答案¶

容量（几 MB vs 几 KB）、是否随请求发送（localStorage 不自动发送）、生命周期（永久 vs 可设过期）、安全性（localStorage 不被每次请求携带，相对更安全）四方面不同。

大白话讲解¶

对比项 Cookie localStorage
存储容量 几 KB（小） 几 MB（大）
数据发送 每次 HTTP 请求自动发给服务器 不自动发送，只存在浏览器
生命周期 可设过期时间 永久存储，除非手动删除
安全性 每次请求都带，有被窃取/篡改风险 只在浏览器端，不随请求走，相对安全

一句话：Cookie 适合"客户端 ↔ 服务器"传数据；localStorage 适合"同域名下页面间共享大块数据"。

Q7 什么数据存 Cookie、什么数据存 localStorage？¶

一句话答案¶

Cookie：需要传给服务器、跨域访问、要设过期时间的数据；localStorage：同域名页面共享、量大、要长期保存的数据。

Q8 JWT 令牌和传统方式（Session/Cookie）有什么区别？¶

一句话答案¶

JWT 是无状态的：用户信息加密在令牌里，服务器无需存会话；靠签名防篡改；通过请求头传递天然防 CSRF；跨域友好。

大白话讲解¶

  • 无状态性：JWT 自带全部身份信息（用户身份、权限等），服务器不用存 Session → 天然适合分布式系统扩展和跨域。
  • 安全性：JWT 用密钥签名，保证完整性和真实性，只有持密钥的服务器能验证解析 → 防篡改防伪造。通过 Authorization: Bearer <token> 请求头传递。
  • 防 CSRF：浏览器跨站请求只会自动带 Cookie，不会自动带自定义请求头 → 攻击者无法在伪造请求里带上 JWT。
  • ⚠️ 注意：防 CSRF 的关键是传递方式（请求头而非 Cookie），不是签名本身。如果把 JWT 放 Cookie 里，一样有 CSRF 风险。
  • 跨域支持：JWT 可在不同域间传递，无需 Cookie 也能跨域身份验证。

Q9 JWT 令牌都有哪些字段？¶

一句话答案¶

JWT = 头部（Header）+ 载荷（Payload）+ 签名（Signature） 三部分，前两部分是 Base64 编码的 JSON，签名是对前两者 + 密钥签名后的结果。

大白话讲解¶

eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOiIxMjMifQ.s5Xx...
└─────Header──────┘ └─────Payload─────┘ └──Signature──┘
  • Header（头部）：声明算法和类型，如 {"alg": "HS256", "typ": "JWT"}；
  • Payload（载荷）：放用户信息（user_id、过期时间 exp 等）；
  • Signature（签名）：用密钥对"头部 + 载荷"签名，保证内容没被篡改。

面试小技巧：答出"三段式 + Base64 + 签名"，再补一句"载荷是明文编码的，别放敏感信息"——这是最容易踩的坑，说了显专业。

Q10 JWT 为什么能解决集群部署？什么是集群部署？¶

一句话答案¶

集群部署 = 多台服务器一起对外提供服务。传统 Session 存在单台服务器内存/数据库里，集群间不共享，用户请求被路由到别的服务器就"掉登录"；JWT 自包含身份信息，任何服务器都能独立验证，不需要共享存储。

大白话讲解¶

  • 传统方案的问题：Session 存服务器 A，用户下次请求被负载均衡分到服务器 B，B 没有这份 Session → 要重新登录。解决办法是引入 Redis 等共享会话存储，但增加了复杂度和性能开销。
  • JWT 方案：登录后服务器签发 JWT（里面装着用户身份），客户端每次请求带着它。每台服务器都能独立验证 JWT、解析出用户身份，不依赖任何共享存储 → 集群随便扩容，任意服务器都能处理请求。

一句话：Session 是"各店记各店的熟客本"，JWT 是"顾客自带会员卡"——换哪家分店都能认。

Q11 JWT 的缺点是什么？¶

一句话答案¶

JWT 一旦签发，在过期前始终有效，无法主动撤销——只能靠业务层加"黑名单"机制补救。

大白话讲解¶

Session 可以随时在服务器端删掉；但 JWT 在客户端手里，服务器管不着。要让某个 JWT 提前失效，只能：

  • 用 Redis 等维护一个黑名单，把要撤销的 JWT 加进去；
  • 每次请求先查黑名单，命中就拒绝。

缺点本质："无状态"的反面就是"管不住已发出去的令牌"。

Q12 JWT 令牌泄露了怎么办？¶

一句话答案¶

三种手段：① 标记失效/加入黑名单；② 刷新令牌（重新签发新的，作废旧令牌）；③ 缩短有效期减少被滥用窗口。

大白话讲解¶

  1. 及时失效：检测到泄露后立即把令牌标记为失效，服务器见到就拒绝；
  2. 刷新令牌：JWT 通常有有效期，泄露后主动刷新（签发新令牌 + 作废旧令牌），让泄露的令牌很快过期；
  3. 黑名单：服务器维护黑名单，收到令牌先查，命中即拒（有效但占性能）。

常见面试延伸：为什么 JWT 有效期一般设短 + 配 refresh token（刷新令牌）？——就是为减小泄露后的滥用窗口。

Q13 前端是如何存储 JWT 的？¶

一句话答案¶

三种选择：localStorage / sessionStorage / Cookie，各有优劣势——localStorage 防不了 XSS，Cookie 可设 HttpOnly 防 XSS 但要防 CSRF。

大白话讲解¶

存储位置 优点 缺点
localStorage 空间大（约 5MB）；不随 HTTP 请求发送，不进缓存/日志 有 XSS 风险：恶意脚本能用 JS 直接读走 JWT
sessionStorage 同 localStorage，但仅限当前标签页，关窗即清，泄露风险小 刷新/新开标签页要重新认证，体验差
Cookie 可设 HttpOnly（JS 读不到，防 XSS）；可设 Secure（仅 HTTPS 发送） 容量小（约 4KB）；每次请求都携带；设置不当有 CSRF 风险

面试总结句式："存 localStorage 防不了 XSS；存 Cookie 配 HttpOnly 能防 XSS，但要注意 CSRF（把 token 放请求头而不是 Cookie 里传）"。

Q14 CSRF 和 Cookie、Session、JWT 是什么关系？¶

一句话答案¶

CSRF 攻击的对象是"浏览器自动携带 Cookie"这个机制——Session 靠 Cookie 认人所以天然怕 CSRF；JWT 走请求头所以天然防 CSRF（一旦放回 Cookie 也一样怕）；防御靠 CSRF Token、SameSite、校验来源。

大白话讲解¶

四个角色先分清：

概念 本质 一句话
Cookie 浏览器端的存储 + 自动携带机制 递纸条的运输工具
Session 服务器端的状态存储 服务器记名单
JWT 客户端自包含的令牌 自带会员卡
CSRF 一种攻击 借你的手干坏事

关系四条链：

  1. Session 依赖 Cookie：sessionId 装进 Cookie 由浏览器自动携带 → Cookie 是 Session 的"运输工具"。
  2. CSRF 攻击的对象是 Cookie 机制：攻击者不需要偷你的 Cookie，只需要骗你的浏览器在访问恶意页面时"顺手"把 Cookie 带给目标服务器 → 服务器以为是你本人操作。
  3. Session 方案天然怕 CSRF：身份凭证靠 Cookie 自动携带，服务器无法区分"你主动发的请求"和"恶意网页借你发的请求"。
  4. JWT 放请求头天然防 CSRF：浏览器只会自动带 Cookie，不会自动带自定义请求头（Authorization: Bearer <token>）→ 伪造请求带不上 JWT → 服务器直接拒绝。但 JWT 一旦塞回 Cookie，浏览器照样自动携带，攻击照旧——防 CSRF 的关键是传递方式，不是签名。

防御四招：

  1. CSRF Token（经典方案）：服务器在表单里嵌一个随机 Token，提交时校验——攻击者的伪造请求拿不到这个 Token；
  2. SameSite Cookie：给 Cookie 加 SameSite=Lax/Strict，跨站请求不带 Cookie（现代浏览器默认 Lax，已缓解大部分场景）；
  3. 校验 Referer/Origin：确认请求来自本站（可被绕过，作辅助手段）；
  4. 关键操作二次确认：转账、改密码等加验证码/二次密码。

一句话："CSRF 只认 Cookie、不认请求头"——所以 Session 怕它，JWT（放请求头）不怕它；想让 JWT 安全，就别把它放回 Cookie。

关联记忆：原理详解见《11 网络攻击》Q3。

本单元小结¶

概念 一句话记住
HTTP 无状态 协议本身不记人，Cookie/Session 是补丁
Cookie 客户端存储，浏览器自动携带，4KB
Session 服务器存储，靠 sessionId 认人，可被禁用 Cookie 影响
JWT 自包含无状态令牌，签名防篡改，请求头传防 CSRF
JWT 缺点 无法主动撤销，靠黑名单/刷新令牌补救
前端存 JWT localStorage 防不了 XSS；Cookie + HttpOnly 防 XSS 但要注意 CSRF
CSRF 与三件套 攻击"Cookie 自动携带"；Session 怕它，JWT 放请求头不怕
