2026-07-26 M1 完成：合约 V2 + 攻击性测试¶

完成内容 - IRegistry.sol：跨合约权限接口（authorOf / workExists）。 - RegistryV2.sol：哈希三元组（originalHash/signedHash/manifestHash）+ hashIndex 链上反查 + 三哈希防重复注册（防抢注）+ setStatus（仅作者）+ getWorkByHash。author = msg.sender，为 M4 前端钱包直发交易铺路。 - LicenseV2.sol：构造注入 IRegistry；grantLicense 强制 authorOf(workId)==msg.sender；新增 revoke / isLicensed（含过期）/ 按作品枚举。 - RoyaltyV2.sol：同样 authorOf 校验，仅作者可设/改规则。 - MockJudicialAnchor.sol：接口 + mock 实现（仅 emit 事件），维持"不接真实司法链"边界。 - scripts/deploy.js：四合约顺序部署，地址写 deployments/<network>.json（兼容一期 start-backend.ps1 的注入机制，新增 MockJudicialAnchor 字段）。 - hardhat.config.js：补显式 localhost 网络块（修复一期缺失）；gasReporter 输出到 reports/。

涉及文件：contracts/contracts/*.sol（5 个）、contracts/scripts/deploy.js、contracts/test/*.test.js（4 个）、contracts/hardhat.config.js

验证结果 - npm test：20 passing（含 5 组攻击用例：重复哈希注册（三哈希各测）revert、非作者 grantLicense revert、非作者 setRoyaltyRule revert、幽灵 workId revert、撤销/过期后 isLicensed=false）。 - hardhat coverage：Stmts 98.21% / Branch 98.44% / Lines 98.55%（目标 ≥80%）。 - Gas：registerWork 平均 294,595（三哈希+索引比一期约贵 10 万 gas，换来链上反查与防抢注，论文可写这笔账）；grantLicense 235,468。 - 部署冒烟：四合约部署成功，deployments JSON 结构正确。

下一步（M2）：openssl 自建 demo CA（Root CA + ES256 叶子证书，EKU 含 emailProtection），c2patool 换用自建证书签名并配置 trust anchor，产出 trusted vs untrusted 对照。若 c2patool 拒收自建证书则走退路（dev 证书 + 文档注明），不阻塞 M3。

2026-07-26 M2 完成：C2PA 信任链（自建 demo CA，未走退路）¶

完成内容 - tools/ca/make-ca.sh + ca.cnf：openssl 生成 EC P-256 Root CA（10 年）→ 签发 ES256 叶子证书（3 年，KU=digitalSignature critical，EKU=emailProtection critical，符合 C2PA 证书 profile）→ 合成 sign-chain.pem（叶子+根）。踩坑记录：Git Bash 会把 -subj /C=CN/... 当路径改写，需 MSYS_NO_PATHCONV=1。 - c2patool 签名切换：manifest 定义 JSON 增加 "alg":"es256"、"private_key"、"sign_cert" 三字段（路径相对 manifest 文件解析——M3 后端生成 manifest 时要用绝对路径）。 - 信任验证：c2patool <asset> trust --trust_anchors tools/ca/rootCA.pem。

涉及文件：tools/ca/make-ca.sh、tools/ca/ca.cnf、reports/test-results/c2pa-trust-comparison.md

验证结果 - 同一张签名图：默认信任列表 → signingCredential.untrusted；加载自建 Root CA → signingCredential.trusted + "validation_state": "Trusted"。自建 CA 被 c2patool 0.26.68 完整接受，退路未启用。 - 对照证据已存 reports/test-results/c2pa-trust-comparison.md（答辩演示"信任列表内外对照"素材）。

下一步（M3）：后端改造。从 bak 复制 backend 作底 → SQLite（modernc.org/sqlite）三表（works/chain_cursor/licenses）→ 删代签、加 POST /api/works/prepare（返回三哈希+CID+calldata）→ c2pa/tool.go 接自建证书与 trust 验证 → FilterLogs 事件监听断点续扫 → 三元组分层验证。

2026-07-26 M3 完成：后端改造（身份/验证两大闭环落地）¶

完成内容 - 删除代签：chain/registry.go（持私钥发交易）整体移除。新 chain/client.go 为只读客户端 + RegisterCalldata（abi.Pack）；ABI 从 hardhat artifacts 动态加载（chain/chain.go），杜绝手写 ABI 漂移。 - prepare 流程（POST /api/works/prepare）：上传 → originalHash → 重复检查 → c2patool 自建证书签名 → signedHash → trust anchor 验证（c2paStatus=trusted）→ manifestHash → pHash 相似预警 → 存储 pin → SQLite 入库（PENDING_ANCHOR）→ 返回 txRequest{to,data,chainId} 由创作者钱包发交易。 - SQLite 索引：modernc.org/sqlite（纯 Go 免 CGO），works（original_hash UNIQUE + signed/manifest 索引）、licenses（事件镜像，upsert 幂等）、chain_cursor（断点）三表。 - 事件监听（chain/listener.go）：2s 轮询 FilterLogs（Registry+License 地址），WorkRegistered→MarkAnchored（回填 chainWorkId/author/txHash/block），LicenseGranted/Revoked→licenses 镜像；游标持久化，重启断点续扫即自动对账。 - 三元组验证：original/signed 精确命中 → DB miss 时链上 getWorkByHash 兜底 → 文件内 C2PA manifest 提取 identifier 反查（tier=manifest-only，即"签名后被篡改"）→ 全 miss 报 none。 - 顺手完成的 M5 项：similarity/phash.go（goimagehash，汉明距离≤10 预警）、tsa/tsa.go（digitorus/timestamp，RFC3161，TSA_URL 可配）、report/pdf.go V2 版（三哈希+信任状态+双时间戳行+可选 Unicode 字体）。 - 单元测试：repository（三级查找/游标/授权镜像/UNIQUE 防重复）、c2pa（ValidationState/ExtractIdentifier/签名字段）、similarity（pHash 自距离 0/异图距离>0）。

踩坑记录（论文第 4 章素材） - c2patool 的 --trust_anchors 在 Windows 上把 F:\... 当 URL scheme、file:/// 又被禁——解法：把 rootCA.pem 复制进资产临时目录用相对路径。 - manifest 里 private_key/sign_cert 路径相对 manifest 文件解析，必须传绝对路径（config 启动时 filepath.Abs）。

验证结果（集成实测，Hardhat+local 存储） - prepare：三哈希 + c2paStatus=trusted + calldata，206ms。 - 账户 #1（创作者，非部署者非后端）发交易 → 监听器 4s 内 ANCHORED，链上 author=0x7099...79C8=创作者钱包（V1 致命缺陷修复实证）。 - 三态验证：原图→original；签名版→signed；篡改 1 字节→manifest-only + C2PA state=Invalid（hard binding 报篡改）。 - 断点续扫：后端离线期间发交易，重启后 work#2 自动补齐 ANCHORED。 - PDF 生成正常；go test ./... 全绿；Gas：registerWork 实链 429,628 / 412,528。

下一步（M4）：前端重构。web 复制作底 → 加 ethers v6 + vue-router → 拆三视图（创作者上传+钱包发交易 / 授权管理 / 验证四态结果页）→ useWallet/useContracts composables（从 /api/chain/info 拉地址与 ABI）→ e2e-demo 脚本自动化验收。

2026-07-26 缺陷修复：作品标题乱码（用户报告）¶

现象：前端作品列表中 work #4 标题显示为乱码（用户截图 乱码.png），其余中文均正常。

根因：该记录是 M5 测试时用 Windows curl 命令行上传的——curl 把命令行参数按本地编码（GBK）发送， 后端将 GBK 字节（\xd6\xd0\xce\xc4...）当作 UTF-8 原样入库，属于测试数据污染，非前端/字体问题。 浏览器 FormData 强制 UTF-8，正常使用不会触发。

修复（三层） 1. 数据修复：SQLite 中 work #4 标题按 GBK→UTF-8 转码，显示恢复"中文标题测试·相似图"； 2. 后端防御：Prepare 增加 utf8.ValidString(title) 校验，无效 UTF-8 直接 400 拒绝（错误信息提示 Windows curl 的 GBK 编码问题），杜绝坏数据入库和嵌入 C2PA manifest； 3. 回归验证：UTF-8 multipart 上传中文标题"风景写生·测试作品"往返一致；GBK 字节标题被 400 拒绝。

教训（论文/使用文档素材）：跨编码边界（命令行 → HTTP → SQLite → 前端）必须在入口做 UTF-8 有效性校验； Windows 命令行工具（curl、openssl -subj、ipfs config）是本项目三次编码/路径踩坑的共同来源。

2026-07-26 功能补充：本地水龙头（用户反馈——自有 MetaMask 账户无余额付 gas）¶

背景：人工验收时用户使用自己的 MetaMask 账户（非 Hardhat 内置测试账户），本地链上余额为 0， 无法支付 registerWork 的网络费。要求"可用测试网或本地余额可自行充值"。

方案：本地水龙头。Hardhat 提供 hardhat_setBalance RPC，可直接为任意地址设置余额—— 比"导入 Hardhat 测试私钥"体验更好（任何自有账户即充即用），也比接公共测试网更符合本地演示定位。

实现 - 后端 POST /api/chain/faucet（chain/client.go SetBalance/BalanceOf + work_handler Faucet）： 为指定地址充值 10 测试 ETH；仅 chainId=31337 放行，其他网络 403——部署到公共测试网时水龙头 自动失效（该 RPC 方法在公网节点也不存在），届时用对应测试网的公共水龙头，架构本身支持任意 EVM 网络 （CHAIN_RPC_URL / DEPLOYMENTS_FILE 均可配）。 - 前端：钱包面板显示实时余额；余额 < 0.01 ETH 时顶栏出现"领取测试币"按钮 + 黄色提示条； 交易完成后自动刷新余额（useWallet.refreshBalance）。

验证：全新地址 0x...1234 经 faucet 充值 → 链上 eth_getBalance = 10 ETH；前端 build 通过。

2026-07-26 缺陷修复：点击"领取测试币"没反应（用户报告）¶

排查过程：后端日志显示 5 次 POST /api/chain/faucet 全部 200，Hardhat 日志确认 hardhat_setBalance 每次都执行——钱实际到账了，但界面刷不出来。

根因：hardhat_setBalance 直接改状态、不产生新区块；MetaMask 与 ethers 都以区块高度作为 余额查询的缓存键，链上没有新块就认为状态没变，eth_getBalance 一直返回缓存的 0。 体感即"点了没反应"。

修复（三处） 1. 后端 faucet 充值后补发 evm_mine 挖一个空块（区块号推进 → 击穿钱包缓存），实测 20→21； 2. 前端充值成功后显示绿色到账提示，余额数字直接取自后端链上读回的 balanceWei，不再依赖 MetaMask 的缓存刷新；faucet 日志打印地址与到账余额，便于后续排查； 3. 顺带修复排查中发现的问题：work #20（猪八戒）author_address 为空——prepare 原先不强制连接钱包。 现 CreatorView 在"① 生成声明与签名"前强制要求连接 MetaMask，作品声明必须绑定创作者地址。

教训：本地开发链的"作弊型" RPC（setBalance/evm_mine）不走出块流程，任何依赖区块高度做缓存的 客户端（MetaMask、ethers Provider）都感知不到状态变化；改状态后必须手动推进区块。
