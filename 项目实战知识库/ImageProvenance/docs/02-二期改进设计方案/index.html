二期改进设计方案（ImageProvenance V2）¶

定位不变：多方互信场景下图像作品的来源声明、确权存证、授权流转一体化系统；不替代司法鉴定。 技术栈不变：Vue 3 + Go/Gin + Solidity/Hardhat + IPFS/Kubo + c2patool。 二期原则：不扩功能面，做实四个闭环——身份、验证、授权、信任。

一、总体架构调整¶

一期架构的根本问题是后端"既当服务员又当签字人"。二期把角色切开：

一期（有缺陷）：
  前端(只展示钱包) -> 后端(持私钥代签一切) -> 合约(author=后端地址)

二期（目标）：
  创作者钱包(MetaMask/ethers.js) ──签名/发交易──> Registry 合约(author=创作者地址)
        │                                            ▲
        │ 上传原图                                    │ 事件
        ▼                                            │
  后端(无签名权)：文件校验 / c2patool 签名 / IPFS pin / 事件监听 -> SQLite 索引

后端从"代签者"降级为"服务者"：只负责计算哈希、调 c2patool、pin IPFS、监听链上事件维护链下索引。上链交易由创作者钱包在前端直接发起（Hardhat 本地链，gas 免费，无门槛）。

备选方案（保留但不做主路径）：EIP-712 元交易——创作者钱包只签结构化消息，后端代付 gas 上链，合约用 ecrecover 恢复作者地址。设计文档里写一节作为"生产环境演进方向"，答辩时可作为加分谈资，但二期代码只实现前端直连路径，避免范围膨胀。

二、哈希语义三元组（解决问题 2）¶

明确定义三个哈希，全部锚定上链，文档、合约、论文使用同一套术语：

字段 定义 用途
originalHash 创作者上传的原始文件的 SHA-256 创作时点完整性锚点
signedHash c2patool 嵌入 Manifest 后签名文件的 SHA-256 对外分发版本的验证锚点
manifestHash Manifest（JSON/JUMBF 提取）的 SHA-256 来源声明内容的锚点

验证规则：验证方上传任意文件，后端计算 SHA-256，链上 hashIndex 反查——命中 originalHash 报"原始文件"，命中 signedHash 报"官方签名分发版"，都未命中且文件内含 C2PA manifest 则提取 manifest 比对 manifestHash（覆盖"图被改但 manifest 还在"的场景），全部未命中报"无记录/已被篡改"。

与 C2PA 内部 hard-binding 哈希的关系在论文第 4 章画一张图说清：hard-binding 保证"manifest ↔ 图像像素"绑定（文件内自洽），链上三元组保证"文件 ↔ 链上记录"绑定（跨平台可查），两层各司其职。

三、合约 V2 设计（解决问题 1、3、4）¶

3.1 RegistryV2¶

struct Work {
    uint256 id;
    address author;          // = msg.sender，即创作者钱包
    bytes32 originalHash;
    bytes32 signedHash;
    bytes32 manifestHash;
    string  imageCid;        // 签名版图片 CID
    string  manifestCid;
    uint64  createdAt;
    WorkStatus status;       // Active / Disputed / Revoked（作者可标记）
}

mapping(bytes32 => uint256) public hashIndex;  // 三种哈希 -> workId，防重复 + 链上反查

function registerWork(...) external returns (uint256) {
    require(hashIndex[originalHash] == 0, "duplicate: original");
    require(hashIndex[signedHash] == 0,   "duplicate: signed");
    // author = msg.sender（创作者钱包直发交易）
}

function getWorkByHash(bytes32 h) external view returns (Work memory);
function authorOf(uint256 workId) external view returns (address);   // 供 License/Royalty 校验

要点： - 防抢注：同一哈希只能注册一次，重复注册直接 revert——这是"确权"系统的第一道防线，也是一个现成的攻击性测试用例。 - 链上反查：getWorkByHash 使链下数据库降级为纯加速缓存，即使库丢了，验证仍可直连链上完成——"跨平台可验证"从口号变成事实。 - authorOf 是给其他合约用的最小接口（抽为 IRegistry）。

3.2 LicenseV2 / RoyaltyV2¶

contract LicenseV2 {
    IRegistry public immutable registry;

    function grantLicense(uint256 workId, address licensee, string calldata usage, uint64 validUntil) external {
        require(registry.authorOf(workId) == msg.sender, "not author");  // 关键修复
        ...
    }
    function isLicensed(uint256 workId, address who) external view returns (bool);  // 供验证页展示
}
  • Royalty 同理加 authorOf 校验；规则更新只允许作者本人。
  • License 增加 revokeLicense（作者可撤销）和按 workId 枚举授权记录的视图函数——验证页可以展示"该作品当前有效授权列表"。
  • 部署顺序：RegistryV2 → LicenseV2(registryAddr) → RoyaltyV2(registryAddr)，构造函数注入，immutable 存储。

3.3 JudicialAnchor¶

维持"只留接口不实现"的口径，但补一个 MockJudicialAnchor 实现（仅 emit 事件），用于演示"未来锚定司法链"的调用形态。论文口径不变：实际接入需司法备案，超出研究范围。

3.4 合约测试升级¶

正常路径之外，必须补攻击性用例（这是论文第 5 章的差异化亮点）：

  1. 重复哈希注册 → revert（防抢注）；
  2. 非作者调用 grantLicense / setRoyaltyRule → revert（防越权）;
  3. 篡改一个字节的图片走验证流程 → 三哈希全不命中（篡改检测有效性）;
  4. 过期授权 isLicensed 返回 false。

覆盖率目标维持 ≥80%，用 solidity-coverage 出报告。

四、C2PA 信任链建设（解决问题 5）¶

一期验证结果永远是 signingCredential.untrusted，二期分三步做实：

  1. 自建 demo CA：openssl 生成 Root CA → 签发 ES256 签名证书（含 C2PA 要求的 EKU 扩展），c2patool 使用该证书签名。
  2. 配置信任列表：c2patool 验证时通过 --trust（trust anchors 配置）加载自建 Root CA，验证状态变为 trusted。演示时展示"信任列表内 → trusted / 列表外 → untrusted"的对照，这一屏就是 C2PA 信任模型的活教材，比一期单纯"签了个名"说服力强一个量级。
  3. 论文口径：demo CA 等价于联盟场景下的"平台方 CA"；生产环境应替换为公共 CA 或 C2PA 官方信任列表成员。诚实声明这一边界。

Manifest 内容同步升级：assertion 中写入创作者钱包地址、workId 占位、创作声明（c2pa.actions + 自定义 assertion），使"文件内声明"与"链上记录"字段级互指——这是"混合溯源"创新点的实体化。

五、后端重构（解决问题 6）¶

5.1 状态机¶

每个作品在链下索引中有明确状态，任何一步失败可重试、可对账：

UPLOADED → SIGNED(c2pa) → PINNED(ipfs) → PENDING_ANCHOR(等待链上事件) → ANCHORED → (INDEXED)
                                              │ 超时未见事件
                                              ▼
                                          STALE(对账任务重查链上)

关键变化："上链"不再是后端调合约，而是后端把待锚定数据返回前端，前端钱包发交易；后端靠事件监听确认。

5.2 事件监听与对账¶

  • go-ethereum FilterLogs 轮询（本地链下比 WebSocket 订阅稳），监听 WorkRegistered / LicenseGranted / RoyaltyRuleSet，写入 SQLite 索引。
  • 记录 lastProcessedBlock，重启后从断点续扫——对账逻辑天然完成"链上有但库里没有"的自愈。
  • 这一节直接回应开题报告"拟解决的关键问题二"（链上链下一致性），论文第 4 章有了真材实料。

5.3 API 调整（相对一期）¶

接口 变化
POST /api/works/prepare 新增：上传原图 → 返回三哈希 + CID + 待签交易参数（calldata），前端钱包据此发交易
POST /api/works/register 废弃（一期后端代签入口）
GET /api/works/:id 增加链上状态、C2PA 验证状态（trusted/untrusted）、授权列表
POST /api/works/verify-file 升级为三元组验证规则（第二节）
GET /api/works/:id/report.pdf PDF 增加：三哈希、C2PA 信任状态、RFC3161 时间戳（P1）

六、前端重构（解决问题 7）¶

  • Vue Router 拆三个视图 + 组件化（一期 995 行 App.vue 拆掉）：
  • 创作者：上传 → 预览三哈希 → 钱包签名上链 → 我的作品/授权管理；
  • 使用方：浏览作品 → 查看授权条款 →（作者端）签发授权演示；
  • 验证方：拖入图片/输入 workId/扫二维码 → 验证结果页（哈希命中类型、C2PA 信任状态、授权状态、来源链时间线）。
  • ethers.js v6 真正接管交易：连接钱包、切换本地链、调 RegistryV2/LicenseV2、等待回执。
  • 验证结果页是答辩演示的主舞台，视觉上区分四种结论：原始文件 / 官方签名版 / manifest 匹配但文件被改 / 无记录。

七、P1 加分项（主闭环完成后按序做）¶

  1. pHash 相似预警（对标参考素材李林逸 2024）：注册时链下计算 pHash 存 SQLite，新上传与已有作品汉明距离 ≤ 阈值时提示"疑似重复/相似作品"，仅预警不上链。一天工作量，直接回应"图改了怎么办"的追问（口径仍是：相似检索不属于确权范围，这只是防误注册的辅助）。
  2. RFC3161 双时间戳：注册时请求 freeTSA 对 manifestHash 出链下时间戳，存证 PDF 同时呈现 block.timestamp + RFC3161 —— 兑现毕设方案 4.4 的"双锚定"承诺。
  3. EIP-712 元交易设计文档（只写不实现，作为第 6 章展望的实体支撑）。

八、明确不做（继承一期边界，答辩口径不变）¶

AI 生成检测、SIFT/水印相似检索（pHash 仅作链下预警）、真实司法链、自定义代币、真实支付、公链部署、大规模压测。
