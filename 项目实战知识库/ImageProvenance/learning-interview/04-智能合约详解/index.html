04 智能合约详解：每个函数的设计理由¶

合约是全系统的"宪法"，本章逐函数讲清设计动机。

4.1 合约关系图¶

┌─────────────────────────────────────────────────────────────┐
│                        IRegistry                            │
│  (接口：authorOf(workId) / workExists(workId))               │
│  作用：让其他合约能查"谁是作者"，而不需要知道 Registry 实现    │
└───────────────────────────┬─────────────────────────────────┘
                            │ implements
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                      RegistryV2                             │
│  (作品登记：三哈希存储、防抢注、状态管理)                       │

                            │ authorOf 校验

4.2 RegistryV2.sol：作品登记合约¶

数据结构¶

struct Work {
    uint256 id;           // 作品ID（从1开始，0保留给"不存在"）
    address author;       // 作者地址 = msg.sender（关键！）
    bytes32 originalHash; // 原图 SHA-256
    bytes32 signedHash;   // C2PA签名后的图 SHA-256
    bytes32 manifestHash; // C2PA声明 SHA-256
    string imageCid;      // 签名版图的 IPFS CID
    string manifestCid;   // 声明的 IPFS CID
    uint64 createdAt;     // 区块时间戳
    WorkStatus status;    // Active / Disputed / Revoked
}

mapping(bytes32 => uint256) public hashIndex;  // 任意哈希 → 作品ID

registerWork：五个 require 的防御逻辑¶

require 防什么攻击 如果少了会怎样
originalHash != 0 垃圾数据占索引 bytes32(0) 会撞 hashIndex 默认值
signedHash != 0 同上 同上
manifestHash != 0 同上 同上
imageCid.length > 0 空 CID 无法取文件 链上指针指向虚空
manifestCid.length > 0 同上 同上
hashIndex[originalHash] == 0 防抢注：同一原图二次登记 小偷可以抢注别人的作品
hashIndex[signedHash] == 0 防拿别人签名版登记 同上
hashIndex[manifestHash] == 0 防拿别人声明登记 同上

关键代码：author = msg.sender¶

id = ++workCount;
works[id] = Work({
    id: id,
    author: msg.sender,  // ← 这一行是整个 V2 的核心
    // ...
});

为什么这是安全的： - msg.sender 不是参数传入的，是从交易签名恢复出来的 - 要伪造 author，需要伪造私钥签名，密码学上不可行 - 对比：V1 用后端私钥签名，所以所有作品 author 都是服务器地址

面试追问：为什么不用 tx.origin？

tx.origin 是交易发起者的原始地址，但能被钓鱼攻击利用（恶意合约可以调用你的合约，tx.origin 还是用户，但用户本意不是调用你的合约）。msg.sender 是直接调用者，永远正确。

getWorkByHash：链上反查¶

function getWorkByHash(bytes32 h) external view returns (Work memory) {
    uint256 id = hashIndex[h];
    require(id != 0, "hash not registered");
    return works[id];
}

意义：验证不依赖链下数据库。把 backend/data/index.db 删了，验证照样工作。

setStatus：标记而非删除¶

function setStatus(uint256 id, WorkStatus status) external {
    require(works[id].author == msg.sender, "not author");
    works[id].status = status;
    emit WorkStatusChanged(id, status);
}

为什么没有 deleteWork：

链上数据本就不可删，与其提供假删除，不如提供带历史的状态标记。Revoked 表达"作者收回声明"但记录仍在，符合存证语义。

4.3 LicenseV2.sol：授权管理合约¶

grantLicense 的 require 清单¶

require(registry.workExists(workId), "work not found");      // 幽灵作品
require(registry.authorOf(workId) == msg.sender, "not author"); // 越权（核心防线）
require(licensee != address(0), "licensee required");        // 空地址
require(bytes(usage).length > 0, "usage required");          // 空用途
require(validUntil > block.timestamp, "invalid expiry");     // 过去时间

每个 require 都有对应测试用例，这是"攻击性测试"的设计。

isLicensed：为什么用数组遍历而不是 mapping？¶

function isLicensed(uint256 workId, address who) external view returns (bool) {
    uint256[] storage ids = licensesByWork[workId];
    for (uint256 i = 0; i < ids.length; i++) {
        LicenseRecord storage rec = licenses[ids[i]];
        if (rec.licensee == who && !rec.revoked && rec.validUntil > block.timestamp) {
            return true;
        }
    }
    return false;
}

权衡讨论（面试亮点）：

方案 优点 缺点
mapping(workId→licensee→bool) O(1) 查询 表达不了"多笔授权、各自期限、可单独撤销"
数组遍历（本项目） 表达力完整 gas 随授权数线性增长

业务假设：单作品授权数有限（<100），所以数组方案可行。追问"如果十万笔授权怎么办"：

链下索引承担规模化查询，链上 isLicensed 服务合约间调用。工业方案是用 The Graph 或自建索引器。

revokeLicense：谁能撤？¶

require(rec.licensor == msg.sender, "not licensor");

是授权人（签发者）而非作品作者。当前两者恒相同（没有转让功能），但字段语义按"签发者"设计。

4.4 RoyaltyV2.sol：分账规则合约¶

基点制（Basis Points）¶

uint16 public constant BASIS_POINTS = 10_000;

require(
    uint256(creatorShareBps) + uint256(platformShareBps) == BASIS_POINTS,
    "shares must total 10000"
);

为什么用基点而不是百分比小数： - EVM 无浮点数，金融字段用最小单位整数是行业惯例 - 8500 bps = 85%，避免浮点精度问题

为什么强制总和恰好 10000 而不是 ≤10000： - 防止"剩余部分归谁"的歧义 - 简化逻辑，避免边界情况

已知取舍：历史规则¶

链上只存最新规则，历史要靠 RoyaltyRuleSet 事件回放。这是 learning/10 的练习一（加分项）。

4.5 IRegistry.sol：接口设计¶

interface IRegistry {
    function authorOf(uint256 workId) external view returns (address);
    function workExists(uint256 workId) external view returns (bool);
}

设计问题：为什么 License/Royalty 依赖接口而不是直接 import RegistryV2？

方面 好处
最小依赖 License 只需要"谁是作者"，不需要知道 Registry 全部实现
可替换性 部署时注入地址，测试时容易 mock
解耦 Registry 升级（如加字段）不影响 License

4.6 合约安全清单（面试必背）¶

防御 实现 说明
溢出检查 Solidity 0.8+ 内置 算术溢出自动 revert
输入校验 所有外部输入 require 垃圾数据不进入状态
权限控制 authorOf == msg.sender 越权操作直接 revert
无重入攻击面 无转账逻辑 不涉及 ETH 转移，无重入风险
无管理员后门 没有 owner 角色 平台自己也改不了记录
不可升级 无 proxy 模式 存证系统要不可变，这是特性

4.7 Gas 优化与成本¶

操作 Gas 消耗 成本（按 30 gwei, ETH=$3000）
registerWork ~413,000 ~$3.7
grantLicense ~235,000 ~$2.1
setRoyaltyRule ~180,000 ~$1.6
setStatus ~45,000 ~$0.4

三哈希 vs 单哈希：多 10 万 gas（~$0.9），换来链上反查与防抢注，值得。
