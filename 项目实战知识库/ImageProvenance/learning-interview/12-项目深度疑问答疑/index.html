12 项目深度疑问答疑¶

来源：学习本项目过程中产生的 7 个深度疑问，涵盖代码量、身份模型、鉴权机制、 链形态选择、gas 成本、司法接口等核心设计权衡。 这些疑问正是答辩/面试中"连环追问"的高频方向——先有疑问、再有解答，理解才立体。

疑问 1：为什么这个系统的代码量不多？¶

核心结论：代码少不是"没做够"，而是"明确边界 + 复杂度外包 + 架构选型"三个因素叠加的结果。

三个原因¶

① 明确的边界（主动做减法）

项目在 README 里划了研究边界，每砍掉一个功能就省一大块代码：

明确不做的事 如果做了要写多少代码
用户注册/登录/鉴权 账号系统、JWT、密码加密、会话管理
AI 生成检测 模型集成、训练数据、推理服务
相似图像检索 向量数据库、索引、召回排序
真实支付/代币 支付网关、对账、退款、合规
真实司法链对接 机构资质、备案、多方协议

这些恰恰是生产系统里最占代码量的部分。

② 复杂度外包给成熟工具（关键原因）

重活 由谁承担 项目自己只写
链上签名、共识、存储 Hardhat + EVM 合约逻辑（300 行）
C2PA 签名/验证 c2patool 外部二进制 shell 调用（几十行）
SHA-256、ECDSA Go 标准库 / go-ethereum 一行调用
pHash 感知哈希 goimagehash 库 包装（40 行）
PDF 生成 gofpdf 库 字段填充

③ 架构模式本身省代码

事件驱动 + 游标 + 幂等，让链下同步用 60 行就做到"不丢、不重、可重建"； 存储抽象（Store 接口）避免 IPFS/本地两套逻辑重复。

面试话术¶

"代码少是我有意为之。我把复杂度放在三个正确的层次：密码学底子交给经过生产检验 的工具；把容易写错的一致性逻辑用'事件溯源 + 幂等'压到 60 行；把边界划清楚。 剩下 4000 行代码，每一行我都能讲清楚为什么存在。'小而完整、全栈可讲透' 本身就是定位，而不是'没写完'。"

疑问 2：多账户地址交互不就相当于用户系统了吗？¶

核心结论：多地址交互确实提供了"身份区分"能力，但这是借来的身份，不是造出来的身份——两者差在"身份是谁建立、谁管理的"。

本质区别¶

维度 传统用户系统 本项目的地址身份
身份怎么产生 用户在平台注册 用户钱包里生成密钥对，地址由公钥哈希推导
身份存哪 平台的 users 表 不存——地址本身就是身份
怎么"登录" 用户名+密码 → 平台发 token 私钥签名 → 链上从签名恢复地址
密码丢了怎么办 平台帮你重置 平台帮不了（不持有密钥）
权限谁判 后端查权限表 链上 authorOf == msg.sender

代码证据¶

  1. SQLite 只有三张表（works / licenses / chain_cursor），没有 users 表；
  2. 后端没有鉴权中间件，所有 API 无鉴权；
  3. 前端没有登录页，只有"连接 MetaMask"；
  4. 身份验证在链上：require(registry.authorOf(workId) == msg.sender)。

一句话总结¶

用户系统 = 平台自己造身份；本项目 = 借区块链的身份。系统不"注册"任何人， 只是把"谁能做什么"交给链上的 msg.sender。信任从平台拿走，交给密码学和共识。

疑问 3：那别人怎么用这个系统进行鉴权？¶

核心结论：鉴权不靠后端，靠"钱包签名交易 → 链上 msg.sender"。msg.sender 不是 前端传来的参数（可伪造），而是从交易签名恢复出来的地址。

完整流程（越权操作被拦截）¶

1. 张三点"签发授权" → 2. 前端用张三 MetaMask 构造 grantLicense 交易
→ 3. MetaMask 弹窗，张三用私钥签名 → 4. 交易发到链上，EVM 恢复出 msg.sender=张三
→ 5. 合约执行 require(authorOf(workId) == msg.sender, "not author")
→ 6. 李四的作品 authorOf=李四 ≠ 张三 → 7. revert（状态零改动）
→ 8. 前端翻译："合约拒绝：当前钱包不是该作品的链上作者"

后端一次都没参与——它只是之前"准备数据"，"谁有权限"的判断在链上完成。

各操作鉴权规则¶

操作 谁能做 鉴权代码
登记 registerWork 任何人（作者=签名者） author: msg.sender
签发授权 grantLicense 仅作品作者 authorOf == msg.sender
撤销授权 revokeLicense 仅签发者 licensor == msg.sender
设置分账 setRoyaltyRule 仅作品作者 authorOf == msg.sender
标记状态 setStatus 仅作品作者 author == msg.sender
验证来源 verify-file 任何人（公开查询） 无需鉴权

对比传统方案¶

后端鉴权 链上鉴权
判断逻辑在哪 后端代码 链上合约
平台能作弊吗 能（改代码/数据库） 不能（合约不可改，平台无私钥）
平台被黑会怎样 攻击者冒用任何身份 攻击者拿不到私钥，伪造不了作者

疑问 4：本地链呢？本项目不就是本地链吗？¶

核心结论：本地链和公链在安全性上是两个不同维度，必须分开看—— 身份鉴权维度两者完全等价，抗篡改维度本地链弱得多。

维度一：身份鉴权（"谁是谁"）——完全等价 ✅¶

msg.sender 从签名恢复、authorOf == msg.sender 判断权限，靠的是 ECDSA 签名算法本身， 跟链上有 1 个节点还是 1 万个节点毫无关系。本地链（Hardhat）用同一套 secp256k1、 同一个 EVM，伪造签名照样不可能。所以"平台无法伪造作者身份"这个性质，本地链完整具备。

维度二：抗篡改（"记录改不了"）——弱得多 ⚠️¶

本地链（本项目） 公链（主网）
节点数量 1 个 成千上万
数据存哪 内存，重启归零 永久持久化
谁能改历史 管理员想改就改 需控制 51% 全网算力
可信度 只有"演示可信" 真正的"社会可信"

那为什么还用本地链？¶

  • 架构是链无关的：换一个 RPC 地址就能上公链，代码一行不改；
  • 本地链零成本、零延迟，适合验证"架构对不对"；
  • 密码学性质（身份鉴权）本地链能完整演示；抗篡改性质靠"换 RPC"即可获得。

诚实红线（答辩必守）¶

"本地链在抗篡改维度确实弱——单节点、内存态、重启归零，管理员能改一切， 所以我从不说它'已上线'。但身份鉴权这一层本地链和公链完全等价。 把这两层分清楚、主动讲清楚，比把本地链吹成'不可篡改的区块链'更专业。"

疑问 5：改 RPC 上公网，那签名和鉴权的高额手续费怎么办？¶

核心结论：先澄清——签名和鉴权查询不花钱，只有"上链写操作"花钱。成本确实存在， 但解决方案是清晰的（元交易 / L2）。

什么花钱、什么不花钱¶

操作 是否花 gas 原因
签名（本地 ECDSA） ❌ 免费 纯本地计算
鉴权查询（authorOf 等 view 函数） ❌ 免费 eth_call 只读不写
写操作（registerWork 等） ✅ 花钱 广播交易、改存储（SSTORE 最贵）

实测成本（30 gwei、ETH $3000）¶

操作 gas 主网成本
登记 registerWork 413,000 约 $37
授权 grantLicense 235,000 约 $21
分账 setRoyaltyRule 180,000 约 $16
状态 setStatus 45,000 约 $4

谁付钱？¶

当前"后端零私钥"架构下，交易是用户钱包签名发的，所以 gas 是用户付。 这是零私钥设计的代价：好处是平台伪造不了作者，代价是用户承担 gas。

解法（项目里已埋了答案）¶

方案 说明
元交易（EIP-712） 用户离线签名、平台代付 gas，链上 author 仍是用户——见 docs/05
L2 扩容链 Arbitrum/Optimism/Base，gas 便宜 10–100 倍，改 RPC 即可
批量上链 多笔登记合并分摊 gas
联盟链 见疑问 6

答辩话术¶

"部署公网后每次写操作要付 gas，当前架构里是用户付——这是零私钥设计的代价，我不回避。 最对口的解法是元交易：用户离线签名、平台代付 gas，链上 author 仍是用户； 其次是换 L2。签名和鉴权查询本来不花钱，真正花钱的只有几次上链写操作， 所以成本可控、有方案，只是演示阶段没实现。"

疑问 6：部署到可信任私有服务器，是不是开销由服务器算力承担、只收少量手续费？¶

核心结论：对，这个思路就是私有链/联盟链——工业界确权存证的主流方案。 本地 Hardhat 就是它的雏形。但必须点破一个代价：用"抗篡改"换"低成本"，退回到"信任平台"。

私有链 vs 公链¶

公链主网 私有链/联盟链
gas 谁定 市场竞价（$37/次） 平台自设，可设 0
成本来源 补偿全球陌生节点 服务器算力+电费（几乎可忽略）
用户手续费 交给矿工/验证者 交给平台，平台定价
查询费用 免费（eth_call） 免费
抗篡改 最强 弱——退回到"信任平台"

关键张力（必须讲清楚）¶

私有链省了 gas，但"不可篡改"退回到"信任平台"——单节点，平台想改历史就改， 和 V1"后端代签、作者是假的"是同一个信任问题，只是换了个壳。

于是有一个真实的两难：

  • 公链：可信但贵 → 平台作不了弊，用户付不起
  • 私有链（单平台）：便宜但不可信 → 用户付得起，平台又能作弊了

工业界真实答案：联盟链（取中间值）¶

由多家权威机构（法院、公证处、版权局、平台方）共同维护，每家跑一个节点：

  • gas 极低甚至免费（节点少、非市场竞价）
  • 抗篡改比单平台强（任何一家单方面改不了，要多数机构同意）
  • 现实案例：北京互联网法院"天平链"、杭州互联网法院司法区块链、蚂蚁链存证

落回本项目¶

架构链无关，改 CHAIN_RPC_URL 指向联盟链节点即可，代码零改动。本地 Hardhat 已经是 私有链雏形。这可以写进论文"部署方案"一节。

答辩话术¶

"公链 gas 对创作者不友好。生产化的正解不是硬上公链，而是联盟链：多机构共治， gas 低到可忽略、查询免费，平台只收少量服务费；多机构背书保证平台单方面改不了历史， 不会退回中心化数据库。我的架构链无关，改 RPC 就能接联盟链。公链可信但贵， 单平台私有链便宜但信任退化，联盟链是确权场景的最优解。"

疑问 7：当前项目有无留下接入真实司法机构的接口？¶

核心结论：有，但只是"接口形态"级的预留，不是可用的对接接口。

留了什么¶

contracts/contracts/MockJudicialAnchor.sol：

// 接口：定义"未来司法锚定"的调用形态
interface IJudicialAnchor {
    function anchorToCourt(bytes32 hash, string calldata courtId) external returns (bytes32 anchorId);
}

// Mock 实现：只发事件，不连接任何真实法院链
contract MockJudicialAnchor is IJudicialAnchor {
    event Anchored(bytes32 indexed anchorId, bytes32 indexed hash, string courtId, address submitter);
    function anchorToCourt(bytes32 hash, string calldata courtId) external returns (bytes32 anchorId) {
        require(hash != bytes32(0), "hash required");
        require(bytes(courtId).length > 0, "court id required");
        anchorId = keccak256(abi.encodePacked(hash, courtId, msg.sender, block.timestamp));
        emit Anchored(anchorId, hash, courtId, msg.sender);
    }
}

但它是"孤立"的，没有接入主流程¶

代码搜索 JudicialAnchor / anchorToCourt 的结果——全项目只有 4 个文件引用：

文件 引用方式
MockJudicialAnchor.sol 定义本身
scripts/deploy.js 部署它
backend/internal/chain/chain.go Deployments 记录地址
test/MockJudicialAnchor.test.js 单独测试

三个"没有"：

  1. RegistryV2/LicenseV2/RoyaltyV2 完全没有引用它；
  2. 后端没有调用它的方法（只记录地址）；
  3. 前端零引用。

也就是说：它被部署了、记录了地址、单独测了，但主业务流（登记→授权→分账→验证） 从头到尾不碰它——是一个"摆好姿势"的占位符。

为什么这么设计¶

真实司法链对接需要机构资质 + 备案流程，超出课题范围。所以只留"调用形态" （anchorToCourt(哈希, 法院编号) → 锚点ID），证明"想过这件事、预留了位置"， 但绝不说"已对接司法链"。未来真接入时，把 Mock 换成真实司法链适配器即可，主流程不用推翻重写。

答辩口径（红线必须守住）¶

"我预留了司法锚定的调用形态——IJudicialAnchor 接口 + MockJudicialAnchor 演示实现。 但它是孤立的占位：没有接入主流程，也没连接任何真实司法链，因为真实对接需要机构资质和 备案，超出课题边界。所以我的表述是'预留了接口形态'，而不是'对接了司法链'。 这两者的差别，答辩时我会主动讲清楚。"

疑问 8：L2 协议是不是解决了 gas 费用过高这个问题？¶

核心结论：L2 大幅缓解了 gas 过高的问题，但没有"完全解决"——它是把成本 "降一个数量级"，不是"降到零"。这个分寸在答辩里很重要，说"解决了"会被追问穿帮。

L1 与 L2 的分工¶

  • L1（主链，以太坊主网）：每笔交易都要全网上万个节点各自算一遍、永久存下来——这就是 gas 贵的根源，你在为"全世界帮你记账"付费。
  • L2（第二层，Arbitrum/Optimism/Base）：把大量交易搬到链下批量处理，只把"压缩后的结果 + 证明"打包回 L1 存档。

类比：L1 是法院，每笔纠纷都开庭（贵）；L2 是仲裁庭，批量处理上百起，只把最终裁决书交法院归档一份（便宜）。

为什么 L2 便宜¶

关键在"打包分摊"：L2 把成百上千笔交易压缩成一笔再提交到 L1，那笔昂贵的 L1 gas 被上千用户分摊，人均成本暴跌。所以 gas 从主网 $37/次，降到 L2 上几毛钱甚至几分钱。

主流 L2 两大类¶

类型 代表 一句话原理
Optimistic Rollup（乐观汇总） Arbitrum、Optimism、Base 默认交易都真，事后留 7 天挑战期给人举证作弊
ZK Rollup（零知识证明） zkSync、Starknet 用数学证明"这批交易都正确"，事前证明，无需等待

但 L2 不是免费的，有自己的代价（诚实）¶

  1. 还是要付 gas，只是便宜，不是归零；
  2. Optimistic Rollup 提现慢：资产从 L2 退回 L1 要等 7 天挑战期（ZK 快但证明生成贵）；
  3. 有额外信任假设：依赖"排序器 sequencer"等新角色，中心化程度、数据可用性是新的讨论点。

落到本项目¶

  1. 架构链无关，改 CHAIN_RPC_URL 指向 L2 即可，代码零改动；
  2. L2 安全性继承自 L1（Rollup 定期把状态根提交主链），所以抗篡改仍有 L1 背书——比单平台私有链强；
  3. 低频确权场景未必首选 L2：登记一张图是低频操作，真正的门槛是"用户得有 ETH、懂钱包"，更对口的是元交易（平台代付）+ L2（降成本）的组合。

答辩话术¶

"L2 是 gas 问题的重要答案，但不是全部。它靠'把交易打包回主链'把成本降 10–100 倍， 同时通过向主链提交状态根继承 L1 安全性。但它不是免费的：还是要付 gas，且 Optimistic Rollup 有 7 天提现挑战期。所以我的完整方案是分层组合：L2 降成本 + 元交易让平台代付、 用户无感；若目标是联盟内低成本存证，联盟链是另一条并行路线。三者的取舍我分别说得出。"

疑问 9：当前用的是 L1 还是 L2？¶

核心结论：当前用的是本地 Hardhat 链，架构上等价于 L1，不是 L2。

为什么说它等价于 L1¶

特征 本项目（本地链） 属于
合约直接部署在 EVM 上 ✅ L1 特征
交易直接发给本地节点执行 ✅ L1 特征
有 rollup 打包/压缩机制 ❌ 没有 无 L2 特征
有 sequencer/状态根提交到另一条链 ❌ 没有 无 L2 特征

所以它是一条"本地模拟的以太坊主网（L1）"，跑主网同款 EVM、同款账户模型， 只是只有 1 个节点、数据在内存里、gas 免费。

更准确的说法¶

它既不是真正的 L1 也不是真正的 L2——L1/L2 是"公网"里的概念。本地 Hardhat 链是 "L1 的本地仿真"：

  • hardhat.config.js 里 chainId: 31337，就是本地模拟主网；
  • 后端连 http://127.0.0.1:8545，不是任何公网 L1 或 L2。

呼应前面的 gas 问题¶

之前说"上公网要付 gas"，正是因为本地链模拟的是 L1，而 L1 的 gas 本来就贵（$37/次）。 未来要便宜，就改 RPC 指向 L2——架构链无关，代码零改动。

答辩口径¶

"当前跑在本地 Hardhat 链上，它等价于 L1 的本地仿真——合约直接部署在 EVM、交易直接发节点， 没有任何 L2 打包机制。选它是因为零成本零延迟，适合验证架构正确性。系统本身链无关： 改一个 RPC 地址，就能从本地链切到公网 L1 或 L2，代码不用改。"

疑问 10：如果要仿真 L2 该怎么做？¶

核心结论：有两条路——连公共 L2 测试网（推荐，改配置即可） 或 本地真起 L2 节点（进阶）。

两种"仿真 L2"¶

方式 做法 成本 适合
A. 连公共 L2 测试网 RPC 指向 Arbitrum/Optimism/Base 测试网 极低（改配置） 演示、答辩、验证链无关
B. 本地真起 L2 节点 用 op-stack / Arbitrum Nitro 跑真 rollup 较高（部署复杂） 深挖 L2 内部机制

对本项目，方案 A 就够，且几乎零代码改动。

方案 A：连公共 L2 测试网（以 Arbitrum Sepolia 为例，4 处配置）¶

  1. 合约层：hardhat.config.js 加 arbitrumSepolia 网络（RPC + 部署账户私钥，用环境变量别硬编码）；
  2. 部署：npx hardhat run scripts/deploy.js --network arbitrumSepolia，生成 deployments/arbitrumSepolia.json；
  3. 后端：改 CHAIN_RPC_URL 和 DEPLOYMENTS_FILE 两个环境变量；
  4. 前端：MetaMask 切到 Arbitrum Sepolia（chainId 421614），从公共水龙头领测试 ETH。

会遇到的坑（项目代码里已埋了这些边界）¶

坑 原因 应对
水龙头 403 项目 Faucet 只在 chainId==31337 放行，L2 测试网没有 hardhat_setBalance 用 L2 官方公共水龙头
evm_increaseTime 不存在 Hardhat 专用 RPC，L2 测试网没有 依赖时间快进的用例跳过
出块 12s（比本地慢） 前端"等事件同步"要等更多轮 调大轮询次数/超时
RPC 限流 免费节点有请求频率上限 用付费 RPC 或降低轮询频率

这些正是 learning/10-实战 练习三"部署到 Sepolia"里列出的坑——说明边界已经想清楚。

方案 B：本地真起 L2 节点（进阶，可选）¶

  • Optimism：官方 op-stack（op-geth + op-node），docker-compose 一键起本地 rollup；
  • Arbitrum：官方 nitro-testnode 仓库，docker 起本地 Arbitrum 链（L2 + 本地 L1 一起跑）；
  • Polygon：polygon-edge 起本地链。

这条路能真正看到"L2 打包交易 → 提交状态根到 L1"的全过程，但配置复杂、吃资源， 一般是为了研究 L2 内部机制，而不是为了跑业务系统。

答辩口径¶

"要验证系统在 L2 上能跑，我不需要真起一条 rollup——架构链无关，改四处配置就能切到 Arbitrum/Optimism 测试网，gas 立刻降一个数量级。切换会踩几个边界：本地水龙头在 L2 上 403、 evm_increaseTime 这类专用 RPC 不存在、出块变慢——这些我在实战练习里都列出来了。 要深挖 L2 内部，则用 op-stack 或 Arbitrum Nitro 本地起真 rollup。"

十个疑问的内在逻辑¶

这十个疑问其实是一条完整的追问链，环环相扣：

``` 代码量为什么少？ └─ 因为没有用户系统、没有鉴权后端 └─ 那身份/鉴权怎么解决？ └─ 靠钱包签名 + 链上 msg.sender └─ 但本地链上这个还成立吗？ └─ 身份鉴权成立，抗篡改不成立 └─ 上公网又付不起 gas ├─ L2 能解决吗？→ 大幅缓解，但不根治 │ ├─ 那当前是 L1 还是 L2？→ 本地 Hardhat，等价 L1 │ └─ 要仿真 L2 怎么做？→ 连测试网 or 本地 op-stack └─ 那用私有链/联盟链？→ 省 gas 但信任退化 └─ 那司法对接留了吗？→ 只留了接口形态

最终落点：链形态的选择（公链 vs L2 vs 联盟链 vs 私有链）是本项目最核心的设计权衡， 也是答辩最容易被打穿、也最能展示深度的地方。
