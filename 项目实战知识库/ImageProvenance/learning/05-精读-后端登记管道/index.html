05 精读:后端登记管道¶

学习目标:把 POST /api/works/prepare 的十步管道画成图并讲出每步的失败路径; 理解"后端做重活但不碰私钥"的分工;顺带吃透验证四态的实现。

主文件:backend/internal/api/work_handler.go(Prepare / VerifyFile / Faucet), 配套模块按出场顺序:hash → repository → c2pa → similarity → storage → tsa → chain。

5.1 先画管道(读 Prepare 函数,边读边画)¶

上传 image + title + authorAddress
  1  UTF-8 校验 title          → 无效直接 400(乱码缺陷的防御,见 docs/04 修复记录)
  2  SHA-256(原文件)          → originalHash        [hash/sha256.go,TeeReader 边读边算]
  3  查重 FindByAnyHash        → 命中返回 409 + 提示哪个哈希撞了(链上还有第二道)
  4  BuildManifest             → 声明 JSON + manifestHash [c2pa/manifest.go]
  5  pHash 相似预警            → warnings 数组(只提示不拦截)[similarity/phash.go]
  6  c2patool 签名+trust验证   → 签名版文件 + signedHash + c2paStatus [c2pa/tool.go]
  7  存储 pin ×3               → 原图/签名版/声明的 CID [storage/{ipfs,local}.go]
  8  (可选)RFC3161            → tsaTimestamp;失败静默跳过 [tsa/tsa.go]
  9  abi.Pack registerWork     → txRequest{to,data,chainId} [chain/client.go]
 10  SQLite 入库               → 状态 PENDING_ANCHOR,返回 201

注意返回体里的 timingsMs——每步耗时都量化(实测:C2PA 250ms、IPFS 5ms、TSA 450ms、 总 799ms)。面试可讲:管道每一步可观测,是定位性能问题的基础设施。

5.2 三个值得精读的设计点¶

① 优雅降级(逐个找到代码位置)¶

依赖 挂了会怎样 代码位置
c2patool 不存在 c2paStatus=unavailable,登记继续(但无签名版、无 txRequest) buildC2PAAssets 开头 CheckTool
IPFS 未启动 自动落本地内容寻址存储(local- 目录) router.go 按 STORAGE_MODE 选 Store 实现
TSA 超时/断网 跳过时间戳,不阻塞 Prepare 里 if err == nil 才写入
链未部署 prepare 仍可用,只是没有 txRequest(纯链下模式) if h.chain != nil

思考:为什么 c2patool 挂了不该 500?(登记的核心是哈希+存证;签名是增强项—— 降级优先级排序是后端设计的常见考题。)

② 后端与私钥的"绝缘"¶

第 9 步只做 abi.Pack 打包 calldata——打包不需要私钥,签名发送在用户钱包。 搜一遍 backend/ 目录:没有任何私钥配置项(一期的 chain/registry.go 代签模块已整体删除, 见 docs/04 M3 记录)。/api/health 的 signerMode: creator-wallet 是这个事实的对外声明。

③ 编码边界防御¶

第 1 步 utf8.ValidString(title):Windows curl 按 GBK 发表单,坏字节一旦入库并嵌进 C2PA manifest 就永久乱码——在入口拒绝,而不是在出口修补。背后有个真实缺陷故事 (docs/04"作品标题乱码"),面试讲踩坑就用它。

5.3 验证四态:VerifyFile 的判定顺序¶

计算上传文件 SHA-256
  ├─ 命中 DB original_hash  → original(原始文件)
  ├─ 命中 DB signed_hash    → signed(官方签名分发版)
  ├─ DB 全 miss → 链上 getWorkByHash 兜底 → 命中则按哪个哈希相等定 original/signed
  ├─ 仍 miss → c2patool 读文件内嵌 manifest → 提取 identifier(=originalHash)反查
  │            命中 → manifest-only(签名后被篡改,附 C2PA state=Invalid)
  └─ 全部落空 → none(无记录)

三个细节:① DB 命中 manifest-only 级别时不直接返回,继续走完整 manifest 提取流程 (读代码确认这点,想想为什么);② 链上兜底路径的 source 字段返回 chain—— 前端会显示"链上反查(本地索引未命中)";③ 提取 identifier 用的正则要求 0x+64 位 hex, 对应 manifest.go 里嵌入的 originalHash 格式。

动手:把 backend/data/index.db 改名 → 重启后端 → 验证一张已登记原图 → 观察结论照常但 source=chain → 改回来。这 5 分钟实验讲透了"验证不依赖链下库"。

5.4 仓储层(repository/work_repository.go)速览¶

  • 三表:works(original_hash UNIQUE + signed/manifest 索引)、licenses(事件镜像)、 chain_cursor(游标,第 06 章主角);
  • FindByAnyHash 按 original→signed→manifest 顺序试探并返回命中层级—— 这个"层级"就是四态的 tier;
  • 迁移风格:启动时 CREATE TABLE IF NOT EXISTS + pragma_table_info 防重入 ALTER (chain_status 列就是这样加的,旧库无损升级)。

5.5 水龙头(Faucet):小接口,三个设计点¶

  1. chainId != 31337 → 403:公共测试网上这个 RPC 根本不存在,双保险;
  2. 充值后补 evm_mine:钱包按区块高度缓存余额(第 02 章 2.6 的真实应用);
  3. 响应带 balanceWei:前端直读链上余额,绕开 MetaMask 缓存。

自测¶

  1. 不看图,默写 prepare 十步顺序;哪几步失败会 4xx/5xx,哪几步失败会静默降级?
  2. 同一张图 prepare 两次,第二次在哪一步被拦?拦截依据是什么?如果绕过后端直接重放 txRequest 呢?
  3. "签名后被篡改"态的完整判定链路是什么?为什么改原图一个字节得到的是 none 而不是它?
  4. 后端如何证明自己"没有能力"代签?(三个证据点)
  5. timingsMs 里哪一步最贵?如果要求 prepare P95 < 300ms,你先动哪里?
