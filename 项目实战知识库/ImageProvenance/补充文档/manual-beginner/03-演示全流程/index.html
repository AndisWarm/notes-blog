03 演示全流程(小白版,带解说)¶

本篇目标:用三个账户把系统完整走一遍,并且每一步都讲清楚"刚刚发生了什么、 数据去了哪里"。这是全手册最长的一篇,建议照着屏幕一步步做。 原手册 manual/03 是"浓缩动作版",本篇是"动作 + 原理版"。

3.0 先认识三个角色和三个页面¶

三个角色(为什么是三个?)¶

角色 是谁 在这个系统里做什么 对应测试账户
甲 创作者 上传作品、签发授权、设分账、标状态 0x7099…79C8
乙 使用方 接受授权;顺便扮演"坏人"演示越权拦截 0x3C44…93BC
平台方 分销渠道 只出现在分账规则里,不需要任何操作 0x90F7…b906

为什么需要三个账户?因为系统要演示三件不同的事: 权限(只有作者能操作)、授权(作者授权给别人用)、分账(收益在作者和平台之间分)。

三个页面(前端导航栏切换)¶

页面 谁用 干什么
创作者 甲 上传登记作品、看作品列表
授权管理 甲(查看/签发)、乙(演示越权) 签发/撤销授权、设置分账、标记争议/撤销声明
来源验证 任何人(不用连钱包) 上传任意文件,得到鉴定结论

3.1 第一步:甲登记作品上链(创作者页)¶

操作步骤¶

  1. 右上角连接 MetaMask,切到甲账户(页面会自动请求切换到 Hardhat Local 网络)。
  2. 选择图片文件(PNG/JPEG),填标题,例如"风景写生·演示"。
  3. 点 ① 生成声明与签名。这一步全在链下(不花 gas、不用确认交易)。
  4. 点 ② 钱包上链确权 → MetaMask 弹出交易 → 确认。

这步背后发生了什么?(对应第 00 篇 0.9 的图)¶

点 ① 之后,后端依次做了:

a. 算三哈希:originalHash(原图指纹)/ signedHash(签名版指纹)/ manifestHash(声明指纹)
   → 声明 manifest 里写入了标题、作者地址、原图哈希——声明和链上记录"互相指向"
b. 用自建 CA 的私钥给图片做 C2PA 签名 → 产出"签名分发版"(新图片文件)
c. 把签名版和声明存进 IPFS(或本地存储)→ 得到 CID
d. 算 pHash 并与已有作品比对 → 可能给出相似预警
e. 把"待签名交易"(txRequest:发给哪个合约、带什么数据)返回给前端

结果卡片上你会看到: - 三个哈希 + 签名版 CID; - 徽标 C2PA trusted(自建 CA + 信任锚验证通过,第 00 篇 0.5 讲过 Trusted 含义); - 若与已登记图相似,黄色 pHash 相似预警(仅提示,不拦截)。

点 ② 之后: - MetaMask 弹出的是"你要把这条数据发到 RegistryV2 合约"的确认框——签名动作发生在你的浏览器里; - 确认后交易被发到链上执行,合约把三哈希、作者地址(=msg.sender,即甲的钱包地址)写入账本; - 合约执行成功会发出 WorkRegistered 事件; - 后端监听器(每 2 秒轮询一次,第 00 篇 0.9 第 ⑧ 步)收到事件后,把作品标记为 ANCHORED; - 前端列表状态从 PENDING_ANCHOR 翻为 ANCHORED。

两个关键点(答辩高频)¶

  1. 列表"作者地址"= 甲的钱包地址。这是 V2 的核心设计:后端零私钥, 谁签名谁是作者——后端想冒充甲也做不到,因为它没有甲的私钥。
  2. 防抢注:同一张图再走一次 ①,后端直接 409 "该文件已注册过"(哈希唯一约束, 第 00 篇 0.2 讲过哈希唯一性);即使有人拿到旧 calldata 绕过后端直接发交易, 合约也会因 duplicate: original hash 回滚——双重防线。

3.2 第二步:甲 → 乙 签发授权(授权管理页)¶

操作步骤¶

  1. 保持甲账户,进入授权管理,下拉选中刚登记的作品。
  2. "签发授权"卡片:被授权方填乙的地址,用途如"网页横幅 web-banner", 有效期 30 天 → 点签发授权(上链) → MetaMask 确认。
  3. 等约 3 秒,"已同步的授权记录"表格出现这条记录。
  4. 再签一笔短期授权(1 天)给乙——演示"同一作品多笔授权并存"。
  5. 对其中一笔点撤销 → 确认 → 3 秒后该记录"有效期"列变已撤销。

原理解说¶

  • 授权记录不是存在前端的:签发交易上链后,LicenseV2 合约发出 LicenseGranted 事件,监听器把它镜像进 SQLite(第 06 篇 4.2 会讲这张表)。 所以表格里的数据来自"链上公告",页面刷新不丢。
  • "有效期"用 Unix 秒存(第 06 篇 4.4 会看到字段),前端显示成人话。
  • 撤销后是否还有效? 链上有个 isLicensed(作品, 乙) 查询:只要还有一笔 未过期且未撤销的授权,乙就仍是合法使用方——这就是"多笔并存"的意义: 撤销一笔不影响其他笔。

3.3 第三步:乙的越权攻击演示(切到乙账户)¶

MetaMask 切到乙账户(页面右上角地址会变),仍选同一作品,然后逐个尝试:

乙的操作 结果 为什么会这样
乙给自己"签发授权" 红色提示:合约拒绝:当前钱包不是该作品的链上作者(越权保护生效) LicenseV2.grantLicense 内部调用 Registry.authorOf(作品ID) 校验,调用者不是作者 → revert(交易回滚)
乙修改分账规则 同上,not author 回滚 RoyaltyV2 同样走 authorOf 校验
乙点"标记争议/撤销声明" 同上 setStatus 也只有作者能调
乙撤销甲签发的授权 合约 not licensor 回滚 只有"签发人本人"能撤销自己的授权

为什么这段是"演示重点"?¶

因为权限是合约在链上强制的,不是前端按钮隐藏了就算完。 任何客户端(网页、脚本、别人写的工具)直接调合约,结果一样被拒。 这回答了一个常见疑问:"前端不让点,绕过前端是不是就行了?"——答案是不行, 防线在链上。

3.4 第四步:甲设置分账规则(切回甲)¶

操作步骤¶

  1. "分账规则"卡片首次显示"该作品尚未设置分账规则(链上无记录)"。
  2. 平台方地址填 0x90F7…b906,创作者份额填 8500 → 设置分账(上链) → 确认。
  3. 卡片回显:当前生效规则:创作者 85% / 平台 15%,平台方 0x90F7…(更新时间)。
  4. 改成 9000 再设一次 → 回显变 90% / 10%。

原理解说¶

  • 份额单位是基点(BPS):1 基点 = 0.01%,总额恒为 10000 = 100%。 8500/10000 = 85%,这就是前端显示 85% 的来源。
  • 合约 RoyaltyV2 存的是 {workId, creator, platform, creatorShareBps, platformShareBps}, 并且校验 creatorShareBps + platformShareBps == 10000(加起来必须等于 100%)。
  • 规则可重复设置覆盖——这就是第 4 步演示的"作者可以更新规则"。
  • ⚠️ 口径提醒:RoyaltyV2 只在链上记录"比例",不做真实支付。 这是研究边界(第 00 篇 0.8 提过),答辩时别把话说满。

3.5 第五步:甲标记链上状态(争议 / 撤销声明)¶

操作步骤¶

  1. "作品链上状态"卡片当前显示正常 → 点标记争议(上链) → 确认 → 约 3 秒后徽标变争议中,作品列表里出现 ⚠ 前缀。
  2. 切到来源验证页按 ID 查询:顶部出现红色警示"作者已在链上将该作品标记为存在权属争议,引用前请自行核实"。
  3. 回授权管理点恢复正常(上链),徽标复原。(撤销确权声明同理,只是警示文案不同。)

原理解说¶

  • 链上状态三档:0 Active / 1 Disputed / 2 Revoked(第 06 篇会详细讲);
  • 每次变更发出 WorkStatusChanged(id, status) 事件 → 监听器镜像到 SQLite → 前端读到后显示徽标/警示。全链路 3 秒内完成;
  • 历史不可删:链上只存"最新值",但每次变更的事件都永久留在区块里。 这就是"存证"的意义——记录可以更新,但痕迹抹不掉。

3.6 第六步:任何人验证(来源验证页,不需要钱包)¶

四态对照表(核心中的核心)¶

你上传什么 结果 原理
甲登记时的原图 绿色 原始文件 文件哈希命中登记的 originalHash
签名分发版 绿色 官方签名分发版 哈希命中 signedHash
签名版改动 1 字节 红色 签名后被篡改 哈希全不中,但文件内嵌的 C2PA 声明还在 → 通过声明里的 identifier 反查 → 命中记录,结论"签名后被篡改"(C2PA 校验 Invalid)
任意无关图片 黄色 无记录 哈希不中,声明也没有 → 无记录

签名分发版从哪拿? - IPFS 模式:打开 http://127.0.0.1:8181/ipfs/<签名版CID>(CID 在登记结果卡片上); - 本地存储模式:在 backend/data/objects/<CID>/ 目录下。

最后一步:下载证据 PDF¶

点下载证据 PDF,里面包含:三哈希、作者地址、区块时间 + RFC3161 双时间戳、二维码。 二维码扫码直达本验证页(通过 ?workId= 参数定位作品)。

这是一份"技术取证材料":证明"某文件在某个时间被某地址登记过、其指纹是什么"。 它不替代司法鉴定——链上记录不能证明上链之前内容的真实性(第 00 篇研究边界)。

3.7 附:命令行(API)演示¶

如果你想体验不用网页、直接用命令调接口:

# 上传登记(注意:Windows curl 发中文标题会被 400 拒绝——GBK 问题,中文走网页)
curl -F "image=@demo.png" -F "title=demo-cli" -F "authorAddress=0x7099..." http://127.0.0.1:8080/api/works/prepare
# 返回 txRequest{to,data}——由钱包/脚本签名发送,后端不代签(核心设计!)

# 验证任意文件
curl -F "image=@somefile.png" http://127.0.0.1:8080/api/works/verify-file

# 水龙头(仅本地链)
curl -X POST -H "Content-Type: application/json" -d '{"address":"0x你的地址"}' http://127.0.0.1:8080/api/chain/faucet

# 作品与授权记录
curl http://127.0.0.1:8080/api/works
curl http://127.0.0.1:8080/api/works/1

为什么"上链一步"没法用 curl 完成? 因为发交易需要私钥签名——curl 没有私钥,而私钥在 MetaMask 里。 这正是零私钥设计:签名这个动作只可能由钱包所有者完成。 (E2E 测试脚本除外:它们直接用 Hardhat 公开测试私钥在脚本里签名,第 04 篇会讲。)

3.8 演示复盘:三张图总结¶

登记:  上传 → 三哈希+C2PA签名+存IPFS → 钱包签名上链 → 监听器 → ANCHORED
授权:  甲签名交易 → LicenseGranted 事件 → 监听器镜像 → 表格出现记录
验证:  上传文件 → 算哈希 → 比对登记表/链上 → 四态结论

贯穿全程的三条线: 1. 身份线:所有"谁干的"都由钱包签名决定,后端无私有钥匙; 2. 数据线:链上是"账本",SQLite 是"索引",IPFS 是"仓库",各司其职; 3. 同步线:链上发生 → 事件 → 监听器 → 索引 → 前端,永远由事件驱动。
