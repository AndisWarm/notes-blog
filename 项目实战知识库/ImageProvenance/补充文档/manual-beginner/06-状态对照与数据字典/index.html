06 状态对照与数据字典(小白版)¶

本篇目标:把最容易混淆的"四套状态"彻底讲清,再把每张表、每个字段讲明白。 对照原手册 manual/06-状态对照与数据字典.md 阅读——本篇是它的逐句注释版。

6.1 为什么会有"四套状态"?先讲清楚¶

一个作品在系统里要经过多个环节,每个环节都有自己的"状态",而且这些状态 互不相同、互不替代。混淆它们是最常见的理解错误,先看一句话区分:

体系 一句话 描述对象
① 链下作品状态 status 登记流程走到哪一步了(进度) 作品
② 链上作品状态 chainStatus 作者最新表态是什么(表态) 作品
③ 验证四态 matchTier 这份文件和登记记录什么关系(鉴定) 某一份文件
④ C2PA 校验态 c2paStatus 签名版的凭证可信吗(凭证质量) 签名

再换个说法:

  • ①② 描述作品(链下的登记记录);
  • ③ 描述某份文件(每次验证时实时判定,不落库);
  • ④ 描述签名质量(一次性写入)。

最实用的记忆法:被问"这个作品什么状态"时,先反问自己"问的是哪套?" 进度?表态?还是这次上传的文件的鉴定结论?

6.2 四套状态的详细流转¶

① 链下作品状态(单向推进,只能往前走)¶

UPLOADED → SIGNED → PINNED ──(链已配置,calldata 已返回)──→ PENDING_ANCHOR ──(监听到 WorkRegistered)──→ ANCHORED

大白话解释每个词:

状态 含义
UPLOADED 文件上传了
SIGNED C2PA 签名完成了
PINNED 文件存进 IPFS/本地了
PENDING_ANCHOR 一切就绪,交易 calldata 已返回,等钱包上链
ANCHORED 链上确认了(监听器收到 WorkRegistered 事件)

三个实际观察要点:

  1. 前三个状态在 prepare 一个请求内瞬间走完——你看到的时候已经是 PINNED 或 PENDING_ANCHOR;
  2. 只 prepare 不上链 → 永远停在 PENDING_ANCHOR(合法状态,不是错误);
  3. ANCHORED 由事件驱动,不是前端回执驱动——后端宕机期间上链,重启后自动补推进 (断点续扫,第 00 篇 0.9 第 ⑧ 步)。

② 链上作品状态(可任意跳转,只有作者能改)¶

        setStatus(1)              setStatus(2)
Active ────────────→ Disputed ────────────→ Revoked
  ↑ ←──────────── setStatus(0) ──────────────┘   (任意两态间均可直接切换)
取值 含义
0 Active 正常
1 Disputed 争议中(作者标记)
2 Revoked 已撤销确权声明

要点:

  • 初始恒为 Active(合约 registerWork 写死);
  • 每次变更发 WorkStatusChanged(id, status) 事件 → 监听器镜像,延迟 ≤3s;
  • 历史不可删:链上只存最新值,变更历史永远留在事件日志里。

③ 验证四态(判定优先级,不是状态机)¶

上传文件算 SHA-256
 1. 命中 originalHash → original(原始文件)
 2. 命中 signedHash   → signed(官方签名分发版)
 3. (库 miss 时先走链上 getWorkByHash 兜底,再按相等哈希归入 1/2)
 4. 文件内嵌 manifest 的 identifier 反查命中 → manifest-only(签名后被篡改)
 5. 全部落空 → none(无记录)

注意第 3 条:本地索引查不到时,接口会直接问链上再判定一次—— 这就是"数据库可丢、链不可丢"的设计体现。

④ C2PA 校验态¶

值 含义 产生条件
trusted 签名有效 + 证书链落在信任锚内 正常路径(自建 CA + trust anchor)
valid-untrusted 签名有效但根不在信任列表 信任锚未配置/证书不在链内
invalid 内容或断言校验失败 硬绑定不匹配、必填断言缺失(如 digitalSourceType)
unavailable: <原因> c2patool 不可用,跳过签名 工具路径错误/未安装(登记降级继续)

6.3 组合语义速查(答辩/面试高频)¶

组合 含义
status=ANCHORED 且 chainStatus=2 已确权登记,但作者其后撤销了确权声明——记录仍在,前端显示红色警示
status=PENDING_ANCHOR 但链上其实已注册 后端还没扫到事件(宕机/延迟窗口),数秒后自动翻转
matchTier=signed 且 chainStatus=1 文件是官方签名版没被动过,但作品正处争议——绿色结论 + 红色警示同时显示,不矛盾(一个说文件,一个说作品)
matchTier=manifest-only 且 c2paState=Invalid 标准的"签名后被篡改"证据组合
c2paStatus=unavailable 且 status=PINNED c2patool 缺失时登记的作品:无签名版、无 txRequest,不能上链

6.4 数据字典:每张表每个字段¶

读法:左边是数据库列名,中间是接口返回的 JSON 字段名,右边是解释。 看到 0x+64hex 就是 SHA-256 哈希(第 00 篇 0.2)。

4.1 SQLite works 表 ↔ Work JSON(作品主表)¶

列 JSON 字段 类型 来源 说明
id id INTEGER PK 自增 链下索引 ID(URL /api/works/:id 用它)
chain_work_id chainWorkId INTEGER WorkRegistered 事件 链上作品 ID,0 = 未上链
title title TEXT 上传表单 入口强制 UTF-8
author_address authorAddress TEXT prepare 传入,事件回填为准 恒小写
original_hash originalHash TEXT UNIQUE 后端计算 0x+64hex;唯一约束 = 链下防重
signed_hash signedHash TEXT(索引) 后端计算 三元组第二元
manifest_hash manifestHash TEXT(索引) 后端计算 三元组第三元
original_cid originalCid TEXT 存储层 原图 CID
image_cid imageCid TEXT 存储层 签名分发版 CID;local 模式形如 local-<sha256>
manifest_cid manifestCid TEXT 存储层 声明文件 CID
c2pa_report_cid c2paReportCid TEXT 存储层 C2PA 校验报告 CID
c2pa_status c2paStatus TEXT c2patool 验证 6.2 节④
phash phash TEXT 相似模块 64bit 十六进制感知哈希
image_file_name imageFileName TEXT 上传文件 原文件名
image_size imageSize INTEGER 上传文件 字节数
storage_backend storageBackend TEXT 配置 ipfs / local
status status TEXT 后端 6.2 节①
chain_status chainStatus INTEGER WorkStatusChanged 事件 6.2 节②;旧库自动 ALTER 迁移,默认 0
tx_hash txHash TEXT 事件回填 存证交易定位
block_number blockNumber INTEGER 事件回填 存证区块定位
tsa_timestamp tsaTimestamp TEXT RFC3161 空 = 未配置 TSA 或获取失败
created_at createdAt TEXT(RFC3339) 后端 UTC 时间

4.2 SQLite licenses 表 ↔ License JSON(授权记录,纯事件镜像)¶

重要:后端从不主动写业务值——这张表的每一行都来自链上事件。

列 JSON 字段 来源事件字段
chain_license_id(PK) chainLicenseId LicenseGranted topics[1]
chain_work_id chainWorkId topics[2]
licensee licensee topics[3],存储时转小写
licensor licensor data 解包
usage usage data 解包(原文)
valid_until validUntil data 解包(unix 秒)
revoked revoked LicenseRevoked 置 1;upsert 幂等
tx_hash txHash 事件所在交易
created_at createdAt 入库时间

事件字段怎么解包(为什么是 topics/data)见 4.5,现在只要知道:链上事件 → 表行。

4.3 SQLite chain_cursor 表(断点续扫的"书签")¶

列 说明
name(PK) 游标名,当前仅 "main"
last_block 已处理到的区块高度;删除该行 = 下次从创世块全量重扫(幂等,安全)

这就是"断点续扫"的物理载体:监听器每轮扫完把高度记在这里, 下次从 last_block+1 继续——所以重启不丢、宕机不丢。

4.4 链上结构(合约存什么)¶

结构 字段
RegistryV2.Work id、author、originalHash/signedHash/manifestHash(bytes32)、imageCid/manifestCid(string)、createdAt(uint64 区块时间)、status(enum)
LicenseV2.LicenseRecord id、workId、licensor、licensee、usage、validUntil(uint64)、createdAt、revoked(bool)
RoyaltyV2.RoyaltyRule workId、creator、platform、creatorShareBps/platformShareBps(uint16,和恒为 10000)、updatedAt

基点:1 基点 = 0.01%,8500/10000 = 85%(第 03 篇 3.4 讲过)。BASIS_POINTS = 10000 是合约常量。

4.5 事件与 topics 布局(链下解码的"契约")¶

背景知识:以太坊事件 = 一条"公告"。topics 是公告的"标签"(可索引,最多 3 个), data 是正文(ABI 编码)。链下解码必须按这个布局来,这就是监听器的"契约":

事件 topics[1..] (indexed) data (ABI 编码)
WorkRegistered(id, author, 3×hash) id, author originalHash, signedHash, manifestHash
WorkStatusChanged(id, status) id status(uint8)
LicenseGranted(id, workId, licensee, …) id, workId, licensee licensor, usage, validUntil
LicenseRevoked(id, workId) id, workId —
RoyaltyRuleSet(workId, creator, platform, …) workId, creator, platform creatorShareBps, platformShareBps(当前未被监听,历史需回放事件)

最后一行值得注意:分账事件目前没有被监听器监听——所以分账历史无法从 SQLite 查,要查只能回放链上事件(这属于已知边界,learning/10 练习一有专门练习)。

4.6 验证结果 VerificationResult(不落库,接口实时返回)¶

字段 含义
matched 是否命中
matchTier 四态(6.2 节③)
reason 人话解释
computedHash 本次文件哈希
source db / chain(chain = 链上反查路径)
c2paState Trusted/Valid/Invalid,仅 manifest 路径有
work 关联作品(含 chainStatus 供警示)

6.5 口径提醒(三条纪律)¶

  1. 被问"作品状态"先反问是哪一套:流程态、链上态、鉴定态还是凭证态;
  2. ①的 ANCHORED 不因②变化而变——撤销声明的作品仍是"已锚定", 这是存证系统"记录不可抹"的体现;
  3. ③永远描述这次上传的文件——同一作品可以同时有四份文件, 各得四种结论,互不矛盾。
