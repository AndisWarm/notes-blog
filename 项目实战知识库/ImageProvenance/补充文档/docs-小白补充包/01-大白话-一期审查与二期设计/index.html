01 大白话：一期审查报告 与 二期改进设计方案¶

对应原文档：docs/01-一期设计审查报告.md、docs/02-二期改进设计方案.md 本文作用：在你读那两篇之前，先讲清背景故事——一期系统是什么、为什么被审查出致命问题、二期怎么改。

一、背景：这个项目经历了"两期"¶

任何大项目都不是一次做成的。这个系统先做了一期（名字叫 ImageProvenance_bak，即"备份"）， 跑通了一个最小完整流程，然后作者自己（或和导师一起）对一期做了架构审查， 发现一堆问题，决定做二期（也就是你现在看到的 ImageProvenanceV2）。

一句话记住两期区别：

一期：先跑通再说（能用，但有结构性缺陷）
二期：把"确权"两个字做实（重做核心设计）

docs/01 是"一期有什么毛病"的诊断书，docs/02 是"二期怎么治"的处方。

二、先补基础概念（读审查报告前必须知道的 5 个词）¶

1. 什么是"确权"？¶

"确权" = 确定权利归属，即证明"这张图是我的"。图像是数字文件，复制零成本， 别人拿了你的图，你很难证明你是作者。这个系统要解决的正是这个问题。

2. "上链"是什么意思？¶

把一条信息（比如图片的指纹）写入区块链（这个项目用的是本地模拟的以太坊链）。 上链之后的特点是：

  • 改不了：一旦写入，任何人都改不掉（区块链的防篡改性质）；
  • 有记录：谁在什么时间写入的，全网可见；
  • 可证明：任何人任何时候都能查。

3. 什么是"合约"（智能合约）？¶

你可以把合约理解为跑在区块链上的小程序，它有几个关键性质：

  • 代码是公开的，写在链上；
  • 任何账户都可以调用它；
  • 它有一个特殊的"作者字段"：msg.sender——谁调用的，这个字段就是谁的地址。 msg.sender 由交易签名决定，伪造不了（详见第 4 节）。

4. "后端代签"是什么意思？为什么是致命的？¶

一期系统的流程是：创作者上传图片 → 后端服务器用自己持有的私钥把指纹发上链。 问题出在这里：

  • 合约记录 author = msg.sender，而 msg.sender 永远是后端的地址（因为交易是后端发的）；
  • 结果：链上所有作品的作者都是同一个地址——服务器的地址。

打个比方：你在一家公证处存证，公证处替你在公证书上签名，公证书上写的"作者"全是 公证处的名字，而不是你的名字。那这份公证还有什么意义？

这就是 docs/01 里说的 P0（最高优先级）致命缺陷：链上作者身份失真。

5. "哈希"是什么？为什么要哈希上链？¶

哈希 = 一段任意内容通过算法算出的固定长度的"指纹"。特点：

  • 同一内容算出的指纹永远相同；
  • 内容改一个字节，指纹就完全变了（叫"雪崩效应"）。

所以"把图片的哈希上链" = "把图片的指纹上链"。好处是链上只存 32 字节的指纹， 不用存整张图（存图太贵），验证时重新算指纹对比即可。

三、docs/01 审查报告：一期发现了 8 个问题¶

审查报告把问题按严重程度排序。前三个是致命的（P0），你必须先理解：

# 问题 白话解释 为什么致命
1 链上作者身份失真（后端代签） 链上所有作品作者都是服务器地址 "确权"系统的根基塌了——作者字段是假的
2 C2PA 哈希语义未落地 只有"一个哈希"，分不清是原图的还是签名版的 用户拿签名版图片验证时对不上号，演示会"自打脸"
3 三份合约互相孤立，权限形同虚设 任何人都能给任何作品签发授权、设置分账规则 "越权操作"一试就破，系统形同虚设

还有几个次要问题（P1/P2），简单了解即可：

  • P1：合约没有"哈希反查"功能——链下数据库一丢，验证就做不了；
  • P1：C2PA 签名永远是 untrusted（"不可信"）——签了名但没人认；
  • P1：后端没有事件监听——链上链下数据可能对不上；
  • P2：前端 995 行写在一个文件里——没法演示、没法讲；
  • P2：承诺过的加分项（双时间戳、相似预警）没做。

四、docs/02 改进方案：二期怎么治——"四个闭环"¶

二期的核心原则是 "不扩功能面，做实四个闭环"。这是整份设计文档的灵魂，背下来：

闭环 1 身份：链上作者 = 创作者本人的钱包
闭环 2 验证：三个哈希 + 链上反查，四态验证
闭环 3 授权：合约之间互相校验，越权被拒
闭环 4 信任：自建 CA，C2PA 验证从 untrusted 变 trusted

闭环 1：身份（解决问题 1）——最核心的改动¶

把流程拆成两段：

一期（有缺陷）：
  前端(只展示钱包) → 后端(持私钥代签一切) → 合约(author=后端地址)

二期（目标）：
  创作者钱包 ──签名/发交易──→ 合约(author=创作者地址)
        │ 上传原图
        ▼
  后端(无签名权)：算哈希 / C2PA 签名 / IPFS 存储 / 监听事件

关键点：

  • 后端从"代签者"降级为"服务者"——它不再持有任何链上私钥；
  • 上链交易由创作者自己的钱包（如 MetaMask）发起，合约里 author = msg.sender = 创作者；
  • 后端只负责"准备好待上链的数据"，把待签交易打包返回给前端。

闭环 2：验证（解决问题 2、4）——"哈希三元组"与"四态验证"¶

一期只有一个哈希，说不清是哪个文件的。二期定义三个哈希（同一套术语，全项目统一）：

字段 是什么的哈希 用途
originalHash 创作者上传的原始文件 创作时点的完整性锚点
signedHash C2PA 签名后的签名版文件 对外分发版本的验证锚点
manifestHash 声明内容（Manifest） 来源声明内容的锚点

为什么必须三个？因为这三个东西是三个不同的字节流：原图、签名后的图（c2patool 会把声明嵌入文件产生新文件）、声明本身。只存一个哈希，另外两个形态就验证不了。

验证时的四种结果（四态验证，答辩演示的主舞台）：

上传任意文件
  ├─ 哈希命中 originalHash  → "原始文件"
  ├─ 哈希命中 signedHash    → "官方签名分发版"
  ├─ 都没命中，但文件里残留 C2PA 声明 → "签名后被篡改"（声明还在，内容已变）
  └─ 全部未命中              → "无记录"

另外合约加了 hashIndex（哈希→作品编号的反查表）：即使链下数据库被删了， 验证还能直接问链上合约，这就是"链上反查"——链下数据库降级为"加速缓存"。

闭环 3：授权（解决问题 3）——合约互相校验¶

一期：License 合约谁都能调用，"越权"是常态。 二期：LicenseV2 / RoyaltyV2 在构造函数里注入 IRegistry 接口，每次授权前先问 Registry：

grantLicense 的第一步：
  require(registry.authorOf(workId) == msg.sender, "not author")
  // 翻译：先问登记合约"这个作品的作者是谁"，如果不是调用者本人，直接拒绝

配合防抢注（同一哈希只能注册一次，重复注册直接 revert），形成一套"权限由合约强制"的机制。

闭环 4：信任（解决问题 5）——自建 CA 让 C2PA 从 untrusted 变 trusted¶

  • 一期用 c2patool 自带的开发证书签名，验证永远是 untrusted（不可信）——"签了但没人信"；
  • 二期用 openssl 自建了一套证书体系（Root CA → 叶子证书），把根证书配置为 c2patool 的信任锚；
  • 同一张签名图：信任列表外验证 = untrusted，信任列表内 = trusted。

这组对照实验（见 reports/test-results/c2pa-trust-comparison.md）直接演示了 C2PA 信任模型的工作原理，是答辩的一个亮点。

五、还需要知道的几个设计细节¶

部署顺序¶

RegistryV2 → LicenseV2(注入 registry) → RoyaltyV2(注入 registry) → MockJudicialAnchor

后两个合约依赖第一个的地址，所以部署有先后顺序（构造函数注入，immutable 存储）。

状态机（链下）¶

后端为每个作品维护一条状态链：

UPLOADED → SIGNED → PINNED → PENDING_ANCHOR → ANCHORED
                                      │ 超时没等到链上事件
                                      ▼
                                    STALE（对账重查）

关键变化："上链"不再是后端调合约，而是后端返回待签交易 → 前端钱包发交易 → 后端靠事件监听确认（这引出 docs/02 的"事件监听与对账"设计，本包 02 篇再展开）。

MockJudicialAnchor 是什么？¶

"司法锚定"= 把记录锚定到真实司法链。本项目不接真实司法链（需要机构备案，超出课题范围）， 但留了接口，并写了一个模拟实现（只发事件不做事），用来演示"未来怎么接"的调用形态。

EIP-712 元交易（展望）¶

二期主路径要求创作者钱包直接发交易（本地链 gas 免费，无门槛）。如果将来部署到真实网络， 用户需要持有 gas 代币才有门槛。设计文档（docs/05）提出了元交易方案：创作者只签名， 平台代付 gas，身份仍然真实。只设计不实现，作为论文展望章节的素材（本包 03 篇细讲）。
