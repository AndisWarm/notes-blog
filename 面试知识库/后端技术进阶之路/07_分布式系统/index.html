07 分布式系统¶

本章覆盖：分布式事务六方案对比、分库分表后主键生成、分库分表后分页查询、高可用架构设计。

1. 你知道哪些分布式事务？¶

一句话回答¶

六种主流方案：2PC、3PC、TCC、本地消息表、MQ 事务消息、Saga，按"一致性强度"和"业务侵入"选型：强一致用 2PC/TCC，最终一致用消息和 Saga。

展开讲¶

2PC（两阶段提交）： - 协调者先问所有参与者"能不能提交"（准备阶段，参与者锁定资源并写 undo/redo 日志），全部说能才发提交命令（提交阶段） - 缺点：同步阻塞（准备后参与者一直占着资源等指令）、协调者单点（协调者挂了大家都卡住）

3PC（三阶段提交）： - 在 2PC 基础上增加 CanCommit（先问"有没有能力"）和 PreCommit（预提交）阶段，引入超时机制，减少阻塞 - 仍无法彻底解决数据不一致，实际生产用得少

TCC（Try-Confirm-Cancel）： - 业务层拆三步：Try 预占资源（如预扣库存）→ Confirm 确认提交 → Cancel 回滚释放 - 优点：不锁数据库资源、性能好；缺点：业务侵入强（每个操作要写三个方法）、要处理幂等和空回滚（Try 没执行却被 Cancel）

本地消息表： - 业务事务内同时写业务表和消息表（同一个数据库事务），再异步投递 MQ，投递失败定时重发 - 优点：实现简单可靠；缺点：业务表和数据表耦合、消息表膨胀

MQ 事务消息（RocketMQ）： - 先发"半消息"（消费者不可见），本地事务成功后确认提交，MQ 才能投递；本地事务没结果时 MQ 反向回查 - 优点：业务无侵入、解耦；缺点：依赖 MQ 能力

Saga： - 把长事务拆成一串本地事务，每个配一个补偿操作；中途失败就逐个执行逆向补偿 - 优点：无锁、适合长流程；缺点：补偿逻辑要自己写、中间状态对外可见

对比表格¶

方案 一致性 业务侵入 性能 适用场景
2PC 强一致 低 差（阻塞） 少用，理论经典
3PC 弱于 2PC 低 一般 极少用
TCC 强一致 高 好 资金类、库存预占
本地消息表 最终一致 中 好 订单 + 通知类
MQ 事务消息 最终一致 低 好 跨服务解耦
Saga 最终一致 高（写补偿） 好 长流程、多步骤

比喻¶

2PC 像两个人约饭必须双方都确认才开席，一个人迟迟不回应全桌干等；Saga 像买一整套家具，缺一件就逐件退货，过程麻烦但不用占着整个商场。

2. 分库分表后主键怎么生成？¶

一句话回答¶

要求是"全局唯一 + 趋势递增"，主流方案是雪花算法和号段模式，UUID 只在不在乎顺序的场景用。

展开讲¶

雪花算法（Snowflake）： - 64 位长整型：1 位符号 + 41 位时间戳（毫秒级，够用约 69 年）+ 10 位机器 ID（5 位机房 + 5 位机器）+ 12 位序列号（同一毫秒内 4096 个） - 优点：无中心化（每台机器自己生成）、趋势递增（时间在前）、性能极高 - 缺点：时钟回拨问题（机器时间往回跳可能生成重复 ID，需要等待或拒绝）、机器号分配要管理

号段模式： - 数据库发号器一次申请一段号（如 1000 个），应用在内存里自增，用完再申请下一段 - 优点：数据库压力小（一次取 1000 个）、趋势递增、实现简单 - 缺点：号段用完瞬间集中请求数据库；重启会跳号（没用完的号段作废）；业界代表：美团 Leaf、滴滴 Tinyid

UUID 及其变体： - 本机生成、全球唯一、无需任何协调，最简单 - 缺点：无序（B+ 树索引随机插入频繁页分裂，性能差）、太长（36 字符占空间大） - 变体：UUID 转成数字存储；UUIDv7 把时间戳放前面，恢复"近似递增"

其他： Redis INCR（简单但有单点）、数据库自增 + 步长（如 1、3、5 号库各以 3 为步长）、百度 UidGenerator、美团 Leaf（号段 + 雪花融合）。

对比表格¶

方案 全局唯一 趋势递增 性能 主要问题
雪花算法 是 是 极高 时钟回拨
号段模式 是 是 高 号段用尽集中请求
UUID 是 否 高 无序、太长
Redis INCR 是 是 高 依赖 Redis 可用性

比喻¶

雪花像身份证号：前几位代表出生时间（时间戳），中间是地区编码（机器 ID），末尾是当天序号，全国唯一还能看出先后；号段像银行取号机：一次吐一叠号（比如 1000 个），领完再按一次。

3. 1 亿数据分库分表后分页查询怎么设计？¶

一句话回答¶

放弃"翻页跳数"的思路，用二次查询或游标（键集）分页，再从业务上禁止深翻页。

展开讲¶

难点： 数据散在多个库多张表，limit 深翻页（如第 100 万条）时，每个分片都要查"前 100 万条"再归并排序，数据量爆炸，越翻越慢。

方案一：跳数法（归并法） - 各分片查 offset + limit 条，应用层归并排序后取第 offset 到 offset+limit 条 - 浅分页（前几页）可用；深分页灾难——offset 每大一点，每个分片都要多查 offset 条

方案二：二次查询法 - 第一步：各分片各查 offset + limit 条（按排序字段），得到各片的最小值 - 第二步：取所有分片最小值中的最小值，用 between 在各分片做条件查询（排序字段 >= 全局最小值） - 第三步：归并排序后取第 offset 到 offset+limit 条 - 比跳数法少查大量数据，但只支持单排序字段，实现较复杂

方案三：游标分页（键集分页）——推荐 - 不翻页，只"向后取"：记住上一页最后一条的排序键（如 id = 10000），下一页用 where id > 10000 order by id limit 20 - 每个分片只查 20 条，稳定且快，数据量再大也不怕 - 局限：只能上一页/下一页顺序浏览，不能随机跳页；排序字段要唯一（一般用主键或联合唯一键）

业务规避： - 限制最大页数（搜索只给前 50 页）、禁止深翻页（提示"数据太多请用搜索"） - 滚动加载/下拉刷新替代页码翻页 - 复杂搜索排序交给 Elasticsearch 等搜索引擎

对比表格¶

方案 深分页性能 实现复杂度 局限
跳数法 差 低 深翻页数据量爆炸
二次查询 中 高 单排序字段
游标分页 好 中 不能随机跳页

比喻¶

像图书馆找书：页码式翻页要从第一本重新数起（跳数法），数一万次太累；游标像记住上次看到哪一本，下次从那里接着找，永远不用从头数。

4. 高可用架构设计¶

一句话回答¶

核心三件事：冗余（没有单点）、故障转移（坏了能自动换）、一致性协议（换了不错不乱），配合 CAP 权衡和 Raft 这类共识算法保证正确性。

展开讲¶

1. 冗余： 消除单点——数据库主从复制、服务多副本、多机房多可用区、消息队列集群。单点就是"一个人生病全家停摆"，冗余让每个角色都有替补。

2. 故障转移： 主节点挂了自动切换到从节点：数据库靠主从切换（VIP 漂移、MySQL 半同步）、注册中心靠选举、应用层靠健康检查摘除坏实例。要求切换快（秒级）、自动、无需人工。

3. 脑裂问题： 网络分区（机房之间断网）时，两边都以为自己是主，各自写数据，恢复后数据就乱了。解决靠两点： - 仲裁（Quorum）：只有获得多数派（超过一半）支持的节点才能当主，少数派自动降级 - Fencing（隔离）：旧主被"物理隔离"（如杀掉进程、吊销令牌），防止它继续写

4. CAP 理论： 一致性（C）、可用性（A）、分区容忍（P）三者只能选两个；分布式环境网络分区不可避免，所以 P 必选，实际是 CP 还是 AP 的取舍： - CP 系统：分区时牺牲可用性，保证数据不错（ZooKeeper、etcd、HBase） - AP 系统：分区时保证可用，数据最终一致（Eureka、Cassandra）

5. Raft 协议（共识算法）： - 节点分 Leader / Follower / Candidate，Leader 负责接收写请求，把日志复制到所有节点 - 只有多数派确认的日志才算提交成功；Leader 挂了，Follower 通过任期（term）+ 投票选出新 Leader - 天然解决脑裂：少数派不可能凑齐多数票，当选不了 Leader - 典型应用：etcd、Consul、ZooKeeper（类 Paxos 思路）

比喻¶

高可用像双引擎飞机：一个引擎坏了另一个自动顶上（冗余 + 故障转移）；但两台仪表不能各说各话（脑裂），必须由"多数仪表一致"的读数说了算（Raft 多数派），否则机长不知道该信谁。
