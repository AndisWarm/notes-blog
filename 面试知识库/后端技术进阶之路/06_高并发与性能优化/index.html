06 高并发与性能优化¶

本章覆盖：CPU 100% 排查、CPU 飙升原因、程序性能提升、1s 响应保障、三种语言 GC、缓存一致性、缓存模式选型、负载均衡算法、负载均衡分层、四层与七层、服务熔断、服务降级、熔断策略设计、服务隔离、监控推拉、数据迁移。

1. CPU 100% 问题怎么排查？¶

一句话回答¶

自上而下定位：先用 top 找到"哪个进程"，再用 top -H 找到"哪个线程"，最后用 jstack 等工具找到"哪行代码"。

展开讲¶

排查步骤（以 Java 为例）： 1. top：执行 top，按 P（大写）按 CPU 排序，找到 CPU 占用最高的进程，记下 PID 2. 找线程：top -Hp PID，同样按 CPU 排序，找到占用最高的线程 ID（十进制的 TID） 3. 转十六进制：printf "%x" TID 把线程 ID 转成十六进制（jstack 里显示的是十六进制） 4. 看线程栈：jstack PID > dump.txt，在 dump 里搜这个十六进制 ID，就能看到该线程正在执行的代码栈，定位到具体类和方法 5. 辅助判断：vmstat 1 看 us/sy 比例（用户态还是内核态占 CPU）；如果是 GC 问题，用 jstat -gcutil PID 看 GC 频率和停顿；加 -XX:+PrintGCDetails 看 GC 日志 6. 火焰图：Linux 下用 perf record 采样，或用 async-profiler 生成火焰图，图越宽的函数就是热点，一目了然

其他语言： Go 用 pprof（go tool pprof）；Python 用 py-spy dump 或 cProfile。

比喻¶

排查 CPU 高像查水表：先看哪栋楼（进程）用水最多，再看哪一户（线程）在狂用，最后进户查是哪个水龙头（代码行）没关紧。

2. 导致 CPU 飙升到 100% 的原因¶

一句话回答¶

本质是"某段代码在疯狂占用 CPU 或在疯狂制造额外开销"，常见有四类：死循环、频繁 GC、锁竞争、正则回溯。

展开讲¶

  • 死循环 / 空转：while(true) 里没有等待或退出条件，CPU 被空转占满，这是最常见的低级错误
  • GC 频繁：堆内存设置过小、存在内存泄漏、大对象频繁创建，导致 GC 线程几乎不停工作，GC 本身就是 CPU 密集操作
  • 锁竞争激烈：多线程抢同一把锁，线程不断自旋或反复阻塞唤醒，上下文切换开销巨大，CPU 的"搬运工"忙个不停
  • 正则灾难性回溯：复杂正则（如 (a+)+$ 这类嵌套量词）遇到超长字符串，回溯量呈指数级爆炸，一个请求就能打满 CPU
  • 其他：超大集合的循环计算、频繁序列化/加密、日志狂打、创建海量小对象等 CPU 密集操作

排查对照： 死循环用上节的 jstack 一眼就能看到；GC 问题看 GC 日志和堆内存（jstat、MAT 分析 dump）；正则问题用正则测试工具复现，改用非贪婪或原子组；锁问题看线程栈里大量 WAITING/BLOCKED 状态。

比喻¶

CPU 100% 像空调压缩机不停转：要么制冷需求真的大（业务确实繁忙），要么温控坏了（代码有 bug），排查就是找出是"需求大"还是"机器坏"。

3. 如何提高程序性能？¶

一句话回答¶

性能优化四板斧：算法（少算）、缓存（少查）、并发（并行干）、I/O（少等），再加代码层面的细节打磨。

展开讲¶

  • 算法与数据结构：把 O(n²) 的遍历改成哈希表/索引的 O(1) 查询，避免重复计算（记忆化），复杂度降一档往往比任何技巧都有效
  • 缓存：热点数据放 Redis 或本地缓存，空间换时间；注意缓存命中率、过期策略、一致性（见第 6 节）
  • 并发：无依赖的任务并行执行（多线程/协程）；但线程不是越多越好，锁竞争和上下文切换也有成本
  • I/O 优化：批量读写（一次拿 100 条而不是 100 次）、连接池复用连接、异步非阻塞（NIO/协程）、减少网络往返（合并请求）
  • 代码层面：避免频繁创建大对象、用 StringBuilder 拼字符串、懒加载、循环里提公共表达式、尽早 return
  • 数据库：加索引、优化慢 SQL、避免 SELECT *、必要时分库分表
  • 原则：先测量（profiling）再优化，别凭感觉；优化收益遵循二八法则，先打最大的头

比喻¶

像整理房间：把常用的东西放手边（缓存），一次多拿几件（批量 I/O），请几个人同时干（并发），而不是一趟一趟跑仓库。

4. 怎样确保系统 1s 内响应用户请求？¶

一句话回答¶

把 1s 拆成链路各环节的预算，逐段控制耗时，核心手段是 CDN、缓存、异步、并行、超时降级。

展开讲¶

  1. 先量化：用全链路追踪（SkyWalking、Pinpoint、Zipkin）和压测找出耗时大头，别盲目优化
  2. 拆预算：比如 1s = 网络 100ms + 网关 50ms + 业务计算 400ms + 数据库 250ms + 渲染 200ms，每段都有指标
  3. CDN：静态资源（图片、JS、CSS）放 CDN，就近节点返回，省去源站压力
  4. 缓存：读多写少的数据（商品详情、配置）走 Redis，命中率做到 90% 以上，数据库只扛 miss
  5. 数据库：索引、慢 SQL 治理、连接池，必要时读写分离
  6. 异步：非核心操作（短信、邮件、写日志、积分）丢消息队列异步处理，不占请求主链路
  7. 并行：多个无依赖的下游调用用 CompletableFuture 并发执行，5 个串行 200ms 变 1 个 200ms
  8. 超时与降级：下游慢就快速失败返回兜底，宁可秒回旧数据也不等 3 秒

比喻¶

像外卖承诺 1 小时送达：菜品提前备好（缓存）、骑手走最优路线（CDN）、爆单的店先不接单（降级）、排队超时就取消订单（超时），每一环都有时间表。

5. Java / Go / Python 的垃圾回收怎么工作？¶

一句话回答¶

GC 是自动回收不再使用内存的机制，三种语言思路不同：Java 分代 + 可达性分析，Go 并发三色标记，Python 引用计数为主。

展开讲¶

Java（JVM）： - 堆分新生代（Eden + 两个 Survivor）和老年代，对象先放新生代，熬过多次 Minor GC 晋升老年代 - 判定存活用可达性分析：从 GC Roots（栈上引用、静态变量等）出发，能到达的对象存活 - 新生代用复制算法，老年代用标记-整理；G1 收集器把堆分成多个 Region，按"回收收益"优先回收，可设定目标停顿时间

Go： - 用三色标记（白、灰、黑）+ 写屏障，标记过程与用户程序并发执行，STW（暂停）时间极短，通常毫秒级 - 内存按 mcache / mcentral / mheap 分层管理，小对象多；可用 GOGC 环境变量调节 GC 触发频率，用空间换时间

Python： - 引用计数为主：对象被引用的次数归零立刻回收，及时但无法处理循环引用 - 循环引用靠标记-清除 + 分代回收兜底（对象按存活时间分 0/½ 代，越老越少扫描）

对比表格¶

语言 判定方式 回收策略 停顿 调优要点
Java 可达性分析 分代 + 复制/标记整理 可控（G1 设目标停顿） 堆大小、GC 选型
Go 三色标记 + 写屏障 并发标记清除 极短（毫秒级） GOGC、内存分配
Python 引用计数 + 分代 计数归零即回收 无（计数法） 避免循环引用、少建大对象

比喻¶

Java 像定期大扫除，按房间新旧分区处理；Go 像商场一边营业一边偷偷扫地的保洁，几乎不影响顾客；Python 像垃圾桶上装了计数器，扔一个收一个，但两个桶互相指着对方就都收不掉，得定期人工检查。

6. 高并发场景下缓存一致性方案¶

一句话回答¶

没有银弹，业界主流是 Cache Aside 模式：读 miss 时查库回填，写时"先更新数据库、再删除缓存"，再用过期时间和延迟双删兜底，最终一致性。

展开讲¶

为什么"删缓存"而不是"更新缓存"： - 更新缓存存在并发写覆盖问题（两个线程先后写库，缓存里可能留下旧值） - 缓存里存的不一定是数据库原样（可能有加工后的中间态），删掉让下次读时重建更安全

为什么"先更新库、后删缓存"而不是反过来： - 先删缓存再更新库，更新库的窗口期大量请求 miss，全部打到数据库，压力大 - 先更新库再删缓存，只有删缓存失败这一个风险点，可控

删缓存失败怎么办： - 重试：删除失败进消息队列，异步重删 - 延迟双删：更新库后，延迟几百毫秒（如 500ms，覆盖"旧值被读回填"的窗口）再删一次缓存 - 过期时间兜底：缓存都设 TTL，即使漏删，最多不一致一个 TTL

其他模式： Read/Write Through（缓存组件代理读写，应用不直接碰库）、Write Behind（先写缓存异步落库，吞吐高但可能丢数据），实现复杂，用得少。

比喻¶

像黑板和账本：改账本（数据库）时把黑板（缓存）上的旧内容擦掉，下一个人要查再重新抄一遍；万一擦漏了，黑板上的粉笔字也会自己淡掉（TTL 过期）。

7. 项目中采用哪种缓存模式解决数据一致性？¶

一句话回答¶

按业务对一致性的要求选：读多写少、可容忍短暂不一致就用 Cache Aside + 删除缓存 + 过期兜底；强一致场景干脆不缓存或只做短 TTL 加速。

展开讲¶

结合业务举例： - 商品详情：读多写少，改价/改库存时"更新库 + 删缓存"，加延迟双删防旧值回填，TTL 设 10 分钟兜底，可容忍秒级不一致 - 订单状态：强一致场景，直接查库不缓存；若为了抗压非要缓存，TTL 设极短（几秒），且只做读加速，不参与写流程 - 计数类（点赞数、评论数）：可容忍分钟级延迟，缓存 + 短 TTL，甚至可以异步批量回写库 - 配置类：缓存 + 发布时主动刷新（写库后同步删缓存），一致性要求较高但冲突少，实现简单

选择逻辑： - 写频繁且一致性要求高 → 不缓存 - 可容忍秒级不一致 → 删缓存 + 短 TTL - 要最终一致 → 删缓存失败进 MQ 重试 + 定时对账任务扫描修复

比喻¶

像图书馆：热门书放前台复印本（缓存），原书改版重印（更新库）后把前台旧复印本扔掉，借阅记录这种关键信息直接查总馆档案（库），不经过前台。

8. 负载均衡算法背诵¶

一句话回答¶

六种经典算法：轮询、加权轮询、随机、哈希、最少连接、一致性哈希，各自解决不同场景的问题。

展开讲¶

算法 原理 优点 缺点 / 适用
轮询 请求轮流分给每台服务器 实现简单、绝对均匀 不感知机器性能差异；适合配置相同的机器
加权轮询 按权重比例分配（如 3:1） 适配异构机器 权重靠人工拍
随机 随机选一台 简单，长期看接近均匀 短时间可能扎堆；适合无状态服务
哈希（IP Hash） 按客户端 IP 哈希到固定机器 同一来源固定落点，利于会话保持 机器增删导致大量重映射
最少连接 分给当前活跃连接最少的机器 能感知实时负载 要维护连接数状态；适合长连接、耗时不均
一致性哈希 节点映射到哈希环，加虚拟节点 增删节点只影响环上少量 key 实现较复杂；适合缓存分片

比喻¶

像食堂打饭：轮询是一个一个叫号；加权是给菜多的窗口多派几个打饭师傅；最少连接是哪个窗口排队人少去哪；一致性哈希是给常客固定座位，新同学加入只影响邻座的安排。

9. 系统负载均衡怎么做？¶

一句话回答¶

从用户到服务器层层做：DNS（地域级）→ 硬件 F5 或 LVS（流量入口）→ Nginx（精细化路由）→ 应用内客户端负载均衡，各层各管一段。

展开讲¶

四层分工： 1. DNS 层：一个域名解析出多个机房 IP，按地域返回最近的节点（全局负载均衡）；缺点：DNS 缓存生效慢，故障切换不及时 2. 接入层：LVS（Linux 虚拟服务器，四层，DR 模式，单机可扛百万级并发）负责大流量转发；大厂入口常用，转发快但不懂业务 3. 反向代理层：Nginx（七层）按 URL、Header、Cookie 精细化路由，还能做缓存、限流、HTTPS 卸载，是应用真正的"门卫" 4. 应用层：服务内部再基于注册中心做客户端负载均衡（如 Spring Cloud LoadBalancer），服务间互相调用自己选节点

硬件 F5：专业负载均衡设备，性能强、稳定、功能全（四层七层都支持），但贵，一般只有金融、大型门户才上。

为什么分层： DNS 管"去哪个城市"，LVS 管"进哪个机房"，Nginx 管"找哪个服务"，应用层管"找哪台实例"，每一层解决不同粒度的分发问题，还互为兜底。

比喻¶

像物流分拣：先按城市分（DNS），再按区域转运中心分（LVS），再按具体小区派送（Nginx），最后快递员（应用）自己挑最顺路的楼栋。

10. 七层和四层负载均衡区别¶

一句话回答¶

四层只看"包裹送到哪"（IP + 端口），七层会拆开看"包裹里是什么"（URL、Header 内容），前者快、后者聪明。

展开讲¶

四层（L4，传输层）： - 基于 IP + 端口做转发，只修改目标地址，不解析应用内容（最多看 TCP 头） - 性能极高、延迟低，转发透明，适合 TCP/UDP 大流量（游戏、长连接、数据库代理） - 代表：LVS、F5（四层模式）、Nginx stream 模块

七层（L7，应用层）： - 解析 HTTP 报文，按 URL 路径、域名、Cookie、Header 路由，例如 /api 走 A 服务、/static 走 CDN - 能做内容过滤、缓存、限流、压缩、HTTPS 卸载 - 性能开销大（要拆包解析），单机吞吐低于四层 - 代表：Nginx、HAProxy、F5（七层模式）

对比表格¶

维度 四层 L4 七层 L7
工作层 传输层（TCP/UDP） 应用层（HTTP 等）
转发依据 IP + 端口 URL / Header / Cookie 内容
性能 高 较低（要解析报文）
功能 单一转发 路由、缓存、限流、HTTPS 卸载
适用 大流量、长连接、非 HTTP 协议 HTTP 服务、精细化路由

比喻¶

四层像快递分拣只看面单上的地址；七层像安检拆开包裹检查内容，再决定送哪——检查得越细，速度就越慢。

11. 服务熔断是什么？¶

一句话回答¶

像电路保险丝：下游故障率超过阈值就主动切断对该下游的调用，快速失败返回兜底，防止故障像雪崩一样蔓延到整个系统。

展开讲¶

三状态状态机： - 关闭（Closed）：正常放行请求，同时用滑动窗口统计失败率 - 打开（Open）：失败率超过阈值（如 10 秒窗口内失败率 > 50% 且请求数 > 20），熔断器打开，所有请求直接拒绝走降级逻辑，不再打到下游 - 半开（Half-Open）：打开后经过休眠窗口（如 5 秒），放行少量探测请求试水；成功则恢复关闭，失败则重新打开

代表框架： - Hystrix（Netflix）：最早普及熔断概念，三态 + 滑动窗口统计 + 线程池/信号量隔离 + fallback，功能完整但已停止维护 - Sentinel（阿里）：熔断 + 限流 + 热点防护一体，支持控制台动态下发规则，错误率/慢调用比例/异常数三种熔断策略

为什么重要： 微服务调用链中一个服务变慢，会拖垮所有调用方线程，形成级联雪崩；熔断把故障"隔离在源头"。

比喻¶

像家里的保险丝：电器短路就跳闸保护全屋电路，过一会儿推一次开关试试（半开），能正常用就合闸恢复，还短路就再跳。

12. 服务降级方案设计¶

一句话回答¶

保核心、弃非核心：系统扛不住时主动砍掉次要功能或返回兜底数据，保证主流程（下单、支付）始终可用。

展开讲¶

降级分级（按业务重要性）： - 一级（核心）：支付、下单、登录——绝不降级，资源优先保障 - 二级（重要）：推荐、评论、搜索——可降为返回缓存数据或默认结果 - 三级（可弃）：积分、日志、非核心展示位——直接关闭

降级手段： - 返回兜底数据：接口降级返回缓存旧数据、默认列表、静态页 - 异步化：非核心操作从同步改异步，不做就跳过 - 关闭依赖：不再调用第三方/非核心服务（如风控、画像） - 快速失败：设置短超时，超时就返回降级结果

触发方式： - 人工开关：运维在配置中心手动降级（最可控，大促前预案） - 自动触发：监控到错误率、RT 超阈值自动降级 - 与熔断配合：熔断是"下游故障自动触发降级"，降级是更广的兜底手段

比喻¶

像餐厅爆满：招牌菜保证做（核心功能），赠品小菜、花式摆盘砍掉（非核心），实在忙不过来就限量供应或让顾客打包（兜底方案），客人不至于饿着。

13. 高并发下好的熔断策略设计¶

一句话回答¶

核心是"滑动窗口统计 + 多维度阈值 + 按粒度熔断 + 快速失败 + 自动恢复"，避免误伤也避免漏判。

展开讲¶

  • 滑动窗口统计：把 10 秒窗口切成 10 个 1 秒桶，滚动统计请求数、失败数、平均 RT。比固定窗口平滑，不会因为前一秒的毛刺误触发，也能及时反映最新状态
  • 多维度阈值组合：不要只看失败率——失败率 > 50% 且请求量 > 20（防冷启动时 1/1 就误判）、平均 RT > 1 秒、慢调用比例、异常数，多个条件综合判断
  • 按粒度熔断：按接口、按依赖服务、按实例维度分别熔断，一个接口挂了别连累整个服务
  • 超时先行：每个下游调用必须有超时（如 200ms），超时快速失败，这是熔断的前置条件
  • 恢复策略：半开状态放行比例流量（如 10%），连续成功超过阈值（如 5 个）才恢复关闭；失败则重新打开
  • 与重试区分：熔断打开期间禁止重试（会放大流量），恢复探测期才允许小流量试探
  • 告警与人工干预：熔断触发要告警，支持人工强开/强关

比喻¶

像智能红绿灯：平时绿灯通行并统计事故率（滑动窗口），事故率超标亮红灯（打开），过一会儿黄灯放几辆车试试（半开），安全了再恢复绿灯；统计的是最近一段时间而不是"开灯以来"的数据。

14. 十倍流量冲击下服务隔离怎么做？¶

一句话回答¶

用舱壁模式（Bulkhead）：把流量和故障关进各自的"船舱"，线程池隔离、信号量隔离、集群隔离三层配合，一个舱进水不影响整艘船。

展开讲¶

  • 线程池隔离：每个下游依赖/每类接口分配独立线程池（Hystrix 默认方式）。A 服务把线程池耗尽，只影响调用 A 的请求，调用 B 的请求照常走自己的池子
  • 信号量隔离：更轻量，不建线程，只限制并发调用数，超了就快速失败。适合延迟低、耗时短的调用；实现简单、开销小
  • 对比表格：
维度 线程池隔离 信号量隔离
资源 独占线程池 只计数，不占线程
隔离强度 强（线程也隔离） 弱（只限并发数）
开销 大（线程切换） 小
适用 耗时不稳定、慢调用 低延迟、快速调用
  • 集群隔离：核心服务（支付、订单）独立部署集群、独立配额，非核心服务抢不到核心的资源；还可以按用户分级隔离（VIP 用户专属集群）
  • 其他配合：熔断（下游坏了快速切断）、限流（入口控量）、队列削峰（异步缓冲）、超时控制（防止线程被慢请求占死）
  • 隔离的目标：把"一个接口变慢/一个下游故障"的影响半径，从整个服务缩小到一个舱

比喻¶

像邮轮的水密隔舱：一个舱进水只淹一个舱，船还能继续开；如果所有舱连通，一个洞就沉船。隔离就是花钱买"影响半径"的缩小。

15. 监控数据推还是拉？¶

一句话回答¶

主流是拉（Pull）：监控系统主动来"抄表"（如 Prometheus 定时抓 /metrics）；推（Push）只在批处理、短任务等拉不到的场景用。

展开讲¶

Pull（拉取）模式（Prometheus 为代表）： - 被监控对象暴露 HTTP 接口（/metrics），Prometheus 每隔 15 秒主动抓取 - 优点：目标不需要知道监控系统在哪；配合服务发现自动发现新实例；拉取失败 = 目标挂了，天然是健康检查；多套监控系统可以共享同一数据源 - 数据按"指标名 + 标签"组织成时序数据，存进时序数据库（TSDB），按时间戳追加写入，适合趋势分析

Push（推送）模式： - 目标主动把数据上报给监控中心（如 Graphite、Zabbix agent） - 优点：适合批处理、短生命周期任务（跑完就没了，拉不到）；适合防火墙后监控系统访问不到的场景 - 缺点：监控方无法感知目标消失（没推送可能是挂了也可能是没活干）；突发流量可能把监控中心打爆

业界实践： Prometheus 为主（Pull + 服务发现 + Alertmanager 告警），短任务用 Pushgateway 转一道，再由 Prometheus 去拉。

对比表格¶

维度 Pull 拉 Push 推
方向 监控系统主动抓 目标主动上报
发现故障 抓不到就是挂了 无消息难判断
适用 常驻服务、k8s 集群 短任务、批处理
压力 可控（抓取频率可控） 可能被目标打爆

比喻¶

Pull 像老师点名，没答到的就知道缺席了；Push 像学生主动交作业，没交的可能是忘了也可能是病了，老师还得挨个去问。

16. 旧库数据平滑迁移到新库¶

一句话回答¶

四步走：双写（新旧库同时写）→ 校验（对账）→ 灰度（流量逐步切）→ 回滚预案，全程可回退，最后才彻底切完。

展开讲¶

  1. 全量 + 增量同步：先把旧库历史数据全量导入新库，再开启增量同步（binlog 订阅/数据同步工具）追平
  2. 双写：应用层同时写旧库和新库（同步写或写 MQ 异步落新库），此时读流量还在旧库，新库只进不出，双写期间是"影子模式"，风险最低
  3. 校验：对账任务对比新旧库：数量一致、抽样字段 hash 比对（如订单号 + 金额 + 状态），不一致的告警并用增量同步重放修复
  4. 灰度切换：读流量先切 5% 到新库 → 观察监控（错误率、延迟）→ 20%、50% → 100%；每步停留观察，发现问题立即回滚（把流量切回旧库）
  5. 写流量最后切：读全部切完后，再把写切到新库，旧库转为只读备份；观察一段时间（如一周）无异常才停掉双写
  6. 回滚方案：双写开关保留，出问题一键切回；新库数据不回退，靠重放修复

注意： 迁移窗口内不做大的结构变更；切换要选低峰期；双写代码要保证新旧库写入失败不影响主流程（新库失败只告警不阻塞）。

比喻¶

像搬家：先在老房子和新房子各放一份东西（双写），对照清单核对（校验），先搬几箱试住一晚（灰度），发现不对还能搬回去（回滚），确认没问题才把家当全搬完。
