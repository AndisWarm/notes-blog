02 数据库与存储¶

本章覆盖：MySQL 架构与一条 SQL 的执行全过程、Redis 是什么与单线程架构、Redis 除缓存外的七大应用场景、ES 倒排索引原理、为什么需要 MongoDB（文档模型与分片复制集）、HDFS 架构（NameNode/DataNode 与副本机制）。

1. MySQL 的架构是怎么样的？¶

一句话回答¶

MySQL 分 Server 层（连接管理、SQL 解析、优化、执行）和存储引擎层（真正落盘读写数据），一条 SQL 从发出到返回要经过：连接器 → 查询缓存（8.0 已删除）→ 解析器 → 优化器 → 执行器 → 存储引擎。

展开讲¶

先记分层：MySQL 像一台电脑——Server 层是主板（接口固定，负责接待请求），存储引擎层是显卡（实现可换，负责真正干活）。SHOW ENGINES 能看到所有可用的"显卡型号"，InnoDB、MyISAM、Memory 都是插件，可以按表选择。

一条 SQL 的完整旅程（背下来）：

  1. 连接器：和客户端建立 TCP 连接，验证账号密码，校验权限。注意：这里只验证"你是谁"，不验证"你能动哪张表"。
  2. 查询缓存：老版本把 SELECT 结果以 SQL 文本为 key 缓存，表一更新全部失效，命中率极低，MySQL 8.0 直接删掉了这个模块，面试要主动说"8.0 已删除"。
  3. 解析器：词法分析把 SQL 拆成 token（关键字、表名、列名），语法分析生成语法树，语法错误在这里报。
  4. 优化器：决定"怎么查最快"——选哪个索引、多表 JOIN 先连哪张、子查询怎么改写，生成执行计划。优化器选错索引是慢查询的常见原因。
  5. 执行器：先做权限校验（对具体表的权限在这里查），再按执行计划逐行调用存储引擎接口。
  6. 存储引擎：真正干活——读磁盘数据页、改 B+ 树、写 redo/undo log、加锁、提交事务。

Server 层 vs 存储引擎层：连接管理、解析、优化、binlog、查询缓存属于 Server 层，与引擎无关；索引结构（B+ 树）、事务、锁、redo/undo log 属于引擎层，每个引擎实现不同。所以同一个库里可以混用不同引擎的表（不推荐）。

面试加分细节：权限校验发生在执行器而不是连接器；连接建立后权限就固定了，中途改权限要重连才生效。

比喻¶

整条链路像餐厅点餐：连接器是门口迎宾（验身份）→ 解析器是服务员听懂你点啥（把话拆成菜品）→ 优化器是厨师长决定先做哪个菜（选最快路线）→ 执行器是传菜员核对菜单（查权限）→ 存储引擎是后厨真正把菜做出来（读写磁盘）。

2. Redis 是什么？架构是怎么样的？¶

一句话回答¶

Redis 是一个基于内存的键值数据库，采用单线程处理命令 + I/O 多路复用的架构，速度快到单机 QPS 能破 10 万，底层提供 String、Hash、List、Set、Zset 五种基本类型和 BitMap、HyperLogLog、GEO、Stream 四种进阶类型。

展开讲¶

为什么快（三个原因）： - 内存 vs 磁盘：Redis 读内存（纳秒级），MySQL 读磁盘（毫秒级），差几个数量级； - 数据结构简单：键值对 + 哈希表查询 O(1)，MySQL 的 B+ 树是 O(logN)； - 单线程免竞争：命令一个个顺序执行，没有锁竞争、没有线程切换开销，也不会死锁。

单线程模型要讲准确：Redis 的网络 IO 和命令执行是单线程的（一条命令执行完才执行下一条，所以单条命令天然原子），但持久化、过期键删除、AOF 重写等重活是后台线程/子进程干的，别把"单线程"理解成整个进程只有一个线程。

五种基本类型（面试必背）：

类型 长什么样 典型场景
String key 对应一个字符串/数字 缓存对象、计数器、分布式锁、共享 Session
Hash key 对应一个小字典（field-value） 缓存对象字段、购物车
List 有序列表，两头可插 简单消息队列（有局限）
Set 无序不重复集合 点赞、共同关注、抽奖（交并差运算）
Zset 有序不重复集合，元素带分数 排行榜、延迟队列、按分数范围查询

进阶类型记三个对应：BitMap 对应签到（一个 bit 存一个人）、HyperLogLog 对应 UV 统计（百万级去重计数，误差约 0.81% 但极省内存）、Stream 对应消息队列（自动生成消息 ID、支持消费组，弥补 List 的不足）。

比喻¶

MySQL 像仓库（东西全但找东西慢），Redis 像柜台货架（只放热门商品，伸手就拿）。用户来了先看货架，货架没有才去仓库翻，这就是缓存。

3. Redis 除了用作缓存还能干嘛？¶

一句话回答¶

Redis 因为"内存快 + 数据结构丰富 + 命令原子"，还能做分布式锁、排行榜、计数器、消息队列、限流、Session 共享、布隆过滤器等七大场景。

展开讲¶

  1. 分布式锁：多台机器抢同一把锁，用 SET key value NX PX 30000——NX 保证只有 key 不存在时才设置成功（谁先抢到算谁的），PX 设过期时间防止拿锁后进程挂掉造成死锁。解锁要先判断是不是自己的锁再删除，两步要用 Lua 脚本保证原子。更可靠的方案是 RedLock（多数节点加锁成功才算拿到锁）。
  2. 排行榜：Zset 天然按分数排序。ZADD 写入分数 → ZINCRBY 点赞加分 → ZREVRANGE 取 TOP N → ZRANGEBYSCORE 按分数段筛选，全部实时完成，不用查数据库排序。
  3. 计数器：INCR 是单线程下的原子操作，适合点赞数、访问量、库存扣减，高并发下不会加错。
  4. 消息队列：两种方式——Pub/Sub 发布订阅（简单、发布者和订阅者解耦，但不支持持久化，没人在线消息就丢了）；List 的 LPUSH + BLPOP 阻塞队列（能 FIFO，但消息确认、重试要自己实现）。要可靠的消息队列还是用 Kafka/RabbitMQ，Redis 只做轻量场景。
  5. 限流：固定窗口用 INCR + 过期时间统计单位时间请求数，超过阈值拒绝；滑动窗口可以用 Zset 记录每个请求的时间戳，ZCOUNT 统计窗口内请求数。或者用 Lua 脚本实现令牌桶。
  6. Session 共享：登录态存 Redis（key 是 sessionId，value 是用户信息），多台应用服务器共享同一份 Session，用户请求打到任何一台机器都能认出他。比本地 Session（只存在一台机器内存里）强。
  7. 布隆过滤器：一个 bit 数组 + 多个哈希函数，判断"一个 key 肯定不存在"（存在误判可能：可能把不存在的判成存在，但绝不会把存在的判成不存在）。用在缓存穿透防护——先把合法 key 全放进去，查询前先过过滤器，不存在的 key 直接挡在外面，不压垮数据库。

比喻¶

Redis 像一个多功能的社区服务站：不仅能放货架（缓存），还能当签到打卡表（BitMap）、投票记分牌（Zset 排行榜）、取号机（限流计数）、公告栏（Pub/Sub）、看门大爷（布隆过滤器挡陌生人）。

4. ES 的倒排索引说一下？¶

一句话回答¶

倒排索引是以词为单位、反过来记录"哪个词出现在哪些文档里"的索引结构，配合分词，让 Elasticsearch 能做到毫秒级全文搜索；而 MySQL 的 LIKE 是全表扫描，数据量一大就慢。

展开讲¶

先分清正排和倒排：

正排索引 倒排索引
组织方式 以文档为主：文档 → 包含的词 以词为主：词 → 出现在哪些文档
查询"哪些文档含某词" 要扫所有文档 直接查词，O(1) 定位
典型代表 MySQL 的 LIKE、关系型数据库 Elasticsearch、搜索引擎

建索引的流程（三个步骤）： 1. 分词：文档进来先被分析器拆成一个个词元（term）。中文用分词器按词典拆，英文按空格和标点拆，还会做小写化、去停用词（的、了、a、the）。 2. 建词典：把所有不重复的词收集起来，就是词典（term dictionary），通常按字母/拼音排序，方便二分查找。 3. 建倒排列表：每个词后面挂一个列表，记录"这个词出现在哪些文档 ID 里、出现在哪些位置、出现了几次"。查询时先查词典定位词，再拿倒排列表直接返回文档列表。

为什么搜索快：查"手机"这个词，不用遍历所有文章，直接去词典里找到"手机"，拿它后面的文档列表就完事，复杂度接近 O(1)。分词粒度决定搜索质量——搜"小米手机"，分词成"小米""手机"两个词，两个词的文档列表取交集就是结果。

和 MySQL LIKE 对比：SELECT * FROM article WHERE content LIKE '%手机%' 开头是通配符，索引直接失效，只能全表逐行扫描，百万行就是百万次字符串匹配；ES 的倒排索引是按词定位，快几个数量级。MySQL 的全文索引（InnoDB 8.0 起）本质也是倒排索引，但分词、相关性打分、分布式能力远不如 ES。

面试可以补一句：ES 单机扛不住时靠分片（每个分片是独立的 Lucene 索引，倒排索引分散在多个分片上）和副本（分片的备份）横向扩展。

比喻¶

正排索引像图书馆按书排列的书架：找哪本书里提到"手机"，得一本本翻；倒排索引像按词条整理的索引卡：每个词一张卡，卡片上写着"哪几本书、第几页提到过这个词"，查词直接抽卡片，秒出答案。

5. 有 MySQL 为什么还要 MongoDB？¶

一句话回答¶

因为 MySQL 是"先定表结构再存数据"的关系型数据库，面对结构多变、嵌套很深、写入量大的数据（日志、商品信息、IoT 数据、评论）非常别扭；MongoDB 用类 JSON 的文档模型、无固定 Schema，存这类数据又快又灵活，还能天然水平扩展。

展开讲¶

MongoDB 是什么：面向文档的 NoSQL 数据库。数据库 → 集合（类似表）→ 文档（类似行）。文档用 BSON（二进制 JSON）存储，支持嵌套对象和数组，一条商品文档可以直接把规格、图片、评论全部嵌进去，不用像 MySQL 那样拆成四五张表再 JOIN。

核心特性： - 无 Schema（模式自由）：同一集合里的文档字段可以不一样，加字段不用 ALTER TABLE，上线不用迁移。 - 文档模型：读写的是完整的 JSON 对象，天然贴合程序里的对象（Java/Python 的类直接映射），免去 ORM 映射的麻烦。 - 分布式架构：副本集（一个主节点处理写、多个从节点同步数据、主挂了自动选举新的）保证高可用；分片集群（按分片键把数据水平切成多片，分散到多个机器）支撑海量数据。 - 索引：支持单字段、复合、TTL（自动过期）、地理空间索引（附近的商家）。

和 MySQL 的对比（面试核心）：

对比项 MySQL MongoDB
数据模型 表 + 行 + 列，需先定 Schema 集合 + 文档（JSON/BSON），无固定 Schema
关联查询 JOIN 多表 靠嵌套文档，关联能力弱
事务 强 ACID，成熟 4.0 起支持多文档事务，但生态不如 MySQL
灵活性 加字段要 ALTER TABLE 直接存，结构随意变
扩展方式 主从、分库分表（较繁琐） 分片集群，天生水平扩展
典型场景 钱、订单、报表等强一致数据 日志、商品、内容、IoT、埋点等结构多变数据

怎么选：需要强事务、复杂报表、数据高度关联 → MySQL；数据是"一个完整的对象"、字段经常变、写入并发大、要水平扩展 → MongoDB。实际项目经常混用：MySQL 存订单资金，MongoDB 存商品和用户行为数据。

比喻¶

MySQL 像印好的表格：每一行必须填固定的格子，想加一列得重新印表；MongoDB 像自由格式的便签：想写什么写什么，可以贴图、可以嵌套，找起来按标签分类。存"规整的账本"用表格，存"五花八门的随手记"用便签。

6. 海量数据怎么存？HDFS 是什么？架构是怎么样的？¶

一句话回答¶

数据量到了 PB 级、单台机器装不下时，HDFS（Hadoop 分布式文件系统）把大文件切块存到一群普通服务器上，每块存多份副本，用"一个管目录的 + 一群存数据的"架构实现海量存储和高容错。

展开讲¶

核心思想：先把大文件切块（默认 128MB 一块，块是存储的基本单位），再把块分散存到多台 DataNode 上，每块默认存 3 个副本（放在不同机器、甚至不同机架），某台机器坏了数据也不丢。

三大角色： - NameNode（管目录的）：只存元数据——文件目录树、每个文件分成哪些块、每块在哪些 DataNode 上。不存实际数据。它是整个集群的"大脑"，挂了集群就瘫了，所以有 Secondary NameNode 定期合并日志做备份。 - DataNode（存数据的）：真正存数据块，周期性地给 NameNode 发心跳（报告"我活着、我有哪些块"）。心跳断了就判定节点挂了，NameNode 会安排其他节点把丢失的块补够副本数。 - Client（用户）：读写请求的发起者。

写入流程（面试常考）：客户端请求 NameNode 创建文件 → NameNode 返回该写哪些 DataNode → 客户端把数据流水线式传给第一个 DataNode（比如 A），A 边收边转给 B，B 再转给 C（副本级联复制）→ 全部写完返回确认 → 告诉 NameNode"写完了"。好处是副本复制不用客户端重复传三遍，坏处是只要一个节点慢，整条流水线就慢。

特性总结：写一次读多次（追加写，不适合频繁修改）、流式访问（适合批处理，不适合低延迟随机读）、适合大文件（块大、文件小反而浪费）、通过副本保证高容错、用普通服务器就能搭（成本低）。

适用场景：离线数仓的底座（Hive 的数据就存在 HDFS 上）、日志归档、机器学习训练数据的存储。不适用：低延迟查询（毫秒级响应请用 HBase 或数据库）、大量小文件（NameNode 内存装不下元数据）、频繁修改（HDFS 只支持追加）。

和海量数据链路串起来：海量数据 → HDFS 存着 → Spark/MapReduce 算 → Hive 查。HDFS 负责"装得下、不丢"，计算引擎负责"算得快"。

比喻¶

HDFS 像图书馆的仓储系统：NameNode 是总目录卡片柜（只记"哪本书在哪个书架的哪个位置"，不存书本身），DataNode 是书架（真正放书），每本书复印三份放在不同分馆（副本），一间分馆着火，另外两间还有。管理员（NameNode）挂了，全馆就找不到书了。
