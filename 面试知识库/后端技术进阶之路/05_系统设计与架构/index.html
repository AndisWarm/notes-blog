05 系统设计与架构¶

本章覆盖：电商秒杀架构、高并发强一致订单系统、高可用评论系统、直播评论（弹幕）系统、点赞系统、亿级用户排行榜、百万 QPS 限流器、十亿级 URL 短链系统、分布式 ID、密码存储、单点登录 SSO、安全对外 API、百万用户架构设计、用户规模放大 100 倍、三高（高可用/高吞吐/高扩展）设计。

1. 电商秒杀架构：如何支撑百万级并发请求？¶

一句话回答¶

秒杀的核心矛盾是「瞬时流量极大、真正能买到的人极少」，所以思路是层层拦截、把流量挡在离数据库最远的地方：前端限流 + CDN 静态化挡掉大部分请求，Redis 预减库存挡住数据库压力，MQ 削峰把同步下单变成异步下单，最后数据库用乐观锁兜底防超卖。

展开讲¶

第一层：前端限流和静态化 - 秒杀页面的 HTML、图片、CSS、JS 全部放到 CDN，用户打开页面根本不打后端服务器 - 秒杀按钮置灰（未开始不可点）、点击后立刻置灰并提示"排队中"，防止同一用户疯狂点击 - 加入验证码或滑块，把真人从机器脚本里筛出来，同时拖慢请求速度 - 网关层（Nginx）按 IP、按用户 ID 做限流，超出的直接返回"已抢完"

第二层：Redis 预减库存 - 活动开始前把商品库存预热进 Redis（一个 key 存剩余库存） - 用户请求进来先用 Redis 扣减库存，扣减用 Lua 脚本保证原子性（判断库存 > 0 再减，一步完成） - Redis 单线程执行命令，天然不会出现两个请求同时读到同一个库存值的问题 - 扣减成功才继续走下单流程，失败直接返回"手慢了"，数据库根本不会被打到

第三层：MQ 削峰 - 库存扣减成功后，不是直接写数据库下单，而是发一条消息到 MQ 就返回"排队中" - 订单服务从 MQ 里慢慢消费消息，异步创建订单，把瞬间百万级的流量摊平成每秒几千的平稳流量 - 用户端通过轮询接口或 WebSocket 接收最终结果（成功/失败）

第四层：数据库扣库存（防超卖）

方案 原理 优点 缺点
数据库行锁（悲观锁） SELECT ... FOR UPDATE 锁住库存行再扣减 绝对不会超卖 大量线程排队等锁，吞吐极低
乐观锁 UPDATE stock SET num = num - 1 WHERE num > 0 或带版本号更新 无锁、性能好、扣减条件保证不超卖 更新失败（影响行数为 0）需要重试或放弃
Redis 预扣 + 数据库兜底 Redis 先扣，异步同步到数据库 扛得住高并发 需要处理 Redis 与 DB 的数据一致性
异步扣减（MQ + 乐观锁） 消息队列消费时用乐观 SQL 扣减 平滑、可靠 用户感知有延迟

实际生产普遍是「Redis 预扣 + MQ 异步下单 + 数据库乐观锁兜底」的组合拳，再加唯一索引（如 user_id + 活动_id）防止同一用户重复下单。

其他细节：库存同步要处理 Redis 和数据库不一致（如用户下单后未支付超时释放库存）；秒杀结果要支持查询（用户轮询订单状态）；整个链路要有监控和降级开关，Redis 挂了要能降级到直接拒绝（秒杀宁可少卖不可超卖）。

比喻¶

秒杀就像春运抢火车票：12306 不会让所有人都挤进售票窗口（数据库），而是先在网上排队取号（Redis 预减）、分批放行（MQ 削峰）、窗口按号办理（异步下单）。大部分人取号时就被告知"没票了"，真正冲到窗口的人很少，窗口永远不挤。

2. 高并发强一致的电商订单系统怎么设计？¶

一句话回答¶

核心手段是状态机管订单流转、分布式事务保一致性、异步化扛并发、发号器生成唯一订单号：下单链路拆成"创建订单 → 扣库存 → 扣款 → 发券"等多个步骤，用状态机约束状态只能按合法路径流转，用事务消息或补偿保证各步骤最终一致，高流量环节全部异步化。

展开讲¶

订单状态机 - 订单状态不能随便跳，必须按预先定义的合法路径流转：待支付 → 已支付 → 已发货 → 已完成，以及 待支付 → 已取消、已支付 → 退款中 → 已退款 等 - 每个状态变更记录一条状态流水（谁、什么时候、从哪到哪、原因），方便对账和排查 - 状态变更用数据库 UPDATE 带条件（WHERE status = '待支付'）防止并发下状态错乱

分布式事务 - 一个下单操作涉及订单库、库存服务、支付服务、营销服务，跨服务跨库无法用单机事务 - 强一致方案：两阶段提交（2PC），性能差，电商极少用 - 主流方案是最终一致：本地消息表 + 消息队列（事务消息），先本地写订单 + 发消息，下游消费后回执，失败则重试 + 定时对账补偿 - 比如"扣库存 + 创建订单"：订单先置为"待确认"，库存扣减成功后才置为"已支付"，失败则自动取消并回滚

异步化 - 支付回调、扣库存这些耗时操作全部异步：用户点"提交订单"立刻返回"下单成功"，后续扣库存、发券、通知在 MQ 里异步完成 - 高峰期（双十一）用"订单创建"和"订单支付"两个队列错峰，甚至"先支付后创单"

唯一订单号 - 订单号不能重复、要全局唯一、最好有序（方便分库分表定位和索引） - 方案：数据库自增（单机可用）、Redis INCR（集群有风险）、雪花算法（时间戳 + 机器号 + 序列号，最常用）、美团 Leaf 号段模式（批量取号） - 详情见本章第 9 节分布式 ID

高并发下的读写分离与分库分表：订单表按 user_id 或 order_id 分片，热点订单走缓存，查询走从库。

比喻¶

订单系统像医院的分诊流程：挂号（创建订单）→ 排队（异步队列）→ 看诊（扣库存）→ 缴费（支付）→ 取药（发券）。每个环节都有固定顺序不能乱跳（状态机），病人走了流程但没缴费会超时作废（状态回滚），医院不会让所有病人都同时挤在同一个窗口（异步化 + 分片）。

3. 高可用评论系统怎么设计，支撑百万级用户实时互动？¶

一句话回答¶

评论系统是典型的「读多写少」场景，核心是读写分离 + 多级缓存扛读、异步写 + 消息队列扛写、分库分表扛数据量：读请求走 Redis 缓存 + MySQL 从库，写请求先写 MQ 异步落库，保证高并发下不卡顿、不丢失。

展开讲¶

读写分离 - 主库负责写（插入评论），多个从库负责读（查评论列表），主从同步延迟通常毫秒级可接受 - 评论刚发出自己立刻要能看到，可以"写后读自己的评论走主库"，其他用户的读走从库

多级缓存 - 热帖的评论列表整体缓存到 Redis（如 comment:list:{post_id}），过期时间短（几十秒） - 更新策略：发新评论时更新缓存（追加到缓存列表尾部）或直接删缓存让读请求回源重建 - 冷帖直接查数据库，热帖命中缓存，命中率高的帖子弹幕式滚动毫无压力

异步写 - 用户发评论，接口只做两件事：校验内容合法性 → 发消息到 MQ，立刻返回"评论成功" - 消费者批量写入数据库（攒批 insert，减少磁盘 IO） - 评论内容先进 Redis 的待展示队列，用户马上能看到（假实时），后台慢慢落库（真持久）

分库分表 - 评论数据量巨大（千万级、亿级），按 post_id 或 user_id 分表 - 分表键选择：按 post_id 分，同一帖子的评论集中在一张表，查列表高效；但热帖单表数据大 - 大 V 的帖子是热点，可用"热帖单独拆表 + 冷帖大池子"策略，或引入 ES 做评论搜索

高可用细节 - 评论内容要做敏感词过滤（同步过滤 + 异步复审） - 发评论频率限流（防刷屏），同一用户 N 秒内只能发一条 - 缓存击穿防护：热帖缓存过期瞬间大量请求打到数据库，用互斥锁或"逻辑过期"方案兜底

比喻¶

评论系统像演唱会大屏的弹幕墙：几千人同时发消息，屏幕（缓存）先显示出来让大家看见，后台工作人员（MQ 消费者）再慢慢把每条留言抄进登记本（数据库）。登记本永远不忙，但大屏永远热闹，抄写员偶尔漏抄也会被复查（异步补偿）。

4. 百万用户同时在线的直播评论（弹幕）系统怎么设计？¶

一句话回答¶

直播弹幕是「高吞吐、低延迟、广播式」的场景，核心是WebSocket 长连接推送 + 消息队列广播分发 + 弹幕服务聚合排序 + 冷热分离存储：用户发弹幕进 MQ，弹幕服务批量消费后通过 WebSocket 推给直播间所有在线用户，历史弹幕冷数据放数据库/对象存储，热弹幕在内存。

展开讲¶

连接层：WebSocket - 用户在进入直播间时建立 WebSocket 长连接，服务端可以随时主动推送弹幕，延迟毫秒级 - 相比 HTTP 轮询（每秒请求一次）和 SSE（单向），WebSocket 全双工、省连接开销，是弹幕的标准通道 - 百万在线用户 = 百万条长连接，连接管理要分散到多台网关机，用网关集群 + 负载均衡（按直播间 hash 到固定网关，保证同一直播间的用户连到同一组机器）

消息链路：MQ 广播 - 用户发弹幕 → 弹幕网关收到 → 写入消息队列（如 Kafka，topic 按直播间分区） - 弹幕服务从 MQ 批量拉取（攒几百条一批），做过滤（敏感词、刷屏控制）后批量推送给该直播间的所有连接 - 推送用"扇形分发"：直播房间维护一个连接列表，一条弹幕推给列表里所有人，而不是每人单独一次网络请求

弹幕服务：聚合与排序 - 弹幕不需要严格持久化顺序，服务端按时间 + 序号聚合，客户端负责渲染动画（滚动、飞过） - 同一直播间弹幕量极大（峰值每秒上万条），弹幕服务按直播间做内存队列 + 分片，避免单机内存爆炸 - 弹幕要限流：同一用户频率限制、全直播间弹幕总量限制，超出的丢弃或降级（只显示一部分）

冷热分离存储 - 弹幕是"现在热、以后冷"的数据：直播中弹幕在内存/Redis 里实时流转 - 直播结束后，弹幕按分钟/小时归档写入数据库或对象存储，需要回看时再加载 - 热数据按直播间 + 时间窗口存 Redis（如 danmu:{room_id}:{minute}），冷数据按天分表 - 弹幕通常只保留一段时间（如 7 天），过期清理，控制存储成本

比喻¶

直播弹幕像体育场里的现场喊话：你喊一句（发弹幕），现场的广播员（弹幕服务）听到了，通过遍布全场的喇叭（WebSocket）同时放给所有人听。散场后（直播结束），喊话内容被录下来归档（冷存储），但现场不会再实时广播了。

5. 高并发场景下不崩的点赞系统怎么设计？¶

一句话回答¶

点赞的特点是「单个操作极轻、总量极大、实时性要求高」，核心方案是 Redis 计数 + 异步批量落库 + 集合去重：点赞数先记在 Redis 里（INCR/DECR 原子操作），异步定期批量刷到数据库，用 Redis Set 或布隆过滤器判断用户是否已点赞，防止重复点赞。

展开讲¶

Redis 计数 - 每个内容一个计数 key（like:count:{content_id}），点赞用 INCR，取消用 DECR，Redis 单线程保证原子性，并发下不会出错 - 计数 key 设置合理过期时间或定期持久化，防止 Redis 重启丢数据

异步落库 - 点赞数不能每次操作都写数据库（百万次点击 = 百万次磁盘写） - 方案一：点赞操作只写 Redis，后台定时任务（如每 5 秒）把增量刷到数据库，或定期全量同步 - 方案二：点赞行为发 MQ，消费者攒批后批量 UPDATE 数据库（UPDATE content SET like_count = like_count + N WHERE id = ?） - 关键：Redis 是准实时展示值，数据库是最终可靠值，两者短暂不一致可接受

去重（防止重复点赞） - 用户对同一内容只能点赞一次，再次点击是"取消点赞" - 方案一：Redis Set（like:set:{content_id}）存已点赞用户 ID，点赞前 SISMEMBER 判断；缺点是 Set 大时占内存 - 方案二：布隆过滤器判断"可能已点赞"，误判率低、省内存，但不能精确取消 - 方案三：数据库唯一索引（user_id + content_id）兜底，重复插入报错即视为取消或忽略 - 判断"我是否点过赞"是高频读，同样走 Redis，未命中再查数据库

数据一致性兜底 - 定期对账：拿 Redis 计数和数据库计数对比，修正偏差 - Redis 挂了降级：点赞直接写数据库（性能下降但功能可用），或直接提示"稍后再试"

比喻¶

点赞系统像超市收银台的计数：顾客往购物车放东西（点赞）时，收银员在计数器上按一下（Redis 计数），速度快不排队；下班后（异步）才把今天的总数抄进账本（数据库）。同时每个顾客有会员卡记录"这个商品你买过了"（去重），防止同一个商品反复计数。

6. 亿级用户排行榜怎么设计？¶

一句话回答¶

排行榜的核心数据结构是 Redis 的 ZSET（有序集合）：分数（score）就是排行依据，Redis 底层跳表天然支持排序和范围查询，O(log N) 复杂度，亿级数据也能毫秒级取出 Top N；海量数据用分段/分桶分散热点，冷热数据分离降低存储成本。

展开讲¶

ZSET 基础用法 - ZADD rank 100 user_1 写入分数，ZREVRANGE rank 0 99 取 Top 100，ZSCORE rank user_1 查某人分数，ZRANK 查某人排名 - ZSET 底层是跳表 + 哈希表：哈希表 O(1) 查分数，跳表 O(log N) 排序取范围，亿级数据毫无压力 - 单 key 数据量大时（几千万成员），单机内存和写入都是瓶颈，需要分桶

分段/分桶（Sharding） - 把用户按 ID 或分数区间拆到多个 ZSET（如 rank:0~rank:99 共 100 个桶，用户 ID hash 后落桶） - 写入时定位桶再 ZADD，写压力分散到多台机器 - 取全局 Top N：对每个桶 ZREVRANGE 取各自 Top N，再在内存里合并排序（多路归并） - 桶越多扩展性越好，但合并计算成本越高，一般 100~1000 个桶

冷热数据分离 - 排行榜有"比赛期间热、平时冷"的特点：热榜存 Redis 内存，冷榜/历史榜存数据库或归档 - 只保留前 N 万名在 Redis，后面的人查排名时去数据库查（冷数据低频访问） - 定期把 Redis 数据快照到数据库，Redis 重启可从库恢复

分数设计 - 分数可以是单值（如积分），也可以拼成复合值（如 总积分 * 1000000 + 时间戳）实现"同分先到者排前" - 排名变化通知：用 Pub/Sub 或定时任务推送"排名上升"消息，不用实时推（控制成本）

其他细节：实时榜 + 日榜/周榜分 key 存储；防刷分（限流 + 风控）；榜单数据与业务数据最终一致（异步同步）。

比喻¶

排行榜像班级成绩排名：老师手里的记分册（ZSET）天生按分数排好序，翻一页就是前十名（Top N）。一个班（一个 key）人太多记不过来，就分成几个小组（分桶），每组先排自己的名次，再把各组第一名放一起比出全年级排名（合并排行）。比赛结束后的旧成绩册（冷数据）收进档案室，平时不翻。

7. 百万 QPS 限流器怎么设计？¶

一句话回答¶

限流器按"窗口/速率"两大思路设计：固定窗口和滑动窗口按时间窗计数，漏桶和令牌桶按速率控制；单机用内存计数器或 Guava RateLimiter，分布式场景用 Redis + Lua 脚本保证原子性，令牌桶是最常用的方案。

展开讲¶

四种经典算法对比

算法 原理 优点 缺点 适用
固定窗口 每个时间窗口（如 1 秒）计数，超过阈值拒绝 实现最简单 窗口边界突刺：前 0.9 秒和 0.1 秒各来满量请求可瞬间打满 2 倍流量 粗略限流
滑动窗口 记录每个请求时间戳，统计最近 N 秒内请求数 消除边界突刺，限流平滑 需要存储窗口内所有时间戳，内存和计算开销大 精确限流
漏桶 请求进桶，桶底按固定速率漏水（处理），桶满则丢弃 输出速率绝对恒定，抗突发 无法应对突发流量（有突发请求也只能匀速处理） 保护下游（数据库、MQ）
令牌桶 令牌按速率生成入桶，请求需取到令牌才放行 允许一定突发（桶里攒的令牌可一次用完），平滑又灵活 实现比漏桶复杂一点 通用场景最常用

单机限流 - 内存计数器 + 原子操作（AtomicLong / 自旋），毫秒级判定，扛百万 QPS 没问题 - Guava RateLimiter 是令牌桶的经典实现，适合单机（每台机器独立限流） - 单机限流的缺点是：N 台机器每台限 100，总量就是 N×100，无法全局精确控制

分布式限流：Redis + Lua - 用一个 Redis key 存窗口计数，每次请求 INCR 后判断是否超阈值 - 关键点：判断 + 计数两步必须原子，否则并发下两个请求同时读到未超限导致穿透，所以用 Lua 脚本把"读计数 → 判断 → 自增"封装成一个原子操作 - 令牌桶的分布式实现：Redis 存令牌数 + 上次补充时间，Lua 里"按时间补充令牌 → 判断是否够 → 扣减"，同样保证原子 - 优缺点：全局精确，但每次请求多一次 Redis 往返（RTT 约 0.1~1ms），百万 QPS 需要 Redis 集群分片 + 本地令牌桶降级

工程实践 - 分层限流：Nginx 层（IP 维度）→ 网关层（用户维度）→ 业务层（接口维度），层层拦截 - 超限响应：返回 429 + 重试提示，或直接降级（返回兜底数据） - 限流阈值用"水位 + 兜底"配置化，动态调整，避免拍脑袋

比喻¶

限流器像地铁安检口：固定窗口像"每分钟放进 100 人"——前一分钟 59 秒时挤进 99 人，下一分钟第 1 秒又涌进 99 人，闸机瞬间堵爆；滑动窗口像"任意 60 秒内最多 100 人"——盯住滚动的一分钟，永远不突刺；漏桶像"传送带匀速送行李"——不管多少人涌来，传送带速度恒定；令牌桶像"安检员手里的小票"——票按固定速度发出，没票的人等着，攒了票的人可以连续过，既能匀速又能应对小高峰。

8. 十亿级 URL 短链系统怎么设计？¶

一句话回答¶

短链系统 = 把长 URL 映射成一个短字符串（如 8 位），访问时 302 跳转回长 URL。核心是短码生成（哈希 or 发号器）、存储映射关系（数据库 + Redis 缓存）、以及防冲突和防爆破；十亿级规模用发号器方案最可靠。

展开讲¶

短码生成两种方案对比

方案 原理 优点 缺点
哈希截断 对长 URL 做 MD5/SHA 哈希，截取前 6~8 位（或转 62 进制） 无状态、不需要发号器、相同 URL 得到相同短码（可去重） 哈希冲突需要处理（冲突后加盐重哈希或用数据库唯一索引重试）；不同 URL 可能同码
发号器 用一个全局自增 ID（数据库自增 / 雪花 / 号段），转成 62 进制字符串（a-zA-Z0-9） 绝对唯一、无冲突、可预测总容量 需要维护发号服务，存在单点；ID 可被枚举（需配合混淆）
  • 62 进制：09、az、A~Z 共 62 个字符，8 位短码容量 = 62^8 ≈ 218 万亿，十亿级绰绰有余
  • 常用做法：发号器生成递增 ID → ID 转 62 进制得到短码；或用"预生成短码池"批量取用

存储与缓存 - 映射表：short_code（主键）→ long_url + 创建时间 + 过期时间，十亿级数据必须分库分表（按短码 hash 分片） - 读路径：访问短链 → 先查 Redis（short:{code} → long_url，命中直接 302）→ 未命中查数据库 → 回填 Redis - 热点短链（爆款活动链接）缓存命中率极高，数据库几乎无压力 - 写路径：用户提交长 URL → 发号器取号 → 写数据库 → 写缓存 → 返回短码

重定向细节 - 用 302 临时重定向而非 301：302 每次都经过短链服务，可以统计点击量、做跳转前广告/风险拦截；301 浏览器会永久缓存，短链服务失去统计和控制能力 - 统计：每次点击异步记一条日志（MQ 消费写库），支持按短码查点击量

安全与可靠性 - 防爆破：短码 8 位空间太大，暴力枚举不可行，但发号器方案连续递增仍可被扫描，可对 ID 做位混淆（如乘以大素数取模） - 恶意链接检测：生成时查黑名单，跳转时拦截 - 发号器高可用：用号段模式（Leaf 方案，一次取一批号本地发，见第 9 节）

比喻¶

短链系统像图书馆的索书号：每本书（长 URL）分配一个唯一编号（短码），读者报编号就能快速找到书（跳转）。编号由前台（发号器）按顺序发放绝不重复，热门书（热点链接）的索书卡（缓存）放在前台台面上，一查就有；冷门书才需要去书库（数据库）翻。图书管理员每次借出都记一笔账（点击统计）。

9. 分布式 ID 怎么设计？¶

一句话回答¶

分布式 ID 要求全局唯一、趋势递增、高性能、高可用，主流方案有四类：UUID、数据库自增、号段模式（美团 Leaf）、雪花算法（Snowflake）；其中雪花算法和号段模式是生产最常用组合，Redis INCR 作为补充方案。

展开讲¶

四种方案对比

方案 生成方式 优点 缺点
UUID 本机生成 32 位十六进制字符串 无中心、绝对唯一、生成极快 无序（做主键导致 B+ 树页分裂、索引碎片化）、太长（占空间大）、无业务含义
数据库自增 MySQL AUTO_INCREMENT 简单、严格递增 单点瓶颈、依赖数据库性能；集群需设步长（如 2 台各 +2），扩容麻烦
号段模式（Leaf-segment） 数据库维护 max_id，服务一次取一段（如 1000 个）本地发，用完再取 高性能（本地发号不碰 DB）、有顺序、DB 压力极小 号段用完瞬间有 DB 请求尖刺；服务重启会浪费未用完的号
雪花算法 64 位 long：1 位符号 + 41 位时间戳 + 10 位机器 ID + 12 位序列号 无中心、趋势递增、每秒单机可生成 4096×N 个 依赖机器时钟，时钟回拨会生成重复 ID，需处理（等待/拒绝/备用位）

美团 Leaf 的完整方案 - Leaf-segment（号段）：DB 表 (biz_tag, max_id, step)，每个业务一个 tag，服务取号段时 UPDATE ... SET max_id = max_id + step 再返回新段，内存缓存本地发 - Leaf-snowflake：雪花算法 + Zookeeper 注册机器 ID，解决时钟回拨：启动时检查本机时间是否小于上次生成 ID 的时间，若是则拒绝服务直到时间追上；运行中定期检查 - 双 buffer 优化：号段快用完时（如剩 10%）提前异步加载下一段，彻底消除 DB 尖刺 - 对比：号段模式性能高、有序（适合订单号），雪花算法无中心、扩展好（适合日志、消息 ID）；大厂常两者都备

如何选择 - 要求严格有序（订单号、对账友好）→ 号段模式 - 要求无中心、吞吐极大、可接受趋势递增 → 雪花算法 - 无所谓顺序、量小 → UUID（注意存储选 binary 或 varchar(32)）

比喻¶

分布式 ID 像电影院取票：UUID 像每个人都自己瞎编一个票号——绝不重复，但号码毫无规律，检票员（数据库索引）得满场乱翻；数据库自增像只有一个售票窗口发号——顺序好但全影院排队；号段模式像售票处整盒整盒地发号——窗口一次领一千张票在手里发，快发完了再去领，发号速度飞快；雪花算法像每个检票口自己按"日期 + 检票口编号 + 流水号"编票号——大家各编各的也不冲突，但前提是所有钟表（服务器时钟）都要准。

10. 项目里密码怎么存储？¶

一句话回答¶

密码绝不能明文或简单哈希存储，正确做法是加盐 + 慢哈希算法（bcrypt / scrypt / Argon2）：每个用户的盐随机独立，哈希算法故意设计得慢（毫秒级），让暴力破解成本高到不可行；配合传输加密、脱敏展示和登录限流防爆破。

展开讲¶

为什么 MD5 / SHA 直接哈希不安全 - MD5、SHA-1 已被证明可碰撞，更致命的是彩虹表：攻击者预先把海量常见密码的哈希算好存起来，拿到你的哈希值一查表就还原出明文 - 即使加固定盐（所有用户同一个盐），只要盐泄露，彩虹表可以针对这个盐重新生成 - MD5/SHA 设计目标是"快"，每秒可算几亿次，暴力破解毫无压力——哈希速度对密码存储是灾难

加盐（Salt） - 每个用户注册时生成一个随机盐（如 16 字节），存 hash = H(password + salt)，盐和哈希一起存库 - 盐必须每个用户独立、足够随机：即使两个用户密码相同，哈希值也不同；攻击者无法用一张彩虹表打所有人，只能针对单个用户单独爆破 - 盐不需要保密（泄露也无妨），它的作用是破坏彩虹表和批量破解

慢哈希算法 - bcrypt：内部多次迭代（成本因子 cost，默认 10~12），单次验证约 50~100ms，每秒只能算几千次，暴力破解成本上升百万倍；自动包含盐，输出格式自带盐信息，实现简单 - scrypt：内存密集算法，除了慢还占大量内存，硬件破解更难 - Argon2：目前公认最强（内存 + CPU 双密集），密码学大赛冠军 - 对比：bcrypt 最普及（Spring Security、PHP、Node 生态都内置），scrypt/Argon2 更抗 GPU 破解但生态略少；三者都远优于 MD5/SHA

配套安全措施 - 传输加密：HTTPS 保证密码在网络上不泄露 - 脱敏：日志、数据库查询、接口返回里密码一律不出现，数据库字段设计上就只存哈希 - 防爆破：登录接口限流 + 验证码 + 失败次数锁定（同一账号连续失败 N 次锁定一段时间），防止撞库和暴力猜解 - 密码复杂度校验 + 强制定期改密（视安全等级而定）

比喻¶

密码存储像存保险箱钥匙：MD5 像把钥匙直接扔进普通文件柜（彩虹表一翻就找到）；加盐像给每把钥匙包上一层专属的、不同的保鲜膜（盐）再锁起来——每把钥匙都不一样，没法批量比对；bcrypt 像给保险箱装了慢速转盘锁——开一次要拧几百圈（慢哈希），小偷试一次要很久，试一万次就要好几天，试到怀疑人生自然放弃。

11. 单点登录 SSO 怎么工作？¶

一句话回答¶

单点登录（SSO）解决"多个系统共用一套账号"：用户在一个系统登录后，访问其他系统无需再次登录。原理是引入独立的认证中心统一发"通行证"（Ticket 或 JWT），各系统都信任认证中心；经典实现是 CAS 流程（Ticket 模式），现代实现常用 JWT + OAuth2。

展开讲¶

从 Cookie/Session 说起 - 单机时代：登录后服务端存 Session，浏览器存 SessionId（Cookie），每次请求带 Cookie 验证身份 - 问题：Session 存在单台服务器，多台机器 / 多套系统无法共享，于是需要把登录状态"集中"或"无状态化"

SSO 核心思想 - 所有系统共同信任一个认证中心（CAS Server / SSO Server） - 登录状态集中管理：认证中心统一存 Session（或发统一签名的票据），各业务系统不再自己管登录 - 无状态方案：认证中心签发 JWT（含用户信息 + 过期时间 + 签名），业务系统验签即可信任，不需要共享 Session

CAS 经典流程（Ticket 模式） 1. 用户访问业务系统 A，未登录 → 重定向到认证中心登录页 2. 用户在认证中心输入账号密码，登录成功 3. 认证中心生成一个一次性 Ticket，浏览器带着 Ticket 跳回系统 A 4. 系统 A 拿 Ticket 去认证中心验证（回调），验证通过拿到用户信息，系统 A 建立自己的会话 5. 用户再访问系统 B：系统 B 发现未登录 → 重定向到认证中心 → 认证中心发现用户已在认证中心登录过（有全局会话 Cookie）→ 不发登录页，直接发 Ticket 跳回系统 B → 系统 B 验证后放行 - 关键点：Ticket 一次性、短时效；全局会话（TGC Cookie）存在认证中心域下；各系统通过"认证中心回调"换取用户信息

JWT 方案 - 认证中心签 JWT（Header.Payload.Signature），业务系统用共享密钥/公钥验签，无需回调认证中心 - 优点：无状态、业务系统零存储、适合分布式和移动端 - 缺点：无法主动失效（签发后到期前一直有效，踢人/封号需引入黑名单或短过期 + refresh token 机制）

OAuth2 简述 - OAuth2 解决的是"授权"问题：第三方应用在用户授权下访问用户在平台的数据（如"微信登录"让小程序拿到你的头像昵称） - 流程：第三方 → 授权服务器 → 用户同意 → 授权服务器发授权码 → 第三方换 access_token → 拿 token 调资源接口 - SSO 和 OAuth2 常组合：OAuth2 管"授权"（我能访问你哪些数据），SSO 管"认证"（你是谁、登录一次全系统通用）；企业内网常用 CAS 式 SSO，面向第三方常用 OAuth2

比喻¶

SSO 像游乐场的通票手环：你在售票处（认证中心）买一次票戴上手环（全局会话），之后去旋转木马（系统 A）、过山车（系统 B）都不用再买票，每个项目门口的工作人员（业务系统）看一眼手环（验票/验签）就放你进。CAS 的 Ticket 像每个项目入口的"当日单次券"——玩完就作废；JWT 像手环上的二维码——上面写着你是谁、有效期到几点，门口扫一下就认。

12. 如何设计安全的对外 API？¶

一句话回答¶

对外 API 的安全防线是四道闸：身份鉴权（你是谁）、签名防篡改（数据没被改过）、防重放（同一请求不能重复用）、限流防攻击（打不死）；敏感数据加密传输，密钥分级管理，配合完整的日志审计。

展开讲¶

鉴权（Authentication & Authorization） - 你是谁：API Key / Access Token / JWT，识别调用方身份 - 你能干什么：权限模型（RBAC 角色权限、按接口粒度授权），未授权接口返回 403 - 常见组合：商户申请 AppId + AppSecret，服务端校验签名和 Token

签名机制（防篡改 + 防伪造） - 调用方把请求参数 + 时间戳 + 随机数（nonce）+ AppSecret 拼成字符串，用 MD5/SHA256 算出签名（sign）随请求发送 - 服务端用同样的规则 + 自己持有的 AppSecret 重算签名，不一致则拒绝——只要密钥不泄露，请求参数被改一个字符签名就对不上 - 签名本质是"带密钥的哈希"：校验的是参数完整性 + 调用方身份（持有密钥的人）

防重放 - 攻击者截获一个合法请求（如转账请求），原封不动重发，服务端可能重复执行 - 对策一：时间戳校验——请求时间与服务器时间差超过 N 分钟直接拒绝 - 对策二：随机数 nonce 一次性——服务端记录用过的 nonce，重复出现即拒绝（存 Redis，设置过期） - 对策三：接口幂等设计——同一业务请求带唯一请求 ID，服务端用唯一索引/Redis 去重，重复请求返回第一次的结果（这才是根治） - 三者结合：时间戳挡过期重放，nonce 挡窗口内重放，幂等挡任何形式重复

加密 - 传输层：HTTPS（TLS）必须，防中间人窃听和篡改 - 业务层：敏感字段（手机号、身份证）额外加密存储 + 加密传输（AES 对称加密，密钥通过非对称分发） - 密钥管理：AppSecret 不落前端代码、不落日志，服务端密钥库集中管理、定期轮换；前端密钥用"签名服务"代替直发密钥

限流与风控 - 按 IP、按 AppId、按用户维度限流（见第 7 节），超限返回 429 - 风控规则：异常频次（如 1 秒内同一账号请求 100 次）、异常时段、黑名单 - 灰度发布 + 全链路监控：API 调用量、错误率、延迟告警

其他 - 参数校验（长度、类型、白名单），防注入和超长参数 - 统一错误码，不泄露内部细节（不返回堆栈） - 完整访问日志（谁、何时、调了什么、结果），可审计可追溯

比喻¶

安全的对外 API 像银行柜台取款：先出示身份证（鉴权）确认是你；再签一份"金额 + 时间 + 签名"的单子（签名防篡改），笔迹对不上就拒办；单子上有日期和时间戳（防重放），昨天的单子今天不能再用；取款有单日限额（限流），取太频繁银行会打电话核实（风控）；现金全程走监控下的通道（HTTPS 加密），柜台的每一笔都有录像（日志审计）。

13. 项目支持百万用户的架构怎么设计？¶

一句话回答¶

百万用户的架构不是一次到位的，而是分层治理 + 逐级分流：接入层（CDN + Nginx）挡静态流量，应用层（服务化 + 集群 + 无状态）扛动态请求，缓存层（Redis）挡数据库读，消息队列削峰异步化，数据库层（读写分离 + 分库分表）兜底持久化，最后配齐监控报警和容量规划。

展开讲¶

经典分层架构（从用户到数据库）

层 组件 作用
客户端 App / Web 本地缓存、请求合并
接入层 CDN + DNS + 负载均衡（LVS/Nginx） 静态资源就近分发；流量分发到多台应用服务器
应用层 应用服务集群（无状态） 业务逻辑；无状态设计使任意请求可落到任意机器，水平扩容
缓存层 Redis 集群 热点数据、Session 集中存储，挡住 90% 以上读请求
消息层 Kafka / RocketMQ 削峰、异步化、解耦（下单、发通知、埋点）
数据层 MySQL 主从 + 分库分表 读写分离扛读、分片扛数据量和写
搜索/日志 Elasticsearch 全文检索、日志检索

关键设计原则 - 无状态化：应用服务器不存用户 Session（Session 放 Redis）、不存本地文件（文件放 OSS），这样加机器 = 加容量，任意机器可以互相替换，故障机器直接摘除 - 缓存优先：热点数据全部进缓存（商品详情、用户信息、配置），缓存击穿/雪崩要有兜底（互斥锁、多级缓存、限流降级） - 异步化：非关键链路（通知、统计、日志）全部 MQ 异步，主链路只做必要的事 - 数据库兜底：读写分离（主写从读）+ 分库分表（按业务键分片）+ 慢查询治理，数据库是最后一道防线，压力必须最小

容量估算与监控 - 先估算：百万用户 → 日活按 10%20%（1020 万）→ 峰值 QPS = 日活 × 人均请求 / 峰值小时秒数，一般百级到千级 QPS - 按 QPS 反推机器：单机应用可扛几百到几千 QPS，单机 MySQL 扛几千 QPS，Redis 单机十万级 QPS——先算清再扩容 - 监控三件套：指标（QPS、RT、错误率、CPU/内存）、日志（ELK）、告警（阈值 + 值班）；容量水位 70% 就要预警扩容

演进路径：单机（MVP）→ 加缓存 + 读写分离（万级）→ 集群 + 分库分表 + MQ（十万级）→ 微服务 + 单元化（百万级+）。架构是演进来的，不是一次设计出来的。

比喻¶

百万用户架构像大型高铁站：乘客（请求）从四面八方来，先在站前广场分流（CDN 就近服务），安检口（网关/负载均衡）把人群均匀分到几十个进站口（应用集群），候车厅的电子屏（缓存）让大部分人不用挤到售票窗口（数据库）问信息，检票分批放行（MQ 削峰），站台（数据库）只做最后的发车确认。人再多，就多开几个进站口（水平扩容），车站本身的设计不用改。

14. 用户规模放大 100 倍怎么应对？¶

一句话回答¶

应对规模放大 100 倍的思路是先算后扩、能缓存就缓存、能异步就异步、能分片就分片：通过水平扩容（加机器）解决吞吐，缓存 + 读写分离解决读压力，分库分表解决数据量和写压力，异步化削峰解耦；同时重构瓶颈点（慢 SQL、热点 key、单点组件），让每一层都有冗余和降级方案。

展开讲¶

第一步：估算瓶颈 - 用户 ×100 → 流量 ×100、数据量 ×100、峰值 QPS ×100 - 画全链路清单：哪些是单点（单库、单 Redis、单机应用）、哪些会先扛不住，按瓶颈顺序逐个解决

扩容策略

维度 方案 说明
应用层 水平扩容（无状态加机器） 应用无状态化后，加机器即可线性提升吞吐；负载均衡自动分发
数据库读 读写分离（一主多从） 读流量打到从库，主库只写；从库可继续加
数据库写/数据量 分库分表 按 user_id / order_id 等业务键分片，每片独立库表；数据量和写压力摊到多台
缓存 Redis 集群扩容 + 多级缓存 冷热分离，热点数据多级缓存（本地 + Redis）
存储 冷热分离 + 归档 历史数据迁移到低成本存储（OSS、冷库），热库只留近 N 天

异步化改造 - 同步链路拆异步：下单、发消息、统计、日志全部 MQ；削峰填谷，让流量峰值不再直接冲击数据库 - 写路径攒批：批量插入、批量更新（见点赞系统），把磁盘 IO 次数降低一个数量级

分片（Sharding）细节 - 分片键选择决定生死：按业务访问模式选（订单按 user_id、消息按会话 ID），保证同一条数据的读写落在同一片 - 跨片查询问题：列表页聚合查询需要"先查分片再合并"，或引入 ES/宽表冗余 - 扩容再分片：从 10 片扩到 100 片要迁移数据，用"双写 + 迁移工具"平滑过渡，或用一致性哈希减少迁移量

专项治理 - 热点 key / 热 key：大 V 账号、爆款商品是热点，单独缓存、本地缓存、限流保护 - 慢 SQL：加索引、改写、查询走缓存 - 单点组件高可用：Nginx 双机热备、Redis 主从 + 哨兵、MQ 集群、数据库主从 - 全链路压测：扩容后必须压测验证，不能拍脑袋

核心理念：放大 100 倍不是"买 100 倍的机器"这么简单，而是架构范式要变——从"一台机器干所有事"变成"每层各司其职、各自可扩展、各自有冗余"，每一层的扩展都是独立的（应用随便加、缓存随便加、数据库按片加）。

比喻¶

用户放大 100 倍像一家小店变成连锁超市：小店一个收银台、一个仓库（单机）；变超市后，门口多了导购（CDN）分流、收银台变成几十个（应用集群）、货架上的热销品直接堆在门口展示（缓存）、补货从"顾客要了才去仓库拿"变成"仓库定时补货"（异步化）、一个仓库变成区域分仓（分库分表）。生意再翻 100 倍，只需多开几家分店（加机器），不用把一家店改成 100 层的楼。

15. 如何做到高可用、高吞吐、高扩展性（三高设计）？¶

一句话回答¶

三高是三个目标、三种手段：高可用靠冗余和故障转移（多副本、主从、集群、降级熔断），高吞吐靠异步化、缓存和并发优化（少做无用功、错峰削峰），高扩展性靠无状态化、分片和微服务化（加机器就能扛、拆模块就能扩）。三者互相制约，设计时要分优先级和取舍。

展开讲¶

高可用（High Availability）：99.99% 不挂 - 核心手段是冗余 + 故障转移：任何组件都有备份，主挂了从顶上，机器挂了流量切走 - 应用层：多副本 + 负载均衡健康检查，挂一台自动摘除 - 缓存层：Redis 主从 + 哨兵/Cluster，主挂自动切换 - 数据库：MySQL 主从 + MHA/半同步复制，主挂自动提升从库 - MQ：集群多副本（Kafka ISR、RocketMQ 主从同步） - 治理手段：降级（非核心功能让路，如大促关掉推荐）、熔断（下游故障快速失败，不拖垮自己）、限流（保护自己不被流量打死）、超时重试 + 幂等（下游恢复后自动补齐） - 衡量：可用性 = 正常运行时间 / 总时间，四个 9 ≈ 一年宕机 52 分钟

高吞吐（High Throughput）：单位时间处理更多 - 异步化：把"同步等待"变成"先返回、后台干"（MQ 削峰），系统不阻塞在慢操作上 - 缓存：读请求不落库（90% 命中率 → 数据库压力降 10 倍） - 批量：攒批读写（批量 insert、批量推送），减少网络和磁盘次数 - 并发优化：连接池、线程池合理配置；无锁/轻锁数据结构；减少串行化（锁粒度从表级降到行级） - 水平扩容：无状态应用加机器线性提升吞吐（这是最粗暴也最有效的） - 衡量：QPS（每秒请求数）/ TPS（每秒事务数）

高扩展性（High Scalability）：加机器就能扛、加业务不伤筋动骨 - 无状态化：Session 出应用（Redis）、文件出应用（OSS），应用层"加机器即扩容" - 分片：数据层按业务键分库分表，数据量和写能力随分片数线性增长 - 微服务化/模块化：按业务域拆服务（订单、用户、库存独立），每个服务独立扩缩容、独立发布；服务间通过接口/消息解耦 - 接口兼容：服务拆分时预留扩展点（版本号、插件化），新功能不破坏旧调用方

三高的取舍 - 高可用 vs 成本：冗余意味着多花钱（多副本、多机房），按业务重要性分级投入（核心交易 4 个 9，非核心 2 个 9 够用） - 高吞吐 vs 一致性：异步化牺牲强一致换吞吐（最终一致），关键链路（支付、扣库存）必须强一致 - 高扩展 vs 复杂度：微服务带来部署和运维复杂度翻倍，小团队小业务没必要拆；"能单体别微服务，能同步别异步，能不分片别分片"

一个完整的"三高"落地清单：无状态应用集群 + 负载均衡（可用 + 扩展）→ Redis 缓存 + 集群（吞吐 + 可用）→ MQ 异步削峰（吞吐 + 解耦）→ 数据库主从 + 分库分表（可用 + 扩展）→ 限流/熔断/降级/重试四件套（可用）→ 监控告警 + 容量规划（一切的前提）。

比喻¶

三高设计像一个经营红火的连锁餐厅：高可用是"厨师、服务员都有备份，主厨请假副厨立刻顶上，食材供应商断了立刻换一家"——任何时候都不关门；高吞吐是"点菜系统先记单、后厨流水线出菜、餐位翻台快"——一晚上接待 1000 桌也不乱；高扩展性是"生意好了多开分店（加机器）、菜单可以随时加新菜（加服务）、每家分店独立运营"——不用把总店改成 100 层的楼。而老板（架构师）要做的，是算清楚哪家店最该多配人手、哪些菜不值得做，把钱花在刀刃上。
