05 锁与死锁¶

本章覆盖：为什么要加锁、自旋锁原理与场景、死锁的四个必要条件、如何避免死锁、银行家算法（完整例题）、乐观锁 vs 悲观锁。

死锁四条件和银行家算法是面试高频考点，建议重点掌握第 3、4、5 节。银行家算法的例题建议自己动手推一遍。

1. 为什么并发执行线程要加锁？¶

一句话回答¶

加锁是为了保护共享数据，防止竞态条件（Race Condition）——多个线程同时访问和操作同一块数据时，最终结果依赖线程的执行顺序，导致数据不一致。

竞态条件例子¶

共享变量 count = 0

线程A: count = count + 1   ← 读 count(0)
线程B: count = count + 1   ← 读 count(0)（A 还没写回去！）
线程A: 写回 count(1)
线程B: 写回 count(1)       ← 两个线程都 +1，结果却是 1，不是 2！

竞态条件：多个线程同时访问修改同一块数据，结果取决于执行顺序，可能出错。

加锁的作用：确保任何时刻只有一个线程能访问共享数据，避免竞态，保证数据一致性和完整性。

类比：公共卫生间——不锁门就乱套，锁门保证同一时刻只有一个人能用。

2. 自旋锁是什么？应用在哪些场景？¶

一句话回答¶

自旋锁加锁失败后，线程会忙等待（一直自旋循环），直到拿到锁；它通过 CPU 的 CAS 指令在用户态完成加锁解锁，不主动产生线程切换。适合被锁代码执行时间很短的场景。

原理：CAS 原子指令¶

普通加锁要两步： 1. 查看锁状态，是否空闲 2. 将锁设置为当前线程持有

CAS（Compare And Swap） 把这两步合并成一条硬件级指令，是原子指令——要么一次执行完两步，要么都不执行，不可分割。

设锁为变量 lock：0 表示空闲，pid 表示线程 ID
加锁：CAS(lock, 0, pid)   ← 比较 lock 是否为 0，是则换成 pid
解锁：CAS(lock, pid, 0)   ← 比较 lock 是否为 pid，是则换成 0

忙等待¶

  • 加锁失败的线程会忙等待（自旋）直到拿到锁
  • 用 while 循环实现，但最好用 CPU 的 PAUSE 指令——减少循环等待时的耗电量

注意事项¶

  • 单核 CPU 上：必须配合抢占式调度器（时钟中断抢走 CPU），否则自旋的线程永远不会放弃 CPU，自旋锁无法使用
  • 自旋时间与被锁代码的执行时间成正比——锁住的代码执行越久，自旋线程占用 CPU 越久

自旋锁 vs 互斥锁（核心区别）¶

对比项 自旋锁 互斥锁
加锁失败时 忙等待（自旋） 线程切换（阻塞睡眠）
开销 小（不切换） 大（切换上下文）
适用 锁内代码执行时间很短 锁内代码执行时间较长

面试金句："如果你能确定被锁住的代码执行时间很短，就应该用自旋锁而不是互斥锁——因为互斥锁的线程切换开销可能比等待本身还贵。"

适用场景¶

  • 临界区很小、锁持有时间很短的场景（如内核里保护一个计数器）
  • 异步、协程等用户态切换请求的编程方式
  • 多核系统下不主动产生线程切换

3. 死锁发生条件是什么？¶

一句话回答¶

死锁要同时满足四个条件：互斥、持有并等待、不可剥夺、环路等待。缺一个都不会死锁。

四个必要条件¶

① 互斥条件 - 多个线程不能同时使用同一个资源 - 类比：一辆车只能一个人开

② 持有并等待条件 - 线程 A 已持有资源 1，又想申请资源 2，而资源 2 被线程 C 持有，于是 A 进入等待 - 关键：A 在等待资源 2 的同时，不会释放自己已持有的资源 1 - 类比：左手抓着碗不放，右手去抢别人的筷子

③ 不可剥夺条件 - 线程已持有的资源，在自己使用完之前不能被其他线程抢走 - 线程 B 想用资源，只能等 A 用完并释放 - 类比：占着座位不让人赶，只能等我自己起来

④ 环路等待条件 - 死锁发生时，两个或多个线程获取资源的顺序构成环形链 - 类比：A 等 B 释放，B 等 A 释放——互相瞪眼

死锁的经典场景¶

线程A：持有锁1，等待锁2
线程B：持有锁2，等待锁1
→ A 等 B，B 等 A，谁都不让，程序卡死

4. 如何避免死锁？¶

一句话回答¶

破坏四个必要条件中的任意一个即可。最常见且可行的是资源有序分配法——让所有线程以相同的顺序申请资源，破坏"环路等待条件"。

资源有序分配法¶

线程A 申请资源的顺序：先资源A → 后资源B
线程B 申请资源的顺序：先资源A → 后资源B   ← 和 A 一致！

为什么能避免死锁？ 如果所有线程都按相同顺序（比如先 A 后 B）申请资源，就不会出现"A 等 B、B 等 A"的环——因为 B 永远在 A 后面申请，谁先拿到 A 谁就能顺利拿到 B。

其他破环思路¶

破坏的条件 方法
互斥条件 尽量用共享访问替代独占（但通常不可行）
持有并等待 一次性申请所有资源（要么全给，要么不给）
不可剥夺条件 允许抢占：等不到就把已持有的先放出来
环路等待条件 资源有序分配法（最常用）

5. 银行家算法¶

一句话回答¶

银行家算法是最有代表性的避免死锁的算法，思想像银行放贷：分配资源前先"预演"一遍，只有确认系统不会进入死锁才分配。核心是不断检查"剩余资源能否满足某个进程的最大需求"，能就执行它并回收资源，最终看能否让所有进程都加入安全序列。

三条业务逻辑（为什么叫"银行家"）¶

原则 说明
总量约束 进程的最大需求量不能超过系统总资源数，否则不接纳执行
可分期请求 进程可分期请求资源，但总请求数不能超过最大需求量
推迟分配 系统现有资源不够时延迟分配，但总让进程在有限时间内拿到资源

完整例题（经典面试题）¶

系统有三类资源 R1、R2、R3，可用数分别为 9、8、5，五个进程 P1~P5 的最大需求量和已分配数如下：

进程 最大需求量 已分配资源数
P1 6 5 2 1 2 1
P2 2 2 1 2 1 1
P3 8 1 1 2 1 0
P4 1 2 1 1 2 0
P5 3 4 4 1 1 3

第一步：算出系统剩余资源和各进程还缺多少

R1 剩余 = 9 - (1+2+2+1+1) = 2
R2 剩余 = 8 - (2+1+1+2+1) = 1
R3 剩余 = 5 - (1+1+0+0+3) = 0
进程 还需要的资源数（最大 - 已分配）
P1 5 3 1
P2 0 1 0 ← 只需要 1 个 R2
P3 6 0 1
P4 0 0 1
P5 2 3 1

第二步：P2 可以执行（剩余 2 1 0 ≥ 它需要的 0 1 0） 执行完 P2 释放资源： 

R1 = 2 - 0 + (2+0) = 4
R2 = 1 - 1 + (1+1) = 2
R3 = 0 - 0 + (0+1) = 1
剩余：4 2 1

第三步：只有 P4 满足（剩余 4 2 1 ≥ P4 需要的 0 0 1） 

R1 = 4 - 0 + (1+0) = 5
R2 = 2 - 0 + (2+0) = 4
R3 = 1 - 1 + (0+1) = 1
剩余：5 4 1

第四步：只有 P5 满足（5 4 1 ≥ P5 需要的 2 3 1） 

R1 = 5 - 2 + (1+2) = 6
R2 = 4 - 3 + (1+3) = 5
R3 = 1 - 1 + (3+1) = 4
剩余：6 5 4

第五步：P1 和 P3 都满足了（6 5 4 ≥ 5 3 1 和 6 0 1）

安全执行顺序：P2 → P4 → P5 → P1 → P3（或 P3 → P1）

银行家算法总结¶

  • 核心思想：分配资源前先判断安全性（预执行），不会导致死锁才分配，否则让进程等待
  • 执行过程：不断检查剩余资源能否满足某进程的最大需求 → 满足则加入安全序列并回收它的资源 → 重复直到所有进程入列
  • 安全性说明：安全状态一定不会死锁，但不安全状态也不一定会死锁——不安全只是存在死锁的可能

面试金句："银行家算法牺牲了一点点资源利用率，换来了'绝对不会死锁'的保证。"

6. 乐观锁和悲观锁有什么区别？¶

一句话回答¶

乐观锁假设很少冲突，读时不加锁，更新时检查版本号，冲突则放弃/重试；悲观锁假设经常冲突，读时就加锁防止别人改。乐观锁适合读多写少，悲观锁适合写多。

对比¶

乐观锁（Optimistic Lock） - 基本思想：假设事务之间很少冲突，读取数据时不加锁，更新时检查数据的版本号/时间戳——版本匹配则执行更新，不匹配则认为发生冲突（放弃或重试） - 适用场景：读多写少，减少锁竞争、提高并发性能 - 类比：教室自习先随便坐，快走的时候发现座位被人占了才处理

悲观锁（Pessimistic Lock） - 基本思想：假设事务之间会频繁冲突，读取数据时就加锁，防止其他事务修改，直到当前事务完成才释放 - 适用场景：写多，通过加锁保证数据一致性（如数据库行级锁） - 类比：进了包厢就锁门，别人想进也进不来

记忆表¶

对比项 乐观锁 悲观锁
假设 很少冲突 经常冲突
加锁时机 更新时检查版本 读取时就加锁
冲突处理 版本不匹配就放弃/重试 直接阻塞等待
适用场景 读多写少 写多
典型实现 版本号、CAS 数据库行锁、互斥锁
