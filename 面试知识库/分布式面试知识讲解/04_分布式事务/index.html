04 分布式事务¶

本笔记覆盖：什么情况下需要使用分布式事务、分布式事务的解决方案有哪些（2PC / 3PC / TCC / Saga / 消息队列 / 本地消息表）、阿里的 Seata 框架了解过吗

1. 什么情况下需要使用分布式事务？¶

一句话回答¶

当业务操作跨越了「单一数据库连接」的范畴——涉及多个物理分离的数据库或多个微服务，又必须保证这些跨节点的操作「要么全部成功、要么全部回滚」时，就必须引入分布式事务。

展开讲¶

两种最典型的触发场景¶

场景一：微服务架构下的跨服务协同（最常见）

微服务时代推崇「一个服务专属一个自己的数据库」。举个经典的电商下单例子：用户点击支付后，后台需要做三件事：

  1. 订单服务 → 更新订单状态（自己的订单库）；
  2. 库存服务 → 扣减库存（自己的库存库）；
  3. 账户服务 → 扣减余额（自己的账户库）。

这三个动作发生在三个独立的系统、三个独立的数据库里。假设前两步都成功了，但在调用账户服务扣钱时，账户服务器宕机了。这时候，传统的本地事务（比如 Spring 的 @Transactional）根本无能为力——它只能回滚自己当前数据库里的操作，完全没办法隔空把已经成功提交的「订单」和「库存」撤销掉。

结果就是：商家的货扣了（或订单状态改了），用户的钱却没扣，数据不一致。

场景二：底层数据量大，做了分库分表

这在单体应用里也可能发生。假如没有微服务架构，所有代码都在一起，但底层由于数据太多，把一个大库拆成了库 A 和库 B。如果在一个方法里同时往库 A 插入账单、往库 B 插入流水——它们在物理上已经是两个独立的数据库实例，走的是两条独立的网络连接，Spring 自带的本地事务就无法保证这两个连接能同时成功提交。一旦一边成功一边失败，也会产生脏数据。

一个重要的观点：能绕开就尽量绕开¶

站在架构师的视角，业界有个共识：能绕开不用分布式事务，就尽量不用。

原因很实际：强一致性的分布式事务（比如传统的两阶段提交）是非常重的——它会让多个节点的数据库锁互相等待，极其拖慢系统的响应速度，根本扛不住互联网的高并发。

所以真实的互联网公司里：

  • 极少数场景（如核心银行转账，对钱要求「强一致性」，必须立刻分毫不差）才咬牙用传统分布式事务；
  • 大多数微服务场景，退而求其次，用消息队列（MQ）+ 本地消息表或重试机制来实现「最终一致性」：允许短时间内数据有点误差，只要过一会儿大家的数据能最终对齐就行，以此换取系统极高的性能。

比喻¶

想象你请了三家供应商（订单、库存、账户）分别给你送货，约定「要么三家一起送到，要么三家都不送」。结果两家送到了，第三家路上车坏了（宕机）。你想让前两家把货退回去——但他们各自都在自己的仓库里，你没法一个电话同时指挥三家（本地事务管不到别的库）。这时候你就需要一个「总调度」（分布式事务协调者）来统一指挥。

而「能绕开就绕开」的智慧在于：如果你只是需要一个结果（比如一天内三家都送到就行，不要求同一秒送到），那就别搞这么复杂的总调度，让三家各自送，送完互相通知确认（消息队列最终一致性）就够了。

面试怎么答¶

  1. 给结论：跨服务调用、或跨数据库（分库分表）操作，要保证数据完全一致时，需要分布式事务。
  2. 讲经典电商例子：订单 + 库存 + 账户三个库，本地事务只能回滚自己的库，无法隔空撤销其他服务已提交的操作。
  3. 补上权衡观点（加分项）：强一致事务太重、扛不住高并发，所以大部分场景用 MQ 做最终一致性，只有对钱强一致的场景才用强一致方案——体现你「懂取舍」，不是只会背方案。

2. 分布式事务的解决方案你知道哪些？¶

一句话回答¶

主流的六大方案是：2PC、3PC、TCC、Saga、消息队列（可靠消息最终一致性）、本地消息表——前两个是强一致性，后四个是最终一致性，从「一致性、性能、复杂度、适用场景」四个维度来选型。

展开讲：先看总览表¶

方案 一致性 性能 复杂度 适用场景
2PC 强一致性 低 中 传统数据库、XA 协议（金融转账）
3PC 强一致性 中低 高 需减少阻塞的强一致场景
TCC 最终一致性 高 高 高并发业务（支付、库存）
Saga 最终一致性 中 高 长事务、跨服务流程（旅游订单）
消息队列 最终一致性 高 中 事件驱动架构（订单支付）
本地消息表 最终一致性 中 低 异步通知（订单-积分）

方案一：两阶段提交（2PC）¶

原理：引入一个「协调者」，分两个阶段：

  1. 准备阶段：协调者向所有参与者发送准备请求，参与者执行事务操作（但不提交），并把结果（成功/失败）反馈给协调者。
  2. 提交阶段：协调者收集反馈——如果所有参与者都准备就绪，就发送提交请求，参与者执行真正的提交；只要有一个参与者失败，就发送回滚请求，所有参与者回滚。

优点：实现简单，能保证事务强一致性。

缺点：

  • 同步阻塞：准备阶段参与者要一直持有资源锁等待协调者指令，其他事务都被堵住，并发性能极低；
  • 单点故障：协调者挂了，整个事务流程卡死；
  • 网络异常时可能出现「协调者已让部分节点提交，但另一个节点没收到指令」的不一致。

适用场景：对一致性要求高、并发度低的场景，如金融系统转账业务（传统 XA 协议就是这个思路）。

方案二：三阶段提交（3PC）¶

原理：在 2PC 的基础上，把「准备阶段」拆成「询问阶段」和「准备阶段」，形成三个阶段：

  1. 询问阶段（CanCommit）：协调者先问所有参与者「你们能不能执行这个事务？」——只是问，不做事；
  2. 准备阶段（PreCommit）：参与者都回答能，才让它们真正执行事务操作并反馈结果；
  3. 提交阶段（DoCommit）：与 2PC 的提交阶段类似。

另外引入了超时机制：参与者在等待协调者指令超时后，会自动提交（默认不再无限期阻塞等待）。

优点：降低了参与者的阻塞时间，提高了并发性能；超时机制一定程度解决了协调者单点故障问题。

缺点：无法完全避免数据不一致——极端网络情况下仍可能出现部分节点提交、部分节点回滚。

适用场景：对并发性能有要求、对数据一致性要求相对较低的场景。

方案三：TCC（Try-Confirm-Cancel）¶

原理：把每个业务操作拆成三个阶段，由开发者手动实现三个方法：

  1. Try（预留）：预留业务资源。比如下单时先把库存「预占」住，但不真正扣减；把钱「冻结」起来，但不真正划走。
  2. Confirm（确认）：全局事务都 Try 成功后，确认执行——把预留的资源真正扣减/划走。
  3. Cancel（取消）：某个 Try 失败时，对已预留的资源做补偿——释放预占的库存、解冻资金。

优点：可根据业务场景定制开发，性能较高，资源占用时间短（Try 阶段才持锁，Confirm/Cancel 很快）。

缺点：开发成本极高——每个参与方都要实现三个方法，还要处理各种异常和补偿逻辑。

适用场景：对性能要求高、业务逻辑复杂的场景，如电商系统的订单处理、库存管理。

方案四：Saga¶

原理：把一个长事务拆成多个短事务，每个短事务都有一个对应的补偿事务（反向操作）。执行顺序是正向的短事务链，一旦某个短事务失败，就按相反顺序执行之前所有短事务的补偿事务，把系统状态回滚回去。

比如旅游预订：订机票 → 订酒店 → 订门票。如果门票订失败了，就依次取消酒店、取消机票（各自有对应的退款补偿操作）。

优点：性能较高（短事务可以并行执行）；对业务侵入性小，只需要额外实现补偿事务，不需要像 TCC 那样写 Try/Confirm/Cancel 三个方法。

缺点：只能保证最终一致性（补偿期间数据是中间状态）；如果某个补偿事务本身也失败了，可能导致系统状态不一致，需要额外的重试/人工介入。

适用场景：业务流程长、对一致性要求为最终一致性的场景，如旅游系统的机票、航班、酒店预订。

方案五：可靠消息最终一致性（基于消息队列）¶

原理：业务系统执行本地事务时，把「要做的业务操作」封装成一条消息发到消息队列（MQ）；下游系统消费这条消息并执行自己的操作；如果下游执行失败，MQ 会重试，直到成功。

优点：实现简单，对业务代码修改小，系统耦合度低（上游发消息、下游收消息，互不直接调用），能保证最终一致性。

缺点：消息队列的可靠性和性能影响整个方案；可能出现消息丢失或延迟；必须处理消息幂等性（下游可能收到重复消息，重复执行会出错）。

适用场景：对一致性要求为最终一致性、系统耦合度低的场景，如电商订单支付、库存扣减。

方案六：本地消息表¶

原理：业务操作和消息存在同一个数据库里，利用本地事务保证两者同时成功或同时失败：

  1. 业务操作 + 写一条「待发送消息」到本地消息表，放在同一个本地事务里提交（保证一致性）；
  2. 后台有一个任务，定时轮询本地消息表，把未发送的消息发到 MQ，通知下游服务；
  3. 下游服务消费成功后，回执确认；失败则重试。

优点：简单可靠，无外部依赖（只有数据库 + MQ）。

缺点：消息可能重复消费，需要幂等设计；多了一条消息表和轮询任务，有一定开发量。

适用场景：异步最终一致性，如订单创建后通知积分服务。

面试怎么答¶

  1. 先亮总览表（一致性 / 性能 / 复杂度 / 适用场景四维度），说明这是「选型问题」不是「背诵问题」。
  2. 重点展开 2PC（两阶段原理必须讲清：准备 + 提交，全成功才提交、有失败就回滚）和 TCC（Try 预留 / Confirm 确认 / Cancel 补偿），这两个是最高频考点。
  3. 强一致方案（2PC/3PC）讲缺点时突出「阻塞、锁资源、性能低」；最终一致方案（TCC/Saga/MQ/本地消息表）突出「性能好但要幂等/补偿」。
  4. 收尾给选型逻辑：对钱强一致 → 2PC/Seata AT；高并发业务 → TCC；长流程 → Saga；解耦异步 → MQ 或本地消息表。

3. 阿里的 Seata 框架了解过吗？¶

一句话回答¶

Seata 是阿里开源的分布式事务解决方案，核心思想是「全局事务通过协调者统一管理各分支事务」，支持 AT、TCC、SAGA、XA 四种模式——其中最常用的是 AT 模式，它对业务代码几乎零侵入。

展开讲¶

Seata 的整体架构有三个角色：

  • TC（Transaction Coordinator，事务协调者）：独立的服务，维护全局事务的运行状态，负责协调和驱动全局提交/回滚（Seata-server）；
  • TM（Transaction Manager，事务管理器）：业务应用里的组件，负责开启、提交、回滚全局事务；
  • RM（Resource Manager，资源管理器）：管理各分支事务（各个微服务里的本地事务），向 TC 报告分支状态。

AT 模式（Seata 默认模式，最常用）¶

基于支持本地 ACID 事务的关系型数据库。它的巧妙之处在于自动生成回滚日志：

  • 在业务 SQL 执行前，记录数据的前镜像（执行前的快照）；
  • 在业务 SQL 执行后，记录数据的后镜像（执行后的快照）；
  • 当全局事务需要回滚时，根据回滚日志把数据恢复成事务开始前的状态（用前镜像覆盖回来）。

整个过程对业务代码零侵入——你只需要在方法上标一个全局事务注解，剩下的交给框架。这也是它最受欢迎的原因。

不过要留意：AT 模式用的是「补偿式」回滚（不是数据库层面的真正回滚），所以要求全局事务里的分支都是可补偿的（依赖快照反推），并且事务期间相关数据不能被其他事务改动（有全局锁机制防脏写）。

TCC 模式¶

需要开发者手动编写 Try、Confirm、Cancel 三个方法：

  • Try：对业务资源进行预留（如冻结库存、冻结资金）；
  • Confirm：确认资源并完成业务操作；
  • Cancel：业务执行失败时释放预留的资源。

相比 AT 模式，TCC 不依赖数据库快照、不受数据库类型限制，性能更好，但开发成本高（每个参与方都要写三个方法）。

SAGA 模式¶

将一个长事务拆分为多个短事务，每个短事务有对应的补偿事务（反向操作）。某个短事务失败时，按相反顺序执行之前短事务的补偿事务，回滚系统状态。适合业务链路特别长的场景（如完整的订票+订房+订车流程）。

怎么选？¶

模式 侵入性 性能 适用场景
AT 几乎零侵入（自动快照） 中 常规业务，Seata 默认首选
TCC 高（手写三个方法） 高 对性能敏感、资源预留型业务
SAGA 中（写补偿事务） 中 超长业务链路

比喻¶

Seata 就像一个全局交警（TC）：每个路口的车（各服务的本地事务/RM）怎么走，都要听他的统一调度。他说「全体通过」（全局提交），所有路口一起放行；他说「全体停下」（全局回滚），所有路口各回各位（AT 模式靠快照恢复原状，TCC 靠 Cancel 补偿，SAGA 靠反向执行补偿事务）。

AT 模式尤其贴心：每个路口的车都装了「行车记录仪」（前后镜像快照），交警说回滚时，记录仪里的画面（前镜像）直接把路面恢复原样——司机（业务代码）什么都不用做。

面试怎么答¶

  1. 先讲 Seata 三角色：TC（协调者）/ TM（事务管理器）/ RM（资源管理器），一句话说清分工。
  2. 重点讲 AT 模式：前后镜像快照 + 全局回滚，对业务零侵入——这是 Seata 最出名的卖点。
  3. 简要对比 TCC（手写三方法、性能高、侵入高）和 SAGA（补偿事务、适合长链路）。
  4. 如果被追问，可以提 AT 模式的局限（依赖可补偿的数据、全局锁有性能代价），以及 XA 模式的存在（Seata 也支持传统 XA）——显得你用过不止一个模式。

本章小结（背诵卡片）¶

问题 一句话答案
什么时候用分布式事务 跨微服务调用、或跨数据库（分库分表）操作需要数据完全一致时；但能绕开尽量绕开，多数场景用 MQ 做最终一致性
2PC 协调者两阶段（准备+提交），全成功才提交、有失败就回滚；强一致但阻塞、性能低、有单点故障
3PC 2PC 加一个询问阶段 + 超时机制；减少阻塞但极端情况下仍可能不一致
TCC Try 预留 / Confirm 确认 / Cancel 补偿，三个方法手写；性能高、资源占用短、开发成本高
Saga 长事务拆短事务 + 补偿事务反向回滚；适合长链路，只保证最终一致性
消息队列 本地事务成功后发消息，下游消费失败靠 MQ 重试；解耦但要注意幂等
本地消息表 业务和消息同库同事务，后台轮询发消息；简单可靠无外部依赖，消息可能重复消费
Seata 阿里开源，TC/TM/RM 三角色；AT 模式（前后镜像自动回滚、零侵入）最常用，另有 TCC / SAGA / XA 模式
