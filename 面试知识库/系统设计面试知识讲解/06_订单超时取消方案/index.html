06 订单超时取消方案¶

本章覆盖：电商系统里"订单下了单但 30 分钟没付款就要自动取消"这个高频面试题的完整解法。你会看到 6 种实现方案——定时轮询、JDK 延迟队列、时间轮算法、Redis 的两种玩法（有序集合 + 键过期监听）、消息队列的两种玩法（延迟队列 + 死信队列），每种方案都会讲清原理、优点、缺点、比喻和适用场景，最后用一张大表横向对比并给出选型建议和"面试怎么答"的话术。

1. 先搞清楚：这是个什么问题？¶

一句话回答¶

用户下单后如果超过 30 分钟没有支付，系统要自动把订单状态改成"已取消"（同时把库存还回去、释放优惠券），核心难题是：怎么让系统在"某个未来的时间点"自动做一件事。

展开讲：问题的本质¶

你平时写代码，都是"来一个请求，处理一个请求"——用户点支付，代码立刻执行支付逻辑，这是一条立刻发生的链路。但"30 分钟后取消订单"不一样：

  • 它不是一个"现在"要执行的动作，而是一个未来某个时刻才要执行的动作；
  • 这个动作不是用户触发的，而是系统自己在后台触发的；
  • 如果只是写死"等 30 分钟再取消"，那这个线程要傻等 30 分钟，什么都干不了——浪费资源。

所以这个问题在计算机里有个专门的称呼：延时任务（也叫延迟任务、定时任务）。它的本质是：把"做什么"（取消订单）和"什么时候做"（30 分钟后）这两个信息存起来，由系统在到点的那一刻自动执行。

比喻：餐馆的等位叫号¶

你去一家火爆的餐馆，服务员给你一张号牌说"大概等 20 分钟"。20 分钟后如果没人喊你的号，你就不知道到底排到了没有——餐厅是怎么保证"到点提醒"的呢？几种做法：

  • 服务员每隔几分钟绕场喊一圈："A12 号！A12 号！"（定时轮询）；
  • 或者给你一个会响的震动叫号器，到点自动响（延迟队列）；
  • 或者门口挂一个大钟，分针转到某一格就处理那一格的任务（时间轮）。

你看，同一个需求，餐馆有不同实现方式，各有优缺点——这就是我们今天要讲的 6 种方案的由来。理解了"延时任务"这个本质，后面的所有方案都是围绕"到点了怎么知道、怎么处理"这两个问题展开的。

2. 方案一：定时轮询（SpringBoot 定时任务扫数据库）¶

一句话回答¶

写一个定时任务，每隔 1 分钟扫描一次订单表，把"创建时间超过 30 分钟且还没支付"的订单批量改成已取消。

展开讲：原理¶

这是最简单、最容易想到的方案，逻辑就是三个步骤：

  1. 定个闹钟：用 SpringBoot 的 @Scheduled 注解，给方法加上执行周期，比如每 60 秒执行一次；
  2. 扫表：每次执行时，用一条 SQL 把"超时未支付"的订单找出来：
update orders set status = 'CANCELLED'
where status = 'PENDING_PAY' and create_time < now() - interval 30 minute
  1. 批量处理：把这些订单状态改成已取消，再异步去释放库存、归还优惠券等。

这段 SQL 是整条链路的灵魂：status = 'PENDING_PAY' 保证只处理待支付订单，create_time < now() - interval 30 minute 保证只处理真正超时的订单，两条条件一起用，天然支持"批量"——一次更新几百上千条都没问题。

展开讲：优点¶

  • 实现极其简单：不引入任何新组件，一个注解 + 一条 SQL 就搞定，新手也能写出来；
  • 直白好理解：逻辑是"扫一遍、改状态"，出问题容易排查；
  • 天然支持批量：一次扫描可以同时取消成千上万条订单，效率并不低。

展开讲：缺点¶

  • 给数据库持续压力：不管有没有超时订单，定时任务每 1 分钟就全表（或按索引）扫描一次订单表。订单量大了以后，这张表可能几千万行，每分钟扫一遍，数据库会被拖垮；
  • 实时性差：订单是"最晚 30 分钟 + 最多 1 个扫描周期"才被取消。比如 13:00:30 下的单，要等 13:30:30 之后的下一次扫描才会被处理，用户可能多等近 1 分钟；
  • 高并发下问题多：如果定时任务跑得慢，上一次还没扫完下一次又启动了，会出现任务重叠，多个线程同时改同一批订单，引发并发问题；为了防重叠又要加分布式锁，复杂度就上来了。

比喻：保安巡逻¶

就像小区保安每 10 分钟巡逻一圈，发现谁家门前堆了垃圾超时没扔，就顺手处理掉。优点是不用装任何设备，保安转一圈就行；缺点是：垃圾可能已经在门口堆了 9 分 59 秒才被发现（实时性差），而且不管有没有垃圾，保安都得一直转圈（白费力气，数据库就是那个一直在被"巡逻"的小区）。

适用场景¶

小型项目、内部系统、订单量不大的场景。比如公司内部的一个请假审批系统，或者日订单量只有几百单的小型商城，用这个方案完全够用，性价比最高。

3. 方案二：JDK 延迟队列（DelayQueue）¶

一句话回答¶

下单时把订单塞进 DelayQueue（JDK 自带的一个延迟队列），并告诉它"30 分钟后叫我"，队列到点会自动把订单取出来交给线程处理取消。

展开讲：原理¶

DelayQueue 是 Java 里现成的类，它内部维护了一个优先级队列（底层是最小堆），队头永远是"离到期时间最近"的那个元素。用法三步：

  1. 下单时入队：把订单封装成一个实现了 Delayed 接口的对象，getDelay() 返回"距离到期还剩多少毫秒"，比如现在入队就返回 30 分钟；
  2. 消费者阻塞取：一个后台线程不断调用 queue.take()，这个方法会一直阻塞，直到队头元素到期才返回——到点了，订单被自动取出；
  3. 取出后处理：拿到订单执行取消逻辑（改状态、释放库存）。

关键点在于：take() 不是傻等 30 分钟，而是"精确地等到下一个到期时间"——队头还有 3 分钟到期就等 3 分钟，还有 30 分钟就等 30 分钟。到期的订单是按到期时间先后一个个精确取出的，一秒不差。

展开讲：优点¶

  • 内部数据结构高效：最小堆的插入和取队头都是 O(log n)，处理几十万订单也不吃力；
  • 线程安全：DelayQueue 内部做好了并发控制，多个线程可以安全地往里放、往外取，不用自己加锁；
  • 减少数据库访问：订单在内存里排着队，到点才取出，不像方案一那样每 1 分钟扫一遍数据库。

展开讲：缺点¶

  • 内存消耗大：所有"还没到期的订单"都必须一直待在内存里。假设一天有 100 万订单，其中 30 万在排队等取消，就要在内存里维护 30 万个对象，内存占用非常可观；
  • 无持久化，崩溃丢数据：订单只存在内存里，进程一重启、一崩溃，队列里的订单全部丢失——没有订单会被取消，用户会一直看到"待支付"的僵尸订单；
  • 单机局限：DelayQueue 是 JVM 进程内的东西，多个应用实例之间不共享，没法直接做分布式扩展（当然可以用分布式锁硬做，但很别扭）。

比喻：闹钟和预约提醒¶

就像你手机里的闹钟/预约提醒：设好 30 分钟后响，手机到点就响，提醒得很精准。但它有个致命问题：手机没电关机（进程崩溃），所有闹钟全部失效；而且你设的闹钟越多，手机里存的提醒条目越多，太占地方（内存）。

适用场景¶

单机应用、订单量可控、能接受重启丢失的小型系统。如果你的服务只有一台机器，且主要诉求是"比轮询更精准、数据库压力小"，这个方案可以快速落地。

4. 方案三：时间轮算法（Timing Wheel）¶

一句话回答¶

把时间想象成一个环形钟表，每个刻度是一个"槽"，每个槽挂着一串到点任务；指针每走一格，就把这一格上的任务全部取出来执行。

展开讲：原理¶

时间轮的核心是一个环形数组，比如一圈 60 个槽（像秒表的 60 个刻度），指针每秒走一格：

  1. 插入任务：任务要延迟 35 秒执行，当前指针在第 5 格，就把它挂到第 (5 + 35) % 60 = 40 格上——挂上就行，不用排序；
  2. 指针转动：一个后台线程驱动指针每秒走一格（也可以走一圈、走一轮），走到第 40 格时，把这一格上挂的一串任务全部取出来执行；
  3. 圈数问题：如果延迟时间超过一圈（比如延迟 90 秒），就记录"第 2 圈"执行——每走完一圈，任务上的圈数减 1，减到 0 的那一圈到点时执行。

所以时间轮的本质是：把"排序"换成了"放格子"。传统延迟队列要维护一个堆，插入要排序；时间轮直接按"当前刻度 + 延迟"算出一个槽位挂进去，插入是 O(1)，指针转动取任务是 O(1)，效率极高。处理海量定时任务时优势非常明显。

展开讲：优点¶

  • 实现简单：就是一个环形数组 + 一个指针 + 每格一个任务链表，几十行代码能写出来；
  • 执行效率高：插入和取出都是常数级时间，比堆排序快，能扛海量定时任务；
  • 有成熟实现库：不用自己造轮子，Netty 的 HashedWheelTimer、Kafka、Dubbo 内部都有时间轮的成熟实现，直接拿来用就行。

展开讲：缺点¶

  • 内存占用：任务同样全部驻留在内存里，量大了内存吃不消；
  • 崩溃丢数据：和 DelayQueue 一样，进程一挂，轮子上的任务全没了，没有持久化；
  • 精度受刻度影响：刻度越大（比如一格 1 秒），精度越粗，可能延迟几秒才执行——对"取消订单"这种业务来说精度够用，但对某些需要毫秒级精确的业务就不行。

比喻：钟表 + 每格挂任务单¶

想象一个大挂钟，每个刻度上钉着一排挂钩，每挂钩上挂一张任务单。你接到一个新任务，看一眼现在分针指到哪，算好 35 分钟后分针会走到哪个刻度，直接把任务单挂到那个刻度上——不用排序，不用比较。分针每走一格，管理员就把这一格上的任务单全部摘下来处理掉。转得快、处理快，但所有任务单都挂在钟面上（内存），钟一坏（进程崩溃），任务单全散落一地，谁也不知道该干什么了。

适用场景¶

高吞吐、海量定时任务的中间件内部（如 Netty 的连接超时检测、Kafka 的延迟操作），或者对"丢失可接受"的延迟任务场景。订单取消单独用它的不多，但它"格子化"的思想是延迟队列类方案的基础，面试官常拿它考原理。

5. 方案四：用 Redis 实现¶

Redis 在缓存之外，还常被当成"延迟任务的中转站"。这一节有两种玩法：方案 A 用有序集合轮询、方案 B 用键过期监听。

5.1 方案 A：有序集合（Sorted Set）轮询¶

一句话回答¶

把订单 ID 存进 Redis 的 ZSet，把"到期时间戳"作为 score，另起一个定时任务每隔一段时间用 zrangebyscore 把到期的订单捞出来取消。

展开讲：原理¶

ZSet（有序集合）每个成员带一个分值 score，天然支持"按分值排序"和"按分值区间取数"，用来做延迟任务简直是为它量身定做的：

  1. 下单时写入：zadd order:delay 到期时间戳 订单ID——比如 13:00 下单，到期时间是 13:30:00，就写入 zadd order:delay 13:30:00 订单1001；
  2. 定时扫描：一个定时任务每隔几秒执行 zrangebyscore order:delay 0 当前时间戳，把"score 小于等于当前时间"的订单全部取出来——凡是能取出来的，都是已经到期的；
  3. 处理并删除：对取出的订单执行取消逻辑，然后 zrem order:delay 订单ID 把它从集合里删掉，防止重复处理。

这套组合拳的关键是：到期时间被编码成分值，数据库的"扫描订单表"变成了 Redis 的"按分值取数"，扫描成本从"全表扫"降为"区间取数"，快好几个数量级。

展开讲：优点¶

  • 查询效率高：zrangebyscore 按分值区间取数，底层是跳表，百万级数据也是毫秒级返回；
  • 分布式环境可用：Redis 是独立服务，多个应用实例都可以读写同一个 ZSet，天然支持多机部署（配合分布式锁防重复处理即可）；
  • 减少数据库压力：扫描发生在 Redis 里，数据库只在"真正要取消订单"时才被访问。

展开讲：缺点¶

  • 依赖定时任务的频率：还是"轮询"思路，实时性受扫描间隔限制——扫得越勤越快，但 Redis 请求量越大，两者要权衡；
  • 事务一致性需额外处理：多个实例同时扫到同一批订单时，会重复执行取消逻辑，需要"取出即删除"或加分布式锁来保证幂等；
  • 多一个组件：系统里多了 Redis 这个依赖，如果 Redis 挂了，延迟任务也就停摆了（好在订单数据本身还在数据库里，可以兜底）。

比喻：银行叫号屏¶

就像银行大厅的叫号屏：每位客户取号时，系统记住他"应被叫到的时刻"，每隔几秒屏幕就刷新一次，把"当前时刻及以前到号"的客户叫出来。屏幕每刷新一次（定时轮询），就有一批新到号的客户被处理。刷新太快浪费电，太慢客户等得久——频率是核心权衡点。

适用场景¶

已经有 Redis 基建、订单量中等、可接受秒级延迟的系统。这是"内存方案"和"持久化方案"之间的折中：比 DelayQueue 抗崩溃（订单记录在 Redis 里而不是 JVM 里），比纯轮询数据库轻量。

5.2 方案 B：Key 过期监听（键空间通知）¶

一句话回答¶

下单时往 Redis 里写一个"30 秒过期"的 key，开启 keyspace notifications 监听过期事件，key 一过期，Redis 就发布事件，我们的代码订阅到事件后执行取消。

展开讲：原理¶

Redis 从 2.8 版本开始支持键空间通知（keyspace notifications）：当某个 key 发生事件（增、删、改、过期）时，Redis 会向订阅了相关 channel 的客户端推送一条消息。利用这一点：

  1. 配置开启：在 Redis 配置里把 notify-keyspace-events 设为 Ex（E 表示键事件、x 表示过期事件）；
  2. 下单时写 key：set order:1001 1 ex 1800——key 是 订单ID，ex 1800 表示 1800 秒（30 分钟）后过期；
  3. 订阅过期事件：业务代码里订阅 channel __keyevent@0__:expired（0 号库的过期事件）；
  4. 收到事件即取消：一旦 key 到期，Redis 推送事件，订阅方收到 order:1001 这个 key 名，就知道"订单 1001 该取消了"，执行取消逻辑。

看起来非常优雅：订单什么时候过期，Redis 什么时候通知我们，实时性拉满。

展开讲：Redis 的过期删除机制（关键背景知识）¶

但这里藏着一个大坑——Redis 删除过期 key 有两种策略：

  • 定期删除：Redis 每隔一段时间（默认 100ms）随机抽查一部分设置了过期时间的 key，把其中已过期的删掉；
  • 惰性删除：当一个 key 被访问时，才检查它是否过期，过期了才删。

问题在于：这两种策略都不能保证"key 一到过期时间就立刻被删除"。如果一个 key 过期后一直没人访问，就可能一直躺在内存里，直到下一次定期删除的随机抽查扫到它——这个间隔可能是几十毫秒，也可能是几百毫秒甚至更久。而过期事件是在"key 真正被删除的那一刻"才发布的。所以：

key 过期的时刻 ≠ 收到过期通知的时刻，两者之间有一段不确定的延迟。

这就是 keyspace notifications"不确定性"的根源：通知会迟到，但不会不到。对"30 分钟取消订单"这种分钟级业务来说，晚几百毫秒完全无所谓；但如果业务要求毫秒级精确，这个方案就不合适。

展开讲：优点¶

  • 实时性好：key 一被真正删除就触发通知，比"定时轮询"（无论轮询数据库还是轮询 ZSet）都快；
  • 资源消耗少：不需要额外的定时任务线程，Redis 自己管过期，业务侧只有一个监听器；
  • 支持高并发：下单只是写一个 key，Redis 写性能极高，扛得住大流量。

展开讲：缺点¶

  • 对 Redis 依赖性强：事件推送依赖 Redis 进程本身，Redis 重启、主从切换期间的事件可能丢失；
  • 极端情况可能成瓶颈：大量 key 同时过期，Redis 要同时发布大量事件，订阅方（消费者）可能处理不过来，事件积压；
  • 过期的不确定性：如上所述，惰性删除导致通知可能延迟；另外还有两个经典坑——订阅端要自己保证幂等（事件可能重复投递），以及 Redis 6.0 之前过期事件不保证精确投递（可能丢失，官方文档明确提示"事件不可靠，可作为辅助手段"）。

5.3 两种 Redis 方案小结¶

  • 方案 A（ZSet 轮询）本质还是"主动去查"，实时性取决于扫描频率，但结果可靠、可控；
  • 方案 B（过期监听）本质是"被动等通知"，实时性好，但通知本身有不确定性；
  • 生产上常用组合拳：过期监听为主、ZSet 兜底定期补偿扫描，把两种方案的缺点互相补掉。

6. 方案五：用消息队列（MQ）实现¶

消息队列（MQ）本身就是"生产者把消息交给队列，消费者异步处理"的架构，天然适合延迟任务。这一节有两种主流玩法。

6.1 方案 A：延迟队列（延迟消息）¶

一句话回答¶

下单时往 MQ 发一条"延迟 30 分钟"的消息，消息在队列里躺满 30 分钟才会被投递给消费者，消费者收到消息就执行取消。

展开讲：原理¶

以 RabbitMQ 的官方延迟插件 rabbitmq_delayed_message_exchange 为例：

  1. 安装插件：给 RabbitMQ 装上延迟消息插件，声明一个 x-delayed-message 类型的交换机（交换机 = 快递分拣中心）；
  2. 发消息时指定延迟：生产者发送消息时带上 x-delay: 1800000（30 分钟，单位毫秒）；
  3. 插件代为保管：消息进入交换机后不会立刻被路由到队列，而是被插件扣住，开始倒计时；
  4. 到点投递：倒计时结束，插件才把消息投递到绑定的队列，消费者正常消费——到点执行取消逻辑。

对业务方来说，发送的还是一条普通消息，只是多了一个"延迟"属性，消费端完全无感知，代码改动极小。

展开讲：优点¶

  • 处理高效、异步执行：下单请求只要把消息发出去就立即返回，取消逻辑完全异步，不阻塞主流程；
  • 易扩展：MQ 本身就是分布式组件，队列可以横向扩展，消费能力不足就加消费者实例；
  • 模块化、解耦：订单服务和取消服务通过 MQ 解耦，订单服务只负责"发消息"，取消逻辑由独立消费者负责，谁挂了都不影响对方。

展开讲：缺点¶

  • 依赖 MQ 服务：系统里多了一个必须稳定运行的中间件，MQ 挂了大面积业务受影响；
  • 配置复杂度增加：要装插件、配交换机、配队列、配消费者，还要处理消息确认（ACK）和重试；
  • 消息丢失/延迟风险：MQ 本身是"至少一次"投递语义，可能丢消息（要配持久化）、可能重复投递（要幂等）、极端情况下可能延迟；
  • MQ 与数据库的一致性：最麻烦的一点——如果"消息发出去了，但订单取消时数据库更新失败"，两边就对不上了，需要引入"本地消息表 + 定时补偿"或事务消息来兜底，复杂度再上一个台阶。

比喻：快递柜的定时取件¶

就像快递柜的定时存放：你把快递（消息）放进柜子，设定 30 分钟后才通知收件人（消费者）。柜子（插件）负责计时，到点自动给收件人发取件码。好处是放进去就不用管了，柜子自动处理；坏处是柜子系统（MQ）必须一直在线，而且万一快递在柜子里丢了（消息丢失）、或者通知发了两遍（重复投递），收件人那边就要自己处理。

适用场景¶

已经有 MQ 基建的中大型系统。这是目前生产环境最主流的订单超时取消方案之一，尤其适合"下单、支付、取消"链路都依赖 MQ 解耦的微服务架构。

6.2 方案 B：死信队列（TTL + 死信交换机）¶

一句话回答¶

给队列设置消息存活时间 TTL（比如 30 分钟），消息超时后没人消费，就会被"扔掉"到死信交换机，由专门监听死信队列的消费者捡起来执行取消。

展开讲：原理——TTL 和死信交换机怎么联动¶

先解释两个名词：

  • TTL（Time To Live，存活时间）：消息在队列里的"保质期"。可以给整个队列设统一 TTL，也可以给单条消息设 TTL。超过 TTL 还没被消费的消息，就被判定为"过期"；
  • 死信交换机（DLX，Dead Letter Exchange）：消息变成"死信"后要去的"垃圾回收站"。死信有几种来源：消息被拒绝（basic.reject/nack 且不重新入队）、消息过期（超过 TTL）、队列长度满了。

联动流程（这就是"TTL 把过期消息扔给死信交换机"的完整链路）：

  1. 声明两个队列：正常队列 order.delay.queue（设 x-message-ttl: 1800000，30 分钟过期；并声明它的死信交换机为 order.dlx），死信队列 order.cancel.queue 绑定在死信交换机 order.dlx 上；
  2. 下单发消息：订单服务把订单消息发到正常队列，消息开始 30 分钟倒计时；
  3. 到点变死信：30 分钟内如果没有任何消费者取走它（正常业务里这个队列就是没人消费的，纯用来计时），RabbitMQ 判定消息过期，把它作为"死信"转发到 order.dlx；
  4. 死信消费者处理：监听 order.cancel.queue 的取消服务收到消息，执行订单取消——此时距离下单正好约 30 分钟。

再强调一次联动本质：正常队列只管"计时"（TTL），死信交换机负责"转运"，死信消费者负责"执行"——三个角色各司其职，拼成一条流水线。你甚至可以给不同订单设置不同的 TTL（单条消息设 TTL），实现"这个订单 30 分钟取消、那个订单 1 小时取消"。

展开讲：优点¶

  • 能捕获、隔离异常消息：除了 TTL 超时，消息被消费方拒绝也会进死信队列——相当于给系统加了一个"异常消息回收站"，方便排查问题；
  • 业务逻辑分离：正常业务队列和取消处理队列完全分离，取消逻辑的变更不影响正常业务；
  • 方便追踪分析：死信队列里能看到"哪些订单过期了、什么时候过期的"，天然留痕，方便监控和统计。

展开讲：缺点¶

  • 处理不够精确：消息 TTL 的计时是从"消息进入队列"开始的，但如果队列里前面有大量消息堆积，后面的消息实际消费时间可能远超 TTL（消息是排队的），取消时间会偏晚；
  • 配置复杂：TTL、死信交换机、死信路由 key、绑定关系，配置项多，新手容易配错；
  • 完整性和一致性问题：消息从正常队列"搬运"到死信队列的过程中若 RabbitMQ 异常，消息可能丢失；且"取消订单"和"数据库更新"之间同样存在一致性风险（同 6.1 的缺点）。

比喻：超市的临期商品货架¶

超市里有一排临期商品货架：刚上架的商品（消息）放在普通货架并贴了保质期标签（TTL），没人买（没人消费）到保质期（TTL 到点），理货员就把它们搬到打折处理区（死信队列），由专门的收银员（死信消费者）来降价处理（取消订单）。好处是过期商品有专门的地方回收、好统计；坏处是如果普通货架堆货太多，排在后面的商品实际被搬走的时间会比保质期晚不少（消息堆积导致延迟）。

适用场景¶

已有 RabbitMQ 且版本低于 3.13（官方延迟插件不可用或不想装插件）、或者希望"顺带获得死信回收能力"的系统。它是延迟队列插件的"穷兄弟"，不用装额外插件，纯靠 RabbitMQ 原生能力就能实现。

8. 选型建议：到底用哪个？¶

一句话回答¶

没有绝对最好的方案，只有最适合的。看订单量、看现有基建、看团队维护能力：小项目用定时轮询，中大型项目优先选 MQ 延迟队列/死信队列，中间过渡可用 Redis ZSet。

展开讲：按场景选¶

  • 日订单量小（几千单）、团队小、追求最快上线：直接上定时轮询，成本最低，够用就行；
  • 单机应用、想改善实时性、能接受重启丢任务：上 JDK DelayQueue 或时间轮，代码量小；
  • 已有 Redis、订单量中等、可接受秒级延迟：Redis ZSet 轮询是性价比之选，比内存方案抗崩溃，比纯数据库轮询轻量；
  • 对实时性要求高、愿意多花钱：Redis 过期监听，但记得配 ZSet 定期补偿兜底（生产组合拳）；
  • 中大型电商、微服务架构、已有 MQ：MQ 延迟队列是主流答案——异步、可扩展、解耦，和整个微服务体系契合；
  • 用的是老版本 RabbitMQ、不想装插件：死信队列方案顶上，还能白捡一个"死信回收"能力。

现代大型系统的主流选择¶

现代大型电商系统（订单量大、要求高可用）几乎不会选"内存方案"和"数据库轮询"，主流是 MQ 延迟队列 / 死信队列，原因三条：

  1. 异步处理：下单请求发消息即返回，取消逻辑后台异步执行，主链路零阻塞；
  2. 资源优化：不占应用内存、不频繁扫数据库，压力都转移到了 MQ 这个专门干这活的组件上；
  3. 扩展性：队列可水平扩展，订单量翻倍就加消费者实例，架构上不用改。

面试怎么答¶

推荐按这个节奏答（3 层递进，体现层次感）：

第一层（概括）：订单超时取消本质是"延时任务"，常见实现有 6 种：数据库定时轮询、JDK DelayQueue、时间轮、Redis ZSet 轮询、Redis 键过期监听、MQ 延迟队列（含死信队列）。

第二层（主流选择）：现代大型系统通常选 MQ 延迟队列或死信队列方案，因为它是异步处理、不占内存、可水平扩展，和微服务架构天然契合；Redis 方案可以作为补充或过渡。

第三层（落地视角）：如果公司已经有 RabbitMQ 基建，就用延迟队列插件（rabbitmq_delayed_message_exchange），配置简单；如果是老版本 MQ，就用 TTL + 死信交换机实现；同时无论选哪个，都要配合订单状态机和幂等处理，防止"取消"和"支付"并发打架。

这样答既有广度（6 种方案都提到）、有深度（能说清原理和权衡）、还有落地感（结合公司基建），面试官很难挑出毛病。

9. 补充：真实业务里的两个关键配套¶

光有"到点取消"还不够，真实业务里还有两个配套细节几乎必问。

9.1 订单状态机¶

订单不能随便改状态，要按状态机流转：待支付 → 已支付 或 待支付 → 已取消。状态机的意义是把"允许的转换"定义死：

  • 只有 待支付 的订单才能被取消，已支付 的订单取消要进退款流程；
  • 只有 待支付 的订单才能被支付成功，已取消的订单不能再支付（提示"订单已失效"）。

用一张表表示允许的转换：

当前状态 允许的下一个状态 触发动作
待支付 已支付 用户支付成功
待支付 已取消 超时自动取消 / 用户主动取消
已支付 退款中 → 已退款 用户申请退款

比喻：就像红绿灯——灯只能按 红→绿→黄→红 的顺序变，不能从"红"直接跳到"黄"以外的乱序状态，否则路口就乱了。状态机就是订单的"交通规则"。

9.2 幂等处理：防止"取消"和"支付"打架¶

最经典的并发场景：订单 13:29:59 到 30 分钟期限，取消任务和用户点击支付几乎同时发生：

  • 取消任务把订单改成"已取消"，用户支付也成功了 → 钱付了，订单却是取消状态，两边打架；
  • 或者两个取消任务同时执行，重复取消、重复释放库存 → 库存被多还一次。

解决思路：

  • 状态机兜底：取消前检查订单状态必须是"待支付"，且"改状态"用带条件的 SQL：update orders set status='CANCELLED' where id=? and status='PENDING_PAY'——只有一条更新成功，谁先执行谁生效，后执行的因为状态已变而更新 0 行，自然失败；
  • 幂等设计：取消逻辑本身要幂等——"取消一个已取消的订单"不报错、不重复扣库存（库存归还用唯一流水号防重）；
  • 分布式锁：以订单 ID 为锁 key，取消和支付都先抢锁，抢到才执行，串行化同一订单的操作。

比喻：就像两个人同时要改同一份合同——先到的人用笔把"生效中"划掉改成"已作废"，后到的人发现合同状态已经变了，就自动收手，不会把合同撕两遍。where status='PENDING_PAY' 这个条件就是"先到先得"的保证。

本节小结¶

订单超时取消的本质是"延时任务"：从最简单的数据库定时轮询，到内存方案（DelayQueue、时间轮），到 Redis 两招（ZSet 轮询、键过期监听），再到生产主流的 MQ 延迟队列与死信队列——实时性、资源占用、可靠性、复杂度四者不可兼得，选型要看订单量、现有基建和团队能力；面试时按"概括 6 种方案 → 说主流选 MQ 及原因 → 补落地细节（公司基建 + 状态机 + 幂等）"三层回答即可。
