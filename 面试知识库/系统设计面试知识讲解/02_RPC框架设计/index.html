02 RPC 框架设计¶

本章覆盖：RPC 的核心目标（让远程调用像本地调用一样简单）、六大模块拆解（动态代理、序列化与通信协议、Netty 网络底座、服务注册与发现、负载均衡与容错、SPI 插件化扩展），以及一次完整 RPC 调用从客户端到服务端的「旅途」串讲。类比 Dubbo、gRPC 等业界框架。

1. RPC 是什么？它的核心目标是什么？¶

一句话回答¶

RPC（Remote Procedure Call，远程过程调用）的核心理念是：让业务开发人员调用远端服务，就像调用本地方法一样简单——不用关心网络、不用关心序列化、不用关心对方在哪台机器上，一切「无感」。

展开讲：没有 RPC 的世界有多痛苦¶

假设你在写一个订单系统，需要调用「用户服务」查用户信息。用户服务部署在另一台服务器上，如果不用 RPC，你得自己写：

// 没有 RPC 的写法：每一步都要自己操心
// 1. 自己建立网络连接
Socket socket = new Socket("192.168.1.100", 8080);
// 2. 自己把参数转成二进制（序列化）
byte[] data = serialize("getUserById", userId);
// 3. 自己拼协议格式、发出去
socket.getOutputStream().write(data);
// 4. 自己收响应、自己解析（反序列化）
byte[] resp = socket.getInputStream().readAllBytes();
User user = deserialize(resp);
// 5. 自己处理网络异常、重试、超时……

这只是调用一个方法的代码！如果系统里有几十个服务互相调用，每个调用都要重复写这一大堆——代码爆炸、极易出错、没法维护。

展开讲：有了 RPC 的世界有多幸福¶

有了 RPC 框架之后，业务代码变成这样：

// 有 RPC 的写法：像调用本地方法一样
UserService userService = rpcProxy.getProxy(UserService.class); // 拿到一个"代理"
User user = userService.getUserById(12345);                     // 直接调用，别的都不用管

你没写任何网络代码，但方法真的在另一台机器上执行了，结果真的传回来了。这就是 RPC 的核心目标：调用方无感——把「远程」两个字藏起来，让程序员感觉自己在调用本地方法。

比喻：打电话 vs 寄信¶

没有 RPC，就像你给远方朋友办事，必须自己写信封（拼协议）、贴邮票（序列化）、跑邮局寄信（网络传输）、等回信再拆开读（反序列化）——每一步都得亲力亲为。有了 RPC，就像拿起电话直接拨号：你说话（调用方法）、对方应答（执行方法）、你听到回答（拿到结果），中间的交换机、基站、线路全被「藏」起来了。

面试怎么答¶

先给一句话：「RPC 的目标是让远程调用像本地调用一样简单，屏蔽网络通信细节」。再补一句：「Dubbo、gRPC、Spring Cloud 的 Feign 都是这个思路——你定义接口，框架负责把调用送到远端」。最后强调：「面试官问 RPC 设计，本质是问你怎么把『打电话』这件复杂的事封装成『拨号即通』」。

2. 模块一：动态代理——RPC 的入口¶

一句话回答¶

RPC 的入口是动态代理：客户端拿到的不是真正的服务实现，而是一个代理对象；你调用代理对象的方法时，代理会拦截这次调用，收集「调哪个类、哪个方法、什么参数」，再交给 RPC 框架去远程执行。

展开讲：为什么必须用动态代理¶

前面说过，调用方拿到的 UserService 只是一个「假对象」（代理）。这个假对象必须做到：用户写代码时感觉它在本地，但它实际会把请求转发到远程。这个「假对象」不能手写（手写的话每个接口都要写一遍转发逻辑，又回到痛苦的起点），必须动态生成——程序运行时自动生成一个实现类，拦截所有方法调用。这就是动态代理。

展开讲：JDK 动态代理 vs CGLIB¶

JDK 动态代理：Java 自带的机制，基于接口工作。要求被代理的类必须有接口（UserService 有 UserService 接口才行）。原理是运行时生成一个实现该接口的匿名类。

CGLIB：基于继承工作，通过生成目标类的子类来代理，不需要接口，可以对普通类直接代理。缺点是依赖字节码生成库，速度上略慢于 JDK 代理（现代版本差距已很小）。

JDK 动态代理 CGLIB
工作方式 基于接口，生成接口实现类 基于继承，生成目标类子类
要求 目标类必须有接口 不需要接口，普通类即可
适用 大多数业务场景（都有接口） 没有接口的类
代表框架 Dubbo、Spring AOP 默认 Spring 在无接口时的备选

展开讲：代理拦截调用后做什么¶

用 JDK 动态代理写一个 RPC 入口（伪代码）：

public class RpcProxy implements InvocationHandler {

    // 代理拦截了调用：method 是调哪个方法，args 是参数
    @Override
    public Object invoke(Object proxy, Method method, Object[] args) {
        // 1. 收集调用信息：调哪个接口、哪个方法、什么参数
        RpcRequest request = new RpcRequest();
        request.setInterfaceName(method.getDeclaringClass().getName()); // 类
        request.setMethodName(method.getName());                        // 方法
        request.setParameterTypes(method.getParameterTypes());          // 参数类型
        request.setArgs(args);                                          // 参数值

        // 2. 交给 RPC 框架：序列化 → 找机器 → 发请求 → 收响应
        RpcResponse response = RpcClient.send(request);

        // 3. 把远端结果返回给调用方
        return response.getResult();
    }
}

调用方视角：userService.getUserById(12345) 这一行代码，真实发生的事是：代理拦截 → 打包成 RpcRequest → 远程执行 → 结果原样返回。调用方全程无感。

比喻：私人助理¶

你（业务代码）给助理（代理对象）打电话说「帮我去银行办一张卡」（调用方法）。助理不用真去银行，他会：记下你要办什么卡（收集方法名和参数）→ 派一个办事员去银行办（远程执行）→ 办完把卡带回来给你（返回结果）。你只跟助理打交道，根本不知道银行在哪、办事员是谁——这就是「无感」。

面试怎么答¶

「RPC 用动态代理做入口：客户端拿到的是代理对象，JDK 动态代理基于接口、CGLIB 基于继承；代理拦截方法调用后，收集接口名、方法名、参数类型和参数值，封装成 RpcRequest 交给底层发送」。再补一句：「Dubbo 就是基于动态代理，让用户只写接口、不写实现，框架自动生成代理」。

3. 模块二：序列化与通信协议——数据怎么在网络上传输¶

一句话回答¶

网络只能传输二进制字节流，所以方法名、参数、返回值这些 Java 对象必须先序列化成字节（发出去），接收方再把字节反序列化成对象（读出来）；同时因为 TCP 是「流」式传输，还要设计自定义协议解决粘包/半包问题。

展开讲：序列化是什么¶

你在内存里有一个 Java 对象：

User{ id=12345, name="小明" }

这个对象在内存里是「结构化的」，但网络不认识对象，只认0 和 1 的字节流。序列化 = 把对象变成字节；反序列化 = 把字节还原成对象。就像把一整套乐高积木拆散装进纸箱（序列化），运到目的地再按图纸拼回去（反序列化）。

展开讲：常见序列化框架对比¶

框架 特点 性能 可读性
JSON 文本格式，人可读，跨语言 慢，体积大 好
Hessian 二进制，Java 友好，老牌 较快 不可读
Protobuf Google 出品，二进制，需定义 .proto 文件 极快，体积最小 不可读

怎么选：追求极致性能和带宽（如大规模微服务）选 Protobuf；Java 生态内部兼容性优先选 Hessian；调试方便、跨语言简单选 JSON。业界大厂（Dubbo 默认 Hessian，gRPC 强制 Protobuf）都是按场景权衡的。

展开讲：TCP 粘包 / 半包问题（必考）¶

问题背景：TCP 是「流」协议，没有「消息」边界。它像一条水管，数据是连续的水流，不是一桶一桶分好的。

  • 粘包：发送方发了 A、B 两条消息，接收方可能一次收到「AB」合在一起——因为数据在缓冲区里连成一片了；
  • 半包：发送方发了一条很长的消息，接收方可能分两次才收到「前一半 + 后一半」——因为网络分片。

比喻：快递公司不会帮你在包裹上贴「第 1 件」「第 2 件」的标签。10 件包裹塞进一辆车，收件人打开车发现混成一堆（粘包）；一件巨大的家具被拆成两车运，先到一半后到一半（半包）。没有标签，你根本分不清「这是一件家具的两半」还是「两件小包裹」。

解决方案：自定义协议头 + 按长度切分

自己设计协议格式，在每条消息前面加上消息总长度：

+------------------+-------------------------+
|  消息头 (Header)  |     消息体 (Body)        |
| 魔数 | 长度 | 类型 |  序列化后的数据          |
+------------------+-------------------------+

接收端（Netty 的 LengthFieldBasedFrameDecoder 就是干这个的）的拆包逻辑：

1. 先读 4 个字节，解析出"本条消息总长度 = N"；
2. 再接着读 N 个字节，凑齐一条完整消息；
3. 如果当前缓冲区不够 N 字节 → 说明是"半包"，继续等；
4. 如果缓冲区里还有剩余数据 → 说明后面还有消息，循环处理（解决"粘包"）。

就像快递箱上印了「本箱重 5kg」：先看标签（读长度），不足 5kg 说明没到齐（半包，继续等），到齐后如果边上还有别的箱子（粘包），就按标签一个个分开处理。

面试怎么答¶

「网络只能传二进制，所以要有序列化框架，我选 Protobuf 追求性能、JSON 方便调试；TCP 是流协议，会有粘包半包，所以自定义协议：魔数 + 消息长度 + 消息体，接收端按长度切分，Netty 的 LengthFieldBasedFrameDecoder 就是标准实现」。提到「魔数」会显得很专业——魔数就是一个固定标记（比如 0xCAFEBABE），用来快速判断「这包数据是不是我们协议的」。

4. 模块三：网络通信底座——为什么选 Netty¶

一句话回答¶

Netty 基于 NIO（非阻塞 IO） 模型，用极少数线程（通常 1~2 个）就能处理海量并发连接；而传统的同步阻塞 IO（BIO）是一个连接一个线程，线程数量扛不住高并发。

展开讲：传统 BIO 为什么不行¶

传统写法（BIO）是「一个连接一个线程」：每个客户端连接来了，就开一个线程专门伺候它，这个线程在等数据的时候阻塞着（干等，啥也不干）。

// BIO 伪代码：每个连接一个线程
while (true) {
    Socket socket = serverSocket.accept();  // 等新连接
    new Thread(() -> handle(socket)).start(); // 每个连接开一个线程
}

问题：Java 一个线程默认要占约 1MB 内存（栈空间）。1 万个连接 = 1 万个线程 = 约 10GB 内存，直接内存爆炸；而且线程多了 CPU 大量时间花在「切换线程」上，真正干活的时间反而少了。一个 RPC 服务要同时服务上万个客户端，BIO 根本扛不住。

比喻：BIO 就像餐厅一个顾客配一个服务员：顾客坐着等菜，服务员就站在旁边干等，什么也别干。10 个顾客要 10 个服务员，1 万个顾客要 1 万个服务员——服务员（线程）比顾客（连接）还贵，餐厅（服务器）直接被工资（内存）压垮。

展开讲：NIO 为什么能行¶

NIO 是「事件驱动」模型：少数几个线程同时监控着成千上万个连接，谁有数据来了，线程就去处理谁；谁没数据，线程就去干别的。线程不再「死等」某个连接。

NIO 模型（简化）：
1. 一个 Selector（选择器）线程，同时盯着所有连接；
2. 某个连接来了数据 → Selector 通知处理线程去读；
3. 没有数据的连接不占线程，只占一个"登记名额"。

比喻：NIO 像餐厅的呼叫铃服务：顾客坐下后按铃点菜，服务员听到哪个桌的铃响就去哪桌，其他时间可以服务别的桌。100 桌客人只要 3 个服务员就够了——因为服务员不再「站在一桌旁边干等」，而是「谁按铃服务谁」。

展开讲：Netty 在 RPC 框架里扮演什么角色¶

Netty 是对 NIO 的封装和增强：自己写 NIO 很难（要处理半包粘包、缓冲区管理、线程模型、断线重连……），Netty 把这些都做好了，还提供了「流水线」（Pipeline）机制——你可以把「拆包 → 反序列化 → 业务处理」当成流水线上的一道道工序挂上去，非常灵活。

RPC 客户端用 Netty：发请求（编码 → 序列化 → 发送）
RPC 服务端用 Netty：收请求（拆包 → 反序列化 → 调业务方法 → 结果序列化回发）

Dubbo 和 gRPC 的底层通信，用的就是 Netty（gRPC 底层是 Netty 或类似的高性能框架）。

面试怎么答¶

「网络底座用 Netty：BIO 一个连接一个线程扛不住高并发，NIO 事件驱动，极少数线程监控海量连接；Netty 把 NIO 的复杂性封装好了，提供 Pipeline 流水线方便挂拆包、序列化等处理逻辑」。再补一个对比：「BIO 是服务员站在每桌旁边等，NIO 是按铃服务，Netty 是把按铃服务做成了成熟产品」。

5. 模块四：服务注册与发现——客户端怎么找到服务端¶

一句话回答¶

服务端启动时把「IP:端口」注册到注册中心；客户端启动时从注册中心拉取服务端地址列表并本地缓存；服务端挂了能自动摘除，新加的机器能自动被发现。这就是服务注册与发现。

展开讲：没有注册中心会怎样¶

服务端有 3 台机器：192.168.1.1:8080、192.168.1.2:8080、192.168.1.3:8080。没有注册中心，客户端就得把这三个地址硬编码在配置里。问题来了：

  • 新增一台机器 → 所有客户端都要改配置重启；
  • 某台机器宕机 → 客户端不知道，继续往死机器上发请求；
  • 机器 IP 变了 → 又得全量改配置。

比喻：没有注册中心就像没有电话簿——你要找修水管师傅，得记住他每一个手机号，他换号了你也不知道，他搬家了你更不知道。有了电话簿（注册中心），你只需要查「修水管」这个服务名，就能拿到当前所有师傅的电话。

展开讲：注册中心怎么做（以 Zookeeper 为例）¶

服务端（提供服务的机器）：

启动时：
1. 向注册中心注册：把自己"UserService + IP:端口"写进去；
2. 启动成功后，周期性发送心跳，告诉注册中心"我还活着"；
3. 宕机或主动下线时，注册中心把它摘除。

客户端（调用服务的机器）：

启动时：
1. 向注册中心查询："UserService" 有哪些机器？→ 拿到地址列表；
2. 把地址列表缓存到本地内存（不用每次调用都查注册中心，省时间）；
3. 监听注册中心的通知：列表变化（有新机器上线 / 有机器下线）→ 更新本地缓存。

展开讲：常见注册中心对比¶

注册中心 特点 一致性模型
Zookeeper 老牌，基于 ZAB 协议，可靠性高 CP（强一致，极端情况牺牲可用性）
Nacos 阿里出品，支持服务发现 + 配置管理 AP/CP 可切换（默认 AP，服务发现要可用性）
Redis 可做简单注册中心（用哈希存地址） 看配置，简单场景够用

业界现状：Dubbo 早期标配 Zookeeper，现在越来越多用 Nacos；大厂自研注册中心也是常见操作。注册中心本身要集群部署，防止它自己挂了导致全网瘫痪。

面试怎么答¶

「服务端启动注册 IP:端口到注册中心并维持心跳，客户端启动拉取地址列表、本地缓存、监听变更；用 Zookeeper 或 Nacos 做注册中心，Zookeeper 偏 CP、Nacos 偏 AP 适合服务发现」。再补一个细节加分：「客户端本地缓存 + 注册中心推送变更，是为了避免每次调用都访问注册中心，把注册中心的压力降下来」。

6. 模块五：负载均衡与容错——选哪台机器、挂了怎么办¶

一句话回答¶

拿到地址列表后，客户端要用负载均衡算法选一台机器发请求（轮询、随机、一致性哈希）；请求失败时按容错策略处理（Failover 自动换台重试、Failfast 快速失败）。

展开讲：负载均衡算法¶

轮询（Round Robin）：三台机器 A、B、C，第一个请求给 A，第二个给 B，第三个给 C，第四个又给 A……大家轮流来，雨露均沾。适合各机器性能差不多的场景。

随机（Random）：每次调用随机选一台。请求量足够大时，分布自然趋于均匀，实现最简单。

一致性哈希（Consistent Hash）：按「请求的某个特征」（比如用户 ID）做哈希，同一个用户永远打到同一台机器。好处：如果服务端有本地缓存，同一个用户总是命中同一台机器的缓存，命中率高。适合有状态场景。

算法 思路 特点 适用
轮询 轮流来 均匀，实现简单 机器性能相近
随机 随机选 简单，量大时均匀 通用
一致性哈希 按特征哈希固定机器 相同请求稳定同机 有状态、带本地缓存

比喻：轮询是食堂打饭「一人一勺挨个来」；随机是抽签；一致性哈希是「按学号固定座位」——同一个学号永远坐在同一个位置，老师（缓存）每次都容易找到你。

展开讲：容错策略¶

Failover（故障转移）：调用 A 失败，自动换 B 再试一次；B 也失败就换 C。默认重试次数（如 3 次）内成功就算成功。适合读操作（查个用户信息，重试无副作用）。Dubbo 默认就是这个策略。

Failfast（快速失败）：第一次调用失败立刻返回失败，不重试。适合写操作——比如扣款、下单，重试可能导致重复扣款（幂等问题），宁可快速失败让上层处理。

策略 失败后 适用场景 风险
Failover 自动换台重试 读操作、幂等操作 重试放大流量
Failfast 立刻报错 写操作、非幂等 单点失败即失败

比喻：Failover 像外卖小哥：这家店没开门（挂了），马上换隔壁一家买；Failfast 像转账：这笔钱转不出去就立刻告诉你「失败」，绝不自动再转一次——万一是账户问题，自动重试可能重复扣钱。

面试怎么答¶

「客户端本地缓存了地址列表，用负载均衡选机器：轮询均匀、随机简单、一致性哈希保证相同请求固定同机；选完调用失败走容错：读操作 Failover 自动重试其他机器，写操作 Failfast 快速失败避免重复扣款」。重点说清楚「读可重试、写不可重试」这个判断依据，面试官会认可。

7. 进阶：SPI 机制——怎么做到插件化扩展¶

一句话回答¶

SPI（Service Provider Interface，服务提供者接口）机制让框架「只定义接口、不绑定实现」：换序列化方式、加新的负载均衡算法，只需要新增一个实现类并配置，完全不用改核心源码。

展开讲：没有 SPI 会怎样¶

如果 RPC 框架把 Protobuf 序列化写死在代码里：

// 写死的代码：想换序列化方式就得改框架源码
public class Encoder {
    public byte[] encode(Object obj) {
        return ProtobufUtil.encode(obj); // 写死 Protobuf
    }
}

想换成 JSON？改框架源码 → 重新编译 → 重新发布，而且改的是「别人写的框架」，容易改坏。更糟的是：框架使用者各有偏好，A 公司想用 Protobuf，B 公司想用 JSON——框架不可能为每家公司写死一种实现。

展开讲：SPI 怎么做¶

核心思想：定义接口，实现交给外部。框架代码只认接口：

// 框架只定义接口，不写死实现
public interface Serializer {
    byte[] serialize(Object obj);
    Object deserialize(byte[] data);
}

// 使用方自己提供实现，并注册
public class JsonSerializer implements Serializer { ... }
public class ProtobufSerializer implements Serializer { ... }

加载机制：框架启动时，去约定的目录（Java 标准 SPI 是 META-INF/services/，Dubbo SPI 是 META-INF/dubbo/）扫描配置文件，把使用方提供的实现类动态加载进来。想换序列化方式？新增一个实现类 + 一行配置，重启即可——核心框架一行代码都不用改。

比喻：电脑的 USB 接口¶

框架是电脑主机，SPI 是 USB 接口。想用新鼠标？插上即用，不用拆开主机改电路（改源码）。换键盘、换硬盘、换显卡（换序列化、换负载均衡）都是同一个道理——接口统一，实现随便换。没有 SPI 的框架就像焊死的电路板，换个零件得重新焊。

面试怎么答¶

「框架用 SPI 做插件化：定义好接口（Serializer、LoadBalancer），实现由使用方提供并通过约定目录注册，框架启动时动态加载。换 Protobuf 换 JSON、加一致性哈希算法，都只加实现类不改核心代码」。补一句：「Dubbo 的 SPI 比 Java 原生 SPI 更强，支持按名字获取实现、自动包装和依赖注入」。

8. 总结：RPC 框架设计的一句话主线¶

一句话回答¶

「动态代理做入口 → 序列化 + 自定义协议 → Netty 发送 → 从注册中心拉取地址 + 负载均衡选机器 → 远端执行 → 结果原路返回」——这就是 RPC 框架的完整设计主线。

展开讲：模块关系总览¶

模块 回答的问题 关键点
动态代理 调用怎么被截获 JDK 代理 / CGLIB，收集方法信息
序列化 + 协议 数据怎么变成字节、怎么切分 Protobuf / Hessian / JSON；协议头带长度
Netty 字节怎么高效传输 NIO 事件驱动，少线程扛高并发
注册中心 服务端在哪 ZK / Nacos，注册、拉取、心跳、缓存
负载均衡 + 容错 选哪台、挂了怎么办 轮询 / 随机 / 一致性哈希；Failover / Failfast
SPI 怎么扩展 接口 + 配置，不改核心源码

比喻：一次完整的「外卖之旅」¶

整个 RPC 就像点外卖：你（业务代码）跟代理（App）说想吃饭（调用方法）；App 查电话簿（注册中心）找到营业的餐厅（服务端机器），按评分选一家（负载均衡）；订单信息被写成小票（序列化 + 协议打包），骑手（Netty）飞快送去；餐厅做好饭原路送回（响应返回）；你拿到饭（结果），全程不知道餐厅地址、不知道骑手是谁——无感。

9. 补充：一次完整 RPC 调用的「旅途」串讲（小白视角）¶

一句话回答¶

把前面所有模块串起来：客户端调用 → 代理拦截 → 序列化打包 → 注册中心找地址 → 负载均衡选机器 → Netty 发送 → 服务端拆包反序列化 → 反射调方法 → 结果原路返回。

展开讲：完整旅程分 10 步¶

第 1 步：发起调用。业务代码写 userService.getUserById(12345)。此时 userService 是代理对象，不是真实现。

第 2 步：代理拦截。动态代理拦截这次调用，收集信息：接口 UserService、方法 getUserById、参数 12345。

第 3 步：序列化打包。把调用信息封装成 RpcRequest 对象，用序列化框架（如 Protobuf）转成字节流。

第 4 步：查地址列表。从本地缓存里拿 UserService 的机器列表（缓存来自启动时向注册中心拉取，之后靠监听更新）。

第 5 步：负载均衡选机器。用轮询 / 随机 / 一致性哈希，从列表里选出一台机器（如 192.168.1.2:8080）。

第 6 步：Netty 发送。客户端 Netty 建立连接，按自定义协议（消息头 + 消息体）把字节流发出去。

第 7 步：服务端接收拆包。服务端 Netty 收到字节流，按协议头的长度信息切分出完整消息（解决粘包半包），再反序列化成 RpcRequest 对象。

第 8 步：反射调用。服务端根据「接口名 + 方法名 + 参数」找到真正的实现类，用反射（Java 反射机制，运行时动态调用方法）执行 getUserById(12345)，拿到 User 对象。

第 9 步：结果返回。把 User 对象序列化成字节，同样按协议发回客户端。

第 10 步：调用方拿到结果。客户端收到响应，反序列化成 User 对象，代理把它返回给业务代码。业务代码从头到尾只写了那一行调用——无感完成。

比喻：寄一封国际快递¶

把这 10 步想象成寄快递：你写好信（调用方法）→ 快递点帮你打包贴单（代理拦截 + 序列化）→ 查快递网点表选最近网点（注册中心 + 负载均衡）→ 货车运输（Netty）→ 收件网点拆包核对（拆包 + 反序列化）→ 收件人看信、回信（反射执行 + 结果返回）→ 原路送回你手上。全程你只需要「把信递给快递点」，剩下的全是框架（快递公司）的事。

面试怎么答（完整版）¶

把第 8 节的「一句话主线」展开成「旅程叙述」：「客户端调用被动态代理拦截，收集接口、方法、参数，序列化后通过 Netty 发出；地址从注册中心拉取并本地缓存，负载均衡选一台机器；服务端 Netty 拆包、反序列化，用反射找到实现类执行方法，结果序列化原路返回」。能把这趟旅程讲顺，RPC 框架设计这道题就稳了。

本节小结¶

RPC 框架设计可以拆成六个模块记：动态代理是入口（拦截调用、收集方法信息），序列化 + 自定义协议解决「对象变字节、流怎么切分」（粘包半包靠协议头长度解决），Netty 解决「怎么高效传输」（NIO 少线程扛高并发），注册中心解决「服务端在哪」（注册、拉取、心跳、缓存），负载均衡 + 容错解决「选哪台、挂了怎么办」（轮询 / 随机 / 一致性哈希，Failover / Failfast），SPI 解决「怎么扩展」（只改配置不改源码）。一句话串起来：动态代理做入口 → 序列化 + 自定义协议 → Netty 发送 → 从注册中心拉取 + 负载均衡选机器。记住「让远程调用像本地调用一样无感」这个核心目标，所有模块都围绕它展开。
