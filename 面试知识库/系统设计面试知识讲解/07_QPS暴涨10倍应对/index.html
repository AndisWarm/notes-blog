07 如果你的系统 QPS 突然提升 10 倍，你会怎么设计？¶

本章覆盖：当系统每秒请求量（QPS）突然变成原来的 10 倍时，该如何应对。先讲「紧急止血」三件套（限流、降级、弹性扩容）保证系统不挂，再讲「架构全面演进」三板斧（多级缓存扛读、消息队列削峰扛写、读写分离 + 分库分表为数据库终极扩容），最后给出完整的面试回答模板和电商大促场景模拟。

1. 先搞清楚：QPS 涨 10 倍到底意味着什么？¶

一句话回答¶

QPS 是每秒请求数，涨 10 倍意味着系统每秒要处理的请求从「能轻松应付」变成「远超承载能力」，第一要务不是体验，而是别让整个系统挂掉，然后再谈架构升级。

展开讲：什么是 QPS 和 TPS？¶

先认识两个高频词，面试和工作中天天见：

  • QPS（Queries Per Second）：每秒查询次数，可以通俗理解为每秒有多少个请求打到你的系统上。一个用户点一下「查看商品详情」，前端就会发 1 个（甚至好几个）请求到后端，这些请求都算 QPS 的一部分。
  • TPS（Transactions Per Second）：每秒事务数，通常指每秒能成功完成多少个完整业务操作（比如「下单」这个动作要经历校验、扣库存、写订单表，整个过程算一个事务）。简单记：QPS 数的是「来了多少请求」，TPS 数的是「办成了多少件事」。

可以这样理解：一个双十一凌晨，商场大门刚开，每秒有 1 万人冲进来（QPS 高），但收银台每秒只能结账 100 单（TPS 有上限）。人再多，结账速度就那么多——所以系统真正的瓶颈，往往是「处理能力」（TPS）跟不上「请求量」（QPS）。

比喻：餐厅突然涌入 10 倍客人¶

想象你开了一家小餐厅，平时每秒进来 10 个客人，厨师、服务员、灶台都是按这个量配置的。突然有一天（比如短视频爆火把你的店带火了），每秒涌进来 100 个客人：

  • 如果什么都不做：厨房忙不过来，菜越积越多，服务员崩溃，最后连灶台都烧了、所有客人都吃不上饭——这就是系统崩溃，所有请求全部失败，用户体验直接归零。
  • 聪明的做法：先在门口拦住一部分人，让里面的人还能正常吃饭（限流）；暂时不做的菜先不做了，把所有厨师集中到最赚钱的招牌菜上（降级）；实在不行临时多雇厨师、多加灶台（扩容）。

这个比喻贯穿全文，后面每一招都能对上号。

面试怎么答¶

先给结论：「QPS 涨 10 倍本质是流量超过系统承载能力，我分两个阶段处理：第一阶段紧急止血保证不挂，第二阶段架构演进彻底治本。」然后展开讲两个阶段。这个「两阶段」框架就是全文的主线，背下来。

2. 第一阶段：紧急应对——「弃车保帅，保证系统不挂」¶

一句话回答¶

流量暴增的第一时间，核心原则是「弃车保帅」：用限流挡住扛不住的请求、用降级关掉非核心功能、用弹性扩容加机器硬扛，先让系统活下来，再谈优化。

为什么必须「保命优先」？¶

系统设计里有个残酷的现实：一个请求失败，损失的是用户体验；整个系统崩溃，损失的是所有用户和全部业务。

  • 如果限流失效，任由 10 倍流量打进数据库，数据库连接池被打满、磁盘 IO 爆炸，最坏结果是数据库宕机——而数据库是所有业务的根基，它一挂，下单、支付、查询全瘫，恢复还要很久；
  • 反过来，如果我们主动拒绝一部分请求（返回「系统繁忙，请稍后再试」），损失的只是这部分用户这一次的体验，但系统其他功能照常运转，大部分用户还能正常购物。

一句话：「保大放小」不是不重视用户体验，而是两害相权取其轻——宁可让 20% 的用户暂时进不来，也不能让 100% 的用户全部用不了。

2.1 第一招：限流——在门口设闸机¶

是什么：在请求进入系统的入口（通常是 网关，比如 Nginx、Spring Cloud Gateway）设置一个最大 TPS 阈值，比如「每秒最多放 1000 个请求进来」。超过这个数的请求快速失败，直接返回「系统繁忙」，不让它们继续往后打。

为什么限在网关层：网关是流量的总闸门，所有请求都必须先经过它。在总闸门这里拦住，后面的服务、数据库就都安全了。如果每个服务各自为政不设防，10 倍流量会同时把所有环节都打爆，四处起火没法救。

比喻：商场限流排队：商场搞促销，保安在门口用围栏拉出蛇形通道，一次只放进去一批人，里面的人逛完出来，才放下一批。外面排队的人虽然等得着急，但至少商场里秩序井然、大家都能买到东西。如果不管不顾全放进去，商场里人挤人，收银台瘫痪，最后谁也买不成——这就是限流的意义：牺牲一部分人的等待时间，换取整体系统的稳定。

Sentinel 是什么、怎么工作：Sentinel 是阿里开源的流量控制组件（同类还有 Hystrix、Resilience4j），它干的事就是上面说的「设阈值、挡流量」。它的原理有好几种算法，这里讲一个最简单的——计数器算法，够面试用了：

  1. 把时间切成一个个小格子，比如每 1 秒一个格子；
  2. 每进来一个请求，格子里的计数 +1；
  3. 当格子里计数达到设定的阈值（比如 1000），这一秒剩下的请求全部拒绝；
  4. 下一秒换一个新格子，计数清零，重新开始放行。

代码大概长这样（伪代码，理解意思即可）：

// 计数器限流（伪代码）
int limit = 1000;        // 每秒最多 1000 个请求
int count = 0;           // 当前这一秒已放行数
long currentSecond = now();  // 当前秒数

if (currentSecond != lastSecond) {
    // 进入新的一秒，计数器清零
    count = 0;
    lastSecond = currentSecond;
}
if (count >= limit) {
    return "系统繁忙，请稍后再试";  // 快速失败，直接拒绝
}
count++;
handleRequest();  // 放行，处理业务

更高级的还有滑动窗口（把 1 秒拆成更多小格，窗口慢慢往前滑，避免「前 0.9 秒空着、后 0.1 秒挤爆」的临界问题）和令牌桶（系统匀速往桶里放令牌，请求必须拿到令牌才能进，没令牌就排队等待，能把突发流量平滑成匀速流量）。面试时能讲清楚计数器，再提一句令牌桶「匀速放令牌、平滑流量」，就已经很加分了。

2.2 第二招：降级——砍掉非核心功能¶

是什么：把非核心业务临时关掉，把宝贵的 CPU 和内存全部让给核心动作。

电商场景举例：

功能 平时 流量暴增时
下单、支付 正常 保留（命根子）
「猜你喜欢」推荐 正常 降级：不推荐了，返回空或简单列表
商品评论显示 正常 降级：不查评论了，评论区显示「加载中」或隐藏
积分发放 正常 降级：先记个账，等流量平缓了再补发

为什么有效：系统资源（CPU、内存、数据库连接）是有限的。「猜你喜欢」要跑推荐算法、评论要查评论表、积分要更新积分字段——这些都在消耗资源。大促时下单的人排着队，如果推荐和评论还在抢资源，等于堵车的时候还有人横穿马路。把它们临时关掉，资源全部让给「下单」和「支付」，核心链路才能扛住。

比喻：医院急诊分流：医院遇到突发事故，大量伤员涌进来，医生护士不够用。这时医院会怎么做？非紧急的普通门诊先停一停，所有医护力量集中到急诊室抢救危重病人。轻症病人等一等没关系，但重伤员必须第一时间处理——降级就是这个道理：分清轻重缓急，把资源给最要命的业务。

注意：降级不是「删代码」，而是通过配置中心（比如 Nacos、Apollo）动态开关某个功能。流量高峰过了，一键把功能打开，服务恢复原样，不用重启、不用改代码。

2.3 第三招：弹性扩容——加机器硬扛¶

是什么：如果公司的基建足够完善（用了容器化和编排平台），可以直接动态增加服务节点：原来跑 10 台机器，流量涨 10 倍就扩到 50 台、100 台，用机器数量把流量硬扛下来。

K8s（Kubernetes）在这里干什么：K8s 是容器编排平台，通俗说就是一群服务器的「自动管家」。你把应用打包成「容器」（可以理解成一个小盒子，里面装着程序和运行环境），K8s 负责决定这个小盒子跑在哪台机器上、跑几个。流量暴增时，K8s 可以根据 CPU 使用率等指标自动创建更多容器副本（这叫水平扩容 HPA），前面再加个负载均衡器把流量平均分到每个副本上；流量降下来后，它还能自动缩回去，省机器省钱。

# K8s 水平自动扩容配置（伪代码，理解意思即可）
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service     # 对「订单服务」做自动扩容
  minReplicas: 10           # 最少 10 个副本
  maxReplicas: 100          # 最多扩到 100 个副本
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # CPU 用到 70% 就自动加副本

比喻：连锁店临时加桌：餐厅突然爆满，总部立刻从别的店调厨师、调桌子过来支援（扩容），或者临时租隔壁店面多摆几十桌（新加节点）。人多就多加桌子，人少就撤桌子——这就是「弹性」。

注意：扩容不是万能的。加机器只能扛「无状态」的请求（比如查询、计算），但如果瓶颈在数据库——所有请求最终都要读写同一台数据库，加再多的应用服务器，数据库也只有一个，照样被挤爆。所以扩容是「应急手段」，治本还得看第二阶段的数据库改造。

面试怎么答¶

「第一阶段我按『限流 → 降级 → 扩容』三步走：限流在网关设 Sentinel 阈值，超出的请求快速失败返回『系统繁忙』；降级把『猜你喜欢』『评论』『积分』等非核心功能通过配置中心动态关闭，资源全部让给下单和支付；扩容用 K8s 的 HPA 自动加容器副本硬扛。核心原则是弃车保帅：损失部分用户体验，保证整个系统不挂。」

3. 第二阶段：架构全面演进——把读流量和写流量分开治理¶

一句话回答¶

如果 10 倍流量变成常态（比如产品真的大火），限流降级只能「续命」不能「治病」，必须对架构动手术：读流量用「多级缓存」挡住，写流量用「消息队列」削峰，数据库用「读写分离 + 分库分表」终极扩容。

为什么必须「读写分开治理」？¶

读和写是两种完全不同的流量，病根不同，药方也不同：

  • 读请求：特点是量大、重复——1 万个用户看的可能是同一个热门商品页。这类请求的痛点在于「查询太慢、数据库扛不住」，核心解法是缓存：让数据待在离用户最近、最快的地方。
  • 写请求：特点是瞬时爆发、不可重复——10 倍用户同时下单，每一单都是新的。这类请求的痛点在于「数据库写入速度有物理上限」，核心解法是排队：把洪峰削平，让数据库按自己的节奏慢慢写。

下面三节分别讲：读怎么扛（多级缓存）、写怎么扛（MQ 削峰）、底层怎么扛（读写分离 + 分库分表）。

3.1 扛 10 倍读请求：多级缓存——本地缓存 + Redis¶

是什么：搭建两级缓存：第一级是本地缓存（Caffeine 或 Guava，存在应用服务器自己的内存里），第二级是分布式缓存（Redis 集群）。读请求按「本地缓存 → Redis → MySQL」的顺序逐级查找，越前面的层级越近、越快，绝大多数请求在最前面就被拦住了。

为什么单靠 MySQL 不行，甚至单靠 Redis 也可能不够：

  • MySQL：数据在磁盘上（即使有内存缓冲池），每次查询要走网络、走 SQL 解析，能支撑的 QPS 也就几千到几万，10 倍流量一来直接被打满；
  • Redis：数据在内存里，单机能扛十万级 QPS，看起来很强了——但注意，每个应用服务器读 Redis 都要走网络。当应用服务器从 10 台扩到 100 台，每台每秒发 1 万个 Redis 请求，那就是每秒 100 万个网络请求，Redis 集群的网络带宽会被打满，延迟飙升，照样顶不住；
  • 本地缓存：数据就在应用进程自己的 JVM 内存里，读它连网络请求都不用发，只是「从内存里取一个变量」级别的操作，响应时间压到微秒级，而且完全不占用 Redis 和 MySQL 的任何资源。

所以正确的姿势是两层一起上：本地缓存挡掉最热的那部分请求（比如爆款商品详情），Redis 挡掉次热的请求（比如销量前 100 的商品），只有真正冷门的数据才落到 MySQL。

两级缓存的完整读取路径（背这个流程）¶

用户请求
   │
   ▼
① 查本地缓存（应用服务器的 JVM 内存，Caffeine/Guava）
   ├─ 命中 → 直接返回（微秒级，不产生任何网络请求）
   ▼ 未命中
② 查 Redis 集群（分布式缓存）
   ├─ 命中 → 回填本地缓存 → 返回（毫秒级）
   ▼ 未命中
③ 查 MySQL（数据库）
   ├─ 查到 → 回填 Redis → 回填本地缓存 → 返回（可能几十毫秒）
   ▼ 也没查到
④ 返回「不存在」（可结合布隆过滤器/缓存空值防穿透）

每一级的作用和职责：

层级 存在哪 特点 放什么数据 淘汰策略
本地缓存（Caffeine/Guava） 每台应用服务器自己的 JVM 内存 最快（微秒级）、零网络开销；但每台服务器各存一份，数据可能不一致 极少变化的热点数据（爆款商品标题、价格、库存快照） LRU（最近最少使用）淘汰 + 短过期时间
Redis 集群 独立部署的分布式缓存服务 快（毫秒级）、所有服务器共享一份，一致性好 次热点数据、所有服务器都要用的公共数据 过期时间 + 内存淘汰策略
MySQL 磁盘 慢（几十毫秒级） 全量数据，兜底 —

为什么本地缓存不怕数据略微不一致：本地缓存里放的必须是「变化极少」的数据——比如商品标题，改了也就是运营改一下描述，晚几秒钟在所有服务器上生效完全没关系。但如果放「用户余额」这种强一致数据，本地缓存就危险了：用户在 A 服务器看到余额 100 元，在 B 服务器又看到 80 元，就出事了。所以选对数据进本地缓存，是这套架构的前提。

比喻：随身小本子 + 小区便利店 + 市中心大仓库：

  • 本地缓存 = 你随身带的记着常用电话号码的小本子：打给爸妈，翻本子 1 秒就拨出去了，不用跑腿（零网络请求）；
  • Redis = 小区门口的便利店：本子上没有的电话，下楼走两步问店员（一次网络请求，毫秒级），顺便把号码抄进本子（回填本地缓存）；
  • MySQL = 市中心的总资料库：便利店也没有的冷门资料，才打车去市中心查（几十毫秒），查到后先告诉便利店、再抄进自己本子（逐级回填）。

大多数人每天打的就是那 5 个号码，都在小本子上——所以绝大多数请求根本走不出应用服务器，Redis 和 MySQL 都被保护得好好的。

面试怎么答¶

「读流量我上两级缓存：Caffeine/Guava 本地缓存 + Redis 集群。本地缓存放在应用服务器 JVM 里，存极少变化的热点数据，命中就直接返回、零网络开销，把最热的那部分流量挡在应用内部；Redis 存次热点数据，所有服务器共享；只有两级都 miss 才查 MySQL 并逐级回填。为什么不用单层 Redis？因为应用服务器多了以后，网络带宽会成为新的瓶颈——本地缓存连网络请求都省了，同时保护了 Redis 和 MySQL。」

3.2 扛 10 倍写请求：消息队列削峰——先答应下来，慢慢办¶

是什么：写请求（下单、点赞、评论）进来后，不让它直接打数据库，而是先做基础校验（比如参数对不对、商品存不存在），校验通过就把这笔操作扔进消息队列（MQ，常用 Kafka 或 RocketMQ），立刻告诉前端「收到，处理中」；后端服务再按照数据库能承受的真实速度，从队列里平稳地、慢慢地拉取消息执行真正的写入。

为什么能扛 10 倍写流量：数据库的写入能力是「硬上限」——比如每秒最多写 1000 条订单。10 倍流量意味着每秒进来 1 万单，直接打库必然崩溃。但有了 MQ 这层「蓄水池」：

  • 前端感知的延迟只有「扔进队列」的时间，毫秒级就返回，用户体验几乎无损；
  • 队列能瞬间吞下海量消息（Kafka 单机就能扛每秒百万级消息写入），把 1 万/秒的洪峰先存起来；
  • 后端消费服务按 1000 条/秒 的节奏慢慢写库，数据库始终处于健康状态；
  • 流量高峰过去后，消费服务继续把积压的消息消化完，最终所有订单都会处理完成，只是时间有先后。

比喻：游乐场门口的蛇形排队通道：游乐场新开一个热门项目，瞬间来了 1 万人。如果所有人都直接涌向项目入口，现场必然失控、甚至发生踩踏（数据库被打爆）。游乐场的做法是：在门口设蛇形排队通道——所有人先进入通道（消息进 MQ），项目一次放 20 个人进去玩（消费者按固定速度消费），玩完再放下一批。外面的人安心排队（收到「处理中」反馈），里面的人有序游玩（数据库平稳写入）——流量洪峰变成了细水长流。

代码示意（伪代码）：

// 下单接口：只做校验 + 扔队列，不直接写库
public Result createOrder(OrderRequest req) {
    // 1. 基础校验：参数、库存预检等
    check(req);
    // 2. 把下单消息扔进 MQ，立刻返回
    mq.send("order_topic", req);   // 毫秒级完成
    return Result.ok("下单成功，处理中");  // 前端马上收到响应
}

// 消费端：按数据库能承受的速度，平稳写库
@KafkaListener(topics = "order_topic", concurrency = "20")  // 20 个并发消费者
public void onOrder(OrderRequest req) {
    orderMapper.insert(req);   // 每秒总量被控制在安全范围
    inventoryMapper.deduct(req.getSkuId(), req.getCount());
}

注意三个细节（面试加分项）：

  1. 消息积压怎么办：如果积压太多（消费速度赶不上），可以临时增加消费者实例，或者用 MQ 自带的重试/死信机制兜底；只要数据库没被打垮，积压只是「晚点处理」，不是「处理不了」；
  2. 消息丢失怎么办：MQ 开启持久化（消息落盘），消费者手动 ACK（处理成功才确认，失败自动重试），保证消息不丢；
  3. 重复消费怎么办：消费者要做幂等处理（比如订单号建唯一索引，重复插入会失败），保证同一条消息处理两次也不产生脏数据。

面试怎么答¶

「写流量我用 MQ 异步削峰：下单请求先做基础校验，通过后扔进 Kafka/RocketMQ 马上返回『处理中』，后端消费者按数据库能承受的速度平稳拉取执行。这样前端体验几乎无损，数据库永远不会被瞬时洪峰打爆。同时我会配套保证可靠性：消息持久化 + 手动 ACK + 消费幂等，防止消息丢失或重复。」

3.3 数据库终极改造：读写分离 + 分库分表¶

是什么：当数据量巨大（上亿行）且并发连接数也到顶时，说明单台 MySQL 已经到了物理极限。终极方案分两步：读写分离解决「并发连接太多」，分库分表解决「单表数据太大」。

3.3.1 读写分离——主库写、从库读¶

原理（主从复制）：MySQL 自带能力，一台主库（Master）负责接收写操作，把每次写入记录成一份「流水日志」（binlog）；若干台从库（Slave）连上主库，把日志同步过来在自己身上重放一遍，于是从库就有了和主库几乎一样的数据。

用户写请求 ──► 主库 Master（只写）
                    │  同步 binlog（异步复制）
         ┌──────────┼──────────┐
         ▼          ▼          ▼
      从库1      从库2      从库3（只读）
         ▲          ▲          ▲
用户读请求 ──────── 随便挑一台从库读
  • 主库只有一台，所有写操作都走它，写入能力集中不分散；
  • 读请求分散到多台从库上，读的吞吐量 = 从库数量 × 单台能力，从 1 台变成 N 台；
  • 通常一个系统读多写少（可能 90% 是读），所以这种「一台写、多台读」的结构能成倍提升整体吞吐。

比喻：总店记账 + 分店查账：总店（主库）只负责记账（写入），每记一笔就把账本复印几份送到各分店（从库），分店只管给顾客查（读取）。顾客多了就多开几家分店，查账永远不排队；而记账只有总店一本，保证了账目不乱。

代价要说清楚：主从复制是异步的，主库写完、从库可能还差零点几秒没同步完——这就是主从延迟。所以「刚下完单立刻查订单」这种强一致读，要么走主库，要么等同步完成；能接受「稍微延迟一下看到结果」的查询才走从库。

3.3.2 分库分表——把一张大表拆成一百张小表¶

为什么要拆：一张表数据到了上亿行，索引再牛也有瓶颈——B+ 树层级变深、磁盘 IO 变多、锁竞争加剧，单表查询越来越慢；而且单台机器的 CPU、内存、磁盘是有限的，数据全堆在一台机器上，机器再强也有顶。

两个拆分方向：

① 垂直拆分（分库/分表）——按「业务」拆

  • 垂直分库：把不同业务的数据拆到不同的数据库——比如电商把「订单库」「商品库」「用户库」分开，各用各的机器，互相不抢资源；
  • 垂直分表：把一张「字段特别多」的表拆成多张——比如「商品表」有 60 个字段，把常用字段拆到「商品主表」，把大文本字段（详情描述）拆到「商品详情表」，查询时只查需要的表，单行变瘦、查询变快。

比喻：一个办公室 100 个人挤在一起干活（一张大表），垂直拆分就是按部门分成产品部、技术部、销售部（分库），每个部门独立办公（各用各的机器），互不干扰；每个部门内部再按职责细分小组（分表）。

② 水平拆分（分表）——按「数据」拆，这是解决单表数据量的关键：

  • 把一张 1 亿行的大表，按某个规则（比如 订单ID % 100）拆成 100 张结构完全相同的小表：order_0、order_1……order_99，每张表只有 100 万行；
  • 这 100 张表可以分散到多台机器上，比如 10 台机器、每台放 10 张表——查询、写入的压力被分摊到 100 张表、10 台机器上，底层吞吐量成倍扩充；
  • 路由规则要提前设计好（取模、按范围、按哈希），写数据时算一下该进哪张表，查数据时按同样规则找到那张表——这套「路由」逻辑通常由中间件（比如 ShardingSphere、MyCat）自动完成，业务代码几乎无感。
// 水平分表：按订单 ID 取模，路由到 100 张表之一（伪代码）
String tableName = "order_" + (orderId % 100);  // order_0 ~ order_99
String sql = "INSERT INTO " + tableName + " (order_id, user_id, amount) VALUES (?, ?, ?)";

比喻：图书馆藏书：一个图书馆藏书 1 亿本，全堆在一个大厅（单表），找书要翻遍全馆。水平拆分就是按书的编号分成 100 个分馆（100 张表），每个分馆只存 100 万本，分散在城市不同位置（不同机器）。读者借书时，先按编号算出书在哪个分馆（路由），直接去那个分馆拿——每个分馆的找书速度都快了 100 倍，而且 100 个分馆可以同时接待读者（并行吞吐）。

拆完带来的新问题（面试要能接得住）：

  • 跨表查询变难：以前一条 SQL 能查完的数据，现在要合并多张表的结果（用中间件做「聚合」），复杂的 JOIN 基本做不了——所以要提前设计好拆分键（sharding key），让绝大多数查询只落在一张表上；
  • 全局唯一 ID：以前靠数据库自增主键，拆表后各表自增会撞车，要改用分布式 ID（雪花算法 Snowflake 等）生成全局唯一主键；
  • 分布式事务：一次操作可能涉及多张表、多台机器，事务从「本地事务」升级成「分布式事务」，要引入 Seata 之类的方案或改造成最终一致。

面试怎么答¶

「数据库的终极扩容我分两步：读写分离——主库扛写、从库扛读，通过 binlog 主从复制同步数据，把读吞吐从 1 台扩成 N 台，同时说清楚主从延迟的代价；分库分表——垂直拆分按业务把大库拆小、把宽表拆瘦，水平拆分按 订单ID 取模 把上亿行的大表拆成 100 张百万行的小表分散到多台机器，用 ShardingSphere 这类中间件做路由。同时我会主动说拆分的代价：跨表查询难、需要分布式 ID、分布式事务——提前设计好拆分键是成败关键。」

4. 总结：完整思路一张表¶

一句话回答¶

先保命，再治本：用限流、降级、扩容保住系统的命；用多级缓存挡住绝大部分读流量；用 MQ 异步削峰消化突发的写流量；最后用读写分离 + 分库分表为数据库做终极扩容。

全流程对照表（背这个）¶

阶段 手段 解决什么问题 比喻
紧急止血 限流（Sentinel 网关限流） 请求超过承载能力，防止系统被打爆 商场限流排队，先进一部分人
紧急止血 降级（关非核心功能） 资源不够，保证核心业务（下单/支付）优先 医院急诊分流，先抢救危重病人
紧急止血 弹性扩容（K8s 加节点） 无状态服务能力不够，加机器硬扛 连锁店临时加桌、调厨师
常态演进 多级缓存（本地缓存 + Redis） 读流量 10 倍，减少对 Redis/MySQL 的依赖 随身小本子 + 便利店 + 总仓库
常态演进 MQ 削峰（Kafka/RocketMQ） 写流量 10 倍，避免直接打爆数据库 游乐场蛇形排队，洪峰变细流
常态演进 读写分离 + 分库分表 单台 MySQL 到极限，终极扩容 总店记账分店查账、图书馆分馆藏书

为什么这个顺序不能乱¶

先限流降级扩容（治标），再多级缓存和 MQ（治本），最后才是数据库改造（终极）：

  1. 流量暴增的当下，你不可能瞬间完成分库分表（要停机、要迁移数据、要改代码），所以第一步必须是不改架构就能上的限流降级扩容，先把命保住；
  2. 架构演进有优先级：缓存和 MQ 是改动相对小、见效最快的（加一层缓存、加一个队列，业务代码改动可控），能解决 90% 的流量问题；
  3. 只有当数据量和并发真的到顶，缓存和队列也救不了的时候，才值得动数据库这最重的一刀——因为分库分表一旦做了，后面所有 SQL 都要跟着改，代价最大，必须放在最后、并且想清楚了才做。

一句话总结：限流是保命，缓存是挡路，MQ 是蓄水，分库分表是扩容——四件事层层递进，缺一不可。

5. 面试怎么答：完整话术 + 场景模拟¶

面试回答模板（两阶段汇报）¶

总起：「如果 QPS 突然涨 10 倍，我会分两个阶段处理：第一阶段紧急止血，保证系统不挂；第二阶段架构演进，让系统真正扛住 10 倍的常态流量。」

第一阶段（紧急应对）：「我会同时做三件事。限流：在网关层用 Sentinel 设最大 TPS 阈值，超出的请求快速失败返回『系统繁忙』，宁可损失部分用户体验，也不能让整个系统崩溃；降级：通过配置中心动态关掉『猜你喜欢』『评论显示』『积分发放』等非核心功能，把 CPU 和内存全部让给『下单』和『支付』；扩容：如果基建完善，用 K8s 的 HPA 自动增加容器节点，加机器硬扛。核心原则是弃车保帅。」

第二阶段（常态演进）：「如果 10 倍流量变成常态，我会把读流量和写流量分开治理。读：上多级缓存——Caffeine/Guava 本地缓存 + Redis 集群，热点数据直接加载到应用服务器自己的 JVM 内存，绝大多数读请求在本地就返回了，连网络请求都不用发，同时保护 Redis 和 MySQL；写：上 MQ 削峰——请求基础校验通过后扔进 Kafka/RocketMQ，马上返回『处理中』，后端按数据库能承受的真实速度平稳消费，把流量洪峰变成细水长流；数据库：如果数据量和并发连接数还是到瓶颈，说明单台 MySQL 到了极限，就做读写分离（主库写、从库读，binlog 主从复制）+ 分库分表（水平拆分按 ID 取模 把大表拆成 100 张小表分散到多台机器），为数据库做终极扩容。」

收尾：「整体思路就是先保命、再治本：限流降级扩容保住系统，多级缓存挡读，MQ 削峰扛写，读写分离分库分表做终极扩容。」

真实场景模拟：电商大促，流量瞬间 10 倍¶

把上面的话术套进一个完整故事里（面试时这样讲，画面感和条理性都拉满）：

背景：某电商平台，平时 QPS 约 1 万。今天 0 点大促开抢，QPS 瞬间冲到 10 万。

第 0 分钟——告警：监控告警响起：网关 QPS 破 5 万，订单服务 CPU 飙到 95%，数据库连接池快被打满。第一反应不是写代码，是止血。

第 1~5 分钟——紧急止血： 1. 限流：在网关紧急下调 Sentinel 阈值到 3 万，超出的请求直接返回「系统繁忙，请稍后再试」。一部分用户被挡在外面，但里面的人还能正常下单； 2. 降级：通过配置中心一键关闭「猜你喜欢」「评论展示」「积分发放」，同时把推荐服务、评论服务的副本缩容，资源全部让给订单和支付链路； 3. 扩容：K8s 的 HPA 检测到订单服务 CPU 超 70%，自动从 20 个副本扩到 80 个，Nginx 负载均衡把流量摊到每个副本上。

第 6~30 分钟——系统稳住：数据库压力回到安全水位，限流误伤率降到可接受范围。这时候才开始治本。

第 1 小时——治本措施上马： 1. 读：商品详情页接入两级缓存——爆款商品的标题、价格、主图在发布时预热进 Caffeine 本地缓存 + Redis，详情页 QPS 从 5 万降到 5 千，Redis 和 MySQL 的压力骤减； 2. 写：下单接口改为「校验后扔 Kafka，立即返回『处理中』」，订单消费服务按每秒 2 万单的节奏平稳写库，数据库写压力从「10 倍洪峰」变成「匀速水流」； 3. 数据库：订单表提前按 用户ID 取模 拆成了 64 张分表、分散在 8 台机器上，配合主从读写分离（主库写、3 台从库读），单库 QPS 稳稳扛住。

大促结束：QPS 回落到 1 万，HPA 自动把副本缩回 20 个，降级开关逐个打开，系统恢复日常状态——整个过程系统没有挂过一秒。

这个故事说明了什么：遇到突发流量，成熟的系统不是「硬扛」，而是「有节奏地让」——先让一部分请求失败（限流）、让一部分功能暂停（降级）、让机器变多（扩容）保住性命；再让读走缓存、写走队列、数据分散存储，把 10 倍流量彻底消化。

面试常见追问（提前准备）¶

追问 回答要点
限流阈值怎么定？ 压测得出系统真实承载上限，留 20%~30% 余量；阈值要配合监控动态调整
降级会不会影响用户体验？ 会，但影响的是「锦上添花」的功能，核心下单支付不受影响；用降级开关 + 文案提示缓解
本地缓存数据不一致怎么办？ 只放「极少变化」的数据 + 短过期时间 + 发布时主动刷新；强一致数据不进本地缓存
MQ 消息积压了怎么办？ 先扩容消费者实例提升消费速度；分析积压原因；保证「宁可慢，不可丢」
分库分表后怎么跨表查询？ 提前设计好拆分键，让 90% 查询单表完成；跨表查询用中间件聚合或走汇总表/宽表

本节小结¶

QPS 暴涨 10 倍不可怕，可怕的是没有预案。记住「先保命，再治本」：第一阶段用限流（Sentinel 网关阈值）、降级（关非核心功能）、弹性扩容（K8s 加节点）保证系统不挂；第二阶段用多级缓存（本地缓存 + Redis）挡住读流量、用 MQ 削峰（Kafka/RocketMQ）消化写流量、用读写分离 + 分库分表为数据库做终极扩容。面试时按「紧急应对 → 常态演进」两阶段汇报，再配一个电商大促的故事，就是一份完整的高分答案。
