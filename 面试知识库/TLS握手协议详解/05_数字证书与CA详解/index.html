05 数字证书与 CA：如何证明"我是我"¶

本章目标：搞清楚三个问题——服务器亮出的证书里到底装了什么？CA 是怎么签发的？浏览器又是怎么验证的？最后讲证书出问题了怎么"吊销"。这是 TLS 里"防冒充"的核心，也是面试高频区。

先解决一个"鸡生蛋"问题¶

回顾第 4 章：密码套件里用 RSA 或 ECDSA 做签名认证。但有个问题——服务器把它的公钥发给客户端，客户端凭什么相信这个公钥真的是目标网站的？

设想你访问"银行官网"，网络上来了一个自称是银行的人，递给你一把钥匙说"这是我的公钥，你把钱用这把钥匙锁起来寄给我"。你信吗？当然不信——任何人都可以说自己是银行。

所以 TLS 需要解决"身份担保"问题，办法是引入一个双方都信任的第三方：CA（Certificate Authority，证书权威机构）。CA 就相当于网络世界的公证处：它先核实"你确实是银行官网"，然后给这份"身份声明"盖一个极难伪造的章。任何人看到这个章，就放心相信公钥确实是银行的。

数字证书里装了什么？¶

Certificate 消息就是服务器把这个"盖了章的身份声明"（数字证书）发给客户端。证书里主要包含：

内容 通俗解释
服务器的公钥 客户端接下来要用它加密 pre-master（第 6 章）
持有者信息 这证书是发给谁的（域名：www.example.com、公司名等）
证书认证机构（CA）的信息 是谁盖的章（比如 DigiCert、GlobalSign）
CA 的数字签名 + 签名算法 那个"极难伪造的章"，以及用什么算法盖的
证书有效期 从哪天到哪天有效，过期就作废
其他额外信息 证书序列号、扩展字段等

Certificate 的作用就是认证公钥持有者的身份，证明 Server 的合法性，以防止第三方进行冒充。 换句话说：证书的本质是——"这个公钥属于这个网站"的担保书。

还有一个细节：服务器发送的往往不是一张证书，而是证书链（Certificate Chain）——从网站自己的证书，一路到根 CA 的证书（第 8 章会展开讲证书链，这里先知道"发的是一串证书"）。

CA 怎么签发证书？（左半张图）¶

CA 签发证书的过程可以分解为三步（结合《图解网络》的图，图左半部分）：

原始信息（持有者公钥、用户名、颁发者、有效期……）
        │
        ▼
  ① 用哈希算法计算  ──────────────►  得到摘要（指纹）H
        │
        ▼
  ② 用 CA 自己的私钥加密这个摘要  ──►  生成数字签名（Certificate Signature）
        │
        ▼
  ③ 把数字签名拼进证书文件      ──►  得到最终的数字证书

第一步：CA 把"持有者的公钥、用户、颁发者、有效期"等信息打包，用哈希算法算出一个摘要（指纹）。

第二步：CA 用自己的私钥把这个摘要加密，得到数字签名——这一步就是"盖公章"。因为私钥只有 CA 有，所以这个签名理论上只有 CA 能造出来。

第三步：把数字签名附加到证书文件中，形成完整的数字证书，交给网站部署。

核心思想：CA 私钥 = 唯一公章。 谁能拿出"CA 私钥加密过的摘要"，谁就真的被 CA 认证过。

客户端怎么验证证书？（右半张图）¶

浏览器/操作系统里预置了各家 CA 的公钥（根证书），这是验证的起点。验证分三步（图右半部分）：

收到证书
    │
    ▼
① 对证书里的原始信息（不含签名）重新算哈希
    │
    ▼
② 用内置的 CA 公钥解开证书里的数字签名   ──►  得到 CA 当初算的摘要 H2
    │
    ▼
③ 比较 H1 和 H2
    ├── 相同 ──► 证书可信（没被改过，确实是该 CA 签的）
    └── 不同 ──► 证书不可信（被篡改过，或根本不是这个 CA 签的）
  • H1：客户端用同样的哈希算法，对证书中的"原始信息"重新计算得到的摘要；
  • H2：客户端用 CA 公钥解密数字签名得到的摘要（即 CA 当初算的那个指纹）。

如果 H1 和 H2 相同，则为可信赖的证书，否则认为证书不可信。

为什么这样就能防篡改？做个思维实验：中间人拿到真证书后，把"持有者信息"改成自己的域名，然后把证书再发给客户端。

  • 原始信息变了 → H1 必然改变（哈希的"指纹"特性）；
  • 但中间人没有 CA 的私钥，无法重新生成匹配的签名；
  • 客户端用 CA 公钥解开签名得到 H2（还是原封不动的旧摘要）→ H1 ≠ H2 → 验证失败，浏览器弹出"不安全"警告。

中间人改任何一个字都逃不过验证——数字签名把证书内容"焊死"了。

顺便说一句：验证通过后，客户端还会额外检查证书的有效期（是否过期）、域名（是否和访问的网址匹配）、CA 是否在信任列表里，全部通过才放行。

证书的吊销：出问题了怎么办？¶

私钥泄露、域名不再使用、CA 发现发错了……证书还没过期就得作废，这个过程叫吊销（Revocation）。目前有两种主流标准：

1. CRL（Certificate Revocation List，证书吊销列表）¶

  • 是什么：CA 维护一张被吊销证书的序列号清单（这些证书并没有过期）。
  • 怎么用：客户端（或服务器）定期去 CA 下载这个清单，看看手上的证书在不在里面。
  • 缺点：列表越来越大（要列出所有被吊销但没过期的证书），下载慢、实时查询起来非常慢。就像查一本越来越厚的"黑名单通讯录"，翻起来费劲。

2. OCSP（Online Certificate Status Protocol，在线证书状态协议）¶

  • 是什么：允许客户端实时查询单张证书的吊销状态。
  • 怎么用：客户端拿着证书序列号去问 CA 的 OCSP 服务器："这张证书还活着吗？"服务器回"活着/吊销了"。
  • 优点：实时查询、精准定位，解决了 CRL"清单太肥、查询太慢"的最大缺点。
  • 缺点（原文特别点出）：并没有解决所有吊销问题——OCSP 本身也带来新的问题：
  • 性能问题：每次连接都多一次查询，增加延迟；
  • 隐私问题：CA 能看到"谁在什么时间查询了哪张证书"，相当于知道用户访问了哪些网站；
  • 新的漏洞：查询服务器可能宕机（有的客户端此时会"静默放行"，反而更不安全）、可能被劫持返回假状态等。

现实中的折中方案：OCSP Stapling（OCSP 装订）——服务器自己定期去 CA 拉取"证书状态证明"，在握手时直接带给客户端，既实时又省去客户端额外查询。这是加分项，面试提出来很亮眼。

一个完整的"证书故事"串讲¶

  1. 网站向 CA 申请证书，CA 核实身份后：算指纹 → 用 CA 私钥加密指纹 → 拼成数字证书。
  2. 握手时服务器把证书链发给客户端。
  3. 客户端：重新算 H1 → 用内置 CA 公钥解签名得 H2 → 比对 → 再查有效期、域名、吊销状态。
  4. 全部通过 → 认定"这个公钥真是该网站的"→ 用它加密 pre-master 寄回去。
  5. 一旦证书私钥泄露，立即向 CA 申请吊销 → CA 把它列入 CRL，或让 OCSP 查询返回"已吊销"。

本章知识点小结¶

  • 证书 = CA 盖章的"公钥归属"担保书，内容含服务器公钥、持有者信息、CA 信息、数字签名、有效期。
  • CA = 网络公证处，它的私钥是整个信任体系的"唯一公章"。
  • 签发 = 对信息算哈希 → CA 私钥加密哈希 → 得到签名，拼入证书。
  • 验证 = 重算 H1 → CA 公钥解签名得 H2 → 比对 → 再查有效期/域名/吊销状态。
  • 吊销有 CRL（黑名单清单，越来越大、查询慢）和 OCSP（实时单查，快但有性能/隐私/漏洞问题）。
