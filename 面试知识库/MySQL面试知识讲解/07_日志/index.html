07 日志¶

本章覆盖：日志文件分类、binlog、undo log、redo log、两阶段提交、update 执行过程、数据不丢失保障、double write。

这是 MySQL 面试的"深水区"，逻辑链：持久性靠 redo log → redo 与 binlog 的一致性靠两阶段提交 → 崩溃恢复的可靠性靠 double write。建议按顺序读。

1. 日志文件是分成了哪几种？¶

一句话回答¶

MySQL 日志分两大类：服务器日志（错误日志、慢查询日志、通用日志，服务管理用）和 数据日志（binlog、redo log、undo log，数据一致性和恢复用）。面试重点永远是后者三个。

完整分类表¶

日志 层级 作用 面试权重
binlog（二进制日志） Server 层 记录所有写操作（逻辑日志），用于主从复制、数据恢复 ⭐⭐⭐
redo log（重做日志） InnoDB 层 记录"数据页被改成什么样"（物理日志），崩溃恢复用 ⭐⭐⭐
undo log（回滚日志） InnoDB 层 记录"修改前的旧值"，回滚 + MVCC 用 ⭐⭐⭐
错误日志 error log Server 层 启动/运行错误、警告 ⭐
慢查询日志 slow query log Server 层 执行超过阈值的 SQL，性能排查 ⭐⭐
通用日志 general log Server 层 记录所有 SQL，默认关闭 ⭐
中继日志 relay log 从库 主从复制中继 binlog ⭐

核心三件套对比（面试必背）¶

对比项 binlog redo log undo log
所属层级 Server 层 InnoDB 层 InnoDB 层
记录内容 SQL/行变更（逻辑） 物理页变更（哪页哪偏移改成什么） 修改前的旧值
写入时机 事务提交时 事务执行过程中 事务执行过程中
主要用途 主从复制、PITR 恢复 崩溃恢复（持久性） 回滚（原子性）、MVCC
文件格式 追加写，可循环/滚动 固定大小循环写 追加写，可清理
没有它 从库无法同步 宕机丢数据 无法回滚

面试回答模板¶

"日志分服务日志（错误、慢查询、通用）和数据日志（binlog、redo、undo）。binlog 是 Server 层的逻辑日志，负责复制和恢复；redo log 是 InnoDB 的物理日志，负责崩溃恢复保证持久性；undo log 记旧值，负责回滚和 MVCC。面试重点在 redo 和 binlog 的关系（两阶段提交）。"

2. 讲一下 binlog¶

一句话回答¶

binlog（二进制日志）是 Server 层的逻辑日志，记录所有改变数据的操作（INSERT/UPDATE/DELETE/DDL），追加写、按事件记录，核心用途是主从复制和基于时间点的数据恢复。

三种记录格式（必背）¶

格式 内容 优点 缺点
STATEMENT 记录的 SQL 语句本身 日志小 依赖函数/顺序，重放可能结果不一致（如 NOW()、UUID()）
ROW（8.0 默认） 记录"哪一行从什么值变成什么值" 精确，重放结果一定一致 日志体积大
MIXED 自动选择 折中 难预测

典型结构（ROW 格式）¶

# 一个 binlog 事件包含：
# - 变更前/后的行数据（ROW 格式）
# - 事务标识、时间戳、执行位置（pos）

binlog 的两大用途¶

① 主从复制（核心用途） 

主库: 事务提交 → binlog 落盘
从库: IO 线程拉取 binlog → 写入自己的 relay log（中继日志）
     SQL 线程重放 relay log → 从库数据与主库一致
（详见 09 章主从复制）

② 数据恢复（PITR，point-in-time recovery） 

# 场景：误删了全表
# 1. 用最近的全量备份恢复数据库
# 2. 把备份时刻之后的 binlog 重放到"误删之前"的位置
mysqlbinlog --stop-position=xxx binlog.000123 | mysql -u root -p
把数据恢复到"任意时间点"，所以 binlog 是 DBA 的后悔药。

其他细节¶

  • 配置：log-bin=mysql-bin 开启；binlog_format=ROW 设格式
  • binlog 文件名带序号滚动：mysql-bin.000001、mysql-bin.000002……
  • 查看 binlog：SHOW BINARY LOGS;（列表）、mysqlbinlog mysql-bin.000001（内容）
  • binlog 与 redo log 的"两阶段提交"关系见本章第 7 节

面试回答模板¶

"binlog 是 Server 层的逻辑日志，三种格式 STATEMENT/ROW/MIXED，8.0 默认 ROW。两个用途：主从复制（从库拉取重放）和时间点恢复（全量备份+binlog 回放到指定位置）。binlog 在事务提交时写入，和 redo log 通过两阶段提交保持一致。"

3. Undo Log 日志的作用是什么？¶

一句话回答¶

undo log 是 InnoDB 的回滚日志，记录每个修改操作执行前的旧值，两大作用：事务回滚（保证原子性）和 MVCC 版本链（让快照读看到历史版本）。

作用一：事务回滚（原子性）¶

BEGIN;
UPDATE account SET balance = 900 WHERE id = 1;
  -- 修改前：把 (id=1, 旧值=1000) 写进 undo log
ROLLBACK;
  -- 读取 undo log，把 balance 恢复成 1000
  • 每条写操作（INSERT/UPDATE/DELETE）都会先记 undo 再改数据
  • 回滚时按 undo log 逆序恢复（后执行的先恢复，避免覆盖）
  • 执行失败 → 自动回滚；显式 ROLLBACK → 手动回滚

作用二：MVCC 版本链（隔离性）¶

每行数据有隐藏字段 DB_ROLL_PTR 指向它的旧版本，旧版本就存在 undo log 里：

当前行 balance=900（trx_id=100）
   ↑ ROLL_PTR
undo: balance=1000（trx_id=50）
   ↑ ROLL_PTR
undo: balance=800（trx_id=10）

快照读时，根据 ReadView 沿这条链找到"自己可见的版本"（详见 05 章第 11 节）。没有 undo log，MVCC 就无从谈起。

三个操作分别怎么记 undo？¶

操作 undo 记录
INSERT 记录主键，回滚时 DELETE
UPDATE 记录旧值（旧行），回滚时恢复旧行
DELETE 记录被删的行内容，回滚时重新插入

补充细节¶

  • undo log 也先写内存 buffer 再异步落盘，写 undo 本身也有 redo 保护（undo 页的修改也要重做日志）
  • 长事务会导致 undo log 无法清理 → 文件膨胀（详见 05 章第 13 节）
  • 8.0 中 undo log 独立文件存储（undo_001、undo_002），可以配置多个

面试回答模板¶

"undo log 记修改前的旧值，两个作用：一是回滚时恢复旧数据，保证原子性；二是形成 MVCC 版本链，快照读沿链找可见版本，保证隔离性。回滚按逆序执行，INSERT 记主键、UPDATE 记旧行、DELETE 记删除内容。"

4. 有了 UndoLog 为啥还需要 RedoLog 呢？¶

一句话回答¶

因为两者解决的问题完全不同：undo log 解决"回滚"（原子性），redo log 解决"崩溃后重放"（持久性）——一个管"撤销"，一个管"重做"，缺一不可。

关键差异¶

undo log redo log
记录内容 修改前的旧值 修改后的新状态（物理页变更）
服务对象 回滚（原子性）+ MVCC 崩溃恢复（持久性）
什么时候需要 事务失败/回滚时 宕机重启时
能替代吗 ❌ ❌

为什么 undo 不能保证持久性？¶

设想：事务执行完，数据还在内存里（InnoDB 数据页缓存，还没刷盘）： - 此时宕机 → 内存数据丢失 - undo log 里记的是旧值——它只能告诉你"改之前长什么样"，不能告诉你"改之后应该是什么样" - 要恢复"已提交但没落盘"的新数据，必须知道新值/新状态——这正是 redo log 记录的内容

一个完整的故事串起来¶

BEGIN;
UPDATE account SET balance = 900 WHERE id = 1;
  ① undo log：记录旧值 1000（防回滚）
  ② 内存页修改为 900（数据还没落盘）
  ③ redo log：记录"第 X 页 balance 改成 900"（防宕机丢失）
COMMIT;

宕机场景：
  重启后内存数据全没 → 读 redo log 重放 → balance=900 恢复 ✅
失败回滚场景：
  执行中报错 → 读 undo log → balance 恢复成 1000 ✅

面试金句¶

"undo 是'刹车'（撤销修改），redo 是'存档'（保住成果）。刹车坏了车停不下来，存档丢了成果找不回，两个机制管两件事，谁也不能替代谁。"

5. Redo Log 怎么保证持久性的？¶

一句话回答¶

WAL 机制（Write-Ahead Logging，先写日志再写数据）：事务提交时先把 redo log 刷到磁盘（顺序写，很快），数据页可以稍后慢慢刷；崩溃后重放 redo log，把已提交但没落盘的数据恢复出来。

WAL 核心流程¶

① 事务执行：修改内存中的数据页（buffer pool）
② 同步生成 redo log 记录（先写内存中的 redo buffer）
③ 提交（COMMIT）时：把 redo log 刷入磁盘 ← 关键一步！
④ 数据页异步刷盘（后台线程慢慢刷，或 buffer 满时刷）
⑤ 宕机：数据页没来得及刷？没关系，重放 redo log 即可

为什么这样就能保证持久性？¶

  • 提交成功的标志 = redo log 落盘成功（而不是数据页落盘）
  • 只要 redo log 在磁盘上，数据就"不会丢"——即使数据页没刷，重启后用 redo 重放
  • 数据页刷盘只是优化（让读更快、腾出内存），不是持久性的前提

redo log 本身的落盘策略（group commit）¶

参数 含义 默认
innodb_flush_log_at_trx_commit 提交时刷 redo 的策略 1（最安全）

三种策略： - =1（默认）：每次提交都 fsync 刷盘 → 最安全，性能略低（每次提交一次磁盘写） - =0：提交时不刷，靠后台定时刷（1秒）→ 快但可能丢最近 1 秒的数据 - =2：提交时写入操作系统缓存（不强制 fsync）→ 每秒刷盘；MySQL 挂了不丢（数据在 OS 缓存），整个机器断电才丢1秒数据

补充：为什么 redo log 刷盘快？¶

  • redo log 是顺序写（追加到文件末尾），磁盘顺序写比随机写快 10 倍以上
  • 数据页刷盘是随机写（分散在不同位置）
  • WAL 的本质：把随机写变成顺序写，用顺序写换持久性

面试回答模板¶

"持久性靠 WAL：提交时强制 redo log 落盘（顺序写），数据页异步刷。落盘策略 innodb_flush_log_at_trx_commit 三档：1 最安全每次提交刷、0 最快每秒刷但 MySQL 崩了丢 1 秒、2 写 OS 缓存断电才丢。默认 1，事务场景必须 1。"

6. 能不能只用 binlog 不用 redo log？¶

一句话回答¶

不能。binlog 是逻辑日志（记 SQL/行变更），redo log 是物理日志（记页变更），redo 的实时性和物理特性是 binlog 替代不了的；binlog 在事务提交才写、格式是逻辑的，宕机恢复时既来不及也不精确。

逐个理由分析¶

① 写入时机不同（最致命） - redo log：事务执行过程中就写（还没提交也要记，因为可能崩溃） - binlog：事务提交时才写 - 如果只靠 binlog：事务执行一半宕机，binlog 里根本没有记录 → 内存里改了一半的数据页无法恢复

② 记录粒度不同 - redo log：物理级，记录"哪个页、哪个偏移、改成什么" → 恢复时直接重放物理操作，快且精确 - binlog：逻辑级，记录 SQL 或行变更 → 恢复时要重新执行逻辑，慢，且 STATEMENT 格式重放结果可能不一致（NOW() 等函数）

③ 覆盖范围不同 - redo log 循环写、覆盖旧记录，只服务"最近的崩溃恢复" - binlog 全量追加、可回放任意时间点，服务"复制和 PITR" - 两者记录的信息有一份冗余，但用途不同，不能互相替代

④ 数据页的物理变更无法用逻辑日志重建 - redo log 连"页内空间整理、页分裂"这类物理操作都记录 - binlog 完全不知道页层面的变化

唯一相似点¶

两者都"追加写、顺序 IO"，所以常常被问"能不能合并"——MySQL 的做法不是合并，而是用两阶段提交保证它们一致（下一节）。

面试回答模板¶

"不能。一是时机：redo 在事务执行中就写，binlog 提交时才写，半途宕机只有 redo 能救；二是粒度：redo 是物理页日志可精确重放，binlog 是逻辑日志重放慢且 STATEMENT 格式有不确定；三是用途：redo 管崩溃恢复，binlog 管复制和 PITR。两者是'同一件事的两个侧面'，必须共存，靠两阶段提交对齐。"

7. binlog 两阶段提交过程是怎么样的？¶

一句话回答¶

MySQL 提交事务时，让 redo log 和 binlog 两份日志都成功落盘且内容一致，采用 prepare → 写 binlog → commit 三个阶段（所以叫两阶段提交）。目的是防止"redo 已写、binlog 没写"导致主从数据不一致，或"binlog 已写、redo 没写"导致主备恢复不一致。

为什么需要两阶段提交？¶

两份日志独立写，崩溃时机不同会导致不一致：

场景A（先 redo 后 binlog，中途崩）：
  redo 已写（主库恢复后数据在），binlog 没写（从库没同步）
  → 主库有新数据，从库没有 → 主从不一致 ❌

场景B（先 binlog 后 redo，中途崩）：
  binlog 已写（从库同步了新数据），redo 没写（主库恢复后丢了这个事务）
  → 从库有，主库没有 → 更严重的不一致 ❌

两阶段提交让"redo 落盘 + binlog 落盘"成为一个不可分割的整体：要么都成功，要么都回滚。

完整过程（三个阶段）¶

事务执行中：生成 redo log（含 XID 事务号）和 binlog，先都留在内存

┌─ 阶段一：prepare（准备）─────────────────────┐
│ ① 把 redo log 写入磁盘（状态：prepare）       │
│    redo 记录里带着 XID                        │
└──────────────────────────────────────────────┘
┌─ 阶段二：写 binlog ──────────────────────────┐
│ ② 把 binlog 写入磁盘（也带 XID）              │
│    （此刻崩溃 → 恢复时发现 redo prepare 但     │
│     binlog 无记录 → 回滚该事务，安全）         │
└──────────────────────────────────────────────┘
┌─ 阶段三：commit（提交）──────────────────────┐
│ ③ 把 redo log 标记为 commit（此刻崩溃 →      │
│    redo prepare + binlog 有记录 → 重放恢复，  │
│    数据不丢）                                │
└──────────────────────────────────────────────┘

崩溃时的恢复判定规则（面试核心）¶

重启时扫描 redo log 和 binlog，按 XID 配对：

redo 状态 binlog 状态 处理
无该事务 无 事务没执行完，丢弃
prepare 无该事务记录 回滚（binlog 没落盘 → 主库不能有这个事务，否则从库没有）
prepare 有该事务记录 重放提交（binlog 已落盘 → 从库会有，主库必须有）
commit 有 已完成，正常恢复

补充：组提交（group commit）¶

高并发下多个事务的提交会合并刷盘：多个 prepare 的 redo 一次 fsync、多个 binlog 一次 fsync，大幅减少磁盘 fsync 次数。MySQL 8.0 里组提交与 binlog 写入深度整合。

面试回答模板¶

"两阶段提交 = redo prepare → binlog 落盘 → redo commit。崩溃恢复按 XID 配对判定：redo prepare 且 binlog 有记录 → 提交（从库会有）；redo prepare 且 binlog 无记录 → 回滚（保证主从不一致最小化）。目的：让主库崩溃恢复结果和从库重放结果完全一致。"

8. Update 语句的具体执行过程是怎样的？¶

一句话回答¶

一条 UPDATE 的完整链路：解析优化 → 加锁定位行 → 写 undo log → 改内存数据页 → 写 redo log → 更新二级索引 → 写 binlog → 提交（两阶段）→ 后台刷盘。

完整执行流程（面试按这个顺序背）¶

以 UPDATE account SET balance = 900 WHERE id = 1 为例：

① Server 层：连接器验证权限 → 解析器 → 优化器生成执行计划
② 执行器：调用 InnoDB 接口，按主键 id=1 从聚簇索引定位记录
③ 加锁：对 id=1 的记录加 X 锁（行锁）
   - 若该行已被其他事务锁住 → 等待
④ 写 undo log：记录修改前的旧值（balance=1000），形成版本链
⑤ 修改内存中的数据页：buffer pool 中 balance 改为 900
   - 数据页不在内存 → 先从磁盘读入 buffer pool 再改
⑥ 写 redo log（内存中的 redo buffer，标记 prepare）：
   记录"第 X 页 balance 从 1000 改为 900"
⑦ 若 balance 列有二级索引 → 同步更新二级索引（旧索引项删、新索引项插）
⑧ 执行器告知 Server 层"修改完成"
⑨ 提交阶段（两阶段提交）：
   a. redo log 刷盘（prepare）
   b. 写 binlog 并刷盘
   c. redo log 标记 commit
⑩ 释放锁；后台线程择机把脏数据页刷到磁盘

关键节点对照（什么操作对应什么日志/锁）¶

步骤 对应机制
第 ③ 步 行锁（X 锁），写写互斥
第 ④ 步 undo log（原子性 + MVCC）
第 ⑤ 步 buffer pool（内存页），未立即落盘
第 ⑥ 步 redo log（持久性），WAL
第 ⑨ 步 两阶段提交（redo/binlog 一致）
第 ⑩ 步 异步刷盘（checkpoint）

注意点¶

  • UPDATE 是"当前读"：先按当前最新版本定位行（可能要走 MVCC 之外的锁读），再修改
  • 无索引的 WHERE → 全表扫描加锁（见 06 章第 5 题）
  • UPDATE 分两步：定位（SELECT 的流程）+ 修改（写链路的流程）

面试回答模板¶

"UPDATE 的链路：定位（当前读+加 X 锁）→ 写 undo（旧值）→ 改内存页 → 写 redo（prepare）→ 更新二级索引 → 两阶段提交（redo prepare → binlog → redo commit）→ 释放锁 → 异步刷盘。核心记忆：undo 记旧值、redo 记新值、binlog 供复制、锁保证互斥。"

9. MySQL 是如何保障数据不丢失的？¶

一句话回答¶

三层保障：事务提交时 redo log 落盘（WAL）保证"已提交不丢"；两阶段提交保证 redo/binlog 一致（主从一致）；binlog 提供"误删可回放"的时间点恢复。加上定期全量备份，构成完整的防丢体系。

逐层拆解¶

第一层：WAL + redo log（防宕机） - 提交 = redo log 落盘成功（innodb_flush_log_at_trx_commit=1） - 数据页没刷没关系，重启后重放 redo log - 保障：已提交的事务，任何时刻宕机都不丢

第二层：两阶段提交（防主从不一致） - redo 和 binlog 原子对齐 - 保障：主库恢复后的数据 = 从库重放后的数据（不出现"主有从无"或"从有主无"）

第三层：binlog + 全量备份（防误删） - 定期全量备份（mysqldump / Xtrabackup） - 误删/误改后：全量恢复 + binlog 回放到误操作前 - 保障：人为事故也能找回

第四层：double write（防半页写） - 防止"写了半个页"的脏页在宕机后污染（详见第 12 节）

不同故障级别对照¶

故障 保障机制 结果
MySQL 进程崩溃 redo log 不丢
服务器断电 redo log（+双写） 不丢（配置=1）
磁盘损坏 全量备份 + binlog 恢复到最近时间点
误删数据 binlog PITR 恢复到误删前
从库损坏 重新从主库/备份同步 可恢复

面试回答模板¶

"MySQL 防丢体系：redo log WAL 保'提交不丢'，两阶段提交保'主从不乱'，double write 防'半页写坏'，binlog+全量备份兜底'误删找回'。四层配合，从进程崩溃到人为事故都有方案。"

10. RedoLog 是在内存里吗？¶

一句话回答¶

有内存部分，也有磁盘部分：redo log 先写在内存的 redo log buffer 里，在特定时机（提交、buffer 满、后台定时）刷到磁盘上的 redo log 文件。面试重点在于"它在哪一层、什么时候落盘"。

完整形态¶

内存（快）：                 磁盘（慢但可靠）：
┌─────────────────┐         ┌─────────────────┐
│ redo log buffer │ ──刷盘──▶ │ redo log 文件     │
│ (redo 缓冲，    │         │ (ib_logfile* /    │
│  默认16MB)      │         │  #ib_redo* 循环写) │
└─────────────────┘         └─────────────────┘

写入时机（什么时候从内存刷到磁盘）¶

  1. 事务提交时（innodb_flush_log_at_trx_commit 决定策略，见第 5 节）
  2. redo log buffer 写满（默认 16MB，innodb_log_buffer_size 可调）→ 强制刷
  3. 后台线程定时刷（约每秒一次）
  4. 数据页刷盘前（保证"先日志后数据"的顺序）

所以"数据在哪"要分三层理解¶

数据 位置
数据页 buffer pool（内存）→ 异步刷到 .ibd 文件
redo log redo buffer（内存）→ 提交时刷到 redo log 文件
binlog binlog buffer（内存）→ 提交时刷到 binlog 文件

面试常见追问¶

  • "redo log buffer 一直不刷会怎样？" → 崩溃丢已执行未提交的数据（未提交本来就不该存在，无害）；但已提交未刷会丢——所以提交时必须刷
  • "redo log 文件循环写满了会怎样？" → 触发 checkpoint：把 buffer pool 里对应的脏页强制刷盘，刷完的 redo 空间才能复用

面试回答模板¶

"redo log 内存部分叫 redo log buffer（默认16MB），提交/写满/定时三个时机刷到磁盘文件。关键不是它在哪，而是'提交时必须落盘'——这是持久性的保证。"

11. 为什么要写 RedoLog，而不是直接写到 B+树里面？¶

一句话回答¶

因为写 redo log 是顺序写（快），写 B+树是随机写（慢），而且"日志先落盘、数据页后台慢慢刷"让提交延迟极低。直接写 B+树要么慢死，要么提交后还没落盘就崩了。

核心对比¶

直接写 B+树的问题： 1. 随机 IO：B+树数据页分散在磁盘各处（索引分层、页分裂），改一行要写"索引页+数据页"多处随机位置 → 一次提交多次随机写，慢 10~100 倍 2. 提交无法立即落盘：如果等数据页全部落盘才返回提交成功，延迟爆炸；如果不落盘就返回，崩溃即丢 3. 页分裂等物理操作：插入引发的页分裂是重量级操作，不能每次提交都做

写 redo log 的好处： 1. 顺序 IO：redo log 追加到文件末尾，磁盘顺序写极快（配合组提交批量刷） 2. 先记账后干活：把"这次改了什么"记下来就算提交成功，数据页的物理修改交给后台慢慢做 3. 崩溃恢复兜底：重启后重放 redo log，把没做完的物理修改补上

形象比喻¶

  • 直接写 B+树 = 每次消费都当场清点全店库存（慢、且容易出错）
  • 写 redo log = 先记流水账（一行字，快），库存清点晚上再统一做（后台刷盘），账本不丢就丢不了货

数据流总结¶

提交时：日志先行（顺序写 redo，毫秒级）
后台：数据页异步刷盘（随机写，慢慢来）
崩溃时：重放 redo log 补齐未刷的数据页

面试回答模板¶

"写 redo log 的本质是 WAL：把'随机写数据页'延迟化，提交时只做一次快速顺序写（日志），数据页异步刷。这样提交延迟低、吞吐高，崩溃时用日志补齐。直接写 B+树是随机 IO，一次提交要写多个分散页，又慢又无法保证原子落盘。"

12. MySQL 两次写（double write buffer）了解吗？¶

一句话回答¶

double write（双写）是 InnoDB 应对半页写（partial page write）问题的机制：刷盘前先把整页数据备份一份到独立的 doublewrite 文件，万一写数据页时断电导致"只写了半个页"，崩溃恢复时能用备份页修复。8.0.20 之前默认开启，8.0.20 后支持关闭（依赖 redo 页级校验恢复）。

问题背景：什么是"半页写"？¶

  • 磁盘写入的最小单位是扇区（512 字节~4KB），而 InnoDB 数据页是 16KB
  • 刷一个 16KB 页 = 多次扇区写入，可能写到一半断电
  • 结果：磁盘上这个页一半是新数据、一半是旧数据（校验和失效，整个页损坏）
  • 更糟的是：redo log 记录的是"页的变更"，基于损坏页重放会越补越错——redo 没法修复半页
  • 这就是 double write 存在的意义

double write 工作原理¶

刷盘流程：
① 把脏页拷贝到内存的 doublewrite buffer（2MB）
② 把整个 buffer 顺序写入磁盘上的 doublewrite 文件（顺序写，快）
③ 再把脏页写回各自的数据文件位置（随机写）

崩溃恢复：
① 扫描 doublewrite 文件，发现数据页损坏（校验失败）
② 用 doublewrite 里的备份页覆盖损坏页
③ 再正常重放 redo log

代价与权衡¶

说明
代价 每次刷盘多写一份（2MB buffer 顺序写），约多 5%~10% 的写开销
收益 杜绝半页写导致的数据页损坏，redo 恢复才可靠
8.0.20+ 默认改用"redo log 记录完整页"的方式恢复半页，可关闭 doublewrite 提升性能（innodb_doublewrite=OFF），但要权衡

面试回答模板¶

"double write 防半页写：断电可能让 16KB 数据页只写了一半，redo 基于损坏页重放会雪上加霜。InnoDB 刷盘前先把整页备份到 doublewrite 文件，恢复时用备份修复。代价是多一次顺序写（约5%-10%性能），换数据页的完整性。8.0.20 之后 InnoDB 可以靠 redo 页级校验恢复，doublewrite 可选关闭。"
