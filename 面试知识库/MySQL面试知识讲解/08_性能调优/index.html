08 性能调优¶

本章覆盖：explain 的作用与字段解读、怎么查看是否走索引、怎么查看表的索引、慢查询排查方案、如何干预优化器选错索引。

1. MySQL 的 explain 有什么作用？¶

一句话回答¶

EXPLAIN 是 MySQL 的执行计划查看器：在 SELECT 前加 EXPLAIN，MySQL 不真正执行查询，而是输出"它打算怎么查"——走哪个索引、扫多少行、是否回表、是否排序，是 SQL 优化最核心的工具。

基本用法¶

EXPLAIN SELECT * FROM student WHERE class_id = 3 AND score > 90;

输出一张表，每行代表查询的一部分（多表 JOIN 会有多行）：

+----+-------------+---------+------------+------+---------------+---------+---------+-------+------+----------+-------+
| id | select_type | table   | partitions | type | possible_keys | key     | key_len | ref   | rows | filtered | Extra |
+----+-------------+---------+------------+------+---------------+---------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | student | NULL       | ref  | idx_class     | idx_class | 4       | const | 100  |    10.00 | NULL  |
+----+-------------+---------+------------+------+---------------+---------+---------+-------+------+----------+-------+

关键字段逐个讲（面试按 type/key/rows/Extra 四个说）¶

① type（访问类型，最重要）——从好到差：

type 含义 好坏
system 表只有一行（系统表） 最好
const 主键/唯一索引等值查询，最多返回 1 行 极好
eq_ref 唯一索引关联查询（JOIN 用主键） 很好
ref 普通索引等值查询 好
range 索引范围查询（>、BETWEEN、IN） 可接受
index 扫描整个索引树（比全表好一点） 一般
ALL 全表扫描 ❌ 要优化

② key / possible_keys - possible_keys：可能用到的索引 - key：实际使用的索引（空 = 没用索引） - key_len：用到的索引字节数（联合索引中可判断用了几列，如 4=只用1个INT列，8=用了2列）

③ rows - 预估扫描的行数（越小越好） - 是全表扫描的 rows = 表总行数

④ Extra（附加信息，暗藏问题）

Extra 值 含义 处理
Using index 覆盖索引，不回表 ✅ 最理想
Using where 索引后还做了过滤 正常，注意量
Using filesort 额外排序（没用索引排序） ⚠️ 优化：让排序列进索引
Using temporary 用了临时表（GROUP BY/DISTINCT） ⚠️ 优化
Using index condition 索引条件下推（ICP） ✅ 5.6+ 自动
NULL 正常回表 看 rows

变体：EXPLAIN ANALYZE（8.0.18+）¶

EXPLAIN ANALYZE SELECT ...;
真实执行并输出每步的实际耗时和实际行数，比估算的 explain 更准。

面试回答模板¶

"explain 看执行计划，重点看四列：type（ALL 要警惕，range 及以上合格）、key（是否命中索引）、rows（预估扫描量）、Extra（filesort/temporary 是优化信号）。8.0 的 EXPLAIN ANALYZE 还能给实际执行耗时。"

2. 怎么查看是否有走索引？¶

一句话回答¶

用 EXPLAIN 看两列：key 是否非空（用了哪个索引）和 type 是否为 ALL（全表扫描），再配合 rows 看扫描行数。

判断步骤（三步法）¶

-- 第一步：explain
EXPLAIN SELECT * FROM user WHERE phone = '13800000000';

-- 第二步：看关键字段
-- 1. key != NULL → 有索引
-- 2. type != ALL → 不是全表扫描（range/ref/const 都好）
-- 3. rows 远小于表总行数 → 索引有效缩小范围

对照判断表¶

key type 结论
非空 ref / range / const ✅ 走了索引，效果良好
非空 index ⚠️ 扫了整棵索引树（索引失效的一种）
NULL ALL ❌ 全表扫描，没走索引
NULL const ✅ 表很小（如 1 行），无所谓

注意误区¶

  • type 是 index 不等于好：index 是"遍历整棵索引树"，只是比 ALL 少回表，数据量大的时候一样慢
  • key 非空 ≠ 一定高效：联合索引可能只用了其中一列（看 key_len），或者 rows 依然很大
  • 慢查询日志 + explain 组合拳：慢查询日志找出慢 SQL → explain 分析 → 对症下药

面试回答模板¶

"explain 看 key 是否命中、type 是否为 ALL、rows 是否合理。三列一起判断：key 有值但 type=ALL 说明优化器放弃索引；key_len 能看出联合索引实际用了几列。快速口诀：'key 非空、type 不过 ALL、rows 越小越好'。"

3. 怎么查看表的索引？¶

一句话回答¶

两条命令：SHOW INDEX FROM 表名（或 SHOW KEYS FROM 表名）看全部索引详情；EXPLAIN 看某个查询实际用哪个。

命令与输出解读¶

SHOW INDEX FROM student;

关键输出列：

列 含义
Table 表名
Non_unique 0=唯一索引（含主键），1=普通索引
Key_name 索引名（PRIMARY=主键索引）
Seq_in_index 联合索引中的第几列（1,2,3…）
Column_name 索引列名
Collation A=升序，D=降序
Cardinality 区分度（不同值数量，除以总行数=区分度）
Index_type BTREE（InnoDB 都是 B+树）
Comment / Index_comment 备注

快速理解 Cardinality（面试加分）¶

  • Cardinality 表示索引的唯一值数量：越大越好
  • 性别字段的 Cardinality ≈ 2，手机号 ≈ 表行数
  • 用它判断"这个索引值不值得建"

其他查看方式¶

-- 查看建表语句（包含所有索引定义）
SHOW CREATE TABLE student;

-- 查看某查询实际用哪个索引（最常用）
EXPLAIN SELECT * FROM student WHERE class_id = 3;

面试回答模板¶

"SHOW INDEX FROM t 看索引定义（Key_name、Seq_in_index、Column_name、Cardinality），Cardinality 反映区分度；SHOW CREATE TABLE 看完整 DDL；EXPLAIN 看实际查询用了哪个。查'有哪些索引'用前者，查'走得对不对'用后者。"

4. 给你张表，发现查询速度很慢，你有那些解决方案？¶

一句话回答¶

按"先定位、再对症"的思路：定位慢 SQL（慢查询日志）→ EXPLAIN 分析执行计划 → 按病因处理（索引缺失/索引失效/回表太多/SQL 写法/大事务锁冲突/数据量过大分库分表）。

排查流程（面试按这个步骤背）¶

第一步：找到慢 SQL 

-- 开启慢查询日志（阈值默认10秒）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
-- 看日志：data 目录下的 *-slow.log

第二步：EXPLAIN 定位病因 重点看 type / key / rows / Extra（见本章第 1 节）。

第三步：按病因对症下药

病因（EXPLAIN 特征） 解决方案
type=ALL，key=NULL（没索引） 给 WHERE/JOIN/ORDER BY 列建索引
索引失效（函数、隐式转换、前置%…） 改写 SQL（见 04 章第 24 节）
rows 大但 type=ref/range 加联合索引、加更精确的条件
Extra=Using filesort 让 ORDER BY 列进索引
Extra=Using temporary 优化 GROUP BY / DISTINCT
回表太多（没有 Using index） 覆盖索引
表数据量巨大（千万级以上） 分库分表、归档冷数据、读写分离
大事务/锁等待（不是查询本身慢） 查 information_schema.innodb_trx、缩短事务
缓存没命中 调大 buffer_pool_size、加 Redis 缓存

第四步：SQL 写法层面的常规优化 1. 避免 SELECT *：只取需要的列（减少回表和网络传输） 2. 分页优化：LIMIT 100000, 20 改成"上次最大 id"游标分页 3. 避免深分页/大偏移：WHERE id > 100000 LIMIT 20 4. IN 改 JOIN / 批量改分批：大 IN 列表拆批 5. 避免大事务：拆分、分批提交

面试回答模板¶

"标准流程：慢查询日志找 SQL → EXPLAIN 分析 → 分类处理：没索引就建、索引失效就改写、回表多就覆盖索引、排序慢就索引排序、表太大就分库分表。同时检查是不是被锁/大事务拖慢——查询慢不一定是查询的问题。"

5. 如果 Explain 用到的索引不正确的话，有什么办法干预吗？¶

一句话回答¶

从软到硬四招：ANALYZE TABLE 刷新统计信息（治本，最常用）→ 改写 SQL 引导优化器（治本）→ FORCE INDEX 强制指定（应急，立竿见影）→ 调整索引设计（治本，一劳永逸）。不建议上来就 FORCE INDEX。

四招详解¶

① ANALYZE TABLE：刷新统计信息（首选）

优化器选索引靠的是统计信息（基数 cardinality），数据大变后统计过期就会选错：

ANALYZE TABLE student;   -- 重新统计，让优化器重新评估
- 8.0 之前是手动，8.0 后有些统计自动更新，但大批量导入/删除后仍建议手动

② 改写 SQL：给优化器更多提示

-- 优化器算错成本？把条件写得更能命中目标索引
-- 或拆成更明确的两段查询（UNION 等）
SELECT * FROM t WHERE a = 1 AND b = 2;   -- 比 WHERE b = 2 AND a = 1 更有引导性？不一定，但更可读

③ FORCE INDEX / USE INDEX：强制指定（应急）

-- 强制走 idx_name（优化器必须用，除非走不了）
SELECT * FROM user FORCE INDEX (idx_name) WHERE name = '张三';

-- 建议优先（USE INDEX 优化器仍可能拒绝）
SELECT * FROM user USE INDEX (idx_name) WHERE name = '张三';

-- 忽略某个索引
SELECT * FROM user IGNORE INDEX (idx_name) WHERE ...

注意：FORCE INDEX 是人肉干预，索引统计一变可能失效（数据变化后这个索引可能真的变差），必须配合监控定期复查，生产环境慎用。

④ 设计层面根治（最终方案）

  • 重建索引：ALTER TABLE t DROP INDEX old, ADD INDEX new (列, 顺序调整)
  • 调整联合索引顺序：让优化器更倾向它
  • 删除干扰索引：多个索引并存时优化器容易选错，删掉冗余索引让目标更明确

面试回答模板¶

"先 ANALYZE TABLE 刷新统计——优化器选错索引多半是统计过期；不行就改写 SQL 引导；再不行 FORCE INDEX 应急（但要备注风险：统计一变强制索引可能失效）；根本解法是调整索引设计（顺序、冗余）。顺序：软干预 → 硬干预 → 根治。"

6. 补充：调优工具与日常体检（了解即可）¶

常用命令速查¶

-- 当前执行的 SQL（发现慢查询/锁等待）
SHOW PROCESSLIST;

-- 当前活跃事务
SELECT * FROM information_schema.innodb_trx\G

-- 锁等待情况
SELECT * FROM information_schema.innodb_lock_waits\G

-- 表状态（行数、数据大小、索引大小）
SHOW TABLE STATUS LIKE 'student'\G

-- 缓冲池命中率
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';

优化优先级思维¶

索引优化 > SQL 改写 > 缓存（Redis）> 读写分离 > 分库分表——从便宜到贵，一步步来。
