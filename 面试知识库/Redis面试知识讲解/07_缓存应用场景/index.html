07 缓存应用场景¶

本章覆盖：为什么使用 Redis（高性能/高并发）、为什么 Redis 比 MySQL 快、本地缓存和 Redis 缓存的区别、单机并发量量级、Redis 应用场景总览、除了缓存还有哪些应用（消息队列/分布式锁）、Redis 支持并发操作吗。

1. 为什么使用 Redis？¶

一句话回答¶

因为 Redis 具备两大特性：高性能（内存读写，比访问数据库快得多）和高并发（单机 QPS 轻松破 10 万，是 MySQL 的 10 倍）。

展开讲：高性能¶

  • 用户第一次访问 MySQL 数据时，从硬盘读取，比较慢；
  • 把数据缓存到 Redis 后，下次访问直接操作内存，速度飞快；
  • 如果 MySQL 数据变了，同步改一下 Redis 缓存即可（注意：这里会引入"Redis 和 MySQL 双写一致性"问题，见第 9 章）。

展开讲：高并发¶

  • Redis 单机 QPS 轻松破 10w；
  • MySQL 单机 QPS 很难破 1w。

所以直接访问 Redis 能扛住的请求量远大于直接访问 MySQL。做法：把数据库的部分数据搬到缓存里，用户请求先打到缓存，只有缓存没命中才落到数据库，数据库压力骤减。

比喻¶

MySQL 像仓库（东西全但找东西慢），Redis 像柜台货架（只放热门商品，拿取快）。用户来了先看货架，货架没有才去仓库翻。

2. 为什么 redis 比 mysql 要快？¶

一句话回答¶

三个原因：内存 vs 磁盘（Redis 读内存、MySQL 读磁盘）、数据结构简单（Redis 哈希查询 O(1)，MySQL B+ 树 O(logN)）、单线程免竞争。

展开讲¶

原因 1：存储介质不同

  • Redis：内存存储，读写不涉及磁盘 I/O；
  • MySQL：磁盘存储，频繁磁盘 I/O（机械盘毫秒级，内存是纳秒级，差几个数量级）。

原因 2：数据结构不同

  • Redis：键值对，简单结构（字符串、哈希、列表、集合、有序集合）。哈希表查询 O(1)；
  • MySQL：需要定义表结构、索引等复杂关系型结构，底层是 B+ 树，查询 O(logN)。

原因 3：线程模型不同

  • Redis：单线程，避免了多线程竞争，省去线程切换开销，不会死锁；
  • MySQL：多线程并发访问，需要锁机制协调。

面试怎么答¶

三个点：内存 vs 磁盘、O(1) vs O(logN)、单线程免竞争。先答第一个（最重要），后两个补充。

3. 本地缓存和 Redis 缓存的区别？¶

一句话回答¶

本地缓存存在应用自己的进程内存里（快、免费、但只本机可见）；Redis（分布式缓存）存在独立的缓存服务器上（能共享、能扩展、但要网络访问）。

展开讲：本地缓存¶

指把数据存在本地应用程序/服务器的内存里（如 JVM 的 ConcurrentHashMap、Caffeine、Guava Cache）。

优势： - 访问速度快：本地内存，无需网络； - 减轻网络压力：不访问远程服务器； - 低延迟：适合实时性要求高的场景。

不足： - 可扩展性有限：受单台机器硬件限制，装不下大规模数据； - 关键缺陷：多个应用实例之间不共享——用户请求打到 A 机器命中缓存，打到 B 机器就 miss。

展开讲：Redis（分布式缓存）¶

数据存在多个分布式节点上，协同提供服务。

优势： - 可扩展性强：节点可以动态扩展，支持大规模数据； - 数据共享：多个应用实例访问同一个 Redis，状态全局共享； - 易于维护：自动化管理，降低维护成本。

不足： - 访问速度相对较慢：要经过网络； - 网络开销大：数据传输有网络成本。

怎么选（面试加分点）¶

场景 选哪个
数据量小、实时性要求高、单实例内使用（本地配置、临时计算结果） 本地缓存
数据量大、需要在多个应用实例间共享（分布式会话、全局热点数据） Redis
网络状况差/不稳定 本地缓存更稳
网络好、需要大规模并发 Redis

比喻¶

  • 本地缓存像自己口袋里的便签：掏出来就看（快），但只有你自己看得见；
  • Redis 像公司公告栏：要看要走到公告栏前（网络访问），但全公司人都能看到、都能往上贴。

4. 高并发场景，Redis 单节点 + MySQL 单节点能有多大的并发量？¶

一句话回答¶

缓存命中时，4 核 8G 配置的 Redis 能支撑 10 万 QPS；缓存未命中落到 MySQL，单节点只能支持 5000 左右 QPS。

展开讲¶

  • 缓存命中的话：4 核心 8G 内存的配置，redis 可以支撑 10w 的 QPS；
  • 缓存没命中的话：同样配置下，mysql 只能支持 5000 左右 QPS。

面试怎么答¶

直接报两个数字（10w vs 5000），然后补一句："所以缓存命中率决定了系统能扛多大并发，缓存设计的核心目标就是提高命中率。"

5. redis 应用场景是什么？¶

一句话回答¶

Redis 基于内存、读写极快，常用在缓存、排行榜、分布式锁、计数器、消息队列等场景。

展开讲（背下这五个）¶

  1. 缓存（最常用）：热门数据放内存，提高访问速度、减轻数据库负载；
  2. 排行榜：Zset 有序集合，天然适合排序和排名系统；
  3. 分布式锁：利用 Redis 的特性（SET NX + 原子操作）保证多进程/多服务间的操作原子性和一致性；
  4. 计数器：原子操作 + 高性能，适合网站访问量统计、点赞数统计；
  5. 消息队列：发布订阅功能（Pub/Sub）实现轻量级消息队列，实时处理消息。

面试怎么答¶

报出五类场景各配一句话。重点：缓存、排行榜（Zset）、分布式锁——这三个是面试官最爱追问的。

6. Redis 除了缓存，还有哪些应用？¶

一句话回答¶

两大应用：消息队列（Pub/Sub 模式 或 List 结构）和分布式锁（SET NX 方式 或 RedLock 算法）。

展开讲：消息队列¶

方式一：Pub/Sub（发布订阅）

  • 任何客户端可以订阅一个或多个频道；发布者向频道发消息，所有订阅者都收到；
  • 优点：实现简单、发布者和订阅者完全解耦、支持模式匹配订阅；
  • 缺点：不支持消息持久化（消息发布后没有订阅者在线会被丢弃）；不保证消息的顺序和可靠传输。

方式二：List 结构

  • LPUSH 把消息推入列表，消费者用 BLPOP/BRPOP 阻塞式取出（先进先出 FIFO）；
  • 优点：实现简单的任务队列；可结合过期时间实现消息 TTL；配合事务保证原子性；
  • 缺点：需要客户端自己实现消息确认、重试等机制，比专门的消息队列系统（Kafka/RabbitMQ）功能弱。

展开讲：分布式锁¶

方式一：SET NX 方式（最常用）

SET resource_name lock_value NX PX milliseconds：

  • NX：只有 key 不存在时才设置成功（相当于"抢占锁"）；
  • PX：锁的有效时间（毫秒），防止客户端拿锁后挂掉导致死锁。

解锁时：先判断锁是不是自己的，再删除——两步操作要用 Lua 脚本保证原子性（详见第 8 章）。

方式二：RedLock 算法

  • Redis 作者提出的更可靠的分布式锁：基于多个独立的 Redis 实例；
  • 原理：客户端在多数（大于半数）实例上同时加锁成功，才算拿到锁；
  • 锁的超时时间应远小于单个实例的超时时间，避免死锁；
  • 好处：跨多个节点，减少单点故障影响，提高锁的可用性和安全性。

面试怎么答¶

消息队列答"Pub/Sub 简单但不持久化、List 能做队列但功能弱"，分布式锁答"SET NX + Lua 解锁"，加分项是 RedLock 的名字和作用。

7. Redis 支持并发操作吗？¶

一句话回答¶

支持。单条命令天然原子（单线程执行）；多个操作可以用事务（MULTI/EXEC）保证一致性。

展开讲¶

单个 Redis 命令的原子性：

Redis 单条命令要么完全执行成功，要么完全不执行，不会出现执行一半的情况。这对并发操作非常重要——比如多个客户端同时 INCR 同一个 key，结果不会错乱。

多个操作的事务：

Redis 支持事务，用 MULTI、EXEC、DISCARD、WATCH 管理：

  • MULTI：开启事务；
  • 之后发的命令入队不执行；
  • EXEC：一起执行；
  • DISCARD：放弃事务；
  • WATCH：监控 key，被改动则事务失败（乐观锁思路）。

面试怎么答¶

"单命令原子 + 事务保证多命令一致"，然后可以补一句"不过 Redis 事务出错不回滚，严谨的原子性用 Lua 脚本"（呼应第 4 章）。
