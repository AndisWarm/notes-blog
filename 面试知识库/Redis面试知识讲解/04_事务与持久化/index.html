04 事务与持久化¶

本章覆盖：Redis 的原子性（单命令 / Lua 脚本 / MULTI+EXEC）、AOF 日志与三种刷盘策略、RDB 快照、混合持久化、AOF 与 RDB 优缺点对比。持久化是 Redis 面试的高频考点。

1. 如何实现 Redis 原子性？¶

一句话回答¶

单条命令天然原子（单线程执行）；多条命令要保证原子性，用 Lua 脚本把多个操作包成一个整体执行，执行过程不会被其他命令打断。

展开讲：为什么单命令是原子的¶

Redis 执行命令是单线程的，一条命令要么完整执行完，要么不执行，不存在多线程同时改同一个数据的竞争问题。

展开讲：多条命令怎么办¶

单条命令原子，但两条命令之间就可能被别的命令插进来。比如分布式锁解锁，要"先判断锁是不是自己的"+"再删除锁"两步，两步之间万一被别的客户端插入操作，锁就可能误删。

解法：Lua 脚本。把多个操作写进一个 Lua 脚本，Redis 会把整个脚本作为一个整体执行，执行过程中不会被其他命令打断，从而保证原子性。

释放锁的经典 Lua 脚本：

// 释放锁时，先比较 unique_value 是否相等，避免锁的误释放
if redis.call("get",KEYS[1]) == ARGV[1] then
    return redis.call("del",KEYS[1])
else
    return 0
end

比喻¶

单条命令像一个人盖章，盖一个章没人抢；多条命令像要盖两个章，中间可能有人插队。Lua 脚本就是把两个章连成一次盖章动作，中途谁也插不进来。

2. 除了 Lua，有没有什么也能保证 Redis 的原子性？¶

一句话回答¶

Redis 事务（MULTI + EXEC）也能保证多条操作的原子性，但只在"正常执行、无错误"时有效；如果事务执行中某条命令出错，Redis 不提供回滚机制，不保证原子性。

展开讲：MULTI + EXEC 用法¶

# 开启事务
127.0.0.1:6379> MULTI
OK
# 发送事务中的第一个操作（此时只入队，不执行）
127.0.0.1:6379> LPOP a:stock
QUEUED
# 发送事务中的第二个操作
127.0.0.1:6379> DECR b:stock
QUEUED
# 实际执行事务
127.0.0.1:6379> EXEC

展开讲：出错时不回滚（关键考点）¶

Redis 事务没有回滚机制。举例子：事务中 LPOP 对一个 String 类型的数据操作，入队时不报错（类型检查在执行时才做），EXEC 执行时报错：

127.0.0.1:6379> EXEC
1) (error) WRONGTYPE Operation against a key holding the wrong kind of value
2) (integer) 8

结果是：LPOP 没执行成功，但 DECR 成功执行了——第一个操作失败不影响第二个操作继续执行。

总结：Redis 对事务原子性的保证¶

  • 事务正常执行（所有命令都没错）→ 可以保证原子性；
  • 事务执行中某条命令出错 → 不保证原子性（已执行的命令不撤销）。

面试怎么答¶

先答 Lua 脚本，再答事务，重点强调"Redis 事务出错不回滚"这个和 MySQL 事务最大的区别。还可以说一句：Redis 官方甚至建议不要依赖事务的原子性，出错场景用 Lua 更靠谱。

3. Redis 有哪 2 种持久化方式？分别的优缺点是什么？¶

一句话回答¶

Redis 的持久化共有三种方式：AOF 日志（记写命令）、RDB 快照（存某一时刻的二进制数据）、混合持久化（4.0 新增，AOF 重写时用 RDB 格式打底 + AOF 命令追加）。

为什么需要持久化¶

Redis 读写都在内存，性能才高，但重启后内存数据就没了。持久化把数据存到磁盘，重启时从磁盘恢复。

AOF 日志：记"操作"¶

每执行一条写操作命令，就把命令以追加的方式写入文件。重启时读文件、逐条重放命令来恢复数据。

优点： - 数据安全性更高（默认 everysec 策略最多丢 1 秒数据）； - 支持多种同步策略，可按需平衡安全性和性能； - 支持重写机制压缩文件体积，加快恢复； - 文件损坏可用 redis-check-aof 工具修复。

缺点： - 记录了每个写操作，文件通常比 RDB 大，更占磁盘； - 频繁磁盘 I/O（尤其 always 策略）会影响写入性能； - 恢复时要重放所有命令，文件大时恢复慢。

RDB 快照：存"数据"¶

把某一时刻的内存数据以二进制方式写入磁盘，像给数据拍一张照片。恢复时直接把文件读入内存即可。

优点： - 文件体积小，备份和恢复非常快； - 通过 fork 子进程生成，不阻塞主线程处理命令； - 定期快照，文件通常比 AOF 小得多。

缺点： - 两次快照之间的数据，如果服务器故障就丢了； - 快照创建到恢复期间有写操作的话，恢复后的数据可能与故障前不完全一致。

混合持久化（4.0 新增）¶

开启方式：配置 aof-use-rdb-preamble yes。

原理：AOF 重写时，先以 RDB 二进制格式写入内存当前状态，再把重写期间新收到的写命令以 AOF 格式追加在后面。

恢复时：先加载 RDB 部分（快速），再回放后续 AOF 命令（补最新）——既有 RDB 快速恢复的特点，又保留 AOF 低丢失率的优势。

面试怎么答¶

"三种方式：AOF 记命令、RDB 拍快照、4.0 混合"。然后说各自优缺点时抓住精髓：AOF 丢得少但恢复慢文件大，RDB 恢复快文件小但两次快照间可能丢数据。

4. AOF 日志是如何实现的？（三种刷盘策略）¶

一句话回答¶

Redis 执行完写命令后，把命令追加到 aof_buf 缓冲区 → 事件循环结束前 write() 到内核 page cache → 再由 fsync() 决定何时真正落盘。三种策略（always / everysec / no）的区别就是 fsync() 的时机。

展开讲：写入链路¶

以 set name xiaolin 为例，执行完这条命令后，AOF 文件里记录的是这条命令本身（RESP 协议格式）。写入分三步：

  1. 命令先追加到用户态的 aof_buf 缓冲区；
  2. 事件循环结束前调用 write() 把 aof_buf 内容写入内核 page cache（此时还没真正落盘）；
  3. fsync() 决定何时把 page cache 刷到硬盘。

write() 只是写进内核的"草稿区"（page cache），断电照样丢；只有 fsync() 才真正写进硬盘。所以三种策略拼的就是什么时候 fsync。

三种写回策略¶

配置项 appendfsync：

策略 fsync 时机 安全性 性能
Always 每次写命令执行完，立即 fsync 最高（最多丢一条刚写的） 最差
Everysec 每隔 1 秒，由后台线程 fsync 一次 宕机最多丢约 1 秒数据 中（默认值）
No 不主动 fsync，交给操作系统自行刷盘（page cache 写满或约 30 秒一次） 最低，丢失量不可控 最好

比喻¶

aof_buf 像记事本上的草稿，write() 像把草稿誊到桌面备忘录（断电就没了），fsync() 像把备忘录内容锁进保险柜（断电也在）。

  • Always：每写一句就开一次保险柜 → 最安全也最累；
  • Everysec：每攒 1 秒开一次保险柜 → 万一停电最多丢最后一秒的内容；
  • No：攒着，等保险公司（操作系统）想起来才锁 → 最轻松但丢多少没准。

5. RDB 快照是如何实现的？¶

一句话回答¶

RDB 快照把某一时刻的内存数据以二进制存成文件；提供 save（主线程执行，会阻塞）和 bgsave（子进程执行，不阻塞）两个命令生成。

展开讲：为什么需要 RDB¶

AOF 记的是命令不是数据，恢复时要把日志全量执行一遍。AOF 日志一多，恢复就慢。RDB 直接存某一时刻的实际数据，恢复时直接把文件读入内存就行，不需要执行命令，所以恢复效率更高。

展开讲：save vs bgsave¶

命令 谁执行 会不会阻塞主线程
save 主线程 会！写入时间长就会阻塞
bgsave 子进程 不会，后台生成

面试时强调：生产环境用 bgsave，save 会阻塞主线程导致 Redis 无法服务请求。

补充：为什么说"某一时刻"¶

RDB 是定期快照（比如每 5 分钟一次），所以两次快照之间的数据，如果服务器故障就丢了——这正是它和 AOF 的区别（AOF 最多丢 1 秒）。

面试怎么答¶

"RDB 存数据、恢复快；bgsave 用子进程不阻塞主线程；缺点是两次快照之间的数据会丢。"
