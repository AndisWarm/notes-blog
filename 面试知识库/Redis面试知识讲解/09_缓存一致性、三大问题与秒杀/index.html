09 缓存一致性、三大问题与秒杀¶

本章覆盖：Redis 和 MySQL 双写一致性（旁路缓存 + 最终一致性方案）、缓存雪崩/击穿/穿透（三大问题必考）、布隆过滤器原理、秒杀场景的高并发与防超卖设计。

1. 如何保证 Redis 和 MySQL 数据缓存一致性问题？¶

一句话回答¶

读：用旁路缓存（Cache Aside）策略，缓存不命中就从数据库加载并回填缓存；写：先更新数据库，再删除缓存；极端情况下用消息队列重试或订阅 binlog 兜底，达到最终一致性。

展开讲：读数据——旁路缓存策略¶

  • 读请求先查缓存（Cache）；
  • 缓存命中 → 直接返回；
  • 缓存不命中 → 从数据库（DB）加载数据 → 回填到缓存 → 返回。

展开讲：写数据——更新 DB 后删缓存¶

写操作选择"先更新数据库，再删除缓存"（而不是"先更新缓存"或"删了缓存再更新 DB"），原因：更新 DB 后删缓存，下次读 miss 时自然会加载新数据，逻辑最简单，且并发窗口最小。

为什么说缓存只能追求"最终一致"¶

缓存是通过牺牲强一致性来提高性能的——这是 CAP 理论决定的：

  • 缓存系统适用非强一致场景，属于 CAP 中的 AP；
  • 如果需要数据库和缓存强一致，就不适合用缓存。

所以缓存一定要设置过期时间，且长短要权衡：

  • 太短：请求更多落到数据库，失去缓存优势；
  • 太长：脏数据让系统长时间处于"延迟一致"状态；而且长时间没人访问的数据一直占内存，浪费。

展开讲：删除缓存失败怎么办（两个兜底方案）¶

"先更新 DB，再删缓存"如果删除缓存失败，缓存里就一直是旧数据。两个方案兜底：

方案一：消息队列重试（删除缓存重试策略）

  1. 把"删除缓存"这个操作的数据加入消息队列，由消费者执行删除；
  2. 删除失败 → 从消息队列重新读取数据，再次删除（重试机制）；重试超过一定次数还没成功 → 向业务层报错；
  3. 删除成功 → 把数据从消息队列移除，避免重复操作。

缺点：对业务代码产生较多侵入（要引入 MQ）。

方案二：订阅 MySQL binlog，再删缓存（Canal + MQ）

"先更新数据库"成功就会产生一条 binlog 变更日志：

  1. 用 Canal 中间件订阅 binlog——Canal 模拟 MySQL 主从复制的交互协议，伪装成 MySQL 的从节点向主节点发 dump 请求；
  2. MySQL 把 Binlog 推送给 Canal，Canal 解析成结构化数据；
  3. 把 binlog 日志采集发送到 MQ 队列；
  4. 编写一个"缓存删除消费者"订阅 binlog 日志，根据更新日志删除缓存，并用 ACK 机制确认处理，保证数据缓存一致性。

优点：对业务代码零侵入（业务只负责更新数据库），是目前最主流的方案。

面试怎么答¶

主线："读走旁路缓存，写先更新 DB 再删缓存，缓存设过期时间做兜底"。面试官追问"删缓存失败怎么办"→ 答 MQ 重试 / Canal 订阅 binlog，两个方案都要能说出原理。

2. 缓存雪崩、击穿、穿透是什么？怎么解决？（必考，三个概念一定要分清）¶

一句话回答¶

  • 雪崩：大量缓存同时过期或 Redis 宕机 → 海量请求直接压垮数据库；
  • 击穿：某一个热点 key 过期 → 大量请求同时打数据库；
  • 穿透：请求的 key 缓存和数据库都没有 → 每次都打到数据库。

区别一句话：雪崩是"一片没了"，击穿是"一个热点没了"，穿透是"压根没有"。

展开讲：缓存雪崩¶

是什么：大量缓存数据在同一时间过期（失效）或者 Redis 故障宕机时，大量用户请求都无法在 Redis 中处理，全部直接访问数据库 → 数据库压力骤增，严重的直接宕机，形成连锁反应，整个系统崩溃。

比喻：商场几百个商家同一天倒闭（同时过期），顾客全涌向仓库（数据库），仓库被挤爆。

解决方案：

  1. 均匀设置过期时间：避免大量数据同一时间过期 → 给过期时间加上一个随机数，把过期时间打散；
  2. 互斥锁：发现数据不在 Redis 里，加个互斥锁，保证同一时间只有一个请求去构建缓存（查 DB → 写 Redis）；其他请求要么等锁释放后重新读缓存，要么返回空值/默认值。注意锁要设超时时间，防止第一个请求异常一直不释放锁导致全系统无响应；
  3. 后台更新缓存：缓存不设置有效期（永久有效），由后台线程定时更新——业务线程只读缓存，永不 miss。

展开讲：缓存击穿¶

是什么：缓存中某个热点数据过期了，此时大量请求都访问这个热点数据 → 缓存读不到，全部直接访问数据库 → 数据库被高并发请求冲垮。

比喻：一个网红店（单个热点 key）突然停业一天（过期），排队的几万人全涌向总仓库。

解决方案：

  1. 互斥锁：同一时间只有一个业务线程更新缓存，其他请求等待锁释放后重读缓存，或返回空值/默认值（与雪崩的互斥锁方案相同）；
  2. 不给热点数据设置过期时间：由后台异步更新缓存；或者在热点数据准备过期前，提前通知后台线程更新缓存并重新设置过期时间（逻辑过期方案）。

展开讲：缓存穿透¶

是什么：用户访问的数据既不在缓存中，也不在数据库中（比如恶意请求一个不存在的商品 ID）→ 缓存 miss → 查数据库也没有 → 没法构建缓存（总不能缓存"没有"）→ 每个请求都穿透到数据库 → 数据库压力骤增。

比喻：顾客来买一个根本不存在的商品（key 两边都没有），每次都得去仓库翻一遍，翻不到还翻不出名堂（没法缓存结果）。

解决方案：

  1. 非法请求的限制：在 API 入口校验请求参数（是否含非法值、字段是否存在），恶意请求直接返回错误，不访问缓存和数据库；
  2. 缓存空值或默认值：查到数据库也没有时，在缓存中设置一个空值或默认值（设短一点的过期时间），后续请求直接命中缓存返回空值，不再查数据库；
  3. 布隆过滤器（最优雅）：在写入数据库数据时，用布隆过滤器做个标记；请求到来时先查布隆过滤器判断数据是否存在：不存在就直接返回，不用查数据库（详见下一节）。

三兄弟对比表（背这个）¶

雪崩 击穿 穿透
本质 大量 key 同时过期 / Redis 宕机 单个热点 key 过期 key 本来就不存在
范围 大面积 单个点 单个/批量（恶意）
数据库压力 海量请求压垮 热点请求压垮 空查询压垮
核心解法 过期时间加随机数、互斥锁、后台更新 互斥锁、热点不过期 参数校验、缓存空值、布隆过滤器

记忆口诀¶

"雪崩是一堆同时没了，击穿是一个热点没了，穿透是压根没有"。

3. 布隆过滤器原理介绍一下？¶

一句话回答¶

布隆过滤器由「初始值都为 0 的位图数组」+「N 个哈希函数」组成：数据写入时把 N 个哈希值对应的位都置 1；查询时看 N 个位是否全为 1——有一个是 0 就一定不存在，全为 1 才"可能"存在（有误判）。

展开讲：写入数据时（标记操作，三步）¶

  1. 用 N 个哈希函数分别对数据做哈希计算，得到 N 个哈希值；
  2. 把这 N 个哈希值对位图数组长度取模，得到每个哈希值在位图数组的对应位置；
  3. 把每个对应位置的值设置为 1。

举例：位图数组长度 8、3 个哈希函数。写入数据 x 后：

  • x 被 3 个哈希函数算出 3 个哈希值；
  • 对 8 取模，假设结果是 1、4、6；
  • 把位图数组第 1、4、6 位置的值设为 1。

展开讲：查询数据时¶

查询数据 x 是否在数据库中：看位图数组第 1、4、6 位置是否全为 1：

  • 只要有一个位是 0 → 数据 x 一定不在数据库中；
  • 全为 1 → 数据 x 可能存在（也可能不存在，因为可能撞了别的数据的标记）。

展开讲：误判是怎么来的¶

布隆过滤器基于哈希函数，存在哈希冲突：

  • 数据 x 和数据 y 的哈希结果可能落在相同的几个位置（比如都落在第 1、4、6 位）；
  • 数据库中实际没有 y，但因为 x 把 1、4、6 都置 1 了，查询 y 时三个位全为 1 → 误判 y 存在。

核心结论（面试必说）¶

查询布隆过滤器说"存在"，并不一定真存在（可能误判）；但查询说"不存在"，一定不存在（无漏报）。

所以布隆过滤器非常适合做缓存穿透的拦截器：它说没有，就真的没有，直接挡回去；它说有，才放行去查数据库（最多浪费一次查询，不会漏数据）。

比喻¶

像门禁黑名单登记本：每来一个"合法"的客人（写入的数据），就在他名字对应的几格里打勾。查人时：只要有一格没打勾，这人肯定没登记过；但几格都打勾，也可能是别人名字的格子和他重合了（误判）。

4. 如何设计秒杀场景处理高并发以及超卖现象？¶

一句话回答¶

秒杀核心要解决两件事：扛住高并发（不能所有请求都打数据库）和防止超卖（库存不能变负数）。方案从低到高：数据库加锁 → 分布式锁 → 分布式锁+分段缓存 → Redis 原子预减库存 + 异步队列（最常用）。

方案一：在数据库层面解决（最简单但性能差）¶

手段 1：查询库存时加排他锁

select * from goods where goods_id=? for update
  • 事务中给数据行加锁；
  • 其他线程可以 select 读，但再 for update 或 update/delete 都会阻塞，直到线程 A 提交（或回滚）；
  • 缺点：性能差；高并发下可能因为拿不到数据库连接或超时等待而报错。

手段 2：更新时带库存限制条件

update goods set stock = stock - 1 where goods_id = ? and stock > 0
  • stock > 0 条件保证不会减成负数（防超卖的关键）；
  • 但依然要数据库承受并发压力。

方案二：利用分布式锁¶

  • 同一个锁 key，同一时间只有一个客户端拿到锁，其他客户端无限等待；
  • 拿到锁的才能执行减库存业务。

缺点：同一个商品的多用户下单被串行化处理——1000 个人抢同一个商品，只能一个一个来，没法并行，吞吐量很差。

方案三：分布式锁 + 分段缓存（并行化改造）¶

把库存分成多段，每段一个锁，多个线程可以并发修改不同段：

  • 假设商品有 100 个库存，在 Redis 放 5 个库存 key：
key1=goods-01, value=20
key2=goods-02, value=20
key3=goods-03, value=20
key4=goods-04, value=20
key5=goods-05, value=20
  • 用户下单时对用户 ID 取模（%5），落在哪个 key 就去哪个段扣减 → 同一时间能处理 5 个进程请求。

坑：某段锁的库存不足时，要自动释放锁并换下一个分段再次尝试加锁处理，实现复杂度较高。

方案四：利用 Redis 的 incr/decr 原子性 + 异步队列（最推荐）¶

完整流程（五步）：

  1. 系统初始化：把商品库存数量加载到 Redis 缓存中；
  2. 预减库存：收到秒杀请求，用 DECR（原子性）在 Redis 中预减库存：
  3. Redis 库存不足（减成负数/小于 0）→ 直接返回秒杀失败；
  4. 库存充足 → 进入第 3 步；
  5. 放入异步队列：把请求放入异步队列，返回"正在排队中"给用户；
  6. 异步出队落库：服务端异步队列出队（可加业务判断，如"该用户是否已秒杀过，防止重复秒杀"），出队成功的请求生成秒杀订单、减少数据库库存（扣减 SQL 依然带 stock > 0 条件防超卖），返回订单详情；
  7. 用户轮询结果：用户在客户端轮询查看是否秒杀成功，成功进入订单详情，失败则提示秒杀失败。

优点：Redis 的 DECR 原子性天然防超卖；数据库只在异步队列里承受"出队量"的压力（远小于秒杀请求量），扛住高并发。

缺点：异步写入数据库可能存在短暂数据不一致；引入了 Redis + MQ + 数据库多个组件，复杂度较高。

面试怎么答¶

从简单到复杂说方案演进，重点讲方案四（Redis 预减库存 + 异步队列）的五步流程，并强调两个细节：DECR 原子性防超卖、数据库扣减带 stock > 0 条件双保险。能画出这个演进过程，秒杀题就稳了。
