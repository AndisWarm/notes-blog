06 集群架构¶

本章覆盖：主从复制的全量同步与增量同步、主从/集群能保证数据一致性吗（CAP 理论）、哨兵机制原理、哨兵选主算法、Redis Cluster 切片集群（哈希槽）、客户端怎么知道访问哪个分片。这是进阶面试的必考内容。

1. Redis 主从同步中的增量和完全同步怎么实现？¶

一句话回答¶

完全同步：首次连接或数据差太多时，主服务器把整个数据集的 RDB 快照发给从服务器；增量同步：断线重连后，主服务器根据复制偏移量，只把断线期间错过的写命令发给从服务器。都用 PSYNC 命令协调。

展开讲：完全同步（全量）¶

什么时候触发：

  • 初次同步：从服务器第一次连接主服务器；
  • 从服务器数据丢失（如断电）后请求同步；
  • 从服务器长时间未同步，数据差异太大。

完整流程（三个阶段、六个步骤）：

第一阶段：建立链接、协商同步 → 第二阶段：主服务器同步数据 → 第三阶段：主服务器发送新写命令。

  1. 从服务器发送 SYNC/PSYNC 命令：请求开始同步；
  2. 主服务器生成 RDB 快照：保存当前数据集到临时文件；
  3. 传输 RDB 文件：主服务器把 RDB 文件发给从服务器；
  4. 从服务器应用 RDB：清空自己当前的数据，载入 RDB 中的数据；
  5. 主服务器记录写命令：RDB 生成和传输期间，主服务器把新收到的写命令记到 replication backlog buffer；
  6. 传输写命令：RDB 传完后，主服务器把 backlog buffer 里的命令发给从服务器执行，保证数据一致。

注意第 5、6 步：RDB 是"拍照瞬间"的数据，拍照之后新来的写命令必须补发给从服务器，否则从服务器就落后了。

展开讲：增量同步（断点续传）¶

从服务器断线重连后，不需要重新全量同步，从断点继续就行。基于 PSYNC，用两个概念：

  • 运行 ID（run ID）：标识主服务器身份；
  • 复制偏移量（offset）：同步进度标记。

三个步骤：

  1. 从服务器恢复网络后，发 psync 命令，offset 参数不再是 -1（-1 表示首次全量同步）；
  2. 主服务器用 CONTINUE 响应，告诉从服务器"接下来增量复制"；
  3. 主服务器把断线期间执行的写命令发给从服务器执行。

展开讲：主服务器怎么知道发哪些增量？¶

答案在两个组件里：

  • repl_backlog_buffer（环形缓冲区）：主服务器传播写命令时，不仅发给从服务器，还会写入这个缓冲区，所以它保存着最近传播的写命令；
  • replication offset（复制偏移量）：主服务器用 master_repl_offset 记自己"写"到的位置；从服务器用 slave_repl_offset 记自己"读"到的位置。

断线重连时：

  • 从服务器通过 psync 把 slave_repl_offset 发给主服务器；
  • 主服务器对比自己的 master_repl_offset 和从服务器的 slave_repl_offset：
  • 如果从服务器要读的数据还在缓冲区里 → 增量同步（把差的部分发过去）；
  • 如果已经被环形缓冲区覆盖了 → 全量同步（重新来一遍）。

展开讲：环形缓冲区被覆盖怎么办（重要调优点）¶

repl_backlog_buffer 默认只有 1M，而且是环形的：写满了就覆盖最旧的数据。

  • 如果主服务器写入速度远快于从服务器读取速度，缓冲区很快被覆盖；
  • 网络恢复时，从服务器想读的数据已被覆盖 → 主服务器只能全量同步，性能损耗大很多。

调优：把 repl_backlog_buffer 调大一些，减少"要读的数据被覆盖"的概率，让主服务器尽量走增量同步。

比喻¶

  • 全量同步像新学期开学：老师把整本教材（RDB）重新发一遍；
  • 增量同步像补课：你请了一周假，回来只需要把这一周的课堂笔记（断线期间的命令）补上，不用重学整本书。

2. redis 主从和集群可以保证数据一致性吗？¶

一句话回答¶

不能保证强一致。Redis 主从和集群在 CAP 理论里属于 AP 模型：网络分区时选择"可用性和分区容忍性"，牺牲"强一致性"，所以可能出现部分节点数据不一致。

展开讲：CAP 是什么¶

CAP 三个属性：

  • C（Consistency）一致性：所有节点同一时刻看到的数据相同；
  • A（Availability）可用性：系统一直能响应请求；
  • P（Partition tolerance）分区容忍性：网络出故障（节点间通信断了）系统还能工作。

CAP 定理：三者最多同时满足两个。

Redis 的选择¶

Redis 主从和集群在网络分区时，选择：

  • 保证 P（分区容忍性）：继续提供服务；
  • 保证 A（可用性）：请求还能被处理；
  • 牺牲 C（强一致性）：部分节点之间数据可能不一致。

后果：主从复制是异步的，主节点写成功就返回了，从节点可能还没同步到；如果此时主节点挂了、从节点顶上，读到的就是"旧数据"。

面试怎么答¶

"Redis 属于 CAP 的 AP，网络分区时牺牲强一致性换可用性，所以主从数据可能短暂不一致。"再补一句："如果需要强一致，就不能用 Redis 做核心数据的存储，只能做缓存（缓存本身也不要求强一致）。"

3. 哨兵机制原理是什么？¶

一句话回答¶

哨兵（Sentinel）是 Redis 2.8 提供的故障转移机制：监控主节点是否存活，主节点挂了就自动把某个从节点提升为新主节点，并通知从节点和客户端。它干三件事：监控、选主、通知。

展开讲：为什么需要哨兵¶

主从模式是读写分离的：主节点写，从节点读。如果主节点挂了：

  • 没有主节点服务写请求；
  • 没有主节点给从节点同步数据；
  • 如果人工介入：手动挑一个从节点转正、让其他从节点指向它、再通知客户端换 IP——太不智能了。

哨兵就是解决这个问题的"自动运维机器人"。

展开讲：哨兵是什么¶

  • 哨兵是一个运行在特殊模式下的 Redis 进程，本身也是一个节点；
  • 它是"观察者节点"，观察主从节点；
  • 发现异常会自动"动手"修复：把从节点升为主节点，通知其他人。

三件事：监控、选主、通知¶

  1. 监控：定时发心跳包检测主从节点是否存活；
  2. 选主：主节点挂了，从从节点中选一个提升为新主节点；
  3. 通知：把新主节点的信息告诉其他从节点（重新指向新主）和客户端（更新连接地址）。

比喻¶

哨兵像大厦的保安队长：平时巡逻（监控），发现老板（主节点）不在岗，就从员工里提拔一个临时负责人（选主），再通知全公司员工都向新负责人汇报（通知）。

4. 哨兵机制的选主节点的算法介绍一下？¶

一句话回答¶

选主分四步：主观下线 → 客观下线 → 哨兵集群选 Leader → Leader 决定新主节点。

第一步：故障节点"主观下线"¶

每个哨兵节点定时对 Redis 集群所有节点发心跳包。

  • 如果一个节点在 down-after-milliseconds 时间内没有回复心跳，该节点就被这个哨兵标记为"主观下线"。

注意关键词：主观——只是"我感觉它挂了"，不一定真挂（可能只是网络抖动）。

第二步：故障节点"客观下线"¶

一个哨兵说挂了不算数，要大家说了算：

  • 该哨兵询问其他哨兵节点；
  • 如果超过 quorum（法定人数） 数量的哨兵都认为该节点主观下线 → 该节点被判为客观下线。

之后分情况：

  • 客观下线的是从节点或哨兵节点 → 到此为止，没有后续操作；
  • 客观下线的是主节点 → 开始故障转移，从从节点里选一个升级为主节点。

第三步：哨兵集群选举 Leader¶

从从节点里选新主之前，先要从哨兵集群里选一个 Leader 来拍板：

  • 每个哨兵都可以竞选 Leader；
  • 一个哨兵确认主节点主观下线后，请求其他哨兵投票给自己；
  • 其他哨兵如果还没同意过别人，就投它一票（票数 +1），否则拒绝；
  • 得票达到 Leader 最低票数 = max(quorum, 哨兵总数/2 + 1) 就当选；否则重新选举。

例子：3 个哨兵，quorum=2，任何一个哨兵拿到 2 票就能当选 Leader。

第四步：Sentinel Leader 决定新主节点¶

Leader 从从节点中选新主，按优先级依次判断：

  1. 过滤掉故障的节点（不健康的不考虑）；
  2. 选 slave-priority（优先级）最大 的从节点（配置文件可设，数字越大优先级越高）——不存在继续；
  3. 选 复制偏移量最大 的从节点（偏移量=已同步的数据量字节数；偏移量越大说明数据越全、越接近主节点）——不存在继续；
  4. 选 runid 最小 的从节点（runid 是 Redis 每次启动生成的随机标识）。

为什么选偏移量大的？¶

复制偏移量表示"从节点收到了主节点多少数据"：偏移量越大，和主节点数据越接近，转正后丢失的数据越少。

面试怎么答¶

按四步背：主观下线（心跳超时）→ 客观下线（quorum 哨兵确认）→ 哨兵选 Leader（过半票数）→ Leader 选新主（过滤故障 → 优先级最大 → 偏移量最大 → runid 最小）。能说出"偏移量最大"这一步，基本就满分了。

5. Redis 集群的模式了解吗？优缺点了解吗？¶

一句话回答¶

缓存数据量大到单台服务器装不下时，用 Redis Cluster（切片集群）：把 16384 个哈希槽分给多个节点，每个 key 通过 CRC16 算法 + 取模 映射到某个槽，从而把数据分散到不同服务器。

展开讲：为什么需要切片集群¶

单机 Redis 内存有限，数据太多装不下 → 需要分片：把数据分布到多台服务器，降低对单主节点的依赖，提高读写性能。

展开讲：哈希槽机制（核心）¶

一个切片集群共有 16384 个哈希槽（类似数据分区）。key → 槽 → 节点的映射分两步：

  1. 根据 key 用 CRC16 算法计算一个 16 bit 的值；
  2. 用这个值对 16384 取模，得到 0~16383 的模数，每个模数对应一个哈希槽。

哈希槽怎么分配给节点？两种方案¶

  • 平均分配：cluster create 创建集群时，Redis 自动把 16384 个槽平均分到各节点（如 9 个节点，每个 16384/9 个）；
  • 手动分配：cluster meet 建立节点连接后，用 cluster addslots 指定每个节点的槽：
redis-cli -h 192.168.1.10 -p 6379 cluster addslots 0,1
redis-cli -h 192.168.1.11 -p 6379 cluster addslots 2,3

注意：手动分配时必须把 16384 个槽全部分完，否则集群无法正常工作。

展开讲：优缺点¶

优点：

  • 高可用性：节点间主从复制，一个节点挂了集群还能工作；
  • 高性能：分片把数据分散到多节点，读写性能提升；业务量大时可以加节点提升吞吐量；
  • 扩展性好：可以动态增加或减少节点（部分节点还能做代理自动转发请求）。

缺点：

  • 部署和维护较复杂：要考虑分片规则、节点布置、主从配置、故障处理，需要较强技术支持；
  • 集群同步问题：节点失败或网络故障时会出现数据同步问题；节点越多，同步复杂度和耗时越大，可能带来读写延迟；
  • 数据分片限制：某些功能受限——同一个 key 多次修改可能因节点位置变化失败；不能跨节点操作（如跨节点的多个 key 操作要额外注意）。

比喻¶

哈希槽像快递分拣柜：一共 16384 个格口（槽），每个快递（key）按规则（CRC16 取模）算出该进哪个格口，每个快递站（节点）负责管理一部分格口。

6. Cluster 集群客户端是怎样知道该访问哪个分片的？¶

一句话回答¶

客户端启动后先向任意节点发 CLUSTER SLOTS 命令，拿到全量的"槽位-节点"映射表缓存到本地；访问 key 时先算槽位、查本地缓存找节点；节点变动时靠 MOVED / ASK 重定向更新缓存。

展开讲：完整流程¶

第一步：获取并缓存映射表

客户端启动后，和集群中任意一个节点建立连接，发送 CLUSTER SLOTS 命令，获取全量的"槽位 → 节点（IP + 端口）"映射关系，缓存到本地。

第二步：访问 key

  1. 对 key 做 CRC16 哈希计算；
  2. 对 16384 取模，算出 key 对应的哈希槽；
  3. 查本地缓存的映射表，找到该槽对应的节点地址；
  4. 直接访问这个节点。

第三步：节点变动时更新缓存

如果集群节点有变动（槽位迁移、节点下线）：

  • 客户端访问时会收到节点返回的 MOVED 或 ASK 重定向指令；
  • 客户端根据指令更新本地的槽位映射缓存；
  • 下次访问这个 key 直接找新节点，不用再重定向。

核心价值¶

全程自动完成，开发者不用手动指定分片——这就是 Redis Cluster 能做到"透明分片访问"的原因。

面试怎么答¶

"客户端先拿全量槽位映射表缓存起来，访问时算槽位、查缓存找节点，遇到变动（MOVED/ASK）就更新缓存，全程自动。"
