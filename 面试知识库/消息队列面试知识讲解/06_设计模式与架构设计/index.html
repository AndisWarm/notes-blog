06 设计模式与消息队列架构设计¶

本章覆盖：MQ 参考的设计模式（观察者模式 vs 发布订阅模式）、"让你设计一个消息队列"这类系统设计题的思考框架。

1. 消息队列是参考哪种设计模式？¶

一句话回答¶

参考了观察者模式和发布订阅模式两种，它们思路相同（一对多、订阅通知），区别在于发布者和接收者之间是否完全解耦。

展开讲：先看一个生活例子¶

  • 观察者模式：公司给员工发月饼发粽子，由行政部门直接发。为什么不交给第三方？因为"公司"和"员工"是一个整体（紧密耦合）；
  • 发布-订阅模式：公司给其他人发快递，通过快递公司中转。因为"公司"和"其他人"是独立的，唯一桥梁是"快递"（松散耦合），所以交给第三方更合适。

道理：如果公司自己管理快递配送，公司就变成了快递公司，业务繁杂难以管理，影响主营业务。用哪种模式，取决于双方是否需要耦合。

两种模式图解¶

观察者模式（Observer）¶

一对多关系：一个主题（被观察者） + 多个观察者。主题发布消息时，通知各个观察者。

  主题（被观察者）
    │ 订阅关系建立后，主题发消息会
    │ 循环观察者列表逐一通知
    ▼
 观察者1   观察者2   观察者3

关键特征：观察者先订阅主题，订阅成功后主题发消息时，循环整个观察者列表，逐一发送消息通知。

发布订阅模式（Publish-Subscribe）¶

区别：发布者和订阅者完全解耦，中间通过发布订阅中心（消息代理）通信。发布者不知道自己发的消息会通知给谁。

 发布者 ──► 发布订阅中心（消息代理） ──► 订阅者1
                             ──► 订阅者2
                             ──► 订阅者3

三个角色：发布者 → 发布订阅中心 → 订阅者。发布者把消息发到中心，中心把消息通知给所有订阅者。

对比总结¶

维度 观察者模式 发布订阅模式
耦合度 主题和观察者互相认识 发布者和订阅者完全解耦
中间角色 无（直接通知） 发布订阅中心（消息代理）
发布者知情 知道有哪些观察者 不知道发给谁
MQ 对应 概念来源 实际架构（Broker 就是发布订阅中心）

面试加分点：现代 MQ（Kafka/RocketMQ/RabbitMQ）实际是发布订阅模式——Broker 就是那个"发布订阅中心"，生产者和消费者互不知晓对方存在。

面试怎么答¶

"MQ 的设计灵感来自观察者模式和发布订阅模式。两者都是'一对多订阅通知'，区别在于：观察者模式里主题直接通知每个观察者，双方耦合；发布订阅模式中间多了个消息代理，发布者和订阅者完全解耦。MQ 落地的是发布订阅模式，Broker 就是消息代理。可以用'公司发月饼（观察者）vs 公司发快递（发布订阅）'的比喻快速讲清。"

2. 让你写一个消息队列，该如何进行架构设计？¶

一句话回答¶

不要求你写过 MQ 源码，只要懂基本架构和工作原理。回答框架：先讲整体流程（生产者→Broker→消费者），再逐个攻克 RPC 设计、持久化、消费关系、可靠性、高可用、事务、扩展性这 7 个设计点。

展开讲：这类设计题的考察意图¶

面试官考察三个层面： 1. 你对消息队列架构原理是否了解； 2. 你的个人设计能力； 3. 你的编程思想：高可用、可扩展性、幂等等。

同类问题：设计一个 Dubbo 框架、设计一个 MyBatis 框架。回答这类题不需要研究过源码，知道基本结构 + 工作原理即可。

完整回答框架（8 个设计点）¶

1. 整体流程¶

producer 发消息给 broker，broker 存储好，broker 再发给 consumer 消费，consumer 回复消费确认。这是最基本的骨架。

2. RPC 设计¶

producer 发消息给 broker、broker 发消息给 consumer，需要两次 RPC。如何设计？可以参考开源框架 Dubbo：服务发现（消费者怎么找到 broker 地址）、序列化协议（消息用什么格式传输）等。

3. Broker 持久化设计¶

消息放文件系统还是数据库？

  • 文件系统：性能高（顺序写磁盘），Kafka 的做法；
  • 数据库：管理方便，但性能差；
  • 还要考虑：会不会消息堆积？堆积如何处理？（见 04 章积压）

4. 消费关系如何保存¶

点对点（一个消息只被一个消费者消费）还是广播方式（所有消费者都能收到）？广播关系如何维护？用 ZooKeeper 还是 config server 保存路由/订阅关系？

5. 消息可靠性¶

消息重复了如何幂等处理？生产者 ack 机制？消费者确认机制？（见 03 章）

6. 高可用设计¶

参考 Kafka 的高可用机制：多副本 → leader & follower → broker 挂了重新选举 leader 即可对外服务。（详见 09 章第 7 节）

7. 事务特性¶

消息事务与本地业务同一个事务：本地消息落库（本地业务和消息一起写入数据库事务）→ 消息投递到服务端成功后，本地才删除 → 定时任务扫描本地消息库，补偿发送。

这是经典的"本地消息表"方案：先写库（业务 + 消息表在同一事务），再投递，投递成功删消息，失败由定时任务补偿重发。注意：这是自己写 MQ 时的事务设计思路，和 RocketMQ 的半消息机制（见 05 章）是两条不同路线。

8. 伸缩性和可扩展性¶

消息积压或资源不够时，如何快速扩容提高吞吐？参照 Kafka 的设计理念：broker → topic → partition，每个 partition 放一台机器，存一部分数据。

  • 资源不够 → 给 topic 增加 partition → 数据迁移 → 增加机器 → 存放更多数据、提供更高吞吐。

完整回答速览（面试背这个）¶

设计一个 MQ，我会从 8 个点展开：
① 整体流程：producer → broker（存储）→ consumer → ack
② RPC 设计：参考 Dubbo（服务发现 + 序列化协议）
③ 持久化：文件系统顺序写（参考 Kafka），考虑积压处理
④ 消费关系：点对点/广播，用 ZK 或 config server 维护
⑤ 可靠性：ack + 幂等设计
⑥ 高可用：多副本 + leader 选举（参考 Kafka）
⑦ 事务：本地消息表，同事务落库，定时补偿发送
⑧ 扩展性：topic 加 partition + 加机器横向扩容

面试怎么答¶

先表态："这类题考察的是对 MQ 架构原理的理解和设计思维。"然后按 8 点顺序展开，每点一两句话，最后总结："核心设计理念是参考 Kafka：broker-topic-partition 分层存储 + 多副本高可用 + 本地消息表做事务，保证可靠性、可扩展性和幂等。"——结构清晰 + 能引用成熟方案，就是高分答案。

附：用一句话记住今天的内容¶

MQ 设计模式 = 发布订阅（生产者、消息代理、订阅者三方解耦）；设计一个 MQ = 流程（生产-存储-消费）+ RPC + 持久化 + 消费关系 + 可靠性 + 高可用（多副本选主）+ 事务（本地消息表）+ 扩展（分区扩容），照着 Kafka 的思路抄作业就行。
