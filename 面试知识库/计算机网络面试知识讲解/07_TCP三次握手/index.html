07 TCP 三次握手¶

面试问法：TCP 头部 / 三次握手过程 / 为什么是三次 / 各种丢包场景 / 半连接队列 / SYN 攻击。 共 12 题，面试比重最大的一章，值得反复精读。

Q1 说一下 TCP 的头部¶

一句话答案¶

TCP 头部最关键的字段：序列号（解决乱序）、确认应答号（解决丢包）、控制位（SYN/ACK/FIN/RST 决定报文类型）。

大白话讲解¶

TCP 头部像快递单上的信息，重点看这几个字段：

字段 作用 类比
序列号（Seq） 建立连接时随机初始化，之后每发一次数据就累加"数据字节数"。解决乱序问题 包裹编号，收件人按编号排顺序
确认应答号（Ack） 表示"下一个期望收到的序列号"，收到它说明"这个序号之前的数据都收到了"。解决丢包问题 回执："1~100 号都收到了，请发 101 号"
控制位 决定报文的"性质" 快递单上的"加急/拒收"标记

四个控制位（必背）：

  • ACK：置 1 时"确认应答"字段生效。TCP 规定：除了建立连接时的 SYN 包，其他包都必须置 1。
  • SYN：置 1 表示"希望建立连接"，并在序列号字段里设定初始序号。
  • FIN：置 1 表示"我这边没有数据要发了，想断开连接"。
  • RST：置 1 表示"连接出现异常，必须强制断开"。

Q2 TCP 三次握手过程说一下？（必考）¶

一句话答案¶

① 客户端发 SYN（带初始序号 client_isn）→ SYN-SENT；② 服务端回 SYN+ACK（带自己的初始序号 server_isn，确认号 = client_isn+1）→ SYN-RCVD；③ 客户端回 ACK（确认号 = server_isn+1）→ 双方 ESTABLISHED。

大白话讲解¶

用"打电话确认"的类比：① 喂，能听到吗？（SYN）② 听到了，你能听到我吗？（SYN+ACK）③ 听到了！（ACK）——双方确认彼此都"听得见"，连接建立。

三次握手逐步走：

客户端                           服务端
CLOSED                           LISTEN（先监听端口）
  │  ① SYN(seq=client_isn)        │
  │──────────────────────────────→│  → SYN-SENT
  │                                │  → SYN-RCVD
  │  ② SYN+ACK(seq=server_isn, ack=client_isn+1)
  │←──────────────────────────────┤
  │  ③ ACK(ack=server_isn+1)      │
  │──────────────────────────────→│  → ESTABLISHED
  │→ ESTABLISHED                   │

关键细节（面试追问高频）：

  1. 前两次握手不能携带数据，第三次握手可以携带数据（因为前两次还没确认对方身份，带数据不安全；第三次已确认连接可用）。
  2. 双方各自随机初始化自己的序列号，互不依赖。
  3. 连接建立后双方都处于 ESTABLISHED 状态，开始传数据。

Q3 TCP 为什么需要三次握手建立连接？（高频追问）¶

一句话答案¶

三个原因：① 阻止重复的历史连接（主要原因）；② 同步双方的初始序列号；③ 避免资源浪费。

大白话讲解¶

原因一：阻止历史连接（RFC 793 明确指出的首要原因）

场景：客户端先发了一个 SYN（seq=90）但网络阻塞了，服务端没收到；客户端重启后又发了个新 SYN（seq=100）。

  • 如果是两次握手：服务端收到 SYN 就进入 ESTABLISHED 并开始发数据。等旧的 SYN（seq=90）到达后，客户端发现序号不对，回 RST 断开——但服务端已经为这个"历史连接"发了数据、浪费了资源。
  • 如果是三次握手：服务端收到旧 SYN 回 SYN+ACK（确认号 91）后，客户端发现"我期望的确认号是 101 而不是 91"，立刻回 RST → 服务端释放连接，在建立连接前就阻止了历史连接，不浪费资源。

核心：三次握手给了"发起方"一个中途拦截的机会——服务端在进入 ESTABLISHED 前，先等客户端确认"这确实是你要的连接"。

原因二：同步双方的初始序列号

序列号是可靠传输的基础（去重、按序、确认收没收到）。双方各自要发初始序列号、各自要被确认：

  • 客户端发 SYN 需要服务端确认（第二次握手的 ACK 完成）；
  • 服务端发自己的 SYN 需要客户端确认（第三次握手的 ACK 完成）。

四次握手也能做到，但第二步（ACK）和第三步（SYN）可以合并成一步，所以就成了三次。两次握手只能保证一方的序列号被确认，无法保证双方的。

原因三：避免资源浪费

只有两次握手时：客户端发的 SYN 在网络里阻塞、超时重传多个 SYN → 服务端每收到一个 SYN 就建立一个连接 → 产生一堆冗余的无效连接，白白分配资源。

Q4 客户端第三次发送的确认包（ACK）丢失了，发生什么？¶

一句话答案¶

服务端收不到第三次握手的 ACK，会超时重传 SYN+ACK，直到收到 ACK 或达到最大重传次数（tcp_synack_retries，默认 5）后断开连接；此时客户端已经是 ESTABLISHED，不受影响。

大白话讲解¶

  • 客户端发完第三次握手的 ACK 后直接进入 ESTABLISHED（它认为连接建好了）。
  • 服务端迟迟收不到 ACK → 触发超时重传，重发第二次握手的 SYN+ACK（序列号和确认号都不变，是同一份报文的重复发送，不是新连接）。
  • ACK 报文本身不会重传（TCP 规则：ACK 丢了，由对方重传它该确认的报文）。
  • 假设 tcp_synack_retries = 2：重传 2 次后仍未收到，再等一个"上次超时 × 2"的时间，仍无响应 → 服务端断开连接。

客户端收到重传的 SYN+ACK 会怎样？ 客户端重新回一个 ACK（确认号仍是 server_isn+1），服务端收到后进入 ESTABLISHED，握手正式完成。所以第三次 ACK 不是客户端主动重传，而是由服务端的重传"唤醒"应答。

怎么区分"正常重传"和"历史僵尸连接"？（易混淆点） 客户端收到 SYN+ACK 时看确认号：

  • 确认号 = 自己期待的（client_isn+1）→ 这是重传的 SYN+ACK → 回 ACK，连接建立（本场景）；
  • 确认号 ≠ 自己期待的（如收到旧 SYN 的应答 91，期待的是 101）→ 这是历史连接 → 回 RST 断开（见 Q3）。

面试亮点：能说出"ACK 不重传，由对方重传对应报文"这条规则，说明你真的懂 TCP。

Q5 服务端发送第二个报文（SYN+ACK）后，连接进入什么状态？¶

一句话答案：SYN_RCVD（半连接状态）。

大白话：服务端收到 SYN、回了 SYN+ACK 之后，还没收到客户端的 ACK，连接"建了一半"，这个状态就是 SYN_RCVD（也叫 SYN_RECEIVED）。

Q6 三次握手和 accept 是什么关系？accept 做了什么？¶

一句话答案¶

三次握手是内核完成的，accept 只是把已完成的连接从全连接队列里取出来交给用户程序——accept 不参与握手。

大白话讲解¶

  • TCP 三次握手全部由操作系统内核自动完成，不经过应用代码。
  • 握手完成的连接会放进内核的全连接队列（accept 队列）。
  • 应用程序调用 accept() 就是从队列里取出一个已完成的连接，交给用户程序使用。

常见误解澄清：不是"accept 建立连接"，而是"连接已经建好，accept 负责领走"。队列满了新连接会被丢弃或回 RST。

Q7 客户端发送的第一个 SYN 报文，服务器没有收到怎么办？¶

一句话答案¶

客户端会超时重传 SYN（序列号相同），最大重传次数由 tcp_syn_retries 控制（默认 5），超时时间逐次翻倍，总耗时约 63 秒后放弃。

大白话讲解¶

  • 客户端发 SYN 后进入 SYN_SENT，迟迟等不到 SYN+ACK → 触发超时重传。
  • 重传的 SYN 序列号相同（不是新连接，是重传）。
  • Linux 默认 tcp_syn_retries = 5，超时节奏：1s → 2s → 4s → 8s → 16s，第五次重传后再等 32s → 放弃。总计 1+2+4+8+16+32 = 63 秒（约 1 分钟）。
  • 内核参数可以改（/proc/sys/net/ipv4/tcp_syn_retries），超时时间的基数（1 秒/3 秒）写死在内核里，改要重编译内核。
SYN 丢失 → 1s后重传 → 2s后重传 → 4s → 8s → 16s → 再等32s → 断开

Q8 服务端回复的 SYN+ACK 报文丢失了怎么办？（经典两头重传）¶

一句话答案¶

客户端会重传 SYN，服务端也会重传 SYN+ACK——两边同时各自重传，分别受 tcp_syn_retries 和 tcp_synack_retries 控制。

大白话讲解¶

第二次握手报文（SYN+ACK）很特殊，它同时干两件事：

  • 其中的 ACK：确认客户端的第一次握手 → 客户端没收到，以为自己的 SYN 丢了 → 客户端重传 SYN；
  • 其中的 SYN：服务端发起连接的请求 → 服务端没等到客户端对它的确认 → 服务端重传 SYN+ACK。

所以第二次握手丢了，客户端和服务端同时在重传，直到一方放弃：

  • 客户端重传次数上限：tcp_syn_retries（默认 5）；
  • 服务端重传次数上限：tcp_synack_retries（默认 5）。

Q9 客户端重传了 SYN，服务端收到重复的 SYN 怎么办？¶

一句话答案：服务端会继续发送第二次握手报文（SYN+ACK），不认为这是错误。

大白话：TCP 用序列号识别重复报文。收到重复 SYN 时，服务端只需要再次回复 SYN+ACK 即可，这是正常处理，不是异常。

Q10 第一次握手后，服务端内部做了哪些工作？¶

一句话答案¶

内核把连接放进半连接队列 → 回 SYN+ACK → 收到第三次握手 ACK 后，把连接从半连接队列移到全连接（accept）队列，等程序 accept 取走。

大白话讲解¶

收到 SYN → 存入半连接队列（SYN queue）
        → 回复 SYN+ACK
收到 ACK → 从半连接队列移除
        → 创建完整连接放入全连接队列（accept queue）
        → 等待 accept() 取走

两个队列都有最大长度限制，满了之后内核会直接丢弃新报文或返回 RST 包。

Q11 大量 SYN 包发给服务端，会发生什么事情？（SYN 攻击）¶

一句话答案¶

半连接队列被打满 → 后续 SYN 被丢弃 → 正常客户端也无法建立连接。防范有四种手段：调大 netdev_max_backlog、增大半连接队列、开启 tcp_syncookies、减少 SYN+ACK 重传次数。

大白话讲解¶

攻击者伪造海量 SYN 却不完成握手 → 半连接队列堆满"半死不活"的连接 → 正常用户连不上。

四种防护方式：

① 调大 netdev_max_backlog：网卡收包速度 > 内核处理速度时，数据包会排队，这个参数控制队列上限（默认 1000，可调到 10000）。

② 增大 TCP 半连接队列：需要同时调三个参数： - net.ipv4.tcp_max_syn_backlog - listen() 函数中的 backlog - net.core.somaxconn

③ 开启 tcp_syncookies（最有效）： - SYN 队列满后，服务端不丢弃新 SYN，而是根据算法算出一个 cookie 值，放进第二次握手报文的序列号里； - 收到客户端的 ACK 后，校验 cookie 的合法性：合法就建立连接放进 accept 队列； - 效果：绕过了半连接队列，SYN 攻击下正常连接照样能建立。 - 参数值：0 关闭 / 1 队列放不下时才启用（推荐，应对攻击设 1）/ 2 无条件开启。

④ 减少 SYN+ACK 重传次数：攻击时会有大量 SYN_RCVD 状态的连接，减少 tcp_synack_retries（如改为 2）能加快这些连接断开，腾出资源。

Q12 TCP 四次挥手过程说一下？¶

本章先给流程，详细追问放下一章《08_TCP四次挥手》。

一句话答案¶

① 客户端发 FIN（不再发数据）→ FIN_WAIT_1；② 服务端回 ACK → 服务端 CLOSE_WAIT，客户端 FIN_WAIT_2；③ 服务端发完剩余数据后回 FIN → LAST_ACK；④ 客户端回 ACK → 服务端 CLOSE，客户端 TIME_WAIT（等 2MSL）后 CLOSE。

大白话讲解¶

客户端                               服务端
ESTABLISHED                          ESTABLISHED
  │  ① FIN                          │
  │───────────────────────────────→ │  → CLOSE_WAIT
  │  ② ACK                          │
  │←─────────────────────────────── │
  │  (FIN_WAIT_2, 还能收数据)         │
  │  ③ FIN（服务端发完数据后）        │
  │←─────────────────────────────── │  → LAST_ACK
  │  ④ ACK                          │
  │───────────────────────────────→ │  → CLOSE
  │  → TIME_WAIT（等2MSL）            │
  │  2MSL后 CLOSE                    │

为什么要四步而不是两步？ 因为被动关闭方（服务端）可能还有数据要发：收到 FIN 后内核立刻回 ACK（第二步），但"什么时候发 FIN"（第三步）要等应用程序把剩余数据处理完——所以 ACK 和 FIN 必须分开。

本单元小结（三次握手部分）¶

概念 一句话记住
握手三包 SYN → SYN+ACK → ACK，前两次不带数据，第三次可带
为什么三次 阻止历史连接（主因）+ 同步双方序列号 + 避免资源浪费
第一次握手丢 客户端重传 SYN，tcp_syn_retries=5，约 63 秒放弃
第二次握手丢 客户端重传 SYN + 服务端重传 SYN+ACK，两头同时重传
第三次握手丢 客户端已 ESTABLISHED；服务端超时重传 SYN+ACK
ACK 重传规则 ACK 不重传，由对方重传它确认的报文
队列 半连接队列（SYN 后）→ 全连接队列（握手完成后，accept 取走）
SYN 攻击 半连接队列被打满；防护：syncookies / 调大队列 / 减重传
