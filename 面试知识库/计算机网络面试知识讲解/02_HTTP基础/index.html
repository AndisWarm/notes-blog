02 HTTP 基础¶

面试问法：HTTP 报文有哪些部分 / 状态码 / GET 和 POST 区别 / 长连接 / 断点续传 / HTTP/1.1 与 HTTP/2 区别 / 连接中断 / HTTP 与 Socket、TCP 的区别等。 本章是应用层最高频考点，共 18 题。

Q1 应用层有哪些协议？¶

一句话答案：HTTP、HTTPS、CDN、DNS、FTP 都是应用层协议。

大白话讲解：应用层就是"最接近用户"的那一层，你平时用的各种"上网服务"对应的协议都在这层：看网页用 HTTP(S)，记域名用 DNS，传文件用 FTP，加速内容用 CDN。

Q2 HTTP 报文有哪些部分？¶

一句话答案¶

分请求报文和响应报文，都是「行 + 头部 + 空行 + 体」的结构。

大白话讲解¶

请求报文（客户端 → 服务器），像一张"点菜单"：

部分 内容 类比
请求行 请求方法 + URL + 协议版本 菜单抬头："我要一份回锅肉"
请求头部 Host、User-Agent、Content-Type 等附加信息 备注："少辣、加饭"
空行 头部和体之间的分隔线 分隔"备注"和"正文"
请求体（可选） 携带的数据，POST 等请求常用 菜品本身（比如登录表单）

响应报文（服务器 → 客户端），像一张"收据"：

部分 内容
状态行 协议版本 + 状态码 + 状态信息
响应头部 Content-Type、Content-Length 等
空行 分隔线
响应体 返回的数据（HTML、JSON 等）

注意：请求报文和响应报文都有"空行"，这是格式要求，别漏了。

Q3 HTTP 常用的状态码？¶

一句话答案¶

状态码分 5 大类：1xx 提示、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务器错误。

大白话讲解¶

状态码就是服务器回复的"处理结果"，第一位数字代表大类：

大类 含义 说明
1xx 提示信息 中间状态，实际用得少
2xx 成功 服务器成功处理了请求，最愿看到的
3xx 重定向 资源变动了，要换个 URL 重新请求
4xx 客户端错误 你发的报文有问题，服务器无法处理
5xx 服务器错误 报文没问题，但服务器内部出错了

最常见的具体状态码：

  • 200：请求成功 ✅
  • 301：永久重定向；302：临时重定向
  • 404：页面找不到；405：请求方法不支持（比如只允许 POST 却发了 GET）
  • 500：服务器内部出错

Q4 HTTP 返回状态 301、302 分别是什么？¶

一句话答案¶

301 是永久重定向（资源已搬家，以后都用新地址）；302 是临时重定向（资源还在，暂时换地址访问）。

大白话讲解¶

想象你搬家：

  • 301：你永远搬到新家了，朋友以后都得去新地址找你（旧地址作废）。
  • 302：你只是暂时住在别处，过阵子还会搬回来（旧地址还有效）。

两者都会在响应头用 Location 字段告诉浏览器"新地址在哪"，浏览器收到后自动跳转，用户无感知。

Q5 HTTP 502 和 504 的区别？¶

一句话答案¶

502：网关收到了上游服务器的"无效响应"；504：网关等了太久，"没等到"上游响应。

大白话讲解¶

拿 nginx 当"中转站"举例：nginx 收到客户端请求后，转发给后端服务器（如 Tomcat），再把结果转回给客户端。

  • 502 Bad Gateway：后端"回了话"，但回的内容是垃圾/无效的 → nginx 转达不了。
  • 504 Gateway Time-out：nginx 等到超时时间，后端"一直没回话" → nginx 放弃等待。

记忆：502 = 回了但回错了；504 = 根本没回。

Q6 HTTP 层请求的类型有哪些？¶

一句话答案¶

GET（获取）、POST（提交）、PUT（更新）、DELETE（删除）、HEAD（只取头部）。

大白话讲解¶

方法 作用 类比
GET 请求获取指定资源 查资料
POST 向服务器提交数据（创建） 提交报名表
PUT 更新已存在的资源 修改资料
DELETE 删除指定资源 删掉记录
HEAD 和 GET 类似，但只返回头部 只看封面不看书

Q7 GET 和 POST 的使用场景，有哪些区别？（高频）¶

一句话答案¶

按规范：GET 是"只读"获取资源，安全且幂等；POST 是"提交数据"修改资源，不安全、不幂等。参数位置也不同：GET 放 URL 里，POST 放 body 里。

大白话讲解¶

GET —— 查：打开一篇文章，浏览器发 GET，服务器返回文章内容。参数写在 URL 里（如 ?id=123），所以：

  • 只能传 ASCII 字符（URL 规范限制）；
  • 浏览器对 URL 长度有限制（注意：HTTP 协议本身没限制，是浏览器限制的）。

POST —— 交：在文章底部写留言点提交，浏览器发 POST，留言内容放在报文的 body 里。所以：

  • body 可以是任意格式（JSON、表单等），只要双方协商好；
  • 浏览器不限制 body 大小。

RFC 规范定义的语义：

对比项 GET POST
语义 获取资源（只读） 提交/新增数据（写操作）
安全性 安全（不修改服务器数据） 不安全（会修改数据）
幂等性 幂等（操作多少次结果一样） 不幂等（多次提交创建多个资源）
缓存 可缓存（浏览器、nginx 都能缓存） 一般不缓存
书签 可以存为书签 不能存为书签

重要补充（面试加分点）：实际开发中开发者不一定遵守规范——可以用 GET 实现删除（那它就不安全不幂等），也可以用 POST 实现查询（那它就安全幂等）。所以"GET 安全"说的是"按规范实现时"。

Q8 HTTP 的长连接是什么？¶

一句话答案¶

长连接（Keep-Alive）：用一个 TCP 连接发送/接收多个 HTTP 请求响应，避免频繁建立、释放连接的开销。

大白话讲解¶

HTTP 是"请求-应答"模式，基于 TCP。如果每次请求都走一遍"建立 TCP → 请求 → 响应 → 释放连接"，就叫短连接——"一次连接只能请求一次资源"，太浪费了。

长连接就是：第一个 HTTP 请求完成后不断开 TCP 连接，后续请求继续用这个连接。只要任意一端没有明确提出断开，连接就一直保持。

实际表现：打开一个网页要加载几十个资源（图片、CSS、JS），长连接能省下几十次"建连-断连"的开销，页面加载快得多。

Q9 HTTP 默认的端口是什么？¶

一句话答案：HTTP 是 80，HTTPS 是 443。

（送分题，必须记住。）

Q10 HTTP/1.1 怎么对请求做拆包？¶

一句话答案¶

靠 Content-Length 头字段：它写明请求体的字节数，服务器按这个数字读取完整个请求。

大白话讲解¶

TCP 是"流式"传输，数据像水管里的水一样没边界，服务器收到的可能是半个请求、也可能是多个请求拼在一起。Content-Length 就像包装盒上标注的"净含量"：服务器知道"这个请求体共 N 字节"，就精确读取 N 字节，不多不少，避免请求丢失或截断。

Q11 HTTP 断点重传（断点续传）是什么？¶

一句话答案¶

HTTP/1.1 支持的续传特性：下载中断后，客户端用 Range 头告诉服务器"从第 N 字节继续传"，服务器返回 206 状态码 + 剩余内容。

大白话讲解¶

下载 1024K 的文件，下到 512K 时网断了。重连后：

  1. 服务器先发 Accept-Ranges: bytes 表示"我支持分段传输"；
  2. 客户端发 Range: bytes=512000- 表示"从第 512K 字节开始传给我"；
  3. 服务器从 512K 位置继续传，并在响应头加 Content-Range: bytes 512000-/1024000 和 Content-Length: 512000，状态码返回 206 Partial Content。

4 个关键头（背下来）：

头 方向 作用
Range 客户端 → 服务器 声明要哪一段内容
Content-Range 服务器 → 客户端 告诉客户端传的是哪一段
Accept-Ranges 服务器 → 客户端 声明支持范围请求
Content-Length 服务器 → 客户端 本次传输的长度

细节：如果客户端请求的 Range 超出资源大小，服务器返回 416。

Q12 HTTP 为什么不安全？¶

一句话答案¶

HTTP 是明文传输，存在三大风险：窃听、篡改、冒充。

大白话讲解¶

明文传输 = 说的话都被人听得到，路上任何节点都能：

  • 窃听风险：通信链路上能直接看到通信内容 → 你的账号密码容易丢；
  • 篡改风险：强制植入垃圾广告 → 视觉污染；
  • 冒充风险：冒充淘宝网站 → 你的钱容易没。

而 HTTPS 在 HTTP 与 TCP 之间加了一层 SSL/TLS 协议，针对性解决：

  • 信息加密 → 内容无法被窃取；
  • 校验机制 → 内容无法被篡改（篡改了就不能正常显示）；
  • 身份证书 → 证明"淘宝是真的淘宝"。

Q13 HTTP 和 HTTPS 的区别？¶

一句话答案¶

四点区别：① HTTPS 多了 SSL/TLS 加密层；② HTTPS 多了 TLS 握手过程；③ 默认端口不同（80 vs 443）；④ HTTPS 需要 CA 签发数字证书。

大白话讲解¶

对比项 HTTP HTTPS
传输 明文，有安全风险 加了 SSL/TLS 安全协议，报文加密
连接过程 TCP 三次握手后直接传报文 TCP 三次握手后还要 TLS 握手，才进入加密传输
默认端口 80 443
身份认证 无 需要向 CA（证书权威机构）申请数字证书

Q14 HTTPS 握手过程说一下？（高频）¶

一句话答案¶

TLS 1.2 基于 RSA 的握手共四次：① ClientHello → ② ServerHello + 证书 → ③ 客户端用公钥加密传输 pre-master key → ④ 双方用三个随机数各自算出"会话密钥"，开始加密通信。

大白话讲解¶

先理解两个背景概念：

  • 非对称加密：公钥加密的东西只有私钥能解。服务器把公钥放在证书里公开，私钥自己藏着。
  • 会话密钥：双方最终用来加密"正式聊天内容"的对称密钥，靠三个随机数 + 协商的算法算出，各自独立计算、结果相同。

四次握手逐一来：

第 1 次（客户端 → 服务器）ClientHello，客户端说： 1. 我支持的 TLS 版本（如 TLS 1.2）； 2. 我生成的随机数 Client Random（后续生成密钥的原料之一）； 3. 我支持的密码套件列表（如 RSA）。

第 2 次（服务器 → 客户端）ServerHello，服务器回： 1. 确认 TLS 版本（不支持就关闭通信）； 2. 我生成的随机数 Server Random（原料之二）； 3. 确认的密码套件； 4. 我的数字证书（里面装着我的公钥）。

第 3 次（客户端 → 服务器），客户端拿到证书后： 1. 用浏览器/系统内置的 CA 公钥验证证书真实性（校验服务器身份）； 2. 验证通过后，从证书里取出服务器公钥； 3. 生成第三个随机数 pre-master key，用服务器公钥加密后发给服务器（只有服务器的私钥能解开）； 4. 发"算法变更通知" + "握手结束通知"（附上之前所有握手内容的摘要供服务器校验）。

此时客户端已有三个随机数，可以算出会话密钥了。

第 4 次（服务器 → 客户端），服务器用私钥解开 pre-master key，凑齐三个随机数，也算出同样的会话密钥，然后： 1. 发"算法变更通知"——之后都用会话密钥加密； 2. 发"握手结束通知"（附摘要供客户端校验）。

至此握手结束，双方用同一个"会话密钥"加密传输 HTTP 内容。

⚠️ 面试加分点：TLS 1.3 已移除 RSA 密钥交换（不支持前向安全），改用 (EC)DHE，握手从 2-RTT 简化为 1-RTT，还支持 0-RTT 会话恢复。现代浏览器默认用 1.2/1.3，RSA 那套当历史知识了解即可。

Q15 HTTPS 是如何防范中间人攻击的？¶

一句话答案¶

靠两招：① 非对称加密协商密钥（加密）；② CA 数字证书校验服务器身份（身份校验）。

大白话讲解¶

中间人攻击就是：攻击者冒充服务器跟客户端通信，同时冒充客户端跟服务器通信，两头骗。

为什么 HTTPS 能防住？因为：

  1. 身份校验：服务器向 CA 申请数字证书（含公钥和身份信息）。客户端建立连接时验证证书——检查有效期、颁发机构是否可信等。攻击者没有 CA 签发的真证书，客户端会警告或中止连接。
  2. 加密：就算攻击者想冒充服务器，他也拿不到服务器的私钥，无法解密客户端发来的加密数据（比如被公钥加密的 pre-master key），也就无法伪装成服务器继续通信。

一句话总结：证书证明"你是谁"，私钥保证"只有你能解密"——中间人两样都没有，所以防得住。

Q16 HTTP/1.1 和 HTTP/2.0 的区别是什么？¶

一句话答案¶

HTTP/2 相比 HTTP/1.1 有四点性能改进：① 头部压缩（HPACK）；② 二进制格式（帧）；③ 多路复用（Stream，解决队头阻塞）；④ 服务器主动推送（Server Push）。

大白话讲解¶

改进点 HTTP/1.1 HTTP/2 类比
头部压缩 每次请求都带完整头部，重复字段反复传 HPACK：两端维护头信息表，重复字段只发索引号 第一次报全名，之后只报外号
二进制格式 纯文本报文，机器要先转二进制 全面二进制，头和数据体都是帧（Headers/Data Frame） 机器只懂 0/1，直接喂二进制更快
并发传输 一问一答，多个请求要排队（队头阻塞） 引入 Stream，多个流复用一条 TCP 连接 单车道 vs 多车道
服务器推送 客户端不请求就不给 客户端还没请求就把相关资源主动推过去 点餐时老板直接上配菜

逐个展开：

  1. 头部压缩（HPACK 算法）：多次请求的头部大多相同或相似（如 User-Agent、Cookie），HPACK 在客户端和服务器各维护一张头信息表，所有字段存入表并生成索引号，之后不再发字段原文、只发索引号 → 头部体积大幅减小，速度提升。
  2. 二进制格式：HTTP/2 不再用 HTTP/1.1 的纯文本，头信息和数据体统一成二进制「帧」——头信息帧（Headers Frame）和数据帧（Data Frame）。对人不如文本好读，但对计算机极友好：收到直接解析二进制，省掉「文本 → 二进制」的转换，提高传输效率。
  3. 并发传输：引入 Stream 概念，多个 Stream 复用同一条 TCP 连接 → 解决 HTTP/1.1 的队头阻塞（一个请求没处理完、后面的都得排队等）。
  4. 服务器主动推送（Server Push）：服务端在客户端还没请求时，主动把相关资源推给它。

⚠️ 注意（面试加分点）：Chrome 106（2022 年 10 月）起已默认禁用 HTTP/2 Server Push——实践中它的采用率不到 2%，性能收益也不稳定；HTTP/3 规范虽保留 Push 但几乎没有实现。现在的替代方案是 103 Early Hints（RFC 8297）：服务器先回 103 告诉浏览器哪些资源可提前加载，再由浏览器自己决定是否预取。

Q17 HTTP 进行 TCP 连接之后，在什么情况下会中断？¶

一句话答案¶

三种情况：① 任一端调用 close 系统调用发 FIN（走四次挥手）；② 发送方超时重传达到最大次数仍收不到 ACK；③ HTTP 长时间没有请求响应、超过超时时间被释放。

大白话讲解¶

中断原因 触发条件 结果
主动关闭 服务端或客户端执行 close 系统调用 → 发 FIN 报文 进入四次挥手流程（详见《08》）
重传耗尽 发送数据后接收方超时一直不回 ACK，重传达最大次数 直接断开 TCP 连接
空闲超时 HTTP 长时间无请求也无响应，超过设定时间 释放连接（即长连接的超时回收）

前两种是「TCP 层」的关闭，第三种是「应用层长连接」的回收——层次不同，别混在一起答。

Q18 HTTP、Socket 和 TCP 的区别？¶

一句话答案¶

HTTP 是应用层协议（定义数据交换的格式和规则）；Socket 是通信的一端（提供网络通信接口的抽象）；TCP 是传输层协议（负责建立可靠的数据传输连接）。三者角色和层次不同。

大白话讲解¶

概念 层次 本质 一句话
HTTP 应用层 定义客户端和服务器之间交换的数据格式与规则 传输和展示 Web 页面的「语言规范」
Socket 接口抽象 描述通信链路的一端，提供底层通信接口 收发数据的「插座/门把手」
TCP 传输层 面向连接、可靠，负责在两端建立可靠传输连接 保证数据可靠送达的「运输通道」

三者的关系：TCP 是「路」（可靠的传输通道），Socket 是「路的出入口」（程序员通过它往路上收发数据），HTTP 是「路上跑的车该装什么货、怎么包装」（数据格式和规则）。写代码时通过 Socket 接口收发数据，底层走 TCP 保证可靠，上层按 HTTP 规范组织内容。
