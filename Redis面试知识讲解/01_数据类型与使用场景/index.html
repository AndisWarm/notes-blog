01 数据类型与使用场景¶

本章覆盖：Redis 有哪些数据类型、五种基本类型和四种进阶类型的应用场景、ZSet 实战（排行榜）、Set vs ZSet 区别、ZSet 在项目里怎么用。

1. 讲一下 Redis 底层的数据结构？¶

一句话回答¶

Redis 常见的有五种基本数据类型：String（字符串）、Hash（哈希）、List（列表）、Set（集合）、Zset（有序集合）；后面又陆续支持了四种进阶类型：BitMap、HyperLogLog、GEO、Stream。

展开讲：五种基本类型¶

类型 长什么样 常用命令 典型场景
String 一个 key 对应一个字符串/数字 SET GET INCR 缓存对象、常规计数、分布式锁、共享 session
Hash 一个 key 对应一个"小字典"（field-value） HSET HGET HGETALL 缓存对象（存对象字段）、购物车
List 一个 key 对应一个有序列表（可从两头插入） LPUSH RPUSH LPOP BLPOP 消息队列（有局限，见下）
Set 一个 key 对应一个无序、不重复的集合 SADD SISMEMBER SINTER 点赞、共同关注、抽奖（交集/并集/差集计算）
Zset 一个 key 对应一个有序、不重复的集合，每个元素带分数 ZADD ZRANGE ZRANK 排行榜、电话和姓名排序

展开讲：四种进阶类型（版本新增）¶

  • BitMap（2.2 版）：用二进制位（bit，0/1）来存二值状态。场景：签到、判断用户登录状态、连续签到用户总数统计。
  • 比喻：一张"打卡表"，每个人占一格，打了勾就是 1，没打就是 0。省内存（1 个 bit 就能存一个人）。
  • HyperLogLog（2.8 版）：用很小的内存做海量数据的基数统计（统计有多少个不同元素）。
  • 场景：百万级网页 UV 计数。
  • 比喻：想知道一个会场来了多少个"不同的人"，不用记每个人的名字，只粗略记个大概数就行。有误差（标准误差约 0.81%）但极省内存。
  • GEO（3.2 版）：存储地理位置信息（经纬度）。场景：滴滴叫车、附近的人。
  • Stream（5.0 版）：专门为消息队列设计的新类型。相比 List 实现的消息队列，多了两个特性：自动生成全局唯一消息 ID、支持消费组。

List 当消息队列的两个坑¶

用 List 做消息队列简单，但有俩问题：

  1. 生产者需要自行实现全局唯一 ID：List 里的元素没有自带 ID，你要自己生成；
  2. 不能以消费组形式消费数据：多个消费者抢消息没问题，但做不到"一个消息只被一个消费组处理"这种高级模式（Stream 可以）。

面试怎么答¶

先报五种基本类型名字，再各说一个场景；如果面试官追问，再补四种进阶类型。重点记住：Zset 对应排行榜，Stream 对应消息队列，BitMap 对应签到统计。

2. ZSet 用过吗？（排行榜实战）¶

一句话回答¶

用过，zset 最适合做排行榜，比如博文点赞排名。

展开讲：完整例子¶

假设小林发表了五篇博文，赞数分别是 200、40、100、50、150。先初始化排行榜：

# arcticle:1 文章获得了200个赞
> ZADD user:xiaolin:ranking 200 arcticle:1
(integer) 1
# arcticle:2 文章获得了40个赞
> ZADD user:xiaolin:ranking 40 arcticle:2
(integer) 1
# arcticle:3 文章获得了100个赞
> ZADD user:xiaolin:ranking 100 arcticle:3
(integer) 1
# arcticle:4 文章获得了50个赞
> ZADD user:xiaolin:ranking 50 arcticle:4
(integer) 1
# arcticle:5 文章获得了150个赞
> ZADD user:xiaolin:ranking 150 arcticle:5
(integer) 1

场景一：文章 arcticle:4 新增一个赞

用 ZINCRBY（给指定元素的分数加 increment）：

> ZINCRBY user:xiaolin:ranking 1 arcticle:4
"51"

场景二：查看某篇文章的赞数

用 ZSCORE（返回指定元素的分数）：

> ZSCORE user:xiaolin:ranking arcticle:4
"51"

场景三：获取赞数最多的 3 篇文章

用 ZREVRANGE（倒序取区间，0 2 就是第 0 到第 2 名，WITHSCORES 把分数也显示出来）：

> ZREVRANGE user:xiaolin:ranking 0 2 WITHSCORES
1) "arcticle:1"
2) "200"
3) "arcticle:5"
4) "150"
5) "arcticle:3"
6) "100"

场景四：获取 100 赞到 200 赞之间的文章

用 ZRANGEBYSCORE（按分数区间查询，分数由低到高）：

> ZRANGEBYSCORE user:xiaolin:ranking 100 200 WITHSCORES
1) "arcticle:3"
2) "100"
3) "arcticle:5"
4) "150"
5) "arcticle:1"
6) "200"

面试怎么答¶

说"用过，做了个排行榜"，然后按上面四个命令讲：ZADD 写入 → ZINCRBY 加分 → ZREVRANGE 取 TOP N → ZRANGEBYSCORE 按分数段筛选。能完整背出命令，面试官就知道你真写过。

3. Redis 中 Set 和 ZSet 的区别是什么？¶

一句话回答¶

核心区别是有没有"分数"、按不按分数排序：Set 无序、只管去重；ZSet 每个元素带一个分数，按分数自动排序，能做排名、范围查询。

展开讲：Set（无序集合）¶

特点：无序、元素唯一（重复添加自动去重）。

常用命令：

  • 添加元素：SADD set1 "a" "b" "c"
  • 查看所有元素：SMEMBERS set1（返回结果无序，如 ["b", "a", "c"]）
  • 判断元素是否存在：SISMEMBER set1 "a"（存在返回 1，否则 0）
  • 集合运算：SINTER set1 set2（交集）、SUNION set1 set2（并集）

适合：存储不重复且无需排序的数据，如用户 ID 列表、标签集合。

展开讲：ZSet（有序集合）¶

特点：元素唯一（分数可以重复），每个元素关联一个"分数（score）"，按分数从小到大排序。

常用命令：

  • 添加元素（带分数）：ZADD zset1 10 "a" 20 "b" 15 "c"
  • 按排名获取（从小到大）：ZRANGE zset1 0 -1 WITHSCORES → "a" 10, "c" 15, "b" 20
  • 按分数范围获取：ZRANGEBYSCORE zset1 12 25 → "c", "b"
  • 增减分数：ZINCRBY zset1 5 "a"（"a" 变 15）
  • 获取排名：ZRANK zset1 "b"（返回 2，排名从 0 开始）

核心区别总结¶

Set ZSet
有序性 完全无序 通过分数维持有序
操作特性 只有集合本身的交并差 多了分数排序、范围查询、排名计算
适用场景 去重、无需排序 排行榜、带权重的任务

比喻¶

  • Set 像一袋子乒乓球：只保证不重复，倒出来是乱序的。
  • ZSet 像排队买奶茶：每个人都拿了个号（分数），按号从小到大排好，随时能知道"谁排第几"。

4. Zset 底层是怎么实现的？¶

一句话回答¶

Zset 的底层是压缩列表或跳表二选一，小数据用压缩列表省内存，大数据用跳表保性能；Redis 7.0 起压缩列表被 listpack 取代。

展开讲：什么时候用哪个¶

  • 如果元素个数小于 128 个，且每个元素的值小于 64 字节 → 用压缩列表（紧凑、省内存）；
  • 只要有一项不满足（元素太多或值太大）→ 用跳表（查询快，O(logN)）。

注意：在 Redis 7.0 中，压缩列表数据结构已经废弃了，由 listpack 实现。所以现在回答"压缩列表或跳表"时，最好补一句"新版用 listpack 替代了压缩列表"，显得你关注版本演进。

为什么这么设计？¶

  • 数据少时，用最简单紧凑的结构（压缩列表）就能搞定，省内存；
  • 数据多了，压缩列表查找要 O(N)（逐个找），太慢，必须换成跳表 O(logN)。

面试怎么答¶

背下"128 个元素 + 64 字节"这两个阈值，再补一句 Redis 7.0 用 listpack 替代了压缩列表。

5. redis 的 Zset，在项目里具体用法是什么？¶

一句话回答¶

Zset 在项目里的核心用法是需要排序、取排名、按分数范围筛选的场景，因为它既保证元素唯一，又能自动按分数排序，查询效率高。

用法一：排行榜（最常用）¶

游戏玩家积分排名、电商商品销量榜单、社区用户贡献值排名。

  • 玩家 ID 当元素，积分当分数，ZADD 添加/更新积分；
  • 查前 10 名：ZREVRANGE（降序取前 10）；
  • 查某个玩家排名：ZREVRANK；
  • 查他的具体积分：ZSCORE。

全部实时完成，不用查数据库排序。

用法二：延迟任务队列¶

电商订单 30 分钟未支付自动取消、定时发送通知。

  • 任务 ID 当元素，"任务执行时间戳"当分数；
  • 后台开一个线程，不断用 ZRANGEBYSCORE 查询"分数 < 当前时间戳"的任务；
  • 执行完用 ZREM 删掉。

这样就能实现定时任务，不用复杂的调度框架。

用法三：范围查询¶

"积分在 1000-2000 之间的玩家""销量前 50 到 100 名的商品"：

  • ZRANGEBYSCORE / ZREVRANGEBYSCORE 直接筛出来；
  • 比在数据库里 ORDER BY ... LIMIT 高效得多，尤其数据量大时。

用法四：带权重的消息队列¶

给重要消息设置更高的分数，消费者优先处理分数高的消息，保证核心业务的优先级。

面试怎么答¶

排行榜必答；有余力再说延迟队列（ZRANGEBYSCORE + ZREM），这个方案很加分，因为很多面试官没听过 Redis 能做延迟队列。
