05 过期删除与内存淘汰¶

本章覆盖：过期删除策略和内存淘汰策略的区别、8 种内存淘汰策略、惰性删除 + 定期删除的完整机制、为什么缓存失效不会立即删除。

1. 过期删除策略和内存淘汰策略有什么区别？¶

一句话回答¶

内存淘汰是内存满了时，主动删掉一些 key 腾出空间；过期删除是把已到期的 key 删掉（Redis 用的是惰性删除 + 定期删除）。

展开讲¶

内存淘汰策略 过期键删除策略
触发时机 运行内存超过 maxmemory 上限时 key 的过期时间到了之后
目的 腾出空间，保存新内容 清理已过期的键值对
删谁 按策略选（最久没用/最少用/随机…） 已过期的 key
方式 由配置的淘汰策略决定 惰性删除 + 定期删除

比喻¶

  • 内存淘汰像冰箱满了：把最不常吃的菜扔了腾地方；
  • 过期删除像食品过期：到了保质期就清理掉。

2. 介绍一下 Redis 内存淘汰策略？¶

一句话回答¶

Redis 共有 8 种淘汰策略，分两大类：不淘汰（noeviction）和淘汰（7 种，又分"只在设置了过期时间的数据中淘汰"和"在所有数据中淘汰"）。

背景知识：maxmemory¶

  • 32 位操作系统下 maxmemory 默认 3G（32 位机器最多 4GB 内存，要给系统留一些，避免内存不足导致 Redis 实例崩溃）；
  • 64 位系统要自己配置上限。

第一类：不进行数据淘汰¶

  • noeviction（Redis 3.0 之后默认策略）：内存超限时不淘汰任何数据，新数据写入直接报错；但查询、删除操作还能正常进行。

第二类：进行数据淘汰（7 种）¶

只在"设置了过期时间"的数据中淘汰：

策略 淘汰什么
volatile-random 随机淘汰任意一个设置了过期时间的 key
volatile-ttl 优先淘汰更早过期的 key
volatile-lru 淘汰设置了过期时间且最久未使用的 key（Redis 3.0 之前的默认策略）
volatile-lfu 淘汰设置了过期时间且最少使用的 key（Redis 4.0 新增）

在所有数据（不管有没有设置过期时间）范围内淘汰：

策略 淘汰什么
allkeys-random 随机淘汰任意 key
allkeys-lru 淘汰整个键空间中最久未使用的 key
allkeys-lfu 淘汰整个键空间中最少使用的 key（Redis 4.0 新增）

LRU vs LFU 怎么记¶

  • LRU（Least Recently Used）：最久没被访问 → 看"时间"，很久没翻的书先扔；
  • LFU（Least Frequently Used）：访问次数最少 → 看"频率"，翻得最少的书先扔。

场景区别：一个 key 昨天被疯狂访问、今天没人用 → LRU 会把它当"最近用过"留着；LFU 结合频率，对"以前热、现在冷"的数据更敏感。

记忆口诀¶

  • 前缀 volatile- = 只动带过期时间的；
  • 前缀 allkeys- = 所有 key 都能动；
  • 后缀 random = 随机；ttl = 按剩余时间；lru = 看最近使用；lfu = 看使用频率。

面试怎么答¶

先报 8 种（noeviction + 3+3 个 volatile/allkeys 各配 random/lru/lfu，加一个 volatile-ttl），然后说一句"默认是 noeviction，不淘汰只报错"。能分清楚 volatile 和 allkeys 前缀就是及格线。

3. 介绍一下 Redis 过期删除策略？¶

一句话回答¶

Redis 用 「惰性删除 + 定期删除」 两种策略配合，在"省 CPU"和"不浪费内存"之间找平衡。

展开讲：惰性删除（懒，用到才删）¶

做法：不主动删过期 key，每次访问/修改 key 时先检查它是否过期，过期就删掉再返回。

实现：db.c 的 expireIfNeeded 函数，Redis 在访问或修改任何 key 之前都会调用它：

int expireIfNeeded(redisDb *db, robj *key) {
    // 判断 key 是否过期
    if (!keyIsExpired(db,key)) return 0;
    ....
    /* 删除过期键 */
    ....
    // 如果 server.lazyfree_lazy_expire 为 1 表示异步删除，反之同步删除；
    return server.lazyfree_lazy_expire ? dbAsyncDelete(db,key) :
                                         dbSyncDelete(db,key);
}
  • key 过期 → 删除（4.0 起可选异步删除），返回 null 给客户端；
  • key 没过期 → 不处理，正常返回值。

优点：CPU 友好——没被访问的过期 key 根本不用管，不花一分钱 CPU。 缺点：内存不友好——一直没人访问的过期 key 会一直赖在内存里，浪费内存。

展开讲：定期删除（每隔一会抽查一轮）¶

做法：每隔一段时间，随机从数据库中取出一定数量的 key 检查，删掉其中过期的。

两个关键数字：

  1. 检查间隔：默认每秒 10 次（配置项 hz，默认 10）。注意：不是遍历所有 key，而是随机抽一批；
  2. 抽查数量：每次随机抽 20 个 key（源码里写死：ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP = 20）。

完整流程（activeExpireCycle 函数）：

  1. 从过期字典中随机抽取 20 个 key；
  2. 检查这 20 个 key 是否过期，删除已过期的；
  3. 如果本轮已过期 key 数量超过 5 个（20/4，占比 > 25%），说明"过期 key 还挺多"，继续重复步骤 1；如果占比 ≤ 25%，停止本轮，等下一轮再检查。

伪代码：

do {
    expired = 0;   // 已过期的数量
    num = 20;      // 随机抽取的数量
    while (num--) {
        // 1. 从过期字典中随机抽取 1 个 key
        // 2. 判断是否过期，已过期则删除，expired++
    }
    // 超过时间限制则退出（防止循环过度卡死线程）
    if (timelimit_exit) return;
} while (expired > 20/4);   // 过期比例 > 25% 就继续抽查

防卡死保护：循环有时间上限，默认不超过 25ms，避免一次性删太多把主线程卡死。

为什么两种要配合¶

  • 只用惰性删除：过期 key 没人访问就永远不删，内存泄漏；
  • 只用定期删除：要频繁扫描所有 key，浪费 CPU；
  • 配合使用：定期删除兜底清掉大部分，惰性删除清理漏网的，CPU 和内存都兼顾。

比喻¶

  • 惰性删除像查资料时顺手清掉过期文件：不查就不管，省事但不彻底；
  • 定期删除像每周五大扫除抽查：随机翻 20 个柜子，发现过期文件多就多翻几轮，但每轮最多干 25 分钟就收工；
  • 两者配合：平时顺手清 + 定期抽查清，垃圾基本留不住。

4. Redis 的缓存失效会不会立即删除？¶

一句话回答¶

不会。Redis 的过期删除策略是「惰性删除 + 定期删除」，到期不会马上删，要靠访问时删除或定期抽查删除。

展开讲¶

  • 惰性删除：不主动删，每次访问 key 时检测是否过期，过期才删；
  • 定期删除：每隔一段时间（默认每秒 10 次）随机抽 20 个 key 检查，删除其中的过期 key。

所以"缓存失效（过期）"和"缓存被删除"是两回事：过期是时间到了，删除要等惰性或定期策略来执行。

面试怎么答¶

直接答"不会"，然后补上两种策略的名字，再说一句"所以刚过期的 key 可能还在内存里待一小会儿"。

5. 那为什么我不过期立即删除？¶

一句话回答¶

因为到期立即删除对 CPU 不友好：过期 key 多时，删除会占用大量 CPU 时间，影响服务器响应速度和吞吐量。

展开讲¶

如果设计成"过期就立刻删"（定时删除策略），需要每时每刻扫描所有 key 的过期时间，并在到点的瞬间触发删除：

  • 在过期 key 比较多的情况下，删除过期 key 会占用相当一部分 CPU 时间；
  • 在内存不紧张但 CPU 时间紧张的情况下，把 CPU 花在删除"和当前任务无关"的过期键上，会拖慢正常请求的响应；
  • 万一到期时间扎堆（比如同时几千个 key 到期），一瞬间的删除风暴可能直接卡死 Redis。

所以 Redis 宁可让过期 key 多活一会儿（惰性 + 定期），也不搞"到点必删"——用一点内存浪费，换 CPU 的稳定。

面试怎么答¶

"到期立即删除需要频繁扫描+到点触发，过期 key 多时会抢占 CPU、拖慢正常请求，所以 Redis 选了惰性+定期，牺牲少量内存换 CPU 稳定。"
