08 分布式锁与大Key热Key¶

本章覆盖：分布式锁的实现原理与使用场景、大 Key 问题（是什么/缺点/怎么解决）、热 Key 问题（是什么/怎么解决）。

1. Redis 分布式锁的实现原理？什么场景下用到分布式锁？¶

一句话回答¶

分布式锁是分布式环境下控制某个资源同一时刻只能被一个应用使用的机制。Redis 用 SET 命令的 NX 参数实现"key 不存在才插入"来加锁，用 Lua 脚本保证解锁的原子性。

展开讲：什么场景用分布式锁¶

多台服务器（多个进程/应用实例）同时处理同一份数据时，需要保证同一时刻只有一个应用能操作。比如：

  • 多个服务实例同时扣减同一个商品库存；
  • 多个任务调度器同时执行同一个定时任务（防止重复执行）；
  • 分布式环境下对共享资源的并发控制。

Redis 本身就是多个客户端共享访问的存储系统，天然适合当"锁的存放地"，而且读写性能高，能扛住高并发的加锁/解锁。

展开讲：加锁原理¶

Redis 的 SET 命令有个 NX 参数（Not eXists，不存在才设置）：

  • key 不存在 → 设置成功 → 表示加锁成功；
  • key 已存在 → 设置失败 → 表示加锁失败（说明别人已经持有锁）。

加锁要满足三个条件：

  1. 原子性：加锁包含"读取锁变量、检查值、设置值"三个操作，必须原子完成 → 用 SET 命令带上 NX 选项一次搞定；
  2. 过期时间：锁必须设置过期时间，防止客户端拿到锁后异常挂掉，锁永远不释放（死锁）→ 用 EX/PX 选项设置过期时间；
  3. 唯一标识：锁的值必须能区分不同客户端，防止释放锁时误删别人的锁 → 每个客户端设置一个唯一值。

满足三个条件的命令：

SET lock_key unique_value NX PX 10000
  • lock_key：锁的 key；
  • unique_value：客户端生成的唯一标识（区分是谁的锁）；
  • NX：只在 lock_key 不存在时才设置；
  • PX 10000：锁 10 秒后自动过期（防止客户端异常导致锁不释放）。

展开讲：解锁原理（关键！为什么要 Lua）¶

解锁不能直接 del lock_key，要先判断锁是不是自己的（unique_value 匹配），是才删除——否则可能把别人刚抢到的锁删了。

判断 + 删除是两个操作，两个操作之间可能被插入别的命令 → 必须用 Lua 脚本保证原子性：

// 释放锁时，先比较 unique_value 是否相等，避免锁的误释放
if redis.call("get",KEYS[1]) == ARGV[1] then
  return redis.call("del",KEYS[1])
else
  return 0
end

Redis 执行 Lua 脚本时以原子方式执行，中间不会被其他命令打断。

展开讲：为什么是 Lua？其他脚本语言不行吗？¶

不是"必须用 Lua"，而是"Redis 只内嵌了 Lua 这一种脚本引擎"，并且脚本必须在 Redis 服务端原子执行才能解决竞态。

  1. Redis 服务端只内嵌 Lua。 Redis 内部只有 Lua 解释器，没有 Python / JavaScript / Ruby 等运行时。把其他语言的代码发给 Redis，它根本没有执行环境。所以不是"别的语言写不了逻辑"，而是"Redis 不认别的语言"。

  2. 原子性来自"在服务端内执行"，不是来自"脚本"本身。 如果在应用层用 Python/Go/Java 写一个"函数"，内部发多条 Redis 命令，那它仍然只是多条独立命令，不具备原子性——这正是要规避的竞态来源。真正的原子性来源是：脚本被 EVAL/EVALSHA 送进 Redis，由 Redis 单线程一口气执行完，中间不被其他命令打断。

所以 Lua 是 Redis 提供的唯一"服务端原子脚本"入口，不是因为 Lua 这门语言多特殊。

两个补充：

  • 加锁其实可以不用 Lua。 SET key token NX PX 本身就是一条原子命令（Redis 2.6.12+ 原生支持），Lua 主要用于解锁和续期。
  • Redis 7 之后有 Redis Functions，本质仍是 Lua，但把脚本管理、版本化做得更规范，推荐替代裸 EVAL。也可以直接换 etcd / ZooKeeper 这类自带 CAS（比较并删除）原生命令的方案。

完整流程总结¶

  • 加锁：SET lock_key unique_value NX PX 10000（一个命令，天然原子）；
  • 业务处理：执行需要互斥的逻辑；
  • 解锁：Lua 脚本（判断唯一值 → 删除），保证原子性。

展开讲：完整流程细化（续期、单实例局限、Redlock）¶

续期（看门狗）。 如果临界区执行时间可能超过锁的过期时间，需要用后台线程在锁过期前不断刷新过期时间，否则会出现"业务还没跑完锁就过期，别人抢到锁，自己业务结束后误删别人的锁"。续期也要带上"确认锁还是我的"的判断（通常还是用 Lua），否则会把别人的锁给续了。Java 的 Redisson 客户端就自带这种"看门狗"续期机制。

单实例的局限。 上面的流程都是单机 Redis。致命弱点：主节点刚写入锁就宕机、还没同步到从节点，从节点提升为主后锁就丢了，可能出现两个客户端同时持锁。

Redlock 算法（多实例）。 高可用场景下 Redis 官方提出 Redlock：用 N 个（通常 5 个）互相独立的 Redis 实例（不是主从集群），客户端依次向所有节点 SET NX PX 加锁，只有当大多数节点（≥ N/2+1）加锁成功、且总耗时小于锁的过期时间，才算加锁成功；解锁时向所有节点发送 Lua 解锁脚本。

注意：Redlock 有争议（时钟跳跃、GC 停顿等场景下仍可能失效）。业务需要强一致性保证时，优先考虑 etcd / ZooKeeper 这类基于共识协议、自带 CAS 的方案，而不是 Redis。

比喻¶

锁像厕所门牌：谁进去就把门牌挂"有人"（NX 设置成功），并写好自己的名字（unique_value）；出来时必须确认门牌上写的是自己的名字才摘牌（Lua 判断 + 删除），不然把下一个人误锁里面了。

2. Redis 的大 Key 问题是什么？¶

一句话回答¶

大 Key 是指某个 key 的 value 占用内存特别大，导致 Redis 性能下降、内存不足、数据不均衡、主从同步延迟等问题。

展开讲：多大的数据算大 Key？¶

没有固定的判别标准，常见的经验值：

  • 字符串类型的 value 占用空间 大于 1M；
  • 集合类型（List/Hash/Set/Zset）的元素数量超过 1 万个。

但标准要根据实际业务评估，例如：

  • 高并发、低延迟场景：10KB 就可能算大 Key；
  • 低并发、高容量环境：大 Key 界限可能在 100KB。

面试怎么答¶

先给经验值（1M / 1 万个元素），再补一句"没有绝对标准，取决于业务场景和性能指标"——显得你理解深入而不是死背书。

3. 大 Key 问题的缺点？¶

一句话回答¶

六个危害：内存占用过高、性能下降、阻塞其他操作、网络拥塞、主从同步延迟、数据倾斜。

展开讲¶

  1. 内存占用过高：大 Key 占大量内存 → 可能触发内存淘汰策略；极端情况内存耗尽、Redis 实例崩溃。

  2. 性能下降：大 Key 导致内存碎片增加；读写、删除大 Key 都消耗更多 CPU 时间和内存资源。

  3. 阻塞其他操作：某些大 Key 操作会导致 Redis 阻塞。例如用 DEL 删除大 Key 时，Redis 一段时间内无法响应其他客户端请求，影响响应时间和吞吐量。

  4. 网络拥塞：每次获取大 Key 产生的网络流量大，可能打满机器或局域网带宽，波及其他服务。举例：一个大 Key 占 1MB，每秒访问 1000 次，就有 1000MB/秒 的流量。

  5. 主从同步延迟：大 Key 占用内存多，主从同步要传大量数据 → 网络传输延迟增加，影响数据一致性。

  6. 数据倾斜（集群模式）：某个数据分片的内存使用率远超其他分片，内存资源不均衡；还可能达到 maxmemory 上限导致重要 key 被逐出，甚至内存溢出。

比喻¶

大 Key 像超大行李箱：拖着它走路慢（性能差）、占地方（内存高）、过安检卡住后面所有人（阻塞）、搬上搬下累坏搬运工（网络/主从同步）。

4. Redis 大 Key 如何解决？¶

一句话回答¶

四个方向：拆分（把大 Key 拆小）、清理（不合适的挪走并异步删除）、监控（内存水位报警）、定期清理过期数据。

展开讲¶

1. 对大 Key 进行拆分

例如：把含有数万成员的一个 HASH Key，拆成多个 HASH Key，每个 Key 成员数控制在合理范围。集群架构下，拆分还能显著改善数据分片间的内存平衡。

2. 对大 Key 进行清理

把不适合放 Redis 的数据挪到其他存储（如数据库、对象存储），并在 Redis 中删除。注意：要使用异步删除（unlink），否则 del 会阻塞主线程。

3. 监控 Redis 内存水位

设置合理的内存报警阈值，例如： - Redis 内存使用率超过 70% 报警； - Redis 内存1 小时内增长率超过 20% 报警。

4. 对过期数据进行定期清理

大量堆积的过期数据会形成大 Key。例如：HASH 类型持续增量写入大量数据、却忽略了数据的时效性。用定时任务定期清理失效数据。

面试怎么答¶

四个点报出来，重点强调"删除用 unlink 异步删"（呼应线程模型章：del 在主线程执行会卡）。

5. 什么是热 Key？¶

一句话回答¶

热 Key 是被请求频率极高的 key——某个 key 的访问量占整个 Redis 的很大比例，导致它所在的节点压力过大。

展开讲：怎么判定热 Key（三个信号）¶

信号 1：QPS 集中在特定 Key

Redis 实例总 QPS 是 10,000，而其中一个 Key 每秒访问量达到 7,000——占 70%，这就是热 Key。

信号 2：带宽使用率集中在特定 Key

对一个拥有上千个成员、总大小 1MB 的 HASH Key，每秒发送大量 HGETALL 操作——单个 key 就把带宽打满。

信号 3：CPU 使用时间占比集中在特定 Key

对一个拥有数万个成员的 ZSET Key，每秒发送大量 ZRANGE 操作——CPU 时间都花在它身上。

比喻¶

热 Key 像网红景点：所有人都挤去同一个地方，其他地方没人去，那个景点（节点）被挤爆，其他景点闲置。

6. 如何解决热 Key 问题？¶

一句话回答¶

两种主流方案：集群中复制热 Key 分散到多个分片（解决写/读热），读写分离架构加从节点（解决读热）。

展开讲：方案一——集群中对热 Key 进行复制¶

集群架构下，热 Key 的迁移粒度问题导致无法把请求分散到其他数据分片（一个 key 只能在一个分片上）→ 单个分片压力降不下来。

做法：把热 Key 复制成多份，迁移到不同分片：

  • 例如热 Key foo 复制出 3 个内容完全一样的 Key：foo2、foo3、foo4；
  • 把这 3 个 Key 迁移到其他数据分片；
  • 请求被随机分摊到 4 个分片，单个分片压力大降。

注意：这是"以空间换压力"的取巧方案，需要处理好多份数据的一致性（比如热 Key 是只读数据才适合复制）。

展开讲：方案二——读写分离架构¶

如果热 Key 的压力来自读请求：

  • 把实例改造成读写分离架构（主节点写、从节点读）；
  • 甚至可以不断增加从节点分担读压力。

缺点（要权衡）：

  • 增加业务代码复杂度：读写要走不同连接；
  • 增加集群架构复杂度：多个从节点需要转发层（Proxy、LVS）做负载均衡；
  • 从节点数量增加后故障率也增加，监控、运维、故障处理挑战更大。

面试怎么答¶

区分读热和写热：读热 → 读写分离加从节点；写热/单分片压力大 → 集群里复制热 Key 分散。最后补一句两者的权衡（复制一致性 / 架构复杂度）。

7. 大 Key 和热 Key 一起记¶

大 Key 热 Key
定义 value 占用内存大（>1M 或 >1 万个元素） key 被访问频率极高（QPS/带宽/CPU 集中）
核心问题 内存、阻塞、网络、同步、倾斜 单分片压力过大、热点集中
解决思路 拆分、清理（异步删）、监控、定期清理 复制分散（写热）、读写分离（读热）
比喻 超大行李箱 网红景点

面试时如果两个一起问，先各下定义（"大是体积大、热是频率高"），再分别给方案，最后能补一句"集群里大 Key 会导致数据倾斜，热 Key 会导致单分片压力大"就完美收尾。
